## 1. Общие папки

OpenMediaVault служит источником настроек общего доступа. Клиенты Windows и Linux используют Samba (SMB), не обращаясь к ext4 или ZFS непосредственно.

На томе 1 ТБ предусматриваются области `shared`, `movies`, `music` и при необходимости `downloads/complete`. На основном ZFS расположен единый каталог `data`.

Имена `sergey`, `sveta`, `danya` берутся из [общего каталога](../../../users.yaml). [access.yaml](../access.yaml) задаёт режим `named_users` с обязательной авторизацией и чтением/записью для `shared`, `movies`, `music`, `data`.

Samba требует имя пользователя и единый пароль из защищённого файла состояния Infra Manager. Гостевой вход выключен, так что Windows может сохранить обычные SMB-учётные данные. OMV/SSH/Authelia продолжают использовать отдельную авторизацию. Регистрация общих ресурсов выполняется штатной базой OMV через `omv-confdbadm` и `omv-salt`; `/etc/samba/smb.conf` напрямую не изменяется.

При `deploy nas` Ansible создаёт отсутствующих Linux/Samba-пользователей, не меняет системные пароли существующих пользователей, передаёт защищённый Samba-пароль через stdin и применяет ACL общей группы `nas-smb` к корням папок. OMV синхронизирует `guest: no` / `readonly: false`. Существующие вложенные ACL не перезаписываются и могут требовать отдельной проверки.

## 2. Торрент-клиент

Выбран `qBittorrent` с веб-интерфейсом, в изолированном контейнере Docker.

- Файлы программы и её настройки располагаются в устойчивой области системного SSD.
- Незавершённые загрузки записываются на том 1 ТБ в `downloads/incomplete`.
- Завершённые загрузки размещаются на том 1 ТБ в `downloads/complete` или перемещаются в соответствующие каталоги мультимедиа.
- При недоступности тома 1 ТБ контейнер не запускается и не начинает записывать данные на системный SSD.
- Порт веб-интерфейса, режим доступа и учётные данные задаются в конфигурации службы до развёртывания; не использовать общеизвестные пароли.

В машинной конфигурации том 1 ТБ закрепляется по UUID. Служба
`nas-qbittorrent.service` проверяет этот UUID при каждом запуске; контейнеру
Docker запрещено самостоятельно запускаться при отсутствии диска. В текущей реализации закреплена сборка
`lscr.io/linuxserver/qbittorrent:5.2.4_v2.0.15-ls479`;
до применения на физическом NAS нужно проверить её совместимость и запуск.

## 3. Централизованная настройка

NAS подключается к Infra Manager по SSH как **внешняя физическая машина**, без OpenTofu-ресурса PVE. Оператор запускает `infra-manager deploy nas` на PVE, передавая выполнение в 910; для NAS не требуется отдельное задание Semaphore.

Развёртывание описывается в `provision.yaml`, `backup.yaml`, `storage.yaml` и `access.yaml`.
Штатная команда `deploy nas` запускает один playbook `automation/ansible/playbooks/deploy-nas.yml`
с ролью `nas`. Сначала идёт этап `base` (Debian/OMV/Docker/ZFS), затем после
независимой проверки UUID, GUID и реальных mountpoint применяется заявленный
набор компонентов (`urbackup_server`, `urbackup_client`, `apps`, `smb`).
Python остаётся транспортом SSH/OpenBao и предохранителем хранения, но не
содержит отдельных функций установки приложений.

Файл `infrastructure/hosts/nas/status.yaml` задаёт штатные проверки
приложений в том же формате, что статусы гостей. Финальная карточка
`deploy nas` / `status nas` использует `provision.yaml`: выводит
адреса, логины и только явно доступные через доверенный PVE терминал пароли.
Действующие пароли OMV/qBittorrent не сбрасываются и не угадываются.
UrBackup GUI пока связан с loopback NAS; для него требуется SSH-туннель.
Открытие HTTP-админки в LAN является отдельным решением по безопасности.

Повторное применение конфигурации должно быть безопасным: существующие каталоги и пользовательские файлы остаются на месте. Новые служебные каталоги создаются только после проверки их родительской файловой системы.

Infra Manager должен уметь проверить доступность Samba, состояние qBittorrent и права служебных каталогов. Работоспособность NAS не должна зависеть от постоянной доступности 910.


Резервирование NAS — отдельная автономная служба UrBackup Server в Docker, не являющаяся частью qBittorrent или Samba. Полная локальная спецификация его установки, хранения, согласованных копий и восстановления описана в [backup.md](backup.md).

## 4. Установка и восстановление программ

Infra Manager не устанавливает Debian или OpenMediaVault вместо оператора. Он проверяет вручную установленную OMV 8 и должен устанавливать OMV-Extras, необходимые пакеты и поддержку ZFS повторяемым способом, проверять версии и совместимость перед применением. Обновления и изменение ядра не объединяются с разрушительными операциями над хранилищами. При перезагрузке из-за смены ядра сначала подтверждается возврат SSH и доступность OMV. Только затем выполняются проверки дисков, настройка Samba и qBittorrent.

После переустановки ОС службы восстанавливаются **после** проверки и подключения существующих файловых систем. Отсутствие тома не должно приводить к записи загрузок или резервных копий на системный SSD.

## Декларативный состав служб и общих папок

`infrastructure/hosts/nas/provision.yaml` описывает компоненты,
операторские URL и Samba shares (имя, роль физического тома, каталог).
Сценарий `infra-manager deploy nas` по-прежнему применяет только два
безопасных этапа: базовые зависимости и проверенный сервисный этап,
после независимого подтверждения физического хранилища. Список компонентов
внутри второй фазы задаёт YAML; Ansible разрешает только именованные задачи
роли `nas`. Для `urbackup_client` обязателен ранее включённый
`urbackup_server`. Пропущенный компонент не перенастраивается и не
объявляется работающим в `status nas`, но его старое состояние не удаляется.

`status.yaml` содержит связанные с компонентами проверки, строго
валидируется схемой и исполняется общим механизмом статуса гостей.
Итоговая карточка перечисляет объявленные активные веб-сервисы, а не
встроенный в Python список. Пароль администратора UrBackup сохраняется root/0600 только на физическом NAS
и не выдумывается 910; изменения или сброса паролей OMV/qBittorrent нет.

Согласование папок OMV теперь выполняет `automation/ansible/roles/nas/tasks/omv-shares.yml` стандартными модулями Ansible через `omv-confdbadm`. Роль проверяет конфликты имён и каталогов до первой записи, повторно читает реальные UUID, назначенные OMV, и сохраняет чужие поля существующих записей. Устаревший Python-сценарий `nas-omv-shares.py` удалён из репозитория. Применение на живом NAS ещё не испытано.

Проверки GUID, аппаратных дисков, защита ZFS-снимков и автовосстановление
UrBackup также остаются специализированными защитными исполнителями.

## Уточнение декларативной конфигурации

В `provision.yaml` объявлены не только активные компоненты, но и
`deployment.dependencies`. Сервер UrBackup обязан предшествовать его
локальному клиенту; зависимость нельзя удалить, отключив проверку в YAML.
Независимые компоненты могут быть выключены или переставлены без требования
фиксированного списка из четырёх служб.

Параметры среды qBittorrent (часовой пояс, порт torrent, список каталогов
загрузок) теперь задаются в `services.qbittorrent.runtime` и применяются
шаблоном Compose и задачами Ansible. Веб-порт 8080 намеренно закреплён
контрактом схемы, пока не реализовано безопасное согласованное изменение
адреса и его проверки в `status.yaml`.

`status.yaml` также задаёт `health.disk_usage_warning_percent` для
предупреждений о заполнении физического тома. Права в `access.yaml`
сверяются с именами ресурсов из `provision.yaml`, а не с параллельным
списком в Python. **Это также механизм применения именных прав доступа**: список сетевых
папок сверяется с `provision.yaml`, на опубликованные корневые каталоги
назначается ACL группы `nas-smb`, а OMV переключает соответствующие
SMB-ресурсы в `named_users/read_write` с отключением Guest only.
Существующие вложенные ACL не изменяются рекурсивно;
резервные тома не публикуются.

Имена ZFS-пулов для проверок резервирования берутся из подтверждённого
`storage.yaml` и сверяются с фактическими GUID/источниками, вместо второго
независимого списка имён в управляющем Python. Названия существующих архивов
UrBackup и их структура при этом не переименовываются.

## Декларативные системные зависимости и адреса

В `provision.yaml` перечислены четыре категории пакетов: `system.packages.diagnostics`,
`omv_prerequisites`, `omv_extensions`, `docker`. Каждый пакет ограничен
проверяемой схемой; Ansible использует `apt state: present`, то есть устанавливает
недостающее, **не удаляет** пакеты при отключении компонента и не запускает
обновление всех установленных пакетов. Сохранены существующие проверки репозиториев,
DNS, DKMS и безопасный отказ до любых операций над HDD.

`system.services.smart` и `system.services.containers` задают службы,
которые должны работать и автоматически запускаться после перезагрузки.
В `status.yaml` разрешены только проверенные типизированные ссылки
`unit_from`, `container_from`, `port_from` на параметры
`provision.yaml`. Имя контейнера qBittorrent, его порт и URL теперь
исходят из единого описания `services.qbittorrent`; при выключенном компоненте
проверки пропускаются без удаления пользовательских данных.

Расписание и значения `retention.keep_daily`/`keep_weekly` из
`backup.yaml` остаются **требованием**, а не подтверждённой политикой
UrBackup Server. Сервер поддерживает отдельное архивирование файловых снимков,
поэтому нельзя просто считать `max_file_incr=7` эквивалентом «7 ежедневных
плюс 4 еженедельных». Для реального применения этой части нужен
проверенный клиентский API, контроль существующих настроек и тест на живом NAS;
пока утверждать её исполнение нельзя.

## Выключенные компоненты без потери данных

`provision.yaml: deployment.components` задаёт желаемый состав сервисов.
`deployment.managed_units` перечисляет только известные unit-файлы systemd
(службы и таймеры), закреплённые схемой. При фазе `services` Ansible
выключает автозапуск и останавливает **только существующие** unit-файлы
компонентов, исключённых из декларации. Для локального UrBackup сначала
останавливается таймер клиента и его служба, затем таймер сервера и сервер.

Отключение не удаляет пользователей, конфигурацию, файлы Docker Compose,
образы, тома, архивы или ZFS-пулы. Обратное включение компонента снова
выполняет его обычную роль Ansible. Для всех включённых компонентов
предусмотрены `systemd_service: enabled: true, state: started`; проверки
`status.yaml` используют те же объявленные unit-имена, но пропускают
компоненты, которых нет в `deployment.components`.

Перед отключением `smb` или `urbackup_server` нужно убедиться, что
они не используются другими машинами; это намеренная остановка службы,
а не скрытая миграция данных. На физическом NAS сценарий отключения
ещё не испытан, поэтому первое применение следует контролировать.
