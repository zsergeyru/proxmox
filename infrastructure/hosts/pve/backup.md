# Резервное копирование PVE-хоста

## Фактическое состояние на 2026-09-12

В Proxmox уже существует хранилище:

```text
name: backup
type: dir
path: /mnt/pve/backup
content: backup
```

Названия параметров оставлены без перевода, поскольку это реальные поля Proxmox.

Физический носитель — USB Kingston DataTraveler около `58 GiB`, файловая система `ext4`.

На момент снимка:

```text
всего:    ~56.5 GiB
занято:   ~19.7 GiB
свободно: ~33.9 GiB
```

Таким образом USB-хранилище резервных копий уже фактически используется, но не считается единственным или окончательным местом хранения копий.

## Что уже есть

- отдельное хранилище Proxmox `backup`;
- USB-носитель отделён от основного NVMe;
- у VM `100` существует снимок `good_restore`;
- ранее создавалась полноценная резервная копия HAOS VM `100`.

Снимок состояния не считается заменой полноценной резервной копии.

## Принятое ближайшее решение

Планируется добавить отдельное SMB/CIFS-хранилище на обычном компьютере и использовать его как основную внешнюю копию резервных данных Proxmox.

Текущее USB-хранилище при этом сохраняется как дополнительная локальная копия и аварийный вариант.

Важно: SMB-хранилище пока только запланировано и ещё не является частью наблюдаемого состояния этого хоста. Компьютер с общей папкой должен иметь стабильный IP и быть включён во время задания резервного копирования.

Отдельный NAS и Proxmox Backup Server на этом этапе не вводятся.

## Резервный SSD 240 ГБ (актуальное уточнение)

Состояние разметки и файловой системы резервного SSD пока **не проверено**. Он может быть неразмеченным, содержать NTFS либо другие данные. Исторический снимок оборудования не следует трактовать как текущее подтверждение. Перед подготовкой необходимы безопасное чтение модели, серийного номера, разделов и сигнатур, затем отдельное подтверждение пользователя. Ни `deploy 910`, ни план резервирования не должны автоматически очищать SSD.

Машинное намерение хранится в [`backup.yaml`](backup.yaml); пока идентификаторы носителей не подтверждены, запись архивов блокируется. Программа устанавливается автоматически вместе с обновлением 910, но её реальное состояние на PVE ещё нужно проверить.

## Что нужно проверить

В снятом `/etc/fstab` отсутствовала запись для USB-раздела `/mnt/pve/backup`. Нужно отдельно выяснить, каким механизмом накопитель монтируется после загрузки и гарантированно ли хранилище возвращается после перезагрузки.

До проверки нельзя считать автоматическое монтирование USB полностью задокументированным и воспроизводимым.

Также остаются открытыми задачи:

- создать и проверить SMB/CIFS-хранилище на компьютере;
- определить расписание резервного копирования;
- определить сроки хранения копий на SMB и USB;
- определить, какие гостевые системы и постоянные данные копируются обязательно;
- выполнить практическую проверку восстановления из резервной копии;
- позднее решить, нужен ли отдельный NAS или Proxmox Backup Server.

Общая политика резервного копирования проекта находится в [`../../../docs/600-storage/610-backup.md`](../../../docs/600-storage/610-backup.md).

## Программа резервирования PVE и 910

В репозитории подготовлены `backup.yaml`, безопасная проверка SSD,
внутренние программы согласования и два зашифрованных restic-хранилища,
согласованные снимки SQLite/Raft, архивы VM 100 и выключенное до проверки расписание копирования. Проверка готовности
запускается автоматически после `infra-manager deploy 910`. Наличие реализации в Git не означает, что она установлена на
физическом PVE или что уже создана новая копия.

Порядок развёртывания, подтверждений, записи ключа на независимый носитель
и пробного восстановления описан в
[840-pve-backup.md](../../../docs/800-operations/840-pve-backup.md).

## Программа копирования состояния 140

Исполняемый код находится в [`scripts/backup/backup-140.py`](../../../../scripts/backup/backup-140.py).
Этот каталог хранит описание PVE, а не сценарии исполнения. Для резервирования 140 используются две заранее подготовленные зашифрованные цели; автоматическое расписание пока не настроено.
