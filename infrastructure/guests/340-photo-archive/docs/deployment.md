# Подготовка развёртывания 340

## Требуемое состояние

Гость 340 разворачивается обычной командой `infra-manager deploy 340`.
Перед Ansible общий механизм на PVE подготавливает **два независимых постоянных
тома в существующем LVM-thin `pve/data`**:

| Том PVE | Размер | Каталог PVE | Подключение в 340 |
| --- | ---: | --- | --- |
| `photo_archive_data` | 180 ГиБ | `/mnt/bindmounts/photo-archive/data` | `mp0: /srv/photo-archive`, только чтение |
| `photo_archive_state` | 60 ГиБ | `/mnt/bindmounts/photo-archive/state` | `mp1: /mnt/persistent-state`, чтение и запись |

Размеры, имена и пути заданы в `provision.yaml` (раздел `pve_storage`).
Оба тома находятся вне системного раздела PVE и отдельно от корневого
диска LXC 340 (16 ГБ). Том данных содержит `originals`; том состояния —
PostgreSQL, служебные файлы Immich и секреты. Исходные фотографии в 340
доступны только для чтения; загрузка с Windows будет выполняться на стороне
хранилища PVE.

Сценарий PVE-only, запускаемый общим механизмом развёртывания, создаёт
недостающие логические тома, форматирует **только созданные в этом запуске**,
подключает файловые системы через `/etc/fstab`, устанавливает `mp0/mp1`
и проверяет реальное подключение внутри гостя. При изменении подключений
запущенный LXC корректно останавливается и запускается снова. При повторном
запуске тома и содержимое не переформатируются.

**Защита данных:** если имя тома уже занято, но размер/файловая система
не соответствуют описанию, если каталоги содержат посторонние данные
или заняты другие `mp0/mp1`, процедура прекращается с ошибкой. Она никогда
не удаляет тома, не переименовывает фотографии и не очищает базу.
Удаление LXC **не означает** удаление внешних томов; удалять такие тома
можно только отдельной осознанной операцией на PVE.

Адрес определяется общей адресацией гостей. Порт Immich: 2283.
`local-lvm` использует тонкое выделение места: номинальные размеры томов
не являются гарантией фактически свободного пространства при заполнении
пула другими машинами. Контролировать заполнение `pve/data` обязательно.

## Первое развёртывание и повторная проверка

1. Проверить фактическую доступность места: `pvesm status` и `lvs`.
2. Выполнить `infra-manager deploy 340` на PVE.
3. Проверить `pct config 340 | grep '^mp[01]:'` и
   `pct exec 340 -- mountpoint /srv/photo-archive`,
   `pct exec 340 -- mountpoint /mnt/persistent-state`.
4. Проверить службы Immich и резервирование базы.

Для хранения томов **не использовать** обычные каталоги на `/`: там
расположен системный раздел PVE, а `local-lvm` — отдельный пул.
Исходный каталог `/srv/photo-archive/originals` при первом запуске пуст;
сама загрузка примерно 125 ГБ фотографий будет отдельной задачей.

Ни привязанные каталоги, ни независимые тома автоматически не резервируются
вместе с обычной резервной копией LXC. Необходимо отдельно резервировать
оба тома, особенно PostgreSQL и оригиналы. При полном диске `backup`
архив пока не защищён резервной копией.

## Ограничения текущей подготовки

Выполнено автоматическое создание постоянных томов и подключений.
Остаются самостоятельными задачами:
- перед первым производственным запуском закрепить проверенную версию Immich
  вместо канала `v3`;
- перенести исходные секреты Immich в OpenBao или обеспечить их независимую
  резервную копию;
- испытать Compose, API-only режим и запрет доступа к PostgreSQL/Redis извне;
- организовать защищённый сетевой доступ работника Windows к медиаданным,
  базе и очереди без публикации служб в интернет;
- проверить работу без Windows, добавление внешней библиотеки,
  резервирование и восстановление.

Предварительная память LXC — 4 ГБ; достаточность подтвердить измерениями.
Для автоматического первоначального создания нужен действующий закрытый
PVE-only доступ из 910: API-токен OpenTofu не может самостоятельно
создать такие подключения каталогов с нужными полномочиями.

## Проверки при вводе

Сначала испытать 100–200 фотографий, затем подтвердить доступ по API и просмотр, запуск и перезапуск PostgreSQL, Redis, создание индексов, сетевой доступ с Windows, остановку фонового работника без потери галереи, реальное потребление памяти и процесс обновления.
