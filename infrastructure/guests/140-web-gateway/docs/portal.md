# Домашняя и административная страницы

**Тип:** локальная спецификация службы
**Статус:** реализовано в Git, проверка на действующем LXC ещё требуется.

## 1. Назначение и доступ

Гость 140 обслуживает два веб-раздела без Homarr и без отдельной базы домашней страницы:

| Адрес | Доступ | Назначение |
|---|---|---|
| `https://home.zsergey.ru/` | Любой вошедший пользователь после пароля и второго фактора Authelia | Ссылки на включённые службы |
| `https://home.zsergey.ru/admin` | Только группа `admins` **и** доверенная сеть/VPN | Пользователи, домены, список гостей |
| `https://home.zsergey.ru/api/admin/*` | Те же ограничения, что для `/admin` | Закрытые действия и данные |
| `https://auth.zsergey.ru` | Публичный HTTPS, вход через Authelia | Пароль и Google Authenticator |

Сама домашняя страница никогда не получает пароли, секреты Caddy и служебные ключи. На неё Caddy пропускает пользователя только после успешной проверки Authelia; в браузере не создаётся собственный сеанс.

Доверенные сети перечислены в `provision.yaml` как `web_gateway.caddy.private_networks`. Пока указан `192.168.0.0/16`; VPN должен давать адрес из разрешённой сети либо его подсеть требуется явно добавить. Одна лишь принадлежность к `admins` **не** разрешает вход извне. Настройки Keenetic должны сохранять настоящий адрес клиента: если весь внешний трафик приходит в 140 с локального IP маршрутизатора, проверка сети теряет смысл и публикацию административной страницы необходимо остановить.

## 2. Развёртывание и сохранность

`infra-manager deploy 140` устанавливает Caddy и Authelia в Docker, две страницы, сценарий просмотра приложений и закрытую системную службу на Unix-сокете. Кнопки управления используют ранее созданный внутренний обработчик гостя; новые публичные порты не появляются. Гость 910 не содержит индивидуальных правил страниц.

Первое развёртывание создаёт пользователя `admin`, постоянные ключи и файл маршрутов только если их нет. Повторное развёртывание не перезаписывает пользователей Authelia, второй фактор, сохранённые домены и сертификаты.

При обновлении с прежней версии только старые назначения `home.zsergey.ru` и `check.zsergey.ru` меняются с `homarr:7575` на внутреннюю домашнюю страницу Caddy; остальные строки `routes.yaml` сохраняются. Старый контейнер Homarr убирается посредством `docker compose up -d --remove-orphans` **без** `down -v`. Его база и секреты остаются на `mp0` на случай отката, но новая домашняя страница их не читает. Автоматически удалять старые пользовательские данные запрещено.

Воспроизводимые файлы:

- `/etc/web-gateway/portal/portal-home.html`, `portal-admin.html`, `portal.css`, `portal.js`;
- `/usr/local/lib/web-gateway/portal-web.py` — только закрытый Unix-сокет;
- `/var/lib/web-gateway/management/catalog/apps.json` — список разрешённых включённых приложений;
- `/var/lib/web-gateway/management/catalog/guests.json` — описание гостей из Git.

Файлы `apps.json` и `guests.json` обновляются в рамках обычных `deploy 140` и `sync 140`. Изменение домена через административную форму также сразу обновляет домашние приложения. Включение маршрута само по себе не подтверждает, что целевое приложение действительно работает.

Перед формированием нового Caddyfile развёртывание проверяет **весь** сохранённый `management/routes.yaml` — включая поддомены, созданные из панели. Проверка использует только чтение постоянного тома и правила из Git, не сбрасывает пользовательские маршруты. При повреждении данных развёртывание прерывается до применения Caddy. Изменённые через панель домены должны сохраняться после повторного `infra-manager deploy 140`.

## 3. Управление пользователями

Раздел **Пользователи** показывает карточки с именем, логином, группами и
признаком разрешённого входа. Есть поиск и отдельные кнопки:
«Изменить», «Новый пароль», «Проверочный код», «Сбросить TOTP»,
«Включить/Отключить», «Удалить» (кроме первоначального admin).
Создание и изменение открывают окно с полями и выбором групп через флажки.
При редактировании логин не меняется; последний действующий администратор
защищён от отключения и лишения прав.

Временный пароль после создания или сброса и проверочный код Authelia
показываются полностью с кнопкой копирования. В карточках также виден
факт подключения TOTP и WebAuthn, а для последнего проверочного кода — оставшееся
время его действия. Для обновления предусмотрена отдельная кнопка. Обычные пользовательские
пароли после выдачи не сохраняются в открытом виде: в файле Authelia
находятся только хеши. Для первоначального admin используется отдельный
сохранённый операторский пароль. Дополнительных подтверждений просмотра
кода нет. Наличие проверочного кода не означает, что TOTP уже подключён.

Удаление пользователя сначала запрашивает удаление его зарегистрированных
TOTP и WebAuthn средствами Authelia. Если очистить факторы не удалось,
учётная запись остаётся сохранённой; случайное повторное присвоение логина
чужому второму фактору недопустимо. Подтверждение требуется только для
существенных действий (сброс пароля, отключение, удаление, сброс TOTP).
Домены можно добавлять, редактировать и удалять отдельными кнопками.
 Включение выполняется переключателем, без выбора технического действия из списка.
 Служебные маршруты защищены от удаления и смены назначения. Пользовательские
 поддомены сохраняются на постоянном томе, не теряются после повторного развёртывания,
 и проходят `caddy validate` до `reload`. При ошибке старые правила возвращаются.
 Текущий просмотр гостей Proxmox остаётся без управляющих действий.

Интерфейс адаптирован для телефона, поддерживает светлую и тёмную тему.
Выбранная тема сохраняется в браузере. При создании домена потребуются
его имя, название и адрес в домашней сети; изменения не требуют ручных команд.

## 4. Проверка безопасности

Caddy проводит проверку Authelia на каждом запросе страниц, скриптов и данных. Для `/admin` и `/api/admin` сначала проверяется исходный адрес соединения, затем Authelia требует группу `admins` и второй фактор; общее правило для остальных поддоменов не может разрешить этот доступ благодаря дополнительному явному `deny`.

Все изменения из браузера принимают только запросы JSON с точным источником `https://home.zsergey.ru` и служебным заголовком. Только после этих проверок отдельный обработчик на Unix-сокете использует сохранённый закрытый ключ; сам ключ в браузер не передаётся. HTML не вставляет содержимое полей как разметку, а скрипты разрешены строгими заголовками страницы. Скрытие кнопок само по себе не считается защитой.

Для приёмки после `deploy 140` проверить:

1. Внешний запрос без входа не выдаёт содержимое `/` и `/api/apps`.
2. После двух факторов семейный пользователь видит ссылки приложений, но получает отказ на `/admin` и `/api/admin/*` даже из дома.
3. Администратор из Интернета получает запрет на `/admin` и `/api/admin/*`, несмотря на действующую сессию.
4. Администратор из домашней сети видит пользователей, домены и гостей; изменяющие действия требуют подтверждения. Поддельный межсайтовый запрос отклоняется.
5. Создать выключенный поддомен с внутренним адресом, включить его, убедиться, что страница отображается в списке приложений; повторить `deploy 140` и убедиться, что адрес, режим доступа и состояние сохранились. Для проверки открытия по имени сначала настроить DNS.
6. Проверить сохранность паролей, второго фактора и доменов после повторного `deploy 140`, отсутствие контейнера Homarr и сохранение прежнего тома. Удалить тестового пользователя без подключённого TOTP, затем проверить удаление пользователя с фактором; при ошибке очистки учётная запись не должна исчезать.
7. Убедиться, что в случае неверного внутреннего адреса или ошибки проверки Caddy сохраняется прежняя конфигурация, а повреждённая SQLite-база не отображается как отсутствие TOTP.
8. Не включать Immich, HA и AI до проверки самих служб и их входа; не выдавать состояние «работает» только по наличию записи Git.
