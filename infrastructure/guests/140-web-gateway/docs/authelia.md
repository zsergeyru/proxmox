# Authelia — общий вход и второй фактор

**Тип:** локальная спецификация службы  
**Статус:** целевое состояние

Authelia — единый источник входа для домашних веб-приложений, поддерживающих OpenID Connect (OIDC), и средство проверки второго фактора. Предусмотрены 3–4 пользователя и 2–3 группы; ими управляют на закрытой странице `https://home.zsergey.ru/admin`.

## 1. Устройство входа

### 1.1. Адрес и клиенты

Authelia доступна пользователям через `https://auth.zsergey.ru` за Caddy; внутренний адрес контейнера и порт 9091 доступны только внутри сети Docker 140. Внешний доступ к внутреннему порту не открывается.

Для Immich и Open WebUI настраиваются отдельные клиенты OIDC с точными адресами возврата, полученными из настроек соответствующих приложений. Для клиентов допускаются `openid`, `profile`, `email` и `groups` по необходимости. Вход и выдача прав проверяются в самом приложении, а не только наличием ссылки на домашней странице.

У разных приложений сохраняются собственные сведения о пользователях и разрешениях. SSO устраняет повторный ввод пароля, но не обязан отменять внутренние права приложений.

### 1.2. Защита и группы

Для опубликованных приложений требуется пароль и второй фактор: TOTP в приложении-аутентификаторе; при поддержке может применяться WebAuthn/ключ доступа. У каждого пользователя свой второй фактор и резервные коды, которые нужно сохранить отдельно.

Первоначальный TOTP создаётся штатной командой Authelia **только для администратора `admin`**. Пароль администратора остаётся в защищённом хранилище, а QR и временная копия URI находятся в `/var/lib/web-gateway/authelia/totp-setup/`. Они никогда не печатаются в журналах и не публикуются напрямую через Caddy.

При первом `deploy 140` открывается `https://auth.zsergey.ru/totp-setup` **только из сети `192.168.0.0/16`**, без ввода дополнительного пароля или одноразового ключа. Доступ идёт через Caddy и временный Unix-сокет: отдельный сетевой порт не создаётся, обработчик отключается через **15 минут**. Пользователь сканирует QR, вводит код из Google Authenticator и нажимает «Подтвердить и удалить QR-код». После правильного кода удаляются QR и временный URI; TOTP в SQLite сохраняется. Кнопка «Закрыть без подтверждения» закрывает страницу, но сохраняет закрытый QR для следующего `deploy`. При истечении 15 минут страница также закрывается; незавершённая настройка может быть открыта повторным `deploy 140` без перевыпуска ключа.

Изображение QR и URI являются секретами. Временная страница без пароля сознательно допускается только на короткое время из домашней сети. Не перенаправлять путь `/totp-setup` в Интернет через другой прокси. Для работы URL нужен действительный HTTPS-сертификат. После подтверждения удаляется именно временный QR; нельзя удалять регистрацию TOTP из SQLite.

При повторном развёртывании подтверждённый TOTP не меняется, а страница не запускается. Если прежний QR уже удалён, но TOTP существует, повторный `deploy` не создаёт новый секрет. Для явного сброса используется отдельная административная операция.

Группы первого этапа:

| Группа | Назначение |
|---|---|
| `admins` | административные разрешения и семейные приложения |
| `family` | фотографии, домашняя страница, домашняя автоматика |
| `guests` | только явно разрешённые приложения |

Правило по умолчанию — запрет, если разрешение не назначено явно. Для защиты новых поддоменов, подключённых через Caddy, предусмотрено отдельное правило второго фактора `*.zsergey.ru`. Сам Caddy решает, какие маршруты публичны, какие проверяются через `forward_auth`, а какие доступны только из внутренней сети. Для `auth.zsergey.ru` дополнительная проверка Caddy запрещена, иначе невозможно открыть саму форму входа. Членство в нескольких группах допустимо. Права на домашней странице не подменяют права на самих приложениях.

Интерфейсы Proxmox, OpenBao и infra-manager нельзя делать публичными ради удобной плитки на домашней странице; они доступны только из доверенной домашней сети либо по отдельному защищённому каналу.

Home Assistant не имеет штатного OIDC-входа; способ подключения необходимо проверить отдельно. Пока это не сделано, сохраняется собственная авторизация Home Assistant. Нельзя объявлять единый вход полностью готовым лишь потому, что открывается домашняя страница.

## 2. Пользователи и секреты

### 2.1. Что хранит Git

Публичный Git содержит названия групп, правила доступа и декларативные настройки. Допускается хранение технических имён пользователей и назначений групп только при отдельном осознанном решении; пароли, хеши, коды восстановления, закрытые ключи и секреты клиентов OIDC в Git не помещаются.

Начальный набор групп и правила доступа задаются конфигурацией. После запуска состав пользователей и назначение групп могут изменяться через закрытую страницу; такие изменения сохраняются на отдельном томе PVE, а не только в управляемом файле Git.

### 2.2. Где хранятся пароли и секреты

Файл `/var/lib/web-gateway/authelia/users_database.yml` на постоянном `mp0` — единственный источник пользователей, групп и Argon2id-хешей. Authelia сама изменяет файл, когда пользователь меняет пароль. Ansible не заменяет его при повторном развёртывании. Операторская копия первоначального пароля admin хранится отдельно на постоянном томе в закрытом файле `/var/lib/web-gateway/management/operator-admin.json` и доступна только доверенному root-терминалу PVE. При смене пароля через Authelia старая копия больше не считается действительной.

В `/var/lib/web-gateway/secrets/` на том же `mp0` лежат ключи шифрования и OIDC, секреты клиентов Immich и сохранившиеся старые ключи Homarr. Их создают при отсутствии, но никогда не перевыпускают при обычном `deploy`. Отдельная синхронизация с OpenBao не нужна; OpenBao обслуживает управляющий контур 910.

### 2.3. Изменение пароля и управление пользователями

Пользователь меняет свой пароль через настройки Authelia: новый хеш сохраняется в постоянном `users_database.yml`. Для этого Authelia получает право записи в `/data`. При изменении пароля и подтверждении личности Authelia использует уведомления; файловый способ уведомлений служит только для проверки и не доставляет письмо пользователю. Для полностью самостоятельного восстановления доступа потребуется настроить SMTP и проверить доставку.

Обычных пользователей создаёт только администратор на странице `https://home.zsergey.ru/admin`, указывая имя, отображаемое имя и группу. Настоящий адрес электронной почты не нужен: для обязательного поля Authelia автоматически формируется внутренний служебный адрес, а сообщения записываются в закрытый файл гостя 140. При создании администратору однократно показывается случайный пароль, который он передаёт пользователю.

Пользователь входит со своим паролем, открывает настройки Authelia и запрашивает подключение Google Authenticator. После запроса администратор выбирает действие «Показать проверочный код» на защищённой странице и передаёт **восьмизначный код**, действующий не дольше **5 минут**, непосредственно пользователю. Пользователь вводит этот код в Authelia, сканирует QR и подтверждает шестизначный код с телефона. Никаких дополнительных команд и получения почты не требуется.

Файловый уведомитель Authelia предназначен для проверочных сред; это осознанное упрощение для небольшого доверенного домашнего круга. Не выдавать пользователю весь файл уведомлений или служебные ключи.

Если пользователь потерял телефон, администратор после проверки личности выбирает действие «Сбросить Google Authenticator» на закрытой странице. Сбрасывается только второй фактор; пароль, группы и данные приложений сохраняются. Затем пользователь повторяет регистрацию через выдаваемый администратором код. При явном сбросе второго фактора `admin` следующий `deploy 140` может заново открыть локальную страницу QR. Регистрация TOTP хранится в SQLite Authelia.

## 3. Файлы и постоянные данные

### 3.1. Целевые каталоги

| Путь гостя | Назначение |
|---|---|
| `/etc/web-gateway/authelia/configuration.yml` | Основная конфигурация Authelia; несекретная часть воспроизводится из проекта |
| `/var/lib/web-gateway/authelia/users_database.yml` | Основной постоянный файл пользователей, `0600`, доступен Authelia для записи |
| `/var/lib/web-gateway/secrets/` | Рабочие секреты, `0700` для каталога, `0600` для файлов |
| `/var/lib/web-gateway/authelia/` | Постоянная база SQLite и другие данные Authelia |
| `/opt/web-gateway/compose/` | Файлы повторяемого запуска служб |

Authelia работает отдельным контейнером Docker: настройки из `/etc` подключены только для чтения, а `/data` — для записи. Секреты из `/var/lib/web-gateway/secrets/` подключаются отдельно, только для чтения, по пути `/run/authelia-secrets` внутри контейнера. Они не должны монтироваться в `/config/secrets`, поскольку весь `/config` подключён только для чтения и Docker не сможет создать там вложенный каталог. `/var/lib/web-gateway/authelia/` физически находится на `/mnt/bindmounts/infra-state/140-web-gateway/authelia/` на PVE (`mp0`). Compose обязан подключить этот каталог к действительному пути хранения SQLite в контейнере; отдельный PostgreSQL не требуется. Путь SQLite из `configuration.yml` должен совпадать с подключённым каталогом. При отсутствии `mp0` Authelia не запускается с новой пустой базой. Схема — в [storage.md](storage.md).

Важно: права `0600` для файла пользователей должны сопровождаться правильным владельцем и UID/GID процесса внутри контейнера. Проверять фактическую возможность чтения, а не автоматически считать, что `root:root` подходит.

### 3.2. Что резервировать

В резервную копию входят `authelia/`, `secrets/` и `management/` как единый комплект на PVE. Копия должна быть зашифрована; SQLite копируют согласованно. Отсутствие любой из частей может привести к потере пользователей, второго фактора либо связей OIDC.

## 4. Развёртывание и эксплуатация

### 4.1. Первый запуск

1. Подготовить конфигурацию службы и постоянные каталоги с требуемыми владельцами.
2. Создать только отсутствующие секреты Authelia и OIDC-клиентов на постоянном томе.
3. При отсутствии файла пользователей создать `admin` со случайным паролем и Argon2id-хешем; сохранить операторскую копию на `mp0`. Пароль показывать только в общем статусе доверенного терминала PVE, но не в журнале Semaphore. Для восстановления утраченного значения применять явную команду сброса.
4. Настроить хранилище SQLite, сеансы, адрес `https://auth.zsergey.ru`, OIDC и требования второго фактора.
5. Запустить Authelia через Docker Compose; проверить журналы без вывода чувствительных данных.
6. При первом развёртывании TOTP для `admin` создаётся штатной командой Authelia без SMTP. Открыть из домашней сети `https://auth.zsergey.ru/totp-setup` в течение 15 минут, считать QR и подтвердить шестизначный код на той же странице. QR и временный URI удаляются автоматически после подтверждения. Другая регистрация TOTP не запускается при обычном повторном развёртывании.
7. Проверить вход на домашнюю страницу через Authelia. Клиента Immich зарегистрировать на 140, но настройку самого Immich выполнить только при `deploy 340`.
8. Сохранить резервную копию постоянного состояния до публикации остальных служб.

Точные версии образов и значения параметров при реализации закрепляются в `provision.yaml` и файлах развёртывания; не применять незакреплённый `latest`.

### 4.2. Повседневные изменения и проверки

Для добавления или отключения пользователя изменять защищённый постоянный файл с резервной копией; Ansible не должен сбрасывать эти изменения. Пользователь сам меняет пароль в Authelia. Проверять вход, второй фактор, самостоятельную смену пароля, сохранность после повторного развёртывания и отсутствие зависимости от работающего 910.

При обновлении Authelia сначала сделать согласованную резервную копию состояния и проверить изменения формата конфигурации и базы; затем обновить закреплённую версию и проверить вход во все OIDC-приложения. Восстановление резервной копии выполняется отдельно администратором, не командой `deploy`. Если в уже установленном госте исчезли SQLite, файл пользователей или секреты, `deploy` должен завершиться ошибкой, а не создавать новые значения. При ручном восстановлении вернуть весь прежний постоянный каталог `140-web-gateway/`, включая SQLite, файл пользователей и секреты. Из Git возвращать только воспроизводимые настройки.
