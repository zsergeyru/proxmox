# Authelia — общий вход и второй фактор

**Тип:** локальная спецификация службы  
**Статус:** целевое состояние

Authelia — единый источник входа для домашних веб-приложений, поддерживающих OpenID Connect (OIDC), и средство проверки второго фактора. Предусмотрены 3–4 пользователя и 2–3 группы; отдельная административная панель пользователей не требуется.

## 1. Устройство входа

### 1.1. Адрес и клиенты

Authelia доступна пользователям через `https://auth.zsergey.ru` за Caddy; внутренний адрес контейнера и порт 9091 доступны только внутри сети Docker 140. Внешний доступ к внутреннему порту не открывается.

Для Homarr, Immich и Open WebUI настраиваются отдельные клиенты OIDC с точными адресами возврата, полученными из настроек соответствующих приложений. Для клиентов допускаются `openid`, `profile`, `email` и `groups` по необходимости. Вход и выдача прав проверяются в самом приложении, а не только наличием ссылки в Homarr.

У разных приложений сохраняются собственные сведения о пользователях и разрешениях. SSO устраняет повторный ввод пароля, но не обязан отменять внутренние права приложений.

### 1.2. Защита и группы

Для опубликованных приложений требуется пароль и второй фактор: TOTP в приложении-аутентификаторе; при поддержке может применяться WebAuthn/ключ доступа. У каждого пользователя свой второй фактор и резервные коды, которые нужно сохранить отдельно.

Группы первого этапа:

| Группа | Назначение |
|---|---|
| `admins` | административные разрешения и семейные приложения |
| `family` | фотографии, домашняя страница, домашняя автоматика |
| `guests` | только явно разрешённые приложения |

Правило по умолчанию — запрет, если разрешение не назначено явно. Членство в нескольких группах допустимо. Права на домашней странице не подменяют права на самих приложениях.

Интерфейсы Proxmox, OpenBao и infra-manager нельзя делать публичными ради удобной плитки на домашней странице; они доступны только из доверенной домашней сети либо по отдельному защищённому каналу.

Home Assistant не имеет штатного OIDC-входа; способ подключения необходимо проверить отдельно. Пока это не сделано, сохраняется собственная авторизация Home Assistant. Нельзя объявлять единый вход полностью готовым лишь потому, что открывается домашняя страница.

## 2. Пользователи и секреты

### 2.1. Что хранит Git

Публичный Git содержит названия групп, правила доступа и декларативные настройки. Допускается хранение технических имён пользователей и назначений групп только при отдельном осознанном решении; пароли, хеши, коды восстановления, закрытые ключи и секреты клиентов OIDC в Git не помещаются.

Начальный набор групп и правила доступа задаются конфигурацией. После запуска состав пользователей и назначение групп могут изменяться через закрытую страницу Homarr; такие изменения сохраняются на отдельном томе PVE, а не только в управляемом файле Git.

### 2.2. Где хранятся пароли и секреты

Файл `/var/lib/web-gateway/authelia/users_database.yml` на постоянном `mp0` — единственный источник пользователей, групп и Argon2id-хешей. Authelia сама изменяет файл, когда пользователь меняет пароль. Ansible не заменяет его при повторном развёртывании. Операторская копия первоначального пароля admin хранится отдельно на постоянном томе в закрытом файле `/var/lib/web-gateway/management/operator-admin.json` и доступна только доверенному root-терминалу PVE. При смене пароля через Authelia старая копия больше не считается действительной.

В `/var/lib/web-gateway/secrets/` на том же `mp0` лежат ключи шифрования и OIDC, секреты клиентов Homarr и Immich. Их создают при отсутствии, но никогда не перевыпускают при обычном `deploy`. Отдельная синхронизация с OpenBao не нужна; OpenBao обслуживает управляющий контур 910.

### 2.3. Изменение пароля и управление пользователями

Пользователь меняет свой пароль через настройки Authelia: новый хеш сохраняется в постоянном `users_database.yml`. Для этого Authelia получает право записи в `/data`. При изменении пароля и подтверждении личности Authelia использует уведомления; файловый способ уведомлений служит только для проверки и не доставляет письмо пользователю. Для полностью самостоятельного восстановления доступа потребуется настроить SMTP и проверить доставку.

Пока создание, блокировку и смену групп выполняют через защищённое изменение того же файла пользователей. Административная страница Homarr для этих операций — отдельный будущий этап: до реализации защищённого обработчика виджеты не считаются рабочими. Второй фактор и его регистрация хранятся в SQLite Authelia.

## 3. Файлы и постоянные данные

### 3.1. Целевые каталоги

| Путь гостя | Назначение |
|---|---|
| `/etc/web-gateway/authelia/configuration.yml` | Основная конфигурация Authelia; несекретная часть воспроизводится из проекта |
| `/var/lib/web-gateway/authelia/users_database.yml` | Основной постоянный файл пользователей, `0600`, доступен Authelia для записи |
| `/var/lib/web-gateway/secrets/` | Рабочие секреты, `0700` для каталога, `0600` для файлов |
| `/var/lib/web-gateway/authelia/` | Постоянная база SQLite и другие данные Authelia |
| `/opt/web-gateway/compose/` | Файлы повторяемого запуска служб |

Authelia работает отдельным контейнером Docker: настройки из `/etc` подключены только для чтения, а `/data` — для записи. Секреты из `/var/lib/web-gateway/secrets/` подключаются отдельно, только для чтения, по пути `/run/authelia-secrets` внутри контейнера. Они не должны монтироваться в `/config/secrets`, поскольку весь `/config` подключён только для чтения и Docker не сможет создать там вложенный каталог. `/var/lib/web-gateway/authelia/` физически находится на `/mnt/bindmounts/infra-state/140-web-gateway/authelia/` на PVE (`mp0`). Compose обязан подключить этот каталог к действительному пути хранения SQLite в контейнере; отдельный PostgreSQL не требуется. Путь SQLite из `configuration.yml` должен совпадать с подключённым каталогом. При отсутствии `mp0` Authelia не запускается с новой пустой базой. Схема — в [storage.md](storage.md).

Важно: права `0600` для файла пользователей должны сопровождаться правильным владельцем и UID/GID процесса внутри контейнера. Проверять фактическую возможность чтения, а не автоматически считать, что `root:root` подходит.

### 3.2. Что резервировать

В резервную копию входят `authelia/`, `secrets/` и `management/` как единый комплект на PVE. Копия должна быть зашифрована; SQLite копируют согласованно. Отсутствие любой из частей может привести к потере пользователей, второго фактора либо связей OIDC.

## 4. Развёртывание и эксплуатация

### 4.1. Первый запуск

1. Подготовить конфигурацию службы и постоянные каталоги с требуемыми владельцами.
2. Создать только отсутствующие секреты Authelia и OIDC-клиентов на постоянном томе.
3. При отсутствии файла пользователей создать `admin` со случайным паролем и Argon2id-хешем; сохранить операторскую копию на `mp0`. Пароль показывать только в общем статусе доверенного терминала PVE, но не в журнале Semaphore. Для восстановления утраченного значения применять явную команду сброса.
4. Настроить хранилище SQLite, сеансы, адрес `https://auth.zsergey.ru`, OIDC и требования второго фактора.
5. Запустить Authelia через Docker Compose; проверить журналы без вывода чувствительных данных.
6. Открыть страницу входа по HTTPS, зарегистрировать второй фактор и получить резервные коды.
7. Проверить вход Homarr. Клиента Immich зарегистрировать на 140, но настройку самого Immich выполнить только при `deploy 340`.
8. Сохранить резервную копию постоянного состояния до публикации остальных служб.

Точные версии образов и значения параметров при реализации закрепляются в `provision.yaml` и файлах развёртывания; не применять незакреплённый `latest`.

### 4.2. Повседневные изменения и проверки

Для добавления или отключения пользователя изменять защищённый постоянный файл с резервной копией; Ansible не должен сбрасывать эти изменения. Пользователь сам меняет пароль в Authelia. Проверять вход, второй фактор, самостоятельную смену пароля, сохранность после повторного развёртывания и отсутствие зависимости от работающего 910.

При обновлении Authelia сначала сделать согласованную резервную копию состояния и проверить изменения формата конфигурации и базы; затем обновить закреплённую версию и проверить вход во все OIDC-приложения. При восстановлении вернуть весь прежний постоянный каталог `140-web-gateway/`, включая SQLite, файл пользователей и секреты. Из Git возвращать только воспроизводимые настройки.
