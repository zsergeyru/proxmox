# Caddy — обратный прокси и сертификаты

**Тип:** локальная спецификация службы  
**Статус:** целевое состояние

Caddy на госте 140 принимает входящие HTTP/HTTPS-запросы, автоматически получает сертификаты и направляет обращения к внутренним веб-приложениям.

## 1. Роль и сеть

### 1.1. Точки входа

| Внешний адрес | Назначение |
|---|---|
| `home.zsergey.ru` | Homarr |
| `auth.zsergey.ru` | Authelia |
| `photos.zsergey.ru` | Immich |
| `ha.zsergey.ru` | Home Assistant |
| `ai.zsergey.ru` | Open WebUI |

Список адресов — целевой. Публиковать можно только проверенные и готовые приложения; несуществующие службы не должны получать рабочие правила.

Для первого запуска предусмотрен **отдельный локальный адрес** `http://192.168.1.40:8080`: статическая начальная страница без пароля, HTTPS и зависимости от Homarr/Authelia. Он не заменяет будущий портал Homarr и не открывает его мастер `/init`. Через Keenetic порт 8080 не перенаправлять.

### 1.2. Доставка соединения

В Beget нужные поддомены `zsergey.ru` должны иметь CNAME на `isergey.netcraze.link`. KeenDNS отслеживает динамический публичный IPv4 Keenetic. На Keenetic входящие TCP 80 и 443 направляются к `192.168.1.40` (гость 140). Административный доступ к самому Keenetic для этого открывать не требуется.

При смене адреса обновление происходит через KeenDNS и обычное обновление DNS. В облачном режиме KeenDNS эта схема с собственными CNAME может не работать; облачное имя не считается доказанным запасным способом доступа к `zsergey.ru`.

Для клиентов домашней сети локальный DNS может направлять те же имена сразу на 140: это устраняет зависимость внутреннего доступа от обратной переадресации на Keenetic. Не создавать разные имена для внутреннего и внешнего входа без необходимости.

## 2. Размещение и настройка

### 2.1. Файлы и порты

Caddy развёртывается как отдельный контейнер Docker в общей конфигурации служб гостя 140. Порты гостя: TCP 80 и 443 для доменов, а также TCP 8080 только для домашней сети. Ограничение на 8080 проверяет реальный адрес клиента через `remote_ip` с перечнем `caddy.private_networks` (`192.168.0.0/16`); посторонним адресам возвращается 403. В Keenetic правила открытия порта 8080 не нужны. Веб-панель управления Caddy и внутренние порты приложений наружу не публикуются.

Целевые пути на госте:

| Путь | Содержимое | Режим |
|---|---|---|
| `/etc/web-gateway/caddy/Caddyfile` | Правила Caddy | управляемый, чтение для службы |
| `/etc/web-gateway/caddy/local-home/index.html` | Начальная страница для домашней сети | воспроизводимый файл из Git |
| `/var/lib/web-gateway/caddy/data/` | Ключи и сертификаты Caddy | постоянные данные |
| `/var/lib/web-gateway/caddy/config/` | Рабочее состояние Caddy | постоянные данные |
| `/opt/web-gateway/compose/` | Описание запуска Docker Compose | воспроизводимая конфигурация |

Каталоги `caddy/data/` и `caddy/config/` должны находиться на отдельном подключении PVE `/mnt/bindmounts/infra-state/140-web-gateway` → `/var/lib/web-gateway` (`mp0`). В Compose явно подключить их к постоянным путям данных и конфигурации Caddy внутри контейнера. При отсутствии `mp0` службу не запускать; новые пустые каталоги на системном диске не создавать.

При реализации конкретные версии контейнеров и конфигурацию Compose закрепить в `provision.yaml`/явных файлах развёртывания. Не использовать незафиксированные плавающие версии. Схема хранения — в [storage.md](storage.md).

### 2.2. Правила перенаправления

Домашние Caddy → Authelia и Homarr должны общаться по внутренней сети Docker; к Immich, Home Assistant и Open WebUI Caddy обращается по их внутренним адресам и портам из машинных описаний соответствующих гостей. Нельзя фиксировать вымышленные адреса приложений в локальной спецификации 140.

Каждое опубликованное имя обслуживается отдельным правилом Caddy. Передаются сведения об исходном протоколе и адресе клиента. В целевых приложениях явно настраивается доверие только к обратному прокси 140, если оно требуется. Для Home Assistant необходимо отдельно настроить `trusted_proxies`.

Для приложений с OIDC (Immich, Open WebUI и Homarr) Caddy не должен добавлять ещё одну форму входа: вход выполняется самим приложением через Authelia. Для приложений без OIDC правила дополнительной защиты согласуются отдельно, а не включаются вслепую — иначе могут перестать работать мобильные клиенты и API.

При управлении через встроенную страницу Homarr изменения маршрутов сохраняются в `/var/lib/web-gateway/management/routes.yaml` на постоянном томе PVE, а обработчик формирует `/etc/web-gateway/caddy/sites.generated.caddy`, включаемый основным `Caddyfile`. Проверка конфигурации **обязательна до применения**; при ошибке остаётся прежняя рабочая версия. Сам Caddy не получает прав на управление пользователями Authelia.

Из формы Homarr можно включать или отключать **только заранее одобренные в Git домены и внутренние назначения**, после отдельного подтверждения. Публикация нового имени или нового адреса приложения через форму запрещена: их сначала надо описать в проекте. Нельзя отключать `auth.zsergey.ru` и `home.zsergey.ru` или превращать другие домены в открытые без входа. Для включения требуются заранее установленный адрес назначения и подходящий режим доступа. Immich остаётся отключённым до отдельной проверки существующих учётных записей и мобильного приложения. Перед изменением формируется временная конфигурация по тому же шаблону, выполняется `caddy validate`. После успеха сохраняется список на `infra_state` и выполняется `caddy reload`; при ошибке возвращаются обе прежние версии. Доступность самой формы Homarr нужно подтвердить на действующем LXC 140.

Для каждого включённого маршрута на постоянном томе используется поле `access`:

| Значение | Правило в Caddy | Для чего |
|---|---|---|
| `public` | Прямое перенаправление без дополнительной проверки | Приветствие Homarr и страница входа Authelia |
| `protected` | Проверка `forward_auth` через Authelia перед обращением к приложению | Обычные веб-службы, доступные после пароля и второго фактора |
| `private` | Доступ только с адресов из `private_networks`; иначе HTTP 403 | Внутренние административные службы, не предназначенные для Интернета |

При первоначальной установке режимы заданы в `provision.yaml`; сохранённый `management/routes.yaml` не перезаписывается. Для старых записей без `access` открытыми остаются **только** имена из `caddy.public_domains` (`home` и `auth`); все остальные по умолчанию считаются `protected`. Указать `public` для имени вне `public_domains` нельзя: роль остановит развёртывание до применения Caddy. Адрес `auth.zsergey.ru` обязан оставаться `public`, иначе возможна петля авторизации.

Для `protected` в Authelia действует требование второго фактора для поддоменов `zsergey.ru`; это не разрешает публиковать их в Caddy. Исключение для публичного маршрута Homarr: Caddy не отдаёт приложение до появления подтверждённой роли 140 отметки `management/catalog/homarr-ready` на постоянном томе, возвращает HTTP 503 при её отсутствии и всегда запрещает `/init` и запросы первоначального создания администратора. Инициализация производится сценарием `initialize-homarr.py` напрямую через локальный порт 7575, независимо от HTTPS. `private_networks` изначально содержит `192.168.0.0/16`; доступ через VPN добавляют только после подтверждения реальной адресации. Если перед Caddy появится ещё один прокси, правило проверки исходного IP нужно пересмотреть.

**Исключение для мобильных клиентов:** приложения с собственным OIDC и API, в частности Immich, нельзя без проверки переводить под общую браузерную проверку `forward_auth`: она может нарушить загрузку фотографий. Маршрут Immich остаётся отключённым, пока для него не проверен совместимый способ входа и защиты каждого интерфейса. Прямые адреса и порты приложений не должны публиковаться в Интернет в обход Caddy.

Ручное изменение сформированного файла не является постоянным источником настройки. Действия и границы допустимых назначений описаны в [administration.md](administration.md).

### 2.3. Сертификаты

Caddy сам получает сертификаты Let's Encrypt для доменов `zsergey.ru`. Сертификат на имя KeenDNS для этих адресов не подходит. Порты 80/443 должны быть доступны извне, а DNS — указывать на действующий публичный IPv4. Данные сертификатов хранятся в постоянном каталоге Caddy.

## 3. Запуск и проверки

### 3.1. Первый запуск

1. Подготовить локальные каталоги и сеть Docker.
2. Создать `Caddyfile` из управляемой конфигурации, сначала с доступными внутренними адресами.
3. Проверить синтаксис конфигурации командой `caddy validate --config /etc/caddy/Caddyfile` внутри контейнера (файл гостя подключается к `/etc/caddy/Caddyfile`).
4. Запустить Caddy через Docker Compose.
5. После настройки DNS и переадресации портов проверить выдачу сертификата и открытие каждого опубликованного адреса из внешней сети.

### 3.2. Проверки после изменения

Без публикации наружу открыть с компьютера в домашней сети `http://192.168.1.40:8080`: должна появиться начальная страница, без редиректа на HTTPS или `/init`. Проверить, что порт 8080 недоступен из Интернета и на Keenetic нет его переадресации. Работа страницы не доказывает готовность Homarr, Authelia или сертификатов.


Проверить `docker compose ps` и журналы Caddy из каталога Compose; запросы `curl -I https://home.zsergey.ru` и `curl -I https://auth.zsergey.ru` должны отвечать по HTTPS без ошибок проверки сертификата. Отдельно проверить перенаправление HTTP на HTTPS и обновление сертификатов до истечения срока.

После изменения правил проверять конфигурацию до перезапуска; неправильное правило не должно отключать работающий шлюз 109.

## 4. Восстановление и ограничения

При пересоздании LXC `Caddyfile` и Compose восстанавливаются из Git, изменённые маршруты — из `management/routes.yaml` на подключённом `mp0`, сертификаты и ключи — из постоянного `/var/lib/web-gateway/caddy/`. Сохранившийся каталог подключают до запуска Caddy и не очищают при повторном развёртывании. При потере постоянных данных сертификаты можно выпустить повторно, если внешний DNS и порты исправны; не следует делать массовые повторные запросы при неисправной DNS-настройке.

Типовые причины ошибки: закрытые порты Keenetic, неверный CNAME, смена режима KeenDNS на облачный, неверный адрес внутреннего приложения и недоверенный сертификат. Диагностику начинать с DNS, сетевого пути и журналов Caddy.
