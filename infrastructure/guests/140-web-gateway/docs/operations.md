## 1. Условия и подготовка

### 1.1. Гость и сеть

Гость — LXC с Debian 13 и Docker Compose, CTID 140, имя `web-gateway`. Адрес по действующему правилу VMID — `192.168.1.40`; IP гостя берётся из `guest.yaml` и общих настроек, а не вручную повторяется в нескольких независимых файлах.

Ориентир начальных ресурсов: 2 виртуальных процессора, 1 ГиБ ОЗУ и 16 ГиБ диска. После первого запуска измерить потребление и при необходимости увеличить ОЗУ. Docker внутри LXC требует правильной настройки контейнера и поддержки нужных возможностей ядра; согласовать с общими правилами развёртывания, не создавать особый ручной путь только для 140.

На Keenetic есть динамический публичный IPv4 и действующее имя KeenDNS `isergey.netcraze.link`; DNS домена `zsergey.ru` обслуживает Beget. Для публикации 140 должны работать CNAME поддоменов, доступ извне к TCP 80/443 и внутренний путь к прикладным гостям.

Маршрутизация домашней сети, DHCP, DNS и VPN относятся к 109. 140 не является запасным или дополнительным сетевым шлюзом.

### 1.2. Исходные файлы

При реализации создать `guest.yaml`, `provision.yaml` и при необходимости `status.yaml` по общим договорам проекта. Отдельные службы описать в одном повторяемом развёртывании (Docker Compose) с закреплёнными версиями образов. Файлы конфигурации должны устанавливаться явными задачами Ansible с проверенными владельцами и правами; дерево `rootfs/` целиком не копируется.

**Обязательное хранилище:** существующий общий том PVE `infra_state` (40 ГиБ), папка `/mnt/bindmounts/infra-state/140-web-gateway`, подключение LXC `mp0` к `/var/lib/web-gateway` (чтение и запись). Корневой диск LXC 16 ГиБ предназначен для системы и программ, а не для невоспроизводимых данных. В `provision.yaml` нужно использовать существующий механизм `pve_storage`; том `infra_state` не создавать второй раз и не форматировать. Подробная схема, состав копий и проверки — в [storage.md](storage.md).

Целевой набор путей на госте:

~~~text
/opt/web-gateway/compose/                 # запуск Docker Compose
/etc/web-gateway/caddy/Caddyfile         # правила прокси
/etc/web-gateway/authelia/configuration.yml
/var/lib/web-gateway/authelia/users_database.yml
/var/lib/web-gateway/secrets/             # сохраняемые ключи и секреты
/var/lib/web-gateway/caddy/              # сертификаты и рабочие данные
/var/lib/web-gateway/authelia/           # SQLite и второй фактор
/var/lib/web-gateway/homarr/             # домашние страницы и настройки
/var/lib/web-gateway/management/         # изменения доменов и пользователей из Homarr
# Все четыре каталога /var/lib/web-gateway/ физически лежат на томе PVE.
~~~

Несекретные файлы воспроизводятся из Git и сохранённых пользовательских изменений. Секреты и хеши паролей находятся только на постоянном `mp0` и не попадают в Git. Для каталога секретов требуются ограниченные права. Файлы с хешами и секретами — `0600`, с учётом UID/GID процессов контейнеров. При повторном развёртывании существующие данные `/var/lib/web-gateway/` и параметры ранее выданных OIDC-клиентов не сбрасываются.

**До запуска 140** проверить, что на PVE действительно смонтирован `infra_state` и `mp0` подключает именно папку `140-web-gateway`. Если источник не подключён или неожиданно пуст при восстановлении, не создавать пустую SQLite-базу и не запускать веб-службы.

## 2. Первый запуск

1. По общему механизму создать LXC 140, настроить сеть и проверить доступ к 910, Keenetic и внутренним гостям.
2. На PVE проверить существующий том `infra_state`, свободное место, папку `140-web-gateway` и настроить `mp0` через `pve_storage`. При повторном развёртывании сохранить все прежние данные, при отсутствии реального подключения остановиться. Защиту от запуска без тома выполнять на PVE до старта LXC.
3. Установить Docker и Compose через Ansible. Подключить все четыре постоянных каталога из `/var/lib/web-gateway` как явные тома соответствующих контейнеров; безымянные тома с уникальными данными не использовать.
4. Из Git восстановить базовые конфигурации и описания виджетов; из сохранённой папки `management/` применить изменения доменов и пользователей. Не перезаписывать постоянные настройки значениями первоначального развёртывания.
5. На проверенном `mp0` создать только отсутствующие секреты и пользователя `admin`. Повторный `deploy` ничего из них не меняет.
6. Запустить Caddy, Authelia и Homarr с подключённым состоянием. Уже на этом этапе Caddy отдаёт статическую домашнюю страницу по `http://192.168.1.40:8080` без сертификатов и авторизации, только клиентам домашней сети; этот адрес не ведёт в мастер Homarr. Не настраивать проброс порта 8080 на Keenetic.\n    После ответа Homarr на закрытом порту `127.0.0.1:7575` роль автоматически завершает его начальную настройку через официальный интерфейс: создаёт группу `admins`, пустую закрытую доску и проверяет этап `finish`. Наличие HTTPS-сертификата для этого не требуется. Пока проверка не завершена, Caddy отвечает HTTP 503, а `/init` и запросы первоначальной настройки через внешний адрес всегда заблокированы. Затем проверить SQLite, второй фактор, страницы и доступ по внутреннему HTTPS.
7. Настроить CNAME в Beget и переадресацию портов на Keenetic; проверить внешнее HTTPS и сертификаты. До открытия внешнего доступа убедиться, что только `home` и `auth` допускают вход без авторизации, а все включённые защищённые маршруты требуют второй фактор. Запрос к внутреннему маршруту извне должен возвращать запрет; убедиться, что порты самих приложений напрямую не опубликованы.
8. Подключить Immich и Open WebUI к OIDC по одному и проверить мобильный Immich. Для Home Assistant оставить собственный вход до принятой рабочей интеграции.
9. Проверить группы, административные виджеты, отсутствие прямого доступа к внутренним портам, повторный `deploy/sync` без потери данных и восстановление из резервной копии.

Порядок может технически потребовать запустить Caddy перед первоначальной проверкой внешнего адреса Authelia, но готовность входа должна быть подтверждена **до** публикации остальных приложений.

### 2.1. Первый администратор и секреты

При первом `deploy 140` роль создаёт на проверенном постоянном томе `/var/lib/web-gateway/authelia/users_database.yml` с пользователем `admin` и Argon2id-хешем случайного пароля. Отдельная защищённая копия первоначального пароля и снимка его хеша сохраняется в `/var/lib/web-gateway/management/operator-admin.json` (права `0600`; каталог изолирован от Docker-контейнеров приложений). В повторных `deploy` пароль не изменяется.

По общему правилу проекта `infra-manager status 140` и успешный `infra-manager deploy 140` в доверенном терминале root PVE показывают адреса Authelia/Homarr, логин `admin` и сохранённый пароль. В журнале Semaphore пароль не читается и показывается как «скрыт». Для Homarr отдельного пароля нет: вход выполняется через Authelia.

При смене пароля через Authelia текущий хеш в файле пользователей перестаёт совпадать с сохранённым снимком, поэтому прежний пароль больше **не показывается как действующий**. Самостоятельно восстановить новый пароль из хеша невозможно. Для явного сброса из доверенного терминала PVE выполнить:

```bash
pct exec 140 -- python3 /usr/local/lib/web-gateway/reset-admin-password.py
```

Команда меняет только пароль `admin`, сохраняет новую операторскую копию на постоянном томе и показывает значение в текущем терминале; второго фактора и других пользователей не касается. Не запускать её из Semaphore.

**Порядок установки этого обновления:** после слияния изменений в основную ветку сначала выполнить `infra-manager deploy 910` для установки нового общего механизма вывода, затем `infra-manager deploy 140` для установки обновлённых сценариев гостя. В последнем выводе и в последующем `infra-manager status 140` появятся операторские данные.

**Ранее созданный гость 140:** при первом обновлении роль попытается сохранить прежний временный пароль из `/run/web-gateway/initial-admin-password`, но только если он ещё существует и подходит к текущему хешу. Если временный файл уже исчез, `deploy` не заменит пароль автоматически; в статусе будет сообщение «не сохранён», и для нового пароля понадобится указанная явная команда.

Ключи Authelia, OIDC и секреты клиентов Homarr и Immich создаются только при отсутствии на `/var/lib/web-gateway/secrets/` с правами `0600` (каталог `0700`). В случае частично созданных или повреждённых секретов запуск останавливается без перевыпуска. При смене пароля самим пользователем Authelia записывает новый хеш в постоянный файл. Настройка SMTP для уведомлений и восстановления доступа выполняется отдельно; файловый извещатель — только для испытаний.

Для будущего подключения Immich 140 сохраняет секрет клиента, а OAuth в самой службе включает только `deploy 340`. Универсальный механизм 910 не получает частных правил для 140.

### 2.2. Первоначальная регистрация Google Authenticator

При первом `deploy 140` Authelia сохраняет TOTP администратора в SQLite и готовит закрытый QR. Из домашней сети открой `https://auth.zsergey.ru/totp-setup`: дополнительного пароля или одноразовой ссылки нет. Страница работает **не более 15 минут** после запуска временного обработчика. Сканируй QR и введи шестизначный код в форме; при успехе QR и временный URI удалятся, а настройка TOTP сохранится. Повторный `deploy` с зарегистрированным TOTP не меняет ключ. Если регистрация не подтверждена, повторный `deploy` может снова открыть окно без перевыпуска кода.

Обычных пользователей создаёт администратор через защищённый файл пользователей. После запроса регистрации пользователем проверить его одноразовый код только из доверенного терминала PVE:

```bash
pct exec 140 -- python3 /usr/local/lib/web-gateway/totp-users.py code anna
```

Если пользователь потерял телефон, администратор проверяет личность и явно сбрасывает только TOTP:

```bash
pct exec 140 -- python3 /usr/local/lib/web-gateway/totp-users.py reset anna --confirm
```

Файловые уведомления не выводятся в журналы развёртывания. Восстановление резервных копий при `deploy` **не выполняется**: если существующее состояние потеряно, установка останавливается. Утерянные данные возвращает администратор отдельно.

### 2.3. Административная страница Homarr

После запуска основных служб создать закрытую страницу «Администрирование» только для `admins` и разместить три пользовательских виджета Custom Widgets v2: управление Caddy, управление пользователями Authelia и управление гостями Proxmox. Для Caddy и Authelia внутренний обработчик 140 выполняет ограниченные операции и не публикуется через Caddy. Для операций над гостями служит 910 infra-manager: на 140 нельзя дублировать механизм OpenTofu, Ansible или операторские полномочия. Закрепить версию Homarr, поддерживающую виджеты и нужные права.

Настройки, изменяемые через формы, сохраняются в `/var/lib/web-gateway/management/`, а рабочие файлы формируются отдельно. Повторное применение Ansible не должно уничтожать изменения. Перед включением панели проверить права, отказ в прямых запросах без полномочий, проверку конфигурации перед применением и восстановление предыдущего варианта. Полная спецификация — [administration.md](administration.md).

### 2.4. Управление гостями через 910

На закрытой административной странице Homarr должен отображаться список гостей, полученный от 910 по защищённому внутреннему интерфейсу. Операции `deploy`, `status`, `sync`, `repair` должны запускаться на 910 с отдельным номером задания. Обычные индикаторы наличия/работы PVE не следует выдавать за результат полной проверки служб.

До подключения виджета подтвердить права `admins`, недоступность управляющих действий из Интернета, контроль VMID и действия на 910 и отображение журнала длительного задания без раскрытия секретов. Действующая веб-страница подтверждения `portal_gateway.py` не является готовым интерфейсом машинных ответов; его потребуется расширить или дополнить на 910. Подробности — [guest-management.md](guest-management.md).

## 3. Проверка и обновление

### 3.1. Приёмочные проверки

- Из внешней сети открываются `home.zsergey.ru` и `auth.zsergey.ru` с действительными сертификатами.
- Вход без второго фактора отклоняется; повторный вход на том же доверенном устройстве использует действующий сеанс.
- Пользователи разных групп получают только разрешённый доступ; сокрытие плитки не заменяет запрета в приложении.
- Мобильный Immich входит через OIDC, загружает фотографии и крупные видео без дополнительной прокси-формы авторизации.
- После перезапуска 140 остаются данные Homarr, SQLite, настройки второго фактора и сертификаты.
- На PVE подтверждено реальное подключение `infra_state`; `mp0` указывает именно на `140-web-gateway`, а рабочие каталоги контейнеров находятся на этом подключении.
- При отключённом `infra_state` старт LXC/служб блокируется, вместо запуска с пустыми базами.
- Проверено пересоздание в отдельной проверочной среде с копией данных: Git и сохранённый `mp0` возвращают прежние настройки без ручного заполнения.
- После остановки 910 существующие пользователи продолжают входить с локальными рабочими данными.
- После остановки веб-служб 140 домашние DHCP, DNS, Интернет и VPN продолжают работать через 109.
- Через страницу Homarr администратор может изменить тестовый маршрут и пользователя; ошибочная настройка отклоняется без нарушения действующей службы.
- На этой же закрытой странице виден актуальный перечень гостей проекта и PVE; поддерживаемые действия передаются в 910 и показывают подтверждённый итог.
- После обновления браузера сохраняется возможность увидеть ход или результат начатого на 910 задания.
- Пользователи `family` и `guests` не видят административную страницу и не могут вызвать её действия напрямую.
- После повторного развёртывания и восстановления из копии сохранены настройки, введённые через панель.

### 3.2. Обновление

Сначала проверить свободное место и сохранность резервной копии. Затем обновлять по одной службе, закрепляя новую версию образа в управляемой конфигурации; для Authelia проверить совместимость структуры SQLite. После каждого обновления проверить вход, сертификаты, доступ приложений и постоянные данные. Не обновлять Caddy, Authelia и Homarr одним непроверяемым изменением.

## 4. Резервирование и восстановление

### 4.1. Что сохранять

Резервировать **весь** `/mnt/bindmounts/infra-state/140-web-gateway/` на PVE, включая `caddy/`, `authelia/`, `homarr/`, `secrets/` и `management/`. Это один комплект постоянного состояния, который не зависит от корневого диска LXC. Базы SQLite копировать согласованно (с учётом журналов записи). В эту же копию включить `secrets/` и файл пользователей; OpenBao 910 резервируется отдельно.

Цель для 140: ежедневная копия, допустимая потеря изменений — до 24 часов, целевое восстановление — до 4 часов при исправном PVE и пригодных копиях. Использовать два независимых физических носителя: основной внешний компьютер по SMB и дополнительный USB согласно [политике 610](../../../../docs/600-storage/610-backup.md). Это **требования к будущему резервированию**, а не утверждение, что задания уже включены. Учитывать место на обоих носителях и шифровать копии с секретами.

Bind mount **не включается автоматически** в обычную резервную копию LXC средствами `vzdump`. Копии только системного диска 140, Docker-образов и `Compose` недостаточно. Подробнее: [storage.md](storage.md).

### 4.2. Полное восстановление

1. Проверить `infra_state`. Если данные `140-web-gateway/` сохранились, использовать их; если они повреждены или потеряны, восстановить из независимой копии только папку 140, без затрагивания 340.
2. Через 910 создать чистый LXC 140 по Git и до запуска служб подключить `/mnt/bindmounts/infra-state/140-web-gateway` в `/var/lib/web-gateway` как `mp0`.
3. Проверить действительное подключение, ожидаемые данные и права. При отсутствии тома или непредвиденной пустоте остановиться, не создавать новые базы вместо прежних.
4. По `provision.yaml` заново установить Docker, закреплённые образы и файлы `/opt`/`/etc`. Из `management/` сформировать изменения доменов; пользователей и группы взять из основного файла Authelia, из сохранённого `mp0` вернуть секреты, файл пользователей и ключи OIDC.
5. Запустить службы с восстановленными постоянными каталогами. Проверить HTTPS, пользователей, прежний второй фактор, Homarr, виджеты и OIDC Immich/Open WebUI.
6. Проверить, что повторный `deploy/sync` не стирает пользовательские изменения, и что отключение 140 не затрагивает DHCP, DNS, Интернет и VPN гостя 109.

Без копии SQLite прежние регистрации второго фактора могут быть утрачены. При потере постоянных секретов 140 старые OIDC-подключения нельзя считать восстановленными.
