# Постоянные данные и восстановление 140

**Тип:** локальная спецификация службы  
**Статус:** целевое состояние; подключение ещё не реализовано

Гость 140 должен пересоздаваться из Git без потери данных Caddy, Authelia, Homarr и изменений административной страницы. Корневая файловая система LXC содержит ОС и воспроизводимые программы. Постоянные данные находятся на PVE и подключаются к контейнеру отдельно. Текущие значения должны быть внесены в `provision.yaml` при реализации, без ручной настройки отдельного способа установки.

## 1. Источники восстановления

| Источник | Содержимое | Как восстанавливается |
|---|---|---|
| Git | `guest.yaml`, `provision.yaml`, версии служб, Docker Compose, основные настройки Caddy/Authelia, определения административных виджетов и шаблоны | Общая автоматизация 910 заново создаёт систему и файлы |
| Постоянные секреты 140 | Файл пользователей, ключи шифрования и OIDC, секреты клиентов | Восстанавливаются из зашифрованной копии `mp0`, без OpenBao |
| Постоянное хранилище 140 | SQLite Authelia и регистрации 2FA, данные Homarr, сертификаты Caddy, назначения пользователей и изменения доменов через Homarr | Отдельное подключение к новому LXC, без очистки |
| 910 | Каталог гостей проекта, выполненные задания и их журналы | Хранение остаётся на 910; данные управления всеми машинами не копируются в 140 |

Один Git без резервной копии постоянного каталога **не возвращает** пользователей, секреты, второй фактор, страницы Homarr и изменения административной панели. OpenBao не является источником секретов 140.

Воспроизводимые файлы располагаются по обычным путям `/opt/web-gateway/` и `/etc/web-gateway/`. Их исходные описания находятся в Git. Изменения через Homarr записываются в **постоянное состояние**, а рабочие файлы из него формируются заново. Ansible не перезаписывает это состояние.

## 2. Размещение на PVE и внутри LXC

### 2.1. Единый каталог данных

Использовать **существующий общий логический том** `infra_state` (40 ГиБ), который уже описан для 340. Не создавать второй том с тем же назначением и не переносить данные 340 или 910 при установке 140. До развёртывания проверить реальное подключение и свободное место на общем томе; при нехватке места остановить установку и решить вопрос ёмкости отдельно.

```text
PVE: /mnt/bindmounts/infra-state/
├── 340-photo-archive/               # уже существующие данные 340
└── 140-web-gateway/                 # только постоянные данные 140
    ├── caddy/
    │   ├── data/                   # сертификаты и ключи Caddy
    │   └── config/                 # рабочее состояние Caddy
    ├── authelia/                   # SQLite, второй фактор, users_database.yml
    ├── homarr/                     # база, страницы и виджеты Homarr
    ├── secrets/                    # ключи и секреты OIDC
    └── management/
        ├── operator-admin.json      # операторский пароль admin (только root)
        ├── routes.yaml             # изменения доменов
```

Единственное подключение постоянного состояния 140:

| Где | Путь |
|---|---|
| PVE, источник | `/mnt/bindmounts/infra-state/140-web-gateway` |
| Конфигурация LXC | `mp0`, доступ на чтение и запись |
| Внутри 140, назначение | `/var/lib/web-gateway` |

В `provision.yaml` необходимо объявить `pve_storage` через **уже имеющийся** механизм 910 подготовки LXC-хранилищ, со ссылкой на существующий `infra_state`, его известный путь и размер 40 ГиБ. Настройка должна повторно использовать том, а не форматировать его или создавать второй. Подключение другого гостя (340) и его данные не изменяются.

На физическом уровне этот том пока находится на том же NVMe PVE, что и система, но **логически и по подключению отделён** от корневого диска LXC 140. Это облегчает пересоздание контейнера, но не защищает от отказа самого NVMe; независимые копии обязательны.

### 2.2. Пути служб

| Каталог в 140 | Что сохраняется |
|---|---|
| `/var/lib/web-gateway/caddy/` | Сертификаты, ключи и служебное состояние Caddy |
| `/var/lib/web-gateway/authelia/` | SQLite Authelia, регистрации TOTP/WebAuthn и нужное постоянное состояние |
| `/var/lib/web-gateway/homarr/` | База, домашние страницы, плитки, права и созданные через интерфейс виджеты |
| `/var/lib/web-gateway/management/` | Изменения Caddy и административных страниц; защищённая операторская копия пароля admin (не подключается к контейнерам) |
| `/var/lib/web-gateway/secrets/` | Ключи шифрования и OIDC, секреты клиентов; сохраняются при пересоздании |

В Docker Compose указать **явные подключения этих каталогов** к соответствующим контейнерам. Не использовать безымянные тома Docker для уникальных данных, не складывать базы и настройки в каталог с Compose или в корневую файловую систему LXC. Точные пути внутри Docker фиксируются вместе с версиями образов.

Воспроизводимые настройки Caddy и Authelia из `/etc/web-gateway/` возвращаются из Git. Постоянные `/var/lib/web-gateway/authelia/users_database.yml` и `/var/lib/web-gateway/secrets/` нельзя перезаписывать или создавать заново поверх существующих. Authelia сама обновляет хеши паролей в своём файле. Базы SQLite, файл пользователей и ключи должны восстанавливаться совместно.

## 3. Защита от потери и перезаписи

- Перед **каждым запуском LXC** и перед запуском служб проверять, что на PVE действительно подключён `infra_state`, а `mp0` указывает на нужную папку гостя. Проверка существования пустого каталога недостаточна; при отсутствии тома запуск блокируется.
- Нельзя автоматически создавать пустую `/var/lib/web-gateway` на системном диске и запускать Authelia/Homarr с новыми базами вместо отсутствующего подключения. Проверять точку подключения и доступность путей, прежде чем устанавливать права или создавать подпапки.
- При повторном `deploy` существующий том, папка 140 и файлы сохраняются. Не форматировать, не очищать и не переносить их автоматически; при неизвестном или несоответствующем источнике остановиться с понятной ошибкой.
- Нельзя рекурсивно менять владельцев общего `infra_state` или чужих папок. Настраивать права только в `140-web-gateway/` с учётом непривилегированного LXC и UID/GID контейнеров Docker.
- Изменения маршрутов и групп сначала записываются в собственное постоянное состояние. Создаваемые из них файлы проверяются перед применением; ошибка не уничтожает предыдущую рабочую конфигурацию.
- Удаление LXC 140 не должно удалять сохранённую папку на PVE. Перед намеренным удалением данных необходима отдельная операция и проверенная резервная копия.
- Если состояние Homarr изменяется через веб-интерфейс, данные его базы остаются в `homarr/`. Git хранит описание и способ создания административной страницы, а не выдаётся за живую копию её пользовательских настроек.

## 4. Резервирование

Резервировать **единым согласованным комплектом** каталог PVE `/mnt/bindmounts/infra-state/140-web-gateway/` со всеми четырьмя подпапками, включая настройки Homarr и изменяемые `management/*.yaml`. Для SQLite Authelia и базы Homarr использовать согласованный снимок/штатную копию базы либо краткую остановку записи, а не произвольное копирование активных файлов. Не забывать дополнительные файлы SQLite (включая WAL, если используются).

В комплект 140 входят ключи, файл пользователей и все базы. Резервная копия шифруется. OpenBao 910 резервируется отдельно по своим правилам. Git и загруженные Docker-образы не требуют отдельной копии в составе уникальных данных 140, если доступна закреплённая версия проекта.

Цель для 140: **ежедневная резервная копия**, допустимая потеря изменений не более **24 часов**, целевое время восстановления — **не более 4 часов** при работающем PVE и доступных копиях; эти показатели являются требованиями, не результатами уже проведённого теста. Использовать основное независимое место (отдельный компьютер по SMB) и дополнительный USB-носитель, согласно [общей политике](../../../../docs/600-storage/610-backup.md). Для критичных данных — 7 ежедневных и 4 еженедельных копии на основном хранилище и не менее двух последних успешных комплектов на дополнительном носителе. Наличие тома `infra_state` **не заменяет резервирование**.

В будущем `provision.yaml` должен перечислять эти невоспроизводимые данные через `persistence.backup_required`; сам перечень не создаёт задания копирования. Перед обновлением Authelia, Homarr, сменой ключей или пересозданием 140 делать внеочередную проверенную копию. `Sync Guest` для 140 меняет только маршруты из сохранённого `management/routes.yaml` и выполняет `caddy reload`, если они изменились. Он не скачивает и не пересоздаёт контейнеры Homarr, Authelia или Caddy и не меняет их версии; для этого используется отдельный `Deploy Guest`.

### Подготовленный способ копирования

В рабочей ветке создан `infrastructure/host/pve/backup/backup-140.py`. Программа запускается **на PVE**, проверяет настоящее подключение тома `infra_state` и обоих мест назначения, отдельно сохраняет согласованные копии баз SQLite через встроенный механизм SQLite, затем передаёт комплект в **два заранее созданных зашифрованных хранилища restic**. Незашифрованные временные файлы создаются в оперативной памяти PVE, в `/run`, и удаляются после выполнения. Копия включает закрытые ключи 140, поэтому её нельзя хранить без шифрования.

**Расписание не включено:** пути сетевой папки, съёмного носителя и расположение защищённого пароля копий ещё не подтверждены. Запуск без этих параметров прекращается с ошибкой. После определения носителей нужны две подготовленные копии, проверка чтения и отдельное расписание по политике 610. Программа не ищет и не применяет резервные копии при `infra-manager deploy`; восстановление выполняет только администратор.

## 5. Полное восстановление и проверки

1. Проверить сохранность общего тома `infra_state`, его свободное место, папку 140 и нужную точку резервной копии. При повреждении/утрате восстановить **только** данные 140 из независимой копии; не затрагивать 340.
2. Через 910 создать чистый LXC 140 по `guest.yaml` из Git. До запуска служб подключить сохранённую папку `infra_state/140-web-gateway` как `mp0` в `/var/lib/web-gateway`.
3. Проверить реальный источник подключения. Если он отсутствует или неожиданно пустой при восстановлении существующей системы, **остановиться** и не инициализировать новые базы.
4. По `provision.yaml` установить Docker и закреплённые версии служб, восстановить воспроизводимые конфигурации. Файл пользователей и ключи использовать из прежнего `mp0`; домены — из сохранённого `management/`.
5. Подключить постоянные каталоги контейнеров и запустить Caddy, Authelia, Homarr. Проверить старые регистрации 2FA, вход через OIDC, страницы Homarr, административные виджеты, домены и HTTPS.
6. Проверить, что повторное применение `deploy/sync` не меняет пользовательские настройки и не создаёт пустых баз. Сверить список сохраняемых файлов и результат независимой резервной копии.

Контрольные отказы: отсутствует `infra_state`, неверная папка `mp0`, недостаточно места на общем томе, потерян `/var/lib/web-gateway/management`, некорректное обновление SQLite. Любая из этих ситуаций должна вызывать понятную ошибку, а не тихую потерю прежнего состояния.
