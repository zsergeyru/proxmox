## 1. Разделение ответственности

### 1.1. Почему веб-доступ вынесен из 109

**Проблема.** Шлюз 109 обеспечивает повседневную маршрутизацию, DNS и VPN. Перезапуски и обновления домашнего портала не должны быть причиной перерыва обычного Интернета.

**Варианты.** Разместить веб-службы на 109 или вынести их в самостоятельный гость.

**Решение.** Создать отдельный LXC веб-доступа 140. Сами Immich, Home Assistant и ИИ-службы остаются на других гостях.

**Последствия.** Добавляется один гость и ещё одна резервная копия; отказ 140 прерывает веб-доступ, но не должен прерывать домашнюю сеть. Пересматривать только если появятся существенные причины объединить службы без ущерба надёжности.

## 2. Выбор служб

### 2.1. Caddy, Authelia и простая домашняя страница

**Проблема.** Нужны HTTPS, единый вход с вторым фактором и удобная домашняя страница без написания своих приложений.

**Варианты.** Для прокси рассматривались Caddy, Nginx Proxy Manager и Traefik; для авторизации — Authentik, Authelia и Pocket ID; для домашней страницы — Homarr, Homepage и Dashy.

**Решение.** Caddy — за воспроизводимую конфигурацию и автоматический HTTPS; Authelia — за готовый вход с паролем, вторым фактором и группами. От Homarr решено отказаться после испытаний 17.10.2026: для автоматической настройки страниц приходилось менять структуру его базы и следить за совместимостью виджетов. Вместо этого Caddy отдаёт небольшие воспроизводимые страницы, не заменяя Authelia и её механизм авторизации.

**Последствия.** Управление пользователями Authelia осуществляется через конфигурацию, а не отдельную административную веб-панель. Поддержка OIDC и передачи групп конкретным приложением проверяется отдельно. Пересмотреть при существенном росте числа пользователей или необходимости выдавать доступ через графический интерфейс.

### 2.2. SQLite вместо отдельной базы

**Проблема.** Для нескольких пользователей отдельный сервер базы данных избыточен.

**Решение.** Использовать SQLite, поддерживаемую Authelia, с постоянным хранением и согласованным резервированием.

**Последствия.** Нельзя терять состояние второго фактора; при росте нагрузки или появлении нескольких экземпляров авторизации следует пересмотреть выбор хранилища.

### 2.3. Администрирование из закрытой страницы

**Проблема.** При нескольких доменах и 3–4 пользователях неудобно вручную менять системные файлы, но отдельная полноценная административная система избыточна.

**Варианты.** Ручное редактирование файлов, отдельные приложения управления или ограниченные формы внутри существующей домашней страницы.

**Решение.** Раздел `/admin` размещается на домашнем HTTPS-сайте, доступен только после второго фактора Authelia, с группой `admins` и из доверенной сети/VPN. Административная страница не знает секретов и не выполняет системные команды напрямую: она обращается к закрытой службе по Unix-сокету, которая использует ограниченный обработчик гостя 140. Просмотр гостей Proxmox остаётся только для чтения; включение действий над машинами требует отдельного решения через 910.

**Последствия.** Нужно поддерживать маленькие HTML, CSS, JavaScript и закрытую системную службу, зато нет зависимости от внутренней базы Homarr. Полномочия проверяются до выполнения действия, поддельные межсайтовые запросы отклоняются. Данные прежнего Homarr сохраняются только для возможного возврата старой версии.

## 3. Хранение данных и доступ

### 3.1. Почему хеши не хранятся в Git

**Проблема.** Репозиторий публичный, а хеши паролей тоже пригодны для попыток подбора.

**Решение.** В Git остаются несекретные правила и названия групп. Хеши Argon2id и секреты OIDC хранятся в защищённых файлах на постоянном томе `mp0`, не в Git. Authelia самостоятельно изменяет файл пользователей, поэтому синхронизация с OpenBao или отдельный демон не нужны.

**Последствия.** Нужно резервировать и шифровать весь постоянный каталог 140, включая пользователей, ключи и второй фактор. Пересмотреть при изменении общей схемы хранения секретов проекта.

### 3.2. Отдельное постоянное состояние вместо копии системы

**Проблема.** Если базы Authelia и Homarr, сертификаты и изменения административной панели лежат только внутри корневого диска LXC, пересоздание гостя приводит к потере уникального состояния.

**Варианты.** Хранить всё внутри LXC и копировать системный диск; создавать отдельный том специально для 140; использовать существующий общий том состояний LXC.

**Решение.** Применить уже существующий `infra_state` (40 ГиБ) с отдельной папкой `140-web-gateway/` и подключением `mp0` к `/var/lib/web-gateway`. Git остаётся источником воспроизводимых программ и конфигураций, а этот каталог — единственным источником прикладных секретов, пользователей и состояния 140. Для установки и повторного развёртывания использовать общий `pve_storage` без нового специального механизма.

**Последствия.** Замена LXC не должна затрагивать состояние 140 и данные 340, а отсутствие настоящего подключения блокирует запуск. Общий том пока расположен на том же физическом NVMe, поэтому отказ SSD требует двух независимых резервных копий по политике 610. Свободное место на общем томе нужно проверять до установки.

Точное размещение, проверки и восстановление описаны в [storage.md](storage.md).

### 3.3. Прямой доступ через Keenetic

**Проблема.** Нужен доступ по собственным поддоменам, без Cloudflare и без обязательного VPS, при изменяемом публичном IPv4.

**Решение.** Использовать KeenDNS для отслеживания публичного адреса, DNS Beget для собственных имён и прямое перенаправление портов на Caddy.

**Последствия.** Публичные адреса зависят от доступности прямого входа через текущего провайдера. Облачный режим KeenDNS не является равнозначным запасным маршрутом для CNAME собственного домена. Пересмотреть при потере публичного IPv4 или необходимости второго независимого внешнего пути.
