# ADR 001 — Ansible и Semaphore в `311-dev-services`

## Статус

Принято.

## Контекст

Для повторяемого развёртывания конфигурации нужен готовый инструмент, чтобы не писать собственный механизм с учётом файлов, прав, удаления, перезапуска сервисов и проверки результата.

Ansible и Semaphore не являются AI-компонентами. Поэтому они не должны постоянно размещаться внутри `301-ai-control` или в каталоге `agents/`.

## Решение

`311-dev-services` является целевым местом для DevOps-инструментов развёртывания:

- Ansible — штатный механизм повторяемого применения конфигурации внутри VM/LXC через SSH;
- Semaphore — веб-интерфейс к Ansible для ручного запуска, истории и журналов;
- Gitea/Gogs, Jenkins и другие CI/CD-инструменты также относятся к этой гостевой системе.

Ansible и Semaphore целесообразно запускать в Docker внутри `311-dev-services`. На управляемые VM/LXC отдельный агент Ansible не устанавливается: транспортом остаётся SSH.

## Разделение ответственности

```text
301-ai-control
  Hermes / AI-агенты
  Proxmox MCP
  клиенты Git/API/SSH
        │
        │ инициирует повторяемую настройку
        ▼
311-dev-services
  Ansible
  Semaphore
        │
        │ SSH
        ▼
109 / 211 / 321 / 331 / 401 / ...
```

В этой схеме перечислены обычные управляемые Linux-гости. `301-ai-control` не является обычной целью собственного управляющего контура и обслуживается отдельной процедурой первоначального ввода и восстановления.

Proxmox MCP остаётся инструментом уровня виртуализации:

- создание VM/LXC;
- CPU, RAM, диск и сеть;
- запуск, остановка и перезагрузка;
- снимки и резервные копии;
- жизненный цикл гостевой системы.

Ansible отвечает за повторяемые изменения внутри ОС гостевой системы:

- пакеты;
- каталоги и файлы;
- `systemd`;
- Docker/Compose;
- конфигурацию приложений;
- запуск и перезапуск сервисов;
- проверки результата.

Прямой SSH из AI Control сохраняется для первичной настройки, диагностики, разовых административных действий и аварийных сценариев. Для повторяемой настройки предпочтителен Ansible.

## Кто использует Semaphore

Semaphore предназначен прежде всего для человека. Он даёт веб-интерфейс для запуска тех же Ansible playbook, просмотра истории, результата и журналов.

Термин `playbook` оставлен без перевода как стандартная сущность Ansible.

Типовой ручной путь:

```text
пользователь
→ Semaphore
→ Ansible
→ SSH
→ нужная гостевая система
```

Semaphore не является обязательным промежуточным слоем для Hermes. Отказ или остановка Semaphore не должны мешать AI Control инициировать Ansible другим предусмотренным способом.

## Модель управляемых файлов

Не вводится универсальное зеркало файловой системы и собственная база управляемых файлов.

Проектные каталоги, полностью принадлежащие одной службе, могут управляться целиком соответствующей Ansible-ролью.

Файлы в общих системных каталогах устанавливаются только по конкретным путям. Удаление такого файла выполняется отдельной явной задачей.

Постоянные данные, Docker volumes, записи камер, пользовательские данные и другое изменяемое состояние не являются воспроизводимой конфигурацией Git и резервируются отдельно.

Пароли, токены, закрытые ключи и другие секреты в Git не хранятся.

## Первичная настройка до появления `311`

Пока `311-dev-services` ещё не развёрнут, текущий `320-ai-control` может продолжать выполнять необходимые операции первоначальной настройки напрямую по SSH. Это временный способ запуска инфраструктуры, а не целевое место размещения Ansible.

После запуска `311` Ansible и Semaphore не должны переноситься внутрь `301-ai-control`: AI Control инициирует работу, а DevOps-инструменты остаются в `311-dev-services`.
