## 1. Граница гостя

### 1.1. Почему общие голосовые службы вынесены из 410

**Проблема.**  
STT и TTS нужны не только Hermes. Ими могут пользоваться Home Assistant, Open WebUI и будущие голосовые панели.

**Рассмотренные варианты.**

- запускать STT/TTS внутри 410;
- запускать отдельные копии в каждом потребителе;
- иметь один общий сервисный гость.

**Принятое решение.**  
Общие AI- и голосовые службы размещаются на `420 ai-services`.

**Почему.**

- перезапуск Hermes не останавливает голосовые функции Home Assistant;
- одна модель не загружается в память несколько раз;
- обновление голосовых служб не требует обновлять 410;
- появляются единые точки STT/TTS API.

**Последствия и ограничения.**

- 420 становится сетевой зависимостью для потребителей;
- нужно ограничить межмашинный доступ к его портам;
- для низкой задержки важна стабильная локальная сеть.

**Когда пересматривать.**  
Если конкретная служба становится нужна только одному потребителю или требует отдельного оборудования.

## 2. Выбор готовых служб

### 2.1. Почему не пишем собственный голосовой API

**Проблема.**  
Собственный API потребовал бы поддерживать форматы аудио, потоковую передачу, модели, ошибки и совместимость клиентов.

**Принятое решение.**  
Использовать готовый OpenAI-совместимый Speaches без собственной обёртки.

**Почему.**

- готовые STT и TTS;
- стандартные OpenAI-совместимые точки API;
- поддержка CPU и GPU;
- динамическая работа с моделями;
- Open WebUI и Hermes могут обращаться к нему напрямую.

**Когда пересматривать.**  
Только если готовый проект перестанет удовлетворять обязательному контракту.

### 2.2. Почему для Home Assistant используется Wyoming OpenAI

**Проблема.**  
Home Assistant штатно работает с внешними голосовыми службами через Wyoming, а Speaches предоставляет OpenAI-совместимый API.

**Рассмотренные варианты.**

- отдельные Whisper/Piper add-on рядом с Home Assistant;
- собственный Wyoming-прокси;
- готовый Wyoming OpenAI.

**Принятое решение.**  
Использовать готовый Wyoming OpenAI как мост к тому же Speaches.

**Почему.**

- Home Assistant получает штатный Wyoming;
- Speaches остаётся единственным backend STT/TTS;
- нет второй копии моделей;
- проект не содержит самописный протокольный преобразователь.

**Когда пересматривать.**  
Если Home Assistant начнёт штатно работать с нужным OpenAI-совместимым аудио API без промежуточного Wyoming.

### 2.3. Почему новые сервисы не ставятся заранее

**Проблема.**  
AI-экосистема содержит много полезных компонентов, но установка каждого «на будущее» увеличивает расход памяти и сопровождение.

**Принятое решение.**  
openWakeWord, Speech-to-Phrase, embeddings, reranker и другие службы добавляются только после появления реальной задачи и общего потребителя.

**Почему.**

- меньше работающих контейнеров;
- понятнее назначение каждого сервиса;
- проще резервирование и обновление;
- не возникает заброшенных компонентов.

## 3. Данные и ресурсы

### 3.1. Почему модели считаются кэшем

**Проблема.**  
Модели занимают много места, но загружаются из внешнего воспроизводимого источника.

**Принятое решение.**  
Кэш моделей Speaches хранится в `/var/cache/ai-services/` и не входит в обязательную резервную копию.

**Почему.**

- восстановление возможно повторной загрузкой;
- резервные копии меньше;
- модели не являются уникальными пользовательскими данными.

**Когда пересматривать.**  
Если появится локальная дообученная или изменённая модель, которую нельзя повторно получить из внешнего источника.

### 3.2. Почему первая версия работает на CPU

**Проблема.**  
Текущий сервер не имеет выделенного GPU для 420.

**Принятое решение.**  
Первая реализация использует официальный CPU-образ Speaches и сравнительно небольшую STT-модель.

**Почему.**

- можно проверить архитектуру без нового оборудования;
- фактические замеры покажут, нужен ли GPU;
- замена CPU-образа на GPU не меняет API потребителей.

**Когда пересматривать.**  
Если задержка или качество на N150 не соответствуют требованиям голосового интерфейса.
