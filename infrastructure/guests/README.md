# Гостевые системы

`infrastructure/guests/` хранит машинные описания и локальную документацию конкретных VM/LXC.

Общий нормативный справочник всех YAML находится в:

[`../../docs/300-guests/320-guest-manifest.md`](../../docs/300-guests/320-guest-manifest.md).

## Структура

```text
guests/
├── defaults.yaml
├── README.md
└── <VMID>-<name>/
    ├── README.md
    ├── guest.yaml
    ├── provision.yaml
    ├── status.yaml
    ├── docs/
    │   ├── README.md
    │   └── decisions.md
    └── rootfs/
        ├── etc/
        └── opt/
```

Не каждый гость обязан иметь все дополнительные файлы.

## Машинные описания

| Файл | Назначение |
|---|---|
| `defaults.yaml` | общие параметры и технические профили |
| `guest.yaml` | объект VM/LXC на уровне Proxmox |
| `provision.yaml` | требуемое состояние поддерживаемой Linux-системы |
| `status.yaml` | необязательное машинное описание проверок и итогового статуса |

### `guest.yaml`

Хранит индивидуальные параметры объекта и осознанные переопределения.

Общие значения не нужно копировать из `defaults.yaml` только ради наглядности.

Наличие `profile` означает, что общий механизм может построить полное техническое состояние объекта.

Профиль не определяет владельца полного жизненного цикла: специальный объект может использовать общий профиль и при этом создаваться отдельным контуром.

### `provision.yaml`

Используется для поддерживаемых Linux-гостей.

Описывает то, что должно быть внутри ОС:

- базовую систему;
- пакеты;
- службы;
- компоненты;
- интеграции;
- постоянные и воспроизводимые данные;
- другие требования, поддерживаемые общей Ansible-логикой.

Отдельный каталог Ansible внутри гостя не создаётся. Общие playbook и roles находятся в `automation/ansible/`.

### `status.yaml`

Необязателен.

Он нужен только тогда, когда для гостя предусмотрены машинно описанные проверки готовности и единый итоговый экран.

Наличие файла требует поддержки используемых типов проверок исполняющим механизмом.

## Человеческая документация

### `README.md`

Содержит:

- назначение гостя;
- эксплуатационные особенности;
- объяснение компонентов;
- необычные условия восстановления или миграции;
- ссылки на связанные документы.

README не должен дублировать полный список машинных значений из YAML.

### `docs/decisions.md`

У сложного гостя устойчивые локальные решения хранятся вместе с подробной документацией в `docs/`.

Файл не должен превращаться в копию общей архитектуры проекта.

У уже существующих простых гостей прежнее размещение решения в корне может сохраняться до отдельной переработки их структуры.

### `STATUS.md`

Используется только для временного фактического состояния или переходного расхождения.

После устранения расхождения постоянное правило должно перейти в машинный контракт, политику или решение.

## Специальные гости

Специальный жизненный цикл не требует специального формата `guest.yaml`.

Например, управляющий LXC использует обычный профиль, общий `provision.yaml` и общий Ansible, но его объект Proxmox принадлежит отдельному первоначальному состоянию.

Поэтому нужно различать:

```text
техническая модель гостя
≠
владелец жизненного цикла объекта
```

## Управляемые файлы внутри Linux

Для файлов, которые принадлежат конкретному гостю и устанавливаются в его файловую систему, можно использовать каталог `rootfs/`.

Он повторяет конечное дерево Linux:

```text
rootfs/etc/systemd/system/example.service
→ /etc/systemd/system/example.service

rootfs/opt/example/compose.yml
→ /opt/example/compose.yml
```

`rootfs/` не является образом диска, резервной копией или механизмом автоматического зеркалирования. Общего `cp rootfs/* /` или `rsync rootfs/ /` в проекте быть не должно.

Каждый файл или каталог из `rootfs/` устанавливается явной задачей Ansible или другим явно описанным повторяемым механизмом. Он обязан задавать конечный путь, владельца, группу и права.

Общие файлы, используемые несколькими гостями, остаются в общей Ansible-роли, а не копируются в каждый `rootfs/`.

Правила размещения конфигурации и данных:

[`../../docs/300-guests/350-linux-filesystem.md`](../../docs/300-guests/350-linux-filesystem.md).

## Проверка

После изменения машинных описаний выполняется:

```bash
python scripts/validate_repo.py
```

Правила объединения `defaults.yaml + profile + guest.yaml` имеют одну общую реализацию и не должны копироваться в отдельные средства развёртывания.
