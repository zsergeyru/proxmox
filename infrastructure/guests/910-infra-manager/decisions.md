# Решения по 910 infra-manager

Этот файл хранит устойчивые архитектурные решения, относящиеся к `910 infra-manager`.

## 910 является обычным управляемым гостем

910 описывается тем же контрактом, что и остальные Linux-гости проекта:

```text
guest.yaml
→ OpenTofu
→ provision.yaml
→ общий Ansible playbook
```

Для 910 не создаётся отдельный штатный механизм настройки операционной системы.

Файлы `scripts/infra-manager/setup.sh` и команда `python3 -m infra_manager setup`
не являются штатным путём первоначального развёртывания 910 и не должны
вызываться из 990.

Если для 910 требуется новая возможность настройки, она добавляется в общий
контракт `provision.yaml` и общий Ansible-механизм либо оформляется как
узкая служебная команда, которую вызывает Ansible.

Недопустима схема:

```text
общий Ansible
→ частичная настройка
→ отдельный setup 910
→ второй оркестратор конфигурации
```

## Особенность 910 только во владельце состояния OpenTofu

910 не управляет собственным объектом Proxmox из постоянного состояния.

Первоначальное создание выполняет временный `990 bootstrap-runner`:

```text
990:
  отдельное состояние OpenTofu → содержит только 910

910:
  постоянное состояние OpenTofu → никогда не содержит 910
```

Поэтому `guest.yaml` 910 использует обычный профиль `debian-lxc-docker`,
но имеет `pve_management: false`.

Это исключение относится только к владению состоянием Proxmox и не меняет
общий способ настройки гостя через Ansible.

## 910 не входит в managed

910 не включается в pool `managed`.

Pool `managed` остаётся границей полномочий менее привилегированных контуров,
например AI Control, но не является границей полномочий самого infra-manager.

## 910 управляет VM/LXC через PVE API

Для постоянной работы используется:

```text
root@pam!infra-manager
```

Token создаётся с `privsep=1` и получает собственные ACL.

910 может управлять гостевыми системами через `/vms`, но не получает
постоянный root SSH на PVE и не должен иметь административные права на
пользователей, ACL, физическую сеть, конфигурацию хоста или определения
хранилищ.

Технически область `/vms` включает и VMID 910, однако:

- постоянное OpenTofu-состояние 910 не содержит собственный объект;
- `protection=true` защищает контейнер от случайного удаления;
- первоначальное состояние 990 является единственным состоянием, владеющим 910.

## Требуемое содержимое 910 задаёт provision.yaml

`provision.yaml` является машинно читаемым источником требований к содержимому
910.

Он должен описывать всё, что требуется внутри гостя, включая по мере реализации:

- базовые пакеты ОС;
- Docker и его службу;
- постоянные каталоги;
- контейнеры и Compose;
- `infra-runtime`;
- Semaphore;
- постоянные состояния;
- доступы и сертификаты;
- проверки готовности;
- OpenBao.

Общий Ansible-механизм обязан применять этот контракт.

Не допускается ситуация, когда существенная часть `provision.yaml` существует
только как документация, а фактическая настройка выполняется отдельным
специальным оркестратором 910.

## Python используется для узких служебных операций

Python-пакет `infra_manager` остаётся допустимым для сложных операций,
которые неудобно или неправильно реализовывать непосредственно задачами
Ansible.

Примеры:

- синхронизация объектов Semaphore;
- проверки состояния;
- работа с PVE API;
- специализированные проверки OpenTofu;
- другие изолированные операции.

Но Python-команда не должна становиться вторым полным механизмом настройки 910.

Оркестратором первоначальной настройки гостя остаётся общий Ansible playbook.

## GitHub Deploy Key

На текущем этапе read-only Deploy Key проекта создаётся первоначальным
контуром на PVE и передаётся в 910.

Это временно сохраняет существующий рабочий контракт до реализации постоянного
хранилища секретов через OpenBao.

Изменение места постоянного хранения GitHub-ключа должно выполняться отдельно
и не должно менять правило общего Ansible-развёртывания 910.

## Semaphore

Первая версия использует один постоянный `infra-runtime` с Semaphore и
инфраструктурными инструментами.

Отдельный remote Runner для одного домашнего 910 не требуется.

В первой версии Semaphore использует SQLite.

## OpenTofu state

Постоянное состояние infra-manager хранится локально внутри 910 и резервируется.

Оно:

- не хранится в Git;
- изменяется только одним заданием одновременно;
- не должно автоматически пересоздаваться пустым поверх существующей
  инфраструктуры после потери;
- никогда не содержит ресурс VMID 910.

## Неиспользуемые доступы заранее не создаются

Новые пользователи, роли и credentials не создаются «на будущее».

Правило:

```text
появилась реальная функция
→ определён необходимый доступ
→ выдан минимально необходимый доступ
```

## Критичные данные резервируются

К критичным относятся как минимум:

- база Semaphore;
- ключ шифрования Semaphore;
- OpenTofu state;
- PVE API credential;
- постоянные секреты реально используемых функций.

Потеря OpenTofu state не должна приводить к автоматическому применению нового
пустого состояния поверх существующей инфраструктуры.
