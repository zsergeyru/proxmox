# Решения по 910 infra-manager

Этот файл хранит устойчивые решения, относящиеся только к `910 infra-manager`.

## Public bootstrap владеет виртуальным объектом 910 и bootstrap credential

`910` создаётся и восстанавливается публичным `bootstrap-pve.sh`.

Публичный сценарий отвечает только за минимальную основу, необходимую до запуска закрытого проекта:

- виртуальный объект 910;
- постоянный read-only GitHub Deploy Key на PVE;
- передачу копии этого ключа внутрь 910;
- получение закрытого проекта;
- запуск закрытого PVE access helper;
- передачу управления `setup.sh`.

Docker, Semaphore, OpenTofu, Ansible и Packer принадлежат внутренней настройке 910.

## 910 не входит в managed

`910` не включается в pool `managed`.

OpenTofu не создаёт и не изменяет собственный виртуальный объект разворачивателя.

## 910 управляет всеми VM/LXC через PVE API

API token 910 получает штатную роль `PVEVMAdmin` на пути:

```text
/vms
```

Для домашнего сервера отдельное разделение VM/LXC по нескольким pool только ради infra-manager не используется.

Pool `managed` сохраняется как граница полномочий AI Control, но не как граница 910.

Это означает:

- 910 может создавать и сопровождать любые VM/LXC, включая управляющие гости;
- 910 технически имеет VM-права и на собственный LXC;
- собственный объект 910 не включается в OpenTofu и остаётся во владении public bootstrap;
- изменение пользователей, ACL, конфигурации PVE-хоста, сети и определений хранилищ этими правами не разрешается.

## Нет root SSH на PVE

Штатное управление Proxmox из 910 выполняется через HTTPS API.

Постоянный root SSH с 910 на физический PVE не используется.

## Один ограниченный PVE API token

Для первой версии используется:

```text
root@pam!infra-manager
```

Token создаётся с `privsep=1` и получает собственные ACL.

Отдельный пользователь `infra-manager@pve`, двойные ACL и собственная роль `InfraManagedGuest` не используются.

Новые PVE-идентичности не создаются заранее для будущих функций.

## Semaphore Server и Runner разделены

Semaphore Server отвечает за интерфейс, задания, историю, расписания и секреты.

Semaphore Runner выполняет инфраструктурные команды и содержит OpenTofu, Ansible, Packer и необходимые зависимости.

## SQLite используется в первой версии

Для одного домашнего сервера отдельная PostgreSQL-база не требуется.

Semaphore использует SQLite. Переход на отдельную СУБД допускается только при практической необходимости.

## OpenTofu state хранится локально

Первая версия использует локальное постоянное состояние внутри 910.

State не хранится в Git, резервируется и изменяется только одним заданием одновременно.

## Неиспользуемые credentials заранее не создаются

Первая версия не создаёт отдельный PVE credential в Semaphore Key Store.

Ansible SSH credential также не создаётся до появления первой реальной Ansible-задачи.

Правило:

```text
сначала появляется функция
→ определяется необходимый доступ
→ создаётся credential
```

а не наоборот.

## GitHub Deploy Key хранится на PVE и копируется в 910

Постоянный read-only ключ закрытого проекта создаётся публичным bootstrap и хранится на PVE:

```text
/root/.config/proxmox-bootstrap/github_proxmox_repo_ed25519
```

Внутрь 910 передаётся копия этого же ключа для чтения закрытого проекта. Отдельный GitHub Deploy Key внутри 910 не создаётся.

PVE-хост хранит private key bootstrap, но не содержит постоянную закрытую Git-копию проекта.

При мягком удалении и повторном создании 910 ключ на PVE сохраняется и используется повторно. При полном удалении bootstrap-состояния ключ удаляется.

Добавление public key в GitHub — единственное обязательное ручное действие первого запуска.

## Критичные данные резервируются

К критичным относятся:

- база Semaphore;
- ключ шифрования Semaphore;
- OpenTofu state;
- PVE API credential;
- постоянные секреты реально используемых функций.

Потеря OpenTofu state не должна приводить к автоматическому `apply` с новым пустым состоянием поверх существующей инфраструктуры.


## 910 имеет guest.yaml без profile

910 должен быть видим проекту как полноценная гостевая система и иметь собственный `guest.yaml`.

Поле `profile` намеренно отсутствует. Это означает:

- общая проверка репозитория видит VMID, имя и постоянные параметры 910;
- обычный генератор OpenTofu пропускает 910;
- наличие манифеста не передаёт жизненный цикл объекта OpenTofu;
- владельцем создания, удаления и восстановления LXC остаётся публичный `proxmox-bootstrap`.

Такое исключение предпочтительнее отсутствия `guest.yaml`: параметры 910 находятся рядом с остальными гостями, но сам управляющий узел не начинает управлять собственным жизненным циклом.

## Требуемое содержимое 910 хранится в provision.yaml

`provision.yaml` фиксирует машинно читаемые требования к содержимому 910:

- базовые пакеты ОС;
- Docker и его службу;
- единый контейнер `infra-runtime` с Semaphore;
- OpenTofu, Packer, Ansible и их версии;
- постоянные пути;
- области обязательного резервного копирования;
- используемые внешние доступы;
- штатные проверки.

`setup.sh`, Compose и Dockerfile являются реализацией этих требований. При изменении состава 910 они должны меняться вместе с `provision.yaml` и проверками контракта.


## OpenBao является центральным хранилищем машинных секретов

OpenBao размещается отдельным Docker-контейнером внутри 910 и не объединяется с infra-runtime.

Первая версия использует один узел, Integrated Storage (Raft), KV v2, policies и AppRole. Дополнительные возможности включаются только по практической необходимости.

Постоянные данные OpenBao должны быть приведены к общему контракту Linux-гостей и храниться под:

~~~text
/var/lib/persistent/openbao/
~~~

## Обычный unseal выполняет PVE

После перезапуска OpenBao обычный unseal должен происходить автоматически без ручного ввода.

Ключ обычного unseal хранится на PVE вне 910. PVE использует небольшой systemd oneshot и штатный pct; отдельный постоянно работающий сервер или дополнительные пакетные зависимости на PVE не требуются.

Аварийные данные восстановления OpenBao хранятся отдельно от PVE и 910.

Автоматический механизм не выполняет первоначальную инициализацию нового OpenBao.

## OpenBao резервируется штатным Raft snapshot

Перед общей резервной копией постоянных данных 910 создаётся штатный Raft snapshot OpenBao.

Снимок сохраняется под /var/lib/persistent/ и попадает в единое резервное копирование гостя.

Потеря базы OpenBao допускает создание нового хранилища и перевыпуск машинных секретов там, где это возможно. Политики и роли OpenBao хранятся как требуемое состояние в Git.
