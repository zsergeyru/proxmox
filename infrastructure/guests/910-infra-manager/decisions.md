# Решения по 910 infra-manager

Этот файл хранит устойчивые архитектурные решения, относящиеся к `910 infra-manager`.

## 910 является обычным управляемым гостем

910 описывается тем же контрактом, что и остальные Linux-гости проекта:

```text
guest.yaml
→ OpenTofu
→ provision.yaml
→ общий Ansible playbook
```

Для 910 не создаётся отдельный штатный механизм настройки операционной системы.

Отдельный `setup.sh` и команда `infra_manager setup` удалены.
Возврат отдельного полного оркестратора настройки 910 запрещён архитектурным
контрактом и проверяется CI.

Если для 910 требуется новая возможность настройки, она добавляется в общий
контракт `provision.yaml` и общий Ansible-механизм либо оформляется как
узкая служебная команда, которую вызывает Ansible.

Недопустима схема:

```text
общий Ansible
→ частичная настройка
→ отдельный setup 910
→ второй оркестратор конфигурации
```

## Особенность 910 только во владельце состояния OpenTofu

910 не управляет собственным объектом Proxmox из постоянного состояния.

Первоначальное создание выполняет временный `990 bootstrap-runner`:

```text
990:
  отдельное состояние OpenTofu → содержит только 910

910:
  постоянное состояние OpenTofu → никогда не содержит 910
```

Поэтому `guest.yaml` 910 использует обычный профиль `debian-lxc-docker`,
но имеет `pve_management: false`.

Это исключение относится только к владению состоянием Proxmox и не меняет
общий способ настройки гостя через Ansible.

## Обычное обновление 910 выполняет тот же Deploy Guest

После первоначального создания 910 обновляется из собственного Semaphore заданием `Deploy Guest 910`.

Это не отдельный механизм настройки:

```text
Deploy Guest 410 → OpenTofu + общий Ansible
Deploy Guest 910 → проверка существующего объекта + общий Ansible
```

Различие существует только из-за владения объектом Proxmox: постоянный OpenTofu state 910 не может содержать собственный VMID 910. При самообновлении OpenTofu для 910 не инициализируется и не изменяется.

Постоянный Ansible-ключ 910 разрешён самому 910 отдельным управляемым блоком `authorized_keys`. Для первого перехода или восстановления этого блока 910 использует свой постоянный root SSH-доступ к PVE; перед изменением PVE обязан подтвердить hostname и метку владения VMID 910.

Semaphore выполняет задания внутри `infra-runtime`. Поэтому самообновление сначала собирает новый образ, завершает Ansible и только затем назначает активацию новой управляющей среды. Перезапуск текущего `infra-runtime` посреди задания запрещён, потому что это оборвало бы само задание Semaphore.

## 910 не входит в managed

910 не включается в pool `managed`.

Pool `managed` остаётся границей полномочий менее привилегированных контуров,
например AI Control, но не является границей полномочий самого infra-manager.

## 910 является доверенным административным контуром PVE

Для постоянной работы используются два канала:

```text
root@pam!infra-manager, privsep=0
→ HTTPS API
→ OpenTofu и обычные операции PVE

отдельный root SSH-ключ
→ операции PVE, которые запрещены API token
```

Отдельная матрица ACL для 910 больше не поддерживается.

Это осознанное упрощение для одного домашнего PVE: компрометация 910
рассматривается как компрометация административного контура гипервизора.

При этом AI Control и прикладные гости не получают ни API secret 910,
ни root SSH-ключ PVE.

Объект 910 по-прежнему имеет особое владение состоянием:

- постоянное OpenTofu-состояние 910 не содержит собственный объект;
- `protection=true` защищает контейнер от случайного удаления;
- первоначальное состояние 990 является единственным состоянием, владеющим 910.

Профиль `container-host` остаётся общим для 910 и других Docker-LXC:
`nesting=1` применяет OpenTofu через API, а `keyctl=1` — общий host-only
слой через root SSH.

## Требуемое содержимое 910 задаёт provision.yaml

`provision.yaml` является машинно читаемым источником требований к содержимому
910.

Он должен описывать всё, что требуется внутри гостя, включая по мере реализации:

- базовые пакеты ОС;
- Docker и его службу;
- постоянные каталоги;
- контейнеры и Compose;
- `infra-runtime`;
- Semaphore;
- постоянные состояния;
- доступы и сертификаты;
- проверки готовности;
- OpenBao.

Общий Ansible-механизм обязан применять этот контракт.

Не допускается ситуация, когда существенная часть `provision.yaml` существует
только как документация, а фактическая настройка выполняется отдельным
специальным оркестратором 910.

## Python используется для узких служебных операций

Python-пакет `infra_manager` остаётся допустимым для сложных операций,
которые неудобно или неправильно реализовывать непосредственно задачами
Ansible.

Примеры:

- синхронизация объектов Semaphore;
- проверки состояния;
- работа с PVE API;
- специализированные проверки OpenTofu;
- другие изолированные операции.

Но Python-команда не должна становиться вторым полным механизмом настройки 910.

Оркестратором первоначальной настройки гостя остаётся общий Ansible playbook.

## Данные PVE и состояние 910 разделяются по владельцу

Целевая модель — не хранить важное состояние только внутри rootfs 910.

На PVE выделяется единый корневой каталог:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

Подкаталоги имеют разное назначение и не монтируются целиком одной общей
областью.

`pve-only/` принадлежит только PVE и никогда не показывается 910. Здесь
должны находиться секреты, которые теряют смысл при доступе из 910, прежде
всего ключ снятия блокировки OpenBao.

`access/` принадлежит PVE, но доступен 910 только для чтения. Сюда относятся
данные, необходимые ещё до создания или полного восстановления 910:

- read-only GitHub Deploy Key проекта;
- отдельный root SSH-ключ доступа 910 к PVE;
- `known_hosts` PVE;
- PVE CA;
- другие постоянные данные доступа, если они действительно должны иметь
  владельцем PVE.

Для этих файлов PVE является единственным источником истины. После реализации
этой схемы постоянные копии тех же файлов внутри rootfs 910 не создаются.

`state/` содержит состояние сервисов 910, которое должно переживать
уничтожение и повторное создание самого LXC:

- Raft-данные OpenBao;
- постоянный OpenTofu state;
- SQLite и служебные данные Semaphore;
- постоянную Ansible-идентичность;
- постоянные секреты и ключи шифрования, владельцем которых является 910.

Этот каталог доступен 910 на запись. Внутри гостя привычные пути могут
сохраняться через привязки или символические ссылки, но физическим источником
данных является PVE.

Git checkout проекта к постоянному состоянию не относится. Репозиторий
клонируется локально в 910 и после пересоздания гостя получается заново из
GitHub. То же правило действует для Docker-образов, Compose-файлов,
установленного Python-кода, кэшей и других воспроизводимых файлов.

Цель разделения:

```text
удалить 910
→ создать чистый 910
→ подключить access/ и state/
→ заново получить код и программы
→ продолжить работу с прежним состоянием
```

Потеря каталога `state/` не считается штатным способом очистки инфраструктуры.
Большую часть состояния можно восстановить вручную или пересоздать, но
автоматизация не должна молча создавать пустое состояние поверх существующих
объектов PVE.

Текущие пути на живой системе остаются действующими до отдельной миграции.
Настоящее решение фиксирует целевую архитектуру; перенос существующих данных
в bind mount выполняется отдельным изменением с остановкой соответствующих
служб и проверкой владельцев UID/GID для непривилегированного LXC.

## Semaphore

Первая версия использует один постоянный `infra-runtime` с Semaphore и
инфраструктурными инструментами.

Отдельный remote Runner для одного домашнего 910 не требуется.

В первой версии Semaphore использует SQLite.

## OpenTofu state

Постоянное состояние OpenTofu относится к `state/` и в целевой схеме
физически хранится на PVE, а не только в rootfs 910.

Оно:

- не хранится в Git;
- изменяется только одним заданием одновременно;
- не должно автоматически пересоздаваться пустым поверх существующей
  инфраструктуры после потери;
- никогда не содержит ресурс VMID 910;
- должно переживать уничтожение и повторное создание LXC 910.

## Неиспользуемые доступы заранее не создаются

Новые пользователи, роли и credentials не создаются «на будущее».

Правило:

```text
появилась реальная функция
→ определён необходимый доступ
→ выдан минимально необходимый доступ
```

## Постоянное состояние не равно резервной копии

Вынос состояния из rootfs 910 защищает от пересоздания самого LXC, но не
заменяет резервное копирование PVE.

К важному состоянию относятся как минимум:

- Raft-данные OpenBao;
- база Semaphore;
- ключ шифрования Semaphore;
- OpenTofu state;
- постоянная Ansible-идентичность;
- постоянные секреты реально используемых функций.

Отдельно сохраняются данные `pve-only/` и `access/`.

Bind mount не должен восприниматься как резервная копия. Для каталогов на PVE
должен появиться отдельный механизм резервного копирования, потому что
резервная копия rootfs 910 сама по себе не гарантирует сохранение данных,
которые физически находятся на PVE.

Потеря OpenTofu state не должна приводить к автоматическому применению нового
пустого состояния поверх существующей инфраструктуры.
