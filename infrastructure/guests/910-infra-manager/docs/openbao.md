# OpenBao на 910 infra-manager

**Назначение:** объяснить, как OpenBao размещён на 910, где хранится его состояние, как он разблокируется, какие секреты и SSH-механизмы обслуживает и что требуется для восстановления.

Нормативные правила безопасности OpenBao задаёт [`740-openbao.md`](../../../../docs/700-security/740-openbao.md). Здесь описано устройство именно 910.

## 1. Где работает OpenBao

OpenBao работает в отдельном Docker-контейнере:

```text
openbao
```

Текущий образ задаётся в [`../provision.yaml`](../provision.yaml). Сейчас используется:

```text
ghcr.io/openbao/openbao:2.7.0
```

Контейнер OpenBao сейчас запускается от пользователя `root` внутри контейнера. Постоянный каталог данных на уровне 910 также закрыт правами `root`.

Для клиента внутри контейнера задаются:

```text
BAO_ADDR=http://127.0.0.1:8200
BAO_LOG_LEVEL=info
```

### 1.1. Сеть

Контейнер использует сеть 910 напрямую:

```text
network_mode: host
```

В текущей реализации OpenBao слушает только локальный адрес:

```text
127.0.0.1:8200
```

Кластерный адрес:

```text
127.0.0.1:8201
```

Текущая локальная связь внутри 910 работает без TLS, потому что интерфейс не выходит за пределы loopback.

### 1.2. Веб-интерфейс

Веб-интерфейс OpenBao отключён:

```text
ui = false
```

Управление выполняется через API и служебные команды проекта.

## 2. Постоянное состояние

OpenBao использует Raft.

### 2.1. Каталог данных

В контейнере Raft находится под:

```text
/openbao/file/raft
```

Этот путь подключён к постоянной области 910:

```text
/mnt/persistent-state/openbao
```

Внутри 910 тот же постоянный каталог доступен также через:

```text
/var/lib/persistent/openbao
```

Идентификатор Raft-узла:

```text
infra-manager-910
```

### 2.2. Что хранится в Raft

В постоянном состоянии OpenBao находятся:

- KV v2 с рабочими секретами;
- закрытый ключ пользовательского SSH CA;
- закрытый ключ CA SSH-серверов;
- политики;
- роли;
- настройки AppRole;
- служебные данные аутентификации;
- после реализации OTP — OTP-роли и машинные AppRole.

Закрытые ключи CA отдельно из OpenBao не экспортируются.

Потеря Raft означает потерю не только базы OpenBao, но и прежних центров доверия.

## 3. Инициализация

OpenBao не инициализируется автоматически простым запуском контейнера.

В [`../provision.yaml`](../provision.yaml) это закреплено как:

```text
auto_initialize: false
```

### 3.1. Штатная операция

Первичная настройка выполняется тем же сценарием, который доступен в Semaphore как:

```text
Initialize OpenBao 910
```

Операция должна быть повторяемой: уже существующий корректный OpenBao не пересоздаётся.

### 3.2. Что создаётся при первой инициализации

Первичная настройка:

1. инициализирует OpenBao;
2. сохраняет ключ снятия блокировки только на PVE;
3. разблокирует OpenBao;
4. создаёт KV v2 `infra-secrets`;
5. переносит рабочие секреты PVE, Git и Semaphore;
6. создаёт ограниченные служебные AppRole;
7. создаёт SSH client CA;
8. создаёт CA SSH-серверов;
9. создаёт необходимые роли подписи;
10. материализует рабочие секреты в `/run`;
11. отзывает первоначальный корневой токен;
12. проверяет итоговое состояние.

Постоянный корневой токен не хранится.

## 4. Разблокировка

Ключ снятия блокировки не находится внутри 910.

### 4.1. Владелец ключа

Ключ хранится в PVE-only области.

Это означает:

```text
910
  не читает unseal key
      ↓
при необходимости просит PVE
      ↓
PVE выполняет узкую операцию разблокировки
```

910 подключается к PVE отдельным SSH-ключом пользователя `root` и вызывает только предусмотренную служебную команду.

### 4.2. Запуск вместе с 910

В 910 установлена служба:

```text
infra-manager-openbao-startup-unseal.service
```

Она запускается после сети и Docker.

Служба:

1. ждёт появления API OpenBao;
2. читает `seal-status`;
3. если OpenBao ещё не инициализирован — завершает работу без ошибки;
4. если OpenBao уже разблокирован — ничего не меняет;
5. если он запечатан — вызывает PVE-only команду разблокировки;
6. повторно проверяет состояние.

Ожидание ограничено тремя минутами на уровне systemd-службы.

### 4.3. Почему нет периодического таймера разблокировки

Старая периодическая служба разблокировки на PVE удаляется.

Штатная модель:

- запуск 910 — одноразовая проверка и разблокировка;
- активация новой рабочей среды — явная проверка и разблокировка;
- обычная работа — без постоянного чтения ключа снятия блокировки.

Если вручную перезапустить только контейнер OpenBao вне этих путей, он может остаться запечатан. `infra-manager-status` должен это показать.

## 5. Рабочие секреты

OpenBao является постоянным источником рабочих секретов управляющего контура.

### 5.1. KV v2

Используется отдельное хранилище:

```text
infra-secrets
```

Основные логические данные:

- секрет PVE API;
- read-only Git Deploy Key;
- секреты Semaphore.

Точные пути и политики определены в [`740-openbao.md`](../../../../docs/700-security/740-openbao.md).

### 5.2. Материализация

Программы внутри 910 не читают Raft напрямую.

Нужные значения временно создаются в:

```text
/run/infra-manager/secrets/
```

После перезапуска 910 эта область создаётся заново из OpenBao.

Такой файл является рабочим представлением секрета, а не его постоянным источником.

### 5.3. Первоначальный запуск

До первой инициализации OpenBao временно используются:

```text
/run/infra-manager/bootstrap-secrets/
```

После успешного переноса рабочих значений в OpenBao первоначальные копии должны быть удалены.

## 6. Служебные AppRole

Постоянные служебные данные AppRole управляющего контура хранятся только на PVE.

### 6.1. Зачем это нужно

910 не должен постоянно иметь универсальные данные, которыми можно:

- перенастраивать OpenBao;
- разблокировать OpenBao;
- читать все секреты;
- подписывать произвольные SSH-сертификаты.

PVE использует отдельные узкие AppRole для конкретных операций.

### 6.2. Восстановление служебных AppRole

Некоторые служебные AppRole являются воспроизводимыми.

Если сохранены:

- Raft;
- ключ снятия блокировки;

то потерянные служебные AppRole можно создать заново через кратковременную восстановительную операцию с временным корневым токеном.

После восстановления корневой токен сразу отзывается.

Это не относится к потере самого Raft.

## 7. SSH-центры доверия

OpenBao хранит два независимых SSH CA.

### 7.1. Пользовательский CA

```text
ssh-client-signer
```

Он используется для краткоживущих сертификатов административного входа Ansible.

Закрытый ключ остаётся внутри OpenBao.

Открытый ключ публикуется в 910:

```text
/etc/infra-manager/ca/ssh-client-ca.pub
```

и устанавливается на управляемые Linux-гости.

### 7.2. CA серверов

```text
ssh-host-signer
```

Он подписывает реальные ключи SSH-серверов управляемых Linux-гостей.

Этот CA отвечает на другой вопрос: не «кто может войти», а «к какому серверу мы подключились».

Поэтому два CA не объединяются.

## 8. Межмашинный SSH OTP

Целевая архитектура `guest → guest` использует OpenBao SSH OTP.

### 8.1. Что должно появиться

Целевая схема требует:

- отдельный механизм SSH OTP в OpenBao с именем `ssh-otp`;
- отдельный машинный AppRole для каждого разрешённого источника;
- OTP-роль, построенную из `access.yaml`;
- защищённый сетевой доступ гостей к OpenBao;
- проверку OTP на целевом госте;
- строгую проверку сертификата SSH-сервера цели.

### 8.2. Сетевой вход для OTP

Текущий OpenBao доступен только через `127.0.0.1` и поэтому ещё не может обслуживать OTP между разными гостями.

Для целевой схемы нужен дополнительный сетевой вход OpenBao:

- только по TLS;
- только из административной сети;
- с обязательной проверкой сертификата;
- без выдачи гостям PVE-only полномочий;
- с отдельными ограниченными машинными AppRole.

Открывать текущий HTTP-порт `8200` в сеть без TLS запрещено.

### 8.3. Текущее переходное состояние

Код пока использует старую схему машинных SSH-сертификатов:

- роли `machine-<VMID>`;
- двухчасовые сертификаты;
- `AuthorizedPrincipalsFile`;
- таймер обновления сертификатов.

Эта схема больше не является целевой.

Её состояние и план замены зафиксированы в [`780-implementation-status.md`](../../../../docs/700-security/780-implementation-status.md).

## 9. Запуск контейнера

Ansible запускает OpenBao раньше всей рабочей среды.

### 9.1. Последовательность

При обычной полной настройке:

1. собирается новая версия `infra-runtime`;
2. запускается контейнер OpenBao;
3. запускается рабочая среда, если это не самообновление 910;
4. выполняется проверка и разблокировка OpenBao.

При самообновлении 910 пересоздание `infra-runtime` откладывается до завершения текущего задания. Подробности находятся в [`infra-runtime.md`](infra-runtime.md).

### 9.2. Перезапуск

У контейнера настроено:

```text
restart: unless-stopped
```

Docker пытается вернуть контейнер после обычного сбоя или перезапуска Docker, но это не отменяет необходимость разблокировки OpenBao после его нового запуска.

## 10. Проверка состояния

Основная команда:

```bash
infra-manager-status --full
```

### 10.1. Что проверяется

Проверка OpenBao подтверждает:

- контейнер `openbao` запущен;
- API на `127.0.0.1:8200` отвечает;
- поля `initialized` и `sealed` имеют корректный вид;
- инициализированный OpenBao не остаётся запечатанным;
- доступ к обязательным KV-данным работает;
- при полной проверке исправен аварийный PVE-only контур.

Если OpenBao ещё не инициализирован во время первоначального создания, сам факт `initialized=false` допустим до выполнения `Initialize OpenBao 910`.

## 11. Резервирование

Raft OpenBao является критичным постоянным состоянием.

### 11.1. Что нужно сохранить вместе

Для полноценного восстановления нужны согласованные части:

- Raft-состояние;
- ключ снятия блокировки;
- обязательные PVE-only данные;
- сведения, необходимые аварийному контуру;
- резервная копия аварийного Git key.

Сохранять только каталог Raft без возможности получить ключ снятия блокировки недостаточно.

### 11.2. Что не нужно экспортировать отдельно

Отдельно не требуется экспортировать:

- закрытые SSH CA;
- корневой токен;
- рабочие копии секретов из `/run`.

Закрытые CA уже входят в Raft, постоянный корневой токен отсутствует, а `/run` восстанавливается из OpenBao.

### 11.3. Запрет пустой повторной инициализации

Если Raft потерян, автоматическое создание нового пустого OpenBao поверх существующей инфраструктуры запрещено.

Это создало бы новые CA и новые секреты, то есть другую систему доверия.

Порядок восстановления определён в [`830-recovery.md`](../../../../docs/800-operations/830-recovery.md).
