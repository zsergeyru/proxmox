# Локальный портал 910

Этот документ задаёт целевое состояние локального портала гостя `910 infra-manager`.

Портал предназначен для быстрого перехода к службам гостя, просмотра их доступности и запуска стандартных операций обслуживания. Он не заменяет Semaphore, OpenBao или проверки `status.yaml`.

## 1. Назначение и границы

### 1.1. Роль портала

На 910 используется Homepage.

Homepage является локальной страницей конкретного гостя. Он показывает только службы и действия, относящиеся к 910.

Общий пользовательский портал квартиры находится вне 910 и не должен дублировать локальную техническую страницу гостя.

### 1.2. Источники данных

Машинным источником описания портала является `provision.yaml`.

`guest.yaml` продолжает описывать только объект LXC в Proxmox: VMID, роль, профиль, ресурсы, сеть и запуск.

В `provision.yaml` верхнеуровневый раздел `portal.local` включает локальный портал и задаёт его заголовок. Публикация отдельной службы задаётся в описании этой службы через `portal.targets`.

Адрес гостя не повторяется в каждой службе. Для локальной службы задаются протокол, порт и при необходимости путь. Итоговый адрес строится автоматизацией из административного IPv4 гостя из `guest.yaml`.

## 2. Требуемое состояние

### 2.1. Локальный портал

Для 910 требуется:

```yaml
portal:
  local:
    enabled: true
    title: Управление инфраструктурой
    trusted_ca: /etc/infra-manager/openbao/tls/ca.crt
```

Включённый локальный портал автоматически получает стандартные действия обслуживания гостя. Отдельный флаг `management` не используется.

Внешний вид не задаётся отдельно для 910. Общая роль `portal` применяет единый технологичный стиль: тёмный фон с шестигранной сеткой, крупный заголовок `Управление инфраструктурой`, неоновые панели, голубые карточки служб и три цветных действия — зелёное `Проверить`, синее `Синхронизировать` и оранжевое `Исправить`. Заголовок и номер гостя подставляются из машинного описания, поэтому тот же шаблон подходит другим локальным панелям.

### 2.2. Публикация служб

Semaphore публикуется локально:

```yaml
portal:
  name: Semaphore
  description: Задачи и автоматизация
  icon: mdi-server-#38bdf8
  scheme: http
  port: 3000
  targets:
    - local
```

OpenBao публикуется локально:

```yaml
portal:
  name: OpenBao
  description: Хранилище секретов
  icon: mdi-lock-#e0f2fe
  scheme: https
  port: 8202
  path: /ui/
  targets:
    - local
```

Значения `targets` являются логическими назначениями, а не именами программ.

Допустимые назначения:

- `local` — локальный Homepage гостя;
- `home` — общий портал квартиры.

Если раздел `portal` у службы отсутствует, служба не публикуется в порталах.

## 3. Службы и действия

### 3.1. Отображаемые службы

На странице 910 должны быть доступны как минимум:

- Semaphore;
- OpenBao.

Для каждой опубликованной службы Homepage должен показывать ссылку и индикатор доступности через `siteMonitor`. Для OpenBao используется его HTTPS-адрес, а контейнер Homepage доверяет внутреннему TLS CA из `/etc/infra-manager/openbao/tls/ca.crt`. Поэтому зелёная точка OpenBao означает успешный ответ именно HTTPS-службы, а не только доступность гостя.

Технические контейнеры и внутренние компоненты без пользовательского интерфейса не публикуются только ради полноты списка.

### 3.2. Стандартные действия гостя

Локальный портал предоставляет три действия:

- **Проверить** — запускает общую операцию `status`;
- **Синхронизировать** — запускает общую операцию `sync`;
- **Исправить** — запускает общую операцию `repair`.

Действия не выполняют команды Proxmox, SSH или Ansible непосредственно из браузера.

Homepage открывает ограниченный посредник на 910. Переход по ссылке выполняется безопасным GET и только показывает страницу подтверждения. После подтверждения POST посредник запускает установленную операторскую команду `infra-manager status|sync|repair VMID` напрямую, без создания задания Semaphore.

Цепочка должна оставаться такой:

```text
Homepage
   -> посредник действий 910
      -> подтверждение
         -> общий операторский слой 910
            -> status / sync / repair
               -> общий механизм обслуживания гостя
```

Semaphore остаётся отдельным пользовательским интерфейсом, историей и планировщиком и может запускать тот же общий механизм из собственных шаблонов, но не является промежуточным слоем для Homepage.

Посредник принимает только белый список `status/sync/repair`, не принимает произвольные команды или аргументы, не передаёт признак `--trusted-pve` и поэтому не выводит операторские секреты. GET никогда не запускает операцию. Изменяющий POST принимается только со страницы самого посредника по проверке `Origin`. Вывод команды экранируется как текст и показывается на странице результата по мере выполнения.

### 3.3. Особенность 910

910 использует те же стандартные действия, что и другие постоянные управляемые Linux-гости.

Его особенность относится не к порталу, а к жизненному циклу объекта Proxmox:

- `pve_management: false`;
- OpenTofu не должен пересоздавать собственный LXC 910;
- первоначальное создание 910 выполняется внешним начальным контуром.

Эти ограничения не запрещают проверять, синхронизировать и исправлять внутреннее состояние 910.

## 4. Развёртывание и проверка

### 4.1. Развёртывание

Повторяемая автоматизация должна:

1. прочитать `portal.local` и описания `portal` у служб из `provision.yaml`;
2. получить административный IPv4 из `guest.yaml`;
3. установить или обновить Homepage;
4. сформировать конфигурацию опубликованных служб;
5. настроить стандартные действия обслуживания;
6. запустить портал;
7. повторно применять те же действия при синхронизации гостя без ручной правки конфигурации.

Файлы Homepage, которые создаются из машинного описания, считаются воспроизводимыми.

### 4.2. Проверка

После развёртывания должно подтверждаться:

- Homepage запущен;
- страница 910 открывается по локальному адресу;
- ссылки Semaphore и OpenBao сформированы из адреса гостя и параметров службы;
- Semaphore открывается;
- OpenBao открывается по TLS на `:8202/ui/`;
- действия `Проверить`, `Синхронизировать`, `Исправить` показывают подтверждение, выполняются напрямую через общий операторский слой и показывают живой журнал без секретов;
- повторная синхронизация восстанавливает конфигурацию портала из Git.
