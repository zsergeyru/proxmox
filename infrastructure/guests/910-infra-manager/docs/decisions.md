# Решения по 910 infra-manager

**Назначение:** сохранить причины решений, которые относятся именно к 910 и не должны теряться при изменении реализации.

Подробное устройство служб находится в [`docs/README.md`](README.md). Общепроектные решения по безопасности, хранению и гостям находятся в основной документации.

## 1. Единый способ управления гостями

### 1.1. 910 настраивается общим Ansible-механизмом

**Проблема.**  
910 сложнее обычного гостя, поэтому легко создать для него отдельный способ установки и постепенно получить две разные системы настройки Linux.

**Решение.**  
910 использует тот же общий путь, что и остальные Linux-гости:

```text
guest.yaml
→ OpenTofu, если объект принадлежит этому состоянию
→ provision.yaml
→ общий Ansible
```

Отдельного полного `setup.sh` или второго оркестратора 910 быть не должно.

**Почему.**

- одно правило проще проверять;
- общие роли исправляются один раз;
- требования к 910 остаются в `provision.yaml`;
- уменьшается риск, что документация, Ansible и отдельный установщик начнут расходиться.

**Последствия.**  
Специальная логика допустима только как узкая служебная команда, которую вызывает общий Ansible, если обычных задач Ansible недостаточно.

### 1.2. 910 не владеет собственным объектом Proxmox

**Проблема.**  
Постоянный управляющий контур не должен зависеть от состояния OpenTofu, в котором он сам описан как управляемый объект.

**Решение.**  
Первоначальный контур создаёт 910 отдельным состоянием. Постоянное состояние OpenTofu внутри 910 никогда не содержит VMID 910.

```text
первоначальный контур
→ отдельное состояние
→ владеет объектом 910

910
→ постоянное состояние
→ управляет другими объектами
→ не содержит 910
```

**Почему.**

- 910 не может безопасно уничтожать или пересоздавать собственный LXC;
- потеря постоянного состояния 910 не должна менять владельца его объекта;
- граница владения остаётся понятной.

**Последствия.**  
В `guest.yaml` 910 используется `pve_management: false`. Это исключение касается только владения объектом Proxmox и не создаёт отдельный способ настройки ОС.

### 1.3. Обычное обновление выполняется через Deploy Guest 910

**Проблема.**  
После первого создания 910 нужно обновлять тем же способом, что и остальные гости, но нельзя применять к самому 910 его постоянное состояние OpenTofu.

**Решение.**  
Semaphore запускает:

```text
Deploy Guest 910
```

Сценарий проверяет существующий LXC и применяет общий Ansible без добавления 910 в постоянное состояние OpenTofu.

**Почему.**

- не нужен постоянный временный 990;
- обновление использует тот же код `deploy-guest`;
- отличия 910 ограничены только тем, чем действительно отличаются его границы владения.

**Последствия.**  
Поскольку задание выполняется внутри `infra-runtime`, новую версию контейнера нельзя активировать до окончания самого задания. Поэтому используется отложенная активация снаружи контейнера.

Подробности находятся в [`docs/infra-runtime.md`](infra-runtime.md).

## 2. Граница доверия

### 2.1. 910 является административно доверенным контуром PVE

**Проблема.**  
910 должен создавать и изменять инфраструктуру, а часть обязательных операций требует административных полномочий PVE.

**Решение.**  
910 считается административно доверенным контуром домашнего PVE.

Основные каналы:

```text
root@pam!infra-manager, privsep=0
→ PVE API
→ обычные операции и OpenTofu

отдельный SSH-доступ пользователя root
→ только операции физического PVE,
  которые нельзя выполнить обычным API-токеном
```

**Почему.**

- полная компрометация 910 всё равно затрагивает управление инфраструктурой;
- сложная искусственная матрица ограничений для самого управляющего контура не даёт достаточной дополнительной защиты;
- менее доверенные системы ограничиваются отдельно.

**Последствия.**

- секреты 910 требуют высокой защиты;
- root SSH к PVE остаётся отдельным каналом;
- прикладные гости и AI Control не получают эти данные.

Общие правила доступа задаёт [`710-pve-access.md`](../../../../docs/700-security/710-pve-access.md).

### 2.2. 910 не входит в pool managed

**Проблема.**  
`managed` используется как граница для менее доверенных операций над обычными гостями. Если туда включить 910, такое право может случайно затронуть сам управляющий контур.

**Решение.**  
910 не входит в `pool managed`.

**Почему.**  
Право управлять обычными гостями не должно автоматически давать право изменять infra-manager.

**Последствия.**  
Например, AI Control может получить ограниченные действия в `managed`, не получая управление 910.

### 2.3. Неиспользуемые права заранее не создаются

**Проблема.**  
Учётные записи и полномочия «на будущее» трудно проверять и легко забыть.

**Решение.**

```text
появилась реальная функция
→ определено нужное право
→ выдано минимально необходимое право
```

**Почему.**  
Отсутствующий доступ безопаснее неиспользуемого доступа.

**Последствия.**  
Новая возможность сначала должна получить явное описание в `access.yaml`, а уже затем техническую реализацию.

## 3. Состав и состояние 910

### 3.1. Требуемое содержимое задаёт provision.yaml

**Проблема.**  
Если список пакетов, служб и путей существует только в коде или документации, невозможно однозначно понять требуемое состояние 910.

**Решение.**  
Машинным источником требований к содержимому 910 является:

```text
provision.yaml
```

Он описывает:

- системные пакеты;
- Docker;
- контейнеры;
- версии основных инструментов;
- постоянные каталоги;
- подключения данных;
- служебные пути;
- Semaphore;
- OpenBao;
- границы постоянного и воспроизводимого состояния.

**Почему.**  
Один машинный источник можно проверять автоматически.

**Последствия.**  
Документация объясняет смысл параметров, но не заменяет `provision.yaml`.

### 3.2. Python используется только для узких операций

**Проблема.**  
Некоторые операции сложно выразить простыми задачами Ansible, но большой Python-установщик снова создал бы второй способ настройки 910.

**Решение.**  
Пакет `infra_manager` используется только для узких задач, например:

- работы с PVE API;
- синхронизации Semaphore;
- проверки состояния;
- подготовки OpenTofu;
- сборки и проверки шаблонов;
- служебных проверок безопасности.

**Почему.**  
Python удобен для сложной проверяемой логики, а Ansible остаётся единым оркестратором настройки Linux.

**Последствия.**  
Python-код не должен хранить отдельный полный список требуемых служб и каталогов 910.

### 3.3. Данные разделяются по владельцу

**Проблема.**  
Если всё важное хранить только в корневой файловой системе 910, пересоздание LXC уничтожит состояние. Если дать 910 доступ ко всем аварийным секретам PVE, исчезнет полезная граница доверия.

**Решение.**  
На PVE используется три области:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

Их смысл:

- `pve-only/` — данные только физического PVE, включая ключ снятия блокировки OpenBao и аварийный Git-доступ;
- `access/` — данные PVE, которые 910 получает только для чтения: SSH-доступ пользователя `root` к PVE, `known_hosts`, PVE CA;
- `state/` — состояние служб 910: OpenBao Raft, Semaphore, OpenTofu и постоянная идентичность Ansible.

Рабочие секреты PVE API, Git и Semaphore после инициализации хранятся в OpenBao и временно материализуются под `/run`.

**Почему.**

- пересоздание корневой файловой системы 910 не уничтожает постоянное состояние;
- ключ снятия блокировки OpenBao не виден 910;
- рабочие секреты не размножаются по постоянным файловым каталогам;
- владелец каждой области понятен.

**Последствия.**  
Подключение каталогов не является резервной копией. Кроме того, потеря `state/` не должна приводить к тихому созданию пустого состояния поверх существующей инфраструктуры.

Подробная карта находится в [`docs/data-and-access.md`](data-and-access.md).

### 3.4. Semaphore и инструменты находятся в одной рабочей среде

**Проблема.**  
Для одного домашнего управляющего узла отдельный удалённый исполнитель Semaphore усложняет систему без явной пользы.

**Решение.**  
Используется один контейнер:

```text
infra-runtime
```

В нём находятся Semaphore, OpenTofu, Ansible, Packer и служебные инструменты.

Semaphore использует SQLite.

**Почему.**

- меньше отдельных компонентов;
- проще резервирование и восстановление;
- задания выполняются рядом с нужными постоянными данными;
- нет отдельного канала регистрации удалённого исполнителя.

**Последствия.**  
Самообновление контейнера требует отложенной активации после завершения текущего задания.

### 3.5. Постоянное состояние OpenTofu не хранится в Git

**Проблема.**  
Состояние OpenTofu содержит фактическую связь между кодом и существующими объектами PVE. Оно меняется во время работы и не является исходным описанием инфраструктуры.

**Решение.**  
Файл состояния хранится в постоянной области 910 и резервируется отдельно.

Он:

- не хранится в Git;
- изменяется только одним инфраструктурным заданием одновременно;
- не содержит VMID 910;
- не создаётся автоматически пустым поверх существующих объектов после потери.

**Почему.**  
Git хранит требуемое состояние, а состояние OpenTofu — фактическую служебную связь с уже созданными ресурсами.

**Последствия.**  
Потеря состояния требует восстановления или явного решения, а не автоматического `apply`.

### 3.6. Файлы конкретного гостя хранятся в rootfs

**Проблема.**  
Отдельные каталоги `compose/` и `systemd/` в корне гостя не показывали, куда эти файлы устанавливаются внутри Linux, и постепенно разрастались рядом с машинными YAML и документацией.

**Решение.**  
Воспроизводимые файлы, принадлежащие именно 910, хранятся в `rootfs/` с повторением конечного пути:

```text
rootfs/opt/infra-manager/compose/...
→ /opt/infra-manager/compose/...

rootfs/etc/systemd/system/...
→ /etc/systemd/system/...
```

При этом `rootfs/` не копируется поверх `/` автоматически.

**Почему.**

- по расположению файла сразу видно его назначение внутри гостя;
- корень каталога 910 остаётся небольшим;
- Compose и systemd больше не являются особыми верхнеуровневыми категориями;
- явная установка через Ansible сохраняет контроль владельца, прав и шаблонизации;
- нет опасного скрытого механизма общего копирования файловой системы.

**Последствия.**  
Каждый файл или каталог из `rootfs/` должен быть явно установлен Ansible или другим повторяемым механизмом. Общие файлы нескольких гостей остаются в общей Ansible-роли. Секреты, изменяемое состояние, журналы и кэш в `rootfs/` не хранятся.

## 4. Восстановление и резервирование

### 4.1. Постоянное состояние не является резервной копией

**Проблема.**  
Хранение данных 910 на PVE защищает от пересоздания LXC, но не защищает от отказа диска PVE, ошибки администратора или потери всего хоста.

**Решение.**  
Постоянные области 910 резервируются независимо от корневой файловой системы LXC.

К важному состоянию относятся:

- Raft OpenBao;
- данные Semaphore;
- состояние OpenTofu;
- постоянная идентичность Ansible, пока она используется;
- PVE-only данные;
- доступы PVE;
- аварийный Git key.

**Почему.**  
Подключённый каталог остаётся тем же физическим набором данных. Его нельзя считать второй копией.

**Последствия.**  
Для критичных данных применяются общие требования [`610-backup.md`](../../../../docs/600-storage/610-backup.md).

### 4.2. Пустая повторная установка не считается восстановлением

**Проблема.**  
После потери OpenBao или OpenTofu можно технически создать новую пустую систему, но она уже не соответствует прежней инфраструктуре и прежней цепочке доверия.

**Решение.**  
Аварийный контур обязан сначала проверить наличие обязательного состояния и остановиться при критичной потере.

**Почему.**

- новый OpenBao создаст новые CA и другую систему доверия;
- пустое состояние OpenTofu может попытаться создать дубликаты существующих объектов;
- потеря истории Semaphore и его секретов не должна скрываться как успешное восстановление.

**Последствия.**  
Восстановление выполняется по [`830-recovery.md`](../../../../docs/800-operations/830-recovery.md), а не через автоматическую пустую переинициализацию.
