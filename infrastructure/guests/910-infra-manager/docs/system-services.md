# Системные службы и команды 910 infra-manager

**Назначение:** объяснить, что запускается вместе с 910, какие служебные команды устанавливаются в систему и в каком порядке они используются.

Этот файл описывает только локальные службы 910. Docker как системная служба Debian настраивается общей ролью и не получает отдельную проектную реализацию.

## 1. Основной порядок запуска

После запуска LXC 910 система должна последовательно вернуть рабочую управляющую среду.

Общий порядок:

```text
сеть
→ Docker
→ контейнеры
→ проверка и разблокировка OpenBao
→ Semaphore и инструменты
→ проверка состояния
```

Не все шаги выполняются одной systemd-службой. Часть относится к Docker Compose, часть — к отдельным служебным командам.

## 2. Docker

Docker устанавливается из официального репозитория Docker.

### 2.1. Состояние службы

Служба Docker должна быть:

```text
enabled: true
state: running
```

Она является основой для двух проектных контейнеров:

```text
infra-runtime
openbao
```

Их собственная политика перезапуска:

```text
restart: unless-stopped
```

## 3. Разблокировка OpenBao при запуске

В 910 установлена служба:

```text
infra-manager-openbao-startup-unseal.service
```

### 3.1. Зависимости

Она требует готовности:

- сети;
- Docker.

В unit-файле используются:

```text
Wants=network-online.target docker.service
After=network-online.target docker.service
```

### 3.2. Выполняемая команда

Служба запускает:

```text
/usr/local/sbin/infra-manager-openbao-startup-unseal <PVE-узел>
```

Тип службы:

```text
oneshot
```

Ограничение времени:

```text
180 секунд
```

Служба включена в обычный запуск системы через `multi-user.target`.

### 3.3. Логика команды

Команда:

1. ждёт API OpenBao до 120 секунд;
2. читает `/v1/sys/seal-status`;
3. проверяет поля `initialized` и `sealed`;
4. если OpenBao не инициализирован — ничего не меняет;
5. если уже разблокирован — завершает работу;
6. если запечатан — подключается к PVE по SSH как `root`;
7. вызывает PVE-only команду `infra-manager-openbao-unseal`;
8. повторно проверяет состояние.

Ключ снятия блокировки внутрь 910 не передаётся.

## 4. Переходная служба межмашинного SSH

Сейчас в 910 установлены:

```text
infra-manager-machine-ssh-refresh.service
infra-manager-machine-ssh-refresh.timer
```

Это переходный механизм, а не целевая архитектура.

### 4.1. Что делает служба сейчас

Она запускает:

```text
/usr/local/sbin/infra-manager-machine-ssh-refresh
```

Команда вызывает Python-модуль:

```text
infra_manager.machine_ssh
```

и читает `access.yaml` из рабочей копии проекта.

Служба зависит от сети, Docker и службы разблокировки OpenBao.

### 4.2. Расписание

Текущий таймер настроен так:

```text
после запуска:       5 минут
повтор:              каждые 30 минут
случайная задержка:  до 2 минут
Persistent:          true
```

### 4.3. Почему это временно

Текущий механизм перевыпускает машинные SSH-сертификаты.

Нормативная схема уже изменена на OpenBao SSH OTP.

После реализации OTP:

- машинные сертификаты `machine-<VMID>` удаляются;
- периодическое обновление сертификатов больше не требуется;
- этот timer должен быть удалён;
- синхронизация прав должна управлять OTP-ролями и машинными AppRole.

Фактический статус перехода находится в [`780-implementation-status.md`](../../../../docs/700-security/780-implementation-status.md).

## 5. Активация новой рабочей среды infra-runtime

Для самообновления 910 используется команда:

```text
/usr/local/sbin/infra-manager-activate-runtime
```

Постоянного заранее включённого systemd-unit для неё нет.

### 5.1. Как она запускается

После `Deploy Guest 910` Ansible создаёт временную службу через:

```text
systemd-run
```

Имя содержит время запуска:

```text
infra-manager-runtime-activate-<epoch>
```

В службу передаются:

- `INFRA_PROJECT_BRANCH`;
- `INFRA_PVE_NODE`.

### 5.2. Почему используется временная служба

Текущее задание выполняется внутри старого `infra-runtime`.

Если пересоздать контейнер сразу, задание уничтожит собственную среду выполнения.

Временная systemd-служба работает снаружи контейнера и может дождаться окончания задания, а затем заменить рабочую среду.

Подробная схема находится в [`infra-runtime.md`](infra-runtime.md).

## 6. Старый таймер разблокировки на PVE

Ранее разблокировка OpenBao выполнялась периодически отдельным systemd-таймером на PVE.

Текущая Ansible-настройка явно удаляет:

```text
infra-manager-openbao-unseal.timer
infra-manager-openbao-unseal.service
```

с PVE.

### 6.1. Зачем удалять старую схему

Наличие двух механизмов разблокировки затрудняло бы понимание, кто отвечает за состояние OpenBao.

Сейчас штатная модель:

- запуск 910 — локальная одноразовая служба;
- самообновление — явная команда активации;
- аварийная операция — PVE-only helper;
- периодического чтения состояния с PVE нет.

## 7. Установленные команды управления

Ansible устанавливает несколько команд в:

```text
/usr/local/sbin/
```

### 7.1. Команды для оператора

```text
infra-manager-status
infra-manager-pve-access-check
infra-manager-pve-lifecycle-test
```

Для первых трёх создаются короткие ссылки в `/usr/local/bin`.

Команда состояния дополнительно доступна как:

```text
/usr/bin/infra-manager-status
```

Это позволяет удобно вызывать её через `pct exec` с PVE.

### 7.2. Внутренние служебные команды

Также устанавливаются:

```text
infra-manager-activate-runtime
infra-manager-openbao-startup-unseal
infra-manager-machine-ssh-refresh
```

Они предназначены для автоматизации и systemd, а не как основной пользовательский интерфейс.

Последняя команда относится к переходной сертификатной схеме межмашинного SSH.

## 8. Проверка состояния

Главная команда:

```bash
infra-manager-status
```

проверяет краткую готовность.

Полный режим:

```bash
infra-manager-status --full
```

### 8.1. С PVE

Можно выполнить:

```bash
pct exec 910 -- infra-manager-status --full
```

Для этого команда состояния специально доступна через стандартный путь `/usr/bin`.

### 8.2. Что проверяет полный режим

Порядок проверок задаёт [`../status.yaml`](../status.yaml).

Сейчас проверяются:

1. Docker и `infra-runtime`;
2. OpenBao;
3. Semaphore;
4. OpenTofu, Ansible и Packer;
5. доступ к PVE.

Полный экран также показывает:

- адрес 910;
- адрес Semaphore;
- логин и пароль Semaphore;
- ветку проекта;
- короткий хэш версии проекта;
- команды повторной проверки.

## 9. Журналы

Главный специальный журнал самообновления:

```text
/var/log/infra-manager/runtime-activation.log
```

### 9.1. Что там должно быть

Журнал показывает:

- начало активации;
- ветку проекта;
- ожидание текущего `Deploy Guest 910`;
- запуск контейнеров;
- разблокировку OpenBao;
- синхронизацию Semaphore;
- итоговую проверку.

Секреты в журнал выводиться не должны.

## 10. Ошибки запуска

Служебные механизмы должны завершаться ошибкой, если обязательный этап не подтверждён.

### 10.1. OpenBao

Ошибка возникает, если:

- API не появился;
- состояние имеет неверный формат;
- инициализированный OpenBao не удалось разблокировать.

### 10.2. Активация рабочей среды infra-runtime

Ошибка возникает, если:

- не задан PVE-узел;
- PID текущего задания некорректен;
- `Deploy Guest 910` не завершился за 15 минут;
- Semaphore не ответил после замены контейнера;
- итоговая проверка 910 не прошла.

Автоматизация не должна скрывать эти ошибки переходом к частично работающему состоянию.
