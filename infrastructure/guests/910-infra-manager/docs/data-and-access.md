# Данные и доступы 910 infra-manager

**Назначение:** объяснить, какие данные 910 постоянны, какие создаются заново, какие доступны только PVE и как 910 получает рабочие учётные данные.

Этот файл описывает размещение данных именно для 910. Общие правила хранения и резервного копирования находятся в основной документации проекта.

## 1. Три области на PVE

Штатная схема задаётся в `provision.yaml:persistence.target_layout`.

Все внешние данные 910 находятся под единым корнем:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

### 1.1. `pve-only/`

Эта область доступна только физическому PVE и внутрь 910 не подключается.

В ней находятся данные, без которых нельзя безопасно восстановить или разблокировать управляющий контур:

- ключ снятия блокировки OpenBao;
- служебные AppRole-данные OpenBao для операций PVE;
- аварийная копия read-only Deploy Key проекта;
- другие данные аварийного контура, явно предусмотренные реализацией.

910 не должен иметь обычного файлового доступа к этой области.

Точные пути определяет [`docs/200-pve/230-host-layout.md`](../../../../docs/200-pve/230-host-layout.md).

### 1.2. `access/`

Эта область подключается в 910 только для чтения:

```text
/mnt/bindmounts/infra-manager/access
        ↓
/mnt/pve-access
```

В ней находятся:

- отдельный SSH-ключ пользователя `root` для узких операций 910 на PVE;
- `known_hosts` для строгой проверки PVE;
- корневой сертификат PVE.

Рабочий секрет PVE API и рабочий Git Deploy Key здесь не хранятся.

### 1.3. `state/`

Эта область подключается в 910 на чтение и запись:

```text
/mnt/bindmounts/infra-manager/state
        ↓
/mnt/persistent-state
```

Она содержит постоянное состояние служб 910:

| Подкаталог | Назначение |
|---|---|
| `ansible/` | постоянная переходная идентичность Ansible |
| `semaphore/` | база и служебные данные Semaphore |
| `opentofu/` | постоянное состояние OpenTofu и рабочие данные |
| `openbao/` | Raft-состояние OpenBao |

Уничтожение корневой файловой системы LXC 910 не должно уничтожать эти данные.

## 2. Привычные пути внутри 910

Часть внешнего состояния подключается к обычным путям через символические ссылки.

### 2.1. Основные соответствия

```text
/mnt/persistent-state/ansible
    → /etc/infra-manager/ansible

/mnt/persistent-state/semaphore
    → /var/lib/infra-manager/semaphore

/mnt/persistent-state/opentofu
    → /var/lib/infra-manager/opentofu

/mnt/persistent-state/openbao
    → /var/lib/persistent/openbao
```

Ansible перед созданием ссылок проверяет старые пути. Если там обнаружены неизвестные данные, автоматическое удаление запрещено и настройка останавливается.

Это защищает от тихой потери данных при изменении схемы хранения.

### 2.2. Локальные воспроизводимые данные

Внутри корневой файловой системы 910 остаются данные, которые можно создать заново:

- рабочая копия проекта в `/var/lib/infra-manager/bootstrap-repo/`;
- файлы Docker Compose в `/opt/infra-manager/compose/`;
- установленный код `infra_manager`;
- Docker-образы;
- кэши и временные файлы.

Их потеря сама по себе не считается потерей постоянного состояния.

## 3. Рабочие секреты

Постоянные рабочие секреты управляющего контура после инициализации хранятся в OpenBao.

### 3.1. Временное представление

Для работы они временно создаются в:

```text
/run/infra-manager/secrets/
```

Сейчас там могут находиться:

- `pve-api.env`;
- `github_proxmox_repo_ed25519`;
- `semaphore-server.env`;
- `initial-admin-password`;
- `semaphore-api-token`;
- служебный признак материализации OpenBao.

Каталог `/run` не является постоянным хранилищем. После перезапуска содержимое должно быть восстановлено из OpenBao.

`infra-runtime` получает этот каталог только для чтения.

### 3.2. Первоначальные секреты

При первом создании 910 ещё нельзя получить рабочие данные из пустого OpenBao. Поэтому первоначальный контур временно использует:

```text
/run/infra-manager/bootstrap-secrets/
```

В него передаются только данные, необходимые для первого запуска, например учётные данные PVE API и Git Deploy Key.

После успешной инициализации OpenBao эти значения переносятся в защищённое хранилище, а первоначальный каталог удаляется.

Постоянная рабочая копия этих секретов в `access/` или `state/secrets/` не создаётся.

## 4. Доступ 910 к внешним системам

910 использует разные учётные данные для разных задач. Они не должны заменять друг друга.

### 4.1. PVE API

Основной канал управления Proxmox:

```text
root@pam!infra-manager
```

Секрет API хранится в OpenBao и во время работы материализуется в `/run/infra-manager/secrets/pve-api.env`.

Проверка TLS выполняется по PVE CA. Отключение проверки сертификата не является штатным режимом.

Полный контракт прав находится в [`710-pve-access.md`](../../../../docs/700-security/710-pve-access.md).

### 4.2. SSH пользователя root к PVE

Отдельный SSH-доступ пользователя `root` используется только для операций, которым нужны полномочия самого хоста и которые нельзя безопасно выполнить через PVE API.

Закрытый ключ доступен 910 только для чтения через `/mnt/pve-access/pve-host/`.

Это отдельная идентичность. Она не используется для Git, Ansible или обычного входа между гостями.

### 4.3. GitHub

Рабочий read-only Deploy Key проекта хранится в OpenBao.

Во время работы он появляется только в `/run/infra-manager/secrets/` и используется Semaphore для получения репозитория.

На PVE дополнительно хранится отдельная аварийная копия ключа:

```text
/mnt/bindmounts/infra-manager/pve-only/recovery/github_proxmox_repo_ed25519
```

Она нужна для восстановления проекта до запуска OpenBao и не является штатным рабочим файлом 910.

Восстанавливаемая копия первоначального контура может находиться по пути:

```text
/root/.config/proxmox-bootstrap/github_proxmox_repo_ed25519
```

Она не является каноническим источником и при необходимости восстанавливается из `pve-only/recovery/`.

Подробности определены в [`730-git-access.md`](../../../../docs/700-security/730-git-access.md).

### 4.4. Ansible

Постоянная переходная идентичность Ansible хранится в постоянной области `state/ansible` и подключается в `infra-runtime` только для чтения.

Штатный административный вход в уже подготовленные Linux-гости должен использовать краткоживущие SSH-сертификаты. Постоянный ключ остаётся только там, где он пока нужен для первого входа и переходной схемы.

Полный SSH-контракт находится в [`720-ssh-access.md`](../../../../docs/700-security/720-ssh-access.md).

## 5. Права файлов

Службы внутри `infra-runtime` работают от пользователя с числовым идентификатором `1001` и группой `0`.

### 5.1. Semaphore

Постоянный каталог Semaphore приводится к владельцу:

```text
1001:0
```

Каталоги получают режим `0770`, обычные файлы — `0660`.

Это нужно, чтобы контейнер мог изменять базу и свои служебные данные, а доступ не открывался посторонним пользователям.

### 5.2. OpenTofu и Ansible

Каталог OpenTofu создаётся для `1001:0` с ограниченными правами.

Каталог Ansible также принадлежит служебному пользователю и хранит постоянную идентичность отдельно от временных секретов OpenBao.

OpenBao использует собственный постоянный каталог с доступом только root на уровне 910.

## 6. Резервирование и восстановление

Подключение `state/` к 910 не является резервной копией.

### 6.1. Что критично

Для восстановления 910 необходимо согласованно сохранить:

- Raft-состояние OpenBao;
- ключ снятия блокировки OpenBao;
- необходимые PVE-only служебные данные;
- данные Semaphore;
- постоянное состояние OpenTofu;
- постоянную идентичность Ansible, пока она нужна;
- данные доступа к PVE;
- аварийный Git key.

Нельзя считать новый пустой OpenBao или новое пустое состояние OpenTofu восстановлением прежнего 910.

### 6.2. Что можно создать заново

Рабочая копия Git, Docker-образы, Compose-файлы, установленный код и кэши должны восстанавливаться из проекта и не требуют отдельной постоянной копии, если в них нет уникальных изменений.

Общие требования, периодичность, RPO и RTO находятся в [`610-backup.md`](../../../../docs/600-storage/610-backup.md), а порядок аварийного восстановления — в [`830-recovery.md`](../../../../docs/800-operations/830-recovery.md).

## 7. Проверка

Перед полной готовностью 910 должны выполняться как минимум такие проверки:

- обе внешние точки подключения действительно смонтированы;
- старые каталоги не скрывают неизвестные данные;
- рабочие секреты доступны из OpenBao;
- PVE CA и данные SSH-доступа пользователя `root` читаются;
- постоянное состояние OpenTofu не заменено пустым;
- Semaphore видит прежнюю базу;
- OpenBao использует прежнее Raft-состояние.

Общая команда проверки:

```bash
infra-manager-status --full
```

С PVE:

```bash
pct exec 910 -- infra-manager-status --full
```
