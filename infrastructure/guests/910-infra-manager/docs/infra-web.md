# Веб-панель 910 infra-manager

**Тип:** локальная спецификация целевого состояния  
**Статус:** реализован защищённый веб-вход в программной ветке; проверка на рабочем LXC не проводилась
**Назначение:** создать единый защищённый интерфейс управления 910 и инфраструктурными заданиями, не вводя второй независимый механизм развёртывания.

## Исправления резервирования и длительного входа

- При отказе ручного резервирования системный посредник возвращает **только закрытый перечень кодов**: нет прав, носитель не подтверждён, копирование уже выполняется, systemd недоступен, служба не установлена, запуск отклонён. Пользователь видит понятное сообщение вместо «резервирование не принято». Произвольные строки из ошибок, журналов, PVE и restic через этот канал **не передаются**. Причина уже запущенного задания остаётся в системном журнале; интерфейс показывает предупреждение по `Result=exit-code/timeout/signal` и безопасную команду просмотра журнала.
- После просмотра реального журнала обнаружен подтверждённый отказ PVE `backup-export.py check`: `Неполное PVE-only состояние для резервирования`. Это отсутствие, пустота или символьная ссылка одного из пяти обязательных файлов (unseal OpenBao, аварийный GitHub-ключ, ограниченный AppRole Raft, помощник снимка Raft, описание гостя 910). До проверки **конкретного отсутствующего файла** нельзя считать причиной только AppRole. Новый PVE-helper указывает название компонента без путей/секретов; управляющий гость пропускает только заранее известные безопасные сообщения, а в разделе бэкапов показывается классификация последней ошибки из systemd-журнала. Первое полное `deploy 910` автоматически вызывает существующий PVE-only `--configure-backup-access` после штатной разблокировки OpenBao: если AppRole уже есть, он не перевыпускается.
- Фактическое отсутствие конкретного PVE-only компонента всё ещё требует read-only проверки наличия файлов на PVE. Успех `systemctl start --no-block` означает только принятие запроса, а не успешную копию. Проверка SSD/NAS, SFTP, OpenBao и restic по-прежнему выполняется штатным `backup_controller` и не обходится из браузера.
- На странице входа появился необязательный флажок **«Запомнить вход на 30 дней на этом устройстве»**. Без него действует прежняя одночасовая сессия. Длительный вход записывается в отдельный каталог `/mnt/persistent-state/web-sessions` на постоянном состоянии 910 (в контейнере `/var/lib/infra-web/sessions`), owner UID 1001, права `0700`; запись сеанса `0600`. Хранится **SHA-256 случайного идентификатора cookie**, CSRF и абсолютное время окончания, но **не** пароль OpenBao, не его токен и не сам cookie.
- Длительный cookie содержит `HttpOnly; Secure; SameSite=Strict; Max-Age=2592000`. Сеанс переживает перезапуск/пересборку `infra-web`, но автоматически истекает через 30 дней без продления. **«Выйти» отзывает серверный файл** и очищает cookie. На чужом компьютере флажок не включать. После кражи cookie до отзыва злоумышленник может использовать сессию: это сознательная цена длительного входа. Смена пароля OpenBao сама по себе не отзывает уже выданные долгие сессии; в этом случае требуется вручную отозвать сеансы на 910.
- Выделенный bind mount доступен только контейнеру web на запись. `infra-runtime`/PVE API и персональные данные OpenBao не монтируются в каталог сессий. Первая установка новой схемы требует **полного deploy 910** (обновлены Compose и Ansible); быстрый путь вправе переключиться в full. Не считать месяц входа работающим до проверки на живом 910.

## 1. Роль и границы

В составе LXC с ролью `infra-manager` должен работать отдельный Docker-контейнер `infra-web`.

Разделение постоянное:

| Компонент | Ответственность |
|---|---|
| `infra-web` | авторизованный интерфейс, отображение состояния, запуск разрешённых действий, просмотр журналов |
| `infra-runtime` | OpenTofu, Ansible, Packer, Python, Git и выполнение инфраструктурных заданий без Semaphore |
| `openbao` | KV v2, секреты, SSH CA, OTP, машинная аутентификация и TLS |
| `systemd` внутри LXC | запуск независимого механизма активации, контроль завершения обновления, откат и ограниченный посредник системных операций |
| PVE, первоначальный контур 990 | создание и аварийное пересоздание 910; не участвует в обычном обновлении |

Системные службы и Docker внутри 910 остаются под управлением общей Ansible-роли `infra_manager`. Версии, настройки и разрешённые подключения определяются `provision.yaml`, воспроизводимые файлы — в `rootfs/`.

**Принятое целевое решение — отказаться от Semaphore.** `infra-web` предоставляет единую панель заданий, истории и планирования, а исполнение остаётся у существующего общего механизма операций в `infra-runtime`, под надзором systemd. Веб-контейнер не содержит Ansible, OpenTofu или Packer. Второй независимый исполнитель и вторая база заданий не создаются.

В действующем машинном описании выбран `infra-web` с HTTPS на порту `8443`, проверкой пароля через OpenBao `userpass` и закрытой сессией. Запуск разрешён только после подготовки собственного сертификата панели. Запросы действий идут в уже существующий системный посредник через закрытый Unix-сокет; браузер и контейнер не получают доступ к PVE-only, SSH-ключам или Docker. Действия по самообновлению управляющего гостя оставлены прямой команде PVE. Старый Homepage для 910 отключён в описании. Пробное развёртывание и доступ из пользовательской сети пока не проверялись. Это **текущее состояние, подлежащее замене**, а не новая целевая схема. После проверки `infra-web` его интерфейс должен заменить локальную техническую страницу Homepage **только у 910**. Общие порталы других гостей и квартиры при этом не меняются. До успешного перехода существующий Homepage нельзя удалять автоматически.

## Переделка UX: единая рабочая панель

После неудобного первоначального интерфейса добавлена новая адаптивная оболочка, рассчитанная на повседневную работу (реализовано в Git, проверка на PVE требуется):

- **Навигация:** единое боковое меню «Обзор → Гости → Задания → Хранилища и бэкапы → Подготовка SSD», на узких экранах — горизонтальная навигация. Одинаковая структура на всех страницах, доступен выход по защищённой POST-форме с CSRF.
- **Обзор:** компактные показатели последних 40 операций (выполняются, успешны, требуют внимания) и понятные ссылки к рабочим разделам. Важно: это **показатели истории заданий**, а не выдуманный health-check всех гостей.
- **Гости:** адаптивные карточки VM/LXC со статусами, VMID и IP; поиск по имени/IP/VMID/роли, фильтр состояния. Карточка гостя отдельно показывает его детали, разрешённые действия и историю. Опасные действия по-прежнему требуют подтверждения.
- **Задания:** таблица с фильтрами и человекочитаемыми названиями, ссылка на детальную страницу. Детальная страница — длительность, этапы, статус, журнал, поиск по безопасным строкам и копирование видимого журнала; обновляется без перезагрузки.
- **Хранилища:** главное предупреждение и последние результаты резервирования видны сразу. Технические таблицы томов PVE/NAS сворачиваются, чтобы не перегружать страницу. Проверка физического mount/UUID и испытание восстановления от этого не появляются.
- **Время и часовые пояса:** ISO timestamps с корректным UTC offset форматируются **в браузере пользователя** в `ДД.ММ.ГГГГ · ЧЧ:ММ`. Выбор: «Моё время (браузер)» (по умолчанию), «Москва», «UTC»; выбор сохраняется локально **в самом браузере**, не в управляющем госте. Время `systemctl show` без однозначного UTC offset показывается в удобном формате `20.10.2026 · 21:30 MSK` с подписью «время сервера», **без выдуманного смещения**. Дата VM100 без часов остаётся датой и не смещается на соседние сутки.
- **Вход и выход:** HTTP 303 перенаправляет после успешного входа/выхода, поэтому обновление страницы браузера не отправляет пароль или POST повторно. Проверка пароля через OpenBao, ограничения входа, сессия, Origin и CSRF не меняются.
- **Реализация:** только локальные `ui.css`, `ui.js`, `diagnostics.js`, без CDN, дополнительных Docker-сервисов, JS-фреймворка, новой базы или прямого доступа веб-контейнера к PVE/OpenBao секретам. CSP, cookie, Origin/CSRF, системный посредник и контракты операций сохраняются. При отключённом JS остаются ссылки, основные данные и действия, но не интерактивные фильтры и смена зоны.

Важное ограничение: UI использует реальные имеющиеся API и историю, не добавляет отсутствующие данные о health-check контейнеров или результатах физической проверки архивов. Первый `deploy 910` с изменением состава web и разрешённых файлов быстрого обновления может потребовать полного Ansible; последующие разрешённые изменения web используют выборочную сборку.

## 2. Внешний вид и функции

Главная страница:

- общее состояние 910: `готов / частично готов / ошибка / обновляется`;
- состояние `infra-web`, `infra-runtime`, `openbao`, Docker и системных служб;
- доступность PVE, NAS и хранилищ по уже определённым машинным описаниям, без придумывания новых источников данных;
- последняя успешная и неуспешная проверка, последнее обновление и ближайшее плановое резервирование;
- переходы к журналам и операциям самого `infra-web` и к защищённому интерфейсу OpenBao.

Раздел «Гости»:

- читать список VM/LXC из действующего каталога гостей, в том числе системные роли, адреса и состояния;
- открыть проверку `status`; после подтверждения — `sync`, `repair`, `deploy`, `test` для разрешённых гостей;
- учитывать `pve_management: false` у управляющей роли: обновление ОС 910 допускается, управление собственным объектом Proxmox через постоянное состояние OpenTofu — нет;
- использовать текущий `guest.yaml`, `provision.yaml` и `status.yaml`, а не вести альтернативный список гостей.

**Второй этап — управление гостями (реализовано в коде, необходимо проверить на PVE):**

- После входа раздел `/guests` показывает список управляемых VM/LXC из действующих `guest.yaml` и `provision.yaml` с VMID, именем, ролью, IP управления и типом, определяемым общим `defaults.yaml`. Дубликатов каталога и новой БД нет.
- `infra-manager-portal-gateway.service` читает состояние PVE одним вызовом `/cluster/resources` для всего списка (тайм-аут 8 секунд). Состояния показываются отдельно от описания Git; при недоступном PVE выводится «не проверено», а не ложный статус «остановлен». Занятый другим именем/типом VMID отображается как конфликт.
- По ссылке `/guests?vmid=109` открывается карточка с текущим состоянием, разрешёнными действиями и последними 20 операциями именно этого гостя из единого защищённого `OperationStore`. История ведёт в уже созданный раздел `/operations?id=<UUID>`.
- `status` запускается из карточки через существующий `POST /action` (CSRF и проверка прав); `sync`, `repair`, `deploy` сначала открывают экран подтверждения, а затем отправляются тому же исполнителю. Ответ `303` направляет на диагностику задания, поэтому обновление страницы не повторяет действие.
- Наличие кнопки не заменяет серверную проверку: реальный список доступных действий вычисляется существующими `operation_guests` и `authorize_action` с `access.yaml`. Самообновление управляющего гостя 910 через браузер не разрешается.
- `/api/guests`, `/api/guest?vmid=...` доступны только с защищённой сессией; чтение проекта и PVE выполняет уже существующий Unix-посредник, а не контейнер `infra-web`.
- Пока не реализованы массовые операции над гостями, произвольный тест `test` из браузера, визуальный редактор `guest.yaml` и отдельные опросы прикладного статуса внутри каждой VM/LXC. Их нельзя считать готовыми только по наличию списка.

Раздел «Задания»:

- предоставлять задания и расписания через единый системный диспетчер 910, выполняющий операции общего механизма без Semaphore; показывать историю, состояние, длительность и результаты;
- показывать отдельно активный этап отложенной systemd-активации при обновлении самого 910;
- блокировать повторную изменяющую операцию над тем же VMID, пока выполняется предыдущая;
- показывать ясный итог: «настройка завершена, идёт активация» **не равнозначно** «обновление успешно».

Раздел «Журналы»:

- потоковый просмотр вывода заданий по постоянному идентификатору операции, не зависящему от жизненного цикла контейнера;
- журналы `infra-runtime` и `openbao` через ограниченный серверный посредник;
- сообщения `infra-manager-openbao-startup-unseal.service` и активации новой версии через `journalctl` и `runtime-activation.log`;
- время, идентификатор задания, VMID, этап, статус и текст ошибки;
- автоматическое обновление, поиск по текущему журналу, ограничение размера ответа и просмотр последней истории;
- исключение закрытых ключей, токенов, паролей, полного окружения процессов и других секретов.

Режимы вывода должны быть одной общей настройкой управляющего контура (а не свойством временного веб-сеанса):

- `Тихий` — итог и ошибки;
- `Обычный` — основные шаги, по умолчанию;
- `Подробный` — расширенная диагностика, но без раскрытия секретов.

Панель и системный исполнитель используют одну настройку подробности из целевого машинного описания; она применяется ко всем источникам журналов. Действующее задание Semaphore `Set Log Level` сохраняется только на период перехода и затем удаляется вместе с самим Semaphore.

**Первый этап диагностики (реализовано в коде, требуется испытание на PVE):**

- После входа история операций содержит ссылки на страницу `/operations?id=<UUID>` с текущим состоянием, временем начала и окончания, кодом завершения, этапами `queued/running/activating/verifying/completed/failed/rolled-back` и диагностикой последней разрешённой ошибки. Запуск действия через POST использует перенаправление `303 See Other` на страницу этого задания, поэтому F5 не повторяет изменяющую операцию.
- Страница запрашивает `/api/operation?id=<UUID>` каждые четыре секунды без перезагрузки, сохраняет выбранное задание и позицию прокрутки журнала. Для этапов с известным временем показывается длительность; выполняющийся этап отсчитывается до текущего времени браузера. Если посредник недоступен, страница остаётся открытой и повторяет чтение.
- Данные берутся через действующий Unix-сокет `infra-manager-portal-gateway.service` из постоянных JSON/JSONL и ограниченной выборки `journalctl` конкретной операции. Для `deploy 910` отдельная метка ID в `runtime-activation.log` связывает вывод независимой systemd-активации с нужной операцией.
- Системный посредник не передаёт браузеру необработанные журналы: только строки стандартных информационных/ошибочных сообщений, прошедшие ограничение размера и фильтр секретов. Полные диагностические файлы остаются закрытыми на 910. Данные вне разрешённого UUID, произвольные пути и произвольные shell-команды запрещены.
- Пока не реализованы общий поиск по произвольным системным журналам, полная потоковая выдача stdout Ansible/внешних инструментов и режимы подробности непосредственно в веб-интерфейсе. Эти возможности нельзя считать готовыми по одному наличию новой страницы.


Раздел «Обслуживание»:

- `Проверить`, `Синхронизировать`, `Исправить`;
- `Обновить 910` с показом отдельного этапа systemd-активации;
- состояние и запуск разрешённого задания резервирования; выбор существующей точки восстановления **без автоматического аварийного пересоздания 910 из браузера**;
- результаты последней проверки целостности копий и пробного восстановления;
- раздельное состояние общих томов `infra_state`, `gogs_data`, `photo_archive`, SSD быстрых копий и NAS по единым `storage.yaml`/`backup.yaml`, без параллельного списка устройств;
- раздельные результаты копирования на SSD и NAS: работа одной копии с предупреждением «вторая независимая копия отсутствует», а не ложное «две копии успешно».

**Третий этап — хранилища и резервирование (реализовано в коде, требуется проверка на PVE):**

- После входа раздел `/infrastructure` показывает декларации PVE (`infra_state`, `gogs_data`, `photo_archive`) и NAS из `infrastructure/hosts/{pve,nas}/storage.yaml`, назначенные точки монтирования и отдельно назначение SSD/NAS из `infrastructure/hosts/pve/backup.yaml`. Ни один диск или путь не объявляется подтверждённым только по YAML.
- Системный посредник запрашивает через read-only Proxmox API состояние зарегистрированных хранилищ `backup-fast` и `nas-backup`: `PVE активно / неактивно / не зарегистрировано / PVE недоступен`. Это **не** проверка UUID, физического mount или рестикового репозитория. Никакого автоматического `mkfs`, `mount` или создания директории ради просмотра нет. NAS-тома показываются как декларация: живой NAS отдельно не опрашивается.
- Результаты берутся только из защищённых записей единого исполнителя 910: `operations/settings/backup-last-core.json`, `backup-last-full.json`, `backup-vm100.json`. Отображаются время UTC, носители, возраст, метка состоявшейся выборочной проверки `restic check --read-data-subset=1%` и подтверждение испытанного восстановления (**обычно отсутствует**). Повреждённые, отсутствующие, будущие, просроченные записи различаются.
- Если в последней проверенной копии `infra-core` указан один носитель, выводится «**Вторая независимая копия отсутствует**». Две записи в истории также не доказывают, что оба носителя доступны **сейчас**.
- Расписание отображается отдельно по `backup.yaml` и по настоящему состоянию `infra-manager-backup.timer` и `infra-manager-backup.service` (через `systemctl show`), включая предыдущий и будущий вызовы, последний код результата. Декларированное расписание само по себе не считается запущенным таймером.
- **Обновление состояния во время резервирования:** страница «Хранилища и бэкапы» показывает ручную кнопку «↻ Обновить состояние» сверху и возле расписания. Когда `infra-manager-backup.service` в `active`/`activating` либо пользователь только что запустил копирование через `POST /infrastructure/run`, страница **автоматически** запрашивает только авторизованный `GET /api/infrastructure` раз в **4 секунды**, обновляя статусы systemd, результаты и объяснения последней ошибки без перезагрузки страницы и без закрытия технических деталей. После завершения копирования фоновый опрос останавливается (в обычном простое запросов нет), а ручная кнопка остаётся доступной. На скрытой вкладке опрос приостанавливается, при возвращении к активному заданию состояние проверяется снова. Повторные одновременные запросы не выполняются. При истечении сеанса опрос прекращается. Браузер не запускает резервирование повторно, не показывает выдуманный процент прогресса и не обходит проверки PVE/SSD/OpenBao.
- **Диагностика restic:** при сбое системная служба сообщает безопасное название этапа — создание репозитория, чтение существующего репозитория, запись архива или проверка целостности; сырой stderr restic по-прежнему не возвращается веб-панели, поскольку может содержать пути и чувствительные данные. Это не устранение самой причины отказа restic на физическом SSD: для анализа реального сбоя понадобится этап из следующего системного журнала.
- По кнопке «Запустить копирование вручную» открывается экран подтверждения. `POST /infrastructure/run` защищён текущими HTTPS-сеансом, Origin и CSRF; системный посредник заново проверяет разрешение в `access.yaml`, наличие хотя бы одного подтверждённого места по текущему `backup_controller.policy()` и отсутствие выполняющегося сервиса. Используется **только существующий systemd-unit** `infra-manager-backup.service`, без второго планировщика, shell, произвольного пути или параметров из браузера. После принятия запроса `303` возвращает к состоянию и **не объявляет резервное копирование успешным** до появления записи об успешной проверке.
- `GET /api/infrastructure` — ограниченный read-only JSON-обзор только после входа. Серийные номера физических дисков, пароли restic, access-токены и первичные системные журналы в ответ не включены.
- **Пока не реализованы:** отдельный мастер восстановления, реальный тест восстановления, просмотр каталога snapshots restic с каждого диска, live-проверка физического mount/UUID PVE или SMART NAS через браузер. Эти операции потребуют дальнейших специальных read-only проверок; интерпретировать существующий обзор как их замену нельзя.

**Подготовка физического SSD** доступна из двух штатных интерфейсов: в `infra-web` увидеть проверенный план и нажать «Да, подготовить SSD» **без ввода серийного номера**; либо из интерактивного SSH-терминала PVE при `infra-manager deploy 910` ответить `да` на вопрос после показа плана. Серийный номер сверяется автоматически в обоих случаях. После нажатия существующий системный диспетчер в 910 сразу запускает независимое systemd-задание, которое продолжится при закрытом браузере. Никакого второго `deploy 910` для применения разрешения не требуется. Это не произвольный shell, не публичная команда и не установка на PVE. При обнаружении нового диска интерфейс показывает подтверждаемый план (модель, объём, устойчивую идентичность, разделы, сигнатуры, операции, путь монтирования, последствия для содержимого), требует **отдельного явного подтверждения** и передаёт только разрешённые параметры системному диспетчеру. Сразу перед записью идентичность повторно проверяется; разрешение относится к одному устройству/плану и не переносится на новый диск. После подготовки ext4 следующие `deploy` только проверяют UUID и восстанавливают монтирование; повторного mkfs и подтверждения нет. Замена SSD запрашивает новый план и согласие. Пока механизм не реализован, показывать «ожидает подтверждения» без изменения диска.

Первая версия рассчитана на одного администратора. Массовые операции, самостоятельный редактор `guest.yaml`, терминал Linux, произвольный shell и управление секретами из веб-формы не входят в требуемый состав.

## 3. Доступ и защита

Интерфейс не публикуется в открытый Интернет. Доступ разрешён только через защищённую административную сеть и HTTPS (после развёртывания 109 — через его обратный прокси); до появления HTTPS с авторизацией доступ извне LXC отключён.

Обязательны:

1. Предусмотреть самостоятельный защищённый вход администратора в `infra-web`, **не зависящий от Semaphore**. Способ хранения и выдачи учётных данных определить через OpenBao и действующий контракт безопасности, не помещая пароли в Git. Панель хранит защищённую серверную сессию и использует cookie `HttpOnly`, `Secure`, `SameSite`, с ограничением попыток входа. Если веб-вход невозможен, аварийное управление выполняется через доверенную PVE CLI, а не через обход авторизации.
2. Проверка CSRF и подтверждение каждой изменяющей операции. GET не выполняет изменений.
   HTML-формы `/login`, `/logout`, `/action`, `/storage-confirm` используют строгую проверку `Host` и `Origin` (`https://<адрес панели>`). Ответы **должны содержать `Referrer-Policy: same-origin`, не `no-referrer`**: иначе браузер для обычной формы POST отправляет `Origin: null`, и правильный пароль отвергается до проверки в OpenBao. `Origin: null`, отсутствие Origin и чужой Origin по-прежнему запрещены; политику не ослаблять. Другие заголовки безопасности (CSP, HSTS, Secure/HttpOnly/SameSite cookie) сохраняются.
3. Серверная проверка разрешённой операции и выбранного VMID по каталогу и `access.yaml`; браузеру нельзя доверять решение о правах.
4. Отсутствие в `infra-web` PVE root SSH key, PVE-only секретов, ключа снятия блокировки OpenBao и полного Docker socket.
5. Никакого произвольного запуска команд, передачи пути к исполняемому файлу, произвольного задания или Docker Compose.
6. Все журналы и JSON/HTML-ответы фильтруются от секретов; сообщения экранируются перед отображением.
7. Для недоступной службы OpenBao допускается ограниченное отображение ошибки; восстановление секретов выполняет отдельный доверенный системный контур или PVE CLI, не браузер.

Нельзя открывать административный API нового приложения через NAT без защищённого входа и проверки полномочий. Аутентификация HTTPS-посредника **не заменяет** проверку полномочий на исполнение операций.

## 4. Связь со службами

Веб-панель — интерфейс над одним системным диспетчером операций 910. Разрешённые действия и параметры берутся из описаний проекта. Исполнение использует общий `guest-operation.py` или его совместимую преемственную точку входа и существующие блокировки. История, задания и расписание хранятся в независимом от `infra-web`, `infra-runtime` и Semaphore постоянном состоянии 910. Контракт идентификатора и результата описан в [`activation-contract.md`](activation-contract.md).

Реализованный веб-интерфейс **не монтирует** каталог `/mnt/persistent-state/operations` и не получает к нему файловых прав: корневой системный исполнитель сохраняет каталоги с правами `0700`, а записи истории — `0600`. Для страницы после входа и `/api/operations` веб-панель запрашивает через существующий закрытый Unix-сокет только разрешённые поля истории (`id`, `kind`, `target`, `phase`, `created_at`). Пароли, токены, пути к журналам и прочие поля записи не передаются. При недоступном посреднике успешная авторизация остаётся действительной: вместо ошибки соединения панель показывает предупреждение, а `/api/operations` возвращает `503`. При развёртывании изменение кода системного посредника вызывает его перезапуск без ручных команд.

Для действий, которые нельзя безопасно выполнять из обновляемого Docker-компонента, необходимо **расширить существующий** системный посредник `infra-manager-portal-gateway.service` (модуль `infra_manager.portal_gateway`), а не устанавливать второй конкурирующий сервер команд. Сейчас он допускает только `status/sync/repair` через подтверждаемый HTTP-запрос и общий операторский слой. Для нового интерфейса нужно добавить серверную авторизацию, ограниченный машинный интерфейс и недостающие разрешённые операции с отдельными проверками. Предпочтительный внутренний транспорт между контейнером и посредником — Unix-сокет с ограниченными правами (переход со старого HTTP должен быть проверен). Посредник принимает строго типизированный набор действий, проверяет источник запроса, полномочия, идентификатор гостя и блокировки. Он не исполняет пользовательскую строку в оболочке.

Прямое предоставление контейнеру `infra-web` прав root на Docker или SSH к PVE не допускается. Связь с ограниченным системным посредником не должна давать произвольного доступа к секретам. Для хранилищ исполнитель 910 сначала использует штатный Proxmox API, затем уже существующие безопасные команды PVE по доверенному SSH. **На PVE нельзя устанавливать ничего без крайней необходимости и отдельного предварительного решения пользователя**: никаких новых пакетов, сервисов, фоновых таймеров или постоянных помощников ради настройки дисков.

После принятия действия панель получает постоянный уникальный идентификатор операции. Состояния: `ожидает`, `выполняется`, `ожидает активации`, `проверка`, `успешно`, `ошибка`, `откачено` (если выполнен откат). Разрыв соединения с браузером не прерывает задание, завершённый результат остаётся доступен после перезапуска интерфейса. Повтор запроса с тем же идентификатором не запускает второй экземпляр. Успех определяется только по подтверждённому результату **этого** идентификатора, а не по исчезнувшему временному маркеру.

Для просмотра журналов предпочтительна передача событий по HTTPS с автоматическим переподключением; допустим опрос с курсором. Ограничения памяти и времени обязательны. История заданий хранится в едином постоянном состоянии операций 910, не копируется между независимыми базами. Срок хранения и резервирование определяются в описании состояния.

## 5. Развёртывание

Изменения выполняются только из Git:

1. Дополнить `provision.yaml` определением `docker.services.web`, образом и фиксированной версией, портом, режимом сети, состоянием, подключениями и проверкой готовности.
2. Поместить воспроизводимый состав веб-панели в `rootfs/opt/infra-manager/compose/web/` и добавить службу `infra-web` в существующий Compose.
3. Расширить существующий `infra-manager-portal-gateway.service` и модуль `portal_gateway.py` с фиксированными разрешёнными операциями и строгим ограничением доступа. Не устанавливать дополнительный сервер команд или второй полный установщик вместо Ansible.
4. Обновить и проверить действующий посредник через `automation/ansible/roles/infra_manager/`, сохраняя прежние разрешённые операции до перехода на новый интерфейс.
5. Настроить авторизацию и HTTPS; проверить недоступность административных вызовов из неавторизованной сети.
6. Подключить системный диспетчер, общий статус, единый журнал и постоянные результаты по [`activation-contract.md`](activation-contract.md), без Semaphore API и дублирующих настроек.
7. Дополнить `infra-manager-status.yaml` проверкой `infra-web`, авторизации, HTTPS и посредника.
8. Только после приёмки заменить локальный Homepage у 910. Не изменять порталы остальных гостей.

При обычном самообновлении 910 компоненты обновляются **выборочно**, без отдельного режима разработчика. Код `infra-web`, Dockerfile `infra-runtime` с зависимостями и конфигурация OpenBao имеют независимые Git-отпечатки. Отсутствующий образ или образ с несовпадающим отпечатком пересобирается; неизменённый образ не пересобирается и не требует обращения к сетевым источникам OpenTofu/Packer. Изменение веб-панели не заменяет работающий `infra-runtime` и не пересоздаёт OpenBao. Обычный `docker compose up` применяет лишь реальные изменения образа и окружения; принудительный повторный запуск `infra-web` не требуется.

На странице входа без авторизации выводится перечень версий **без секретов**: `infra-web` с коротким Git SHA коммита, в котором образ был собран, а также версии `infra-runtime`, OpenBao, OpenTofu, Ansible, Packer и целевой Git SHA по декларации `deploy`. SHA сборки и общий SHA целевого проекта могут различаться, если код веб-панели не изменился. Это **не ошибка**: предупреждение появляется лишь при несовпадении отпечатка кода запущенной панели с требуемым отпечатком. Приведённые по конфигурации версии инструментов не являются независимой проверкой установленных бинарников.

При `deploy 910` Ansible сверяет отпечатки требуемых исходных файлов с метками содержимого существующих Docker-образов и строит только необходимые образы. Затем systemd-активация проверяет SHA *реально запущенных* `infra-web` и `infra-runtime` с **их собственными отпечатками исходников** из `.versions.env`, а также выполняет штатные проверки OpenBao, HTTPS и системного посредника. Общий SHA Git сохраняется для аудита релиза. Простого HTTP-ответа и запущенного контейнера недостаточно для `[ОК]`. Во время развёртывания отдельно показывается план сборки и продолжительность её этапов.


## 6. Приёмочные проверки

Проверка выполняется на испытательном госте/узле, без удаления рабочего 910:

- новая панель показывает те же VMID и состояние, что общий операторский слой;
- выполняется одно разрешённое задание, виден его живой журнал и история в независимом постоянном состоянии 910;
- доступны все три режима вывода, одна настройка не расходится между веб-панелью и системным исполнителем;
- повторный запрос не создаёт дубликат; две изменяющие операции одного VMID не выполняются параллельно;
- без входа, без CSRF или с запрещённым VMID запрос отклоняется;
- при отключённом `infra-web` выполняющиеся задания и системная активация продолжают работать;
- при остановленном `infra-runtime` веб-панель показывает неисправность, а системный механизм восстановления остаётся доступен;
- в ответах и журналах отсутствуют пароли, ключи и токены;
- обновление самого `infra-web` не останавливает системное управление;
- при обновлении `infra-runtime` панель показывает промежуточное состояние и окончательный итог только после проверки новой версии;
- диск после успешной подготовки сохраняет UUID и не предлагается к повторному форматированию; подмена SSD требует нового подтверждения;
- при подтверждённом SSD и недоступном NAS можно копировать на SSD с предупреждением об отсутствующей второй копии; недоступные носители не заменяются каталогами на системном PVE.
