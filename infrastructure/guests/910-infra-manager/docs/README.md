# Документация 910 infra-manager

Этот каталог является практической документацией конкретного гостя `910 infra-manager`.

Его задача — не повторять архитектуру проекта, а содержать **целевые локальные спецификации**, достаточные для развёртывания, проверки, обновления и восстановления служб 910.

Общие документы проекта отвечают на вопросы «зачем нужен компонент» и «как он взаимодействует с другими частями системы». Файлы здесь отвечают на вопрос «каким этот компонент должен быть на 910 и как получить это состояние».

Если текущий код отличается от локальной спецификации, целевой документ не урезается под код: расхождение фиксируется в документе состояния реализации и устраняется в реализации.

## Как восстанавливать 910 по этой документации

Практический порядок чтения после создания пустого LXC 910:

1. [`data-and-access.md`](data-and-access.md) — убедиться, что PVE подключил `access/` и `state/`, а нужные каталоги существуют.
2. [`infra-runtime.md`](infra-runtime.md) — установить Docker-файлы из `rootfs`, записать версии, собрать `infra-runtime` и запустить контейнеры.
3. [`openbao.md`](openbao.md) — проверить OpenBao, выполнить первичную инициализацию либо разблокировать существующий Raft.
4. Для принятого standalone 910 использовать [`infra-web.md`](infra-web.md) и [`activation-contract.md`](activation-contract.md); Semaphore в штатном контуре больше не нужен. [`semaphore.md`](semaphore.md) — лишь историческое описание прежней версии, не инструкция к установке.
5. [`system-services.md`](system-services.md) — установить целевые systemd-службы и служебные команды 910.
6. [`automation-tools.md`](automation-tools.md) — проверить OpenTofu, Ansible, Packer, Git и Python.
7. [`portal.md`](portal.md) — проверить существующий Homepage; при реализации новой схемы следовать [`infra-web.md`](infra-web.md) и заменить портал 910 только после приёмки.
8. С физического PVE выполнить `infra-manager status` и устранить все ошибки до передачи 910 в эксплуатацию.
9. Для развития сверки физических томов PVE, разметки подтверждённого SSD, резервирования и независимого аварийного восстановления использовать [`self-maintenance.md`](self-maintenance.md) и [`activation-contract.md`](activation-contract.md). **На PVE запрещены любые дополнительные установки без крайней, доказанной необходимости и предварительного согласования.** Целевые функции не считать реализованными только по тексту документа.

Штатно роль Ansible `infra_manager` приводит службы и инструменты 910 к требуемому состоянию. При первоначальном развёртывании и восстановлении внешняя оркестрация затем инициализирует OpenBao и только после этого выполняет внутреннюю полную проверку; операторский итог подтверждается командой `infra-manager status` на PVE. При обычном самообновлении 910 итоговую проверку выполняет отложенная активация новой среды. Документация нужна для понимания этих шагов, проверки результата и ручного восстановления при неисправности.

## Где находится фактическая реализация

Главные источники реализации 910:

| Источник | Что в нём находится |
|---|---|
| [`../guest.yaml`](../guest.yaml) | параметры LXC 910 в Proxmox |
| [`../provision.yaml`](../provision.yaml) | версии, службы, контейнеры, пути и постоянные данные действующего standalone 910 |
| [`../status.yaml`](../status.yaml) | проверки итогового состояния 910 |
| [`../rootfs/`](../rootfs/) | воспроизводимые файлы, которые должны оказаться по соответствующим путям внутри 910 |
| [`../../../../automation/ansible/roles/infra_manager/`](../../../../automation/ansible/roles/infra_manager/) | фактический порядок настройки 910 |
| [`../../../../scripts/infra-manager/`](../../../../scripts/infra-manager/) | служебные команды, задания Semaphore и Python-логика |

`rootfs/` не копируется целиком поверх `/`. Ansible явно устанавливает нужные файлы в нужные места.

## Как читать точные значения

Локальная документация может приводить версии, пути, режимы файлов и команды, чтобы ей можно было пользоваться при развёртывании.

После полной реализации машинные файлы и локальные спецификации должны описывать одно и то же требуемое состояние. Точное исполняемое значение берётся из машинного файла. Основные примеры:

- версия OpenBao — `provision.yaml:docker.services.openbao.image`;
- версии OpenTofu, Packer и остальных инструментов — `provision.yaml:docker.services.runtime`; Semaphore для штатного 910 не требуется;
- состав контейнеров и подключения — `rootfs/opt/infra-manager/compose/docker-compose.yml`;
- конфигурация OpenBao — `rootfs/opt/infra-manager/compose/openbao/openbao.hcl`;
- systemd-службы — `rootfs/etc/systemd/system/`;
- порядок установки — `automation/ansible/roles/infra_manager/tasks/`.

Если код и локальная спецификация расходятся, сначала определяется целевое состояние по локальному документу и общим контрактам, затем код приводится к нему. Временное расхождение фиксируется в `780-implementation-status.md`.
