# 910 infra-manager

`910 infra-manager` — постоянный служебный LXC, из которого выполняется штатное развёртывание и сопровождение инфраструктуры проекта.

Он не предназначен для прикладных служб квартиры. Его задача — хранить состояние управляющих средств и безопасно запускать OpenTofu, Ansible, Packer, Semaphore и OpenBao.

## 1. Назначение

910 является управляющим контуром проекта.

### 1.1. Что делает 910

Через 910 выполняются:

- построение плана OpenTofu;
- создание и обновление управляемых VM/LXC;
- настройка Linux-гостей через Ansible;
- сборка базового шаблона VM через Packer;
- запуск инфраструктурных заданий Semaphore;
- хранение рабочих секретов в OpenBao;
- выпуск SSH-сертификатов;
- проверка состояния управляющего контура;
- подготовка и проверка аварийного восстановления.

### 1.2. Что в 910 не размещается

910 не используется для:

- Home Assistant;
- MQTT;
- Zigbee2MQTT;
- ESPHome;
- Frigate;
- прикладных программ квартиры;
- общего файлового хранилища;
- сервисов разработки, не относящихся к управлению инфраструктурой.

Такое разделение не даёт прикладным службам смешиваться с административным контуром PVE.

## 2. Объект Proxmox

Точные параметры находятся в [`guest.yaml`](guest.yaml).

| Параметр | Значение |

| имя | `infra-manager` |
| тип | непривилегированный LXC |
| ОС | Debian 13 amd64 |
| CPU | 2 |
| RAM | 4096 MB |
| swap | 1024 MB |
| диск | 32 GB |
| хранилище | `local-lvm` |

910 не входит в собственное постоянное состояние OpenTofu.

## 4. Состав 910

В Debian 910 устанавливается только то, что нужно для работы Docker и служебных команд.

Основная работа выполняется в двух контейнерах.

### 4.1. Контейнеры

| Контейнер | Назначение |
|---|---|
| `infra-runtime` | Semaphore и инструменты управления |
| `openbao` | защищённое хранение секретов, SSH CA и служебные роли |

Оба контейнера используют сеть 910 напрямую.

Подробности:

- [`docs/infra-runtime.md`](docs/infra-runtime.md);
- [`docs/openbao.md`](docs/openbao.md).

### 4.2. Инструменты внутри infra-runtime

В `infra-runtime` находятся:

- Semaphore;
- Ansible;
- OpenTofu;
- Packer;
- Python;
- `proxmoxer`;
- Git;
- OpenSSH client.

OpenTofu, Ansible и Packer не работают как отдельные постоянные службы Debian.

Их устройство описано в [`docs/automation-tools.md`](docs/automation-tools.md).

## 5. Службы

Самостоятельные части 910 имеют отдельные локальные документы.

### 5.1. Semaphore

Semaphore хранит проект, задания, историю запусков и свой интерфейс.

Он использует SQLite и работает внутри `infra-runtime`.

Подробности:

[`docs/semaphore.md`](docs/semaphore.md).

### 5.2. OpenBao

OpenBao работает отдельным контейнером и хранит:

- рабочие секреты PVE, Git и Semaphore;
- закрытые ключи SSH CA;
- политики и служебные роли.

Raft-состояние хранится вне корневой файловой системы 910.

Подробности:

[`docs/openbao.md`](docs/openbao.md).

### 5.3. Системные службы

systemd отвечает за:

- разблокировку OpenBao при запуске 910;
- отложенную активацию новой рабочей среды при самообновлении;
- переходное периодическое обновление машинных SSH-сертификатов.

Последний механизм должен исчезнуть после реализации OpenBao SSH OTP.

Подробности:

[`docs/system-services.md`](docs/system-services.md).

## 6. Постоянные данные

Корневая файловая система 910 не является единственным местом хранения состояния.

### 6.1. Корень на PVE

Используется:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

В 910 подключаются только:

```text
access/ → /mnt/pve-access       только чтение
state/  → /mnt/persistent-state чтение и запись
```

`pve-only/` внутрь 910 не монтируется.

### 6.2. Что хранится постоянно

В `state/` находятся:

- Raft OpenBao;
- состояние OpenTofu;
- данные Semaphore;
- постоянная идентичность Ansible.

Рабочие секреты PVE API и Git после инициализации хранятся в OpenBao и во время работы материализуются только под `/run`.

Подробная карта находится в [`docs/data-and-access.md`](docs/data-and-access.md).

## 7. Доступ к PVE

910 является доверенным административным контуром PVE.

Он использует два разных канала.

### 7.1. PVE API

Основное управление выполняется через:

```text
root@pam!infra-manager
```

API используется OpenTofu и обычными операциями управления.

### 7.2. Root SSH

Отдельный SSH-доступ пользователя `root` к PVE используется только для операций, которым нужны полномочия самого физического хоста.

Этот ключ:

- не является Git-ключом;
- не является Ansible-ключом;
- не используется для обычного межмашинного SSH.

Точная модель прав находится в [`710-pve-access.md`](../../../docs/700-security/710-pve-access.md).

## 8. Жизненный цикл

910 создаётся отдельным первоначальным контуром, но после создания настраивается тем же общим Ansible-путём, что и другие Linux-гости.

### 8.1. Первое создание

Упрощённо:

```text
PVE
→ временный LXC 990
→ отдельное состояние OpenTofu для 910
→ создать LXC 910
→ общий provision.yaml + Ansible
→ запустить OpenBao и infra-runtime
→ инициализировать OpenBao
→ проверить 910
→ удалить временный 990
```

Подробный порядок находится в [`810-deployment.md`](../../../docs/800-operations/810-deployment.md).

### 8.2. Обычное обновление

После первого создания новый 990 для обычного обновления не нужен.

Обновление выполняется заданием Semaphore:

```text
Deploy Guest 910
```

Используется тот же общий `deploy-guest.py`, что и для остальных гостей.

Объект LXC 910 при этом не добавляется в постоянное состояние OpenTofu самого 910.

### 8.3. Самообновление рабочей среды

Поскольку `Deploy Guest 910` выполняется внутри `infra-runtime`, контейнер нельзя заменить до окончания собственного задания.

Поэтому новая среда активируется снаружи контейнера через временную systemd-службу.

Подробности находятся в [`docs/infra-runtime.md`](docs/infra-runtime.md).

## 9. Проверка состояния

Основная команда:

```bash
infra-manager-status
```

Полная:

```bash
infra-manager-status --full
```

С PVE:

```bash
pct exec 910 -- infra-manager-status --full
```

### 9.1. Что проверяется

В текущем `status.yaml` проверяются:

- Docker и `infra-runtime`;
- OpenBao;
- Semaphore;
- OpenTofu, Ansible и Packer;
- PVE API и, в полном режиме, полный контракт прав.

Полный экран показывает:

- адрес 910;
- адрес Semaphore;
- логин `admin`;
- сохранённый пароль Semaphore;
- ветку проекта;
- текущую версию проекта;
- команды повторной проверки.

## 10. Резервирование и восстановление

Внешние каталоги делают 910 устойчивым к пересозданию rootfs, но сами по себе не являются резервной копией.

### 10.1. Критичное состояние

Нужно сохранять согласованно:

- OpenBao Raft;
- ключ снятия блокировки и связанные PVE-only данные;
- Semaphore;
- постоянное состояние OpenTofu;
- необходимые SSH-идентичности;
- аварийный Git key.

### 10.2. Восстановление

Аварийное восстановление начинается локально на PVE.

Основная последовательность определяется в:

[`docs/800-operations/830-recovery.md`](../../../docs/800-operations/830-recovery.md).

Подробное размещение данных 910:

[`docs/data-and-access.md`](docs/data-and-access.md).

## 11. Границы

910 не входит в `pool managed`.

Это защищает управляющий контур от операций, разрешённых только для обычных управляемых гостей.

### 11.1. Владелец требований

910 исполняет требования проекта, но сам не должен становиться вторым источником архитектуры.

Требования находятся в Git.

Права находятся в `access.yaml`.

Рабочие секреты находятся в OpenBao.

Состояние OpenTofu и Semaphore хранит фактическое состояние, но не заменяет требуемую конфигурацию.
