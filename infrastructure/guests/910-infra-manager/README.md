# 910 infra-manager

`910 infra-manager` — постоянный служебный LXC для штатного управления инфраструктурой проекта.

Он не предназначен для прикладных служб квартиры. Его задача — запускать средства развёртывания и сопровождения, хранить их постоянное состояние и предоставлять единый проверяемый управляющий контур.

## Назначение

Через 910 выполняются:

- построение и применение изменений OpenTofu для управляемых объектов;
- настройка Linux-гостей через Ansible;
- сборка базового шаблона через Packer;
- запуск инфраструктурных заданий Semaphore;
- работа OpenBao как защищённого хранилища рабочих секретов и SSH-центров доверия;
- проверка состояния управляющего контура.

Home Assistant, MQTT, Zigbee2MQTT, ESPHome, Frigate и другие прикладные службы в 910 не размещаются.

## Состав

В 910 работают два основных контейнера:

| Контейнер | Назначение |
|---|---|
| `infra-runtime` | Semaphore и инструменты управления: Ansible, OpenTofu, Packer, Python, Git и OpenSSH |
| `openbao` | рабочие секреты, SSH client/host CA, AppRole и SSH OTP |

Кроме контейнеров, в 910 есть системные службы для запуска, разблокировки OpenBao и безопасной активации новой версии рабочей среды. Межмашинный SSH в целевой схеме использует OpenBao SSH OTP.

Подробное устройство частей 910 описано в [`docs/README.md`](docs/README.md).

## Границы

910 является административным управляющим контуром, но не входит в `pool managed` и не управляет собственным объектом Proxmox через своё постоянное состояние OpenTofu.

Права между субъектами задаются общим машинным контрактом [`infrastructure/security/access.yaml`](../../security/access.yaml). Общие правила доступа находятся в разделе [`docs/700-security`](../../../docs/700-security/README.md).

Постоянные данные 910 хранятся вне его корневой файловой системы в областях PVE. Поэтому пересоздание LXC не должно уничтожать состояние OpenBao, Semaphore и OpenTofu. Точное размещение описано в [`docs/data-and-access.md`](docs/data-and-access.md).

## Жизненный цикл

Первое создание 910 выполняет первоначальный контур. После этого обычное обновление использует тот же общий механизм развёртывания гостей. С PVE достаточно `infra-manager deploy 910`: обновление постоянной Git-копии выполняется автоматически перед запуском. В Semaphore остаётся единое задание `Deploy Guest` с выбором `910 infra-manager`. Оба входа сходятся в одном диспетчере операций.

Обычный `deploy 910` предназначен только для уже существующего управляющего гостя: он обновляет и исправляет воспроизводимую конфигурацию по штатному сертификатному SSH. Первое создание и полное аварийное пересоздание 910 выполняет временный LXC 990 и не расширяет интерфейс общего `deploy-guest`.

Если обычный `deploy` или `repair` 910 невозможен, оператор использует `infra-manager recover`. Recovery сохраняет `/mnt/bindmounts/infra-manager`, создаёт новый временный bootstrap-сеанс 990 и полностью пересоздаёт rootfs 910.

Особенности безопасного самообновления `infra-runtime` описаны в [`docs/infra-runtime.md`](docs/infra-runtime.md).

Общий порядок развёртывания находится в [`810-deployment.md`](../../../docs/800-operations/810-deployment.md), аварийного восстановления — в [`830-recovery.md`](../../../docs/800-operations/830-recovery.md).

## Проверка состояния

В обычном контуре 910 проверяется тем же заданием Semaphore `Status Guest`, что и остальные управляемые гости. Общий [`status.yaml`](status.yaml) подключает внутреннюю глубокую проверку 910, а итоговый операторский экран формирует общий механизм состояния гостей.

На физическом PVE сохраняется единая операторская команда:

~~~bash
infra-manager guests
infra-manager status [VMID]
infra-manager deploy VMID
infra-manager sync VMID
infra-manager repair [VMID]
infra-manager test VMID
infra-manager recover
~~~

Команда на PVE является только оболочкой: обычные операции передаются через `pct exec` установленной операторской команде внутри 910. Для `deploy`, `sync`, `repair` и `test` оператор делает `docker exec` в `infra-runtime` и запускает общий `guest-operation.py` без создания задания Semaphore. Сам Semaphore вызывает ту же точку входа из своих шаблонов. Поэтому OpenTofu, Ansible и Packer остаются только в `infra-runtime`, а отдельный набор инструментов в системе 910 не нужен. Изменяющие операции защищены общей блокировкой по VMID; обновление и создание снимка рабочей Git-копии координируются отдельной блокировкой проекта.

Исключение — `recover`: он выполняется PVE-only recovery helper и не зависит от работоспособности 910. Recovery создаёт временный 990, который получает временные полномочия, полностью пересоздаёт управляющий rootfs и удаляется после успешной передачи управления. `repair` без VMID может запустить остановленный LXC, после чего дальнейшее восстановление служб выполняется внутри 910.

Внутри 910 остаётся техническая команда `infra-manager-status --full`. Её машинное описание находится в [`infra-manager-status.yaml`](infra-manager-status.yaml), устанавливается как `/etc/infra-manager/status.yaml` и не является отдельным операторским экраном.

Данные входа OpenBao и другие операторские пароли выводятся только по доверенному запросу root с PVE, например:

~~~bash
infra-manager status 910
~~~

В журналах Semaphore и Homepage пароли скрываются.

## Источники точных значений

README является паспортом гостя и не заменяет машинные файлы.

| Источник | Что задаёт |
|---|---|
| [`guest.yaml`](guest.yaml) | объект Proxmox и его основные свойства |
| [`provision.yaml`](provision.yaml) | ОС, пакеты, контейнеры, версии, пути, подключения и постоянное состояние |
| [`status.yaml`](status.yaml) | дополнительные проверки общего `Status Guest` |
| [`infra-manager-status.yaml`](infra-manager-status.yaml) | внутренняя глубокая проверка служб 910 |
| [`rootfs/`](rootfs/) | воспроизводимые файлы 910, разложенные по конечным путям Linux |
| [`docs/decisions.md`](docs/decisions.md) | причины решений, относящихся именно к 910 |

Каталог `rootfs/` не копируется на гостя целиком автоматически. Каждый файл устанавливается явным повторяемым механизмом.
