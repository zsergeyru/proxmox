# 910 infra-manager

`910 infra-manager` — постоянный служебный LXC для штатного управления инфраструктурой проекта.

Он не предназначен для прикладных служб квартиры. Его задача — запускать средства развёртывания и сопровождения, хранить их постоянное состояние и предоставлять единый проверяемый управляющий контур.

## Назначение

Через 910 выполняются:

- построение и применение изменений OpenTofu для управляемых объектов;
- настройка Linux-гостей через Ansible;
- сборка базового шаблона через Packer;
- запуск инфраструктурных заданий Semaphore;
- работа OpenBao как защищённого хранилища рабочих секретов и SSH-центров доверия;
- проверка состояния управляющего контура.

Home Assistant, MQTT, Zigbee2MQTT, ESPHome, Frigate и другие прикладные службы в 910 не размещаются.

## Состав

В 910 работают два основных контейнера:

| Контейнер | Назначение |
|---|---|
| `infra-runtime` | Semaphore и инструменты управления: Ansible, OpenTofu, Packer, Python, Git и OpenSSH |
| `openbao` | рабочие секреты, SSH-центры доверия и служебные механизмы OpenBao |

Кроме контейнеров, в 910 есть системные службы для запуска, разблокировки OpenBao, активации новой версии рабочей среды и переходных механизмов, которые ещё не заменены целевой архитектурой.

Подробное устройство частей 910 описано в [`docs/README.md`](docs/README.md).

## Границы

910 является административным управляющим контуром, но не входит в `pool managed` и не управляет собственным объектом Proxmox через своё постоянное состояние OpenTofu.

Права между субъектами задаются общим машинным контрактом [`infrastructure/security/access.yaml`](../../security/access.yaml). Общие правила доступа находятся в разделе [`docs/700-security`](../../../docs/700-security/README.md).

Постоянные данные 910 хранятся вне его корневой файловой системы в областях PVE. Поэтому пересоздание LXC не должно уничтожать состояние OpenBao, Semaphore и OpenTofu. Точное размещение описано в [`docs/data-and-access.md`](docs/data-and-access.md).

## Жизненный цикл

Первое создание 910 выполняет первоначальный контур. После этого обычное обновление выполняется тем же общим механизмом развёртывания гостей через задание Semaphore `Deploy Guest 910`.

Объект LXC 910 при обычном обновлении не добавляется в постоянное состояние OpenTofu самого 910. Особенности самообновления `infra-runtime` описаны в [`docs/infra-runtime.md`](docs/infra-runtime.md).

Общий порядок развёртывания находится в [`810-deployment.md`](../../../docs/800-operations/810-deployment.md), аварийного восстановления — в [`830-recovery.md`](../../../docs/800-operations/830-recovery.md).

## Проверка состояния

Основная проверка внутри 910:

~~~bash
infra-manager-status --full
~~~

С PVE:

~~~bash
pct exec 910 -- infra-manager-status --full
~~~

Состав проверок и итогового экрана задаёт [`status.yaml`](status.yaml).

## Источники точных значений

README является паспортом гостя и не заменяет машинные файлы.

| Источник | Что задаёт |
|---|---|
| [`guest.yaml`](guest.yaml) | объект Proxmox и его основные свойства |
| [`provision.yaml`](provision.yaml) | ОС, пакеты, контейнеры, версии, пути, подключения и постоянное состояние |
| [`status.yaml`](status.yaml) | проверки и итоговое представление состояния |
| [`rootfs/`](rootfs/) | воспроизводимые файлы 910, разложенные по конечным путям Linux |
| [`docs/decisions.md`](docs/decisions.md) | причины решений, относящихся именно к 910 |

Каталог `rootfs/` не копируется на гостя целиком автоматически. Каждый файл устанавливается явным повторяемым механизмом.
