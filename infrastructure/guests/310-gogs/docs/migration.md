# Перенос Gogs из Docker Desktop

**Статус:** первичный перенос данных и запуск гостя 310 выполнены.
Исходный Windows Gogs выключен; архив до переноса сохранён на Windows.
Для возврата к идентичному исходному образу нужен отдельный контролируемый
этап смены Docker-образа. Не запускать `deploy 310` с новым digest до проверки
исходной SQLite и образа.

## 1. Исходное состояние

- Windows: `E:\\!SERVICES\\GOGS\\gogs` подключён как `/data`;
- Gogs `0.15.0+dev`, SQLite, `/data/gogs/conf/app.ini`;
- `[database] PATH = data/gogs.db`; файл базы следует проверить перед переносом;
- `[repository] ROOT = /data/git/gogs-repositories`, около 8,7 ГиБ данных;
- прежний контейнер: HTTP 3000, SSH снаружи контейнера на 2222;
- том `/backup` практически пуст и не является основной копией данных.

**Исходная сборка Windows:** `gogs/gogs@sha256:593818f84e4f6233560706173fd5cdf8ba903065b9619c91bcbb796c3dc73e41`,
`amd64`, создана 2026-05-19. Именно этот digest следует использовать для
возврата к первоначальной версии Gogs. Внутри исходного образа OpenSSH слушает
TCP 22; Docker публикует его как `192.168.3.10:2222`.

**Предыстория:** при первом развёртывании 310 ошибочно использовалась другая
сборка edge с React. Она открывала перенесённую SQLite; следовательно,
нельзя считать текущую базу автоматически совместимой с исходным образом.
Первоначальный TAR на Windows не удалять, держать Gogs на Windows остановленным
до приёмки Linux-установки.

## 2. Сначала развёртывание инфраструктуры

Выполнить с PVE `infra-manager deploy 310`. Подготовка создаёт LXC
310 (при отсутствии), отдельный логический том 30 ГиБ и подключение
`/var/lib/gogs`. Пока данные не импортированы, роль Gogs останавливается
с понятной ошибкой **до загрузки образа и запуска контейнера**.
Это ожидаемое поведение первого развёртывания.

Том PVE: `/mnt/bindmounts/gogs-data/310-gogs` — не `infra_state`.
Нельзя вручную создавать каталог `/var/lib/gogs` на системном диске
взамен неработающего подключения. Путь внутри Docker: `/data`.

## 3. Согласованный экспорт с Windows

1. Сделать независимую копию исходного каталога и убедиться, что она
   читается. Не удалять старые данные до успешного перевода.
2. Записать контрольную сводку: количество репозиториев, версию Gogs,
   размер `/data` и имена существующих пользователей.
3. Остановить **запись** в старый Gogs: `docker stop gogs`.
4. Создать архив всего каталога, включая скрытые файлы, через Linux
   внутри Docker (для сохранения структуры и связей):

   ```cmd
   docker run --rm -v "E:\!SERVICES\GOGS\gogs:/source:ro" -v "E:\!SERVICES\GOGS:/export" alpine:3.23 sh -c "cd /source && tar -czf /export/gogs-data.tar.gz ."
   ```

   Файл `E:\!SERVICES\GOGS\gogs-data.tar.gz` должен быть вне каталога
   `gogs`, чтобы не попасть в собственный архив. При переносе сверить
   целостность архива и проверить, что в нём есть база, конфигурация и
   каталог репозиториев. Пароли и содержимое `app.ini` не публиковать.
5. Передать архив в 310 по доверенному административному каналу
   (например, через PVE), распаковать **только** на настоящий подключённый
   том `/var/lib/gogs`. Не запускать приложение во время переноса.
   Не копировать в исходный рабочий каталог Gogs.

После распаковки проверить путь базы `/var/lib/gogs/gogs/data/gogs.db`.
Если он иной, остановиться и выяснить действующее расположение SQLite,
а не создавать новую базу.

## 4. Подтверждение переноса и запуск

После успешного копирования с LXC 310:

```bash
python3 /opt/gogs/prepare_data.py --data /var/lib/gogs --confirm
```

Программа проверяет реальную SQLite и каталоги, переводит файлы в
владение UID/GID 1000 (совместимо с новым образом) и создаёт
`/var/lib/gogs/.gogs-imported`. Она должна запускаться только при
остановленном Gogs. После этого повторить:

```bash
infra-manager deploy 310
```

Это команда **на PVE**, а не внутри LXC. В штатном развёртывании
Ansible проверяет постоянные данные и меняет только предназначенные
для новой установки поля `app.ini`; старый секретный ключ сохраняется.
Если проверка SQLite или старт Gogs не проходят, старый контейнер на
Windows можно вернуть в работу, не затрагивая его данные.

## 5. Подключение домена и проверка

После успешного запуска в 310 проверить локальный HTTP и SSH.
В административной странице `https://home.zsergey.ru/admin` найти
выключенный маршрут `git.zsergey.ru`, задать
`http://192.168.3.10:3000`, выбрать `git_https` и включить.
Потребуется DNS-запись `git.zsergey.ru` на текущую внешнюю
точку входа Caddy.

Проверить вход существующего пользователя, закрытые репозитории,
список веток и коммитов, а также `git clone`, `pull`, `push` по HTTPS.
Проверить внутренний SSH на `192.168.3.10:2222` со старым ключом.
Наружу TCP 2222 не направлять. После переключения не запускать
оба сервера одновременно для записи: данные разойдутся.

Только после приёмки сделать независимую резервную копию 310,
а старый Windows Gogs оставить выключенным до проверки восстановления.
