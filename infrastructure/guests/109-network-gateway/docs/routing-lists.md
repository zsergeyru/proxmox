## 1. Назначение и модель

### 1.1. Зачем нужен отдельный механизм

Маршрут не должен зависеть от конкретного поставщика списков.

Источником может быть:

- локальный файл проекта;
- обычный текстовый файл по HTTP/HTTPS;
- файл из GitHub или другого Git-хранилища;
- новый внешний поставщик, который появится позже.

После загрузки данные приводятся к единому внутреннему виду, поэтому замена поставщика не требует менять логику SmartDNS, nftables или VPN.

Общая цепочка:

~~~text
локальные и внешние источники
          ↓
проверка и нормализация
          ↓
группы direct / vpn1 / vpn2 / zapret
          ↓
SmartDNS / nftables
          ↓
WAN / VPN1 / VPN2 / NFQUEUE→nfqws2
~~~

### 1.2. Что хранится в Git

В Git хранятся:

- описание источников;
- назначение каждого источника;
- локальные небольшие списки и исключения;
- правила приоритетов;
- параметры обновления.

Большие внешние списки в Git проекта копировать не требуется. Они загружаются на 109 и имеют собственную последнюю рабочую копию.

Конкретные поставщики, например MetaCubeX, ru-route-lists или domain-list-community, являются только возможными источниками данных и не являются частью архитектурного контракта.

## 2. Источники и форматы

### 2.1. Универсальное описание источника

Целевая машинная модель должна позволять описать источник независимо от его поставщика.

Пример:

~~~yaml
routing:
  default: direct

  sources:
    - name: youtube
      type: http
      url: https://example.invalid/youtube.txt
      format: domain-list
      target: vpn1
      priority: 100

    - name: local-direct
      type: file
      path: rules/direct.txt
      format: domain-list
      target: direct
      priority: 1000
~~~

Новый поставщик добавляется новой записью. Код 109 при этом не должен требовать отдельной поддержки имени поставщика.

### 2.2. Типы источников

На первом этапе достаточно двух типов:

| Тип | Назначение |
|---|---|
| `file` | локальный файл, поставляемый проектом |
| `http` | файл, загружаемый по HTTP/HTTPS |

Позже могут появиться другие способы получения данных, но они не должны менять модель групп и маршрутизации.

### 2.3. Форматы

На первом этапе следует поддержать:

| Формат | Содержимое |
|---|---|
| `domain-list` | домены и доменные суффиксы |
| `hosts` | записи в формате hosts, из которых извлекаются имена |
| `ip-list` | отдельные IPv4/IPv6 |
| `cidr-list` | IPv4/IPv6 сети |

Поддержка `geosite`, `geoip` или других форматов может быть добавлена позже через отдельный преобразователь.

Внутренний результат не должен зависеть от исходного формата.

### 2.4. Нормализация

При загрузке источник:

1. скачивается или читается локально;
2. проверяется на допустимый формат;
3. очищается от пустых строк и комментариев;
4. приводит доменные имена к единому виду;
5. удаляет дубликаты;
6. преобразует IP и сети к канонической записи;
7. передаёт нормализованный результат в целевую группу.

Ошибочная строка не должна незаметно превращаться в правило маршрутизации.

## 3. Назначения и приоритеты

### 3.1. Фиксированные виды действия

Источники данных отделены от действий.

На первом этапе используются четыре логических назначения:

| Назначение | Действие |
|---|---|
| `direct` | обычный WAN через Keenetic |
| `vpn1` | первый VPN-выход |
| `vpn2` | второй VPN-выход |
| `zapret` | прямой WAN с обработкой выбранного трафика через `nfqws2` |

Позже можно добавить `vpn3` или другой именованный VPN без изменения формата источников.

`zapret` не является VPN. Это отдельный способ обработки трафика перед обычным выходом в WAN.

### 3.2. Маршрут по умолчанию

Базовое правило:

~~~text
нет совпадения → direct
~~~

Таким образом не требуется перечислять весь обычный Интернет.

### 3.3. Приоритет

Каждый источник или локальное правило может иметь числовой `priority`.

Чем больше число, тем выше приоритет.

Локальные исключения проекта должны иметь более высокий приоритет, чем массовые внешние списки.

Пример:

~~~text
*.com        → vpn1   priority 100
github.com   → direct priority 1000
~~~

Результат для `github.com` — `direct`.

### 3.4. Конфликты

Один домен или адрес может попасть в несколько внешних списков.

Правила разрешения конфликтов:

1. выбирается запись с наибольшим `priority`;
2. при одинаковом приоритете неоднозначность считается ошибкой конфигурации;
3. система не должна молча выбирать одно из равноправных назначений;
4. локальные явные исключения используются для разрешения известных конфликтов.

Для доменов более точное имя может использоваться как исключение из более общего суффикса.

Пример:

~~~text
.com             → vpn1
example.com      → direct
api.example.com  → vpn2
~~~

## 4. Обновление и отказоустойчивость

### 4.1. Периодическое обновление

Внешние источники обновляются автоматически по расписанию.

Период обновления должен задаваться отдельно от адреса источника.

Обновление не должно перезапускать сетевой шлюз целиком.

### 4.2. Последняя рабочая копия

Для каждого внешнего источника хранится последняя успешно проверенная копия.

Если новый файл:

- не загрузился;
- пуст;
- имеет неверный формат;
- содержит явно аномальное количество записей;
- не проходит проверку;

текущая рабочая копия остаётся активной.

Недоступность GitHub или другого поставщика не должна ломать маршрутизацию.

### 4.3. Безопасное применение

Обновление выполняется в порядке:

~~~text
download → validate → normalize → build new sets → atomic switch
~~~

Старая конфигурация удаляется только после успешной подготовки новой.

После применения выполняется короткая проверка direct, каждого VPN и `zapret`.

При неуспехе должен быть возможен возврат к предыдущей рабочей версии.

### 4.4. Доверие к внешним спискам

Внешний список влияет на маршрут домашнего трафика, поэтому источник считается частью цепочки доверия.

Следует:

- использовать HTTPS;
- выбирать известные поддерживаемые источники;
- по возможности закреплять конкретный URL файла, а не HTML-страницу;
- поддержать контрольную сумму или подпись, если поставщик их предоставляет;
- журналировать время и результат обновления;
- не выполнять полученный файл как код.

## 5. Результат для SmartDNS и nftables

### 5.1. Доменные группы

Нормализованные домены передаются SmartDNS.

SmartDNS определяет принадлежность DNS-запроса группе и помещает IP-адреса ответа в соответствующий nftables set.

Пример:

~~~text
youtube.example → vpn1
some-service.example → vpn2
blocked.example → zapret
остальные → direct
~~~

### 5.2. IP и CIDR

Списки IP/CIDR не требуют DNS-разрешения и могут сразу формировать соответствующие nftables sets.

Доменные и IP-правила должны сходиться в одной модели назначений.

### 5.3. Выбор действия

~~~text
set direct → main table → Keenetic
set vpn1   → mark VPN1 → table VPN1
set vpn2   → mark VPN2 → table VPN2
set zapret → NFQUEUE → nfqws2 → main table → Keenetic
нет set    → main table → Keenetic
~~~

`nfqws2` получает только трафик, для которого явно выбрано назначение `zapret`.

## 6. Проверка и восстановление

### 6.1. Проверка

Должны проверяться:

- чтение локального источника;
- загрузка внешнего источника;
- обработка каждого поддерживаемого формата;
- удаление дубликатов;
- приоритет локального исключения;
- обнаружение конфликта одинакового приоритета;
- сохранение последней рабочей копии при ошибке обновления;
- заполнение nftables set из тестовой доменной группы;
- direct, VPN1, VPN2 и `zapret` на тестовых целях.

### 6.2. Восстановление

Для восстановления нужны:

- описание источников из Git;
- локальные списки и исключения;
- механизм загрузки и нормализации;
- последняя рабочая копия внешних источников либо возможность загрузить их заново;
- конфигурация SmartDNS;
- конфигурация nftables и PBR.

Кэш загруженных внешних списков полезен для быстрого восстановления, но не заменяет машинное описание источников.
