## 1. Принято

Архитектурно принято:

- VMID 109;
- Debian 13 VM;
- 2 vCPU, 2 GiB RAM, 16 GiB disk;
- 109 является штатным шлюзом HOME;
- 109 является штатным DHCP и DNS HOME;
- основной DHCP на 109 реализуется через dnsmasq;
- SmartDNS остаётся основным DNS;
- локальный домен — home.arpa;
- постоянные устройства получают DHCP-резервации и согласованные локальные DNS-имена;
- Keenetic DHCP HOME в штатном режиме выключен, но заранее подготовлен для ручного аварийного включения;
- Keenetic остаётся пограничным маршрутизатором и ручным аварийным обходом;
- TRANSIT — 10.0.0.0/30;
- Keenetic TRANSIT — 10.0.0.1;
- 109 WAN — 10.0.0.2;
- HOME — 192.168.0.0/16;
- LAN-IP 109 — 192.168.1.9;
- динамический DHCP HOME — 192.168.1.100–192.168.1.250;
- VLAN 10 = TRANSIT;
- VLAN 20 = HOME;
- один физический NIC PVE переносит обе сети;
- обычный WAN использует NAT только на Keenetic;
- SmartDNS, nftables, PBR и исходящие VPN принадлежат 109;
- аварийное переключение выполняется вручную.

## 2. Уже есть в проекте

В Git присутствуют:

- guest.yaml для VMID 109;

- решения в decisions;
- общая документация сетевой схемы;

Фактическое развёртывание целевой сетевой схемы на PVE этим документом не подтверждается. Общий контракт `network.interfaces` уже реализован в машинной схеме, resolver, валидаторе и OpenTofu, а `guest.yaml` 109 использует два интерфейса.

## 3. Ещё нужно реализовать

1. Определить формат списка постоянных устройств и DHCP-резерваций.
2. Добавить `provision.yaml`.
3. Создать Ansible-роли для сетевой настройки, dnsmasq, nftables, SmartDNS, WireGuard/AmneziaWG, PBR и проверок.
4. Настроить VLAN 10 и VLAN 20 на Keenetic.
5. Настроить VLAN-aware bridge на PVE.
6. Применить два VirtIO-интерфейса VM 109 через OpenTofu.
7. Добавить маршрут HOME на Keenetic через 10.0.0.2.
8. Подготовить аварийный DHCP HOME на Keenetic и оставить его выключенным.
9. Проверить один тестовый клиент: DHCP, DNS, home.arpa, прямой WAN и VPN.
10. Проверить ручной аварийный возврат на Keenetic.
11. Только после этого перевести всю HOME на DHCP 109.

## 4. Проверка готовности

109 готов к роли основного шлюза только после подтверждения:

- WAN 10.0.0.2 ↔ 10.0.0.1;
- DHCP на 109;
- DHCP-резервации;
- локальных имён home.arpa;
- доступа LAN-клиента к 109;
- прямого Интернета;
- обратного маршрута Keenetic → 109 → HOME;
- отсутствия двойного NAT;
- SmartDNS;
- DoH/DoT;
- PBR по тестовой доменной группе;
- AmneziaWG/WireGuard;
- восстановления после перезапуска;
- ручного аварийного режима без PVE/109.

До прохождения этих проверок Keenetic остаётся действующим основным шлюзом и DHCP сети.
