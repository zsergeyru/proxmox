## 1. Назначение и состав

### 1.1. Роль VM

VM 109 является штатным шлюзом внутренней сети.

Через неё проходят:

- обычный выход клиентов в Интернет;
- DNS-запросы;
- DHCP;
- трафик, направляемый по отдельным правилам;
- исходящие VPN;
- удалённый VPN-доступ, если он включён.

На 109 не размещаются обратный прокси, домашняя стартовая страница, прикладные веб-службы и службы управления инфраструктурой.

### 1.2. Ресурсы

~~~text
VMID: 109
name: network-gateway
OS: Debian 13
vCPU: 2
RAM: 2 GiB
disk: 16 GiB
NIC: 2 x VirtIO
QEMU Guest Agent: enabled
~~~

Два сетевых интерфейса логические: физический сетевой порт PVE один.

## 2. Сеть

### 2.1. Физическая схема

Keenetic подключён к провайдеру, к общей домашней сети и отдельным кабелем к единственному физическому порту PVE.

Порт Keenetic ↔ PVE работает как trunk:

~~~text
VLAN 10 → TRANSIT
VLAN 20 → HOME
~~~

Отдельной нетегированной клиентской сети на этом trunk нет.

### 2.2. TRANSIT

VLAN 10 используется только между Keenetic и WAN-интерфейсом 109:

~~~text
network: 10.0.0.0/30
Keenetic: 10.0.0.1
109 WAN: 10.0.0.2
~~~

DHCP в TRANSIT не нужен.

Обычный маршрут по умолчанию VM 109:

~~~text
default via 10.0.0.1
~~~

### 2.3. HOME

VLAN 20 является основной домашней сетью.

~~~text
192.168.0.0/16
~~~

Проводные клиентские порты Keenetic относятся к VLAN 20 как access-порты. Основной Wi-Fi также относится к HOME/VLAN 20.

LAN-интерфейс 109 подключён к VLAN 20 и является штатным шлюзом, DHCP и DNS для клиентов.

Точный LAN-IP 109 должен быть закреплён до реализации одновременно в настройках Keenetic, PVE, guest.yaml и DHCP HOME.

### 2.4. Обычный путь в Интернет

~~~text
client
  ↓
109 LAN
  ↓
routing / nftables
  ↓
109 WAN 10.0.0.2
  ↓
Keenetic 10.0.0.1
  ↓
NAT Keenetic
  ↓
Internet
~~~

Для обычного прямого выхода через Keenetic NAT на 109 не выполняется.

Keenetic должен иметь маршрут к HOME через 10.0.0.2, поэтому ответный трафик также проходит через 109.

## 3. Службы и порядок работы

### 3.1. Обязательные компоненты

На уровне ОС:

- Linux IP forwarding;
- nftables;
- ip rule;
- отдельные таблицы маршрутизации;
- DHCP-служба;
- AmneziaWG/WireGuard;
- systemd-службы контроля сетевого состояния.

SmartDNS допускается запускать в Docker, но маршрутизация и межсетевой экран не должны зависеть от Docker-сети.

Для DHCP на первом этапе используется dnsmasq как простой DHCP-сервер для HOME. SmartDNS остаётся основным DNS-сервером.

sing-box допускается только там, где обычной L3-маршрутизации недостаточно.

### 3.2. Общая логика

~~~text
DHCP
  ├── IP
  ├── gateway = 109
  └── DNS = 109

DNS request
  ↓
SmartDNS
  ↓
destination addresses / nftables set
  ↓
fwmark
  ↓
ip rule
  ↓
routing table
  ├── ordinary WAN
  ├── AmneziaWG
  └── other VPN
~~~

## 4. DHCP и локальные имена

### 4.1. Основной DHCP

Основной DHCP для HOME работает на VM 109.

Keenetic DHCP для HOME в штатном режиме выключен, но его аварийная конфигурация должна быть заранее подготовлена.

DHCP 109 раздаёт клиентам:

- IP-адрес;
- маску;
- gateway 109;
- DNS 109;
- при необходимости постоянное назначение адреса по MAC/идентификатору клиента.

### 4.2. Имена устройств

Для постоянных устройств используются понятные имена в домене home.arpa.

Примеры:

~~~text
nas.home.arpa
printer.home.arpa
tv-living.home.arpa
phone-sergey.home.arpa
~~~

Для устройств, которым нужен постоянный адрес и имя, DHCP-резервация является источником назначения адреса, а локальная DNS-запись должна соответствовать этой резервации.

Не следует вручную раздавать статические адреса на самих клиентах без необходимости, если тот же результат можно получить через DHCP-резервацию.

### 4.3. Связь DHCP и DNS

DHCP и SmartDNS должны использовать согласованный список постоянных устройств.

На первом этапе допускается хранить декларативный список устройств в проекте и из него формировать:

- DHCP-резервации dnsmasq;
- локальные записи home.arpa для SmartDNS.

Это исключает расхождение между именем устройства и его постоянным адресом.

## 5. Развёртывание и запуск

### 5.1. Предварительные условия

До переключения клиентов на 109 должны быть готовы:

- VLAN 10 и VLAN 20 на Keenetic;
- VLAN-aware bridge на PVE;
- два интерфейса VM 109;
- связь 109 WAN ↔ 10.0.0.1;
- связь LAN 109 с HOME;
- маршрут HOME на Keenetic через 10.0.0.2;
- DHCP на 109;
- SmartDNS;
- nftables;
- прямой WAN-маршрут;
- проверенный VPN-маршрут, если VPN включается сразу;
- заранее подготовленный, но выключенный аварийный DHCP Keenetic.

### 5.2. Безопасный порядок миграции

1. Создать TRANSIT/VLAN 10 на Keenetic.
2. Настроить trunk Keenetic ↔ PVE.
3. Включить VLAN-aware bridge на PVE.
4. Подключить WAN 109 к VLAN 10.
5. Подключить LAN 109 к VLAN 20.
6. Проверить связь 109 с Keenetic и HOME.
7. Настроить маршрут HOME на Keenetic через 109.
8. Запустить DHCP, SmartDNS и маршрутизацию на 109.
9. На одном тестовом клиенте проверить получение адреса, gateway и DNS от 109.
10. Проверить локальное имя клиента в home.arpa.
11. Проверить прямой Интернет и VPN.
12. Только после этого выключить DHCP HOME на Keenetic для штатного режима и перевести остальные клиенты на DHCP 109.

## 6. Проверка

Должны подтверждаться:

~~~text
109 → 10.0.0.1
client → DHCP 109
client → DNS 109
client → 109 LAN
client → Keenetic through 109
client → Internet directly
client → Internet through VPN
~~~

Для постоянного тестового клиента дополнительно проверяются:

- получение закреплённого IP;
- разрешение имени client.home.arpa;
- совпадение DHCP-резервации и DNS-записи.

Путь ответа обычного WAN:

~~~text
Internet → Keenetic → 109 → client
~~~

Двойного NAT на обычном WAN быть не должно.

После перезапуска VM автоматически восстанавливаются интерфейсы, forwarding, nftables, DHCP, таблицы маршрутизации, SmartDNS и VPN.

## 7. Авария и восстановление

### 7.1. Падение 109 или PVE

Автоматическое переключение не требуется.

Keenetic сохраняет прямое физическое подключение к HOME. При аварии оператор:

1. включает заранее подготовленный DHCP HOME на Keenetic;
2. Keenetic раздаёт собственный адрес как gateway;
3. Keenetic раздаёт собственный DNS;
4. клиенты обновляют DHCP-аренду или переподключаются к сети.

После этого клиенты выходят в Интернет напрямую через Keenetic.

В аварийном режиме могут отсутствовать локальные имена home.arpa, SmartDNS, доменный PBR и VPN 109. Базовый Интернет должен работать.

### 7.2. Возврат

После восстановления:

1. проверить WAN и LAN 109;
2. проверить DHCP 109;
3. проверить SmartDNS и home.arpa;
4. проверить прямой WAN;
5. проверить VPN;
6. выключить аварийный DHCP Keenetic;
7. обновить DHCP одного тестового клиента;
8. после проверки обновить остальные клиенты.

### 7.3. Полное восстановление

VM должна быть воспроизводима из guest.yaml, будущего provision.yaml, Ansible-ролей, локальной документации и секретов из принятого хранилища секретов.

Закрытые ключи и VPN-секреты в Git не хранятся.
