# 109 — network-gateway

**Тип:** VM  
**ОС:** Debian 13  
**Назначение:** основной шлюз внутренней сети, DNS, исходящие VPN, маршрутизация по правилам, межсетевой экран и сетевые сервисы на Linux.

Общая схема сети описана в [../../../docs/400-network/410-network-layout.md](../../../docs/400-network/410-network-layout.md). Текущая граница ответственности Keenetic и этой VM зафиксирована в [decisions/002-primary-gateway-and-fallback.md](decisions/002-primary-gateway-and-fallback.md).

## Что делает 109

На уровне ОС VM:

- nftables;
- ip rule и отдельные таблицы маршрутизации;
- fwmark и PBR;
- AmneziaWG/WireGuard и другие исходящие VPN;
- основной VPN для удалённого доступа;
- контроль работоспособности и восстановление сетевых сервисов;
- при необходимости отражение mDNS между явно разрешёнными сегментами.

В Docker допускаются:

- SmartDNS — основной DNS-сервис;
- AdGuard Home — только необязательный веб-интерфейс для статистики и фильтрации;
- sing-box — только для прокси и сложных исходящих соединений, где обычной L3-маршрутизации недостаточно.

Маршрутизация VPN/PBR принадлежит ОС VM, а не внутренней сети Docker.

## DNS и маршрутизация

Принятая схема:

~~~text
SmartDNS
   ↓
адреса назначения / наборы nftables
   ↓
fwmark
   ↓
ip rule / таблицы маршрутизации
   ├── обычный WAN через Keenetic
   ├── AmneziaWG
   └── другие VPN и выходы
~~~

SmartDNS поддерживает обычные внешние DNS-серверы, DoH/DoT и группы доменов. keen-pbr внутри VM не используется.

Постоянный внутренний домен — home.arpa. .local используется только для mDNS.

## Сетевые интерфейсы и адресация

PVE-хост имеет один физический сетевой порт. Поэтому VM 109 получает два логических VirtIO-интерфейса через разные VLAN одного VLAN-aware bridge.

### WAN / TRANSIT

~~~text
сеть:      10.0.0.0/30
Keenetic:  10.0.0.1
109 WAN:   10.0.0.2
~~~

Это отдельная служебная сеть только между Keenetic и 109.

### LAN

Домашняя адресация остаётся в диапазоне:

~~~text
192.168.0.0/16
~~~

Точный LAN-адрес 109 и номера VLAN задаются одинаково в конфигурации Keenetic, PVE и гостя.

В штатном режиме 109 является шлюзом и DNS для внутренней сети.

## Обычный выход в Интернет

Путь трафика:

~~~text
клиент
  ↓
109
  ↓
10.0.0.2
  ↓
Keenetic 10.0.0.1
  ↓
Интернет
~~~

Для обычного прямого выхода через Keenetic дополнительный NAT на 109 не используется.

Keenetic выполняет единственный NAT к провайдеру и должен иметь маршрут к внутренней сети через 10.0.0.2.

## Аварийный режим

Keenetic сохраняет прямое физическое подключение к внутренней сети.

При отказе PVE или 109 оператор вручную возвращает Keenetic в роль шлюза и DNS для клиентов. Автоматическое резервирование на первом этапе не требуется.

В аварийном режиме базовый Интернет должен работать без 109, но функции SmartDNS, PBR и VPN на 109 могут быть недоступны.

## VPN для удалённого доступа

Основная туннельная сеть:

~~~text
10.60.0.0/16
~~~

Удалённые доверенные клиенты получают домашний DNS и доступ только к разрешённым сегментам. Поддерживаются профили с маршрутизацией только домашней сети и всего трафика через VPN.

Ограниченный аварийный VPN на Keenetic допускается отдельно, чтобы доступ к инфраструктуре не зависел от VM 109.

## IPv6

Архитектура IPv6 должна сохранять ту же границу ответственности: 109 является штатным сетевым шлюзом внутренней сети, а Keenetic остаётся пограничным устройством к провайдеру и аварийным обходом.

Точная схема DHCPv6-PD, RA и IPv6-маршрутизации будет зафиксирована отдельно до реализации IPv6.

## Размещение конфигурации

Управляемые файлы гостевой ОС должны создаваться явными Ansible-ролями по фактическим путям назначения, например:

~~~text
/etc/nftables.conf
/etc/systemd/system/...
/etc/wireguard/...
/opt/network-gateway/smartdns/...
~~~

Статические файлы роли, шаблоны и данные provision.yaml используются явно; общего зеркала файловой системы из Git нет.

Секреты VPN, закрытые ключи, предварительно согласованные ключи и пароли в Git не добавляются.
