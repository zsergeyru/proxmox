## 1. Назначение

### 1.1. Роль Open WebUI

Open WebUI является основным пользовательским веб-интерфейсом 410.

Он отвечает за:

- вход пользователей;
- диалоги;
- историю диалогов;
- стандартные возможности рабочего интерфейса Open WebUI;
- выбор доступной модели AI Control;
- передачу пользовательского запроса внутреннему API AI Control.

Open WebUI не является владельцем полномочий квартиры и не должен напрямую получать административные доступы к Home Assistant, Proxmox, сети или другим системам.

Управляющая цепочка:

```text
браузер
↓
Open WebUI :4100
↓
OpenAI-совместимый API AI Control :4110
↓
Hermes
↓
модели и инструменты AI Control
```

### 1.2. Почему Open WebUI не заменяет ядро

Open WebUI является пользовательской оболочкой.

В ядре AI Control остаются:

- основной агент;
- выбор модели;
- инструменты;
- права;
- задачи;
- события;
- память AI Control;
- подтверждения действий;
- журнал управляющих операций.

Поэтому замена Open WebUI в будущем не должна требовать переработки интеграций квартиры.

## 2. Размещение

### 2.1. Контейнер

Open WebUI запускается в Docker внутри VM 410.

Требуемый образ задаётся в `provision.yaml` и должен быть закреплён на конкретной версии.

Текущая версия:

```text
ghcr.io/open-webui/open-webui:0.11.4-slim
```

Используется облегчённый образ, потому что сами AI-модели не запускаются внутри контейнера Open WebUI.

### 2.2. Сеть

Контейнер использует сетевой режим хоста.

Open WebUI слушает:

```text
0.0.0.0:4100
```

Внутреннее ядро AI Control слушает только:

```text
127.0.0.1:4110
```

Поэтому Open WebUI может обращаться к ядру через локальный адрес, но внутренний API не публикуется в домашнюю сеть.

Прямое размещение Open WebUI в Интернете не является штатной схемой. Внешний доступ должен добавляться отдельным защищённым решением.

## 3. Связь с AI Control

### 3.1. OpenAI-совместимый API

Open WebUI подключается к:

```text
http://127.0.0.1:4110/v1
```

Ядро должно предоставлять как минимум:

```text
GET  /v1/models
POST /v1/chat/completions
```

Текущий логический идентификатор модели:

```text
hermes-agent
```

Для Open WebUI это модель, а внутри AI Control запрос передаётся основному агенту Hermes.

### 3.2. Внутренний ключ

Open WebUI обращается к API AI Control по отдельному внутреннему Bearer token.

Ключ:

- создаётся при первом развёртывании;
- не хранится в Git;
- не является пользовательским паролем;
- используется только для связи локального Open WebUI с ядром.

Файл:

```text
/etc/ai-control/api.env
```

## 4. Данные и секреты

### 4.1. Постоянные данные

Постоянные данные Open WebUI размещаются в:

```text
/opt/ai-control/state/open-webui/
```

Контейнер получает этот каталог как:

```text
/app/backend/data
```

Он входит в общий резервируемый каталог `/opt/ai-control/state/`. На хосте каталог создаётся с владельцем `root` и режимом `0700`.

В нём находятся пользовательские учётные записи, диалоги и внутренние настройки Open WebUI.

### 4.2. Секреты

Локальные секреты Open WebUI хранятся в:

```text
/etc/ai-control/open-webui.env
```

Там находятся:

- `WEBUI_SECRET_KEY`;
- адрес начального администратора;
- начальный пароль администратора.

Файл создаётся только на госте, имеет режим `0600` и не входит в Git.

Начальный администратор:

```text
admin@ai-control.local
```

Пароль можно посмотреть административной командой на 410:

```bash
grep '^WEBUI_ADMIN_PASSWORD=' /etc/ai-control/open-webui.env
```

После первого входа пароль можно изменить средствами Open WebUI.

## 5. Развёртывание и обновление

### 5.1. Развёртывание

Роль `ai_control` должна:

1. убедиться, что Docker установлен общей ролью `docker`;
2. подготовить постоянный каталог данных;
3. создать локальные секреты;
4. сформировать Compose-файл;
5. проверить его через `docker compose config --quiet`;
6. получить закреплённый образ;
7. запустить контейнер с `no-new-privileges`;
8. оставить автоперезапуск `unless-stopped`.

Compose-файл:

```text
/opt/ai-control/compose/open-webui.yml
```

### 5.2. Обновление

Версия Open WebUI меняется только через `provision.yaml`.

Штатный порядок:

```text
изменить image tag
→ применить Ansible
→ docker compose pull
→ docker compose up -d
→ проверить интерфейс и связь с AI Control
```

Плавающие `:main` и `:latest` не используются для штатного развёртывания.

## 6. Проверка и восстановление

### 6.1. Проверка

После развёртывания проверяются:

- контейнер `open-webui` работает;
- порт `4100` доступен из разрешённой сети;
- вход администратора работает;
- в списке моделей виден `hermes-agent`;
- Open WebUI получает список моделей с AI Control;
- пользовательский запрос доходит до `POST /v1/chat/completions`;
- после перезапуска сохраняются пользователь и история диалогов.

До установки Hermes сам запрос может завершаться состоянием `agent_unavailable`. Это означает, что связка Open WebUI → AI Control работает, но агент ещё не подключён.

### 6.2. Восстановление

При восстановлении 410:

1. восстановить `/opt/ai-control/state/`;
2. повторно применить Ansible;
3. заново создать локальные секреты, если они не сохранены;
4. получить закреплённый Docker-образ;
5. запустить Open WebUI;
6. проверить вход и связь с внутренним API.

Если `WEBUI_SECRET_KEY` был создан заново, существующие сессии пользователей могут потребовать повторного входа. Данные Open WebUI при этом остаются в постоянном каталоге.
