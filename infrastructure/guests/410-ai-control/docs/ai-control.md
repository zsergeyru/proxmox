# AI Control на 410

**Тип:** локальная спецификация  
**Статус:** целевое состояние  
**Назначение:** описать состав и границы системы `410 ai-control`.

AI Control — это **название всей интеллектуальной управляющей системы 410**, а не отдельная самописная программа.

## 1. Назначение и состав

### 1.1. Роль 410

`410 ai-control` предоставляет единый интеллектуальный интерфейс квартиры.

Базовая схема:

```text
пользователь
↓
Open WebUI :4100
↓
Hermes API :8642
↓
Hermes Agent
├── память и сессии
├── cron и длительные задачи
├── skills / MCP / инструменты
├── выбор и вызов модели
└── разрешённые интеграции
    ├── Home Assistant
    ├── 910 infra-manager
    ├── сеть
    └── мониторинг
```

В штатной конфигурации используется один основной универсальный агент — Hermes.

### 1.2. Компоненты

В 410 размещаются:

- Docker;
- Hermes Agent;
- Open WebUI;
- постоянное состояние Hermes;
- постоянное состояние Open WebUI;
- локальные секреты связи Open WebUI с Hermes;
- в будущем — конфигурация разрешённых MCP и других интеграций.

Отдельного процесса, службы или API с названием `AI Control` не требуется.

## 2. Разделение ответственности

### 2.1. Hermes

Hermes является агентной средой 410 и отвечает за:

- агентный цикл;
- OpenAI-совместимый API;
- память и сессии;
- расписание и фоновые задания;
- skills и MCP;
- вызов моделей;
- выполнение разрешённых инструментов;
- делегирование подзадач и подтверждения, если соответствующая возможность включена.

Подробности — в `hermes.md`.

### 2.2. Open WebUI

Open WebUI является основным пользовательским интерфейсом.

Он отвечает за:

- вход пользователей;
- диалоги;
- историю;
- пользовательские настройки;
- передачу запросов Hermes через его OpenAI-совместимый API.

Open WebUI не получает прямых административных прав к системам квартиры.

Подробности — в `open-webui.md`.

### 2.3. Внешние системы

410 не заменяет:

- Home Assistant;
- `910 infra-manager`;
- Proxmox VE;
- маршрутизатор, DNS и VPN;
- NVR;
- мониторинг;
- сервер локальной модели;
- резервное копирование.

Hermes обращается к ним только через явно подключённые и ограниченные интерфейсы.

## 3. Каталоги и данные

### 3.1. Целевая структура

```text
/opt/ai-control/
├── compose/
│   └── docker-compose.yml
└── state/
    ├── hermes/              → /opt/data в контейнере Hermes
    └── open-webui/          → /app/backend/data в Open WebUI

/etc/ai-control/
├── hermes.env               API Hermes и будущие локальные секреты
└── open-webui.env           ключ связи и начальная учётная запись WebUI
```

Hermes хранит собственные config, sessions, memories, skills, cron, hooks и другие рабочие данные внутри своего постоянного `/opt/data`.

Не нужно создавать параллельные каталоги памяти, задач или событий только ради AI Control.

### 3.2. Резервирование

Обязательно сохраняются:

- `/opt/ai-control/state/`;
- `/etc/ai-control/hermes.env`;
- `/etc/ai-control/open-webui.env`.

Compose-файл воспроизводится Ansible и в резервную копию не требуется.

В дальнейшем секреты могут быть перенесены во внешний механизм OpenBao; после этого локальные env-файлы можно будет считать материализуемыми.

## 4. Сеть и безопасность

### 4.1. Порты

Open WebUI:

```text
0.0.0.0:4100
```

Hermes API:

```text
127.0.0.1:8642
```

Hermes Dashboard по умолчанию выключен. Его штатный порт зарезервирован как `9119`.

Open WebUI и Hermes используют `network_mode: host`, поэтому WebUI может обращаться к Hermes через loopback, а API Hermes не публикуется в домашнюю сеть.

### 4.2. Граница полномочий

Контейнер Hermes не получает Docker socket и не получает неограниченный root-доступ к PVE.

Для повторяемых инфраструктурных изменений используется отдельный ограниченный инструмент Hermes: он вызывает операторскую команду `infra-manager` на PVE, которая передаёт операцию в `910 infra-manager`. Semaphore в этом маршруте не нужен. Агент не получает ни root SSH на PVE, ни административного PVE API token.

Для доступа предусматривается отдельная техническая SSH-идентичность с краткоживущим сертификатом OpenBao, принудительной командой на PVE и проверкой полномочий по `access.yaml`. Разрешённые операции: `guests`, `status`, `test`; `deploy`, `sync`, `repair VMID` — только для разрешённых VMID и с подтверждением оператора вне агента. Самостоятельное изменение 100, 410, 910, выполнение `recover`, `repair` без VMID и произвольных команд PVE запрещено.

Агентский вызов не должен наследовать режим `--trusted-pve` существующей операторской оболочки: пароли и другие секреты не показываются. Проверки принадлежности 910, общий исполнитель, блокировки и журнал выполнения сохраняются. Этот канал пока спроектирован, но не реализован; подробности — в `decisions.md` и общем разделе о PVE-доступе.

Для Home Assistant, сети и других систем права должны добавляться одновременно с соответствующей интеграцией.

Правила поведения агента не заменяют технические ограничения ACL и учётных данных.

## 5. Развёртывание и проверка

### 5.1. Развёртывание

Штатный порядок:

1. создать VM 410;
2. применить `linux_base`;
3. установить Docker общей ролью `docker`;
4. ролью `ai_control` создать каталоги и локальные секреты;
5. сформировать Compose;
6. получить закреплённые образы Hermes и Open WebUI;
7. запустить оба контейнера;
8. дождаться `/health` Hermes;
9. дождаться `/health` Open WebUI;
10. настроить поставщика модели Hermes;
11. подключать внешние инструменты по одному.

### 5.2. Минимальная проверка

После развёртывания подтверждаются:

- контейнер `hermes` работает;
- `http://127.0.0.1:8642/health` отвечает;
- контейнер `open-webui` работает;
- `http://127.0.0.1:4100/health` отвечает;
- пользователь может войти в Open WebUI;
- Open WebUI видит модель `hermes-agent`;
- данные обоих контейнеров переживают перезапуск;
- Hermes API снаружи VM не доступен.

Полный AI-ответ возможен только после настройки хотя бы одного поставщика модели.
