## 1. Назначение и границы

### 1.1. Роль 410

`410 ai-control` является центральной рабочей средой AI квартиры.

Внутри 410 работает один основной универсальный агент. Он взаимодействует с пользователями и использует общие инструменты для работы с Home Assistant, инфраструктурой, сетью, мониторингом, Git и другими разрешёнными системами.

410 отвечает за:

- пользовательский диалог;
- понимание задачи;
- выбор AI-модели;
- выбор разрешённого инструмента;
- ведение рабочего контекста;
- постановку и выполнение задач;
- обработку значимых событий;
- запрос подтверждения опасных действий;
- проверку результата;
- уведомление пользователя.

### 1.2. Что остаётся вне 410

В 410 не переносятся только ради удобства AI:

- Home Assistant;
- `910 infra-manager`;
- OpenTofu, управляющий Ansible и Packer;
- маршрутизатор, DNS и VPN;
- NVR и видеонаблюдение;
- общие STT/TTS;
- сервер локальной AI-модели, если для него используется отдельный компьютер;
- общее файловое хранилище;
- самостоятельная система мониторинга.

Остановка 410 не должна останавливать базовую автоматику квартиры, сеть и самостоятельные сервисы.

## 2. Внутреннее устройство

### 2.1. Логические части

Целевая схема:

```text
веб-интерфейс
      │
      ▼
AI Control
├── основной агент
├── механизм выбора моделей
├── слой инструментов
├── задачи и расписание
├── события
├── память
├── подтверждения действий
└── уведомления
```

Это логические части. Они не обязаны становиться отдельными программами или systemd-службами без практической необходимости.

Минимальная реализация должна иметь одну основную службу `ai-control.service`, которая предоставляет общее ядро и внутренний API.

Основной агент подключается к ядру через адаптер. Если конкретному агенту нужен отдельный долгоживущий процесс, для него используется отдельная управляемая служба.

### 2.2. Веб-интерфейс

Обязательным пользовательским интерфейсом 410 является Open WebUI.

Разделение ответственности:

```text
Open WebUI
→ вход пользователей
→ диалог и история
→ пользовательский интерфейс

AI Control
→ внутренний API
→ основной агент
→ выбор модели
→ инструменты и права
→ задачи и память
```

Open WebUI работает отдельно от Hermes и обращается к ядру через OpenAI-совместимый API.

Точная локальная спецификация Open WebUI находится в `open-webui.md`.

### 2.3. Основной агент

В штатном состоянии используется один основной универсальный агент.

Текущий основной агент — Hermes.

Отдельные агенты для Home Assistant, сети, инфраструктуры и мониторинга не создаются. Эти области подключаются как инструменты одного агента.

Дополнительный агент допускается только при отдельной необходимости:

- независимая длительная задача;
- параллельная работа, которую основной агент не должен блокировать;
- другой программный движок с отдельным жизненным циклом.

Требования к Hermes описаны в `hermes.md`.

## 3. Каталоги, пользователь и данные

### 3.1. Системный пользователь

AI Control должен работать от отдельного системного пользователя `ai-control`.

Процессы AI Control не должны штатно запускаться от `root`.

Права `root` используются только внешним механизмом установки и настройки. Привилегированные действия на других системах выполняются через разрешённые API, 910 или краткоживущие механизмы доступа.

### 3.2. Целевая структура

```text
/opt/ai-control/
├── core/                   ядро и внутренний API AI Control
├── compose/
│   └── open-webui.yml      воспроизводимый запуск Open WebUI
├── agents/
│   └── hermes/             текущий основной агент
├── repos/
│   └── proxmox/            рабочая копия проекта
├── instructions/           подключаемые инструкции
├── tools/                  общие инструменты
└── state/
    ├── memory/
    ├── conversations/
    ├── tasks/
    ├── events/
    ├── observations/
    ├── agents/
    │   └── hermes/
    └── open-webui/         база и пользовательские данные Open WebUI

/etc/ai-control/
├── ai-control.env          несекретная конфигурация ядра
├── api.env                 внутренний ключ API
├── open-webui.env          локальные секреты Open WebUI
├── models.json             реестр моделей
└── tools.json              реестр инструментов

/run/ai-control/             временное состояние процесса
/var/cache/ai-control/       воспроизводимый кэш
```

Секреты не хранятся в Git, `instructions/` или `tools/`.

Машинные права и доверие, создаваемые общим механизмом проекта, остаются под `/etc/proxmox-guest/`.

### 3.3. Постоянные и воспроизводимые данные

Обязательному сохранению подлежит `/opt/ai-control/state/`. Также сохраняются локальные секреты `/etc/ai-control/api.env` и `/etc/ai-control/open-webui.env`, пока для них не реализовано внешнее хранилище секретов.

Рабочая копия Git, ядро, агент, инструкции и инструменты должны восстанавливаться из воспроизводимых источников.

`/run/ai-control/` и `/var/cache/ai-control/` в резервную копию не требуются.

Текущий `provision.yaml` должен быть приведён к этой модели при реализации. Расхождения перечислены в `implementation-status.md`.

## 4. Модели, инструменты и полномочия

### 4.1. Источники AI-моделей

AI Control должен поддерживать одновременно несколько источников моделей:

- локальную модель на отдельном компьютере или сервере;
- внешнюю модель через API;
- несколько поставщиков, если это потребуется.

Для каждого источника должны быть заданы:

- логическое имя;
- адрес или тип подключения;
- доступные модели;
- класс допустимых данных;
- порядок проверки доступности;
- секрет доступа, если он требуется.

Секреты моделей должны поступать из принятого механизма секретов и не храниться в репозитории.

Механизм выбора модели учитывает:

- сложность задачи;
- доступность;
- скорость;
- стоимость;
- конфиденциальность;
- возможность работы без внешнего Интернета.

### 4.2. Инструменты

Общие инструменты принадлежат AI Control, а не Hermes.

Целевые области:

```text
tools/
├── home_assistant/
├── infrastructure/
├── network/
├── monitoring/
├── git/
├── knowledge/
└── notifications/
```

Инструмент должен предоставлять понятные ограниченные операции.

Примеры:

```text
Home Assistant
→ прочитать состояние
→ получить историю
→ вызвать разрешённый сервис
→ работать с автоматизацией

инфраструктура
→ получить состояние
→ сформировать параметры
→ вызвать разрешённое задание 910
→ проверить результат

сеть
→ получить сведения об устройствах и состоянии
→ вызвать только явно разрешённое изменение
```

### 4.3. Права

Машинным источником внешних прав является `infrastructure/security/access.yaml`.

AI Control не должен:

- самостоятельно расширять свои права;
- получать постоянный root SSH к PVE;
- получать прямой PVE API token для штатных инфраструктурных изменений;
- хранить административные секреты в файлах агента;
- обходить 910 прямыми командами, если операция относится к повторяемому инфраструктурному изменению.

Для SSH между гостями используется принятый механизм OpenBao и OTP только к разрешённым целям.

## 5. Задачи, события, память и уведомления

### 5.1. Задачи

AI Control должен иметь постоянный реестр задач.

Минимальные состояния:

```text
created
queued
running
waiting_confirmation
completed
failed
cancelled
```

Для каждой задачи должны сохраняться:

- источник;
- время создания;
- краткое описание;
- текущий статус;
- агент;
- используемая модель;
- выполненные значимые действия;
- итог;
- причина ошибки, если она возникла.

Длительная задача не должна блокировать возможность пользователя открыть веб-интерфейс и начать другой диалог.

### 5.2. События и расписание

AI Control должен принимать:

- события от интегрированных систем;
- задания по расписанию;
- запросы пользователя.

Массовые однозначные события сначала проходят обычные фильтры и правила.

AI-модель вызывается только когда требуется анализ, объяснение или выбор действия.

### 5.3. Память

Память делится как минимум на:

- долговременную память;
- контекст диалогов;
- состояние выполняемых задач;
- наблюдения.

Память AI не заменяет Git, Home Assistant или другую систему-владельца фактического или требуемого состояния.

Перед использованием сохранённого факта для управляющего действия AI должен при необходимости сверить актуальное состояние с системой-владельцем.

### 5.4. Подтверждения и уведомления

Уровни действий определяются общим документом `520-ai-management.md`.

веб-интерфейс должен уметь показывать запрос подтверждения с понятным описанием:

- что будет изменено;
- какой системой;
- какое действие будет вызвано;
- какие основные последствия ожидаются.

Уведомления являются общей функцией AI Control. Дополнительные каналы могут подключаться позже без изменения логики основного агента.

## 6. Развёртывание и обновление

### 6.1. Требуемый порядок

После создания Debian 13 VM:

1. установить пакеты из `provision.yaml`;
2. применить базовое SSH/OpenBao/Git-доверие;
3. установить Docker;
4. создать пользователя и каталоги AI Control;
5. установить ядро и внутренний API AI Control;
6. создать локальные внутренние секреты;
7. запустить `ai-control.service` на `127.0.0.1:4110`;
8. развернуть Open WebUI по `open-webui.md` на порту `4100`;
9. установить Hermes по `hermes.md`;
10. настроить источники AI-моделей;
11. подключить разрешённые инструменты;
12. выполнить проверки раздела 7.

Версии внешних компонентов должны быть закреплены в машинной конфигурации.

### 6.2. Обновление

Обновление должно быть повторяемым.

Штатный порядок:

```text
изменить воспроизводимый источник
→ применить Ansible
→ обновить файлы и зависимости
→ перезапустить только необходимые службы
→ проверить веб-интерфейс/API/агент/интеграции
```

Ручное изменение программы внутри `/opt/ai-control/` не считается постоянным обновлением.

## 7. Проверка и восстановление

### 7.1. Минимальная проверка

После развёртывания необходимо подтвердить:

- `ai-control.service` работает;
- контейнер `open-webui` работает;
- Open WebUI открывается на порту `4100` из разрешённой сети;
- пользователь может пройти аутентификацию в Open WebUI;
- внутренний API AI Control слушает только `127.0.0.1:4110`;
- Open WebUI получает `hermes-agent` через `GET /v1/models`;
- основной агент доступен;
- хотя бы один разрешённый источник модели отвечает;
- Git доступен в требуемом режиме;
- связь с 910 работает;
- Home Assistant и другие включённые интеграции показывают понятный статус;
- задача создаётся, выполняется и сохраняет результат;
- запрос подтверждения может перейти в продолжение или отмену;
- состояние после перезапуска 410 восстанавливается.

### 7.2. Восстановление

При потере VM 410:

1. создать новую VM из штатного Debian-шаблона;
2. применить `guest.yaml` и `provision.yaml`;
3. восстановить воспроизводимые файлы через Ansible;
4. восстановить `/opt/ai-control/state/` из резервной копии;
5. заново выдать машинные права и секреты штатным механизмом;
6. восстановить рабочую копию Git;
7. установить Hermes;
8. запустить AI Control;
9. выполнить полную проверку.

Секреты и машинные доступы не должны восстанавливаться копированием старых случайных файлов, если проект умеет выдать их заново.
