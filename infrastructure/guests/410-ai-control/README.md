# 410 ai-control

`410 ai-control` — центральная VM рабочей среды AI-агентов проекта.

Она предназначена для анализа состояния инфраструктуры, работы с проектом в Git и обращения к разрешённым механизмам управления. AI Control не является отдельным источником требуемого состояния и не заменяет специализированные средства развёртывания и настройки.

## Источники требований

Требования к 410 разделены по назначению:

| Источник | Что определяет |
|---|---|
| `guest.yaml` | параметры VM на уровне Proxmox |
| `provision.yaml` | требуемое содержимое ОС, компоненты, постоянные данные и границы |
| `../../security/access.yaml` | разрешённые внешние доступы 410 |
| `decisions.md` | устойчивые решения по конкретному гостю |
| этот README | назначение, устройство, эксплуатацию и связь с остальной инфраструктурой |

Общая архитектура AI-контура находится в `docs/500-ai/`.

## Назначение

410 обеспечивает:

- запуск одного или нескольких AI-агентов;
- рабочую копию репозитория проекта;
- подключаемые инструкции и вспомогательные программы;
- запуск разрешённых инфраструктурных операций через Semaphore 910;
- административный SSH только к разрешённым Linux-гостям;
- обращение к специализированному инфраструктурному исполнителю 910;
- локальное рабочее состояние AI.

Основным агентом на текущем этапе является Hermes, но архитектура не должна зависеть от него.

## Объект Proxmox

Требуемые параметры VM:

```text
VMID:          410
name:          ai-control
тип:           VM
профиль:       debian-vm
CPU:           2
RAM:           4096 MB
диск:          24 GB
onboot:        наследуется из общего профиля
protection:    наследуется из общих настроек
managed pool:  нет
```

VM создаётся из общего Debian-шаблона проекта.

`pve_management: false` задан явно. Это принципиально: AI Control не должен попадать в собственную область изменения `managed` и управлять жизненным циклом VM, внутри которой сам работает.

## Первоначальная подготовка

Пакеты и содержимое операционной системы 410 описываются в `provision.yaml` и применяются общим Ansible playbook.

Git входит в `system.required_packages` вместе с другими базовыми пакетами.

Доступ к закрытому репозиторию и отдельные исходящие полномочия не являются частью установки пакетов. Они настраиваются отдельным механизмом безопасности после базового запуска VM.

## Состав ОС

Точный минимальный состав фиксируется в `provision.yaml`.

Базово требуются:

- Debian 13 amd64;
- CA certificates;
- curl;
- Git;
- jq;
- OpenSSH client;
- Python 3;
- Python virtual environments.

Специфические зависимости конкретного AI-агента должны добавляться вместе с его реальной установкой, а не заранее.

## Структура внутри VM

Целевая структура:

```text
/opt/ai-control/
├── agents/          AI-агенты
├── repos/           рабочие копии репозиториев
│   └── proxmox/
├── instructions/    подключаемые инструкции
├── tools/           вспомогательные программы
└── state/           постоянное локальное состояние

/etc/proxmox-guest/
├── ssh/             машинная SSH-идентичность и сертификат
└── git/             управляемый read-only доступ к проектному Git
```

Конкретный агент размещается отдельно:

```text
/opt/ai-control/agents/<agent>/
```

Общие средства AI Control не должны принадлежать каталогу Hermes или любого другого конкретного агента.

## Git

Рабочая копия проекта:

```text
/opt/ai-control/repos/proxmox
```

Репозиторий:

```text
git@github.com:zsergeyru/proxmox.git
```

Базовый доступ — только чтение.

Право чтения задаётся в общем `access.yaml`. Право записи в GitHub является отдельным полномочием и не появляется автоматически вместе с чтением.

## SSH

`access.yaml` уже фиксирует два независимых требования 410:

- собственная исходящая SSH-идентичность;
- административный SSH только к целям из `pool:managed`.

Централизованный механизм использует отдельный локальный Ed25519 key 410 и двухчасовой сертификат OpenBao с principal `guest-410`. Private key не покидает 410 и не является ключом Ansible или Git.

Цели входа вычисляются только из `access.yaml`. Для текущего правила `pool:managed` 410 не получает доступ к PVE и не получает доступ к 910, потому что 910 не входит в `managed`.

Прямой SSH используется только для разрешённых диагностических, проверочных и административных действий. Постоянная повторяемая настройка должна выполняться через штатный инфраструктурный контур.

## Proxmox

410 не получает прямой PVE API token и root SSH к физическому PVE.

Повторяемые инфраструктурные операции выполняются через разрешённые действия Semaphore на 910. Текущий контракт допускает логические операции:

- построить OpenTofu plan;
- развернуть или обновить объект в разрешённой области `managed`;
- проверить управляемый объект.

Это не даёт 410 права:

- изменять собственную VM 410 или 910;
- расширять ACL;
- администрировать пользователей и токены PVE;
- менять сеть или определения хранилищ PVE;
- выполнять bootstrap, произвольный shell или обслуживание физического PVE.

Точный машинный источник этих ограничений — `infrastructure/security/access.yaml`.

## Связь с 910 infra-manager

410 и 910 имеют разные роли:

```text
410 ai-control
→ анализ
→ принятие решения
→ взаимодействие с человеком
→ выбор нужного механизма

910 infra-manager
→ Semaphore
→ OpenTofu
→ Ansible
→ Packer
→ повторяемое инфраструктурное выполнение
```

Поэтому OpenTofu, управляющий Ansible и Packer не требуется устанавливать непосредственно в 410.

Для штатных повторяемых изменений AI должен использовать специализированный механизм проекта, а не создавать второй аналогичный исполнитель внутри своей VM.

Прямой SSH к разрешённым Linux-гостям остаётся отдельным механизмом. Доступ к самому PVE выполняется только через 910 и разрешённые инфраструктурные операции.

## Постоянные и воспроизводимые данные

Обязательному резервному копированию подлежат как минимум:

```text
/opt/ai-control/state/
/etc/proxmox-guest/ssh/
```

Рабочая копия Git и воспроизводимые компоненты AI Control должны восстанавливаться из внешнего источника:

```text
/opt/ai-control/repos/proxmox/
/opt/ai-control/agents/
/opt/ai-control/instructions/
/opt/ai-control/tools/
```

Кэш, результаты команд, временные файлы и полученные сведения о текущем состоянии инфраструктуры не являются требуемым состоянием проекта.

## Что не размещается в 410

410 не используется для:

- OpenTofu/Ansible/Packer как основного инфраструктурного исполнителя;
- Home Assistant и домашней автоматизации;
- STT/TTS и других общих голосовых сервисов;
- мониторинга и видеонаблюдения;
- общего файлового хранилища;
- прикладных Docker-сервисов, не относящихся к рабочей среде AI.

Общие голосовые AI-сервисы должны оставаться независимыми от перезапуска AI Control.

## Развёртывание

Целевая последовательность:

```text
guest.yaml
→ создать/обновить VM 410
→ административный SSH
→ повторяемая настройка из provision.yaml через Ansible
→ установить AI Control
→ установить основной AI-агент
→ материализовать разрешённые доступы из access.yaml
→ проверить Git, разрешённый SSH и связь с Semaphore 910
```

Жизненный цикл самой VM выполняется внешним управляющим контуром. AI внутри 410 не должен самостоятельно пересоздавать или удалять собственную VM.

## Нумерация

`410-ai-control` — основной AI Control в диапазоне `400–490`.

Номера `411–419` резервируются для дополнительных или тестовых экземпляров того же сервиса, если они понадобятся.
