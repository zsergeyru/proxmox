# 990 bootstrap-runner

`990 bootstrap-runner` — временный технический LXC для первоначального
создания и полного аварийного пересоздания управляющего гостя с ролью
`infra-manager`. Номер гостя определяется по `guest.yaml` основного проекта,
а не жёстко задан в закрытой программе.

Он не является обычным гостем проекта и поэтому не имеет `guest.yaml` в каталоге
`infrastructure/guests/`: 990 создаётся напрямую минимальным публичным сценарием
на PVE и удаляется после успеха **и после контролируемой ошибки**.

## Обязательное правило жизненного цикла

- **990 всегда одноразовый.** При повторном запуске используется новый чистый
  контейнер. После успеха или контролируемого отказа его временный токен
  отзывается, а сам контейнер удаляется после проверки принадлежности.
  Технические журналы хранятся на PVE; сохранять 990 ради диагностики не нужно.
- **Управляющий гость создаётся по единому алгоритму.** При новой установке
  или явном полном восстановлении создаётся новый rootfs. При штатном
  обновлении действующего гостя 990 не используется.
- **Постоянное состояние принадлежит PVE:** `pve-only/`, `access/`,
  `state/`. Удаление 990 и пересоздание rootfs не удаляет эти данные.
  При наличии данных OpenBao, Semaphore или OpenTofu автоматическое
  разрушительное повторение запрещено до явного восстановления и проверки.
- **Каждый новый rootfs получает новый PVE API-токен управляющего гостя.**
  Старый `root@pam!infra-manager` отзывается, а секрет нового токена
  передаётся в новый контейнер. Существующий токен нельзя переиспользовать,
  если его секрет утрачен.
- **Частичное завершение не требует повторного развёртывания.** Если
  `ready` уже записан и гость готов, повторная проверка только завершает
  удаление оставшегося 990 и временных доступов.
- **Защитные операции простые и общие.** `authorized_keys` на PVE
  заменяется атомарно, защита `protection` у пережившего неудачное удаление
  объекта восстанавливается, шаблон освобождается только через `pvesm free`,
  без прямого удаления файла.

Если автоматическая очистка 990 не удалась, необходимо явно сообщить об
оставшихся объектах и полномочиях. Нельзя удалять чужой контейнер или
объявлять очистку успешной без проверки результата.

Общий обязательный контракт:
[первоначальная подготовка PVE](../../docs/200-pve/210-host-bootstrap.md).

## Постоянство

Все данные 990 считаются временными.

Используются отдельные пути:

~~~text
/etc/bootstrap-runner/       временная конфигурация и доступы
/var/lib/bootstrap-runner/   временные рабочие данные текущего запуска
~~~

Эти пути не пересекаются с постоянными данными `910 infra-manager`. OpenTofu state создаётся только на время шага `create` и удаляется сразу после него; повторный bootstrap никогда не продолжает старый state.

## Среда выполнения

Каталог `runtime/` содержит минимальный образ временного контура 990.

В образ входят только средства, необходимые для создания и базовой настройки 910:

- OpenTofu;
- Ansible;
- Python;
- Git;
- SSH-клиент;
- служебные программы.

Semaphore и Packer в 990 не устанавливаются.

Образ запускается временно через Docker внутри LXC 990. Постоянная служба
`bootstrap-runner` не создаётся.

## Устройство программного кода

`scripts/bootstrap-runner/bootstrap-host.py` отвечает за выбор режима и порядок
операций, не содержит собственного перечня всех файлов или отдельного
алгоритма поиска роли.

Общие операции распределены между небольшими модулями:

- `bootstrap_runner/role.py` — единый поиск гостя по роли; может запускаться
  непосредственно через Python внутри временного контейнера 990;
- `bootstrap_runner/paths.py` — каталоги PVE и внутренние пути контейнеров;
- `bootstrap_runner/commands.py` — вызов команд PVE, сохранение полного
  журнала и краткое отображение этапов;
- `bootstrap_runner/access.py` — доступы и проверка временного 990;
- `bootstrap_runner/persistence.py` — постоянное состояние и восстановление;
- `bootstrap_runner/infra.py` — создание и настройка управляющего гостя;
- `bootstrap_runner/cleanup.py` — отзыв временных полномочий и очистка.

При переносе кода наружные точки запуска и порядок развёртывания не меняются.

## Доступ к PVE

Временный токен `root@pam!bootstrap-runner` с полными полномочиями PVE
создаёт `BootstrapAccessMixin.prepare_runner_pve_access()` в
`scripts/bootstrap-runner/bootstrap_runner/access.py`. Он передаётся 990
через защищённый временный файл, а не через параметры командной строки.
Токен `root@pam!infra-manager` для управляющего гостя готовится отдельно
в `BootstrapInfraMixin.prepare_infra_pve_access()`.

После успешной установки и при контролируемом отказе временный токен
990 должен быть отозван, а сам 990 — удалён после проверки принадлежности.
Это относится и к сбою проверки готовности 990. Если очистка невозможна
или процесс аварийно прерван, наличие токена и контейнера проверяют
отдельно; оператору сообщают, что именно осталось. Постоянные данные
управляющего гостя не удаляются.

Первоначальный SSH-ключ для связи с управляющим гостем используется
только до настройки и подтверждения сертификатного SSH. Постоянный
ключ доступа к PVE хранится отдельно в области, доступной управляющему
гостю только на чтение.

## Внутренние режимы

`bootstrap-host.py` вызывается публичным загрузчиком на PVE после подготовки
990. Параметры ниже относятся к **закрытой точке входа**, а не автоматически
к параметрам публичного установщика:

| Режим | Назначение | Изменяет состояние |
| --- | --- | --- |
| Без параметров (`apply`) | Новая установка или выбор восстановления при прежних данных | Да |
| `--recover` | Полное пересоздание после строгой проверки сохранённых данных | Да, удаляет прежнюю rootfs |
| `--check` | Проверка готовности и завершение временного контура | Да, удаляет 990 и его токен |
| `--remove` | Удаление управляющего гостя и его хостовых средств | Да, сохраняет постоянные данные |
| `--purge` | То же и удаление каталога первоначального загрузчика на PVE | Да, постоянные данные сохраняет |

Ни `--remove`, ни `--purge` не являются очисткой всех постоянных
данных. Для действующего управляющего гостя обычное обновление и ремонт
выполняются средствами `infra-manager`, без пересоздания через 990.

## Состояния первоначального контура

На PVE в `/mnt/bindmounts/infra-manager/pve-only/bootstrap-installation.json`
сохраняется защищённый маркер с ролью, номером управляющего гостя и состоянием.
При новой установке сначала создаётся отдельный временный каталог с маркером,
после чего он целиком переименовывается в постоянный каталог на том же разделе.
Так между появлением постоянного каталога и записью маркера нет разрыва:

- `installing` — первая установка началась, но её готовность ещё не подтверждена;
- `ready` — управляющий контейнер прошёл проверку готовности.

Внутренний загрузчик различает четыре ситуации:

1. **Новая установка** — нет контейнера, нет постоянного каталога и маркера.
2. **Прерванная установка** — присутствует собственный маркер `installing`.
3. **Готовый контейнер** — объект существует, нового развёртывания не требуется.
4. **Восстановление** — контейнер отсутствует, но остались постоянные данные
   либо маркер `ready`.

Повтор прерванной установки допускается только при собственном маркере `installing`
и при отсутствии файлов в постоянном каталоге `state/` и ключа разблокировки
OpenBao. Если первичная подготовка оборвалась до создания `state/`,
каталог и файлы начального доступа создаются при повторном запуске.
Если постоянные данные уже появились, загрузчик останавливается: нельзя
пересоздавать контейнер вслепую. При безопасном повторе старый управляемый
rootfs удаляется лишь после успешной подготовки временной рабочей среды.

После успешной проверки создаётся маркер `ready`. При контролируемой ошибке
временный токен PVE отзывается, а временный 990 удаляется; журнал остаётся на PVE.
Сохранённые данные без маркера рассматриваются как прежняя установка и никогда
не переинициализируются автоматически. Маркер не заменяет проверку целостности
постоянного состояния. Полное восстановление должно быть разрешено только после
строгой проверки данных.

При запуске на PVE действует исключительная блокировка
`/run/proxmox-bootstrap-runner.lock`: второй одновременно запущенный
экземпляр завершается без изменений. Для разрушительных действий требуется
точное совпадение имени и меток владения VM/LXC, а не только номер объекта
или совпадение подстроки в описании.

## Линейный сценарий

Публичный установщик запускает 990 независимо от наличия управляющего
гостя. Уже внутри временного контура роль `infra-manager` определяется
по `guest.yaml` основного проекта. При обычном запуске существующий
объект не пересоздаётся; полное восстановление требует отдельного
внутреннего режима и строгих предварительных проверок. Наличие работающего
гостя не мешает запуску 990, но не является разрешением на его изменение.

Для нового или полностью восстанавливаемого управляющего гостя задан
следующий порядок (восстановление сперва проверяет сохранённые данные):

~~~text
проверить состояние, принадлежность и постоянные каталоги
→ подготовить 990, SSH-доступ и временный токен PVE
→ при восстановлении удалить старый rootfs после проверки данных
→ create (OpenTofu) и подключить постоянные каталоги
→ configure-base (Ansible)
→ передать временные PVE/Git данные
→ configure-control-plane либо configure-recovery-control-plane
→ инициализировать или восстановить OpenBao
→ передать публичные SSH CA в 990
→ configure-ssh-trust, подтвердить сертификатный SSH
→ удалить первоначальное SSH-разрешение
→ configure (полный Ansible)
→ проверить infra-manager-status --full
→ записать маркер ready
→ удалить временный токен, секреты и LXC 990
→ проверить окончательную готовность
~~~

Шаги `create`, `configure-base` и `configure` являются только внутренними шагами реализации 990. Они не доступны в обычном `deploy-guest`, не имеют варианта `existing` и не используются для обслуживания рабочего 910.

## Bootstrap SSH

990 создаёт одну одноразовую пару `infra_manager_ed25519`. В начале каждого нового bootstrap/recovery-сеанса старая локальная пара, если она осталась, удаляется и генерируется новая. Открытая часть передаётся 910 только при создании LXC, закрытая используется для первоначального Ansible-входа.

990 не добавляет отдельный ключ в `authorized_keys` уже созданного 910. После появления OpenBao должен быть подтверждён вход по краткоживущему сертификату, после чего bootstrap authorization и локальная пара удаляются.

Обычный `deploy-guest` не имеет bootstrap-флагов 910. Внутренние технические шаги первоначального контура вызываются только из закрытого bootstrap-runner и не являются операторским интерфейсом.

## Отказы и проверка безопасности

При ошибке подготовки 990 существующий управляющий контейнер не
удаляется. При незавершённой установке автоматическое пересоздание
разрешено только с правильным маркером `installing`, когда постоянные
данные и ключ разблокировки OpenBao ещё не появились. Иначе выполнение
останавливается до изменения rootfs.

При отказе после создания гостя результат может быть частичным.
Повторный запуск допустим только после проверки состояния и сообщения
об ошибке. При восстановлении нельзя продолжать поверх неполных
данных OpenBao, Semaphore или OpenTofu.

После контролируемого отказа выполняются отзыв токена и удаление 990.
Если отозвать полномочия или удалить свой 990 не удалось, необходимо
показать отдельную ошибку, не скрывая первоначальную причину отказа.
Нельзя сохранять действующий постоянный root SSH-ключ PVE внутри
диагностического контейнера. Повторный запуск начинается с чистого 990.
Если гость уже готов и маркер `ready` записан, повторная операция должна
ограничиться проверкой и окончательной очисткой без пересоздания гостя.
Сам `--check` изменяет состояние, поэтому не является просмотром.

При неудачном удалении управляющего объекта его защита восстанавливается,
если объект остался. Для очистки скачанного шаблона используется только
штатная операция PVE; напрямую удалять его файл запрещено.

Проверки без работающего PVE находятся в
`scripts/tests/test-bootstrap-host.py`; архитектурные ограничения —
в `scripts/tests/test-bootstrap-architecture.sh`. Они проверяют
контракты и моделируют отказы, но не заменяют испытание восстановления
на реальном PVE с резервной копией постоянного состояния.

Этот README описывает временную среду и её защитные границы. Полную
схему повседневного управления гостями определяет профильная документация.
