# Сеть Proxmox

Здесь фиксируются решения, относящиеся именно к сетевой части Proxmox и его гостей.

## Базовые принципы

- один физический uplink сервера;
- VLAN-aware bridge на Proxmox;
- Proxmox не должен становиться неявным маршрутизатором между сегментами;
- пользовательская маршрутизация, VPN, PBR и DNS относятся к `101-network-gateway`;
- межсегментная маршрутизация и firewall выполняются явно через сетевой шлюз;
- удалённые доверенные устройства должны иметь полноценный доступ к домашней сетевой архитектуре через отдельный remote-access VPN.

## Целевая адресация новой квартиры

Для новой квартиры принимается простое правило:

> **второй октет IPv4-адреса совпадает с номером VLAN, а каждый основной VLAN получает собственную сеть `/16`.**

Базовая схема:

| Сегмент | VLAN | Подсеть | Типичный шлюз |
|---|---:|---|---|
| MAIN | native / untagged | `10.0.0.0/16` | `10.0.0.1` |
| SERVERS | 10 | `10.10.0.0/16` | `10.10.0.1` |
| IOT | 20 | `10.20.0.0/16` | `10.20.0.1` |
| CAMERAS | 30 | `10.30.0.0/16` | `10.30.0.1` |
| REMOTE-VPN | tunnel, номер 60 зарезервирован | `10.60.0.0/16` | `10.60.0.1` |

При появлении новых VLAN сохраняется то же правило, например:

```text
VLAN 40 → 10.40.0.0/16
VLAN 50 → 10.50.0.0/16
```

`MAIN` — специальный случай: `10.0.0.0/16` используется как native/untagged сеть. Это **не означает использование VLAN 0**.

`REMOTE-VPN` также специальный случай: клиенты находятся на tunnel-интерфейсе WireGuard/AmneziaWG, поэтому физический VLAN 60 для удалённого доступа не требуется. Номер 60 резервируется для понятной адресации и возможного будущего расширения.

Такое распределение позволяет использовать `/16` без пересечения сетей: `10.10.0.0/16`, `10.20.0.0/16`, `10.30.0.0/16` и `10.60.0.0/16` являются разными маршрутными сетями.

Внутри каждого VLAN третий октет можно использовать для логической группировки устройств без создания дополнительного VLAN. Например в IOT:

```text
10.20.1.x → освещение
10.20.2.x → ESP-контроллеры
10.20.3.x → бытовая техника
```

Это только логическое распределение адресов; все такие устройства по-прежнему находятся в одном VLAN 20 и одной сети `10.20.0.0/16`.

## Удалённый доступ через VPN

Целевой remote-access VPN завершается на `101-network-gateway`, а не на отдельном приложении внутри произвольного гостя. Базовая технология — WireGuard; AmneziaWG можно использовать как совместимый вариант там, где обычный WireGuard хуже проходит через ограничения сети.

Удалённые доверенные клиенты — ноутбуки, компьютеры и телефоны — получают адреса из:

```text
REMOTE-VPN → 10.60.0.0/16
gateway    → 10.60.0.1
```

После подключения клиент должен работать как полноценный участник домашней сети на уровне L3:

- использовать домашний DNS через `101-network-gateway`;
- обращаться к MAIN `10.0.0.0/16`;
- обращаться к SERVERS `10.10.0.0/16`;
- обращаться к IOT `10.20.0.0/16`;
- обращаться к CAMERAS `10.30.0.0/16`;
- использовать те же firewall/PBR/VPN-политики, которые применяются сетевым шлюзом к локальным клиентам;
- при full-tunnel режиме отправлять интернет-трафик через домашний `network-gateway`, включая выбранные исходящие VPN-маршруты;
- при split-tunnel режиме отправлять через домашний VPN только домашние сети и нужные маршруты.

Для доверенных личных устройств целевой профиль допускает доступ ко всем домашним сегментам. В будущем при необходимости можно добавить отдельные ограниченные VPN-профили, например только для Home Assistant или только для администрирования.

Домашний DNS должен выдаваться VPN-клиентам явно. Предпочтительно использовать адрес самого tunnel-шлюза `10.60.0.1`, на котором DNS-запросы передаются в общий AdGuard Home / SmartDNS. Это важно в том числе для DNS-зависимого PBR: удалённый клиент должен пользоваться тем же DNS-контуром, что и локальные устройства.

Целевой путь трафика:

```text
remote phone/laptop
        │
        │ WireGuard / AmneziaWG
        ▼
10.60.0.1 — 101-network-gateway
        │
        ├── DNS → AdGuard Home / SmartDNS
        ├── MAIN     10.0.0.0/16
        ├── SERVERS  10.10.0.0/16
        ├── IOT      10.20.0.0/16
        ├── CAMERAS  10.30.0.0/16
        └── Internet → обычный WAN или выбранный исходящий VPN/PBR
```

Пока внешний интернет-шлюз остаётся на отдельном физическом роутере, он должен пробрасывать входящий UDP-порт remote-access VPN на `101-network-gateway`. После переноса роли основного маршрутизатора в `101-network-gateway` VPN-сервер будет принимать подключения непосредственно на WAN-интерфейсе этой VM.

Для аварийного доступа можно дополнительно оставить второй, ограниченный VPN-сервер на физическом edge-router. Он не заменяет основной remote-access VPN и нужен только как резервный административный канал, если Proxmox или `101-network-gateway` недоступны.

Приватные VPN-ключи, peer-конфигурации с секретами и preshared keys в Git не хранятся.

## Текущая квартира и миграция

Действующую сеть `192.168.0.0/16` не требуется немедленно перенумеровывать. Она может продолжать работать в текущем виде до плановой миграции.

Если отдельные VLAN понадобятся ещё до полного перехода на новую адресацию, их следует размещать в непересекающихся сетях `10.<VLAN>.0.0/16`, например:

```text
IOT / VLAN 20     → 10.20.0.0/16
CAMERAS / VLAN 30 → 10.30.0.0/16
```

Remote-access VPN можно ввести уже на текущем этапе с сетью `10.60.0.0/16`: она не пересекается с действующей `192.168.0.0/16` и затем без перенумерации переносится в новую квартиру.

## Серверный сегмент

Целевой серверный VLAN новой квартиры — VLAN 10, сеть `10.10.0.0/16`.

Для management IP VM/LXC внутри него сохраняется читаемое соответствие VMID → IP; правило описано в [`vmid-plan.md`](vmid-plan.md).

Детальная конфигурация сетевой VM хранится в `guests/101-network-gateway/` и её `rootfs/`.

Общий проект физической сети, сетевого оборудования, камер и квартиры остаётся в репозитории `zsergeyru/appart-rennovation`. Здесь хранятся только серверные и эксплуатационные сведения, непосредственно относящиеся к Proxmox.

Граница между репозиториями описана в [`apartment-infrastructure.md`](apartment-infrastructure.md).
