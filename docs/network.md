# Сеть Proxmox

Здесь фиксируются решения, относящиеся именно к сетевой части Proxmox и его гостей.

## Базовые принципы

- один физический uplink сервера;
- VLAN-aware bridge на Proxmox;
- Proxmox не должен становиться неявным маршрутизатором между сегментами;
- пользовательская маршрутизация, VPN, PBR и DNS относятся к `101-network-gateway`;
- межсегментная маршрутизация и firewall выполняются явно через сетевой шлюз;
- удалённые доверенные устройства должны иметь полноценный доступ к домашней сетевой архитектуре через отдельный remote-access VPN;
- отдельный VLAN только для серверов не требуется: Proxmox, VM/LXC и доверенные пользовательские устройства находятся в MAIN.

## Целевая адресация новой квартиры

Для новой квартиры принимается правило:

> **MAIN использует `10.0.0.0/16`, а для изолированных VLAN второй октет IPv4-адреса совпадает с номером VLAN. Каждый основной сегмент использует собственную сеть `/16`.**

Базовая схема:

| Сегмент | VLAN | Подсеть | Типичный шлюз |
|---|---:|---|---|
| MAIN / TRUSTED | native / untagged | `10.0.0.0/16` | `10.0.0.1` |
| IOT | 20 | `10.20.0.0/16` | `10.20.0.1` |
| CAMERAS | 30 | `10.30.0.0/16` | `10.30.0.1` |
| REMOTE-VPN | tunnel, номер 60 зарезервирован | `10.60.0.0/16` | `10.60.0.1` |

При появлении новых изолированных VLAN сохраняется правило, например:

```text
VLAN 40 → 10.40.0.0/16
VLAN 50 → 10.50.0.0/16
```

`MAIN` — специальный случай: `10.0.0.0/16` используется как native/untagged сеть. Это не означает использование VLAN 0.

Серверы находятся непосредственно в MAIN. Отдельный `VLAN 10 / SERVERS` не используется, пока не появится практическая необходимость дополнительно изолировать серверы от доверенных клиентов.

`REMOTE-VPN` также специальный случай: клиенты находятся на tunnel-интерфейсе WireGuard/AmneziaWG, поэтому физический VLAN 60 для удалённого доступа не требуется. Номер 60 резервируется для понятной адресации и возможного будущего расширения.

Такое распределение позволяет использовать `/16` без пересечения сетей: `10.0.0.0/16`, `10.20.0.0/16`, `10.30.0.0/16` и `10.60.0.0/16` являются разными маршрутными сетями.

Внутри каждого сегмента третий октет можно использовать для логической группировки устройств без создания дополнительного VLAN. Например в IOT:

```text
10.20.1.x → освещение
10.20.2.x → ESP-контроллеры
10.20.3.x → бытовая техника
```

## Серверные адреса в MAIN

Для Proxmox и обычных VM/LXC используются статические адреса в `10.0.0.0/16`.

Для VM/LXC сохраняется читаемое соответствие VMID → IP, описанное в [`vmid-plan.md`](vmid-plan.md):

```text
VMID XYZ → 10.0.X.YZ/16
```

Примеры:

```text
PVE       → 10.0.0.10/16
201       → 10.0.2.1/16
211       → 10.0.2.11/16
301       → 10.0.3.1/16
321       → 10.0.3.21/16
401       → 10.0.4.1/16
501       → 10.0.5.1/16
```

## Переход с текущей `192.168.0.0/16` на `10.0.0.0/16`

Переезд на новую адресацию выполняется заранее и без массовой смены IP в день физического переезда.

### 1. Две сети временно работают в одном MAIN/L2

В текущей квартире сохраняется существующая сеть:

```text
192.168.0.0/16
текущий gateway: 192.168.1.1
```

На Keenetic Hopper на том же домашнем LAN-интерфейсе добавляется дополнительный адрес:

```text
10.0.0.1/16
```

То есть на переходный период Keenetic обслуживает одновременно:

```text
192.168.1.1/16  → старый адрес шлюза
10.0.0.1/16     → постоянный будущий адрес шлюза MAIN
```

Для сети `10.0.0.0/16` на Keenetic должен быть настроен выход в интернет/NAT и проверена маршрутизация между `192.168.0.0/16` и `10.0.0.0/16`.

Конкретные CLI-команды Keenetic не считаются частью постоянной архитектуры и перед применением проверяются по фактической версии KeeneticOS и текущей конфигурации Hopper.

### 2. Новые серверы сразу получают постоянные `10.0.x.x`

Новые VM/LXC создаются сразу с целевым адресом `10.0.X.YZ/16` и default gateway:

```text
gateway → 10.0.0.1
```

Для совместимости со старой сетью сервер при необходимости может временно иметь второй адрес `192.168.X.YZ/16` на том же интерфейсе.

Пример:

```text
321-app-services

10.0.3.21/16      → постоянный целевой адрес
192.168.3.21/16   → временный legacy-адрес

default gateway   → 10.0.0.1
```

Default gateway должен быть один. Не назначать одновременно обычные default route через `192.168.1.1` и `10.0.0.1`.

### 3. Уже работающие серверы мигрируют постепенно

Для существующего сервера сначала добавляется будущий `10.0.x.x` как второй адрес. После проверки доступности, DNS и маршрутизации его default gateway переводится на `10.0.0.1`. Старый `192.168.x.x` некоторое время остаётся только как совместимый адрес.

Таким образом будущий IP и gateway проверяются ещё в старой квартире.

### 4. Переезд в новую квартиру

В новой квартире роль `10.0.0.1` получает целевой основной сетевой шлюз. Серверы уже имеют постоянные адреса и gateway:

```text
10.0.x.x/16
gateway 10.0.0.1
```

Поэтому на каждом сервере в день переезда менять IP или default gateway не требуется. После проверки новой сети временные `192.168.x.x` удаляются.

Ключевой принцип миграции:

```text
меняется физическое устройство, владеющее 10.0.0.1,
но адреса и gateway серверов остаются неизменными.
```

### 5. DNS вместо жёстко записанных IP

Сервисы и пользователи по возможности должны обращаться к инфраструктуре по локальным DNS-именам. Это уменьшает зависимость приложений и закладок от конкретных IP во время миграции.

## Удалённый доступ через VPN

Целевой remote-access VPN завершается на `101-network-gateway`, а не на отдельном приложении внутри произвольного гостя. Базовые варианты — WireGuard/AmneziaWG.

Удалённые доверенные клиенты — ноутбуки, компьютеры и телефоны — получают адреса из:

```text
REMOTE-VPN → 10.60.0.0/16
gateway    → 10.60.0.1
```

После подключения клиент должен работать как полноценный участник домашней сети на уровне L3:

- использовать домашний DNS через `101-network-gateway`;
- обращаться к MAIN `10.0.0.0/16`, включая Proxmox и серверы;
- обращаться к IOT `10.20.0.0/16`;
- обращаться к CAMERAS `10.30.0.0/16`;
- использовать firewall/PBR/VPN-политики сетевого шлюза;
- поддерживать full-tunnel и split-tunnel профили.

Для доверенных личных устройств целевой профиль допускает доступ ко всем домашним сегментам. В будущем при необходимости можно добавить отдельные ограниченные VPN-профили.

Домашний DNS должен выдаваться VPN-клиентам явно. Предпочтительно использовать адрес tunnel-шлюза `10.60.0.1`, который передаёт DNS-запросы в общий AdGuard Home / SmartDNS.

Целевой путь трафика:

```text
remote phone/laptop
        │
        │ WireGuard / AmneziaWG
        ▼
10.60.0.1 — 101-network-gateway
        │
        ├── DNS → AdGuard Home / SmartDNS
        ├── MAIN     10.0.0.0/16
        ├── IOT      10.20.0.0/16
        ├── CAMERAS  10.30.0.0/16
        └── Internet → обычный WAN или выбранный исходящий VPN/PBR
```

Пока внешний интернет-шлюз остаётся на отдельном физическом роутере, он пробрасывает входящий порт remote-access VPN на `101-network-gateway`. После переноса WAN-маршрутизации в `network-gateway` VPN-сервер принимает подключения непосредственно на WAN-интерфейсе этой VM.

Для аварийного доступа можно дополнительно оставить второй ограниченный VPN-сервер на физическом edge-router. Он не заменяет основной remote-access VPN и нужен как резервный административный канал, если Proxmox или `101-network-gateway` недоступны.

Приватные VPN-ключи, peer-конфигурации с секретами и preshared keys в Git не хранятся.

## VLAN до переезда

Если изолированные VLAN понадобятся ещё в текущей квартире, они сразу используют будущие непересекающиеся сети:

```text
IOT / VLAN 20     → 10.20.0.0/16
CAMERAS / VLAN 30 → 10.30.0.0/16
```

Remote-access VPN также можно вводить сразу с `10.60.0.0/16`.

Детальная конфигурация сетевой VM хранится в `guests/101-network-gateway/` и её `rootfs/`.

Общий проект физической сети, сетевого оборудования, камер и квартиры остаётся в репозитории `zsergeyru/appart-rennovation`. Здесь хранятся только серверные и эксплуатационные сведения, непосредственно относящиеся к Proxmox.

Граница между репозиториями описана в [`apartment-infrastructure.md`](apartment-infrastructure.md).
