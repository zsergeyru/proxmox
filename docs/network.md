# Сеть Proxmox

Здесь фиксируются решения, относящиеся именно к сетевой части Proxmox и его гостей.

## Базовые принципы

- у Proxmox-сервера одна физическая Ethernet-карта `nic0`;
- второй физический сетевой адаптер в принятой архитектуре не требуется;
- до переезда сеть работает без VLAN;
- после переезда тот же единственный Ethernet-порт может использоваться как VLAN trunk через VLAN-aware `vmbr0`;
- Proxmox не должен становиться неявным маршрутизатором между сегментами;
- DNS, исходящие VPN, remote-access VPN, PBR и связанные сетевые сервисы относятся к `101-network-gateway`;
- точное разделение L3/firewall-функций между будущим физическим роутером и `101-network-gateway` определяется отдельно перед вторым этапом;
- отдельный VLAN только для серверов в целевой новой квартире пока не требуется: доверенные серверы относятся к MAIN.

## Два этапа сети

Сеть строится поэтапно. Первый этап нужен для запуска всей серверной инфраструктуры ещё до переезда и не требует VLAN. Второй этап вводит VLAN уже в новой квартире без добавления второй сетевой карты в Proxmox.

### Этап 1 — текущая квартира, без VLAN

Текущий Keenetic разделяет три сетевых направления:

```text
                    Internet / WAN
                          │
                          ▼
                       Keenetic
                      /        \
                     /          \
          общая домашняя      серверная сеть
                сеть                │
                                    │ отдельный Ethernet
                                    ▼
                                 Proxmox
                                  nic0
                                    │
                                  vmbr0
                                    │
                              VM / LXC, включая 101
```

Для Proxmox используется один физический Ethernet-порт `nic0`, подключённый к серверной сети Keenetic. VLAN на этом этапе не используются.

Фактически наблюдаемое состояние PVE сейчас:

```text
PVE:     192.168.1.11/16
gateway: 192.168.1.1
bridge:  vmbr0 → nic0
```

В таблице маршрутов PVE серверная сеть представлена как `192.168.0.0/16`. Адресация общей домашней сети в этом документе отдельно не фиксируется, если она не нужна для настройки Proxmox.

На первом этапе уже разворачивается `101-network-gateway`. Не нужно ждать VLAN, чтобы запустить:

- внутренний DNS и `home.arpa`;
- AdGuard Home / SmartDNS;
- DoH/DoT и выбор upstream DNS;
- исходящие VPN, включая Amnezia/AmneziaWG;
- policy-based routing;
- remote-access VPN;
- `nftables`, health-check и watchdog;
- остальные сетевые сервисы, не требующие физического разделения VLAN.

Keenetic на этом этапе остаётся физическим edge-router: он имеет WAN, общую сеть и серверную сеть. `101-network-gateway` находится внутри серверной сети и предоставляет сетевые сервисы. Доступ клиентов общей сети к этим сервисам и направление их трафика через `101` настраиваются явно на Keenetic по мере необходимости; наличие VLAN для этого не требуется.

### Этап 2 — после переезда, с VLAN

После переезда физическая схема Proxmox не усложняется: сервер по-прежнему использует один `nic0` и один кабель. Меняется содержимое этого соединения — по нему может идти VLAN trunk.

Базовая идея:

```text
Internet
   │
edge-router (вероятно OpenWrt)
   │
managed switching / VLAN
   │
   ├── MAIN
   ├── IOT / VLAN 20
   ├── CAMERAS / VLAN 30
   └── trunk → Proxmox nic0
                  │
               vmbr0
            VLAN-aware
```

OpenWrt является вероятным вариантом физического edge-router после переезда, но пока не считается окончательно выбранным. До отдельного решения не фиксируется, какие именно функции L3/firewall останутся на OpenWrt, а какие будет выполнять `101-network-gateway`.

При этом DNS, VPN, PBR, remote-access VPN и другие уже работающие сервисы `101` не нужно проектировать заново только из-за появления VLAN. Второй этап прежде всего добавляет физическое и логическое разделение MAIN/IOT/CAMERAS.

## Целевая адресация новой квартиры

Для новой квартиры принимается правило:

> **MAIN использует `10.0.0.0/16`, а для изолированных VLAN второй октет IPv4-адреса совпадает с номером VLAN. Каждый основной сегмент использует собственную сеть `/16`.**

Базовая схема:

| Сегмент | VLAN | Подсеть | Типичный шлюз |
|---|---:|---|---|
| MAIN / TRUSTED | native / untagged | `10.0.0.0/16` | `10.0.0.1` |
| IOT | 20 | `10.20.0.0/16` | `10.20.0.1` |
| CAMERAS | 30 | `10.30.0.0/16` | `10.30.0.1` |
| REMOTE-VPN | tunnel, номер 60 зарезервирован | `10.60.0.0/16` | `10.60.0.1` |

При появлении новых изолированных VLAN сохраняется правило, например:

```text
VLAN 40 → 10.40.0.0/16
VLAN 50 → 10.50.0.0/16
```

`MAIN` — специальный случай: `10.0.0.0/16` используется как native/untagged сеть. Это не означает использование VLAN 0.

Серверы находятся непосредственно в MAIN. Отдельный `VLAN 10 / SERVERS` не используется, пока не появится практическая необходимость дополнительно изолировать серверы от доверенных клиентов.

`REMOTE-VPN` также специальный случай: клиенты находятся на tunnel-интерфейсе WireGuard/AmneziaWG, поэтому физический VLAN 60 для удалённого доступа не требуется. Номер 60 резервируется для понятной адресации и возможного будущего расширения.

Внутри каждого сегмента третий октет можно использовать для логической группировки устройств без создания дополнительного VLAN. Например в IOT:

```text
10.20.1.x → освещение
10.20.2.x → ESP-контроллеры
10.20.3.x → бытовая техника
```

## Серверные адреса в MAIN

Для Proxmox и обычных VM/LXC используются статические адреса в `10.0.0.0/16`.

Для VM/LXC сохраняется читаемое соответствие VMID → IP, описанное в [`vmid-plan.md`](vmid-plan.md):

```text
VMID XYZ → 10.0.X.YZ/16
```

Примеры:

```text
PVE       → 10.0.0.10/16
201       → 10.0.2.1/16
211       → 10.0.2.11/16
301       → 10.0.3.1/16
321       → 10.0.3.21/16
401       → 10.0.4.1/16
501       → 10.0.5.1/16
```

`101-network-gateway` является специальным сетевым гостем, поэтому его адреса определяются фактической сетевой ролью, а не обычным правилом VMID → IP.

## Переход с текущей серверной сети на `10.0.0.0/16`

Переезд на новую адресацию по возможности выполняется заранее, чтобы не менять IP всех серверов в день физического переезда.

### 1. Сохраняется текущая серверная сеть Keenetic

До переезда Proxmox продолжает работать в отдельной серверной сети через один обычный Ethernet без VLAN:

```text
текущая server network: 192.168.0.0/16
PVE:                    192.168.1.11/16
текущий gateway:        192.168.1.1
```

### 2. Будущая MAIN-адресация может быть проверена заранее

На серверном интерфейсе Keenetic можно добавить будущий адрес:

```text
10.0.0.1/16
```

Это не требует VLAN и не объединяет общую и серверную сеть: дополнительная адресация вводится именно на текущем серверном сегменте.

Для `10.0.0.0/16` на Keenetic должен быть настроен выход в интернет/NAT и при необходимости маршрутизация к другим текущим сетям.

Конкретные CLI-команды Keenetic не считаются частью постоянной архитектуры и перед применением проверяются по фактической версии KeeneticOS и текущей конфигурации Hopper.

### 3. Новые серверы можно сразу переводить на постоянные `10.0.x.x`

Новые VM/LXC могут создаваться с целевым адресом `10.0.X.YZ/16` и default gateway:

```text
gateway → 10.0.0.1
```

Для совместимости со старой серверной адресацией при необходимости временно добавляется второй `192.168.x.x/16` адрес на том же виртуальном интерфейсе.

Default gateway должен быть один. Не назначать одновременно обычные default route через `192.168.1.1` и `10.0.0.1`.

### 4. Существующие серверы мигрируют постепенно

Для существующего сервера сначала добавляется будущий `10.0.x.x` как второй адрес. После проверки доступности, DNS и маршрутизации его default gateway переводится на `10.0.0.1`. Старый `192.168.x.x` некоторое время может оставаться как совместимый адрес.

### 5. Переезд в новую квартиру

После переезда адрес `10.0.0.1` должен принадлежать целевому шлюзу MAIN. Каким именно устройством будет этот шлюз и как разделятся функции между вероятным OpenWrt и `101-network-gateway`, определяется перед вторым этапом.

Серверы при этом уже могут сохранить:

```text
10.0.x.x/16
gateway 10.0.0.1
```

После проверки новой сети временные `192.168.x.x` удаляются.

Ключевой принцип миграции:

```text
физическая сеть и VLAN-слой могут измениться,
но постоянные адреса серверов и gateway не должны без необходимости меняться повторно.
```

## DNS вместо жёстко записанных IP

Сервисы и пользователи по возможности должны обращаться к инфраструктуре по локальным DNS-именам. Это уменьшает зависимость приложений и закладок от конкретных IP во время миграции.

Основной внутренний домен — `home.arpa`; подробнее см. [`dns.md`](dns.md).

## Удалённый доступ через VPN

Целевой remote-access VPN завершается на `101-network-gateway`. Базовые варианты — WireGuard/AmneziaWG.

Удалённые доверенные клиенты получают адреса из:

```text
REMOTE-VPN → 10.60.0.0/16
gateway    → 10.60.0.1
```

После подключения клиент должен использовать домашний DNS через `101-network-gateway` и, согласно firewall-политике, получать доступ к нужным домашним сегментам:

- MAIN `10.0.0.0/16`;
- IOT `10.20.0.0/16`;
- CAMERAS `10.30.0.0/16`;
- интернету через обычный WAN или выбранный исходящий VPN/PBR.

Поддерживаются full-tunnel и split-tunnel профили.

Предпочтительно выдавать VPN-клиентам DNS через tunnel-шлюз `10.60.0.1`, который передаёт запросы в общий AdGuard Home / SmartDNS.

Целевой путь трафика после появления сегментов:

```text
remote phone/laptop
        │
        │ WireGuard / AmneziaWG
        ▼
10.60.0.1 — 101-network-gateway
        │
        ├── DNS → AdGuard Home / SmartDNS
        ├── MAIN     10.0.0.0/16
        ├── IOT      10.20.0.0/16
        ├── CAMERAS  10.30.0.0/16
        └── Internet → обычный WAN или выбранный исходящий VPN/PBR
```

На первом этапе физический Keenetic остаётся edge-router и при необходимости пробрасывает входящий порт remote-access VPN на `101-network-gateway`. После переезда схема входящего VPN зависит от окончательного разделения ролей между физическим edge-router и `101`.

Дополнительный ограниченный VPN на физическом edge-router можно сохранить как аварийный административный канал на случай недоступности Proxmox или `101-network-gateway`.

Приватные VPN-ключи, peer-конфигурации с секретами и preshared keys в Git не хранятся.

## VLAN и единственная NIC Proxmox

До переезда VLAN специально не вводятся только ради будущей архитектуры. Первый этап должен оставаться простым: один Ethernet, одна серверная сеть, `vmbr0` и работающие сетевые сервисы.

После переезда тот же физический порт может стать trunk. Для целевых сегментов используются:

```text
MAIN                → native / untagged → 10.0.0.0/16
IOT / VLAN 20       → 10.20.0.0/16
CAMERAS / VLAN 30   → 10.30.0.0/16
```

Наличие нескольких VLAN не означает необходимость нескольких физических NIC на Proxmox. Разделение выполняется тегами VLAN поверх одного физического соединения.

## Граница с физической сетью квартиры

Детальная конфигурация сетевой VM хранится в `guests/101-network-gateway/` и её `rootfs/`.

Общий проект физической сети, сетевого оборудования, камер и квартиры остаётся в репозитории `zsergeyru/appart-rennovation`. Здесь хранятся только серверные и эксплуатационные сведения, непосредственно относящиеся к Proxmox.

Граница между репозиториями описана в [`apartment-infrastructure.md`](apartment-infrastructure.md).
