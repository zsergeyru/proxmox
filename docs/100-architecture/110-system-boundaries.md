# Границы ответственности частей системы

**Тип:** обзор  
**Статус:** действующий  
**Назначение:** объяснить, какая часть системы за что отвечает и где заканчивается её область управления.

Этот документ отвечает на вопрос:

> Кто за что отвечает в проекте Proxmox?

Он не описывает точные права, команды, пути и параметры. Такие подробности находятся в профильных разделах документации.

## 1. Общий принцип

Система разделена на несколько частей, и каждая из них отвечает только за свою область.

Это нужно для того, чтобы:

- изменения были предсказуемыми;
- автоматизация не получала лишних полномочий;
- было понятно, где искать причину ошибки;
- одну часть системы можно было изменять, не затрагивая остальные;
- разные средства управления не пытались одновременно управлять одним и тем же объектом разными способами.

Главное правило:

> Одна часть системы не должна незаметно брать на себя обязанности другой части.

## 2. Proxmox VE

Proxmox VE отвечает за уровень виртуализации.

В его область входят:

- виртуальные машины;
- LXC-контейнеры;
- их процессор, память и диски;
- подключение гостевых систем к сетям;
- запуск, остановка и перезапуск;
- снимки;
- хранение параметров виртуализации;
- предоставление API для управления виртуализацией.

Proxmox не отвечает за постоянную настройку приложений внутри Linux-гостей.

Например, установка веб-сервера, Docker, базы данных или изменение прикладного конфигурационного файла не является задачей самого Proxmox.

## 3. Физический PVE-хост

Физический сервер отвечает за работу самого Proxmox и базовой среды, на которой он запущен.

К этой области относятся:

- операционная система хоста;
- пакеты Proxmox;
- локальная конфигурация хоста;
- подключение хранилищ;
- служебные пользователи;
- средства управления, работающие непосредственно на хосте;
- локальное состояние этих средств.

Изменения самого хоста рассматриваются отдельно от управления виртуальными машинами и контейнерами.

## 4. Средство развёртывания гостевых систем

Средство развёртывания отвечает за создание и приведение гостевой системы к требуемому состоянию, описанному в проекте.

Оно связывает два уровня:

- описание требуемого состояния;
- фактическое состояние Proxmox и гостевой системы.

В его область входят:

- создание новой VM или LXC;
- изменение параметров существующего гостя;
- подготовка сетевых параметров гостя;
- запуск необходимых первоначальных действий;
- проверка результата;
- безопасный повторный запуск.

Средство развёртывания не должно превращаться в универсальную систему постоянной настройки приложений.

После первоначальной подготовки длительное управление Linux-системой должно передаваться специализированному средству.

## 5. Гостевая операционная система

Гостевая система отвечает за своё внутреннее состояние.

Внутри неё находятся:

- Linux;
- системные службы;
- установленные пакеты;
- пользователи;
- локальная конфигурация;
- Docker;
- приложения;
- данные приложений;
- журналы.

Гость не должен самостоятельно изменять конфигурацию самого PVE-хоста, если такое право специально не предусмотрено архитектурой.

## 6. Первоначальная настройка гостя

Первоначальная настройка отвечает только за минимальную подготовку новой гостевой системы к дальнейшей работе.

Она может:

- подготовить административный доступ;
- установить базовые необходимые компоненты;
- подготовить Git;
- подготовить Docker;
- подготовить Ansible или другие заранее определённые средства.

Она не должна содержать всю дальнейшую конфигурацию сервисов проекта.

Её задача — довести гостевую систему до состояния, в котором ею можно надёжно управлять дальше.

## 7. Ansible

Ansible отвечает за повторяемую настройку Linux внутри гостевых систем.

В его область входят:

- установка пакетов;
- создание и изменение конфигурационных файлов;
- настройка системных служб;
- развёртывание приложений;
- повторное применение одной и той же конфигурации;
- поддержание одинакового состояния нескольких систем.

Ansible не отвечает за:

- изменение самого Proxmox-хоста;
- создание или удаление виртуальных машин как основной механизм;
- управление правами Proxmox;
- изменение физической сети хоста.

## 8. AI Control

AI Control отвечает за автоматизированное управление разрешённой частью инфраструктуры.

Он может использовать разные средства:

- Proxmox API;
- SSH;
- Ansible;
- другие разрешённые интерфейсы.

AI Control не является отдельным уровнем виртуализации и не заменяет Proxmox.

Он также не должен получать неограниченное право менять всё подряд.

Его задача — использовать уже определённые механизмы управления в заранее установленных границах.

## 9. Git-репозиторий

Git-репозиторий отвечает за хранение описания проекта.

В нём находятся:

- документация;
- описание требуемого состояния;
- исходный код;
- конфигурационные шаблоны;
- сценарии;
- правила.

Git не отвечает за хранение текущего рабочего состояния инфраструктуры.

В нём не должны храниться:

- действующие закрытые ключи;
- пароли;
- секретные API-токены;
- изменяемые данные приложений;
- резервные копии виртуальных дисков.

## 10. Сетевая часть

Сетевая часть отвечает за передачу трафика между системами и сетями.

В неё входят:

- адресация;
- маршрутизация;
- DNS;
- VPN;
- сетевые правила;
- связь между сегментами.

Сетевые функции не должны случайно смешиваться с обязанностями PVE-хоста.

Если отдельная гостевая система выполняет роль маршрутизатора или DNS-сервера, это является её явным назначением.

## 11. Хранилища и резервное копирование

Хранилища отвечают за размещение данных.

Резервное копирование отвечает за возможность восстановить потерянное или повреждённое состояние.

Это разные задачи.

Рабочий диск виртуальной машины не является её резервной копией.

Снимок также не заменяет независимую резервную копию.

## 12. Безопасность и управление доступом

Система безопасности определяет:

- кто может выполнять действие;
- над каким объектом;
- через какой интерфейс;
- с какими ограничениями.

Она не должна подменять функциональные обязанности других частей системы.

Например:

- Proxmox ACL определяет, что разрешено через Proxmox;
- SSH определяет доступ внутрь гостевой операционной системы;
- Git-учётные данные определяют доступ к репозиторию.

Эти виды доступа независимы друг от друга.

## 13. Внешние связанные системы

Некоторые системы участвуют в общей инфраструктуре, но не являются частью этого репозитория.

Например, физическая инфраструктура квартиры может определять:

- где установлен сервер;
- где проходят кабели;
- где находятся камеры;
- как размещено сетевое оборудование.

Проект Proxmox использует эту инфраструктуру, но не должен дублировать её полное физическое описание.

## 14. Краткая таблица ответственности

| Часть системы | За что отвечает |
|---|---|
| Proxmox VE | Виртуализация и жизненный цикл VM/LXC |
| PVE-хост | Работа самого Proxmox и его локальной среды |
| Средство развёртывания | Создание и первоначальное приведение гостя к требуемому состоянию |
| Гостевая ОС | Внутреннее состояние Linux и приложений |
| Первоначальная настройка | Минимальная подготовка гостя к дальнейшему управлению |
| Ansible | Повторяемая настройка Linux и приложений |
| AI Control | Автоматизированное управление через разрешённые интерфейсы |
| Git | Хранение описания проекта и требуемого состояния |
| Сетевая часть | Адресация, маршрутизация, DNS, VPN и сетевые правила |
| Хранилища | Размещение рабочих данных |
| Резервное копирование | Возможность восстановления |
| Система доступа | Ограничение полномочий пользователей и автоматизации |

## 15. Главное правило

Если непонятно, где должна находиться новая функция, сначала нужно определить:

> Какая часть системы по своему назначению должна за неё отвечать?

Только после этого выбирается конкретный файл, программа или механизм реализации.

Причины выбора крупных архитектурных границ фиксируются отдельно в `190-decisions.md`.
