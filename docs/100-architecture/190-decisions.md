## 1. Правила фиксации архитектурных решений

### 1.1. Что считается архитектурным решением

В этот файл попадают решения, которые:

- влияют сразу на несколько частей системы;
- задают долгосрочную границу ответственности;
- определяют основной способ управления инфраструктурой;
- влияют на безопасность, восстановление или воспроизводимость;
- сложно или дорого изменить после внедрения;
- требуют понимания причин выбора, а не только текущего результата.

Для каждого решения важно зафиксировать не только итог, но и логику выбора.

### 1.2. Что сюда не входит

В этот файл не должны попадать:

- конкретные IP-адреса;
- VMID и CTID;
- точные пути файлов;
- текущие версии пакетов;
- параметры отдельных VM и LXC;
- команды установки;
- временные настройки;
- текущее состояние реализации;
- инструкции эксплуатации.

Такая информация относится к профильной документации, конфигурации или разделу текущего состояния.

### 1.3. Как описывается решение

Каждое архитектурное решение по возможности описывается одинаково:

1. какая проблема или вопрос возникли;
2. какие варианты рассматривались;
3. какое решение принято;
4. почему выбран именно этот вариант;
5. какие последствия и ограничения появились;
6. при каких условиях решение нужно пересмотреть.

Если решение очевидно и альтернативы практически отсутствовали, описание может быть короче.

### 1.4. Как пересматриваются решения

Архитектурное решение не считается вечным.

Если условия изменились, решение может быть:

- уточнено;
- заменено;
- отменено.

При этом старое решение не следует бесследно удалять, если понимание его причин всё ещё важно для истории проекта.

Нужно явно указать:

- что изменилось;
- почему старое решение перестало подходить;
- какое новое решение его заменяет;
- с какого момента действует новый подход.

## 2. Решения по управлению состоянием

### 2.1. Почему требуемое состояние хранится в Git

**Проблема.**  
Нужно было определить, где хранить описание того, как инфраструктура должна быть устроена, чтобы оно было проверяемым, воспроизводимым и имело историю изменений.

**Рассмотренные варианты.**

- хранить параметры только в текущей конфигурации Proxmox;
- поддерживать настройки вручную через интерфейсы управления;
- хранить описание в отдельных локальных файлах на PVE;
- использовать Git как основной источник воспроизводимого требуемого состояния.

**Принятое решение.**  
Воспроизводимое требуемое состояние хранится в Git.

**Почему.**

- изменения имеют историю;
- можно понять, кто и когда изменил конфигурацию;
- изменения можно просматривать до применения;
- состояние можно восстановить после потери рабочей системы;
- один и тот же способ описания можно использовать для автоматизации и проверки.

**Последствия и ограничения.**

- изменение фактической системы вручную не должно автоматически становиться новым требуемым состоянием;
- секреты и рабочие данные не должны попадать в Git только ради того, чтобы всё находилось в одном месте;
- автоматизация должна уметь сравнивать описание с фактическим состоянием.

**Когда пересматривать.**  
Если появится другой механизм хранения требуемого состояния, который даст не меньшую воспроизводимость, проверяемость и историю изменений и при этом лучше решит задачи проекта.

### 2.2. Почему фактическое состояние не считается источником требований

**Проблема.**  
Ручные изменения в работающей системе могут расходиться с тем, что было описано как правильное состояние.

**Рассмотренные варианты.**

- считать любое фактическое состояние автоматически правильным;
- автоматически переносить все ручные изменения обратно в описание проекта;
- разделять фактическое и требуемое состояние.

**Принятое решение.**  
Фактическое состояние показывает, что существует сейчас, но само по себе не становится источником требований.

**Почему.**

- случайная ручная правка не должна закрепляться как новое правило;
- можно явно видеть расхождения;
- повторное развёртывание остаётся предсказуемым;
- решение о принятии ручного изменения остаётся осознанным.

**Последствия и ограничения.**

- расхождения нужно отдельно анализировать;
- намеренное ручное изменение нужно затем перенести в основной источник требуемого состояния;
- автоматизация может вернуть фактическое состояние к описанному.

**Когда пересматривать.**  
Если будет внедрён надёжный двусторонний механизм управления состоянием с чёткими правилами разрешения конфликтов.

### 2.3. Почему не всё состояние хранится в Git

**Проблема.**  
Часть данных воспроизводима, а часть возникает во время работы или содержит чувствительную информацию.

**Рассмотренные варианты.**

- пытаться хранить в Git всё;
- вообще не использовать Git для состояния;
- разделить данные по типам.

**Принятое решение.**  
В Git хранится только подходящее для версионирования и воспроизведения состояние.

**Почему.**

Git хорошо подходит для:

- текстовой конфигурации;
- сценариев;
- шаблонов;
- документации;
- воспроизводимых параметров.

Git плохо подходит для:

- секретов;
- баз данных;
- виртуальных дисков;
- журналов;
- резервных копий;
- изменяемых пользовательских данных.

**Последствия и ограничения.**

- в системе остаётся несколько типов хранилищ;
- для каждого вида данных нужно заранее понимать его основной источник;
- восстановление системы требует не только Git, но и резервных копий уникальных данных.

**Когда пересматривать.**  
Если изменится используемый способ хранения данных или появится безопасный механизм версионирования тех классов данных, которые сейчас сознательно исключены из Git.

### 2.4. Почему AI Control не является отдельным источником состояния

**Проблема.**  
AI Control может создавать и изменять инфраструктуру, поэтому возник риск появления второго независимого описания того, какой система должна быть.

**Рассмотренные варианты.**

- дать AI Control собственное независимое состояние;
- разрешить ему хранить часть конфигурации отдельно;
- заставить AI Control использовать существующие источники и механизмы управления.

**Принятое решение.**  
AI Control не является отдельным источником требуемого состояния.

**Почему.**

- не возникает конкурирующих источников истины;
- изменения остаются проверяемыми;
- AI использует те же правила, что и другие средства управления;
- архитектура не зависит от конкретного AI-инструмента.

**Последствия и ограничения.**

- AI должен работать через существующие интерфейсы;
- долгосрочные изменения должны попадать в основной источник состояния;
- часть действий AI требует дополнительного шага фиксации в Git.

**Когда пересматривать.**  
Если AI Control станет самостоятельной системой декларативного управления и появится чёткая модель синхронизации с основным источником состояния.

## 3. Решения по развёртыванию и автоматизации

### 3.1. Почему развёртывание отделено от постоянной настройки ОС

**Проблема.**  
Создание VM/LXC и настройка Linux внутри них относятся к разным уровням системы, но технически их можно было объединить в один большой механизм.

**Рассмотренные варианты.**

- один универсальный сценарий делает всё;
- отдельный deploy создаёт гостя, а затем другой механизм настраивает ОС;
- полностью ручная настройка после создания гостя.

**Принятое решение.**  
Развёртывание гостя отделено от его постоянной настройки.

**Почему.**

- уменьшается связность;
- проще повторно применять изменения;
- легче понимать, где произошла ошибка;
- разные уровни системы можно развивать независимо;
- средство развёртывания не превращается в универсальный монолит.

**Последствия и ограничения.**

- появляется переход между этапами;
- нужно явно определить, где заканчивается deploy и начинается настройка ОС;
- часть общей логики приходится распределять между несколькими средствами.

**Когда пересматривать.**  
Если разделение создаст больше сложности, чем пользы, либо появится единый инструмент, который обеспечит те же границы ответственности без потери прозрачности.

### 3.2. Почему первоначальная настройка должна оставаться минимальной

**Проблема.**  
Первоначальный bootstrap легко превратить в ещё одну полноценную систему конфигурации.

**Рассмотренные варианты.**

- выполнять в bootstrap всю настройку сервиса;
- ограничить bootstrap только подготовкой среды;
- отказаться от bootstrap и всё делать вручную.

**Принятое решение.**  
Первоначальная настройка выполняет только минимальные действия, необходимые для дальнейшего управления.

**Почему.**

- bootstrap остаётся простым;
- меньше логики дублируется с Ansible;
- проще тестировать создание нового гостя;
- меньше зависимостей возникает на самом раннем этапе.

**Последствия и ограничения.**

- после bootstrap требуется следующий этап настройки;
- нельзя без необходимости добавлять туда прикладную конфигурацию.

**Когда пересматривать.**  
Если появится необходимость гарантированно выполнять дополнительный минимальный набор действий до того, как становится доступен основной механизм настройки.

### 3.3. Почему для постоянной настройки выбран Ansible

**Проблема.**  
Нужно было выбрать механизм повторяемой настройки Linux и сервисов.

**Рассмотренные варианты.**

- набор собственных shell-скриптов;
- ручная настройка;
- конфигурация только через Docker;
- Ansible.

**Принятое решение.**  
Для повторяемой настройки Linux используется Ansible.

**Почему.**

- конфигурация описывается явно;
- операции можно выполнять повторно;
- удобно работать сразу с несколькими системами;
- большая часть типовых задач уже поддерживается готовыми модулями;
- Ansible не требует отдельного агента в каждом Linux-госте.

**Последствия и ограничения.**

- требуется поддерживать inventory, роли и playbook;
- сложная логика может сделать Ansible-код трудно читаемым;
- не все задачи нужно пытаться решать через Ansible.

**Когда пересматривать.**  
Если Ansible перестанет подходить по сложности, скорости или модели управления либо появится более подходящий инструмент для основной массы Linux-гостей.

### 3.4. Почему AI Control использует существующие механизмы управления

**Проблема.**  
AI Control мог бы напрямую реализовать собственные способы создания VM, изменения Linux и управления сетью.

**Рассмотренные варианты.**

- реализовать всю инфраструктурную логику внутри AI Control;
- разрешить прямые действия без общей модели;
- использовать существующие deploy, API, SSH и Ansible.

**Принятое решение.**  
AI Control использует уже существующие механизмы управления.

**Почему.**

- правила управления не дублируются;
- проще проверять и ограничивать действия;
- AI остаётся заменяемым компонентом;
- одни и те же операции можно выполнять как вручную, так и через AI.

**Последствия и ограничения.**

- возможности AI зависят от качества существующих инструментов;
- для новой операции сначала может потребоваться добавить нормальный управляемый механизм.

**Когда пересматривать.**  
Если для части задач AI потребуется специализированный интерфейс, который нельзя разумно выразить через существующие средства.

## 4. Решения по безопасности и доступу

### 4.1. Почему разделены доступ к PVE, SSH и Git

**Проблема.**  
Разные типы доступа дают разные полномочия, но их можно было связать одной общей учётной записью или ключом.

**Рассмотренные варианты.**

- одна универсальная учётная запись;
- один общий SSH-ключ;
- отдельные учётные данные для разных систем и задач.

**Принятое решение.**  
Доступ к PVE, SSH гостевых систем, Git и другим системам разделён.

**Почему.**

- компрометация одного доступа не открывает автоматически остальные;
- проще выдавать минимальные полномочия;
- можно независимо отзывать доступ;
- яснее назначение каждой учётной записи.

**Последствия и ограничения.**

- становится больше ключей и учётных данных;
- требуется механизм их учёта и синхронизации.

**Когда пересматривать.**  
Если будет внедрён единый надёжный механизм идентификации с отдельными областями полномочий и независимым отзывом прав.

### 4.2. Почему не используется одна универсальная техническая учётная запись

**Проблема.**  
Универсальная учётная запись упрощает настройку, но смешивает роли человека, deploy, AI и других средств автоматизации.

**Рассмотренные варианты.**

- одна общая административная учётная запись;
- одна учётная запись для всей автоматизации;
- отдельные учётные записи по назначению.

**Принятое решение.**  
Разные управляющие роли используют отдельные учётные данные.

**Почему.**

- проще понять источник действий;
- можно выдавать разные права;
- отзыв одной роли не затрагивает остальные;
- снижается масштаб последствий компрометации.

**Последствия и ограничения.**

- права и ключи нужно сопровождать отдельно;
- документация доступа становится важной частью проекта.

**Когда пересматривать.**  
Если появится централизованная система идентификации, которая сохранит такое же разделение ролей без отдельных локальных учётных записей.

### 4.3. Почему секреты не хранятся в Git

**Проблема.**  
Git удобен для конфигурации, но его история делает удаление случайно опубликованного секрета сложным и ненадёжным.

**Рассмотренные варианты.**

- хранить секреты рядом с конфигурацией;
- хранить их в зашифрованном виде в Git;
- держать секреты отдельно.

**Принятое решение.**  
Секреты не хранятся в обычном Git-репозитории проекта.

**Почему.**

- уменьшается риск случайной публикации;
- доступ к конфигурации не означает доступ к секретам;
- секреты можно отдельно менять и отзывать.

**Последствия и ограничения.**

- для воспроизведения системы одного Git недостаточно;
- требуется отдельная процедура восстановления секретов.

**Когда пересматривать.**  
Если будет выбран и формально принят отдельный безопасный механизм хранения зашифрованных секретов вместе с Git.

### 4.4. Почему автоматизация получает ограниченные полномочия

**Проблема.**  
Полные административные права упрощают разработку автоматизации, но увеличивают риск ошибки и компрометации.

**Рассмотренные варианты.**

- полный root-доступ ко всему;
- широкие права одной общей учётной записи;
- минимальные права по назначению.

**Принятое решение.**  
Автоматизация получает только необходимые ей полномочия.

**Почему.**

- ошибка в одном компоненте имеет ограниченные последствия;
- проще отделять зоны ответственности;
- безопасность не зависит только от корректности программы.

**Последствия и ограничения.**

- некоторые операции требуют отдельных ролей или дополнительных механизмов;
- права нужно сопровождать при развитии функций.

**Когда пересматривать.**  
Не само правило минимальных полномочий, а конкретный способ его реализации может меняться при смене механизмов доступа.

## 5. Решения по инфраструктурным границам

### 5.1. Почему сетевые функции не размещаются непосредственно на PVE

**Проблема.**  
PVE технически может выполнять дополнительные сетевые функции, но это связывает доступность виртуализации с маршрутизацией, DNS и VPN.

**Рассмотренные варианты.**

- выполнять сетевые функции на самом PVE;
- оставить их на внешнем физическом роутере;
- выделить отдельную сетевую VM или другой специализированный уровень.

**Принятое решение.**  
PVE не используется как основной маршрутизатор, DNS- или VPN-центр.

**Почему.**

- гипервизор остаётся проще;
- сетевые функции можно обновлять и менять отдельно;
- снижается количество нестандартной конфигурации PVE;
- проще понимать границы отказа.

**Последствия и ограничения.**

- появляется отдельный сетевой компонент;
- нужно учитывать зависимость части инфраструктуры от его доступности.

**Когда пересматривать.**  
Если изменится физическая или логическая схема сети и отдельный сетевой уровень перестанет давать преимущества.

### 5.2. Почему рабочее состояние и резервные копии разделены

**Проблема.**  
Хранение копии рядом с рабочими данными не защищает от многих общих отказов.

**Рассмотренные варианты.**

- полагаться на рабочее хранилище;
- использовать только снимки;
- хранить отдельные резервные копии.

**Принятое решение.**  
Рабочее состояние и резервные копии считаются разными сущностями.

**Почему.**

- повреждение рабочего хранилища не должно уничтожать единственную копию;
- можно хранить несколько точек восстановления;
- резервная копия имеет собственный жизненный цикл.

**Последствия и ограничения.**

- требуется дополнительное место;
- резервные копии нужно проверять и сопровождать.

**Когда пересматривать.**  
Может меняться конкретная технология резервного копирования, но само разделение рабочего и восстановительного состояния сохраняется, пока данные требуют защиты.

### 5.3. Почему снимок не считается полноценной резервной копией

**Проблема.**  
Snapshot удобен для быстрого отката, поэтому его легко принять за достаточную защиту данных.

**Рассмотренные варианты.**

- использовать только snapshots;
- отказаться от snapshots;
- использовать snapshots для краткосрочных задач, а backup — для восстановления.

**Принятое решение.**  
Снимок не заменяет независимую резервную копию.

**Почему.**

- snapshot обычно зависит от того же хранилища;
- потеря исходного хранилища уничтожает и снимок;
- snapshot решает другую задачу — быстрый локальный откат.

**Последствия и ограничения.**

- для полноценного восстановления нужен отдельный механизм backup;
- снимки всё равно могут использоваться там, где они удобны.

**Когда пересматривать.**  
Если используемая технология snapshot физически и логически обеспечивает независимую копию данных, эквивалентную требованиям к backup.

### 5.4. Почему физическая инфраструктура квартиры вынесена в отдельный проект

**Проблема.**  
Серверная инфраструктура связана с кабелями, шкафами, камерами и другими физическими объектами квартиры, но объединение всего в один проект создаёт смешение областей.

**Рассмотренные варианты.**

- хранить всё в одном репозитории;
- дублировать физические данные в обоих проектах;
- разделить проекты и связывать их ссылками.

**Принятое решение.**  
Физическая инфраструктура квартиры ведётся в отдельном проекте, а Proxmox-репозиторий содержит только относящуюся к серверной системе информацию и необходимые ссылки.

**Почему.**

- каждый проект сохраняет ясную область ответственности;
- меньше дублирования;
- физическая и программная инфраструктура могут развиваться независимо;
- проще навигация по документации.

**Последствия и ограничения.**

- некоторые вопросы требуют перехода между двумя проектами;
- связи между ними нужно явно указывать.

**Когда пересматривать.**  
Если граница между проектами станет настолько искусственной, что значительная часть информации начнёт постоянно дублироваться или требовать одновременного изменения в обоих репозиториях.
