# Модель состояния и размещения данных

**Тип:** обзор  
**Статус:** действующий  
**Назначение:** объяснить, где находятся разные виды данных системы и что считается главным источником для каждого из них.

Этот документ отвечает на вопрос:

> Где что хранится и откуда система должна брать правильное состояние?

Документ описывает общую архитектуру хранения. Точные пути, форматы файлов и технические параметры находятся в профильных разделах.

## 1. Основной принцип

В системе нет одного места, в котором хранится абсолютно всё.

Разные виды данных имеют разные источники.

Главное правило:

> Для каждого вида данных должен быть понятен его основной источник.

Это позволяет избежать ситуации, когда одно и то же состояние независимо редактируется в нескольких местах.

## 2. Требуемое состояние

Требуемое состояние описывает:

> Как система должна быть устроена.

Основным источником такого описания является Git-репозиторий.

В нём могут храниться:

- параметры гостевых систем;
- структура сервисов;
- конфигурационные шаблоны;
- правила развёртывания;
- сценарии;
- документация;
- другие воспроизводимые настройки.

Требуемое состояние должно быть проверяемым и версионируемым.

## 3. Фактическое состояние Proxmox

Proxmox хранит текущее фактическое состояние уровня виртуализации.

К нему относятся:

- существующие VM и LXC;
- их процессор и память;
- диски;
- сетевые интерфейсы;
- состояние запуска;
- снимки;
- параметры виртуализации.

Это состояние показывает:

> Что реально существует и работает сейчас.

Оно не заменяет описание требуемого состояния в Git.

## 4. Фактическое состояние гостевой системы

Внутри VM или LXC хранится состояние самой операционной системы и приложений.

Например:

- установленные пакеты;
- локальные пользователи;
- конфигурационные файлы;
- службы;
- Docker-контейнеры;
- базы данных;
- данные приложений;
- журналы.

Часть такого состояния может быть воспроизводима из Git и Ansible.

Другая часть возникает во время работы и требует отдельного хранения и резервного копирования.

## 5. Локальное состояние средств управления

Некоторые данные нужны только для работы самих средств управления и не являются частью описания инфраструктуры в Git.

Например:

- сведения о завершённых этапах;
- сохранённые ключи доверия к удалённым системам;
- блокировки;
- служебные отметки;
- локальные реестры;
- технические данные повторного запуска.

Такие данные хранятся рядом с тем средством, которому они принадлежат.

Они не должны без необходимости превращаться в часть Git-репозитория.

## 6. Секреты и закрытые учётные данные

Секреты хранятся отдельно от обычной конфигурации.

К ним относятся:

- закрытые SSH-ключи;
- пароли;
- API-токены;
- закрытые ключи доступа к внешним системам;
- другие данные, дающие полномочия.

Git не является местом хранения таких данных.

Открытая часть ключа может храниться отдельно, если она не предоставляет доступа сама по себе.

## 7. Хранилища данных

Рабочие данные размещаются в предназначенных для этого хранилищах.

К ним могут относиться:

- виртуальные диски;
- файловые системы контейнеров;
- постоянные данные сервисов;
- архивы;
- шаблоны;
- образы;
- большие файлы, которые не должны храниться в Git.

Хранилище рабочего состояния и хранилище резервных копий могут быть разными.

## 8. Резервные копии

Резервная копия является отдельным сохранённым состоянием, предназначенным для восстановления.

Она не считается источником текущей конфигурации.

Её задача другая:

> вернуть данные или систему после потери, повреждения или ошибочного изменения.

Резервные копии могут содержать данные, которых нет и не должно быть в Git.

## 9. Документация

Документация описывает устройство системы, правила и принятые решения.

Она является источником понимания архитектуры, но не должна дублировать машинные конфигурационные данные без необходимости.

Например, если параметр уже хранится в рабочем конфигурационном файле, документация должна объяснять его смысл, а не становиться второй независимой копией того же значения.

## 10. Что считается главным источником

| Вид информации | Основной источник |
|---|---|
| Архитектурные правила | Документация |
| Причины принятых решений | Файлы решений `x90` |
| Требуемое состояние инфраструктуры | Git |
| Фактическое состояние VM/LXC | Proxmox |
| Фактическое состояние Linux | Конкретная гостевая система |
| Повторяемая настройка Linux | Git и Ansible |
| Служебное состояние средства управления | Локальное состояние этого средства |
| Секреты | Защищённое локальное хранилище или специально предназначенное хранилище секретов |
| Рабочие данные сервисов | Хранилище соответствующего сервиса |
| Резервные копии | Отдельное хранилище резервных копий |
| Физическая инфраструктура квартиры | Отдельный проект квартиры |

## 11. Как состояние проходит через систему

Общая схема выглядит так:

```text
Git
│
│ требуемое состояние
▼
средство управления
│
│ сравнение
▼
фактическое состояние
│
├── Proxmox
└── гостевая система
```

Средство управления должно:

1. прочитать требуемое состояние;
2. получить фактическое состояние;
3. определить разницу;
4. показать или проверить необходимые изменения;
5. применить только разрешённые изменения;
6. проверить итоговый результат.

## 12. Требуемое и фактическое состояние не должны смешиваться

Не следует вручную считать текущее состояние Proxmox новым источником требований.

Например, если параметр был изменён вручную в Proxmox, это ещё не означает, что новое значение стало правильным требуемым состоянием.

Сначала нужно решить:

- изменение было намеренным;
- оно должно сохраниться;
- его нужно перенести в основной источник требуемого состояния.

Иначе следующий повторный запуск автоматизации может вернуть систему к прежнему описанному состоянию.

## 13. Не всё должно храниться в Git

Git хорошо подходит для данных, которые:

- текстовые;
- версионируемые;
- воспроизводимые;
- не содержат секретов;
- должны проходить проверку изменений.

Git плохо подходит для:

- секретов;
- больших виртуальных дисков;
- баз данных;
- журналов;
- временного состояния;
- резервных копий;
- изменяемых пользовательских данных.

## 14. Не всё фактическое состояние нужно сохранять

Часть состояния можно восстановить из описания проекта.

Например:

- создать новую VM;
- установить пакеты;
- развернуть конфигурацию;
- запустить нужную службу.

Такое состояние предпочтительно воспроизводить.

Другая часть состояния уникальна и должна сохраняться:

- пользовательские данные;
- базы данных;
- закрытые ключи;
- уникальные идентификаторы;
- другие невоспроизводимые данные.

Для них требуется отдельная стратегия хранения и резервного копирования.

## 15. Главное правило

Для любого нового файла, параметра или данных сначала нужно определить:

1. это требуемое состояние или фактическое;
2. это воспроизводимые данные или уникальные;
3. содержат ли они секрет;
4. какой объект системы ими владеет;
5. где находится их основной источник;
6. нужно ли их резервировать.

После этого выбирается конкретное место хранения.

Причины выбора общей модели состояния фиксируются отдельно в `190-decisions.md`.
