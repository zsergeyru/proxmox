# Правила создания документации

**Статус:** действующий  
**Назначение:** единые правила для всей документации проекта Proxmox.

Этот файл является основным источником правил оформления и организации документации в каталоге `docs/`.

## 1. Общие правила документации

### 1.1. Назначение документации

Документация должна помогать человеку:

- быстро понять устройство проекта;
- найти основной документ по нужной теме;
- отличить правила от текущей реализации;
- найти точные технические сведения;
- понять причины принятых решений;
- не читать все документы подряд ради одного ответа.

Структура документации должна облегчать поиск информации, а не отражать историю того, как проект развивался.

### 1.2. Язык документации

Документация пишется по-русски.

Не использовать англицизмы там, где есть понятный и естественный русский термин.

Допустимо оставлять без перевода:

- официальные названия технологий и продуктов;
- имена команд;
- имена файлов и каталогов;
- имена полей конфигурации;
- идентификаторы;
- технические сущности, для которых перевод ухудшает точность.

Примеры:

`Proxmox`, `SSH`, `API`, `guest.yaml`, `deploy-guest`, `management.ssh_identity` сохраняются без перевода.

### 1.3. Простота формулировок

Даже техническая документация должна быть написана максимально ясно.

Предпочтительно:

- короткие предложения;
- прямые формулировки;
- явные причинно-следственные связи;
- сначала общий смысл, затем детали.

Не использовать сложный профессиональный язык, если ту же мысль можно передать проще без потери точности.

### 1.4. Ссылки вместо повторов

Если подробное описание уже находится в другом документе, нужно дать ссылку на него.

Не следует после ссылки снова повторять полное описание той же темы.

Один документ должен быть основным источником подробного описания конкретной темы.

## 2. Структура каталогов и нумерация

### 2.1. Трёхзначная нумерация

Документация использует трёхзначную нумерацию.

Пример:

```text
100-architecture/
200-pve/
300-guests/
400-network/
500-ai/
600-storage/
700-security/
800-operations/
900-boundaries/
```

Внутри каждого раздела документы также имеют трёхзначные номера.

Пример:

```text
300-overview.md
310-manifest-reference.md
320-desired-state.md
330-deploy-guest.md
390-decisions.md
```

### 2.2. Номер определяется смыслом документа

При переработке старой документации нельзя автоматически сохранять старый номер или старый раздел.

Номер нового документа определяется его смыслом.

Если информация из старого файла относится к нескольким новым областям, она должна быть распределена между соответствующими документами.

Нельзя переносить старую структуру только потому, что она уже существовала.

### 2.3. Обзорный файл `x00`

Первый файл каждого тематического раздела имеет номер, оканчивающийся на `00`.

Примеры:

`100`, `200`, `300`, `400`, `500`.

Такой файл является обзорным.

Обзор должен:

- давать полную картину раздела;
- быть написан простым и понятным языком;
- быть понятен человеку без профессиональной подготовки;
- объяснять, что относится к разделу;
- показывать основные части раздела;
- показывать связи между ними;
- указывать, в каких документах искать подробности.

После прочтения обзорного файла человек должен понимать устройство раздела в целом, даже если он ещё не читал технические документы.

Обзорный файл не должен превращаться в подробную техническую спецификацию.

Точные команды, пути, параметры, права, алгоритмы и внутренние детали должны находиться в профильных документах.

### 2.4. Файл решений `x90`

Файл с номером, оканчивающимся на `90`, используется для фиксации причин ключевых решений раздела.

Примеры:

`190-decisions.md`, `290-decisions.md`, `390-decisions.md`.

Файл решений отвечает на вопрос:

> Почему был выбран именно такой подход?

Он не должен повторять текущее описание архитектуры, конфигурации или реализации.

Подробные правила для файлов `x90` определены в разделе 5.

### 2.5. `README.md` тематического раздела

Каждый крупный тематический каталог может содержать минимальный `README.md`.

Его задача — быть точкой входа и оглавлением раздела.

В `README.md` рекомендуется включать:

- краткое описание назначения раздела;
- список файлов раздела;
- короткое назначение каждого файла;
- кликабельные ссылки на документы;
- рекомендуемый порядок чтения, если он полезен.

`README.md` не должен дублировать содержание обзорного файла `x00` или профильных документов.

## 3. Разделение ответственности между документами

### 3.1. Один документ — одна основная ответственность

Каждый документ должен отвечать на один основной вопрос.

Не следует объединять в одном файле:

- справочник полей;
- архитектурные принципы;
- пошаговую инструкцию;
- историю принятия решений;
- текущий статус реализации.

Если тема достаточно самостоятельна, она должна иметь отдельный документ.

### 3.2. Одна тема — один основной документ

У каждой темы должен быть один основной документ.

Другие документы могут:

- кратко упоминать тему;
- объяснять её связь со своей областью;
- давать ссылку на основной документ.

Но они не должны повторять полное описание той же темы.

Если одно и то же правило подробно описано в нескольких местах, документацию нужно переработать.

### 3.3. Требования и фактическая реализация

Не смешивать требования проекта и текущее состояние кода.

Архитектура, политика и спецификации описывают:

> как должно быть.

Отдельный документ состояния реализации описывает:

> что уже реализовано фактически.

Не следует добавлять в каждый технический документ длинные пояснения вида «это уже реализовано», «это пока не реализовано» или «это планируется».

### 3.4. Не копировать историческое дублирование

При переносе документации из `docs/legacy/` старые файлы используются как источник информации, но не как шаблон новой структуры.

Перед переносом нужно определить:

- к какой области относится информация;
- кто является владельцем темы;
- является ли это правилом, справкой, инструкцией или решением;
- не существует ли уже основного документа по этой теме.

Дублирующиеся части нужно объединять, а не копировать.

## 4. Типы документов

### 4.1. Обзор

Отвечает на вопрос:

> Как в целом устроен раздел?

Пишется простым языком.

### 4.2. Политика

Отвечает на вопрос:

> Какие правила проекта приняты?

Описывает обязательные принципы и ограничения.

### 4.3. Спецификация

Отвечает на вопрос:

> Как именно должно работать?

Содержит точный технический контракт.

### 4.4. Справочник

Отвечает на вопрос:

> Что означает конкретный параметр, поле, путь или объект?

Предназначен для быстрого поиска точной информации.

### 4.5. Инструкция

Отвечает на вопрос:

> Что нужно сделать по шагам?

Описывает последовательность действий оператора.

### 4.6. Решения

Отвечает на вопрос:

> Почему мы сделали именно так?

Документы этого типа размещаются в файлах `x90-decisions.md`.

Они описывают причины выбора, альтернативы, последствия и условия пересмотра, а не текущее устройство системы само по себе.

## 5. Правила файлов решений `x90`

### 5.1. Что считается архитектурным или системным решением

В файл `x90` включается решение, если оно:

- влияет на несколько частей раздела или системы;
- задаёт долгосрочную границу ответственности;
- определяет основной способ управления;
- влияет на безопасность, восстановление или воспроизводимость;
- сложно или дорого изменить после внедрения;
- требует сохранения причин выбора и рассмотренных альтернатив.

Мелкие параметры реализации не считаются самостоятельными решениями для `x90`.

### 5.2. Что не должно попадать в `x90`

В файл решений не следует помещать:

- конкретные IP-адреса;
- VMID и CTID;
- точные пути файлов, если сам выбор пути не является архитектурным решением;
- текущие версии пакетов;
- параметры отдельных VM и LXC;
- команды установки;
- пошаговые инструкции;
- временные настройки;
- текущее состояние реализации;
- обычное описание того, как система устроена сейчас.

Такая информация должна находиться в профильной документации, конфигурации или документах состояния реализации.

### 5.3. Как группировать решения внутри файла

В файле `x90` используется двухуровневая структура.

Разделы первого уровня объединяют несколько связанных решений по одной теме.

Разделы второго уровня описывают отдельные решения.

Нежелательно делать каждый раздел первого уровня одним решением.

Пример:

```text
## 2. Решения по управлению состоянием

### 2.1. Почему требуемое состояние хранится в Git
### 2.2. Почему фактическое состояние не считается источником требований
### 2.3. Почему не всё состояние хранится в Git
```

### 5.4. Единая структура описания решения

Каждое отдельное решение по возможности описывается в одинаковом порядке:

1. **Проблема** — какой вопрос нужно было решить.
2. **Рассмотренные варианты** — какие основные подходы сравнивались.
3. **Принятое решение** — какой вариант выбран.
4. **Почему** — основные причины выбора.
5. **Последствия и ограничения** — что решение упрощает, усложняет или ограничивает.
6. **Когда пересматривать** — при каких условиях решение может перестать быть подходящим.

Если решение простое и очевидное, отдельные части можно сократить, но смысл должен сохраняться.

### 5.5. Как фиксировать альтернативы

Нужно указывать только реальные варианты, которые действительно рассматривались или были разумной альтернативой.

Не следует искусственно придумывать варианты только ради заполнения шаблона.

Для отвергнутого варианта достаточно объяснить его основное преимущество и причину отказа, если это важно для понимания выбора.

### 5.6. Как фиксировать последствия и ограничения

Файл решений должен содержать не только преимущества выбранного подхода.

Нужно также явно указывать:

- дополнительную сложность;
- новые зависимости;
- ограничения;
- неудобства;
- риски;
- стоимость сопровождения.

Это позволяет в будущем понять, остаётся ли решение оправданным.

### 5.7. Когда решение пересматривать

Для существенных решений нужно указывать условия пересмотра.

Основанием могут быть:

- изменение требований;
- изменение масштаба системы;
- появление нового инструмента;
- изменение модели безопасности;
- выявленная сложность сопровождения;
- изменение физических или инфраструктурных ограничений.

Фраза «никогда не пересматривать» не должна использоваться без серьёзного основания.

### 5.8. Как фиксировать отмену или замену решения

Старое решение не следует бесследно удалять, если понимание его причин важно для истории проекта.

При замене решения нужно указать:

- что изменилось;
- почему прежний подход больше не подходит;
- какое решение принято вместо него;
- с какого момента действует новый подход;
- ссылку на новое решение, если оно описано отдельно.

Устаревшее решение должно быть явно помечено как заменённое или отменённое.

## 6. Правила специальных видов документации

### 6.1. Справочники должны быть удобны для поиска

Если документ описывает множество параметров, полей или свойств, он должен быть организован как справочник.

Например, описание `guest.yaml` должно позволять быстро найти конкретное поле и увидеть:

- его тип;
- допустимые значения;
- обязательность;
- где оно задаётся;
- наследуется ли оно;
- значение по умолчанию;
- краткое назначение;
- ссылку на подробную механику, если она находится в другом документе.

### 6.2. Пошаговые инструкции

Инструкция должна описывать последовательность действий оператора.

Она должна:

- начинаться с понятных предварительных условий;
- содержать действия в правильном порядке;
- указывать ожидаемый результат;
- отделять обязательные шаги от проверок и дополнительных действий;
- ссылаться на спецификацию или политику, если требуется объяснить причину правила.

Инструкция не должна становиться основным источником архитектурных требований.

### 6.3. Документы состояния реализации

Текущее состояние реализации должно храниться отдельно от требований и спецификаций.

Такой документ может содержать:

- что уже реализовано;
- что реализовано частично;
- что ещё не реализовано;
- известные временные ограничения;
- ссылки на связанные задачи или изменения.

Он не должен менять смысл нормативных документов.

## 7. Работа со старой документацией

### 7.1. Назначение `docs/legacy/`

Каталог `docs/legacy/` содержит старую документацию на период переработки.

Старые файлы используются как источник информации, но не считаются целевой структурой.

### 7.2. Как переносить информацию

При переносе нужно:

- проверить актуальность информации;
- определить правильную тематическую область;
- определить тип документа;
- найти основной документ темы;
- устранить дублирование;
- переносить решение отдельно от текущей спецификации, если это разные по смыслу сведения.

Новая документация создаётся по текущим правилам, а не копированием структуры legacy.

### 7.3. Когда старый документ можно удалить

Старый документ можно удалять только после того, как:

- вся актуальная информация перенесена;
- дублирование устранено;
- ссылки на новую документацию проверены;
- подтверждено, что старый файл больше не нужен как временный источник.

Удаление legacy выполняется отдельным осознанным изменением.

## 8. Итоговые требования к структуре

### 8.1. Как человек должен входить в раздел документации

Для первого знакомства человек должен открыть:

1. `README.md` раздела, если он существует;
2. обзорный файл `x00`.

После этого должно быть понятно, какие документы относятся к разделу и куда идти за подробностями.

### 8.2. Как должны находиться подробности

Профильные документы должны иметь ясное назначение и не дублировать друг друга.

Человек должен иметь возможность перейти от общего описания к:

- политике;
- спецификации;
- справочнику;
- инструкции;
- состоянию реализации.

### 8.3. Как должны находиться причины решений

Если нужно понять, почему выбран текущий подход, человек должен перейти в файл `x90-decisions.md`.

Технические документы описывают принятое состояние.

Файл решений объясняет причины выбора, рассмотренные альтернативы, последствия и условия пересмотра.

Главный принцип всей документации:

> сначала понять, затем быстро найти подробности, а при необходимости отдельно узнать причины принятого решения.
