# Сеть Proxmox

**Тип:** Спецификация  
**Статус:** Действующий  
**Основной источник:** Да — для общей архитектуры IPv4, VLAN, VPN, PBR и сетевых требований проекта.

Фактическое состояние PVE хранится в [`../host/pve/network/README.md`](../host/pve/network/README.md), детали VM `109` — в [`../guests/109-network-gateway/README.md`](../guests/109-network-gateway/README.md).

## Базовые принципы

- у Proxmox одна физическая Ethernet-карта `nic0`;
- PVE не является неявным маршрутизатором между сегментами;
- до переезда VLAN не нужны;
- после переезда `nic0` используется как транковое соединение через `vmbr0` с поддержкой VLAN;
- OpenWrt как пограничный маршрутизатор отвечает за WAN, VLAN, DHCP и базовую L3-маршрутизацию/межсетевой экран;
- `109-network-gateway` отвечает за DNS, исходящие VPN, маршрутизацию по правилам PBR, VPN для удалённого доступа и связанные сервисы;
- отказ Proxmox или VM `109` не должен отключать обычный интернет и базовую маршрутизацию квартиры.

## Текущая квартира

Сейчас Keenetic остаётся пограничным WAN-маршрутизатором. PVE и гостевые системы находятся в одной плоской LAN:

```text
LAN:      192.168.0.0/16
PVE:      192.168.1.11/16
gateway:  192.168.1.1
bridge:   vmbr0 → nic0
```

Центральная сеть гостевых систем в `guests/defaults.yaml`:

```yaml
defaults:
  network:
    bridge: vmbr0
    subnet: 192.168.0.0/16
    gateway: 192.168.1.1
    addressing: vmid
```

Имена полей YAML оставлены без перевода, поскольку это машинный интерфейс.

## Целевая квартира

Физическая модель:

```text
Интернет
   │
OpenWrt — пограничный маршрутизатор
   │
управляемый коммутатор / VLAN
   ├── MAIN / основная сеть
   ├── IOT / VLAN 20
   ├── CAMERAS / VLAN 30
   └── транк → Proxmox nic0 → vmbr0 с поддержкой VLAN
```

Сегменты:

| Сегмент | VLAN | Подсеть | L3-шлюз |
|---|---:|---|---|
| MAIN / доверенная | основная | `10.0.0.0/16` | `10.0.0.1` OpenWrt |
| IOT | 20 | `10.20.0.0/16` | `10.20.0.1` OpenWrt |
| CAMERAS | 30 | `10.30.0.0/16` | `10.30.0.1` OpenWrt |
| REMOTE-VPN | туннель | `10.60.0.0/16` | VPN на VM 109 |

Серверы пока остаются в MAIN; отдельный серверный VLAN не вводится.

## Административный IP

Обычный адрес не хранится в каждом `guest.yaml`. Он вычисляется из активной центральной подсети и VMID:

```text
VMID XYZ + A.B.0.0/16
→ A.B.X.YZ
```

Текущие примеры:

```text
109 → 192.168.1.9
211 → 192.168.2.11
301 → 192.168.3.1
311 → 192.168.3.11
321 → 192.168.3.21
331 → 192.168.3.31
401 → 192.168.4.1
```

После смены центральной подсети на `10.0.0.0/16` те же VMID автоматически дают:

```text
109 → 10.0.1.9
211 → 10.0.2.11
301 → 10.0.3.1
311 → 10.0.3.11
321 → 10.0.3.21
331 → 10.0.3.31
401 → 10.0.4.1
```

Для исключения допустимо явное переопределение `network.ipv4.address` в конкретном `guest.yaml`. В нём хранится только IPv4 без префикса.

## Один IP и один шлюз

Архитектура больше не использует:

```text
пару current/target address
mode=current/dual/target
два IP одновременно
default_gateway selector
```

Названия удалённых полей оставлены без перевода, чтобы было понятно, какие именно элементы старой схемы больше не поддерживаются.

В каждый момент времени у гостевой системы одна штатная сетевая конфигурация Proxmox, один административный IP и один шлюз по умолчанию.

Это одинаково относится к VM и LXC и не требует второго механизма настройки сети внутри гостевой ОС.

## Миграция `192.168 → 10.0`

Перед переключением новый шлюз `10.0.0.1` и L2-доступ к новой сети должны быть готовы.

В Git меняются только центральные значения:

```yaml
defaults:
  network:
    subnet: 10.0.0.0/16
    gateway: 10.0.0.1
```

Обычные `guest.yaml` не изменяются.

Будущее средство миграции должно применять новое требуемое состояние по одной гостевой системе:

```text
предварительно проверить новый шлюз и L2
→ гостевая система N
   вычислить новый IP из VMID
   изменить IP и шлюз штатным механизмом Proxmox
   применить изменения или перезагрузить при необходимости
   проверить доступ по новому IP
→ только после успеха перейти к системе N+1
→ остановиться при первой ошибке
```

Такой процесс уменьшает область влияния ошибки и позволяет отдельно восстановить конкретную гостевую систему, не переключая всю инфраструктуру одновременно.

Гость с явным переопределением IP требует отдельного внимания: при смене подсети адрес должен быть вручную приведён к новой сети. Проверяющий скрипт блокирует адрес вне активной центральной подсети.

## DNS

Постоянные сервисы используют `home.arpa`; `.local` остаётся для mDNS.

На VM `109` работает SmartDNS. DNS сам по себе не является механизмом маршрутизации: выбор ISP или VPN выполняется через `nftables` и PBR.

## Маршрутизация по правилам и VPN

На VM `109`:

```text
SmartDNS / правила доменов
        ↓
наборы nftables + fwmark
        ↓
ip rule / таблицы маршрутизации
        ├── обычный WAN
        ├── AmneziaWG
        └── другие VPN или выходы
```

OpenWrt остаётся базовым шлюзом по умолчанию для VLAN.

## VPN для удалённого доступа

Основной удалённый VPN завершается на VM `109`:

```text
REMOTE-VPN → 10.60.0.0/16
```

На физическом маршрутизаторе допускается отдельный ограниченный аварийный VPN, чтобы административный доступ не зависел от Proxmox.

## IPv6

IPv6 включается позднее как второй стек наряду с IPv4. DHCPv6-PD, RA и межсетевой экран локальных VLAN принадлежат OpenWrt. NAT66 по умолчанию не используется.

## Критерий отказоустойчивости

При остановке Proxmox или VM `109` должны сохраняться:

```text
локальная L3-маршрутизация между разрешёнными VLAN
обычный доступ в интернет через WAN
DHCP
базовый межсетевой экран
```

Могут быть недоступны только функции, сознательно вынесенные на `109`: SmartDNS, специальные VPN/PBR, VPN для удалённого доступа и отражение mDNS между сегментами.
