# `deploy-guest` — спецификация развёртывания гостевых систем

**Тип:** Спецификация  
**Статус:** Действующий  
**Основной источник:** Да — для поведения команды `deploy-guest`, построения плана, применения изменений VM/LXC, безопасного повторного запуска и проверки результата.

Формат `guest.yaml`, общих настроек и итогового требуемого состояния определяет [`30-guest-manifest.md`](30-guest-manifest.md). Права API Proxmox определяет [`25-pve-access-control.md`](25-pve-access-control.md). Модель запуска `root` → `pvedeploy` описана в [`26-deploy-guest-and-agent-access.md`](26-deploy-guest-and-agent-access.md). Начальный SSH-доступ и границу дальнейшей настройки определяет [`33-guest-bootstrap-and-provisioning.md`](33-guest-bootstrap-and-provisioning.md).

## 1. Назначение

`deploy-guest` — средство на стороне PVE-хоста для детерминированного приведения одной VM/LXC к требуемому состоянию, описанному в Git.

Базовая цепочка:

```text
guests/defaults.yaml
+
profile
+
guests/<VMID>-<name>/guest.yaml
+
детерминированные правила проекта
        ↓
scripts/guest_config.py
        ↓
итоговое требуемое состояние
        ↓
фактическое состояние Proxmox
        ↓
ПЛАН
        ↓
--apply ?
        ↓
ПРИМЕНЕНИЕ
        ↓
проверка Proxmox
        ↓
проверка административного SSH, если гость должен работать
```

Команда не является универсальным средством управления конфигурацией Linux.

## 2. Граница ответственности

Первая версия `deploy-guest` отвечает за:

- поиск и проверку манифеста;
- построение итогового требуемого состояния через `scripts/guest_config.py`;
- чтение фактического состояния Proxmox;
- создание новой VM или LXC;
- приведение поддерживаемых параметров существующего управляемого объекта;
- первоначальную установку открытого SSH-ключа PVE при создании объекта;
- запуск гостевой системы, если это требуется политикой запуска;
- проверку фактической конфигурации PVE;
- проверку SSH `root` для гостя, который после применения должен работать;
- безопасный повторный запуск после ошибки.

Первая версия **не** отвечает за:

- установку прикладных сервисов;
- применение `rootfs/`;
- повторяемую настройку через Ansible;
- будущие `bootstrap.capabilities` и `provisioning.capabilities`;
- удаление VM/LXC;
- автоматическое пересоздание VM/LXC;
- автоматическое принятие под управление существующего чужого объекта;
- уменьшение дисков;
- автоматический перенос дисков между хранилищами;
- массовую миграцию сети;
- автоматическую перезагрузку уже работающей гостевой системы ради изменения конфигурации.

## 3. Интерфейс командной строки

Основной интерфейс первой версии:

```bash
deploy-guest <VMID>
deploy-guest <VMID> --apply
```

Пример:

```bash
deploy-guest 311
deploy-guest 311 --apply
```

Без `--apply` команда только читает данные, выполняет проверки и строит план. Она не должна выполнять ни одного изменяющего вызова API Proxmox и не должна изменять конфигурацию гостевой системы.

С `--apply` сначала строится тот же полный план. Изменения начинаются только после успешного завершения всех предварительных проверок и подтверждения, что в плане нет запрещённых или неоднозначных действий.

В первой версии отсутствуют `--force`, `--delete`, `--recreate`, `--adopt` и другие параметры, позволяющие обходить защитные проверки.

## 4. Источники данных

### 4.1. Требуемое состояние

Единственный источник параметров VM/LXC:

```text
guests/defaults.yaml
+
profile
+
guests/<VMID>-<name>/guest.yaml
+
scripts/guest_config.py
```

Python-код `deploy-guest` не должен содержать параллельный набор значений по умолчанию для CPU, RAM, диска, сети, пула, хранилища или источника гостевой системы.

### 4.2. Локальная конфигурация PVE

Используется:

```text
/etc/proxmox-deployer/config.yaml
```

Этот файл содержит параметры самого контура развёртывания и не подменяет `guest.yaml`.

### 4.3. API-токен

Используется:

```text
/etc/proxmox-deployer/secrets/host-deploy.token
```

Ожидаемый формат:

```text
token_id=deployer@pve!host-deploy
token_secret=<secret>
```

Секрет никогда не выводится в терминал или журнал.

### 4.4. SSH-ключ PVE

Используется постоянная пара:

```text
/etc/proxmox-deployer/ssh/pve_guest_ed25519
/etc/proxmox-deployer/ssh/pve_guest_ed25519.pub
```

`deploy-guest` не создаёт и не меняет эту пару автоматически.

## 5. Ревизия исходного кода

Root-обёртка `/usr/local/sbin/deploy-guest` до запуска Python-кода:

```text
берёт общую блокировку
→ проверяет доверенную основную копию Git
→ получает актуальную ревизию ветки
→ фиксирует точный Git SHA
→ запускает scripts/pve/deploy-guest.py от pvedeploy
```

Python-код получает SHA через:

```text
DEPLOY_GUEST_SOURCE_REVISION
```

Он обязан убедиться, что значение является корректным SHA и соответствует реально выполняемой основной копии проекта.

Один запуск работает только с одной Git-ревизией.

## 6. Обязательные предварительные проверки

До первого изменяющего вызова API должны успешно завершиться все проверки.

Минимальный набор:

1. VMID передан в допустимом формате;
2. для VMID найден ровно один каталог `guests/<VMID>-<name>/`;
3. `guest.yaml` существует;
4. каталог и `vmid`/`name` в манифесте согласованы;
5. `deployable: true`;
6. весь репозиторий проходит `scripts/validate_repo.py`;
7. итоговое состояние успешно строится через `scripts/guest_config.py`;
8. итоговое состояние проходит действующие требования схемы;
9. Git SHA текущего запуска подтверждён;
10. `config.yaml` читается;
11. API-токен читается и имеет ожидаемый идентификатор `deployer@pve!host-deploy`;
12. закрытый и открытый SSH-ключи PVE существуют и согласованы;
13. Proxmox API доступен;
14. целевой PVE node существует;
15. нужный bridge существует и разрешён текущей моделью PVE;
16. нужное хранилище существует и доступно;
17. требуемый pool существует, если он задан;
18. источник создания VM/LXC существует;
19. фактический VMID не находится в неоднозначном состоянии;
20. весь план может быть применён первой версией без запрещённых действий.

Ошибка любой предварительной проверки означает остановку **до изменений PVE**.

## 7. Доступ к Proxmox API

Основной `scripts/pve/deploy-guest.py`, выполняемый от `pvedeploy`, работает с Proxmox через HTTPS API от имени:

```text
deployer@pve!host-deploy
```

Использование `qm`, `pct`, `pvesh` или другого локального root-обхода модели RBAC в основной логике `deploy-guest.py` запрещено.

Для одновузловой первой версии адрес API строится из целевого node:

```text
https://<node>:8006/api2/json
```

Проверка сертификата обязательна. Доверенным корнем локального PVE является:

```text
/etc/pve/pve-root-ca.pem
```

Отключение проверки TLS (`verify=false`, `CERT_NONE` и аналоги) запрещено.

Для API-токена используется заголовок авторизации Proxmox. CSRF-токен для API-токена не требуется.

Первая версия работает только с локальным PVE node, на котором запущен `deploy-guest`. Автоматическая миграция объекта между узлами кластера не входит в контракт.

## 8. Асинхронные задачи Proxmox

Изменяющая операция Proxmox может вернуть UPID асинхронной задачи.

В этом случае `deploy-guest` обязан:

```text
получить UPID
→ дождаться завершения задачи
→ прочитать итоговый exitstatus
→ продолжить только при успешном результате
```

Следующий зависимый шаг нельзя начинать только потому, что API принял запрос.

При истечении времени ожидания или неуспешном `exitstatus`:

- текущий запуск останавливается;
- UPID записывается в журнал;
- автоматическая разрушительная очистка не выполняется;
- следующий запуск заново читает фактическое состояние PVE.

Таймауты должны быть конечными и различаться для коротких операций и длительного создания/клонирования.

## 9. Поиск фактического объекта

По VMID программа сначала определяет:

```text
объект отсутствует
объект является VM
объект является LXC
узел, на котором находится объект
текущее состояние running/stopped
текущий pool
текущую конфигурацию объекта
```

Наличие VMID само по себе не означает, что объект принадлежит проекту.

Если существующий тип не совпадает с требуемым:

```text
VM существует, требуется LXC
или
LXC существует, требуется VM
→ STOP
```

Автоматического пересоздания нет.

## 10. Маркер управляемого объекта

Каждый объект, созданный `deploy-guest`, получает зарезервированный тег:

```text
proxmox-deployer
```

Также его `description` начинается детерминированным служебным блоком:

```text
managed-by=proxmox-deployer
source-repo=zsergeyru/proxmox
manifest=guests/<VMID>-<name>/guest.yaml

<description из guest.yaml>
```

`deploy-guest` владеет этим служебным блоком и описанием, полученным из `guest.yaml`. Ручные эксплуатационные заметки для управляемого объекта должны храниться в Git, а не дописываться внутрь управляемой части `description` Proxmox.

Для объекта, создание или применение которого ещё не завершено успешно, дополнительно используется зарезервированный тег:

```text
deploy-incomplete
```

Программа изменяет только свои зарезервированные теги и не удаляет другие существующие теги Proxmox.

### 10.1. Существующий объект

```text
VMID существует
+ тег proxmox-deployer присутствует
+ служебный блок description соответствует этому manifest
→ объект считается управляемым этим проектом
```

Если VMID существует, но маркер отсутствует, неполон или указывает на другой manifest:

```text
→ STOP
```

Первая версия не выполняет автоматическое принятие такого объекта под управление.

## 11. Незавершённое развёртывание

После создания нового VMID программа как можно раньше закрепляет:

```text
proxmox-deployer
deploy-incomplete
служебный блок description
```

Тег `deploy-incomplete` удаляется только после полного успешного применения и обязательных проверок результата.

Если следующий запуск обнаруживает:

```text
proxmox-deployer + deploy-incomplete
```

он не удаляет объект. Он заново читает его фактическое состояние и:

- продолжает только те действия, которые однозначно безопасны и соответствуют текущему плану;
- останавливается, если состояние неоднозначно;
- никогда не уничтожает остаток автоматически.

Если сбой произошёл между выделением VMID и записью маркера, следующий запуск увидит существующий немаркированный объект и остановится для ручной проверки.

## 12. Построение плана

План всегда строится до применения.

Основные итоговые состояния плана:

```text
CREATE
UPDATE
NO CHANGE
BLOCKED
```

Каждое отличие существующего объекта классифицируется как:

```text
ONLINE
→ можно применить без остановки работающего объекта

REQUIRES-STOP
→ можно применить только к остановленному объекту

FORBIDDEN
→ первая версия не имеет права выполнять изменение автоматически
```

Если хотя бы один пункт имеет `FORBIDDEN`, общий план считается `BLOCKED`.

Если работающий объект требует хотя бы одного `REQUIRES-STOP`, общий план также считается `BLOCKED` для первой версии. `deploy-guest` не останавливает и не перезагружает уже работающий существующий объект автоматически.

При `BLOCKED` режим `--apply` завершается **до любого изменения**, даже если в том же плане присутствуют безопасные `ONLINE`-действия.

## 13. Представление плана

Для нового объекта вывод должен содержать как минимум:

```text
Guest
Type
Action
Node
Pool
Storage
Source
CPU
Memory
Swap, если применимо
Disk
Bridge
IPv4
Gateway
On boot
Start after deploy
SSH user
SSH key
Git revision
```

Для существующего объекта каждое отличие выводится как:

```text
параметр
текущее значение
требуемое значение
класс действия
```

Пример:

```text
Memory
  current: 2048 MiB
  desired: 4096 MiB
  action: REQUIRES-STOP

Disk
  current: 20 GiB
  desired: 32 GiB
  action: ONLINE
```

Происхождение требуемых значений по возможности показывается в терминах, принятых в [`30-guest-manifest.md`](30-guest-manifest.md): общие настройки, профиль, манифест, VMID или фактическое состояние PVE.

## 14. Создание VM

Для VM используется только источник из итогового состояния:

```text
vm.source.template_vmid
vm.source.clone=full
```

Первая версия поддерживает только Full Clone.

Последовательность создания:

```text
проверить исходный шаблон
→ создать Full Clone с целевым VMID и именем
→ установить маркер проекта и deploy-incomplete
→ настроить CPU/RAM/диск
→ настроить bridge и Cloud-Init IPv4/gateway
→ установить ciuser=root
→ передать pve_guest_ed25519.pub
→ применить onboot/pool/protection
→ обновить Cloud-Init
→ выполнить итоговую проверку конфигурации до первого запуска
→ запустить, если start_after_deploy=true
→ дождаться готовности
→ проверить SSH root
→ повторно сверить конфигурацию PVE
→ удалить deploy-incomplete
```

Все параметры, которые могут и должны быть заданы до первого запуска, задаются до первого запуска.

Закрытый SSH-ключ через Cloud-Init не передаётся.

## 15. Создание LXC

`lxc.source.ostemplate` задаёт семейство образа, а не конкретный архив.

`deploy-guest`:

```text
читает selector семейства
→ получает список установленных архивов разрешённого хранилища
→ выбирает наиболее новую доступную подходящую версию
→ фиксирует разрешённый архив в плане текущего запуска
```

Если подходящего архива нет:

```text
→ STOP до создания LXC
```

`deploy-guest` не скачивает LXC-образ самостоятельно. Подготовка образа является ответственностью PVE Configuration.

Последовательность создания LXC:

```text
выбрать конкретный установленный архив
→ создать LXC с целевым VMID
→ сразу передать pve_guest_ed25519.pub через ssh-public-keys
→ установить маркер проекта и deploy-incomplete
→ настроить ресурсы, features, storage и сеть
→ применить onboot/pool/protection
→ проверить конфигурацию до запуска
→ запустить, если start_after_deploy=true
→ проверить SSH root
→ повторно сверить конфигурацию PVE
→ удалить deploy-incomplete
```

## 16. Начальные SSH-ключи

Первая версия при **создании** VM/LXC гарантированно устанавливает только:

```text
pve_guest_ed25519.pub
```

Добавление открытых ключей AI Control, Ansible и других контуров будет реализовано отдельным согласованным механизмом и не должно появляться в `deploy-guest.py` как скрытая логика.

Для уже существующего управляемого объекта `deploy-guest` не переписывает автоматически `authorized_keys` и не выполняет скрытую смену административных ключей.

Если существующий объект должен быть доступен по SSH, но `pve_guest_ed25519` не работает:

```text
→ STOP
```

Исправление или смена ключа выполняется отдельной операцией восстановления.

## 17. CPU и память

Для нового объекта CPU и память задаются до первого запуска.

Для существующего **остановленного** объекта поддерживаемые параметры CPU/RAM могут быть приведены к требуемому состоянию.

Для существующего **работающего** объекта изменение CPU/RAM первой версией считается `REQUIRES-STOP`, даже если конкретная конфигурация Proxmox теоретически допускает горячее изменение.

Это исключает зависимость базового контракта от индивидуальной настройки hotplug конкретной VM/LXC.

## 18. Диски

Основное правило:

```text
desired > current
→ увеличение разрешено

desired == current
→ изменений нет

desired < current
→ FORBIDDEN / STOP
```

Автоматическое уменьшение диска запрещено.

Если текущее хранилище диска отличается от требуемого:

```text
→ FORBIDDEN / STOP
```

Автоматический перенос диска между хранилищами в первую версию не входит.

`deploy-guest` отвечает за размер виртуального диска или тома на уровне PVE. Расширение файловой системы внутри уже работающей обычной VM не становится скрытой обязанностью средства развёртывания; это отдельная задача гостевой ОС/Ansible, если она требуется.

## 19. Сеть

Для нового объекта сеть задаётся до первого запуска.

Для существующего остановленного объекта поддерживаются изменения параметров, которые однозначно отображаются из итогового требуемого состояния:

```text
bridge
IPv4/prefix
gateway
```

Для работающего существующего объекта изменение сети считается `REQUIRES-STOP`.

Первая версия не реализует двухадресную сетевую миграцию и не добавляет временный второй IP.

Массовая миграция центральной подсети выполняется отдельным инструментом/режимом согласно [`30-guest-manifest.md`](30-guest-manifest.md), а не скрыто внутри обычного `deploy-guest <VMID>`.

## 20. Pool, protection и onboot

Эти параметры относятся к требуемому состоянию PVE и могут применяться к существующему объекту без автоматической перезагрузки, если API Proxmox допускает операцию в текущем состоянии.

`deploy-guest` не использует pool как признак SSH-доступа. Членство в `managed` и открытые SSH-ключи — независимые механизмы.

Изменение `protection` не используется для обхода запрета удаления: первая версия `deploy-guest` в любом случае не удаляет гостевые системы.

## 21. Имя и тип объекта

`vmid` и `name` являются частью идентичности управляемого объекта.

Если существующий управляемый объект имеет другой тип:

```text
→ FORBIDDEN / STOP
```

Если служебный `manifest=` указывает на другой каталог или имя не согласуется с ожидаемым объектом:

```text
→ STOP
```

Автоматическое переименование уже существующего объекта в первой версии не выполняется. Оно должно быть отдельным осознанным изменением/миграцией.

## 22. Семантика `state`

Поле:

```yaml
state: planned | active | bootstrap | legacy
```

описывает жизненную стадию объекта и само по себе **не является командой** `deploy-guest`.

Возможность применения определяется прежде всего:

```yaml
deployable: true
```

Поэтому сочетание:

```yaml
state: planned
deployable: true
```

разрешает создание объекта.

`bootstrap` и `legacy` при `deployable: true` не превращаются автоматически в удаление или пересоздание. Проверяющий скрипт может выдавать предупреждение, а `deploy-guest` показывает состояние в плане.

## 23. `start_after_deploy`

Поле:

```yaml
boot:
  start_after_deploy: true|false
```

определяет, должен ли `deploy-guest` **запустить остановленный объект после успешного применения**.

Оно не является требованием постоянно держать объект в состоянии `running` и не означает автоматическую остановку уже работающего объекта при `false`.

Правила:

```text
true + объект stopped после применения
→ запустить

true + объект уже running
→ не перезапускать только ради этого поля

false + объект stopped
→ оставить stopped

false + объект running
→ не останавливать
```

## 24. Готовность и SSH-проверка

Если после применения объект должен работать (`start_after_deploy=true`) либо уже был запущен до применения, успешное завершение требует проверки административного SSH:

```text
user=root
port=22
key=/etc/proxmox-deployer/ssh/pve_guest_ed25519
```

Для новой VM до SSH-проверки при необходимости ожидаются QEMU Guest Agent и завершение Cloud-Init в пределах конечного таймаута.

Для LXC ожидается запуск контейнера и доступность SSH.

Если объект согласно правилам остаётся остановленным, SSH-проверка не выполняется и это явно отражается в результате.

## 25. Проверка SSH host key

Глобальное отключение проверки SSH host key запрещено.

Для гостевых систем используется отдельное постоянное хранилище известных SSH-ключей `pvedeploy`, независимое от root-only `known_hosts` GitHub.

Целевая область:

```text
/var/lib/pvedeploy/.ssh/known_hosts
```

Для **нового** объекта допускается первичное принятие нового host key только для вычисленного административного адреса текущего VMID. После принятия реальное соединение обязательно повторяется со строгой проверкой ключа.

Для уже известного управляемого объекта неожиданное изменение SSH host key означает:

```text
→ STOP
```

Автоматическое удаление старой записи и принятие нового ключа для существующего объекта запрещено.

Потеря локальной базы известных ключей не должна приводить к молчаливому доверию всем существующим гостям: повторное принятие выполняется отдельной осознанной операцией или через подтверждённый сценарий восстановления.

## 26. Применение изменений

Общий порядок `--apply`:

```text
1. выполнить все предварительные проверки
2. получить фактическое состояние
3. построить полный план
4. убедиться, что план не BLOCKED
5. создать объект, если он отсутствует
6. установить маркер проекта и deploy-incomplete
7. применить placement/pool и поддерживаемые параметры
8. применить CPU/RAM
9. увеличить диск, если требуется
10. применить сеть
11. применить Cloud-Init/начальный SSH для нового объекта
12. применить onboot/protection
13. проверить конфигурацию до запуска
14. запустить, если это требуется
15. дождаться готовности
16. проверить SSH root, если гость должен работать
17. повторно прочитать и сверить состояние PVE
18. удалить deploy-incomplete
19. записать успешный итог в журнал
```

Реальный порядок отдельных независимых API-вызовов может быть оптимизирован реализацией, но обязательные зависимости и принцип «всё возможное до первого запуска» сохраняются.

## 27. Ошибка при создании

Если VM/LXC уже создана, но последующий шаг завершился ошибкой:

```text
→ объект НЕ удалять автоматически
→ deploy-incomplete оставить
→ записать последнюю подтверждённую операцию и ошибку
→ завершиться с ошибкой
```

Это относится и к прерыванию процесса.

Следующий запуск выполняет новую сверку с PVE, а не продолжает слепо с номера последнего шага.

## 28. Ошибка при изменении существующего объекта

Полный автоматический откат всех уже применённых изменений не обещается.

Используется модель:

```text
выполнить один шаг
→ дождаться завершения
→ проверить результат
→ только затем следующий шаг
```

При ошибке:

```text
→ STOP
→ не выполнять следующие действия
→ не пытаться разрушительно вернуть прошлое состояние
→ следующий запуск заново строит план из фактического состояния
```

Именно поэтому план должен быть полностью проверен на запрещённые действия **до** первого изменения.

## 29. Проверка результата

Успех не определяется только успешным HTTP-ответом.

После применения программа повторно читает PVE и проверяет поддерживаемые параметры требуемого состояния.

Минимально сверяются:

- VMID и тип;
- node;
- имя;
- маркер проекта;
- pool;
- CPU/RAM;
- размер диска на уровне PVE;
- bridge и требуемые сетевые параметры;
- onboot;
- protection;
- источник первоначального создания в той части, где его можно однозначно подтвердить для нового объекта;
- отсутствие `deploy-incomplete` после успеха.

Для работающей управляемой Debian VM/LXC дополнительно проверяется SSH `root` по ключу PVE.

Только после всех обязательных проверок запуск считается успешным.

## 30. NO CHANGE

Если фактическое поддерживаемое состояние уже соответствует требуемому:

```text
Action: NO CHANGE
```

Без `--apply` команда выводит план и завершается успешно.

С `--apply` изменяющие вызовы API не выполняются, но разрешены повторные проверки доступности и SSH, если они являются частью обязательной приёмки текущего объекта.

Повторный запуск корректно развёрнутого объекта должен быть штатным сценарием.

## 31. Удаление и пересоздание

Первая версия `deploy-guest` не удаляет VM/LXC ни при каких значениях `state`.

Отсутствие манифеста в Git, `state: legacy`, конфликт типа, неправильный источник или несовместимое состояние не являются разрешением на `destroy`.

Удаление, пересоздание и принятие существующего объекта под управление проектируются как отдельные осознанные операции с собственными защитными правилами.

## 32. Журнал аудита

Каждый запуск создаёт отдельный журнал в:

```text
/var/log/proxmox-deployer/audit/
```

Журнал должен позволять установить как минимум:

```text
дата/время
VMID и имя
режим PLAN или APPLY
Git SHA
путь manifest
итоговое требуемое состояние без секретов
фактическое исходное состояние в необходимом объёме
полный план
выполненные изменяющие действия
UPID задач Proxmox
результаты проверок
SUCCESS / FAILED / BLOCKED
```

В журнал запрещено записывать:

- `token_secret`;
- закрытый SSH-ключ;
- полный набор переменных окружения;
- другие секреты.

Вывод в терминал и постоянный журнал используют одни и те же смысловые этапы, но журнал не обязан содержать ANSI-оформление терминала.

## 33. Коды завершения

Первая версия использует небольшой стабильный набор:

```text
0  план успешно построен или применение полностью успешно
1  ошибка конфигурации, схемы, репозитория или предварительной проверки
2  неоднозначное/запрещённое состояние; план BLOCKED
3  ошибка Proxmox API или асинхронной задачи
4  ошибка готовности гостя, QGA/Cloud-Init или SSH-проверки
```

Неожиданная внутренняя ошибка также не должна маскироваться как успех и может завершаться общим ненулевым кодом с диагностикой без секретов.

## 34. Зависимости реализации

`deploy-guest.py` должен переиспользовать:

```text
scripts/guest_config.py
scripts/validate_repo.py
```

и не реализовывать второй набор правил объединения манифеста.

PVE-хост обязан иметь Python-зависимости, необходимые действующему проверяющему скрипту, включая `PyYAML` и `jsonschema`.

HTTP-клиент первой версии должен сохранять обязательную проверку TLS. Выбор стандартной библиотеки Python или отдельной библиотеки не должен менять API-контракт документа.

## 35. Требования к тестам

Реализация `deploy-guest.py` сопровождается модульными тестами как минимум на:

- поиск манифеста по VMID;
- `deployable: false`;
- создание плана новой VM;
- создание плана нового LXC;
- выбор конкретного установленного LXC-архива;
- отсутствие подходящего LXC-архива;
- отсутствие шаблона VM;
- существующий корректно управляемый объект;
- существующий чужой/немаркированный VMID;
- неправильный `manifest=` в маркере;
- VM вместо LXC и LXC вместо VM;
- `NO CHANGE`;
- увеличение диска;
- попытку уменьшения диска;
- смену хранилища;
- изменение сети работающего объекта;
- изменение CPU/RAM работающего объекта;
- остановленный объект с изменяемой конфигурацией;
- частично созданный объект с `deploy-incomplete`;
- ошибку Proxmox API;
- неуспешный UPID;
- таймаут задачи;
- ошибку SSH;
- неожиданную смену SSH host key;
- отсутствие секретов в журнале;
- повторный запуск после частичного применения.

Отдельная обязательная проверка:

> В режиме PLAN код технически не должен иметь возможность выполнить изменяющий API-запрос.

Тест должен перехватывать API-вызовы и завершаться ошибкой, если без `--apply` предпринимается POST/PUT/DELETE или другое изменение PVE.

## 36. Что сознательно остаётся за пределами первой версии

```text
удаление VM/LXC
пересоздание
--force
--adopt
уменьшение диска
перенос диска между хранилищами
автоматическая миграция между PVE nodes
автоматический stop/reboot уже работающего существующего объекта
массовая миграция сети
двойной временный IP
управление authorized_keys существующего гостя
rootfs sync
Ansible provisioning
bootstrap.capabilities
provisioning.capabilities
управление AI через deploy-guest
```

Расширение этого списка требует изменения спецификации и тестов до изменения поведения программы.

## 37. Итоговый контракт

```text
root-обёртка
→ доверенная Git-ревизия
→ pvedeploy
→ validate_repo.py
→ guest_config.py
→ итоговое требуемое состояние
→ HTTPS Proxmox API как deployer@pve!host-deploy
→ фактическое состояние
→ безопасный PLAN
→ --apply только если весь план допустим
→ пошаговое применение с ожиданием UPID
→ проверка PVE
→ проверка SSH при работающем госте
→ SUCCESS
```

Главные правила:

1. **PLAN ничего не меняет.**
2. **Неоднозначный VMID не трогается.**
3. **Чужой объект автоматически не принимается под управление.**
4. **Удаление и пересоздание не входят в первую версию.**
5. **Диск можно только увеличивать.**
6. **Работающий существующий объект автоматически не перезапускается.**
7. **Ошибка не вызывает разрушительную автоматическую очистку.**
8. **Каждый изменяющий шаг подтверждается результатом Proxmox до следующего шага.**
9. **Успех означает подтверждённое итоговое состояние, а не только принятый API-запрос.**
10. **Основная логика работает с PVE только через ограниченную учётную запись `deployer@pve!host-deploy`.**
