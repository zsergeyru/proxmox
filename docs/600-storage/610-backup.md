# Политика резервного копирования

**Тип:** политика  
**Статус:** проектируется  
**Назначение:** определить единый объект резервного копирования Linux-гостей и правила для данных, которые не входят в этот объект.

## 1. Основной принцип

Для каждого обычного управляемого Linux-гостя стандартным объектом резервного копирования является один и тот же путь:

```text
/var/lib/persistent/
```

Имя гостя, VMID и перечень сервисов не входят в правило резервного копирования.

Система резервного копирования должна уметь применить одинаковую операцию к любому гостю:

```text
подключиться к гостю
→ сохранить /var/lib/persistent/
→ проверить результат
```

## 2. Что должно находиться в стандартной копии

Под `/var/lib/persistent/` размещаются все невоспроизводимые постоянные данные проекта, потеря которых не должна требовать ручного восстановления из работающей системы.

К ним относятся:

- базы и внутреннее состояние приложений;
- OpenTofu state;
- состояние OpenBao;
- состояние Semaphore, если требуется его сохранение;
- постоянное состояние AI-агентов;
- локальные секреты, которые нельзя безопасно перевыпустить;
- другие уникальные данные конкретного гостя.

Каждый сервис использует собственный подкаталог.

## 3. Что не входит в стандартную копию

Обычно не резервируются:

- `/opt` — воспроизводится из Git, пакетов или образов;
- воспроизводимая часть `/etc` — восстанавливается Ansible;
- `/var/log` — если для журналов не задана отдельная политика;
- `/var/cache`;
- `/run`;
- `/tmp` и `/var/tmp`;
- рабочая копия Git;
- Docker-образы и другой пересоздаваемый кэш.

Критичный невоспроизводимый файл не должен оставаться исключением в одном из этих каталогов. Его необходимо либо сделать воспроизводимым, либо перенести сохраняемую часть под `/var/lib/persistent/`.

## 4. Крупные данные

Крупные данные, для которых обычная резервная копия постоянного состояния не подходит, могут храниться в `/srv` или на отдельном диске/хранилище.

Для них обязательно отдельно определить одно из состояний:

- резервируются отдельным заданием;
- сохраняются внешней системой;
- допускается их потеря и резервная копия не требуется.

Примером могут быть длительные видеозаписи Frigate.

## 5. Docker

Постоянные данные проектных Docker-контейнеров должны быть доступны из `/var/lib/persistent/`.

Предпочтительный вариант:

```text
/var/lib/persistent/<service>
→ bind mount
→ штатный каталог данных внутри контейнера
```

Анонимный или именованный Docker volume не должен быть единственным местом хранения критичных данных, если он не включён в тот же единый механизм резервного копирования.

## 6. Восстановление

Обычный порядок восстановления Linux-гостя:

```text
Git + OpenTofu
→ создать объект VM/LXC

Git + Ansible
→ восстановить ОС, пакеты и конфигурацию

резервная копия
→ восстановить /var/lib/persistent/

отдельные копии
→ восстановить /srv или другие крупные данные, если они используются
```

Таким образом резервная копия не заменяет Git, а Git не заменяет резервную копию невоспроизводимого состояния.

## 7. Следующие решения

Отдельно должны быть определены:

- место хранения резервных копий;
- периодичность;
- срок хранения;
- число поколений;
- шифрование;
- проверка восстановления;
- политика резервного копирования самого PVE и bootstrap-state 910.
