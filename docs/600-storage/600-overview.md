# Обзор хранения данных

**Тип:** обзор  
**Статус:** действующий  
**Назначение:** описать виды данных проекта, места их хранения, различие между воспроизводимыми и невоспроизводимыми данными и границы ответственности.

Этот документ отвечает на вопрос:

> Какие данные существуют в проекте, где они хранятся и какие из них требуют отдельного сохранения?

## 1. Назначение и границы

### 1.1. Что описывает документ

Раздел хранения определяет общую модель размещения данных проекта.

Он нужен для того, чтобы было понятно:

- какие данные являются частью требуемого состояния;
- какие данные возникают во время работы систем;
- где должны храниться разные виды данных;
- какие данные можно восстановить из проекта;
- какие данные требуют отдельного сохранения;
- где заканчивается ответственность хранения и начинается резервное копирование или восстановление.

Основной принцип:

> способ защиты данных зависит прежде всего от их назначения и возможности воспроизведения, а не только от того, на каком диске они находятся.

### 1.2. Что находится в других документах

Этот документ не описывает:

- периодичность и сроки хранения резервных копий;
- допустимую потерю данных и допустимое время восстановления;
- конкретные задания резервного копирования;
- пошаговый порядок восстановления;
- точные пути и параметры подключения хранилищ PVE;
- размеры дисков отдельных VM/LXC.

Политика резервного копирования относится к `610-backup.md`.

Причины ключевых решений по хранению относятся к `690-decisions.md`.

Пошаговое восстановление относится к разделу эксплуатации.

Конкретные параметры дисков отдельной VM/LXC относятся к документации этой гостевой системы.

## 2. Виды данных

### 2.1. Требуемое состояние

Требуемое состояние описывает, каким проект должен быть.

К нему относятся, например:

- документация;
- `guest.yaml`;
- общие параметры гостевых систем;
- сценарии и программы проекта;
- настройки Ansible;
- управляемые файлы из `rootfs/`;
- шаблоны конфигурации;
- другие версионируемые правила проекта.

Основным местом хранения такого состояния является Git.

Требуемое состояние не должно зависеть только от файлов, существующих внутри работающей VM/LXC или на одном конкретном PVE-хосте.

### 2.2. Рабочие данные

Рабочие данные возникают или изменяются во время обычной работы сервисов.

Примеры:

- базы данных;
- состояние Home Assistant;
- файлы приложений;
- данные контейнеров;
- пользовательские документы;
- записи и изображения систем наблюдения;
- иные данные, которые невозможно однозначно получить заново только из конфигурации проекта.

Рабочие данные являются фактическим состоянием и обычно требуют отдельной защиты.

### 2.3. Служебное состояние

Служебное состояние необходимо для работы средств управления, но не является обычными пользовательскими данными.

К нему могут относиться:

- реестры открытых ключей;
- данные доверия;
- локальные признаки завершённых операций;
- служебные сведения средств автоматизации;
- состояние, необходимое для безопасного повторного выполнения операций.

Для каждого такого вида данных должно быть понятно, можно ли его восстановить автоматически или он требует отдельного сохранения.

### 2.4. Секреты и учётные данные

К этой группе относятся:

- закрытые ключи;
- токены;
- пароли;
- другие данные, предоставляющие доступ к системам.

Они не должны храниться в открытом виде в Git.

Место хранения и жизненный цикл таких данных определяются правилами безопасности.

Если потеря конкретного секрета требует сложной смены ключей, токенов или доверия, его сохранность должна учитываться отдельно при планировании восстановления.

### 2.5. Временные данные

Временные данные нужны только для текущей работы и могут быть получены заново.

Например:

- кэш;
- временные файлы;
- промежуточные результаты выполнения;
- загруженные установочные файлы, которые можно повторно получить;
- краткоживущие рабочие данные.

Такие данные обычно не требуют резервного копирования.

Журналы относятся к временным данным только тогда, когда их потеря допустима. Если журналы нужны для аудита или расследования, для них должен быть определён отдельный срок хранения.

## 3. Размещение данных

### 3.1. Git

Git используется для хранения воспроизводимого и версионируемого состояния проекта.

В нём могут находиться:

- документация;
- манифесты;
- сценарии;
- настройки;
- управляемые файлы;
- шаблоны;
- исходный код.

Git не используется для хранения:

- действующих секретов;
- рабочих баз данных;
- виртуальных дисков;
- резервных копий;
- постоянно изменяемого состояния приложений.

### 3.2. Хранилища PVE

Хранилища Proxmox используются для размещения объектов уровня виртуализации.

К ним относятся:

- виртуальные диски VM;
- корневые файловые системы LXC;
- дополнительные виртуальные диски;
- образы и шаблоны, необходимые Proxmox;
- другие объекты, которыми управляет PVE.

Общая цепочка выглядит так:

```text
физическое устройство хранения
↓
хранилище PVE
↓
виртуальный диск или корневая файловая система LXC
↓
файловая система гостевой системы
↓
данные приложения
```

PVE управляет диском как объектом виртуализации, но не обязан понимать назначение каждого файла внутри гостевой системы.

### 3.3. Гостевые системы

Внутри VM/LXC находятся:

- операционная система;
- системная конфигурация;
- приложения;
- данные приложений;
- локальные журналы;
- временные данные.

Часть файлов внутри гостя может быть воспроизводимой из Git и Ansible.

Например, файл, поставляемый из `rootfs/`, не является уникальным рабочим данным только потому, что физически находится внутри виртуального диска.

В то же время база данных или изменяемые данные приложения внутри того же диска могут быть невоспроизводимыми и требовать резервного копирования.

### 3.4. Единый корень постоянных данных Linux-гостя

Для обычных управляемых Linux-гостей проект использует единый физический корень невоспроизводимых постоянных данных:

```text
/var/lib/persistent/
```

Это правило специально не включает VMID или имя гостя в путь: сама VM/LXC уже является границей данных.

Внутри корня каждый сервис использует собственный подкаталог, например:

```text
/var/lib/persistent/
├── semaphore/
├── opentofu/
└── openbao/
```

Приложение может продолжать видеть свой штатный путь. Для контейнеров и других управляемых приложений допускается bind mount или эквивалентная настройка из `/var/lib/persistent/` в ожидаемый приложением каталог.

Стандартная система резервного копирования Linux-гостя должна уметь работать без знания внутреннего состава сервисов:

```text
гость
→ резервировать /var/lib/persistent/
```

Каталог `/srv` используется только для крупных или отдельно обслуживаемых данных и всегда требует собственной явно заданной политики резервирования.

### 3.5. Внешние хранилища

Внешние хранилища могут использоваться для данных, которые не должны зависеть от единственного системного диска PVE.

К таким задачам относятся прежде всего:

- хранение резервных копий;
- долговременное хранение данных;
- перенос данных между системами;
- хранение крупных наборов данных, если это предусмотрено архитектурой конкретного сервиса.

Конкретный тип внешнего хранилища и способ его подключения определяются профильной документацией.

### 3.6. Защищённые локальные данные

Некоторые данные по своей природе должны находиться локально на PVE или внутри конкретной гостевой системы, но не могут храниться в Git.

Например:

- закрытые ключи;
- локальные токены;
- защищённые данные доверия;
- отдельное служебное состояние.

Для таких данных должно быть заранее определено одно из двух:

1. они безопасно создаются заново;
2. они должны сохраняться и восстанавливаться отдельно.

Не должно существовать критичного локального файла, для которого неизвестно, как действовать при его потере.

## 4. Воспроизводимость и защита данных

### 4.1. Воспроизводимые данные

Данные считаются воспроизводимыми, если их можно однозначно получить заново из известных источников проекта.

Упрощённая схема:

```text
Git
+ Ansible
+ штатные средства развёртывания
→ требуемая конфигурация системы
```

Примеры воспроизводимых данных:

- управляемый конфигурационный файл;
- установленный через Ansible пакет;
- сценарий проекта;
- файл из `rootfs/`;
- конфигурация, которая полностью описана в Git.

Для таких данных главным средством защиты является сохранность нормативного источника и возможность повторного применения.

### 4.2. Невоспроизводимые рабочие данные

Данные считаются невоспроизводимыми, если после их потери проект не может однозначно создать то же содержимое заново.

Примеры:

- рабочая база данных;
- история автоматизации;
- пользовательские файлы;
- накопленные данные приложений;
- уникальные локальные ключи, если их потеря требует смены доверия.

Именно такие данные в первую очередь определяют требования к резервному копированию.

### 4.3. Снимок и резервная копия

Рабочее состояние, снимок и резервная копия имеют разное назначение.

```text
рабочий диск
≠
снимок
≠
независимая резервная копия
```

Снимок удобен для быстрого возврата к предыдущему состоянию, но обычно зависит от того же хранилища, где находится рабочая система.

Поэтому снимок сам по себе не считается заменой независимой резервной копии.

Подробные требования к резервным копиям определяются в `610-backup.md`.

### 4.4. Какие данные требуют отдельного сохранения

При определении необходимости резервного копирования нужно задавать вопрос:

> Можно ли восстановить эти данные только из нормативных источников проекта и штатной автоматизации?

Если да, отдельная резервная копия может быть необязательной.

Если нет, данные должны быть включены в план резервного копирования или иметь другой явно определённый способ восстановления.

Особое внимание требуется для:

- рабочих данных приложений;
- баз данных;
- уникальных секретов и ключей;
- служебного состояния, без которого невозможно безопасное продолжение работы;
- данных, восстановление которых вручную слишком сложно или ненадёжно.

## 5. Границы ответственности

### 5.1. Хранилища и рабочие данные

Раздел хранения определяет:

- виды данных;
- место их размещения;
- различие между воспроизводимыми и невоспроизводимыми данными;
- требования к разделению рабочего и сохраняемого состояния.

Конкретное подключение и настройка хранилищ на PVE относятся к документации PVE.

Конкретные диски и данные отдельной VM/LXC относятся к документации этой гостевой системы.

### 5.2. Резервное копирование

`610-backup.md` определяет:

- что именно резервируется;
- с какой периодичностью;
- сколько копий хранится;
- как долго они сохраняются;
- требования к допустимой потере данных;
- требования к допустимому времени восстановления;
- как проверяется пригодность резервных копий.

`600-overview.md` только определяет, какие виды данных существуют и почему часть из них требует резервного копирования.

### 5.3. Восстановление

Раздел хранения и политика резервного копирования определяют, какие данные должны быть доступны для восстановления.

Сам порядок действий при аварии относится к разделу эксплуатации.

Таким образом:

```text
600
→ какие данные существуют и где они хранятся

610
→ какие из них и как резервируются

830
→ как выполнять восстановление
```
