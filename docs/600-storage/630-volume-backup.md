# Универсальное резервирование постоянных томов PVE

**Тип:** спецификация  
**Статус:** принятое целевое состояние; механизм ещё не реализован и не проверен на рабочем PVE.  
**Назначение:** единый контракт резервирования LVM-томов с постоянными данными гостей, без отдельных заданий для каждого тома.

## 1. Границы и источники настроек

**910 Infra Manager** отвечает за расписание, контроллер, Restic, историю операций и интерфейс `infra-web`. **PVE** предоставляет штатные LVM/Proxmox и существующий защищённый SSH-доступ. Новые службы, таймеры, пакеты, Docker или второй исполнитель на PVE не устанавливаются. Приоритет — штатный Proxmox API, затем уже разрешённый SSH-контур; расширение существующего PVE-only помощника допускается только в минимально необходимых пределах. Иные исключения из правила минимального PVE требуют отдельного решения владельца.

| Источник | Ответственность |
|---|---|
| `infrastructure/hosts/pve/storage.yaml` | ID, размер, пул, файловая система, путь подключения существующего тома |
| `infrastructure/hosts/pve/backup.yaml` | Какие тома копировать, расписание, назначения, способ и сроки хранения |
| `infrastructure/guests/*/provision.yaml` | Подкаталоги и подключения гостя, `persistence.backup_required`, способ согласованного копирования приложения |
| Защищённое наблюдаемое состояние | Подтверждённые UUID/устройства, история и результаты операций; не подменяет описание из Git |

**Не путать** `infra_state` (общий LVM-том 40 ГиБ для данных 140 и 340) и защищённые области самого 910 `/mnt/bindmounts/infra-manager/{pve-only,access,state}`. Вторые продолжает сохранять отдельное задание `infra-core`. Системные диски LXC не включаются в резервирование постоянных томов автоматически: они воспроизводятся из Git.

## 2. Декларация резервируемых томов

Предлагаемое расширение **будущей версии схемы** `backup.yaml` (пример, **не действующая конфигурация**):

~~~yaml
volume_backups:
  defaults:
    enabled: true
    schedule: daily
    destinations: [fast-ssd, nas-backup]
    method: lvm_snapshot
  volumes:
    - id: infra_state
    - id: gogs_data
~~~

До реализации валидатора и исполнителя **не добавлять** этот раздел в рабочий `backup.yaml`. Расширение должно сопровождаться версионированием схемы. Параметры из `defaults` наследуются записями, допустимые переопределения отдельного тома проверяются по закрытому перечню. Используются существующие назначения и правила `retention` — второго списка носителей, размеров, секретов или ключей не создаём.

Для добавления **уже объявленного** нового тома достаточно добавить `- id: имя_тома` и указать необходимые требования согласованности его новых приложений в `provision.yaml`. Само появление в `storage.yaml` или `persistence.backup_required` **не включает** копирование. Повторные/неизвестные ID, неподтверждённый источник, неподдерживаемые файловая система или способ копирования запрещают запуск.

**Первый состав:** `infra_state` (40 ГиБ) и `gogs_data` (30 ГиБ), ежедневные копии на проверенный SSD и после готовности NAS. `photo_archive` (240 ГиБ) не добавляется автоматически: это отдельный большой набор с зависимостью от PostgreSQL Immich.

## 3. Создание копии

1. 910 сопоставляет включённые ID с `storage.yaml`, реальными LVM-объектами, UUID, файловыми системами, mount и `pve_storage.mounts` гостей. Папка без подтверждённого mount не является источником.
2. Проверяет свободное **физическое** место и метаданные thin-pool, прогнозируемый рост временного снимка, состояние служб, блокировки, объём данных и свободное место назначения. Номинальный размер тома не равен занимаемому месту.
3. Выполняет ограниченное по времени согласование **всех** приложений, которые пишут на том. При отсутствии поддерживаемой стратегии, отказе приложения или превышении времени — остановка с ошибкой, не создание «успешной» копии.
4. Создаёт **временный LVM-thin snapshot** строго выбранного рабочего тома. При необходимости кратковременно останавливает запись и сбрасывает буферы. Службы обязательно возвращаются к работе даже при сбое создания снимка; возобновление и ошибки проверяются.
5. Читает снимок **только для чтения** и передаёт данные потоком в Restic из 910. Не создаёт полную незашифрованную копию на системном диске PVE; сохраняет проверяемые владельцев, права, времена, ссылки и расширенные атрибуты. Snapshot сам по себе — ещё не резервная копия.
6. Для каждого подтверждённого назначения независимо проверяет завершение экспорта, Restic и выборочную целостность; отдельно фиксирует результат. Недоступность NAS не блокирует работающий SSD (и наоборот), но явно отмечается отсутствие второй копии. При отсутствии обоих назначений запись запрещена.
7. В любом исходе освобождает блокировки и удаляет **только собственный временный snapshot** по защищённому идентификатору операции. Чужие снимки и рабочие тома не трогает. Неочищенный снимок — отдельная критичная ошибка с безопасной повторной сверкой.

Задания томов выполняются последовательно с ограничениями по одновременной нагрузке thin-pool и совместимостью с `infra-core` и `deploy 910`. Резервирование никогда не форматирует, не пересоздаёт потерянные тома, не инициирует восстановление и не устанавливает программы на PVE.

## 4. Согласованность приложений

**LVM snapshot или `fsfreeze` без согласования приложения не гарантирует логически целую базу.** Исполнитель сопоставляет `pve_storage.mounts` с `persistence.backup_required` и выбирает только поддерживаемую кодом стратегию, объявляемую возле приложения в `provision.yaml`. Точные поля/значения этой новой части контракта добавить при реализации; не исполнять произвольные команды, полученные из YAML.

| Том и приложение | Требование |
|---|---|
| `infra_state/140-web-gateway` | Согласованный снимок SQLite Authelia и других баз, файл пользователей, ключи, 2FA и настройки одним совместимым комплектом: SQLite online backup либо краткая остановка записи |
| `infra_state/340-photo-archive` | PostgreSQL Immich: штатный согласованный экспорт/backup с необходимыми WAL либо доказуемо корректная остановка записи и snapshot. Копирование работающего `PGDATA` как обычных файлов запрещено |
| `gogs_data/310-gogs` | На короткое время остановить запись Gogs и получить единый снимок SQLite **и Git-репозиториев**, настроек и секретов; либо равноценная доказанная процедура |

Один `infra_state` используют несколько гостей: проверка обязана охватить каждого активного писателя. Неизвестный писатель не игнорируется, `crash-consistent` нельзя выдавать за согласованный backup приложения.

**Ограничение Immich:** PostgreSQL/секреты 340 расположены в `infra_state`, но фотографии — в `photo_archive`. Копия только первого тома не гарантирует полного восстановления Immich. Для полной защиты нужен согласованный комплект с медиатомом и отдельный проверенный сценарий восстановления. До этого в статусе отмечается неполное покрытие Immich.

## 5. Хранение и восстановление

- Использовать существующий Restic с шифрованием, подтверждённые `fast-ssd`/`nas-backup` и аварийный доступ к ключу независимо от работающего 910. Отсутствие необязательной выгрузки ключа на третий носитель — предупреждение, не запрет копирования.
- Для отдельных сроков хранения и восстановления создавать по одному Restic-репозиторию на том и назначение: `volumes/<volume-id>/`. Не смешивать их с `infra-core` и не инициализировать неизвестные непустые каталоги. Дедупликация Restic действует **внутри одного репозитория**, не между разными томами.
- SSD: ориентир — два последних пригодных комплекта; NAS: семь ежедневных и четыре еженедельных. Перед запуском проверить реальные размеры и ёмкость SSD 240 ГБ. Последнюю пригодную копию не удалять ради освобождения места или после неудачного задания; выполнять общие правила проверки и хранения.
- Сохранять метаданные состава, ID тома, подтверждённого источника и способа согласования, даты/идентификатора точки, успешных назначений и версии проекта. Проверка Restic не заменяет практическое восстановление.
- Восстановление выполняется из выбранной точки **в изолированное место**, с проверкой ключа, структуры, прав, SQLite/PostgreSQL, репозиториев и запуска службы. Никакого автоматического восстановления поверх рабочего тома при `deploy`. Замена данных требует отдельного явного подтверждения и остановки зависимых служб.

## 6. Статус и критерии приёмки

`infra-web` и `infra-manager status 910` показывают **по каждому тому и назначению**: включено ли копирование, следующее расписание, время/размер/ID последней успешной копии, подтверждение источника, состояние SSD и NAS, ошибки согласования/снимка/Restic, проверку целостности и **отдельно** дату пробного восстановления. Отсутствие подтверждённого результата — «не настроено»/«не проверено», не «готово». Ручной запуск — только через существующий интерфейс 910, **без новой публичной команды или диспетчера**.

Критерии завершения реализации:

1. `infra_state` и `gogs_data` реально резервируются и восстанавливаются с SSD, а после подключения NAS — независимо с него. Новому тому достаточно записи ID и объявления стратегии для новых типов приложений.
2. Автоматические тесты покрывают отсутствующий/ложный mount, неправильный UUID, неизвестный или повторный ID, нехватку thin-pool/SSD, отказ согласования, сбой экспорта/Restic, отсутствие одного или обоих назначений, очистку своего snapshot после отказа и сохранность прежних архивов.
3. Проверено, что рабочие тома не изменяются, службы возобновляются после снимка, а существующие `infra-core` и VM 100 продолжают работать.
4. В изоляции испытано восстановление Gogs (SQLite, Git, секреты), 140 (SQLite, 2FA, ключи) и данных PostgreSQL 340, причём зависимость Immich от `photo_archive` показана честно.
5. Нет новых пакетов/служб на PVE. До прохождения этих проверок оба новых задания считаются **не реализованными**, даже если в Git появился пример YAML.
