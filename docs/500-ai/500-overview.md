## 1. Назначение AI-контура

### 1.1. Для чего нужен AI Control

AI-контур нужен для автоматизированной работы с инфраструктурой проекта через уже существующие механизмы управления.

Он помогает:

- читать текущее и требуемое состояние проекта;
- планировать изменения;
- выполнять разрешённые действия;
- проверять результат;
- использовать подходящий механизм для конкретной задачи;
- связывать действия человека с существующей автоматизацией проекта.

AI должен упрощать управление инфраструктурой, но не создавать параллельную систему правил.

### 1.2. Что AI не заменяет

AI не заменяет основные компоненты проекта.

Он не является заменой:

- Proxmox VE;
- `deploy-guest`;
- Git;
- Ansible;
- SSH;
- сетевых механизмов;
- механизмов безопасности;
- резервного копирования;
- профильных средств настройки сервисов.

Если для задачи уже существует специализированный механизм, AI должен использовать его, а не создавать собственный параллельный способ выполнения той же операции.

### 1.3. Основной принцип работы

AI не является отдельным источником требуемого состояния.

Требуемое состояние хранится и определяется существующими источниками проекта.

AI использует эти источники, получает фактическое состояние инфраструктуры и через разрешённые механизмы приводит систему к нужному состоянию.

Упрощённо:

```text
требуемое состояние
        +
фактическое состояние
        ↓
       AI
        ↓
разрешённый механизм управления
        ↓
    изменение
        ↓
проверка результата
```

## 2. Место AI в архитектуре проекта

### 2.1. Общая схема

AI находится над существующими средствами управления и использует их как инструменты.

Общая модель:

```text
пользователь
    ↓
AI-агент
    ↓
AI Control
    ↓
разрешённые интерфейсы управления
├── Proxmox API / Proximo
├── Git
├── SSH
└── Ansible
    ↓
инфраструктура и сервисы
```

AI Control не должен становиться обязательным посредником для всех операций проекта.

Человек и другие средства автоматизации могут использовать те же профильные механизмы напрямую, если это предусмотрено их назначением.

### 2.2. Связь с Git

Git хранит воспроизводимое описание проекта и требуемое состояние там, где это предусмотрено архитектурой.

AI использует Git для:

- чтения конфигурации и документации;
- понимания принятого требуемого состояния;
- анализа структуры проекта;
- подготовки изменений, если для этого предоставлен соответствующий механизм.

Фактическое состояние работающей инфраструктуры не должно автоматически записываться в Git как новое требование только потому, что AI его обнаружил.

### 2.3. Связь с Proxmox и гостевыми системами

Для операций с VM/LXC AI использует разрешённый интерфейс Proxmox.

При этом нужно различать два уровня:

```text
Proxmox
→ жизненный цикл и параметры VM/LXC

гостевая ОС
→ состояние Linux и приложений внутри VM/LXC
```

Права на объект Proxmox не означают автоматически право административного доступа внутрь операционной системы.

Для работы внутри гостевой системы используются отдельные механизмы, например SSH или Ansible.

## 3. AI Control

### 3.1. Роль AI Control

AI Control — это центральная среда, в которой могут работать AI-агенты и общие средства взаимодействия с инфраструктурой.

Он предоставляет агентам доступ к разрешённым интерфейсам проекта и общей рабочей среде.

AI Control является частью управляющего контура, а не источником требований для остальных компонентов.

### 3.2. Основные части

На общем уровне AI Control включает:

- один или несколько AI-агентов;
- общие средства и интерфейсы управления;
- рабочую копию проекта;
- доступ к разрешённым инфраструктурным системам;
- локальное рабочее состояние, необходимое для работы агентов.

Точные каталоги, компоненты и правила внутреннего устройства относятся к отдельной документации AI Control.

### 3.3. Независимость от конкретного агента

Архитектура AI Control не должна зависеть от одного конкретного AI-агента.

Hermes или другой агент является заменяемым компонентом.

Общие механизмы управления инфраструктурой должны оставаться пригодными для других агентов без изменения базовой архитектуры проекта.

Это позволяет отделить:

```text
AI-агент
→ рассуждение и выбор действий

AI Control
→ общая среда

инструменты проекта
→ фактическое выполнение операций
```

## 4. Способы управления инфраструктурой

### 4.1. Proxmox

Для работы с объектами Proxmox AI использует разрешённый API-интерфейс.

Через него могут выполняться поддерживаемые операции с VM/LXC, например:

- чтение состояния;
- создание;
- изменение параметров;
- запуск и остановка;
- другие явно разрешённые действия.

Точные права определяются механизмами безопасности, а не самим AI.

### 4.2. Git

Git используется для работы с воспроизводимым состоянием проекта.

AI может:

- читать проект;
- анализировать конфигурацию;
- подготавливать изменения;
- использовать историю для понимания текущего состояния проекта.

Возможность изменения удалённого репозитория должна рассматриваться отдельно от обычного доступа на чтение.

### 4.3. SSH

SSH используется для административной работы внутри гостевой операционной системы там, где это разрешено.

Он подходит для:

- диагностики;
- проверки состояния;
- первоначальных действий;
- специальных или аварийных операций.

SSH не должен незаметно превращаться в основной механизм постоянной повторяемой настройки Linux, если для этой задачи предусмотрен Ansible.

### 4.4. Ansible

Ansible используется для повторяемой настройки операционных систем и приложений.

Если изменение должно быть воспроизводимым и регулярно применяемым к Linux-гостям, предпочтительно описать его через соответствующий механизм Ansible, а не выполнять как набор разовых команд AI.

### 4.5. Ограничения полномочий

AI действует только в пределах прав, предоставленных внешними механизмами доступа.

Он не должен:

- самостоятельно расширять собственные полномочия;
- обходить принятые механизмы безопасности;
- заменять запрещённую операцию другим способом только ради достижения результата;
- использовать более привилегированный интерфейс, если для задачи предусмотрен ограниченный профильный механизм.

Если имеющихся прав недостаточно, изменение модели доступа должно выполняться отдельно и осознанно.

## 5. Как AI выполняет задачу

### 5.1. Получение и анализ задачи

Сначала AI должен определить:

- что требуется изменить или проверить;
- какая часть системы является владельцем этой функции;
- какие источники состояния относятся к задаче;
- какие ограничения действуют для этой области.

Это позволяет выбрать правильный механизм до начала изменений.

### 5.2. Выбор механизма управления

После определения области AI выбирает существующий механизм проекта.

Примеры:

```text
VM/LXC в Proxmox
→ Proxmox API / Proximo

требуемое состояние проекта
→ Git

диагностика внутри Linux
→ SSH

повторяемая настройка Linux
→ Ansible
```

Если нужной операции нет среди существующих механизмов, это не означает, что AI должен автоматически реализовать обходной путь.

### 5.3. Проверка состояния

Перед изменением AI должен получить фактическое состояние соответствующей части системы.

Это необходимо, чтобы:

- не выполнять уже выполненную операцию;
- не затронуть неправильный объект;
- обнаружить расхождение с требуемым состоянием;
- определить безопасный способ изменения.

Для разных задач фактическое состояние может находиться в Proxmox, гостевой ОС, Git или прикладном сервисе.

### 5.4. Выполнение и проверка результата

После выполнения изменения AI должен проверить фактический результат.

Недостаточно получить только успешный ответ от инструмента.

В зависимости от операции проверяется:

- что изменён правильный объект;
- что новое состояние действительно применено;
- что требуемый сервис работает;
- что не возникло очевидного нового несоответствия;
- что результат соответствует исходной задаче.

### 5.5. Работа с требуемым и фактическим состоянием

AI использует общую модель состояния проекта.

```text
Git и другие нормативные источники
→ каким состояние должно быть

Proxmox, гостевые ОС и сервисы
→ каким состояние является сейчас
```

Обнаруженное вручную изменённое фактическое состояние само по себе не считается новым требованием.

Если ручное изменение должно стать постоянным, оно должно быть осознанно перенесено в соответствующий источник требуемого состояния.

## 6. Границы раздела

### 6.1. Архитектура

Общие архитектурные принципы проекта, модель состояния и границы между крупными подсистемами относятся к разделу `100-architecture`.

Раздел AI описывает только применение этих принципов к AI-контуру.

### 6.2. Гостевые системы

Требуемое состояние конкретной VM/LXC, правила её создания и жизненный цикл объекта Proxmox относятся к разделу `300-guests`.

AI может использовать этот механизм, но не определяет его контракт заново.

### 6.3. Безопасность

Учётные записи, токены, ACL, административные SSH-ключи и другие механизмы доступа относятся к разделу `700-security`.

Раздел AI описывает, какие интерфейсы используются, но не должен дублировать их точную модель безопасности.

### 6.4. Эксплуатация

Сквозные инструкции по развёртыванию всей системы, регулярному обслуживанию и аварийному восстановлению относятся к разделу `800-operations`.

AI может участвовать в этих процедурах, но их порядок не определяется обзором AI-контура.
