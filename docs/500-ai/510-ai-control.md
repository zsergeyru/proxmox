## 1. Назначение и состав

### 1.1. Роль AI Control

AI Control — это отдельная управляющая среда для AI-агентов проекта.

В этом файле не повторяются общие архитектурные принципы AI-контура. Они описаны в `500-overview.md`.

Задача AI Control — предоставить агентам готовую рабочую среду, в которой доступны:

- рабочая копия проекта;
- подключаемые инструкции;
- вспомогательные программы;
- средства доступа к инфраструктуре;
- локальные рабочие данные.

### 1.2. Состав подсистемы

На текущем этапе состав AI Control выглядит так:

```text
AI Control
├── VM 301
│   ├── основной AI-агент
│   ├── рабочая копия репозитория proxmox
│   ├── подключаемые инструкции
│   ├── вспомогательные программы
│   ├── доступ к Proxmox
│   ├── доступ к Git
│   ├── доступ по SSH
│   ├── доступ к Ansible
│   └── локальные рабочие данные
```

AI Control не должен содержать собственную отдельную модель инфраструктуры, которая конкурирует с проектом в Git.

## 2. Гостевая система AI Control

### 2.1. VM 301

AI Control размещается в отдельной виртуальной машине с VMID `301`.

Эта VM является рабочей средой AI-агентов и отделена от PVE-хоста.

Размещение AI Control в отдельной VM позволяет:

- не устанавливать AI-компоненты непосредственно на PVE;
- ограничивать доступ AI к инфраструктуре;
- обновлять AI-среду независимо от PVE;
- восстанавливать AI Control как обычную гостевую систему.

Параметры самой VM как объекта Proxmox должны описываться в документации гостевых систем, а не в этом файле.

### 2.2. Назначение VM

VM 301 предназначена для управляющих задач AI.

Она должна обеспечивать:

- запуск AI-агента;
- хранение рабочей копии проекта;
- использование подключаемых инструкций и служебных программ;
- доступ к разрешённым внешним системам;
- выполнение команд, необходимых для управления инфраструктурой.

VM 301 не должна использоваться как место постоянного хранения данных других сервисов проекта.

### 2.3. Что устанавливается внутри

Внутри VM 301 должны находиться как минимум:

- основной AI-агент;
- Git;
- SSH-клиент;
- средства выполнения подключаемых инструкций;
- клиентские средства для обращения к Proxmox REST API;
- средства работы с Ansible, если они требуются выбранной схеме;
- рабочая копия репозитория проекта.

Конкретные пакеты, версии и порядок установки относятся к документации развёртывания.

## 3. AI-агенты

### 3.1. Основной агент

Текущим основным агентом AI Control принимается Hermes.

Hermes используется как основной пользовательский интерфейс для работы с инфраструктурой через AI.

Он получает задачу пользователя и использует средства, доступные внутри AI Control.

### 3.2. Подключение других агентов

AI Control не должен быть жёстко связан только с Hermes.

При необходимости в ту же среду могут быть добавлены другие AI-агенты, если для них определены:

- назначение;
- разрешённые инструменты;
- необходимые права;
- способ работы с общей рабочей копией проекта.

### 3.3. Общая среда для агентов

Общие средства управления должны находиться вне конкретного агента настолько, насколько это возможно.

Предпочтительная схема:

```text
AI-агент
    ↓
общая рабочая среда AI Control
    ↓
подключаемые инструкции и инструменты
    ↓
внешние системы
```

Это позволяет заменить или добавить агента без переработки всех способов управления инфраструктурой.

## 4. Рабочая среда

### 4.1. Рабочая копия репозитория

В AI Control должна находиться рабочая копия репозитория `proxmox`.

Она используется для:

- чтения документации;
- чтения конфигурации;
- подготовки разрешённых изменений;
- анализа истории;
- получения файлов, необходимых инструментам AI Control.

Рабочая копия является локальным представлением Git-репозитория и может быть восстановлена из него.

AI Control имеет доступ на чтение ко всему необходимому репозиторию. Право записи отделено от права чтения и ограничивается только специально разрешённой областью VM 301.

### 4.2. Подключаемые инструкции

Подключаемые инструкции описывают, как агент должен работать с конкретной системой или инструментом.

Они должны хранить правила использования, а не секретные данные.

Для каждой инструкции должно быть понятно:

- с какой системой она работает;
- какие операции предоставляет;
- какие ограничения действуют;
- каким образом проверяется результат.

### 4.3. Вспомогательные программы

Если одной инструкции недостаточно, AI Control может содержать небольшие вспомогательные программы и сценарии.

Они нужны для повторяемого выполнения технических операций, которые нецелесообразно каждый раз собирать агенту вручную.

Такие программы должны иметь понятное назначение и не создавать второй независимый механизм управления для уже существующей функции.

### 4.4. Постоянные и временные данные

Внутри AI Control нужно различать постоянные и временные данные.

К постоянным относятся данные, без которых среду нельзя нормально восстановить и продолжить использовать. Для них должен быть определён внешний источник или отдельный порядок восстановления.

К временным относятся:

- кэш;
- результаты команд;
- временные файлы;
- рабочие данные агента;
- полученные сведения о текущем состоянии инфраструктуры.

Временные данные можно потерять без изменения требуемого состояния проекта.

## 5. Инструменты AI Control

### 5.1. Общий принцип

AI Control использует существующие механизмы управления проектом и не создаёт для каждой задачи собственный путь.

Подробные правила выбора между инструментами описываются в `520-ai-management.md`.

В этом файле фиксируется только то, какие средства входят в рабочую среду AI Control.

### 5.2. Proxmox

Для работы с Proxmox используется отдельный `skill`, обращающийся к Proxmox REST API.

За основу принимается подход `proxmox-ops`, адаптированный под этот проект.

Схема работы:

```text
AI-агент
    ↓
Proxmox skill
    ↓
клиент REST API
    ↓
Proxmox VE
```

Отдельный MCP-сервер для управления Proxmox не является обязательной частью AI Control.

Набор доступных операций должен быть ограничен задачами AI, а реальные полномочия дополнительно ограничиваются ACL самого Proxmox.

### 5.3. Git

Git используется для чтения проекта и для хранения воспроизводимых файлов AI Control, которые должны сохраняться между пересозданиями среды.

Доступ на чтение и право записи рассматриваются как разные полномочия.

AI-агенту может предоставляться ограниченное право записи только в специально выделенную часть файлов своей гостевой системы. Такое ограничение должно обеспечиваться технически, а не только инструкцией для агента.

Конкретные каталоги, в которые разрешена запись, структура skills, правил и вспомогательных программ, а также их размещение внутри VM описываются в документации соответствующей гостевой системы, а не в этом общем документе.

### 5.4. SSH

SSH-клиент используется для разрешённого прямого доступа к гостевым операционным системам.

Ключи, учётные записи и правила такого доступа описываются в разделе безопасности.

### 5.5. Ansible

AI Control должен иметь возможность использовать Ansible для повторяемой настройки гостевых систем там, где это предусмотрено архитектурой проекта.

Управляемые файлы конкретной VM применяются средствами повторяемой настройки гостевой системы. Их точная структура относится к документации самой гостевой системы и Ansible-контуру.

### 5.6. Другие инструменты

Дополнительные инструменты могут подключаться по мере появления реальной необходимости.

Каждый новый инструмент должен иметь конкретное назначение и не дублировать без причины уже существующий механизм.

## 6. Границы ответственности

AI Control отвечает за рабочую среду AI-агентов и доступ к разрешённым средствам управления.

При этом:

- общая архитектура AI-контура описывается в `500-overview.md`;
- правила выбора способа управления описываются в `520-ai-management.md`;
- общие правила состояния и развёртывания VM/LXC описываются в `300-guests`;
- устройство конкретной VM, её каталоги и внутренние компоненты описываются рядом с ней в `guests/<VMID>-<name>/`;
- права, токены и SSH-ключи описываются в `700-security`;
- установка, обслуживание и восстановление AI Control описываются в `800-operations`;
- повторяемая настройка гостевых ОС остаётся задачей Ansible;
- `deploy-guest` остаётся отдельным штатным механизмом развёртывания гостевых систем.
