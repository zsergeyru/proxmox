# AI Control

**Тип:** устройство подсистемы  
**Статус:** действующий  
**Назначение:** описать устройство AI Control как интеллектуального контура квартиры и роль VM 410.

AI Control — это **не отдельная самописная программа**. Это название системы, которая объединяет пользовательский интерфейс, основной агент и разрешённые интеграции.

## 1. Состав и общая схема

### 1.1. Базовая модель

Текущая реализация строится так:

```text
пользователь
↓
Open WebUI
↓
Hermes Agent
├── память и сессии
├── cron и длительные задачи
├── skills / MCP / инструменты
├── выбор и вызов модели
└── интеграции
    ├── Home Assistant
    ├── 910 infra-manager
    ├── сеть
    └── мониторинг
```

Hermes является текущей агентной средой 410. Open WebUI является основным пользовательским интерфейсом.

### 1.2. Что остаётся внешним

AI Control не заменяет специализированные системы:

- Home Assistant;
- Proxmox VE;
- `910 infra-manager`;
- маршрутизатор, DNS и VPN;
- NVR;
- мониторинг;
- резервное копирование;
- серверы локальных моделей.

410 использует их штатные API, MCP или другие специально ограниченные интерфейсы.

## 2. Основной агент и модели

### 2.1. Один основной агент

В штатной конфигурации используется один основной универсальный агент.

Сейчас это Hermes.

Отдельные агенты для Home Assistant, сети и инфраструктуры не создаются только ради разделения функций. Эти области предоставляются Hermes как инструменты.

Дополнительный агент допустим позже, если для него появится отдельный жизненный цикл или реальная потребность в независимой параллельной работе.

### 2.2. Модели

Hermes должен уметь использовать:

- локальные модели на другом компьютере или сервере;
- внешние модели через API;
- несколько поставщиков моделей при необходимости.

Выбор модели не должен давать дополнительных технических полномочий.

Конкретные поставщики и их секреты относятся к локальной конфигурации 410 и не должны храниться в общей документации.

## 3. Пользовательский интерфейс

### 3.1. Open WebUI

Open WebUI является основной пользовательской точкой входа.

Он отвечает за:

- вход пользователей;
- диалоги;
- историю;
- пользовательские настройки;
- передачу запросов Hermes.

Open WebUI не является владельцем прав к Home Assistant, Proxmox, сети или другим системам.

### 3.2. API Hermes

Open WebUI подключается непосредственно к штатному OpenAI-совместимому API Hermes.

Дополнительный самописный API между Open WebUI и Hermes не создаётся.

Это уменьшает количество собственного кода и не дублирует возможности агентной среды.

## 4. Инструменты и полномочия

### 4.1. Общий принцип

Hermes может иметь мощные встроенные инструменты, но внешние права квартиры добавляются отдельно.

Предпочтительная схема:

```text
Hermes
↓
ограниченный инструмент / MCP / API
↓
профильная система
↓
разрешённое действие
```

Текстовая инструкция агенту не считается техническим ограничением.

### 4.2. Инфраструктура

Для повторяемых инфраструктурных изменений используется `910 infra-manager`.

Целевая схема:

```text
Hermes
↓
ограниченный инструмент инфраструктуры
↓
910 infra-manager
↓
OpenTofu / Ansible / Packer
```

Hermes не должен получать прямой PVE API token только ради штатного развёртывания гостей.

### 4.3. Home Assistant и сеть

Для Home Assistant сначала следует использовать штатные возможности Hermes, если они удовлетворяют требованиям проекта и позволяют ограничить права.

Для сети и других сервисов предпочтительны отдельные ограниченные API или MCP-инструменты.

## 5. Память, задачи и события

### 5.1. Владение состоянием

Не создаётся отдельная база AI Control поверх собственных механизмов Hermes и Open WebUI.

Hermes является владельцем своего:

- состояния агента;
- сессий;
- памяти;
- cron;
- skills;
- hooks;
- профилей.

Open WebUI является владельцем пользовательских учётных записей и своей истории интерфейса.

### 5.2. Источники истины

Память агента не заменяет:

- Git как источник требуемого состояния проекта;
- Home Assistant как источник состояния дома;
- Proxmox как источник состояния VM/LXC;
- профильные системы как владельцев своих данных.

Перед управляющим действием актуальное состояние при необходимости запрашивается у системы-владельца.

### 5.3. События

Массовые и однозначные события сначала должны фильтроваться обычными правилами.

AI подключается, когда требуется:

- анализ;
- объяснение;
- выбор действия;
- сопоставление нескольких систем;
- нетипичное решение.

## 6. VM 410

### 6.1. Размещение

AI Control размещается в отдельной Debian VM `410 ai-control`.

Это позволяет:

- не устанавливать AI-зависимости на PVE;
- отдельно ограничивать права;
- обновлять Hermes и Open WebUI независимо от гипервизора;
- восстанавливать среду как обычного гостя.

### 6.2. Контейнеры

Текущая реализация использует Docker:

```text
410
├── hermes
└── open-webui
```

Постоянное состояние обоих сервисов хранится отдельно от контейнерных образов.

Точный состав, версии, каталоги и порты определяет локальная документация 410.

### 6.3. Граница самоуправления

410 не входит в собственную область штатного управления Proxmox.

Жизненный цикл VM 410 выполняется внешним управляющим контуром.

## 7. Границы ответственности

AI Control не должен превращаться в место размещения всех сервисов квартиры.

В 410 не переносятся только ради удобства AI:

- Home Assistant;
- локальный inference-сервер, если ему нужно отдельное оборудование;
- STT/TTS общего назначения;
- NVR;
- DNS/VPN;
- файловое хранилище;
- мониторинг.

Критичные права обеспечиваются внешними ACL, техническими идентичностями и ограниченными интерфейсами.
