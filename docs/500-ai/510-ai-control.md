## 1. Назначение AI Control

### 1.1. Роль в проекте

AI Control — это отдельная управляющая среда для AI-агентов.

Она предоставляет агентам:

- рабочую копию проекта;
- разрешённые средства управления инфраструктурой;
- доступ к необходимым внешним системам;
- общие правила работы;
- локальную среду для выполнения служебных операций.

AI Control не является самостоятельным источником требуемого состояния и не должен создавать параллельную систему управления инфраструктурой.

### 1.2. Что входит в AI Control

В состав AI Control могут входить:

- один или несколько AI-агентов;
- рабочая копия репозитория проекта;
- подключаемые инструкции для работы с отдельными системами;
- вспомогательные программы и сценарии;
- средства доступа к Proxmox, Git, SSH и Ansible;
- локальные служебные данные, необходимые для работы агентов.

Точный набор компонентов может меняться без изменения общей роли AI Control.

### 1.3. Что в AI Control не входит

AI Control не включает в себя:

- сам Proxmox VE;
- гостевые VM/LXC как часть своей внутренней среды;
- постоянное требуемое состояние инфраструктуры;
- общие правила безопасности проекта;
- резервные копии инфраструктуры;
- сетевые службы проекта;
- постоянную настройку Linux-гостей, если она должна выполняться через Ansible.

Эти части имеют собственных владельцев в документации проекта.

## 2. Размещение и устройство

### 2.1. Где работает AI Control

AI Control разворачивается в отдельной гостевой системе проекта.

Это отделяет AI-среду от самого узла Proxmox и позволяет:

- обновлять её независимо;
- ограничивать её сетевой и административный доступ;
- восстанавливать её как обычную гостевую систему;
- не устанавливать AI-компоненты непосредственно на PVE-хост.

Конкретные параметры гостевой системы относятся к документации гостевых систем, а не к этому файлу.

### 2.2. Основные компоненты

Упрощённо AI Control состоит из следующих частей:

```text
AI Control
├── AI-агент
├── рабочая копия проекта
├── подключаемые инструкции
├── вспомогательные программы
├── доступ к внешним системам
└── локальные служебные данные
```

Агент принимает решение о действии, а фактическое выполнение должно происходить через предусмотренное для этой задачи средство управления.

### 2.3. Рабочая копия проекта

AI Control должен иметь рабочую копию репозитория проекта.

Она используется для:

- чтения документации;
- чтения конфигурации;
- определения принятого требуемого состояния;
- подготовки изменений;
- анализа истории проекта при необходимости.

Рабочая копия является локальным представлением репозитория, а не отдельным источником истины.

Изменения, которые должны стать частью требуемого состояния проекта, должны быть оформлены через обычный порядок работы с Git.

### 2.4. Локальные и временные данные

AI Control может хранить локально:

- временные файлы;
- результаты выполнения команд;
- рабочие данные агента;
- кэш;
- журнал служебных действий;
- временно полученные сведения о фактическом состоянии.

Такие данные не должны автоматически считаться требуемым состоянием проекта.

Важные параметры инфраструктуры не должны существовать только внутри локального состояния AI Control, если для них предусмотрен постоянный источник в проекте.

## 3. AI-агенты

### 3.1. Основной агент

В AI Control может использоваться основной агент, через который пользователь выполняет большую часть задач управления инфраструктурой.

Агент:

- получает задачу от пользователя;
- изучает относящиеся к ней данные;
- выбирает подходящее средство управления;
- выполняет разрешённые действия;
- проверяет результат.

Конкретный программный продукт не должен определять архитектуру всей подсистемы.

### 3.2. Возможность нескольких агентов

AI Control должен допускать использование нескольких агентов.

Разные агенты могут использоваться, например, для:

- повседневного управления;
- работы с исходным кодом;
- анализа инфраструктуры;
- специальных задач.

Они могут использовать одну и ту же рабочую среду и общие средства доступа, если это разрешено моделью безопасности.

### 3.3. Независимость от конкретного агента

Средства управления инфраструктурой должны по возможности существовать отдельно от конкретного AI-агента.

Предпочтительная схема:

```text
AI-агент
    ↓
общие инструкции и средства
    ↓
внешняя система
```

Это позволяет заменить одного агента другим без переработки способов управления Proxmox, Git, SSH или Ansible.

## 4. Подключаемые инструкции и инструменты

### 4.1. Общий принцип

Для каждой внешней системы AI Control должен использовать понятный и ограниченный способ работы.

Подключаемая инструкция должна объяснять агенту:

- для каких задач предназначен инструмент;
- какие действия разрешены;
- какие действия требуют особой осторожности;
- как получить текущее состояние;
- как выполнить изменение;
- как проверить результат.

Инструкция помогает агенту правильно пользоваться средством управления, но не заменяет технические ограничения прав доступа.

### 4.2. Proxmox

Для работы с Proxmox принимается подход на основе отдельного `skill`, использующего REST API Proxmox.

Основная схема:

```text
AI-агент
    ↓
Proxmox skill
    ↓
вспомогательный клиент
    ↓
Proxmox REST API
```

За основу может использоваться подход проекта `proxmox-ops`, адаптированный под правила этого проекта.

Интерфейс должен предоставлять только те операции, которые действительно нужны AI-агенту.

Управление пользователями, ACL, настройками самого PVE-хоста и другими привилегированными областями не должно добавляться только потому, что соответствующие методы существуют в API.

Основным техническим ограничением прав остаётся модель доступа Proxmox.

### 4.3. Git

Git используется для работы с репозиторием проекта.

AI Control может использовать его для:

- чтения файлов;
- просмотра истории;
- определения изменений;
- подготовки новых изменений;
- отправки изменений, если это отдельно разрешено.

Доступ на чтение и возможность изменять удалённый репозиторий должны рассматриваться как разные полномочия.

### 4.4. SSH

SSH используется для прямого доступа к гостевым операционным системам, когда такой доступ предусмотрен.

Он нужен прежде всего для:

- диагностики;
- первоначальной проверки;
- разовых административных действий;
- аварийных операций;
- задач, для которых ещё нет постоянной автоматизации.

SSH не должен подменять Ansible для повторяемой постоянной настройки системы.

### 4.5. Ansible

Ansible используется для воспроизводимой настройки Linux-гостей и приложений.

AI Control может:

- читать существующие сценарии Ansible;
- подготавливать изменения;
- запускать разрешённые сценарии;
- проверять результат применения.

Постоянная настройка, которая должна воспроизводиться после повторного развёртывания системы, по возможности должна быть описана через Ansible или другой профильный постоянный механизм.

### 4.6. Другие подключаемые инструменты

При необходимости в AI Control могут добавляться новые средства для работы с отдельными системами.

Новый инструмент должен добавляться только тогда, когда:

- существует конкретная задача;
- текущие средства её не решают;
- определены его полномочия;
- понятен источник требуемого и фактического состояния;
- не создаётся дублирующий путь управления без необходимости.

## 5. Источники состояния

### 5.1. Требуемое состояние

AI Control не определяет требуемое состояние самостоятельно.

Он получает его из предусмотренных проектом источников, прежде всего из Git и профильных описаний подсистем.

Общая модель требуемого состояния определяется в архитектурной документации.

### 5.2. Фактическое состояние

Фактическое состояние AI получает непосредственно из управляемых систем.

В зависимости от задачи источником могут быть:

- Proxmox;
- гостевая операционная система;
- Git;
- Ansible;
- прикладной сервис;
- сетевая система.

Полученные данные используются для проверки текущего состояния перед изменением и после него.

### 5.3. Что AI Control может хранить локально

Локально допустимо хранить рабочие и временные данные.

Локальное состояние AI Control не должно становиться единственным местом хранения:

- параметров инфраструктуры;
- постоянных правил;
- конфигурации гостевых систем;
- сведений, необходимых для полного повторного развёртывания проекта.

Если информация должна пережить потерю AI Control, для неё должен существовать соответствующий постоянный источник.

## 6. Границы ответственности

### 6.1. AI Control и Proxmox

AI Control использует Proxmox как внешнюю систему управления виртуализацией.

Он не должен:

- изменять модель безопасности Proxmox по собственной инициативе;
- считать полный API Proxmox автоматически разрешённым;
- переносить настройки PVE-хоста в собственную локальную конфигурацию.

Операции с VM/LXC выполняются только в пределах предоставленных прав.

### 6.2. AI Control и deploy-guest

`deploy-guest` остаётся отдельным штатным механизмом развёртывания гостевых систем.

AI Control может использовать его там, где требуется именно предусмотренный проектом процесс развёртывания.

Наличие прямого доступа AI к Proxmox API не отменяет контракт `deploy-guest` и не делает его ненужным.

Прямой API и `deploy-guest` решают разные задачи и не должны незаметно подменять друг друга.

### 6.3. AI Control и Ansible

AI Control может запускать и изменять Ansible-конфигурацию, но не заменяет собой механизм воспроизводимой настройки.

Если агент один раз выполнил команду через SSH, это не означает, что требуемая постоянная настройка системы была описана.

Для постоянных изменений должен использоваться соответствующий воспроизводимый механизм.

### 6.4. AI Control и безопасность

AI Control пользуется уже созданной моделью доступа.

Конкретные:

- учётные записи;
- ACL;
- токены;
- SSH-ключи;
- правила их хранения;
- порядок замены и отзыва

описываются в разделе безопасности.

В этом документе фиксируется только принцип: AI действует через отдельные ограниченные полномочия и не управляет собственными правами.

### 6.5. AI Control и эксплуатация

Порядок первоначального развёртывания AI Control, его восстановления после сбоя и регулярного обслуживания относится к эксплуатационной документации.

Этот файл описывает устройство работающей подсистемы, а не пошаговую процедуру её установки.
