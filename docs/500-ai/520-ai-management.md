# Управление системами через AI

**Тип:** правила управления  
**Статус:** действующий  
**Назначение:** описать, как AI выбирает способ управления инфраструктурой и домашними сервисами, оценивает риск, выполняет действие и проверяет результат.

Этот документ отвечает на вопрос:

> Как AI должен выполнять конкретную задачу управления квартирой и её техническими системами?

## 1. Назначение

AI должен использовать профильный механизм той системы, которой принадлежит изменение.

Основной порядок:

```text
задача или событие
  ↓
определить объект
  ↓
получить текущее состояние
  ↓
выбрать штатный механизм
  ↓
оценить уровень действия
  ↓
выполнить или запросить подтверждение
  ↓
проверить результат
```

AI не должен выбирать более привилегированный способ только потому, что так проще.

## 2. Выбор способа управления

### 2.1. Home Assistant

Для домашних сущностей, сценариев и автоматизаций используется штатный интерфейс Home Assistant.

Прямое изменение файлов или операционной системы HA не должно применяться вместо профильного интерфейса без отдельной причины.

### 2.2. Proxmox и гостевые системы

Для жизненного цикла и параметров VM/LXC используется принятый инфраструктурный механизм.

Стандартное развёртывание гостя выполняется через `deploy-guest` и `910 infra-manager`. Для Hermes принято целевое подключение: ограниченный SSH-вызов штатной команды `infra-manager` на PVE, который передаёт работу в 910 напрямую, без Semaphore. Это не доступ к оболочке PVE и не административный PVE API. Разрешённые чтение/проверка и подтверждаемые изменяющие операции разграничиваются на PVE по `access.yaml`; опасные цели и восстановление PVE недоступны агенту. До реализации канала эта схема является только требованием.

Для гостевой ОС:

- SSH используется для диагностики и разрешённых разовых действий;
- Ansible используется для повторяемой настройки;
- Git используется для постоянного требуемого состояния.

### 2.3. Сеть

Для DNS, маршрутизации, VPN, клиентов и других сетевых функций используется профильный интерфейс соответствующей сетевой системы.

Наличие SSH к сетевому узлу не означает, что произвольное изменение конфигурации является штатным способом управления.

### 2.4. Прикладные сервисы

Если сервис предоставляет API, CLI или иной штатный интерфейс, AI использует его.

Для каждого интегрированного сервиса должно быть понятно:

- как получить состояние;
- какие действия разрешены;
- где находится требуемая конфигурация;
- как проверить результат;
- какие действия считаются опасными.

## 3. Порядок выполнения задачи

### 3.1. Определить задачу

AI должен определить:

- чего хочет пользователь или что означает событие;
- какой объект затрагивается;
- кто является владельцем его состояния;
- нужно ли только чтение или изменение.

### 3.2. Получить фактическое состояние

Перед изменением нужно получить актуальное состояние из системы-владельца.

Нельзя считать кэш AI достаточным подтверждением текущего состояния.

### 3.3. Выбрать штатный механизм

Примеры:

```text
свет, климат, HA automation
→ Home Assistant

VM/LXC
→ 910 / deploy-guest / Proxmox

постоянная настройка Linux
→ Ansible

диагностика Linux
→ SSH

постоянная конфигурация проекта
→ Git

маршрут или VPN
→ профильный сетевой интерфейс
```

### 3.4. Выполнить минимально необходимое действие

AI не должен попутно исправлять другие обнаруженные проблемы, если они не мешают безопасно выполнить исходную задачу.

### 3.5. Проверить результат

После действия AI заново получает фактическое состояние и проверяет именно конечный эффект.

Успешный ответ команды или API не считается достаточной проверкой сам по себе.

## 4. Уровни действий

Уровень определяет, насколько свободно AI может выполнить действие. Точные разрешения задаются политиками конкретной подсистемы.

### 4.1. Уровень 0 — чтение

Примеры:

- получить состояние;
- прочитать журнал;
- посмотреть историю;
- проверить доступность;
- объяснить событие.

Такие действия обычно могут выполняться автоматически в пределах выданных прав.

### 4.2. Уровень 1 — безопасное оперативное действие

Примеры:

- включить или выключить бытовую сущность;
- выполнить заранее разрешённый сценарий;
- перезапустить некритичный сервис;
- запустить безопасную проверку.

Автоматическое выполнение допустимо, если оно заранее разрешено правилами конкретной системы.

### 4.3. Уровень 2 — изменение конфигурации

Примеры:

- изменить автоматизацию Home Assistant;
- установить или обновить программу;
- изменить конфигурацию приложения;
- изменить постоянный параметр сервиса.

Такое действие должно быть воспроизводимым и, если требуется политикой, подтверждаться пользователем.

### 4.4. Уровень 3 — инфраструктурное изменение

Примеры:

- создать VM или LXC;
- изменить ресурсы гостя;
- развернуть новый сервис;
- изменить инфраструктурную конфигурацию.

Такие действия выполняются через специализированный инфраструктурный контур и его проверки.

### 4.5. Уровень 4 — критичное действие

Примеры:

- удалить данные;
- удалить VM/LXC;
- изменить критичную сеть;
- изменить права доступа;
- затронуть секреты;
- изменить PVE-хост;
- выполнить действие с высоким риском потери доступа или восстановления.

Для такого действия требуется явное осознанное разрешение пользователя и технически доступный путь восстановления, если он необходим.

## 5. Разовые и постоянные изменения

### 5.1. Разовое действие

Разовым считается действие, которое не должно воспроизводиться после повторного развёртывания.

Например:

- диагностика;
- просмотр журнала;
- временная проверка;
- перезапуск;
- аварийное временное исправление.

### 5.2. Постоянное изменение

Изменение, которое должно сохраниться после пересоздания системы, фиксируется в соответствующем источнике требуемого состояния.

Это может быть:

- Git;
- `guest.yaml`;
- `provision.yaml`;
- Ansible;
- конфигурация Home Assistant;
- профильная конфигурация сервиса.

Успешное ручное изменение не означает, что постоянная настройка уже оформлена.

## 6. Проверка результата и ошибки

### 6.1. Проверка

Проверка выполняется через владельца фактического состояния.

Например:

- после изменения HA — прочитать состояние HA;
- после изменения VM — проверить Proxmox;
- после настройки Linux — проверить гостевую ОС и сервис;
- после изменения сети — проверить маршрут, DNS или доступность;
- после изменения Git — проверить итоговые файлы и проверочные тесты.

### 6.2. Частичное выполнение

Если операция завершилась частично, AI сначала повторно собирает фактическое состояние.

Он не должен без проверки повторять всю последовательность.

### 6.3. Когда автоматическое выполнение прекращается

AI прекращает автоматические действия, если:

- текущее состояние нельзя достоверно определить;
- действие может заметно ухудшить ситуацию;
- требуются дополнительные права;
- выбранный механизм не способен безопасно завершить задачу;
- требуется решение или подтверждение пользователя.

Недостаток прав не является основанием для обхода через более привилегированный канал.

## 7. Границы ответственности

Этот документ описывает правила выбора и выполнения действий AI.

Он не определяет:

- устройство AI Control — это `510-ai-control.md`;
- точные права — раздел `700-security`;
- внутреннюю работу `deploy-guest` — раздел `300-guests`;
- архитектуру сети — раздел `400-network`;
- локальную настройку конкретного сервиса — документация его гостя;
- общую модель состояния — раздел `100-architecture`.
