# Управление инфраструктурой через AI

**Тип:** правила управления  
**Статус:** действующий

> Как AI должен выполнять конкретную задачу управления инфраструктурой?

## 1. Назначение

AI должен управлять инфраструктурой через уже принятые в проекте средства, а не создавать для каждой задачи новый способ.

Основной порядок:

```text
задача
  ↓
определение области изменения
  ↓
проверка текущего состояния
  ↓
выбор штатного средства управления
  ↓
выполнение изменения
  ↓
проверка результата
```

Если для задачи существует профильный механизм, AI должен использовать его в первую очередь.

## 2. Выбор способа управления

Способ управления определяется не удобством для агента, а тем, какой компонент является владельцем нужного изменения.

### 2.1. Proxmox

Для чтения и изменения состояния VM/LXC на уровне Proxmox используется доступ к REST API через принятый Proxmox skill.

Этот путь подходит для операций с объектами виртуализации, например:

- чтение состояния VM/LXC;
- запуск и остановка;
- изменение разрешённых параметров;
- выполнение других операций, доступных агенту в пределах ACL.

Прямой доступ к API не должен использоваться для обхода `deploy-guest`, если задача относится именно к штатному развёртыванию гостевой системы.

### 2.2. deploy-guest

`deploy-guest` используется тогда, когда нужно развернуть гостевую систему по принятому в проекте контракту.

AI может запускать этот механизм, но не должен повторять его внутреннюю логику собственными вызовами API без необходимости.

### 2.3. Git

Git используется, когда изменение относится к требуемому состоянию проекта, документации или воспроизводимой конфигурации.

Если ручное или автоматическое изменение должно сохраняться после повторного развёртывания, нужно определить, где оно должно быть зафиксировано в проекте.

### 2.4. SSH

SSH используется для:

- диагностики;
- проверки состояния;
- разовых административных действий;
- первоначальных действий;
- аварийных операций.

SSH не должен использоваться как постоянная замена воспроизводимой настройке.

### 2.5. Ansible

Ansible используется для повторяемой настройки гостевых операционных систем и приложений.

Если изменение должно воспроизводиться после переустановки или повторного развёртывания системы, предпочтительно описать его через Ansible или другой принятый постоянный механизм.

### 2.6. Прикладные средства

Если сервис имеет собственный штатный интерфейс управления, AI может использовать его вместо низкоуровневого вмешательства в систему.

Перед добавлением нового способа управления нужно убедиться, что существующие средства проекта не решают ту же задачу.

## 3. Порядок выполнения задачи

### 3.1. Определить объект и область изменения

Перед действием AI должен определить:

- какой объект нужно изменить;
- к какой подсистеме он относится;
- где находится требуемое состояние;
- где можно получить фактическое состояние;
- какие ограничения действуют для этой операции.

### 3.2. Получить текущее состояние

AI не должен начинать изменение, опираясь только на предположение о текущем состоянии.

Перед изменением нужно проверить фактическое состояние через соответствующую систему: Proxmox, гостевую ОС, Git, Ansible или прикладной сервис.

### 3.3. Выбрать штатный механизм

После проверки состояния выбирается средство управления.

Пример:

```text
изменить VM/LXC в Proxmox
→ Proxmox API

развернуть гостевую систему по контракту
→ deploy-guest

изменить постоянную конфигурацию Linux
→ Ansible

проверить или исправить что-то разово
→ SSH

изменить требуемое состояние проекта
→ Git
```

### 3.4. Выполнить изменение

AI должен выполнять только необходимое изменение и не затрагивать соседние области без причины.

Если в ходе задачи обнаружено другое несоответствие, его не следует исправлять автоматически, если оно не относится к исходной задаче и не мешает её безопасному выполнению.

### 3.5. Проверить результат

После выполнения AI должен повторно получить фактическое состояние и убедиться, что:

- изменён правильный объект;
- новое состояние действительно применено;
- задача выполнена полностью;
- не возникло очевидного нового несоответствия.

Успешный ответ команды или API сам по себе не считается достаточной проверкой.

## 4. Разовые и постоянные изменения

AI должен различать разовое действие и изменение требуемого состояния.

### 4.1. Разовое изменение

Разовым считается действие, которое не должно обязательно воспроизводиться после повторного развёртывания.

Примеры:

- диагностика;
- просмотр журналов;
- перезапуск сервиса;
- временная проверка;
- аварийное исправление до подготовки постоянного решения.

### 4.2. Постоянное изменение

Если изменение должно сохраняться как часть проекта, оно должно быть отражено в соответствующем постоянном источнике.

В зависимости от задачи это может быть:

- Git;
- описание гостевой системы;
- Ansible;
- профильная конфигурация сервиса.

Факт успешного ручного изменения не означает, что постоянная настройка уже оформлена.

### 4.3. Перенос разового исправления в постоянную конфигурацию

Если через SSH или другой прямой способ было выполнено изменение, которое должно остаться постоянным, AI должен определить его владельца и подготовить изменение в соответствующем воспроизводимом механизме.

## 5. Опасные действия

К опасным относятся действия, которые могут привести к потере данных, недоступности инфраструктуры или затруднить восстановление.

В частности:

- удаление VM/LXC;
- удаление или уменьшение дисков;
- изменение хранилищ;
- остановка критичных систем;
- изменение сетевых параметров, способное потерять доступ;
- удаление резервных копий или снимков;
- изменение прав доступа;
- действия, последствия которых нельзя надёжно определить заранее.

Для таких операций AI должен:

- проверить объект и его текущее состояние;
- определить последствия;
- проверить наличие требуемой возможности восстановления, если она необходима;
- не выполнять действие при существенной неопределённости;
- запрашивать явное подтверждение пользователя, если операция необратима или имеет высокий риск.

Ограничения, реализуемые средствами ACL, ключей и учётных записей, описываются в разделе безопасности.

## 6. Проверка результата и ошибки

### 6.1. Проверка результата

Проверка должна выполняться тем способом, который подтверждает реальный результат операции.

Например:

- после запуска VM — проверить её состояние в Proxmox;
- после изменения Linux — проверить фактическую конфигурацию внутри системы;
- после настройки сервиса — проверить сам сервис;
- после изменения требуемого состояния — проверить итоговые файлы проекта.

### 6.2. Частично выполненная операция

Если операция завершилась ошибкой после выполнения части действий, AI не должен автоматически повторять её целиком.

Сначала нужно заново получить фактическое состояние и определить:

- что уже выполнено;
- что не выполнено;
- безопасно ли продолжение;
- требуется ли откат или ручное решение.

### 6.3. Когда прекратить автоматические действия

AI должен прекратить автоматическое выполнение, если:

- невозможно достоверно определить текущую ситуацию;
- дальнейшее действие может ухудшить состояние;
- необходимы дополнительные права;
- требуется решение пользователя;
- выбранный механизм не позволяет безопасно завершить задачу.

В такой ситуации AI должен сообщить фактическое состояние и причину остановки, а не переходить к более привилегированному обходному способу.
