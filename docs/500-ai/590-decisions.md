## 1. Решения по роли AI

### 1.1. Почему AI не является отдельным источником требуемого состояния

**Проблема.**  
AI может получать сведения о фактическом состоянии инфраструктуры и выполнять изменения. Если считать его собственные выводы отдельным источником требований, в проекте появится параллельная модель состояния, которая может расходиться с Git и другими нормативными источниками.

**Рассмотренные варианты.**

- разрешить AI хранить собственное требуемое состояние;
- использовать фактическое состояние как источник требований;
- считать AI средством работы с уже определёнными источниками состояния.

**Принятое решение.**  
AI не является отдельным источником требуемого состояния. Он читает и изменяет те источники, которые уже определены архитектурой проекта.

**Почему.**

- сохраняется единая модель состояния;
- изменения остаются проверяемыми и воспроизводимыми;
- не возникает скрытой конфигурации, известной только агенту;
- после замены AI-агента проект продолжает работать по тем же правилам.

**Последствия и ограничения.**

- постоянное изменение должно быть отражено в соответствующем источнике проекта;
- локальная память или рабочие данные агента не заменяют Git, Ansible или профильную конфигурацию сервиса.

**Когда пересматривать.**  
Если в проекте появится отдельный нормативный источник состояния AI, явно включённый в общую модель состояния.

### 1.2. Почему AI использует штатные механизмы проекта

**Проблема.**  
AI может самостоятельно вызывать низкоуровневые команды и API, но это создаёт риск появления обходных способов управления, дублирующих штатные механизмы.

**Рассмотренные варианты.**

- разрешить AI выбирать любой технически доступный способ;
- создать отдельный набор AI-специфичных механизмов;
- использовать существующие средства проекта.

**Принятое решение.**  
AI использует существующие штатные механизмы управления и не создаёт параллельный путь только потому, что он удобнее для агента.

**Почему.**

- сохраняются единые правила проверки и безопасности;
- человек и AI используют одну модель управления;
- проще воспроизводить и расследовать изменения;
- уменьшается количество независимых реализаций одной функции.

**Последствия и ограничения.**

- AI иногда должен использовать более формальный механизм вместо прямой команды;
- новый AI-инструмент оправдан только тогда, когда он не дублирует уже существующую функцию без причины.

**Когда пересматривать.**  
Если существующие механизмы принципиально не позволяют безопасно автоматизировать нужный класс задач.

## 2. Решения по управлению инфраструктурой

### 2.1. Почему Proxmox управляется через skill и REST API

**Проблема.**  
Для управления Proxmox AI нужен понятный и ограничиваемый интерфейс.

**Рассмотренные варианты.**

- выполнять команды непосредственно на PVE по SSH;
- использовать отдельный MCP-сервер как обязательный слой;
- использовать подключаемую инструкцию (skill) и клиент Proxmox REST API.

**Принятое решение.**  
Основной путь управления Proxmox из AI — отдельный skill, использующий Proxmox REST API.

**Почему.**

- REST API является штатным интерфейсом Proxmox;
- права контролируются ACL самого Proxmox;
- skill может ограничивать доступный набор операций;
- не требуется отдельный обязательный сервер-посредник.

**Последствия и ограничения.**

- skill должен иметь чётко определённый набор поддерживаемых операций;
- наличие функции в REST API само по себе не означает, что AI должен иметь право её выполнять.

**Когда пересматривать.**  
Если появится другой штатный интерфейс, который даст более простую или более безопасную модель управления.

### 2.2. Почему отдельный MCP для Proxmox не является обязательным

**Проблема.**  
MCP может дать удобный интерфейс для агента, но отдельный сервер добавляет ещё один компонент, который нужно разворачивать, обновлять и защищать.

**Рассмотренные варианты.**

- сделать MCP обязательной частью AI Control;
- полностью отказаться от MCP;
- считать MCP дополнительным интерфейсом, а не обязательным слоем.

**Принятое решение.**  
Отдельный MCP-сервер для Proxmox не является обязательной частью архитектуры.

**Почему.**

- необходимые операции доступны через REST API;
- уменьшается количество обязательных компонентов;
- конкретный AI-агент не привязывает всю архитектуру к одному протоколу интеграции.

**Последствия и ограничения.**

- MCP может быть добавлен позже как удобный интерфейс;
- его появление не должно менять основную модель прав и ответственности.

**Когда пересматривать.**  
Если MCP станет необходим для нескольких агентов или даст существенные преимущества, которых нельзя получить через текущий интерфейс.

### 2.3. Почему `deploy-guest` остаётся отдельным механизмом

**Проблема.**  
AI может создавать и изменять VM/LXC напрямую через Proxmox API. Возникает вопрос, нужен ли после этого отдельный механизм `deploy-guest`.

**Рассмотренные варианты.**

- полностью заменить `deploy-guest` прямыми вызовами API;
- заставить AI использовать только `deploy-guest`;
- сохранить оба механизма с разной ответственностью.

**Принятое решение.**  
`deploy-guest` сохраняется как детерминированный механизм развёртывания гостя по контракту проекта. Прямое управление Proxmox через AI не заменяет его.

**Почему.**

- `deploy-guest` реализует единый контракт PLAN/APPLY/VERIFY;
- стандартное развёртывание не зависит от конкретного AI-агента;
- прямой API удобен для разрешённых операций, но не должен дублировать внутреннюю логику развёртывания.

**Последствия и ограничения.**

- AI должен выбирать механизм по задаче;
- изменение контракта развёртывания выполняется в гостевом контуре, а не в skill Proxmox.

**Когда пересматривать.**  
Если появится другой единый детерминированный механизм, полностью заменяющий контракт `deploy-guest`.

### 2.4. Почему повторяемая настройка гостевой ОС выполняется через Ansible

**Проблема.**  
После создания VM/LXC нужно повторяемо настраивать файлы, пакеты, службы и приложения.

**Рассмотренные варианты.**

- расширить `deploy-guest` до полноценной настройки ОС;
- выполнять постоянные изменения через SSH;
- использовать Ansible как отдельный слой повторяемой настройки.

**Принятое решение.**  
Повторяемая настройка гостевой ОС и приложений выполняется через Ansible.

**Почему.**

- Ansible предназначен для идемпотентной настройки ОС;
- `deploy-guest` остаётся ограниченным инфраструктурным механизмом;
- постоянные изменения не зависят от разовых SSH-команд.

**Последствия и ограничения.**

- часть полного развёртывания состоит из нескольких последовательных механизмов;
- граница между первоначальной подготовкой и постоянной конфигурацией должна оставаться явной.

**Когда пересматривать.**  
Если проект перейдёт на другой единый механизм повторяемой настройки гостевых систем.

### 2.5. Почему SSH не используется как основной способ постоянной настройки

**Проблема.**  
Через SSH можно выполнить практически любую операцию, поэтому он легко превращается в удобный, но невоспроизводимый основной механизм изменений.

**Рассмотренные варианты.**

- использовать SSH для всех изменений внутри Linux;
- полностью запретить прямой SSH;
- оставить SSH для диагностики, разовых и аварийных действий.

**Принятое решение.**  
SSH используется для диагностики, проверки, разовых и аварийных действий. Постоянные повторяемые изменения должны переходить в соответствующий воспроизводимый механизм.

**Почему.**

- сохраняется возможность быстро диагностировать проблему;
- постоянная конфигурация не остаётся только в истории команд;
- повторное развёртывание не зависит от ручных действий.

**Последствия и ограничения.**

- разовое исправление может потребовать последующего оформления в Ansible, Git или другом нормативном источнике.

**Когда пересматривать.**  
Если прямой SSH перестанет быть необходимым для эксплуатации или будет заменён другим административным каналом.

## 3. Решения по полномочиям AI

### 3.1. Почему AI использует отдельные технические идентичности

**Проблема.**  
Использование учётных данных человека или общих административных учётных записей затрудняет ограничение прав и аудит действий AI.

**Рассмотренные варианты.**

- использовать учётную запись человека;
- использовать общую административную идентичность;
- выдавать AI отдельные технические идентичности для соответствующих систем.

**Принятое решение.**  
AI использует отдельные технические учётные записи, токены и ключи там, где это поддерживается системой.

**Почему.**

- можно независимо ограничивать и отзывать права;
- проще отличать действия AI от действий человека;
- замена агента не требует передачи личных учётных данных.

**Последствия и ограничения.**

- появляется отдельный жизненный цикл технических учётных данных;
- конкретные права и секреты описываются в разделе безопасности.

**Когда пересматривать.**  
Если внешняя система предоставляет более подходящий механизм краткоживущих или делегированных полномочий.

### 3.2. Почему реальные ограничения должны обеспечиваться самой инфраструктурой

**Проблема.**  
Текстовая инструкция может сказать агенту «не выполнять» определённые операции, но сама по себе она не является технической защитой.

**Рассмотренные варианты.**

- полагаться только на правила поведения агента;
- выдавать широкие права и фильтровать операции внутри skills;
- ограничивать AI средствами ACL, учётных записей и областей доступа самой системы.

**Принятое решение.**  
Критичные границы полномочий должны обеспечиваться техническими средствами инфраструктуры.

**Почему.**

- ошибка агента не должна автоматически превращаться в полномочие;
- ограничения сохраняются при смене модели или инструмента;
- правила поведения становятся дополнительным, а не единственным уровнем защиты.

**Последствия и ограничения.**

- доступ может потребовать нескольких отдельных учётных записей и токенов;
- не все внешние системы позволяют одинаково точно ограничить область доступа.

**Когда пересматривать.**  
Если используемая система предоставляет более сильную и удобную модель делегирования прав.

### 3.3. Почему чтение Git и запись в Git разделены

**Проблема.**  
AI должен читать документацию и конфигурацию проекта, но это не означает, что ему автоматически требуется право изменять те же данные.

**Рассмотренные варианты.**

- один общий доступ на чтение и запись;
- только чтение без возможности самостоятельных постоянных изменений;
- отдельные полномочия на чтение и ограниченную запись.

**Принятое решение.**  
Чтение Git и запись в Git являются разными полномочиями и выдаются независимо.

**Почему.**

- чтение проекта требуется значительно чаще записи;
- минимальные права уменьшают последствия ошибки;
- право записи можно выдавать только там, где это действительно нужно.

**Последствия и ограничения.**

- для некоторых задач AI потребуется отдельное право записи;
- конкретная область записи определяется владельцем соответствующих данных.

**Когда пересматривать.**  
Если архитектура репозитория или используемый Git-сервис изменит модель полномочий.

### 3.4. Почему AI не получает произвольную запись во весь проект

**Проблема.**  
Некоторые AI-функции требуют сохранять постоянные изменения, но полная запись во весь репозиторий даёт доступ к областям, не относящимся к ответственности агента.

**Рассмотренные варианты.**

- не давать AI запись вообще;
- предоставить полную запись;
- ограничивать запись заранее определённой областью ответственности.

**Принятое решение.**  
Если AI получает право записи, оно должно ограничиваться заранее определённой областью, необходимой для его функции.

**Почему.**

- ошибка в одной подсистеме не должна давать возможность изменить весь проект;
- область прав совпадает с областью ответственности;
- постоянные изменения всё равно остаются в Git и имеют историю.

**Последствия и ограничения.**

- ограничение должно обеспечиваться технически;
- точные разрешённые пути относятся к документации владельца соответствующей области, а не к этому общему документу.

**Когда пересматривать.**  
Если AI станет полноправным общим разработчиком проекта и для этого будет принята другая модель контроля изменений.

## 4. Решения по воспроизводимости

### 4.1. Почему постоянные компоненты AI-среды не должны существовать только локально

**Проблема.**  
AI может создавать собственные инструкции, вспомогательные программы и другие полезные компоненты. Если они существуют только внутри текущего экземпляра рабочей среды, их можно потерять при пересоздании или восстановлении.

**Рассмотренные варианты.**

- считать локальный диск AI Control достаточным источником;
- полагаться только на резервную копию всей VM;
- иметь внешний воспроизводимый источник для постоянных компонентов.

**Принятое решение.**  
Компоненты AI-среды, которые должны переживать пересоздание рабочей среды, должны иметь внешний воспроизводимый источник.

**Почему.**

- рабочую среду можно восстановить с нуля;
- постоянные изменения имеют историю и понятного владельца;
- резервная копия VM не становится единственным источником конфигурации.

**Последствия и ограничения.**

- нужно различать постоянные и временные данные;
- конкретный внешний источник определяется владельцем компонента.

**Когда пересматривать.**  
Если AI Control перейдёт на другую модель хранения, которая обеспечивает эквивалентную воспроизводимость.

### 4.2. Почему временное рабочее состояние не является требуемым состоянием

**Проблема.**  
AI постоянно создаёт кэш, результаты команд, промежуточные файлы и сведения о текущем состоянии инфраструктуры. Если относить их к требуемому состоянию, проект начнёт хранить быстро устаревающие данные.

**Рассмотренные варианты.**

- сохранять всё состояние AI как часть проекта;
- сохранять только явно постоянные компоненты;
- полностью не хранить состояние AI.

**Принятое решение.**  
Временное рабочее состояние AI не является требуемым состоянием проекта.

**Почему.**

- его можно безопасно пересоздать;
- оно быстро устаревает;
- фактическое состояние инфраструктуры должно запрашиваться у владельца этого состояния, а не восстанавливаться из кэша агента.

**Последствия и ограничения.**

- после пересоздания среды часть временного контекста может быть потеряна;
- действительно постоянные данные должны быть явно вынесены в соответствующий воспроизводимый источник.

**Когда пересматривать.**  
Если появится класс локальных данных AI, без которых невозможно корректно продолжить работу и для которых потребуется отдельная нормативная модель.
