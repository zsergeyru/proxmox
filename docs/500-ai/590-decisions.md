## 1. Решения по рабочей среде AI

### 1.1. Почему skills должны быть воспроизводимыми

**Проблема.**  
AI-агент должен иметь возможность самостоятельно создавать новые skills. Если хранить их только локально внутри VM 301, они могут быть потеряны при пересоздании или восстановлении AI Control.

**Рассмотренные варианты.**

- хранить созданные агентом skills только локально в VM 301;
- разделить skills на локальные и управляемые;
- хранить постоянные skills в Git как часть конфигурации VM 301.

**Принятое решение.**  
Skills и вспомогательные программы, которые агент создаёт для постоянного использования, хранятся в Git как часть воспроизводимой конфигурации его гостевой системы.

Конкретное размещение этих файлов в репозитории и внутри VM относится к документации самой гостевой системы.

**Почему.**

- skills сохраняются при потере VM 301;
- изменения имеют историю;
- состояние AI Control остаётся воспроизводимым;
- не требуется отдельное деление на локальные и управляемые skills;
- принадлежность файлов конкретной гостевой системе остаётся явной.

**Последствия и ограничения.**

- AI требуется ограниченная возможность записи в Git;
- применение изменённых файлов внутри VM должно выполняться штатным механизмом настройки гостевой системы;
- секреты не должны попадать в эти каталоги.

**Когда пересматривать.**  
Если skills будут вынесены в отдельный репозиторий или появится другой воспроизводимый источник состояния AI Control.

## 2. Решения по доступу к Git

### 2.1. Почему агент не получает запись во весь репозиторий

**Проблема.**  
Для самостоятельного развития skills агенту нужна запись в Git, но полное право изменения репозитория позволило бы ему менять архитектуру, манифесты других гостей, документацию, скрипты и другие критичные части проекта.

**Рассмотренные варианты.**

- оставить AI только чтение и создавать skills вне Git;
- предоставить AI запись во весь репозиторий;
- предоставить запись только в специально разрешённую часть VM 301.

**Принятое решение.**  
AI получает чтение необходимого содержимого репозитория и отдельное ограниченное право записи только в специально выделенную часть файлов своей гостевой системы.

Остальной репозиторий для этого права записи недоступен. Точные разрешённые пути фиксируются в документации конкретной гостевой системы.

**Почему.**

- агент может самостоятельно создавать и улучшать собственные инструменты;
- его изменения остаются воспроизводимыми;
- ошибка агента не должна давать возможность переписать `guest.yaml`, документацию или конфигурацию других систем;
- область полномочий совпадает с областью ответственности AI Control.

**Последствия и ограничения.**

- ограничение должно обеспечиваться техническим механизмом на стороне Git, а не только текстовым правилом;
- обычное право записи на весь репозиторий для агента не подходит;
- конкретный способ технического ограничения должен поддерживать разрешение записи по пути либо эквивалентную изоляцию;
- изменение общих правил поведения агента не входит в это право.

**Когда пересматривать.**  
Если агенту понадобится управлять другими воспроизводимыми частями проекта и для этого будет определена отдельная безопасная область записи.

### 2.2. Почему правила агента не входят в область самостоятельной записи

**Проблема.**  
Skills расширяют возможности агента, а правила определяют ограничения его поведения. Если агент сможет без отдельной границы менять собственные обязательные правила, техническое ограничение полномочий станет менее понятным.

**Рассмотренные варианты.**

- разрешить одинаковую запись и в skills, и в правила;
- запретить агенту менять постоянные правила;
- выделить отдельную часть правил, которую агент сможет менять самостоятельно.

**Принятое решение.**  
На текущем этапе постоянные правила агента не входят в область самостоятельной записи AI.

**Почему.**

- правила являются частью управляющей политики;
- изменение skill и изменение ограничений поведения имеют разный уровень риска;
- право записи можно расширить позже отдельно и осознанно.

**Последствия и ограничения.**

- агент может самостоятельно развивать skills и вспомогательные программы, но не постоянные обязательные правила;
- изменения правил выполняются через обычный управляемый процесс проекта.

**Когда пересматривать.**  
Если будет определён отдельный класс правил, безопасный для самостоятельного изменения агентом.
