# Восстановление резервных копий и аварийное восстановление

**Тип:** Инструкция  
**Статус:** Действующий  
**Основной источник:** Да — для пошаговой проверки восстановления и восстановления PVE после потери хоста.

Требования к резервным копиям, срокам хранения и RPO/RTO определены в [`22-storage-and-backup.md`](22-storage-and-backup.md). Этот документ отвечает только на вопрос **«как проверить восстановление и что делать при аварии»**.

## 1. Проверка восстановления одной гостевой системы

Для критичных систем такую проверку выполнять не реже одного раза в три месяца и после существенных изменений схемы резервного копирования или хранения.

Порядок:

1. выбрать актуальную резервную копию;
2. убедиться, что исходная рабочая гостевая система не будет затронута;
3. выбрать свободный временный VMID/CTID;
4. восстановить копию во временный объект или изолированную среду;
5. не подключать восстановленную гостевую систему к рабочей сети, если существует риск конфликта IP, имени хоста или идентификаторов сервисов;
6. запустить восстановленную систему;
7. проверить загрузку ОС;
8. проверить работу ключевого приложения или сервиса;
9. проверить наличие ожидаемых постоянных данных;
10. для управляющего гостя проверить наличие и согласованность его собственной management SSH-пары;
11. зафиксировать результат, дату и фактическое время восстановления;
12. после успешной проверки остановить и удалить временную гостевую систему.

Проверка считается успешной только если сервис действительно запускается и необходимые данные доступны.

## 2. Что зафиксировать по результату проверки

Минимальная запись:

```text
дата
исходная резервная копия
временный VMID/CTID
проверенный сервис
результат: успешно/ошибка
время восстановления
обнаруженные проблемы
последующие действия
```

Если тест выявил проблему, исправить цепочку резервного копирования и восстановления и повторить проверку.

## 3. Полная потеря системного диска PVE

Базовый порядок:

```text
чистая установка Proxmox VE
→ вернуть имя хоста и базовую сеть управления
→ восстановить постоянные инфраструктурные учётные данные
→ восстановить или проверить management public-key registry
→ запустить Public Bootstrap / PVE Configuration
→ проверить конфигурацию хоста
→ подключить хранилища резервных копий
→ убедиться, что копии доступны
→ восстановить критичные управляющие VM/LXC
→ проверить их management identities и ожидаемые PVE tags management-ssh
→ выполнить sync-management-keys
→ восстановить остальные критичные VM/LXC
→ проверить критичные сервисы
→ восстановить остальные гостевые системы
→ повторно выполнить/проверить sync-management-keys
→ проверить задания резервного копирования
```

Инструкция инициализации чистого хоста: [`20-pve-initialization.md`](20-pve-initialization.md).

## 4. Что восстановить до запуска проектной настройки

На полностью новом хосте сначала требуется вернуть минимум, необходимый для безопасного запуска автоматики проекта:

- корректное имя хоста;
- сеть управления и доступ к PVE;
- постоянные учётные данные, которые нельзя получить повторно без смены ключей или токенов;
- доступ к закрытому исходному коду проекта на GitHub по принятой процедуре первоначальной настройки;
- при наличии резервной копии — канонический каталог зарегистрированных management public keys.

Точные пути и владельцы определены в [`21-pve-filesystem-layout.md`](21-pve-filesystem-layout.md).

## 5. Инфраструктурные учётные данные и management SSH

Особое внимание:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
/etc/proxmox-deployer/ssh/pve_guest_ed25519
/etc/proxmox-deployer/secrets/host-deploy.token
/etc/proxmox-deployer/secrets/ai-agent-infra.token
/var/lib/proxmox-deployer/public-keys/
```

`github_proxmox_repo_ed25519` является мастер-копией общего GitHub Deploy Key только для чтения `zsergeyru/proxmox`. Локальные копии этого credential в гостях с `management.project_repo_read: true` не считаются отдельными независимыми ключами и могут быть восстановлены из PVE мастер-копии после восстановления безопасного deploy-контура.

### Если `pve_guest_ed25519` восстановлен

Продолжить штатную настройку PVE и затем проверить SSH-доступ с хоста к тестовой Debian-гостевой системе.

Открытая часть deployer identity должна присутствовать в каноническом management public-key registry как `deployer.pub`.

### Если `pve_guest_ed25519` потерян

Не генерировать новую пару как незаметную замену старой.

Порядок:

```text
осознанно создать и зарегистрировать новую пару ключей
→ определить гостевые системы со старым открытым ключом
→ добавить новый открытый ключ
→ проверить доступ новым закрытым ключом
→ обновить canonical public-key registry
→ выполнить sync-management-keys
→ только после проверки удалить старый открытый ключ, если это требуется
```

Это отдельная операция восстановления и смены ключей.

На текущем новом PVE-хосте отдельная миграция прежнего `pve_guest_ed25519` не требуется: старого рабочего management-контура ещё нет. После первого создания ключ считается постоянным и не должен автоматически заменяться при обычной повторной конфигурации.

### Если потерян общий GitHub Deploy Key только для чтения

Создать новый **read-only** Deploy Key, зарегистрировать его открытую часть на GitHub для `zsergeyru/proxmox` и восстановить мастер-копию на PVE по правилам первоначальной настройки. Старый ключ считается утраченным и отзывается.

После восстановления мастер-копии определить гостей, использующих `management.project_repo_read: true`, и безопасно материализовать новый общий credential повторным управляемым deploy/операцией ротации. Старые локальные копии должны быть отозваны/заменены в рамках явной ротации; обычное отсутствие поля в manifest не используется как скрытый механизм удаления ключа.

Если потеря произошла только у локальной копии гостя, а PVE мастер-копия цела, новый GitHub Deploy Key создавать не требуется: гостевая копия воспроизводится из существующей мастер-копии.

### Если потерян `/var/lib/proxmox-deployer/public-keys/`

Этот каталог не содержит private keys, но его нельзя восстанавливать из непроверенных источников.

Порядок:

```text
восстановить deployer.pub из проверенной пары pve_guest_ed25519
→ восстановить управляющие гости из резервных копий
→ для каждого гостя с management.ssh_identity=true проверить его стандартную private/public пару
→ получить только проверенные .pub
→ зарегистрировать каждый ключ как <VMID>.pub
→ сверить fingerprints с имеющимися резервными записями/журналами, если они доступны
→ заново собрать canonical registry
→ проверить/восстановить tag management-ssh только у доказанно участвующих Debian-гостей
→ запустить sync-management-keys
```

Если происхождение конкретного public key или принадлежность объекта management SSH-контуру не удаётся доказать, запись/добавление не выполняется автоматически.

### Если потерян private management key управляющего гостя

Для гостя с:

```yaml
management:
  ssh_identity: true
```

собственная пара хранится внутри него:

```text
/etc/proxmox-guest/ssh/management_ed25519
/etc/proxmox-guest/ssh/management_ed25519.pub
```

Если VM/LXC восстановлена из резервной копии вместе с этой парой, сначала проверяется соответствие private/public и зарегистрированному fingerprint в `<VMID>.pub`.

Если пригодной копии private key нет, запрещено молча создавать новую пару под видом старой. Нужна явная ротация management identity:

```text
создать новую пару осознанной recovery-операцией
→ зарегистрировать новый <VMID>.pub на PVE
→ выполнить sync-management-keys
→ проверить доступ новой identity к целевым гостям
→ только затем считать старую identity отозванной
```

Точный жизненный цикл management key registry определяет [`28-management-ssh-keys.md`](28-management-ssh-keys.md).

### Удаление гостя и повторное использование VMID

Публичный ключ management identity связан только с VMID:

```text
/var/lib/proxmox-deployer/public-keys/<VMID>.pub
```

Поэтому:

```text
удалили управляющий guest
→ удалить его <VMID>.pub
→ выполнить sync-management-keys

создали новый guest с тем же VMID
→ не использовать старую identity
→ создать новую пару
→ зарегистрировать новый <VMID>.pub
```

Переименование гостя само по себе ключ не меняет.

## 6. Подключение хранилищ резервных копий

После восстановления конфигурации хоста:

1. подключить SMB/CIFS-хранилище резервных копий;
2. подключить и проверить USB-хранилище, если оно требуется;
3. убедиться, что Proxmox видит содержимое с резервными копиями;
4. проверить свободное место и права доступа;
5. не начинать восстановление рабочих систем, пока источник резервных копий не проверен чтением и просмотром содержимого.

Фактические сведения о хранилищах нужно брать из [`../host/pve/storage/README.md`](../host/pve/storage/README.md) и [`../host/pve/backup/README.md`](../host/pve/backup/README.md), а не из этой инструкции.

## 7. Порядок восстановления гостевых систем

Рекомендуемый приоритет:

```text
1. критичная сеть и управляющий контур, если без них невозможно продолжение
2. рабочий Home Assistant
3. остальные критичные сервисы
4. прикладные сервисы и сервисы данных
5. мониторинг
6. разработка, тесты и легко воспроизводимые гостевые системы
```

Конкретный порядок может меняться в зависимости от зависимостей между сервисами.

Перед каждым восстановлением проверить:

- правильный VMID/CTID;
- целевое хранилище;
- сетевую конфигурацию;
- отсутствие конфликта с уже существующей гостевой системой;
- наличие нужной версии резервной копии;
- для управляющего гостя — ожидаемый management key fingerprint, если он уже зарегистрирован;
- для Debian-гостя management-контура — ожидаемое наличие PVE tag `management-ssh`.

## 8. `sync-management-keys` после восстановления

После восстановления deployer identity и управляющих гостей необходимо привести публичный каталог и управляемые Debian-гости к одному состоянию.

```text
проверить /var/lib/proxmox-deployer/public-keys/*.pub
→ проверить имена дополнительных ключей в формате <VMID>.pub
→ собрать/проверить management-authorized-keys
→ проверить, какие Debian VM/LXC доказанно должны иметь tag management-ssh
→ запустить sync-management-keys
→ убедиться, что обработаны только объекты с management-ssh и все дополнительные проверки прошли
→ убедиться, что локальные каталоги public keys обновились
→ проверить управляемый набор root authorized_keys
→ проверить SSH минимум двумя независимыми management identities, если они существуют
```

`sync-management-keys` не используется для создания или ротации private keys. Он распространяет только уже зарегистрированные открытые ключи.

Для нового гостя первое запоминание SSH host key допускается только для ожидаемого адреса в доверенной домашней сети. Для уже известного гостя неожиданная смена host key означает остановку; старая запись не удаляется автоматически.

Не запускать синхронизацию, если canonical registry содержит ключ с неподтверждённым происхождением или область `management-ssh` восстановлена неоднозначно.

## 9. Проверка после восстановления хоста

Минимальный перечень приёмочных проверок:

```text
PVE доступен по сети управления
Public Bootstrap / PVE Configuration проходят успешно
основная копия проекта не содержит локальных изменений
общий GitHub Deploy Key только для чтения работает с PVE
хранилища доступны
учётные записи и ACL проекта в PVE работают
текущий шаблон 9000 валиден
deployer management identity работает
canonical public-key registry проверен
PVE tags management-ssh соответствуют ожидаемому management-контуру
sync-management-keys завершился успешно
management identities управляющих гостей соответствуют ожидаемым fingerprints
критичные гостевые системы запущены
критичные приложения работают
SSH-доступ с PVE-хоста работает
для гостей с management.project_repo_read восстановлен read-only доступ к проектному Git
задания резервного копирования снова включены
новая резервная копия после восстановления создаётся успешно
```

## 10. Учебное восстановление

После существенного изменения архитектуры первоначальной настройки, management SSH keys или резервного копирования рекомендуется выполнить учебный сценарий в безопасной тестовой среде:

```text
чистый PVE
→ восстановить инфраструктурные учётные данные
→ восстановить/пересобрать public-key registry
→ выполнить первоначальную настройку и конфигурацию
→ подключить хранилище резервных копий
→ восстановить тестовую VM/LXC
→ восстановить/проверить ожидаемый tag management-ssh
→ проверить management SSH identity и административный доступ
→ выполнить sync-management-keys
→ проверить загрузку и сервис
→ создать новую резервную копию
```

Цель такого теста — проверить всю цепочку, а не только отдельный файл резервной копии.

## 11. Когда остановиться

Остановиться и не выполнять разрушительную очистку, если:

- неясно, какая резервная копия является правильной;
- целевой VMID/CTID уже занят неизвестным объектом;
- сопоставление хранилищ отличается от ожидаемого;
- учётные данные восстановлены только частично и их происхождение неизвестно;
- public key не удаётся связать с проверенной management identity;
- неизвестно, должен ли объект участвовать в `management-ssh`;
- восстановленная гостевая система может конфликтовать с рабочей по IP, имени хоста или идентификаторам сервисов;
- нет способа проверить результат.

В неоднозначной ситуации сначала сохранить текущее состояние и разобраться в расхождении.
