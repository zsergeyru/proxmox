# План VMID / CTID

**Тип:** Спецификация  
**Статус:** Действующий  
**Основной источник:** Да — для функциональной нумерации VMID/CTID и правил адресации по VMID; фактическое требуемое состояние конкретной гостевой системы остаётся в `guest.yaml`.

Функциональная нумерация применяется только к новым VM/LXC. VMID не определяет порядок запуска и не является причиной перенумеровывать уже работающие системы.

| Диапазон | Назначение |
|---|---|
| `100–199` | сеть и базовая инфраструктура |
| `200–299` | Home Assistant и автоматика |
| `300–399` | прикладные, DevOps- и AI-сервисы |
| `400–499` | мониторинг и обслуживание |
| `500–599` | видео и камеры |
| `600–699` | временные и экспериментальные VM/LXC |
| `900–999` | устаревшие и служебные объекты |

## Административный IP

Для управляемых инфраструктурных VM/LXC используется детерминированная формула VMID.

Активная подсеть хранится только в `guests/defaults.yaml`:

```yaml
defaults:
  network:
    subnet: 192.168.0.0/16
    gateway: 192.168.1.1
    addressing: vmid
```

Правило:

```text
VMID XYZ + A.B.0.0/16
→ A.B.X.YZ
```

При текущей сети:

```text
109 → 192.168.1.9
201 → 192.168.2.1
202 → 192.168.2.2
203 → 192.168.2.3
211 → 192.168.2.11
301 → 192.168.3.1
311 → 192.168.3.11
321 → 192.168.3.21
331 → 192.168.3.31
401 → 192.168.4.1
501 → 192.168.5.1
```

Если центральная подсеть будет изменена на `10.0.0.0/16`, те же VMID автоматически дадут:

```text
109 → 10.0.1.9
201 → 10.0.2.1
202 → 10.0.2.2
203 → 10.0.2.3
211 → 10.0.2.11
301 → 10.0.3.1
311 → 10.0.3.11
321 → 10.0.3.21
331 → 10.0.3.31
401 → 10.0.4.1
501 → 10.0.5.1
```

В обычном `guest.yaml` IP не хранится.

Осознанное исключение задаётся через:

```yaml
network:
  ipv4:
    address: 192.168.8.50
```

без префикса. Проверяющий скрипт предупреждает, если явно заданный адрес не соответствует формуле VMID.

## Proxmox-хост

Сам PVE-хост не обязан следовать формуле VMID и не вычисляет административный адрес из собственного идентификатора.

Целевой административный адрес после сетевой миграции:

```text
10.0.0.10/16
gateway 10.0.0.1
```

Фактическое текущее состояние хоста хранится только в [`../host/pve/network/README.md`](../host/pve/network/README.md).

## Шлюзы

Текущий центральный шлюз гостевой сети:

```text
192.168.1.1
```

После переезда шлюз MAIN:

```text
10.0.0.1
```

В новой квартире OpenWrt владеет L3-шлюзами VLAN:

```text
MAIN / основная сеть → 10.0.0.1/16
IOT / VLAN 20       → 10.20.0.1/16
CAMERAS / VLAN 30   → 10.30.0.1/16
```

`109-network-gateway` предоставляет DNS, VPN, PBR и VPN для удалённого доступа, но не является обязательным L3-шлюзом локальных VLAN.

REMOTE-VPN использует:

```text
10.60.0.0/16
```

## Миграция

Две адресные стадии внутри каждого манифеста больше не хранятся.

Переезд сети выполняется изменением центральных `subnet` и `gateway` в `guests/defaults.yaml`, после чего средство миграции или развёртывания последовательно приводит реальные VM/LXC к новому требуемому состоянию.

## Текущий план

- `100` — `haos` (VM, **рабочая система**, исторический VMID сохраняется)
- `109` — `network-gateway` (VM)
- `201` — `ha-main` (LXC, только возможная будущая миграция с VM 100)
- `202` — `ha-test` (LXC, при необходимости)
- `203` — `ha-flat2` (LXC, при необходимости)
- `211` — `automation-services` (LXC)
- `301` — `ai-control` (VM, целевой управляющий контур)
- `311` — `dev-services` (LXC)
- `320` — `ai-control` (VM, текущий временный контур до перехода на 301)
- `321` — `app-services` (LXC)
- `331` — `ai-services` (LXC)
- `401` — `monitoring` (LXC, при практической необходимости)
- `411` — резерв под `backup-services`, если появится отдельная роль
- `501` — `frigate` (VM/LXC после теста)

Запланированный VMID не означает обязательное создание гостевой системы. Проверяющий скрипт намеренно не читает этот документ: основной источник требуемого состояния для развёртывания — `guests/defaults.yaml` и существующие `guest.yaml`.
