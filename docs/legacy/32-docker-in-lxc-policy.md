# Docker внутри LXC — принятая политика

**Тип:** Политика  
**Статус:** Действующий  
**Основной источник:** Да — для допустимых границ Docker внутри непривилегированного LXC и обязательных условий безопасности.

## Статус решения

**Принят вариант B:** сервисные контейнеры Docker разрешено запускать внутри непривилегированного Proxmox LXC ради меньшего расхода RAM/CPU и более простой плотной консолидации сервисов.

Это осознанное отклонение от более изолированного варианта `Docker → QEMU VM`. Проект принимает меньшую изоляцию только для доверенных домашних и инфраструктурных сервисов.

## Где применяется

Текущие Docker-LXC:

```text
211 automation-services
311 dev-services
321 app-services
331 ai-services
401 monitoring
```

В итоговом профиле это фиксируется так:

```yaml
lxc:
  container_runtime: docker
  source:
    ostemplate: local:vztmpl/debian-13-standard
  unprivileged: true
  features:
    nesting: true
    keyctl: true
```

`container_runtime: docker` является машинно-читаемым признаком принятого варианта. CI запрещает Docker-LXC без `unprivileged: true`, `nesting: true` и `keyctl: true`.

## Источник LXC

`lxc.source.ostemplate` обозначает **семейство** образов, а не конкретное имя архива.

В Git хранится:

```text
local:vztmpl/debian-13-standard
```

Не хранится:

```text
debian-13-standard_13.6-1_amd64.tar.zst
```

PVE Configuration самостоятельно выполняет `pveam update`, определяет актуальный стандартный архив Debian 13 и при необходимости скачивает его в `local:vztmpl`.

Будущий `deploy-guest` должен:

```text
прочитать семейство из итогового состояния
→ найти установленные архивы этого семейства на разрешённом хранилище
→ выбрать наиболее новую доступную версию
→ если ничего не найдено — остановиться до любых изменений
```

`deploy-guest` не скачивает LXC-образ сам и не подменяет Debian 13 другим семейством.

Это позволяет не привязывать манифесты гостевых систем к временной метке или ревизии пакета Proxmox и одновременно не выдавать AI право `Datastore.AllocateTemplate`.

## Административный доступ

Docker-LXC подчиняется общим требованиям гостевой системы:

```text
административный пользователь: root
вход по паролю: отключён
SSH: только открытые ключи
```

При создании LXC начальные открытые ключи передаются через Proxmox `ssh-public-keys`. Получение SSH-доступа `root` не зависит от необязательной возможности `base`.

## Почему выбран LXC

Для этих сервисов важнее:

- небольшой расход ресурсов самой виртуализации;
- быстрый запуск и остановка;
- компактные резервные копии;
- отсутствие отдельного полноценного ядра для каждого Docker-хоста;
- простое распределение небольших сервисов по отдельным CTID.

Это не означает, что LXC считается эквивалентом VM по уровню изоляции.

## Граница безопасности

Docker внутри LXC допускается только для **доверенных сервисов проекта**.

По умолчанию запрещено:

- привилегированный LXC;
- `lxc.apparmor.profile=unconfined`;
- передача Docker socket хоста PVE внутрь LXC;
- широкое подключение системных каталогов PVE через bind mount;
- произвольная передача устройств;
- `mknod`, FUSE и дополнительные возможности монтирования без отдельного решения;
- запуск недоверенного кода нескольких независимых пользователей или недоверенных сборок;
- использование LXC как защитной песочницы для потенциально враждебного кода.

Если сервису требуются привилегированный контейнер, нестандартные возможности ядра, широкий доступ к устройствам, недоверенные задачи сборки или более сильная изоляция, для него выбирается QEMU VM либо оформляется отдельное ADR.

## Обязательные проверки средства развёртывания

Для `lxc.container_runtime: docker` до применения и итоговой проверки должны выполняться:

```text
unprivileged == true
nesting == true
keyctl == true
resolved ostemplate принадлежит выбранному семейству
установлен административный SSH-ключ root
```

После настройки ОС должны успешно проходить как минимум:

```bash
docker version
docker info
docker compose version
```

Проверка прикладного стека относится к Ansible и проверке работы сервисов соответствующей гостевой системы.

## Обязательная проверка резервного копирования и восстановления

Docker-LXC нельзя считать полностью проверенным только потому, что Docker запустился.

До перевода нового класса Docker-LXC в рабочее состояние требуется хотя бы одна практическая проверка восстановления:

```text
создать и настроить LXC
→ запустить Docker и тестовый или реальный Compose-стек
→ сделать резервную копию Proxmox
→ восстановить её во временный CTID
→ запустить восстановленный LXC
→ проверить административный SSH-доступ root
→ docker info
→ docker compose config и состояние сервисов
→ убедиться в сохранности постоянных данных
→ удалить временно восстановленный объект после проверки
```

Проверка восстановления повторяется после существенного изменения:

- основной версии Proxmox/LXC;
- семейства или существенного изменения базового LXC-образа Debian;
- настроек безопасности и возможностей (`nesting`, `keyctl`, отображение идентификаторов);
- схемы хранения постоянных данных Docker.

Обычная резервная копия должна захватывать корневую файловую систему и постоянные данные, которые по политике проекта находятся внутри резервируемого хранилища LXC. Внешние точки монтирования и отдельные наборы данных имеют собственные правила резервного копирования.

## Обновления Docker

Среда Docker не должна бесконтрольно обновляться самим `deploy-guest`. Управление версией и обновлением Docker относится к первичной и повторяемой настройке ОС и изменяется отдельным коммитом проекта с последующей проверкой Docker-LXC.

Это правило не означает обязательную фиксацию точной версии каждого внешнего пакета Debian/Proxmox.

## Когда пересмотреть решение

Переход конкретного сервиса с LXC на VM рассматривается, если:

- появляются реальные проблемы совместимости Docker с LXC, cgroup или ядром;
- требуется более сильная изоляция от PVE-хоста;
- сервис исполняет недоверенный код;
- необходим доступ к устройствам, существенно расширяющий поверхность атаки;
- резервное копирование или восстановление Docker-LXC оказывается ненадёжным;
- эксплуатационная сложность LXC становится выше экономии ресурсов.

## Главный принцип

> Docker внутри LXC — контролируемый вариант для доверенных сервисов: непривилегированный LXC + `nesting` + `keyctl` + семейство Debian 13 + административный доступ `root` только по ключу + проверенное резервное копирование и восстановление.
