# Файловая структура Linux-сервисов

**Тип:** Политика  
**Статус:** Действующий  
**Основной источник:** Да — для размещения кода, конфигурации, постоянных данных, журналов, кэша и временных рабочих файлов внутри Linux-гостей проекта.

Этот документ относится ко всем Linux VM/LXC проекта. Он не является частью спецификации шаблона `9000`: шаблон не создаёт каталоги будущих сервисов заранее.

## 1. Базовая модель

Для собственного сервиса используется следующая смысловая схема:

```text
/opt/<service>       → приложение, наш код, файлы развёртывания и административные скрипты
/etc/<service>       → конфигурация
/var/lib/<service>   → внутреннее постоянное состояние приложения
/srv/<service>       → данные, которые сервис предоставляет наружу
/var/log/<service>   → файловые журналы
/var/cache/<service> → пересоздаваемый кэш
/run/<service>       → файлы состояния текущего запуска
/tmp, /var/tmp       → временные файлы
```

Создаются только реально необходимые каталоги. Разделение нужно не ради формальности, а чтобы сущности с разным жизненным циклом можно было независимо обновлять, резервировать, очищать и восстанавливать.

## 2. `/opt/<service>` — приложение и развёртывание

`/opt` используется для собственного кода, вручную устанавливаемых приложений и проектной обвязки развёртывания, которые не являются штатными Debian-пакетами.

Пример:

```text
/opt/my-service/
├── app/
├── scripts/
├── deploy/
└── README.md
```

В `/opt/<service>` допустимы:

- собственный код;
- shell/Python-скрипты;
- файлы развёртывания;
- вручную поставляемые бинарники;
- Docker Compose-файлы, если они являются частью развёртывания сервиса;
- административные инструменты проекта.

Содержимое `/opt/<service>` должно по возможности восстанавливаться из Git, архива выпуска, пакета или другого воспроизводимого источника.

Не хранить там как единственную копию:

- базы данных;
- пользовательские файлы;
- большие постоянные тома;
- секреты;
- постоянно растущие журналы;
- кэш.

## 3. `/etc/<service>` — конфигурация

`/etc/<service>` хранит конфигурацию, которая должна жить отдельно от кода и обновляться независимо от приложения.

```text
/etc/my-service/
├── config.yaml
└── policy.conf
```

Конфигурация часто входит в требования к резервному копированию и восстановлению. Секреты, пароли, токены и закрытые ключи не должны попадать в Git даже тогда, когда несекретная часть конфигурации версионируется.

## 4. `/var/lib/<service>` — внутреннее постоянное состояние

`/var/lib` предназначен для изменяемого постоянного состояния приложения:

- базы данных;
- индексы;
- очереди;
- метаданные;
- файлы состояния;
- внутренние реестры и служебные данные.

Примеры штатных каталогов:

```text
/var/lib/postgresql/
/var/lib/docker/
/var/lib/prometheus/
```

Если без этих данных сервис теряет состояние, `/var/lib/<service>` обычно входит в резервную копию.

## 5. `/srv/<service>` — обслуживаемые данные

`/srv` используется для данных, ради которых работает сервис и которые он предоставляет пользователям или другим системам.

```text
/srv/files/
/srv/www/
/srv/media/
/srv/backups/
```

Разница:

```text
/var/lib → внутреннее состояние приложения
/srv     → содержимое, которое сервис предоставляет наружу
```

Такое разделение удобно и для последующего переноса больших данных на отдельное хранилище.

## 6. Журналы, кэш и файлы текущего запуска

### `/var/log/<service>`

Используется только если сервис пишет файловые журналы. Для них настраиваются сроки хранения и `logrotate`. Если сервис использует только `journald`, отдельный каталог создавать не нужно.

### `/var/cache/<service>`

Хранит данные, которые можно безопасно пересоздать. Потеря кэша не должна означать потерю пользовательских или рабочих данных. Обычно кэш не включается в резервную копию.

### `/run/<service>`

PID-файлы, Unix-сокеты, файлы блокировок и другое состояние текущего запуска. Это не постоянные данные и из резервной копии не восстанавливается.

### `/tmp` и `/var/tmp`

Только временные данные. Важные данные там не хранятся.

## 7. Сводка правил резервного копирования

| Каталог | Назначение | Обычно резервировать |
|---|---|---|
| `/opt/<service>` | код, файлы развёртывания, скрипты | нет, если воспроизводится из Git или выпуска |
| `/etc/<service>` | конфигурация | да |
| `/var/lib/<service>` | внутреннее постоянное состояние | да, если состояние важно |
| `/srv/<service>` | пользовательские или обслуживаемые данные | по ценности данных |
| `/var/log/<service>` | журналы | обычно нет |
| `/var/cache/<service>` | пересоздаваемый кэш | нет |
| `/run/<service>` | состояние текущего запуска | нет |
| `/tmp`, `/var/tmp` | временные данные | нет |

## 8. Небольшие собственные сервисы

Для небольшого сервиса допустим упрощённый старт:

```text
/opt/my-service/
├── app/
├── config/
├── data/
└── scripts/
```

Разделять каталоги следует, когда появляются разные требования к резервному копированию, хранилищу, правам, срокам хранения или обновлению.

Например:

```text
/opt/my-service/data
→ /var/lib/my-service
```

если это внутреннее состояние приложения, либо:

```text
/opt/my-service/files
→ /srv/my-service
```

если это обслуживаемые файлы.

## 9. Пакетные сервисы Debian

Для программ, установленных из Debian-пакетов или официальных сторонних пакетов, используется штатная структура самого приложения. Не нужно искусственно переносить её в проектные каталоги.

Примеры:

```text
/var/lib/postgresql
/var/lib/docker
/etc/ssh
```

Это упрощает обновление, диагностику и использование документации разработчика.

## 10. Отношение к шаблону `9000`

Базовый `tpl-debian13` не создаёт `/opt/<service>`, `/etc/<service>`, `/var/lib/<service>` или `/srv/<service>` для будущих ролей.

Шаблон отвечает только за универсальную базу Debian. Конкретная структура сервиса создаётся слоем повторяемой настройки при развёртывании соответствующей роли.

Основная спецификация шаблона находится в [`../templates/debian13/build-policy.md`](../templates/debian13/build-policy.md), а граница между `deploy-guest` и дальнейшей настройкой — в [`33-guest-bootstrap-and-provisioning.md`](33-guest-bootstrap-and-provisioning.md).

## 11. Модель восстановления

Для собственного сервиса целевой сценарий:

```text
1. Развернуть чистую Linux-гостевую систему.
2. Получить приложение и файлы развёртывания из Git → /opt.
3. Восстановить конфигурацию → /etc.
4. Восстановить постоянное состояние → /var/lib.
5. Восстановить обслуживаемые данные → /srv.
6. Запустить и проверить сервис.
7. Кэш, файлы текущего запуска и обычные журналы создать заново.
```

Главный принцип: **код должен быть воспроизводим, постоянные данные — явно отделены, а резервная копия должна сохранять только то, что нельзя безопасно получить заново.**
