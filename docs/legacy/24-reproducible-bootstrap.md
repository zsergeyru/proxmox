# Версии и воспроизводимость первоначальной настройки и конфигурации

**Тип:** Политика  
**Статус:** Действующий  
**Основной источник:** Да — для версионирования, фиксации ревизии исходного кода, повторного запуска, восстановления и границ воспроизводимости проекта.

Этот документ отвечает на вопрос **«какие изменения считаются новой версией требований и что делает запуск воспроизводимым»**. Действия оператора находятся в [`20-pve-initialization.md`](20-pve-initialization.md), файловая и рабочая структура — в [`21-pve-filesystem-layout.md`](21-pve-filesystem-layout.md), спецификация шаблона — в [`../templates/debian13/build-policy.md`](../templates/debian13/build-policy.md).

## 1. Что проект версионирует явно

Проект имеет три независимые версии собственных требований:

```text
Public Bootstrap
PVE Configuration
шаблон Debian VM
```

Конкретные текущие значения определяются соответствующим кодом и паспортом шаблона; вторичные документы не должны копировать их без необходимости.

Версии повышаются только при изменении собственных требований проекта, а не при каждой правке текста или изменении внешнего пакета.

## 2. Версия Public Bootstrap

Версия Public Bootstrap меняется, когда меняется поведение публичной точки входа, например:

- первый запуск;
- правила продолжения и повторной попытки;
- передача управления закрытой PVE Configuration;
- обновление постоянной копии исходного кода;
- правила общей блокировки запуска;
- граница доверия к исходному коду;
- передаваемые параметры и отметки состояния.

Между отдельными запусками Public Bootstrap получает актуальный `main`, но один конкретный запуск обязан зафиксировать одну точную Git-ревизию закрытого исходного кода.

## 3. Версия PVE Configuration

Версия PVE Configuration меняется при изменении требований к конфигурации хоста, например:

- файловой и рабочей структуры;
- модели учётных данных;
- ролей и ACL PVE;
- требований к хранилищам;
- схемы файлов состояния;
- ответственности контура сборки шаблона;
- правил безопасного приведения к требуемому состоянию;
- жизненного цикла проверки шаблона.

Она не обязана меняться при правке комментариев, сообщений или документации, которая не меняет требования.

## 4. Версия шаблона

Версия шаблона меняется только при изменении требований самого шаблона `9000`, заметных его клонам.

Примеры:

- административный пользователь и правила SSH;
- модель ядра и консоли;
- базовые пакеты гостевой системы, если они входят в обязательные требования;
- поведение Cloud-Init;
- правила очистки и финализации;
- поведение, видимое после клонирования.

Изменение только логики на стороне PVE-хоста или реализации проверочной VM само по себе не требует повышения `Template-Version`.

Основная спецификация шаблона: [`../templates/debian13/build-policy.md`](../templates/debian13/build-policy.md).

## 5. Одна Git-ревизия на один запуск

Один запуск PVE Configuration не должен смешивать код из разных Git-ревизий.

Нормальная модель:

```text
Public Bootstrap выбирает точную ревизию закрытого репозитория
→ передаёт SHA в PVE Configuration
→ PVE Configuration проверяет код, из которого запущена
→ основная копия репозитория синхронизируется на тот же SHA
→ файлы состояния фиксируют эту ревизию
```

Если `main` изменился после начала запуска, текущий запуск продолжает работать только со своей выбранной ревизией либо останавливается, если подтвердить её невозможно.

## 6. Граница доверия root

Код, который выполняется от `root`, должен происходить из дерева исходного кода, доверенного `root`.

Минимальные свойства:

```text
основная копия репозитория принадлежит root
родительский каталог недоступен pvedeploy на запись
repo/.git недоступен pvedeploy на запись
мастер-копия общего Git read-only key доступна постоянно только root
в рабочей копии нет локальных изменений
```

Точные пути и права задаёт [`21-pve-filesystem-layout.md`](21-pve-filesystem-layout.md).

`pvedeploy` может читать исходный код для своей работы, но не должен изменять код, который затем будет исполнен от `root`.

Принятый `access.project_repo_read` не отменяет эту границу. Если конкретному гостю нужно чтение `zsergeyru/proxmox`, root-wrapper может передать **значение фиксированного общего read-only key** текущему `deploy-guest` через отдельный file descriptor только на время этого запуска. Это не даёт `pvedeploy` постоянного доступа к root-only файлу, не позволяет выбирать другой secret и не делает гостевую копию источником доверия для PVE.

## 7. Временная и постоянная копии репозитория

Временная копия первого запуска является одноразовой и может очищаться или пересоздаваться.

Постоянная основная копия работает по принципу «при сомнении остановиться»:

```text
обнаружены локальные изменения
→ остановиться
→ не стирать их автоматически
```

Это защищает от незаметного уничтожения неизвестного локального состояния и от подмены исходного кода, который выполняется от `root`.

Рабочие копии проекта внутри 301/311 независимы от доверенной root-копии PVE. Даже если они читают GitHub тем же общим read-only credential, они не могут напрямую подменить исходный код следующего root-run на PVE.

## 8. Повторный запуск и идемпотентность

Повторный запуск должен быть штатным сценарием.

Автоматика проекта должна:

- обнаруживать уже существующее корректное состояние;
- повторно использовать его;
- добавлять только недостающее там, где это безопасно;
- не менять учётные данные без отдельного решения;
- не уничтожать неоднозначные VM/LXC, шаблоны или проверочные объекты;
- после приведения к требуемому состоянию обязательно проверять результат.

Для локальной копии общего Git read-key повторный запуск может подтвердить fingerprint/права и вернуть `NO CHANGE`; ротация или отзыв общего key является отдельной явной операцией, а не побочным эффектом обычного deploy.

При неоднозначности остановка предпочтительнее разрушительной догадки.

## 9. Состояние и сохранность отметок

Состояние на стороне хоста должно позволять понять как минимум:

- выполнялся ли запуск;
- какая ревизия исходного кода использовалась;
- завершился ли он успешно, ошибкой или прерыванием;
- в каком состоянии находится проверка шаблона;
- какая ревизия была последней успешно применённой.

Файлы состояния по возможности должны записываться атомарно.

Точные пути к ним принадлежат [`21-pve-filesystem-layout.md`](21-pve-filesystem-layout.md).

## 10. Сохранность одноразового секрета API-токена

Одноразовый секрет API-токена нельзя повторно получить из PVE после создания.

Поэтому создание токена и сохранение его секрета рассматриваются как одна чувствительная к сбою операция:

```text
создать токен
→ получить одноразовый секрет
→ безопасно записать его во временный файл
→ выставить владельца и права
→ атомарно переместить файл в основное место
→ считать операцию завершённой
```

Если новый токен текущего запуска создан, но его секрет сохранить не удалось, автоматика может удалить именно этот новый незавершённый токен.

Уже существующий токен не удаляется и не меняется автоматически.

## 11. Внешние компоненты

Для внешних стабильных компонентов по умолчанию не фиксируется каждая точная ревизия пакета.

Базовый принцип:

```text
доверенный стабильный канал
→ штатная проверка контрольной суммы или подписи, если она доступна
→ явная проверка результата после установки
```

Точная фиксация версии или архивный репозиторий вводятся только там, где есть практическая потребность в более строгой воспроизводимости.

Это относится в том числе к пакетам Debian и ревизиям LXC-образов.

## 12. Что считается воспроизводимым результатом

Проект не гарантирует побайтово идентичный хост или образ гостевой системы.

Гарантируется воспроизводимость **требуемых свойств**:

```text
те же правила проекта
те же исходные манифесты
совместимые внешние стабильные компоненты
→ ожидаемые свойства хоста и гостевых систем
→ обязательная проверка результата
```

Ревизии исходного образа или пакетов могут отличаться между датами сборки, если они удовлетворяют принятой политике.

## 13. CI и проверка на реальном PVE

CI должна проверять статические требования настолько, насколько это возможно:

- проверку репозитория и схем;
- синтаксис Python и shell;
- статический анализ;
- генератор шаблона и его схему;
- модульные проверки безопасности, состояния и повторного применения;
- проверки границы доверия к исходному коду;
- отсутствие запрещённых устаревших точек входа.

После реализации `access.project_repo_read` CI также должна проверять, что manifest не может выбирать произвольный secret/path/write access, а root-wrapper передаёт только фиксированный общий Git read-key.

CI не заменяет настоящий Proxmox.

Реальные свойства хоста, шаблона и полного клона подтверждаются PVE Configuration и проверочной VM согласно спецификации шаблона.
