# Безопасность инфраструктуры

**Тип:** Политика  
**Статус:** Действующий  
**Основной источник:** Да — для общих правил безопасности и границ административного SSH-доступа.

Точный жизненный цикл инфраструктурных SSH-ключей, каталог открытых ключей, `management.ssh_identity`, PVE tag `management-ssh` и `sync-management-keys` задаёт [`28-management-ssh-keys.md`](28-management-ssh-keys.md). Точные роли, привилегии и ACL Proxmox задаёт [`25-pve-access-control.md`](25-pve-access-control.md).

## 1. Основные правила

1. Автоматизация управляет только теми VM/LXC, для которых это разрешено соответствующим механизмом доступа.

2. Сам Proxmox не изменяется автоматикой гостевых систем без отдельного решения. Особенно это относится к сети хоста, хранилищам, пользователям, ролям, ACL, API-токенам, сертификатам, репозиториям, firewall и управлению питанием физического хоста.

3. Для управляемых Debian VM/LXC единый административный пользователь — `root`. Пароль `root` заблокирован; вход по паролю и интерактивная аутентификация с клавиатуры отключены. SSH-доступ `root` разрешён только по открытому ключу.

4. Разные субъекты административного управления используют независимые пары SSH-ключей. Закрытый административный ключ остаётся на системе, откуда инициируется действие.

5. ACL PVE и SSH-доступ внутрь гостевой системы решают разные задачи. Наличие прав на VM/LXC через API Proxmox само по себе не означает SSH-доступ внутрь ОС и наоборот.

6. Пароли, токены, закрытые ключи и другие секреты не хранятся в Git. Открытые SSH-ключи секретами не являются, но их происхождение, регистрация, распространение и отзыв должны быть управляемыми.

7. Перед разрушительной операцией проверяются правильность выбранного объекта и наличие способа восстановления.

8. После изменения проверяются фактическое состояние гостевой системы, работа нужных сервисов и ошибки.

9. Действия автоматики журналируются без значений секретов.

10. Если автоматике не хватает прав, она не расширяет их самостоятельно. Изменение доступа является отдельным инфраструктурным решением.

## 2. Модель административного SSH-доступа

Для Debian-гостей принят единый набор требований:

```text
user: root
port: 22
root password: locked
PermitRootLogin: prohibit-password
PasswordAuthentication: no
KbdInteractiveAuthentication: no
PermitEmptyPasswords: no
PubkeyAuthentication: yes
```

Универсальный административный пользователь `ops` не является частью требований проекта.

Одновременно могут существовать независимые SSH identities:

```text
ключ deployer на PVE
ключ AI Control
ключ Ansible
личный ключ — при необходимости
другие технические ключи — при необходимости
```

Несколько субъектов могут входить как `root`, но каждый использует собственный закрытый ключ. Отзыв одной identity не должен ломать остальные каналы управления.

Точный механизм регистрации и распространения их открытых частей определяет [`28-management-ssh-keys.md`](28-management-ssh-keys.md).

## 3. SSH identity deployer

Постоянная техническая пара средства развёртывания на PVE:

```text
/etc/proxmox-deployer/ssh/pve_guest_ed25519
/etc/proxmox-deployer/ssh/pve_guest_ed25519.pub
```

Несмотря на историческое имя файла, это **SSH identity deployer для входа в гостевые ОС**, а не идентичность самого гипервизора Proxmox.

Закрытый ключ остаётся на PVE, не хранится в Git и не попадает в шаблон. Пара создаётся PVE Configuration, а обычный `deploy-guest` её не генерирует и не ротирует.

Открытая часть регистрируется как базовый ключ канонического public-key registry и должна присутствовать в наборе ключей новых управляемых Debian-гостей.

Потеря закрытого ключа является отдельной ситуацией восстановления; незаметная автоматическая смена запрещена.

## 4. SSH identities управляющих гостей

AI Control, Ansible и будущие управляющие Debian-гости не получают заранее зашитые в PVE Configuration специальные ключи по имени роли или VMID.

Если конкретному гостю требуется собственная management SSH identity, это описывается целевым полем внутри единого раздела `management`:

```yaml
management:
  ssh_identity: true
```

`deploy-guest` после появления собственного SSH-доступа deployer обеспечивает стандартную пару **внутри этого гостя**. Закрытая часть остаётся только в госте; наружу забирается лишь `.pub`, которая регистрируется в каноническом каталоге на PVE.

После регистрации новый public key распространяется отдельным `sync-management-keys`. Поэтому AI, Ansible и другие управляющие системы не должны иметь SSH/root-доступ к PVE ради регистрации своих ключей и не должны писать в `/etc/proxmox-deployer`.

Точный контракт, стандартные пути, повторный запуск, ротация и обработка ошибок находятся в [`28-management-ssh-keys.md`](28-management-ssh-keys.md).

## 5. Канонический каталог открытых management keys

На PVE поддерживается один канонический публичный каталог:

```text
/etc/proxmox-deployer/public-keys/
```

Он содержит только открытые административные SSH-ключи и производный `management-authorized-keys`. Закрытых ключей, API-токенов и Git credentials в нём нет.

Отдельный скрипт:

```bash
sync-management-keys
```

синхронизирует публичный каталог и управляемый набор `authorized_keys` только по Debian VM/LXC с техническим PVE tag:

```text
management-ssh
```

Tag является необходимым признаком участия, но не отменяет fail-closed проверку типа объекта, SSH host key и ожидаемого management-контракта.

Для Debian-гостя, развёрнутого через `deploy-guest`, tag выводится из наличия `management.ssh` в effective state. Для Debian-гостя, создаваемого AI или другим управляющим контуром напрямую через PVE API, создатель обязан поставить тот же tag одновременно с передачей `management-authorized-keys`.

Tag `management-ssh` не является признаком lifecycle ownership и не заменяет `proxmox-deployer`.

Управляющий гость получает локальную копию каталога и использует её при создании новой VM/LXC, чтобы новая машина сразу получила существующие management public keys, в том числе ключ deployer. Поэтому отдельный канал записи `AI → PVE` не требуется.

## 6. Общий GitHub Deploy Key только для чтения

Для чтения закрытого проектного репозитория:

```text
git@github.com:zsergeyru/proxmox.git
```

принят один общий GitHub Deploy Key с правами **read-only**.

Мастер-копия хранится на PVE:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519.pub
```

Закрытая мастер-копия остаётся `root:root 0600`. `pvedeploy` не получает постоянного права чтения этого файла.

Гость может запросить только логическую возможность внутри того же раздела `management`:

```yaml
management:
  project_repo_read: true
```

Это поле означает ровно одно: локальная копия фиксированного общего read-only Deploy Key может быть материализована в этом госте для `clone/fetch` основного репозитория. `guest.yaml` не содержит имя файла секрета, путь на PVE, private key, имя произвольного credential или возможность выбрать другой секрет.

При deploy root-wrapper открывает мастер-копию только если текущему гостю требуется `management.project_repo_read`, передаёт значение текущему запуску через отдельный file descriptor и закрывает его после запуска. Значение не передаётся через аргументы командной строки или environment и не журналируется.

Стандартное место локальной копии внутри управляемого Debian-гостя:

```text
/etc/proxmox-guest/credentials/github-proxmox-read
```

с владельцем `root:root` и режимом `0600`.

Общий read-key разрешает только чтение `zsergeyru/proxmox`. Он не является административным SSH-ключом гостя, SSH-ключом PVE, PVE API token или GitHub credential с правом записи.

Нахождение `ssh_identity` и `project_repo_read` в одном manifest-разделе не объединяет credentials: у них разные private keys, назначения и lifecycle.

Если AI требуется `push`, создание веток или PR через Git credential, это отдельный write-контур. Общий read-key никогда не повышается до write ради этой задачи.

## 7. Личные и другие технические ключи

Личный закрытый ключ хранится только на устройстве человека. В гостевую систему при необходимости добавляется только открытая часть.

Наличие канонического management public-key registry не означает, что любая произвольная `.pub` автоматически должна туда попадать. Каталог предназначен для инфраструктурных identities, которым требуется систематический административный доступ к управляемым Debian-гостям.

Личные, аварийные или иные ключи могут оставаться вне управляемого блока `authorized_keys` и не должны уничтожаться при синхронизации.

## 8. `authorized_keys` гостевой системы

Одна Debian-гостевая система может содержать несколько независимых открытых ключей пользователя `root`.

`sync-management-keys` владеет только выделенным блоком инфраструктурных ключей и не перезаписывает неизвестные строки целиком. Логически:

```text
/root/.ssh/authorized_keys

<личные/внешние ключи, которыми sync не управляет>

# BEGIN PROXMOX-MANAGEMENT-KEYS
<актуальный management-authorized-keys>
# END PROXMOX-MANAGEMENT-KEYS
```

Git read-key здесь отсутствует: он используется клиентом для исходящего соединения гостя с GitHub.

## 9. Учётные данные в шаблоне

Шаблон `9000` не содержит административных или Git-учётных данных:

```text
пароль root заблокирован
/root/.ssh отсутствует перед финализацией
список административных authorized_keys пуст
закрытые административные ключи отсутствуют
общий Git read-key отсутствует
```

Каждый клон получает нужные management public keys отдельно при создании. Если клон должен иметь собственную management identity, её private key создаётся уже внутри готового гостя по контракту:

```yaml
management:
  ssh_identity: true
```

SSH host keys (`/etc/ssh/ssh_host_*`) идентифицируют сервер, а не клиента. Они удаляются перед финализацией шаблона, чтобы каждый клон создал собственные уникальные ключи сервера.

Подробная спецификация шаблона: [`../templates/debian13/build-policy.md`](../templates/debian13/build-policy.md).

## 10. Доступ через консоль Proxmox

Консоль Proxmox для Debian-шаблона даёт локальный доступ `root`. Поэтому привилегия `VM.Console` фактически является административным доступом внутрь гостевой системы и выдаётся только доверенным учётным записям PVE.

Точные ACL PVE находятся в [`25-pve-access-control.md`](25-pve-access-control.md).

## 11. Резервные копии и закрытые ключи

Если закрытый technical management key находится внутри рабочей VM/LXC, полная резервная копия этого гостя содержит такой ключ и должна считаться чувствительным объектом.

В частности, backup управляющего гостя с `management.ssh_identity: true` содержит его собственный private key. Если гостю также выдан общий Git read-key через `management.project_repo_read`, backup содержит и его локальную копию.

Ключи на стороне PVE:

```text
/etc/proxmox-deployer/ssh/pve_guest_ed25519
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
```

не входят в резервную копию отдельной гостевой системы и должны отдельно резервироваться как инфраструктурные секреты PVE.

Каталог:

```text
/etc/proxmox-deployer/public-keys/
```

секретом не является, но полезен для восстановления; при необходимости он может быть восстановлен из проверенных открытых частей соответствующих identities.

## 12. Главный принцип

> Доступ к Proxmox, административный SSH внутрь гостевой системы, чтение проектного Git и права приложения — независимые уровни. `management` объединяет их описание в manifest только там, где они относятся к управлению гостем, но не объединяет сами credentials. Закрытые management SSH keys остаются у своих владельцев; их открытые части централизованно регистрируются у deploy-контура и распространяются `sync-management-keys` по объектам с tag `management-ssh`. Общий Git read-key является отдельным credential и никогда не используется для административного SSH.
