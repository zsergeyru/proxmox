# Безопасность инфраструктуры

Этот документ фиксирует общие правила безопасности проекта. Частные ограничения для отдельных виртуальных машин, контейнеров и сервисов описываются в их собственной документации.

## Основные правила

1. Автоматизация управляет только теми виртуальными машинами и контейнерами, для которых это явно разрешено соответствующим механизмом доступа.

2. Сам Proxmox не изменяется автоматикой без отдельного решения. Особенно это относится к:
   - сетевым мостам и физическим сетевым интерфейсам;
   - маршрутам самого сервера;
   - настройкам хранилищ;
   - пользователям, ролям и правам доступа;
   - репозиториям обновлений и сертификатам;
   - сетевому экрану самого Proxmox;
   - выключению и перезагрузке физического сервера.

3. Для управляемых Debian VM/LXC единый management user — `root`. Пароль root заблокирован; `PasswordAuthentication` и keyboard-interactive authentication отключены. Root SSH допускается только по public key.

4. Разные потребители используют разные SSH identities, а не разные Linux-пользователи. Как минимум host-side deployer и AI control используют независимые ключи. Удаление public key одной identity отзывает только её доступ и не затрагивает остальные.

5. PVE ACL и guest SSH решают разные задачи. Pool `managed` ограничивает Proxmox guest-level операции AI через PVE API; наличие отдельного AI public key определяет возможность прямого SSH внутрь конкретной Linux VM/LXC. Эти механизмы не должны автоматически синхронизироваться друг с другом.

6. Пароли, токены, закрытые ключи и другие секреты не хранятся в Git. Public SSH keys секретами не являются, но их lifecycle должен быть явным и проверяемым.

7. Перед удалением, откатом или другим опасным изменением необходимо проверить правильность выбранного объекта и наличие способа восстановления: резервной копии, снимка состояния или воспроизводимой конфигурации.

8. После изменения обязательно проверяется результат: состояние гостя, работа нужных служб и журналы ошибок.

9. Действия автоматизации по возможности журналируются. В журнале должно быть понятно, что и над каким объектом было сделано, но секретные значения туда попадать не должны.

10. Для контейнеров используются минимально необходимые привилегии. Если сервису требуются широкие системные права или особый доступ к оборудованию, предпочтительнее отдельная виртуальная машина. Подробные правила Docker внутри LXC описаны в [`32-docker-in-lxc-policy.md`](32-docker-in-lxc-policy.md).

11. Если автоматике не хватает прав, она не должна расширять их самостоятельно. Изменение прав является отдельным инфраструктурным решением.

## Главный принцип

> Proxmox-права, SSH-доступ и application permissions разделены. Management SSH для Debian-гостей выполняется как root только по независимым ключам; каждый credential можно отозвать отдельно.

Дополнительные правила конкретных подсистем описываются в соответствующих документах и ADR.
