# Roadmap

## Ближайшие задачи

1. Проверить два наблюдаемых вопроса текущего PVE-хоста: каким механизмом после reboot монтируется USB storage `/mnt/pve/backup`, и почему в `/etc/network/interfaces` присутствует `nic1`, которого нет в `ip -br link`.
2. Развернуть и проверить `101-network-gateway` с DNS, исходящими VPN, remote-access VPN, PBR и firewall, сохранив независимый аварийный доступ к Proxmox.
3. Реализовать переходную сетевую схему: текущая `192.168.0.0/16` остаётся рабочей, Keenetic получает будущий gateway `10.0.0.1/16`, а новые серверы сразу используют постоянные `10.0.x.x/16`.
4. Развернуть `311-dev-services` как DevOps/deploy-контур: Ansible в Docker как штатный повторяемый deploy по SSH; Semaphore в Docker как ручной web-интерфейс; затем постепенно добавить Git/CI-сервисы.
5. Подготовить целевую `301-ai-control` на основе решений, проверенных на текущем bootstrap-узле `320-ai-control`; проверить Proxmox MCP, прямой SSH и запуск повторяемого deploy через Ansible на `311`, затем переносить управление и только после проверки выводить 320 из эксплуатации.
6. Определить startup/shutdown order и аварийный путь доступа, не зависящий от `101-network-gateway` и не требующий Semaphore.
7. Реализовать минимальные Ansible playbook для безопасного применения `rootfs/`: принадлежащие проекту `/opt/<service>/` можно синхронизировать с удалением, системные файлы устанавливаются по конкретным путям, их удаление выполняется явно; глобальный `rsync --delete rootfs/ /` запрещён.
8. Выбрать VM/LXC для `501-frigate` после теста iGPU/OpenVINO.
9. Настроить временную двухуровневую backup-схему: основной внешний backup на SMB/CIFS-папку обычного компьютера и дополнительная копия на текущий USB storage; затем определить расписание, retention и выполнить практический restore-тест. NAS/PBS пока не вводятся.
10. Проверить параметры IPv6 у провайдера новой квартиры: native IPv6, DHCPv6-PD, размер и стабильность префикса; после этого включать dual stack по плану из [`ipv6.md`](ipv6.md).
11. Переносить из `appart-rennovation` только эксплуатационные серверные сведения, не дублируя общий проект квартиры.

## Уже зафиксировано

- фактический PVE-хост: Proxmox VE 9.2.18, Debian 13, kernel 7.0.14-16-pve, Intel N150, 15 GiB RAM;
- текущий management IP PVE `192.168.1.11/16`, gateway `192.168.1.1`, bridge `vmbr0` через `nic0`;
- фактические storage/LVM, swap 8 GiB и текущий USB storage `backup`;
- реально существующие гости: `100 HAOS` и `320 ai-agent`; LXC на момент inventory отсутствуют;
- VM `100 HAOS` зафиксирована как текущая legacy production-система;
- `320-ai-control` зафиксирован как bootstrap, включая observed drift между `guest.yaml` и фактическим `qm config`;
- целевая VMID/CTID-схема и читаемое соответствие VMID → `10.0.X.YZ`;
- серверы размещаются в MAIN `10.0.0.0/16`, отдельный server VLAN пока не используется;
- IOT и CAMERAS изолируются отдельными VLAN;
- переходная схема `192.168.0.0/16` → `10.0.0.0/16` без массовой перенастройки серверов в день переезда;
- `home.arpa` принят как основной внутренний DNS-домен, `.local` оставлен для mDNS; mDNS reflection между VLAN включается только при необходимости;
- remote-access VPN как часть `101-network-gateway`;
- IPv6 как дополнительный dual-stack, а не замена IPv4;
- структура гостей `README.md + guest.yaml + rootfs/`;
- Ansible и Semaphore закреплены за `311-dev-services`, а не за `ai-control`;
- Ansible принят как штатный механизм повторяемого deploy внутри гостей через SSH; Semaphore — ручной web-интерфейс и не обязательный слой для Hermes;
- для `rootfs/` принята простая модель без собственной базы managed files: `--delete` только внутри полностью принадлежащих проекту каталогов, системные файлы — поштучно и с явным удалением;
- временная backup-схема: планируемый основной внешний backup через SMB/CIFS на обычный компьютер, текущий USB storage остаётся дополнительной копией; NAS/PBS пока не вводятся;
- `301-ai-control` определён как целевой control plane.

Статусы конкретных гостей ведутся в `guest.yaml` и при необходимости в `README.md`/`STATUS.md`. Актуальная нумерация VMID/CTID определяется только [`vmid-plan.md`](vmid-plan.md).
