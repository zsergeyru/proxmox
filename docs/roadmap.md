# Roadmap

## Ближайшие задачи

1. Проверить, каким механизмом после reboot монтируется USB storage `/mnt/pve/backup`; отдельно выполнить контрольную проверку интерфейсов PVE и после неё убрать остаточную строку `iface nic1 inet manual`, поскольку сервер имеет одну физическую Ethernet-карту.
2. Развернуть и проверить `101-network-gateway` в текущей отдельной серверной сети Keenetic без VLAN: DNS, исходящие VPN, remote-access VPN, PBR и firewall, сохранив независимый аварийный доступ к Proxmox.
3. Реализовать первый этап сетевой миграции без VLAN: текущий Keenetic сохраняет три направления — Internet/WAN, общую домашнюю сеть и отдельную серверную сеть; на серверном сегменте заранее проверить будущую адресацию `10.0.0.0/16` и сетевые сервисы `101`.
4. Подготовить второй этап сети для новой квартиры: тот же единственный Ethernet-порт Proxmox использовать как VLAN trunk; MAIN/IOT/CAMERAS разделить VLAN, вероятно с OpenWrt как физическим edge-router. Точное разделение L3/firewall-функций OpenWrt и `101-network-gateway` определить перед переездом.
5. Развернуть `311-dev-services` как DevOps/deploy-контур: Ansible в Docker как штатный повторяемый deploy по SSH; Semaphore в Docker как ручной web-интерфейс; затем постепенно добавить Git/CI-сервисы.
6. Подготовить целевую `301-ai-control` на основе решений, проверенных на текущем bootstrap-узле `320-ai-control`; проверить Proxmox MCP, прямой SSH и запуск повторяемого deploy через Ansible на `311`, затем переносить управление и только после проверки выводить 320 из эксплуатации.
7. Определить startup/shutdown order и аварийный путь доступа, не зависящий от `101-network-gateway` и не требующий Semaphore.
8. Реализовать минимальные Ansible playbook для безопасного применения `rootfs/`: принадлежащие проекту `/opt/<service>/` можно синхронизировать с удалением, системные файлы устанавливаются по конкретным путям, их удаление выполняется явно; глобальный `rsync --delete rootfs/ /` запрещён.
9. Выбрать VM/LXC для `501-frigate` после теста iGPU/OpenVINO.
10. Настроить временную двухуровневую backup-схему: основной внешний backup на SMB/CIFS-папку обычного компьютера и дополнительная копия на текущий USB storage; затем определить расписание, retention и выполнить практический restore-тест. NAS/PBS пока не вводятся.
11. Проверить параметры IPv6 у провайдера новой квартиры: native IPv6, DHCPv6-PD, размер и стабильность префикса; после этого включать dual stack по плану из [`ipv6.md`](ipv6.md).
12. Переносить из `appart-rennovation` только эксплуатационные серверные сведения, не дублируя общий проект квартиры.

## Уже зафиксировано

- фактический PVE-хост: Proxmox VE 9.2.18, Debian 13, kernel 7.0.14-16-pve, Intel N150, 15 GiB RAM;
- текущий management IP PVE `192.168.1.11/16`, gateway `192.168.1.1`, bridge `vmbr0` через `nic0`;
- PVE имеет одну физическую Ethernet-карту; вся текущая и будущая серверная сеть проектируется через один `nic0`;
- текущая физическая схема Keenetic содержит три направления: Internet/WAN, общую домашнюю сеть и отдельную серверную сеть, к которой подключён Proxmox;
- до переезда VLAN на серверном соединении не используются; DNS/VPN/PBR и другие сетевые сервисы `101-network-gateway` разворачиваются уже на этом этапе;
- после переезда тот же единственный Ethernet-порт Proxmox должен поддерживать VLAN trunk; вероятный физический edge-router — OpenWrt, но окончательное разделение ролей OpenWrt и `101` пока не принято;
- фактические storage/LVM, swap 8 GiB и текущий USB storage `backup`;
- реально существующие гости: `100 HAOS` и `320 ai-agent`; LXC на момент inventory отсутствуют;
- VM `100 HAOS` зафиксирована как текущая legacy production-система;
- `320-ai-control` зафиксирован как bootstrap, включая observed drift между `guest.yaml` и фактическим `qm config`;
- целевая VMID/CTID-схема и читаемое соответствие VMID → `10.0.X.YZ`;
- целевая MAIN — `10.0.0.0/16`; отдельный server VLAN в новой квартире пока не используется;
- IOT и CAMERAS изолируются отдельными VLAN на втором этапе;
- переходная схема к `10.0.0.0/16` должна позволить проверить постоянные адреса серверов до физического переезда;
- `home.arpa` принят как основной внутренний DNS-домен, `.local` оставлен для mDNS; mDNS reflection между VLAN включается только при необходимости;
- remote-access VPN как часть `101-network-gateway`;
- IPv6 как дополнительный dual-stack, а не замена IPv4;
- структура гостей `README.md + guest.yaml + rootfs/`;
- Ansible и Semaphore закреплены за `311-dev-services`, а не за `ai-control`;
- Ansible принят как штатный механизм повторяемого deploy внутри гостей через SSH; Semaphore — ручной web-интерфейс и не обязательный слой для Hermes;
- для `rootfs/` принята простая модель без собственной базы managed files: `--delete` только внутри полностью принадлежащих проекту каталогов, системные файлы — поштучно и с явным удалением;
- временная backup-схема: планируемый основной внешний backup через SMB/CIFS на обычный компьютер, текущий USB storage остаётся дополнительной копией; NAS/PBS пока не вводятся;
- `301-ai-control` определён как целевой control plane.

Статусы конкретных гостей ведутся в `guest.yaml` и при необходимости в `README.md`/`STATUS.md`. Актуальная нумерация VMID/CTID определяется только [`vmid-plan.md`](vmid-plan.md).
