# Восстановление резервных копий и аварийное восстановление

**Тип:** Инструкция  
**Статус:** Действующий  
**Основной источник:** Да — для пошаговой проверки восстановления и восстановления PVE после потери хоста.

Требования к резервным копиям, срокам хранения и RPO/RTO определены в [`22-storage-and-backup.md`](22-storage-and-backup.md). Этот документ отвечает только на вопрос **«как проверить восстановление и что делать при аварии»**.

## 1. Проверка восстановления одной гостевой системы

Для критичных систем такую проверку выполнять не реже одного раза в три месяца и после существенных изменений схемы резервного копирования или хранения.

Порядок:

1. выбрать актуальную резервную копию;
2. убедиться, что исходная рабочая гостевая система не будет затронута;
3. выбрать свободный временный VMID/CTID;
4. восстановить копию во временный объект или изолированную среду;
5. не подключать восстановленную гостевую систему к рабочей сети, если существует риск конфликта IP, имени хоста или идентификаторов сервисов;
6. запустить восстановленную систему;
7. проверить загрузку ОС;
8. проверить работу ключевого приложения или сервиса;
9. проверить наличие ожидаемых постоянных данных;
10. зафиксировать результат, дату и фактическое время восстановления;
11. после успешной проверки остановить и удалить временную гостевую систему.

Проверка считается успешной только если сервис действительно запускается и необходимые данные доступны.

## 2. Что зафиксировать по результату проверки

Минимальная запись:

```text
дата
исходная резервная копия
временный VMID/CTID
проверенный сервис
результат: успешно/ошибка
время восстановления
обнаруженные проблемы
последующие действия
```

Если тест выявил проблему, исправить цепочку резервного копирования и восстановления и повторить проверку.

## 3. Полная потеря системного диска PVE

Базовый порядок:

```text
чистая установка Proxmox VE
→ вернуть имя хоста и базовую сеть управления
→ восстановить постоянные инфраструктурные учётные данные
→ запустить Public Bootstrap / PVE Configuration
→ проверить конфигурацию хоста
→ подключить хранилища резервных копий
→ убедиться, что копии доступны
→ восстановить критичные VM/LXC
→ проверить критичные сервисы
→ восстановить остальные гостевые системы
→ проверить задания резервного копирования
```

Инструкция инициализации чистого хоста: [`20-pve-initialization.md`](20-pve-initialization.md).

## 4. Что восстановить до запуска проектной настройки

На полностью новом хосте сначала требуется вернуть минимум, необходимый для безопасного запуска автоматики проекта:

- корректное имя хоста;
- сеть управления и доступ к PVE;
- постоянные учётные данные, которые нельзя получить повторно без смены ключей или токенов;
- доступ к закрытому исходному коду проекта на GitHub по принятой процедуре первоначальной настройки.

Точные пути и владельцы определены в [`21-pve-filesystem-layout.md`](21-pve-filesystem-layout.md).

## 5. Инфраструктурные учётные данные

Особое внимание:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
/etc/proxmox-deployer/ssh/pve_guest_ed25519
/etc/proxmox-deployer/secrets/host-deploy.token
/etc/proxmox-deployer/secrets/ai-agent-infra.token
```

### Если `pve_guest_ed25519` восстановлен

Продолжить штатную настройку PVE и затем проверить SSH-доступ с хоста к тестовой Debian-гостевой системе.

### Если `pve_guest_ed25519` потерян

Не генерировать новую пару как незаметную замену старой.

Порядок:

```text
осознанно создать и зарегистрировать новую пару ключей
→ определить гостевые системы со старым открытым ключом
→ добавить новый открытый ключ
→ проверить доступ новым закрытым ключом
→ только после проверки удалить старый открытый ключ, если это требуется
```

Это отдельная операция восстановления и смены ключей.

### Если потерян GitHub Deploy Key

Создать новый Deploy Key, зарегистрировать его открытую часть на GitHub и восстановить основной ключ доступа на PVE по правилам первоначальной настройки. Старый ключ считается утраченным и отзывается.

## 6. Подключение хранилищ резервных копий

После восстановления конфигурации хоста:

1. подключить SMB/CIFS-хранилище резервных копий;
2. подключить и проверить USB-хранилище, если оно требуется;
3. убедиться, что Proxmox видит содержимое с резервными копиями;
4. проверить свободное место и права доступа;
5. не начинать восстановление рабочих систем, пока источник резервных копий не проверен чтением и просмотром содержимого.

Фактические сведения о хранилищах нужно брать из [`../host/pve/storage/README.md`](../host/pve/storage/README.md) и [`../host/pve/backup/README.md`](../host/pve/backup/README.md), а не из этой инструкции.

## 7. Порядок восстановления гостевых систем

Рекомендуемый приоритет:

```text
1. критичная сеть и управляющий контур, если без них невозможно продолжение
2. рабочий Home Assistant
3. остальные критичные сервисы
4. прикладные сервисы и сервисы данных
5. мониторинг
6. разработка, тесты и легко воспроизводимые гостевые системы
```

Конкретный порядок может меняться в зависимости от зависимостей между сервисами.

Перед каждым восстановлением проверить:

- правильный VMID/CTID;
- целевое хранилище;
- сетевую конфигурацию;
- отсутствие конфликта с уже существующей гостевой системой;
- наличие нужной версии резервной копии.

## 8. Проверка после восстановления хоста

Минимальный перечень приёмочных проверок:

```text
PVE доступен по сети управления
Public Bootstrap / PVE Configuration проходят успешно
основная копия проекта не содержит локальных изменений
хранилища доступны
учётные записи и ACL проекта в PVE работают
текущий шаблон 9000 валиден
критичные гостевые системы запущены
критичные приложения работают
SSH-доступ с PVE-хоста работает
задания резервного копирования снова включены
новая резервная копия после восстановления создаётся успешно
```

## 9. Учебное восстановление

После существенного изменения архитектуры первоначальной настройки или резервного копирования рекомендуется выполнить учебный сценарий в безопасной тестовой среде:

```text
чистый PVE
→ восстановить инфраструктурные учётные данные
→ выполнить первоначальную настройку и конфигурацию
→ подключить хранилище резервных копий
→ восстановить тестовую VM/LXC
→ проверить загрузку, сервис и административный доступ
→ создать новую резервную копию
```

Цель такого теста — проверить всю цепочку, а не только отдельный файл резервной копии.

## 10. Когда остановиться

Остановиться и не выполнять разрушительную очистку, если:

- неясно, какая резервная копия является правильной;
- целевой VMID/CTID уже занят неизвестным объектом;
- сопоставление хранилищ отличается от ожидаемого;
- учётные данные восстановлены только частично и их происхождение неизвестно;
- восстановленная гостевая система может конфликтовать с рабочей по IP, имени хоста или идентификаторам сервисов;
- нет способа проверить результат.

В неоднозначной ситуации сначала сохранить текущее состояние и разобраться в расхождении.
