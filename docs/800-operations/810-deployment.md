## 1. Предварительные условия

На чистом PVE должны быть доступны базовая сеть, хранилища, Debian LXC template для первоначального 910 и read-only GitHub Deploy Key, зарегистрированный для проекта.

Секретные значения не передаются через Git.

## 2. Общая схема

~~~text
PVE
→ минимальный bootstrap
→ временный LXC 990
→ создание 910
→ подключение постоянных PVE-каталогов
→ общий provision.yaml + Ansible
→ OpenBao
→ KV + SSH CA + policies
→ Semaphore / OpenTofu / Ansible / Packer
→ обычные VM/LXC
~~~

PVE не становится постоянным узлом общей автоматизации.

## 3. Временный первоначальный контур 990

990 существует только во время первоначального создания или полного восстановления 910.

До появления OpenBao он получает Git-проект через защищённый recovery read-only Deploy Key из PVE-only области.

Для создания 910 допускается временный PVE API-доступ, жизненный цикл которого заканчивается после передачи управления постоянному контуру.

990 хранит отдельное OpenTofu state только для объекта 910. Постоянный OpenTofu state самого 910 не владеет ресурсом 910.

## 4. Создание 910

Объект 910 создаётся по общему `guest.yaml` и профильному контракту.

Первоначальный контур может использовать раздельные фазы `deploy-guest`, если постоянные mount points и доступы необходимо подготовить между созданием объекта и полной настройкой Linux.

Специальный жизненный цикл объекта 910 не должен порождать отдельный второй способ настройки его ОС.

## 5. Подготовка постоянного состояния PVE

До полной настройки 910 на PVE создаётся канонический корень:

~~~text
pve-only
access
state
~~~

`pve-only` в 910 не монтируется.

`access` подключается только для чтения.

`state` подключается для чтения и записи.

Recovery SSH и recovery Git private keys остаются только в PVE-only.

Рабочие PVE API и Git credentials не передаются 910 как постоянные файлы: после запуска OpenBao они хранятся и выдаются через KV.

## 6. Настройка 910

Общий Ansible применяет `infrastructure/guests/910-infra-manager/provision.yaml`.

Он должен обеспечить:

- базовую Debian-систему;
- Docker;
- постоянные mount points;
- root SSH-доступ 910 к PVE через PVE-owned read-only identity;
- PVE CA;
- Semaphore и `infra-runtime`;
- OpenTofu, Ansible и Packer;
- контейнер OpenBao с Raft на внешнем `state/openbao/`.

Воспроизводимый Git checkout и Compose-файлы создаются заново и не считаются уникальным состоянием.

## 7. Инициализация OpenBao

Для пустого OpenBao доверенный PVE-only механизм:

1. выполняет инициализацию;
2. сохраняет unseal key только в PVE-only;
3. создаёт KV v2;
4. создаёт SSH Client CA и SSH Host CA;
5. создаёт auth methods и минимальные служебные policies;
6. публикует открытые CA;
7. отзывает initial root token.

Для существующего `state/openbao/` повторная инициализация запрещена.

OpenBao получает постоянные данные только через `state/openbao/` на PVE.

## 8. Подготовка рабочих secrets и policies

После готовности OpenBao:

- рабочий PVE API secret помещается в KV;
- рабочее представление read-only GitHub Deploy Key помещается в KV;
- создаются остальные инфраструктурные secrets;
- `infrastructure/security/access.yaml` преобразуется в OpenBao policies и roles;
- при необходимости создаются отдельные machine identities гостей.

Recovery-копия Git key остаётся в PVE-only и не заменяется рабочим KV-секретом.

## 9. Развёртывание обычного гостя

Обычный поддерживаемый Linux-гость проходит:

~~~text
guest.yaml
→ OpenTofu
→ первоначальный SSH
→ установка доверия к OpenBao SSH Client CA
→ provision.yaml
→ SSH Host Certificate
→ recovery public key
→ общая настройка online SSH helper, если гость участвует в межмашинном доступе
~~~

Приложения и пакеты определяет `provision.yaml`. Межсистемные права определяет `access.yaml`.

## 10. Изменение политики доступа

Обычное изменение `access.yaml` не должно приводить к повторному развёртыванию всех Linux-гостей.

`infra-manager` строит plan изменений и применяет изменившиеся OpenBao policies/roles и конечные ACL.

Например, изменение SSH-цели гостя меняет централизованную OpenBao policy. Повторный Ansible нужен только если изменился сам общий механизм доверия на целевой системе.

## 11. Проверка готовности

После первоначального развёртывания проверяются:

- 910 и его постоянные mount points;
- OpenBao `initialized=true`, `sealed=false`;
- KV и оба SSH CA;
- PVE API и root SSH;
- Semaphore и инструменты runtime;
- OpenTofu state;
- штатный Git-доступ;
- SSH по короткоживущему сертификату;
- наличие recovery public key на управляемых Linux-гостях;
- разрешённые и запрещённые сценарии `access.yaml`.

Фактический статус реализации целевой схемы находится в `780-implementation-status.md`.

## 12. Завершение первоначального контура

После подтверждённой готовности 910 временный 990 и временные bootstrap credentials удаляются.

Канонические PVE-only recovery data, `access/` и `state/` при этом сохраняются.
