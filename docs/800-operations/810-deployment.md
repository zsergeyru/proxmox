## 1. Общая схема

```text
PVE
→ публичный минимальный bootstrap
→ временный LXC 990 bootstrap-runner
→ закрытый bootstrap-host.py
→ одноразовый OpenTofu create без постоянного bootstrap-state
→ LXC 910 infra-manager
→ общий provision.yaml + Ansible
→ Semaphore
→ OpenTofu / Ansible / Packer
→ обычные VM/LXC
```

PVE не становится постоянным узлом автоматизации.

## 2. Первоначальный контур 990

990 существует только во время первоначального создания или полного восстановления 910.

Публичная часть создаёт 990, передаёт ему read-only Deploy Key, получает закрытый проект и запускает закрытую точку входа.

Дальше закрытая часть:

- создаёт временный PVE API-доступ;
- запускает минимальный `bootstrap-runtime`;
- использует OpenTofu state только внутри шага создания 910 и сразу удаляет его;
- создаёт 910 через внутренний bootstrap-шаг на общей OpenTofu/Ansible базе;
- запускает общий Ansible для настройки 910;
- после подтверждения готовности больше не нужен.

Постоянный OpenTofu state infra-manager никогда не содержит ресурс самого infra-manager. Временный state 990 не переживает шаг `create` и не используется для продолжения следующей bootstrap-попытки.

## 3. Единый путь настройки Linux-гостей

Для 910 и остальных Linux-гостей используется один путь:

```text
guest.yaml
→ OpenTofu
→ provision.yaml
→ automation/ansible/playbooks/configure-guest.yml
→ общие Ansible roles
```

Playbook не содержит подробной настройки гостя. Он проверяет входные данные и последовательно подключает:

```text
linux_base
→ docker, если требуется
→ специализированная роль гостя, если требуется
→ portal, если включён локальный портал
→ guest_layout
```

Для `infra_manager` внутренняя последовательность дополнительно разделена на части:

```text
persistence
→ pve_access
→ ansible_access
→ repository
→ semaphore
→ runtime
→ openbao
→ recovery
→ verify
```

Постоянный Ansible inventory не хранится. Общий `deploy-guest` использует адрес выбранного гостя и передаёт его Ansible как одноузловый inventory.

Отдельного `setup.sh` для 910 больше нет.

Если для 910 требуется новая возможность, она добавляется в соответствующую общую role или реализуется узкой служебной Python-командой, которую вызывает Ansible.

## 4. Первоначальный контур 910

Первое создание и полное аварийное пересоздание управляющего гостя не являются обычной операцией `deploy-guest`. Эту редкую задачу выполняет временный LXC 990.

990 отвечает только за первоначальный управляющий контур:

```text
получить временные полномочия
→ получить проект
→ создать или полностью пересоздать infra-manager
→ подключить постоянные каталоги
→ выполнить первоначальную настройку
→ поднять или восстановить OpenBao
→ подтвердить вход по краткоживущему SSH-сертификату
→ удалить bootstrap SSH-доступ
→ проверить готовность 910
→ удалить временные полномочия
→ удалить 990
```

990 не является вторым infra-manager и не используется для обычного обновления гостей. Он не хранит постоянное состояние проекта, не переносит рабочую копию проекта на PVE и не оставляет постоянные SSH-ключи.

Первоначальная настройка 910 может внутри bootstrap-контура состоять из нескольких технических шагов, поскольку SSH CA появляется только после запуска OpenBao. Эти шаги не являются фазами общего `deploy-guest` и не должны расширять его интерфейс.

## 5. Временные данные первоначального контура

При первоначальном создании или recovery 990 получает только временные данные, необходимые конкретному запуску:

- временный PVE API token;
- Git credential для чтения проекта;
- временный доступ root к PVE только если он нужен PVE-only операциям;
- один одноразовый bootstrap SSH key создаваемого 910.

Bootstrap SSH key 910 существует только в рамках текущей bootstrap-попытки. Его открытая часть передаётся при создании LXC, закрытая часть используется для первоначального Ansible-входа. После запуска OpenBao 990 получает краткоживущий SSH-сертификат, подтверждает сертификатный вход в 910 и удаляет bootstrap authorization и закрытый bootstrap key.

Bootstrap SSH key не является recovery-данными и не сохраняется в `/mnt/bindmounts/infra-manager`. Если незавершённый 990 потерян до перехода на сертификатный доступ, недоделанный rootfs 910 пересоздаётся новой bootstrap-попыткой с новым ключом.

Постоянными остаются только данные из:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

Рабочая Git-копия проекта и все временные bootstrap credentials воспроизводимы и не относятся к постоянному состоянию.

## 6. Полная настройка 910 через provision.yaml

`infrastructure/guests/910-infra-manager/provision.yaml` определяет:

- системные пакеты;
- Docker;
- постоянные каталоги;
- Ansible SSH-идентичность;
- CA bundle;
- Compose;
- `infra-runtime`;
- Semaphore;
- OpenTofu input;
- служебные команды;
- локальный Homepage и шлюз стандартных действий.

Общий Ansible применяет эти требования через roles `linux_base`, `docker`, `infra_manager`, `portal` и `guest_layout`. Специализированная логика 910 находится только внутри `infra_manager`; данные конкретного гостя остаются в `provision.yaml`.

Для 910 действует тот же общий контракт состояния, что и для остальных гостей:

```text
infrastructure/guests/910-infra-manager/status.yaml
```

Этот файл подключает глубокую внутреннюю проверку 910 через разрешённый тип `local_status`. Само внутреннее описание хранится отдельно в `infra-manager-status.yaml`, устанавливается как `/etc/infra-manager/status.yaml` и исполняется технической командой `infra-manager-status`.

Адреса служб, логины и источники операторских паролей задаются рядом со службами в `provision.yaml` и не дублируются в файлах состояния.

## 7. Docker и infra-runtime

Docker устанавливается из официального репозитория Docker.

Постоянный контейнер:

```text
infra-runtime
```

содержит:

- Semaphore;
- OpenTofu;
- Ansible;
- Packer;
- Python;
- proxmoxer;
- Git;
- SSH-клиент.

Отдельный remote Runner для одного домашнего 910 не используется.

## 8. Semaphore

Первая версия автоматически поддерживает:

- проект `Proxmox Infrastructure`;
- ключ `GitHub project read-only`;
- Git-репозиторий `proxmox`;
- набор переменных `OpenTofu PVE`;
- общие настройки `Infra Manager`;
- `OpenTofu Plan`;
- `Build Template 9000`;
- `Set Log Level`;
- `Deploy Guest`;
- `Status Guest`;
- `Repair Guest`;
- `Test Guest`;
- `Sync Guest`;
- `Sync SSH Access`.

В веб-интерфейсе эти шаблоны распределяются по Views:

```text
Guests
├── Deploy Guest
├── Status Guest
├── Repair Guest
├── Test Guest
└── Sync Guest

Infrastructure
├── OpenTofu Plan
├── Build Template 9000
└── Set Log Level

Security
└── Sync SSH Access
```

Синхронизация этих объектов выполняется узкой Python-командой:

```text
python3 -m infra_manager semaphore-project
```

Она вызывается из общего Ansible и не является отдельным механизмом настройки 910.

Пять гостевых операций используют общий машинный каталог и отдельные шаблоны Semaphore. `Sync Guest` предназначен для изменений, которые можно применить без полного развёртывания гостя. Для обычного поддерживаемого Linux-гостя он повторно применяет фазу `provision` к существующему объекту без общего OpenTofu-применения. Для `infra-manager` сохраняется более узкая синхронизация: свежая Git-копия текущего задания обновляет проект и шаблоны Semaphore через API без пересборки 910.

Группа `Infra Manager` содержит общую несекретную настройку уровня вывода:

```text
INFRA_LOG_LEVEL=normal
```

Она меняется штатным заданием `Set Log Level` через выпадающий список `Обычный / Подробный / Тихий`. В Variable Group сохраняются соответственно `normal / verbose / quiet`; выбранное значение применяется ко всем следующим заданиям и не перезаписывается обычной синхронизацией проекта.

## 9. OpenTofu

Постоянный state 910:

```text
/var/lib/infra-manager/opentofu/state/proxmox.tfstate
```

Он:

- не хранится в Git;
- входит в резервное копирование;
- не должен автоматически пересоздаваться пустым поверх существующей инфраструктуры;
- никогда не содержит ресурс VMID 910.

Для временного 990 OpenTofu state существует только внутри одного шага `create` и удаляется сразу после создания объекта. Он не считается постоянным состоянием, не определяет владение 910 и не используется для возобновления другой bootstrap-попытки.

## 10. Проверка готовности

Для управляемых гостей используется единое задание Semaphore `Status Guest`. Оно всегда проверяет объект Proxmox, запуск, административный адрес, SSH и опубликованные службы, а затем выполняет дополнительные проверки из `status.yaml`.

Успешный `Deploy Guest` завершает работу тем же полным операторским выводом. `Test Guest` использует тот же проверочный движок, но не выводит секреты.

Для 910 общий `status.yaml` дополнительно вызывает внутреннюю проверку:

```text
/usr/local/sbin/infra-manager-status --full --quiet
```

На физическом PVE сохраняется только минимальная операторская оболочка:

```bash
infra-manager guests
infra-manager status [VMID]
infra-manager deploy VMID
infra-manager sync VMID
infra-manager repair [VMID]
infra-manager test VMID
infra-manager recover
```

Для `guests/status/deploy/sync/repair/test` оболочка не выполняет рабочую логику на PVE. Она проверяет, что настроенный VMID действительно принадлежит управляющему LXC, и передаёт команду через `pct exec` операторскому слою внутри 910. Если выполняется `repair` без VMID, оболочка может сначала запустить остановленный управляющий LXC, но дальнейшее восстановление служб выполняется уже внутри него.

Изменяющие команды конкретного гостя внутри 910 запускают через `docker exec` общий `guest-operation.py` в `infra-runtime`, где уже находятся OpenTofu, Ansible и Packer. Шаблоны Semaphore вызывают ту же точку входа, поэтому Semaphore остаётся интерфейсом и планировщиком, но не является промежуточным слоем для PVE CLI. Перед прямым `deploy` постоянная Git-копия автоматически обновляется под исключительной блокировкой и из неё создаётся временный снимок; `sync/repair/test` создают снимок текущей копии под разделяемой блокировкой. После снимка блокировка проекта освобождается. `deploy/sync/repair/test` также защищены общей блокировкой по VMID; `status` остаётся неблокирующим чтением. Журнал Semaphore всегда формируется без секретов, а доверенный вызов с PVE может показать пароль только в текущем root-терминале.

`recover` является исключением: он не передаётся в 910 и выполняется минимальным PVE-only recovery helper, поэтому доступен даже при полностью неработающем управляющем госте.

Для 910 в глубокой проверке подтверждаются:

- Docker и Compose;
- обязательное постоянное состояние;
- `infra-runtime`;
- Homepage и шлюз стандартных действий;
- OpenBao, его состояние и доступ к KV v2;
- материализованные рабочие секреты;
- Semaphore;
- OpenTofu, Packer и Ansible;
- Git-доступ Semaphore;
- PVE API;
- полный контракт PVE-прав.

До итоговой проверки первоначальный контур также завершает инициализацию OpenBao, проверяет recovery-контур и удаляет временные bootstrap credentials. Только после этого первоначальный контур может считаться успешно завершённым.

## 11. Первичный пароль Semaphore

Пароль создаётся один раз и после инициализации OpenBao хранится в `infra-secrets/data/services/semaphore`.

Для работы и вывода состояния он материализуется в:

```text
/run/infra-manager/secrets/initial-admin-password
```

Права временного файла — `0600`.

Адрес Semaphore и логин `admin` остаются в полном результате `Status Guest` и успешного `Deploy Guest`, но сохранённый пароль в журнал Semaphore не выводится. Техническая команда `infra-manager-status`, общий процесс Ansible, Homepage и автоматические проверки также пароль не печатают.

Получить фактический пароль в доверенной root-сессии физического PVE можно через единый статус гостя:

```bash
infra-manager status 910
```

От root внутри 910 рабочее значение также доступно явно:

```bash
cat /run/infra-manager/secrets/initial-admin-password
```

## 11.1. Приведение OpenBao к рабочему состоянию

После настройки 910 первоначальный контур автоматически запускает одну идемпотентную операцию приведения OpenBao к рабочему состоянию. Она одинаково обслуживает пустой новый OpenBao и сохранённый OpenBao при recovery. Отдельного задания Semaphore `Initialize OpenBao` и отдельной операторской команды для этой операции нет.

При дальнейшей эксплуатации обычные исправления выполняются через `infra-manager repair`, а аварийное восстановление — через `infra-manager recover`. Поэтому временные bootstrap credentials не переживают успешное завершение первоначального развёртывания.

Операция должна:

```text
проверить OpenBao
→ подготовить TLS
→ если OpenBao новый — инициализировать его
→ если OpenBao сохранён — разблокировать и проверить Raft
→ при потере одноузлового quorum безопасно восстановить Raft
→ сохранить unseal key только на PVE
→ создать KV v2 `infra-secrets`
→ перенести рабочие PVE, Git и Semaphore secrets
→ подготовить ограниченные KV AppRole
→ материализовать рабочие secrets в /run
→ подготовить два независимых SSH CA
→ подготовить ограниченные служебные доступы SSH
→ опубликовать открытые ключи CA
→ отозвать root token
→ проверить итоговое состояние
```

Повторный запуск не должен пересоздавать существующие корректные CA.

Точные security-требования, роли, сроки токенов и граница PVE-only определены в [`../700-security/740-openbao.md`](../700-security/740-openbao.md).

## 11.2. SSH-доверие Linux-гостей

Полная настройка Linux-гостя должна:

- установить доверие к пользовательскому SSH CA;
- использовать краткоживущий сертификат для штатного входа Ansible;
- получить и установить сертификат реального SSH host key;
- сохранить строгую проверку подлинности сервера;
- не передавать закрытые CA-ключи гостю или `infra-runtime`.

Переходный постоянный Ansible-ключ допускается только в случаях, определённых SSH-спецификацией.

Целевая схема межмашинного `guest → guest` использует OpenBao SSH OTP.

После реализации OTP настройка должна дополнительно:

- выдавать исходному гостю только его собственный машинный AppRole, если `access.yaml` содержит `ssh/identity/issue`;
- строить OTP-роль этого источника только из его `ssh/guest/connect-root`;
- устанавливать OTP helper и PAM/sshd-настройку на Linux-гостях, которые могут быть целями;
- устанавливать доверие к TLS-сертификату OpenBao;
- сохранять проверку SSH-сервера через `ssh-host-signer`;
- проверять разрешённое и запрещённое получение OTP;
- проверять невозможность повторного использования OTP.

Изменение `access.yaml` должно синхронизировать OTP-роли, policy и машинные AppRole OpenBao через `Sync SSH Access`.

После обновления 910 выполняется задание Semaphore:

```text
Sync SSH Access
```

Оно только синхронизирует OTP-роли, policy и машинные AppRole OpenBao по `access.yaml`. Развёртывание гостей и сквозные SSH-проверки выполняются отдельными механизмами.

Полный нормативный контракт находится в [`../700-security/720-ssh-access.md`](../700-security/720-ssh-access.md), OpenBao-контракт — в [`../700-security/740-openbao.md`](../700-security/740-openbao.md), фактическое состояние перехода — в [`../700-security/780-implementation-status.md`](../700-security/780-implementation-status.md).

## 12. Обновление 910

Обычное обновление существующего 910 может запускаться с PVE одной командой `infra-manager deploy 910` или через единое задание Semaphore `Deploy Guest` с выбором `910 infra-manager`. При прямом запуске с PVE Git-копия обновляется автоматически перед созданием снимка операции. В обоих случаях само развёртывание выполняет один `run_guest_operation()` внутри `infra-runtime`.

Дальше используется обычный `run_deploy_guest()` для уже существующего управляющего гостя:

```text
проверить проект
→ проверить существующий LXC 910 через PVE API
→ получить краткоживущий SSH-сертификат OpenBao
→ подтвердить сертификатный вход
→ применить provision.yaml общим Ansible
→ обновить status.yaml и служебный код
→ синхронизировать Semaphore
→ проверить текущее состояние
→ после завершения задания активировать собранный infra-runtime
```

Обычный deploy 910 не создаёт bootstrap SSH key и не восстанавливает доступ через временный 990. Если сертификатный вход или сам управляющий гость настолько повреждены, что штатное обновление невозможно, операция завершается ошибкой; далее используется `repair`, а при необходимости полного пересоздания — `recover`.

Постоянный OpenTofu state infra-manager при этом не инициализируется, не читается и не изменяется. Объект Proxmox текущего гостя с ролью `infra-manager` остаётся во владении первоначального контура.

Внутри 910 включена одноразовая служба `infra-manager-openbao-startup-unseal.service`. При штатном запуске 910 она ждёт OpenBao и при необходимости вызывает хостовый сценарий на PVE. Периодической проверки на PVE нет. Если перезапустился только контейнер OpenBao и штатная служба не восстановила его состояние, `infra-manager status` покажет ошибку; безопасное ручное исправление выполняется через `infra-manager repair`.

`infra-runtime` нельзя перезапускать посреди выполняющейся операции. Перед самообновлением общий диспетчер создаёт отдельный файл-признак активации с указанием пространства PID и PID текущего процесса. Штатные `Deploy Guest` из Semaphore и `infra-manager deploy` с PVE выполняются внутри `infra-runtime`, поэтому используют `runtime:<PID>`; формат `host:<PID>` сохраняется для безопасного служебного host-side запуска. Внешняя systemd-служба активации ждёт завершения процесса в правильном пространстве PID и только после этого может пересоздать `infra-runtime`.

Пока файл-признак активации существует, новые инфраструктурные операции завершаются до начала изменений с сообщением о выполняющейся активации. Этот механизм отделён от обычных lock-файлов по VMID и исключает запуск следующей операции в промежутке между окончанием обновления 910 и заменой контейнера.

После `docker compose up` служба активации обязана сначала проверить и при необходимости разблокировать OpenBao через доверенный PVE-хост. Только после подтверждения разблокировки разрешены синхронизация Semaphore и полная проверка состояния 910. Файл-признак снимается при завершении службы активации независимо от её результата.

Результат активации записывается в:

```text
/var/log/infra-manager/runtime-activation.log
```

При обычном обновлении Ansible восстанавливает рабочие секреты из OpenBao. Постоянные старые файловые источники больше не используются.

## 13. Завершение временного контура

После успешной внутренней полной проверки 910 bootstrap обязан:

```text
удалить /etc/bootstrap-runner/secrets
→ убедиться, что временный OpenTofu state шага create отсутствует
→ удалить ACL временного token root@pam!bootstrap-runner
→ удалить сам token
→ остановить и удалить LXC 990
→ удалить скачанный bootstrap LXC-template, если он был создан именно bootstrap
```

Если любой этап до итоговой проверки 910 завершается ошибкой, 990 не удаляется автоматически: он остаётся для диагностики и безопасного повторного запуска.

Обычный `deploy 910` вообще не запускает 990 и не создаёт bootstrap-state. Он работает только с существующим управляющим гостем по краткоживущему SSH-сертификату. Если этот путь недоступен, оператор использует `infra-manager recover`, который полностью пересоздаёт воспроизводимый rootfs с сохранением постоянных каталогов.
