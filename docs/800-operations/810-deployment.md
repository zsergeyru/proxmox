# Развёртывание инфраструктуры

**Тип:** эксплуатация  
**Статус:** проектируется  
**Назначение:** описать штатный путь от чистого PVE до работающего `910 infra-manager` и дальнейшего развёртывания обычных гостей.

## 1. Общая схема

```text
PVE
→ публичный минимальный bootstrap
→ временный LXC 990 bootstrap-runner
→ закрытый bootstrap-host.py
→ отдельное состояние OpenTofu только для 910
→ LXC 910 infra-manager
→ общий provision.yaml + Ansible
→ Semaphore
→ OpenTofu / Ansible / Packer
→ обычные VM/LXC
```

PVE не становится постоянным узлом автоматизации.

## 2. Первоначальный контур 990

990 существует только во время первоначального создания или полного восстановления 910.

Публичная часть создаёт 990, передаёт ему read-only Deploy Key, получает закрытый проект и запускает закрытую точку входа.

Дальше закрытая часть:

- создаёт временный PVE API-доступ;
- запускает минимальный `bootstrap-runtime`;
- хранит отдельный OpenTofu state только для VMID 910;
- создаёт 910 через общий `deploy-guest`;
- запускает общий Ansible для настройки 910;
- после подтверждения готовности больше не нужен.

Постоянный OpenTofu state 910 никогда не содержит ресурс 910.

## 3. Единый путь настройки Linux-гостей

Для 910 и остальных Linux-гостей используется один путь:

```text
guest.yaml
→ OpenTofu
→ provision.yaml
→ automation/ansible/playbooks/configure-guest.yml
→ общие Ansible roles
```

Playbook не содержит подробной настройки гостя. Он проверяет входные данные и последовательно подключает:

```text
linux_base
→ docker, если требуется
→ infra_manager, только для 910
→ guest_layout
```

Для `infra_manager` внутренняя последовательность дополнительно разделена на части:

```text
persistence
→ pve_access
→ ansible_access
→ repository
→ semaphore
→ runtime
→ openbao
→ verify
```

Постоянный Ansible inventory не хранится. Общий `deploy-guest` использует адрес выбранного гостя и передаёт его Ansible как одноузловый inventory.

Отдельного `setup.sh` для 910 больше нет.

Если для 910 требуется новая возможность, она добавляется в соответствующую общую role или реализуется узкой служебной Python-командой, которую вызывает Ansible.

## 4. Фазы deploy-guest для 910

Обычный гость обычно проходит весь цикл одним вызовом.

Для 910 первоначальный контур использует три общие фазы:

```text
1. --infrastructure-only
   OpenTofu создаёт или сверяет LXC 910
   общий host-only шаг применяет root-only требования профиля

2. --provision-base-only
   Ansible применяет базовую часть provision.yaml
   и устанавливает системные пакеты

3. --provision-only
   после передачи первоначальных доступов
   Ansible полностью применяет provision.yaml
```

Такое разделение нужно только потому, что постоянные данные доступа 910 можно передать лишь после появления самого LXC 910. Само применение host-only требований остаётся частью общего deploy-guest.

## 5. Передача первоначальных данных

После создания 910 первоначальный контур подготавливает постоянные области PVE и подключает их к LXC.

910 получает только предусмотренные контрактом представления:

- PVE CA;
- постоянный PVE API credential;
- отдельный root SSH-доступ к PVE;
- read-only GitHub Deploy Key;
- постоянное состояние сервисов.

Данные из области `access/` доступны 910 только для чтения, а `state/` — для чтения и записи. PVE-only секреты внутрь 910 не монтируются.

Точные пути и права определены в [`../200-pve/230-host-layout.md`](../200-pve/230-host-layout.md), а модель полномочий — в [`../700-security/710-pve-access.md`](../700-security/710-pve-access.md).

Рабочая Git-копия проекта является воспроизводимой и создаётся внутри 910; она не является способом передачи секретов.

## 6. Полная настройка 910 через provision.yaml

`infrastructure/guests/910-infra-manager/provision.yaml` определяет:

- системные пакеты;
- Docker;
- постоянные каталоги;
- Ansible SSH-идентичность;
- CA bundle;
- Compose;
- `infra-runtime`;
- Semaphore;
- OpenTofu input;
- служебные команды.

Общий Ansible применяет эти требования через roles `linux_base`, `docker`, `infra_manager` и `guest_layout`. Специализированная логика 910 находится только внутри `infra_manager`; данные конкретного гостя остаются в `provision.yaml`.

Порядок проверок готовности, источники фактических данных и состав итогового экрана вынесены отдельно в:

```text
infrastructure/guests/910-infra-manager/status.yaml
```

Python-код состояния не хранит конкретный список строк экрана: он исполняет разрешённые типы проверок и источников, объявленные в этом файле.

## 7. Docker и infra-runtime

Docker устанавливается из официального репозитория Docker.

Постоянный контейнер:

```text
infra-runtime
```

содержит:

- Semaphore;
- OpenTofu;
- Ansible;
- Packer;
- Python;
- proxmoxer;
- Git;
- SSH-клиент.

Отдельный remote Runner для одного домашнего 910 не используется.

## 8. Semaphore

Первая версия автоматически поддерживает:

- проект `Proxmox Infrastructure`;
- ключ `GitHub project read-only`;
- Git-репозиторий `proxmox`;
- набор переменных `OpenTofu PVE`;
- `OpenTofu Plan`;
- `Build Template 9000`;
- `Deploy Guest 410`;
- `Deploy Guest 910`;
- `Initialize OpenBao 910`.

Синхронизация этих объектов выполняется узкой Python-командой:

```text
python3 -m infra_manager semaphore-project
```

Она вызывается из общего Ansible и не является отдельным механизмом настройки 910.

## 9. OpenTofu

Постоянный state 910:

```text
/var/lib/infra-manager/opentofu/state/proxmox.tfstate
```

Он:

- не хранится в Git;
- входит в резервное копирование;
- не должен автоматически пересоздаваться пустым поверх существующей инфраструктуры;
- никогда не содержит ресурс VMID 910.

Для временного 990 используется отдельный state.

## 10. Проверка готовности

После полного Ansible сначала выполняется скрытая полная проверка:

```bash
infra-manager-status --full --quiet
```

После удаления временного 990 обычный `infra-manager-status --full` выводит единый итоговый экран состояния 910 по `status.yaml`. Эту же команду можно выполнить в любой момент независимо от первоначального контура.

Проверяются:

- Docker и Compose;
- обязательное постоянное состояние;
- `infra-runtime`;
- OpenBao, его состояние и доступ к KV v2;
- материализованные рабочие секреты;
- Semaphore;
- OpenTofu, Packer и Ansible;
- Git-доступ Semaphore;
- PVE API;
- полный контракт PVE-прав.

Только после этого первоначальный контур может считаться успешно завершённым.

## 11. Первичный пароль Semaphore

Пароль создаётся один раз и после инициализации OpenBao хранится в `infra-secrets/data/services/semaphore`.

Для работы и вывода состояния он материализуется в:

```text
/run/infra-manager/secrets/initial-admin-password
```

Права временного файла — `0600`.

Открытый `infra-manager-status --full` показывает адрес Semaphore, логин `admin` и сохранённый пароль. Внутренние проверки используют `--quiet`, поэтому общий процесс Ansible пароль не печатает и в технический журнал он не записывается.

Получить пароль от root внутри 910 можно также явно:

```bash
cat /run/infra-manager/secrets/initial-admin-password
```

## 11.1. Первичная инициализация OpenBao

После первого успешного создания 910 пустой OpenBao инициализируется отдельным заданием:

```text
Initialize OpenBao 910
```

Операция должна:

```text
проверить OpenBao
→ при необходимости инициализировать
→ сохранить unseal key только на PVE
→ разблокировать
→ создать KV v2 `infra-secrets`
→ перенести рабочие PVE, Git и Semaphore secrets
→ подготовить ограниченные KV AppRole
→ материализовать рабочие secrets в /run
→ подготовить два независимых SSH CA
→ подготовить ограниченные служебные доступы SSH
→ опубликовать открытые ключи CA
→ отозвать root token
→ проверить итоговое состояние
```

Повторный запуск не должен пересоздавать существующие корректные CA.

Точные security-требования, роли, сроки токенов и граница PVE-only определены в [`../700-security/740-openbao.md`](../700-security/740-openbao.md).

## 11.2. SSH-доверие Linux-гостей

Полная настройка Linux-гостя должна:

- установить доверие к пользовательскому SSH CA;
- использовать краткоживущий сертификат для штатного входа Ansible;
- получить и установить сертификат реального SSH host key;
- сохранить строгую проверку подлинности сервера;
- не передавать закрытые CA-ключи гостю или `infra-runtime`.

Переходный постоянный Ansible-ключ допускается только в случаях, определённых SSH-спецификацией.

Полный контракт находится в [`../700-security/720-ssh-access.md`](../700-security/720-ssh-access.md), а текущее состояние перехода — в [`../700-security/780-implementation-status.md`](../700-security/780-implementation-status.md).

## 12. Обновление 910

Обычное обновление существующего 910 выполняется из Semaphore заданием:

```text
Deploy Guest 910
```

Оно использует тот же `scripts/infra-manager/jobs/deploy-guest.py`, что и остальные гости, но для VMID 910 действует зафиксированная граница владения:

```text
проверить проект
→ собрать итоговое описание 910 без записи OpenTofu input
→ проверить существующий LXC 910 через PVE API
→ при необходимости восстановить собственный Ansible-доступ через доверенный root SSH к PVE
→ применить provision.yaml общим Ansible
→ обновить status.yaml и служебный код
→ синхронизировать Semaphore
→ проверить текущее состояние
→ после завершения задания активировать собранный infra-runtime
```

Постоянный OpenTofu state 910 при этом не инициализируется, не читается и не изменяется. Объект Proxmox 910 остаётся во владении первоначального контура.

Внутри 910 включена одноразовая служба `infra-manager-openbao-startup-unseal.service`. При штатном запуске 910 она ждёт OpenBao и при необходимости вызывает хостовый сценарий на PVE. Периодической проверки на PVE нет. Если перезапустился только контейнер OpenBao, `infra-manager-status` должен показать `sealed=true`; обработка этого состояния относится к будущему мониторингу и уведомлениям.

Semaphore выполняет задание внутри `infra-runtime`, поэтому нельзя перезапускать этот же контейнер посреди задания. Новый образ сначала собирается, а активация назначается через systemd после завершения задания. Результат активации записывается в:

```text
/var/log/infra-manager/runtime-activation.log
```

При обычном обновлении Ansible сначала пытается восстановить рабочие secrets из OpenBao. Старые файловые копии используются только как переходный источник до завершения общей миграции.

## 13. Завершение временного контура

После успешного `infra-manager-status --full` bootstrap обязан:

```text
удалить /etc/bootstrap-runner/secrets
→ удалить /var/lib/bootstrap-runner/opentofu/state
→ удалить ACL временного token root@pam!bootstrap-runner
→ удалить сам token
→ остановить и удалить LXC 990
→ удалить скачанный bootstrap LXC-template, если он был создан именно bootstrap
```

Если любой этап до итоговой проверки 910 завершается ошибкой, 990 не удаляется автоматически: он остаётся для диагностики и безопасного повторного запуска.

Повторный обычный запуск при уже существующем 910 не создаёт новый OpenTofu state для 910. Он проверяет существующий объект и повторно применяет `provision.yaml` через общий Ansible.
