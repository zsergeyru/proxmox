# Восстановление инфраструктурного контура

**Тип:** инструкция
**Статус:** действующий
**Назначение:** задать единый безопасный порядок проверки, исправления и аварийного восстановления `infra-manager` с физического PVE.

Оператор не должен выбирать между отдельными командами OpenBao, Semaphore и recovery. Штатная точка входа одна:

```text
infra-manager
```

## 1. Операторские режимы

Для восстановления важны три команды, вызываемые человеком с физического PVE:

```bash
infra-manager status
infra-manager repair
infra-manager recover
```

При этом сама PVE-команда является только минимальной оболочкой.

### `status`

PVE-оболочка проверяет принадлежность управляющего LXC и передаёт команду через `pct exec` операторскому слою внутри 910.

Внутри 910 выполняется полный status:

```text
PVE shell
→ тонкая оболочка
→ pct exec
→ 910 operator
├── локальные проверки 910
└── узкие PVE-only проверки через helper
```

Так проверяются Docker, OpenBao, Semaphore, OpenTofu, Ansible, Packer, PVE-доступ и аварийный контур. При доверенном вызове с физического PVE итоговый status также может показать операторские пароли в текущем root-терминале.

### `repair`

Используется для обычной неисправности, когда постоянное состояние сохранно.

PVE-оболочка делает только две вещи:

1. проверяет, что настроенный VMID принадлежит проектному infra-manager;
2. при необходимости запускает остановленный LXC и передаёт `repair` внутрь 910.

Дальше операторский слой 910:

1. через PVE-only recovery helper выполняет обязательный preflight постоянного состояния;
2. запускает Docker;
3. запускает существующий Compose OpenBao;
4. через узкий PVE-only OpenBao helper безопасно приводит OpenBao к рабочему состоянию на прежнем Raft;
5. материализует рабочие секреты;
6. активирует управляющую среду и синхронизирует Semaphore;
7. завершает работу полным status.

`repair` не пересоздаёт infra-manager и не является аварийным bootstrap.

### `recover`

Используется, когда обычного исправления недостаточно, в том числе если infra-manager удалён или его воспроизводимый rootfs повреждён.

Это единственная операторская операция, которая не передаётся в 910. PVE-оболочка вызывает `infra-manager-recovery --recover`, а recovery helper:

1. выполняет recovery-preflight;
2. получает минимальную bootstrap-точку входа и создаёт временный 990;
3. проверяет сохранённые каталоги и строгую принадлежность существующего 910;
4. полностью подготавливает временный 990: PVE/Git-доступ, Docker и среду Ansible/OpenTofu;
5. **только после успешной подготовки 990** удаляет воспроизводимый объект/rootfs существующего 910, если он есть, не затрагивая `/mnt/bindmounts/infra-manager`;
6. создаёт 910 заново через единый bootstrap и подключает прежние постоянные каталоги;
7. идемпотентно приводит OpenBao к рабочему состоянию на сохранённом Raft;
8. после успешной проверки отзывает временные полномочия и удаляет 990.

Сбой во время подготовки 990 не должен удалять существующий 910.
После удаления старого rootfs последующие операции всё ещё могут завершиться
ошибкой (например, при отказе хранилища или сети): для доказательства полного
восстановления требуется отдельное испытание на реальном PVE.

Публичный `bootstrap-pve.sh` используется **без параметров** для
передачи первоначального запуска временному 990. Публичный загрузчик
не знает VMID и роли управляющего гостя, **не проверяет его существование**
и не блокирует создание 990 при наличии уже работающего объекта.
Получив основной проект, 990 определяет управляющего гостя по роли
`infra-manager` из `guest.yaml` и самостоятельно выбирает безопасное
поведение: обычный запуск при существующем объекте прекращается без его
изменения; аварийное пересоздание возможно только в явно переданном
внутреннем режиме восстановления после проверки сохранённых данных.
После неуспешного запуска 990 может оставаться для диагностики.

Оператор использует исключительно `infra-manager status/deploy/repair/recover`.
При `infra-manager recover` независимый помощник PVE запускает тот же
публичный загрузчик со **внутренним признаком** восстановления, а не с
пользовательским параметром `--recover`. Для установленных ранее помощников
в публичном Python пока сохраняется скрытая совместимость со старым вызовом;
в README и справке этот режим не предлагается.
Публичные `--check`, `--remove`, `--purge` недоступны.

## 2. Граница безопасного исправления

Обязательное состояние хранится на PVE:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

Rootfs infra-manager считается воспроизводимым.

### Что `repair` может исправить автоматически

Допустимы повторяемые действия:

- запуск остановленного LXC;
- запуск Docker;
- возврат контейнера OpenBao из существующего Compose;
- снятие блокировки OpenBao;
- восстановление служебной конфигурации OpenBao на существующем Raft;
- повторная материализация секретов;
- запуск `infra-runtime`;
- синхронизация проекта Semaphore;
- повторная полная проверка.

### Что `repair` делать не имеет права

Автоматически запрещено:

- удалять или очищать Raft;
- выполнять новый `sys/init` вместо потерянного прежнего состояния;
- создавать пустой OpenTofu state вместо потерянного;
- заменять существующие SSH CA как способ «починить» потерю состояния;
- удалять управляемые VM/LXC;
- пересоздавать infra-manager;
- принимать чужой объект с тем же VMID за infra-manager.

Если требуется одно из этих действий, `repair` должен завершиться ошибкой.

## 3. Аварийное восстановление

Перед любым `recover` проверяются данные, без которых автоматическое восстановление продолжать нельзя.

Обязательны:

- аварийная копия GitHub Deploy Key;
- `unseal.key`;
- непустое Raft-состояние OpenBao;
- база Semaphore;
- постоянный OpenTofu state, если в `pool managed` уже есть объекты.

Если `pool managed` пуст, отсутствие `proxmox.tfstate` допустимо.

Потеря `ssh-access.json`, `kv-access.json` или `operator-access.json` не является необратимой: при сохранных Raft и unseal key служебные AppRole могут быть выпущены заново, а оператору может быть создан новый случайный пароль.

Поэтому начальный recovery-preflight не требует эти три файла. После восстановления полный `infra-manager-recovery --check` обязан подтвердить их наличие вместе с остальным рабочим контуром.

### Существующий infra-manager

Если объект существует и обычный `repair` или `deploy` ещё возможен, используется обычный контур 910. `recover` предназначен для случая, когда этот путь уже недостаточен и требуется полное воспроизводимое пересоздание управляющего rootfs.

Recovery не пытается добавлять новый постоянный SSH-доступ в существующий 910. Если требуется полное восстановление, временный 990 создаёт новый bootstrap-сеанс.

### Полное пересоздание infra-manager

Если rootfs infra-manager утрачен или признан непригодным, но `pve-only/`, `access/` и `state/` сохранны, recovery:

1. создаёт временный 990;
2. выдаёт ему только временные PVE/Git полномочия;
3. создаёт новый одноразовый bootstrap SSH key для 910;
4. создаёт новый rootfs 910 и подключает прежние постоянные каталоги;
5. запускает OpenBao на сохранённом Raft и разблокирует его через PVE-only данные;
6. получает краткоживущий SSH-сертификат и подтверждает сертификатный вход;
7. удаляет bootstrap SSH key из 910 и временной среды;
8. выполняет итоговую проверку;
9. отзывает временные полномочия и удаляет 990.

Bootstrap SSH key не восстанавливается из резервной копии и не переживает bootstrap-сеанс. Каждая новая recovery/bootstrap-попытка начинает с новой пары ключей; старая локальная пара не переиспользуется. Потеря 990 до успешного перехода на сертификатный SSH означает новую bootstrap-попытку с новым ключом.

Git checkout, Docker-образы, Compose-файлы, установленный Python-код, кэши и `/run` не являются резервируемым состоянием и создаются заново.

## 4. Защита от пустого состояния

`infra-manager recover` не должен превращаться в новую установку.

Если потеряны Raft OpenBao, `unseal.key`, аварийный Git key или обязательный OpenTofu state, автоматическое восстановление блокируется. Новый OpenBao или новое пустое состояние вместо прежнего не создаются.

Строгая проверка объекта Proxmox требует одновременно:

```text
hostname=<имя infra-manager>
unprivileged=1
owner=proxmox-project
role=infra-manager
```

Одного VMID недостаточно.

## 5. Внутренняя реализация

На PVE сохраняются только минимальные внутренние механизмы:

```text
/usr/local/sbin/infra-manager
/usr/local/sbin/infra-manager-recovery
/usr/local/sbin/infra-manager-openbao-unseal
```

Первый файл — тонкая оболочка `pct exec`. `infra-manager-recovery` содержит независимую аварийную логику, а `infra-manager-openbao-unseal` — только узкие PVE-only операции OpenBao. Обычная операторская логика находится внутри 910.

Внутри infra-manager также остаются:

```text
infra-manager-status
infra-manager-activate-runtime
infra-manager-openbao-startup-unseal
```

Оператору не требуется выбирать между ними при обычной проверке или восстановлении.

## 6. Проверка результата

Штатная итоговая проверка одна:

```bash
infra-manager status
```

Для углублённой диагностики внутренний status можно вызвать явно:

```bash
pct exec 910 -- infra-manager-status --full
```

Сквозную приёмочную проверку SSH-доступов при разработке можно выполнить отдельно:

```bash
python3 scripts/acceptance/verify-ssh-access.py
```

Восстановление считается завершённым только если прежнее постоянное состояние OpenBao и OpenTofu сохранено, Semaphore использует прежнюю базу, PVE-доступ работает и `infra-manager status` завершается успешно.

## 7. Приёмочные испытания на отдельном PVE

Автоматические проверки исходного кода подменяют команды PVE и не
подтверждают завершение реальной установки. Для допуска recovery к
рабочему узлу необходим отдельный испытательный PVE с возможностью
вернуться к исходному снимку. **На рабочем PVE эти испытания не
удаляют 910, 990, постоянные данные или другие гости.**

### Сценарий А: первоначальная установка

Исходное состояние: нет LXC 910 и 990, нет каталога
`/mnt/bindmounts/infra-manager`; есть доступ в сеть, хранилища
`local` и `local-lvm`, мост `vmbr0`, Debian 13 и доступ к GitHub.

1. Выполнить публичный `bootstrap-pve.sh` без параметров.
2. Если GitHub Deploy Key ещё не зарегистрирован, первый запуск только
   создаст ключ и выведет открытую часть для регистрации. После
   регистрации повторить команду. Этот ручной первый шаг **ожидаемый**.
3. Дождаться завершения bootstrap без ручного исправления файлов.
4. Подтвердить отсутствие 990 и его временного PVE API token.
5. Подтвердить работоспособность `infra-manager status` и
   `pct exec 910 -- infra-manager-status --full`.

Результат засчитывается только после успешной итоговой проверки 910
без ручного изменения прав, служб или контейнеров.

### Сценарий Б: 910 отсутствует, постоянные данные сохранены

Исходное состояние: первоначальная установка на испытательном PVE
завершена; состояние `pve-only/`, `access/`, `state/`
сохранено и отдельно проверено. Подготовлена возможность возврата
снимка испытательного PVE.

1. Записать признаки прежней идентичности SSH CA и состояние
   Semaphore/OpenTofu без вывода закрытых ключей и паролей.
2. На испытательном PVE удалить **только** воспроизводимый 910.
   Постоянные каталоги не удалять.
3. Выполнить `infra-manager recover` с физического PVE.
4. Подтвердить автоматическое создание 910, подключение прежних данных,
   восстановление сертификатного SSH, запуск OpenBao/Semaphore,
   успешный полный статус и удаление 990.
5. Проверить сохранение прежней SSH CA и прикладных данных Semaphore
   и OpenTofu. Новый пустой OpenBao не считается восстановлением.

### Сценарий В: отказ без удаления рабочего 910

На испытательном PVE при сохранённом 910 намеренно нарушить доступность
подготовки 990 или убрать обязательный элемент из **копии**
постоянных данных, после чего проверить отказ recovery.
Существующий 910 не должен быть удалён до завершения проверки
состояния и подготовки 990. После испытания вернуть исходный снимок.

Для каждого сценария сохраняют версию проекта, журнал, исходное и
итоговое состояние PVE, ошибки и результат полного статуса. Без
реального прохождения сценариев А и Б надпись «восстановление с нуля
проверено» запрещена.
