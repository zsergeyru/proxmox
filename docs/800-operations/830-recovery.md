# Восстановление инфраструктурного контура

Этот документ фиксирует целевой порядок восстановления `910 infra-manager` и его постоянного состояния.

## Основной принцип

Операционная система и код 910 считаются воспроизводимыми. Важное состояние не должно зависеть от существования rootfs 910.

Целевой корень на PVE:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

`pve-only/` никогда не показывается 910.

`access/` подключается в 910 только для чтения и содержит данные, владельцем которых является PVE, но которые нужны 910 для работы или восстановления.

`state/` подключается в 910 с правом записи и содержит состояние сервисов, которое должно пережить удаление и повторное создание LXC.

## Что восстанавливается из состояния

В `state/` должны сохраняться как минимум:

- Raft-данные OpenBao;
- OpenTofu state;
- база и служебные данные Semaphore;
- постоянная Ansible-идентичность;
- постоянные секреты и ключи шифрования 910.

В `access/` должны сохраняться как минимум:

- GitHub Deploy Key;
- root SSH-ключ доступа 910 к PVE;
- `known_hosts` PVE;
- PVE CA;
- постоянный PVE API credential.

Ключ снятия блокировки OpenBao относится к `pve-only/` и внутрь 910 не передаётся.

## Что не восстанавливается из состояния

Следующие данные должны создаваться заново:

- Git checkout проекта;
- Docker-образы;
- Compose-файлы;
- установленный служебный Python-код;
- кэши;
- временные файлы.

На PVE не должна появляться постоянная копия Git checkout. Для повторного получения проекта используется сохранённый GitHub Deploy Key.

## Восстановление после уничтожения 910

Целевой порядок:

```text
проверить сохранность pve-only/, access/ и state/
→ создать чистый LXC 910
→ подключить access/ только для чтения
→ подключить state/ для чтения и записи
→ проверить владельцев и права каталогов
→ получить проект из GitHub
→ применить provision.yaml
→ запустить Docker и infra-runtime
→ запустить OpenBao на прежних Raft-данных
→ снять блокировку ключом, который остаётся только на PVE
→ проверить существующий OpenTofu state
→ выполнить infra-manager-status --full
```

## Защита от опасного пустого состояния

Если каталог `state/` отсутствует или повреждён, автоматизация не должна молча считать это новой чистой установкой.

Особенно запрещено автоматически создавать новый пустой OpenTofu state и выполнять `apply` поверх уже существующих объектов PVE.

Если OpenBao инициализирован, но отсутствуют его Raft-данные или ключ снятия блокировки, автоматическая повторная инициализация также запрещена.

Такие случаи являются восстановлением после потери состояния и должны требовать отдельного явного действия.

## Резервное копирование

Размещение состояния на PVE защищает от пересоздания 910, но не от отказа диска PVE или ошибочного удаления каталога.

Поэтому отдельно должны резервироваться:

- `pve-only/`;
- `access/`;
- `state/`.

Резервная копия rootfs 910 не считается достаточной резервной копией постоянного состояния.

## Текущее состояние реализации

Эта схема включена для новых установок: `provision.yaml:persistence.target_layout.implemented` имеет значение `true`. Штатный код не содержит автоматической миграции существующего 910.

Если старый 910 ещё не переведён на bind mount, его необходимо мигрировать вручную до следующего штатного `Deploy Guest 910` или bootstrap. Стандартный запуск в таком состоянии должен завершиться ошибкой до изменения данных.
