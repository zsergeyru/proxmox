# Восстановление инфраструктурного контура

**Тип:** инструкция  
**Статус:** действующий  
**Назначение:** описать штатное аварийное восстановление `910 infra-manager` из постоянного состояния PVE без принятия пустого состояния за новую установку.

## 1. Граница восстановления

Rootfs 910 считается воспроизводимым. Обязательное состояние хранится на PVE под:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

Восстановление опирается на эти каталоги, а не на резервную копию rootfs 910.

PVE-only точка входа:

```text
/usr/local/sbin/infra-manager-recovery
```

Она не зависит от работающего 910 и не монтирует `pve-only/` внутрь гостя.

## 2. Проверка готовности

Перед восстановлением на PVE выполняется минимальная проверка:

```bash
infra-manager-recovery --preflight
```

Она проверяет данные, без которых автоматическое восстановление продолжать нельзя:

- аварийную копию GitHub Deploy Key;
- `unseal.key`;
- непустое Raft-состояние OpenBao;
- базу Semaphore;
- постоянный OpenTofu state, если в `pool managed` уже есть объекты.

После `Initialize OpenBao 910` полный аварийный контур проверяется автоматически. Ручная полная проверка:

```bash
infra-manager-recovery --check
```

Дополнительно она требует восстановленные `ssh-access.json` и `kv-access.json`.

Если AppRole-файлы потеряны, `--preflight` не блокирует recovery: при сохранных Raft и unseal key OpenBao восстанавливает эти служебные данные через временный root token. До этого момента полный `--check` закономерно не проходит.

## 3. Восстановление Git-доступа

Аварийная копия Deploy Key хранится только на PVE:

```text
/mnt/bindmounts/infra-manager/pve-only/recovery/github_proxmox_repo_ed25519
```

Штатная настройка 910 поддерживает её автоматически.

Если bootstrap-копия потеряна, но аварийная копия сохранна:

```bash
infra-manager-recovery --restore-git-access
```

Команда восстанавливает:

```text
/root/.config/proxmox-bootstrap/github_proxmox_repo_ed25519
/mnt/bindmounts/infra-manager/access/github/github_proxmox_repo_ed25519
```

Содержимое ключа не выводится в журнал.

Если обнаружены разные постоянные экземпляры одного Deploy Key, автоматическая замена запрещена.

## 4. Восстановление существующего 910

Если LXC 910 существует, но потерян PVE API secret или нарушена его настройка:

```bash
bootstrap-pve.sh --recover
```

До изменений bootstrap выполняет recovery-preflight.

При успешной проверке:

1. проверяется постоянное состояние;
2. при необходимости перевыпускается `root@pam!infra-manager`;
3. восстанавливается доступ 910 к PVE;
4. проект приводится к выбранной ветке;
5. повторно применяется настройка 910;
6. OpenBao запускается на прежних Raft-данных;
7. выполняется итоговая проверка состояния.

## 5. Восстановление после уничтожения 910

Если LXC 910 удалён, но `pve-only/` и `state/` сохранны, восстановление возможно даже при потере `access/`.

1. на PVE выполнить:

   ```bash
   infra-manager-recovery --preflight
   ```

2. если bootstrap Git key отсутствует:

   ```bash
   infra-manager-recovery --restore-git-access
   ```

3. запустить:

   ```bash
   bootstrap-pve.sh --recover
   ```

4. bootstrap создаёт чистый 910;
5. `access/` проверяется или создаётся заново из PVE и аварийного Git key;
6. подключается сохранный `state/`;
7. проект заново получается из GitHub;
8. Docker и `infra-runtime` создаются заново;
9. OpenBao запускается на прежнем Raft-состоянии;
10. OpenBao разблокируется ключом, который остаётся только на PVE;
11. при необходимости заново создаются ограниченные OpenBao AppRole;
12. выполняются проверки Semaphore, OpenTofu, PVE-доступа и SSH-доверия.

Git checkout, Docker-образы, Compose-файлы, установленный Python-код, кэши и `/run` восстанавливаются заново и не считаются постоянным состоянием.

## 6. Защита от пустого состояния

Режим `recover` не должен превращаться в чистую установку.

До изменения 910 проверяются обязательные каталоги и данные OpenBao.

Если `pool managed` содержит объекты, отсутствие постоянного OpenTofu state блокирует восстановление.

Если `pool managed` пуст, отсутствие `proxmox.tfstate` допустимо: это нормальное состояние новой установки до появления управляемых гостей.

Потеря Raft-данных OpenBao, `unseal.key`, аварийного Git key или обязательного OpenTofu state требует отдельного решения. Автоматическая повторная инициализация вместо восстановления запрещена.

Потеря `ssh-access.json` или `kv-access.json` не относится к необратимой потере: при сохранных Raft и unseal key они создаются заново штатной инициализацией OpenBao.

Потеря всего `access/` также не блокирует preflight. Bootstrap заново создаёт его технические данные: Git key восстанавливается из `pve-only/recovery/`, PVE API token перевыпускается, root SSH 910→PVE и файлы доверия создаются заново. Полный `--check` выполняется только после этого.

## 7. Проверка результата

После восстановления выполнить:

```bash
pct exec 910 -- infra-manager-status --full
infra-manager-recovery --check
```

После изменения или восстановления OpenBao также выполнить штатные задания:

```text
Initialize OpenBao 910
Sync Machine SSH
```

Итог считается успешным только если:

- 910 использует прежнее постоянное состояние;
- OpenBao разблокирован и использует прежние CA и KV;
- Semaphore открывает прежнюю базу;
- OpenTofu state не заменён пустым;
- PVE API-доступ работает;
- межмашинный SSH снова соответствует `access.yaml`.

Проверка независимых резервных копий, RPO и RTO описана отдельно в политике резервного копирования.
