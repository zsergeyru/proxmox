# Автоматическое резервирование PVE и управляющего контура

**Тип:** процедура эксплуатации. **Состояние:** код подготовлен; работа на
физических дисках и восстановление ещё требуют отдельной проверки.

## 1. Что копируется

PVE создаёт единый зашифрованный комплект состояния: `/etc/pve`, сеть и
конфигурацию хоста, закрытые области
`/mnt/bindmounts/infra-manager/pve-only`,
`access`, состояние `opentofu`, `physical-hosts`, файлы Semaphore и
действительные данные PVE. Для работающей SQLite Semaphore используется
штатная копия SQLite; исходный изменяющийся файл базы исключается. OpenBao
предоставляет согласованный **Raft snapshot API**, а не сырой каталог
работающего Raft. Постоянные секреты `pve-only` не выдаются в 910.

HAOS VM 100 сохраняется штатным `vzdump` в ограниченный временный каталог
на резервном SSD, а затем включается в оба шифрованных restic-хранилища.
Постоянно открытый файл `vzdump` не сохраняется. Это не включает крупные
фотографии 340 или будущий NAS `nas-data`: для них нужны отдельные задания.

Изменяющие задания infra-manager и копирование PVE используют общую
блокировку в постоянном `state/locks/backup-gate.lock`. Состояние OpenTofu,
ключи и каталоги нельзя копировать в середине другого `deploy`.

## 2. Как устанавливается код

Очередной `infra-manager deploy 910` устанавливает на PVE отдельную
команду `infra-manager-backup`, Python-программы, описание и systemd-службы.
При этом обычная оболочка `infra-manager` не меняет своего назначения.
Установщик не форматирует носители, не создаёт ключей, не инициализирует
restic и **не включает таймер**. Существующий
`/etc/infra-manager/backup/backup.yaml` не перезаписывается из Git.

Начальное описание:
`infrastructure/hosts/pve/backup.yaml`. В нём идентификаторы диска
и сетевого NAS первоначально равны `null`, поэтому запись невозможна.

В нужный момент PVE самостоятельно устанавливает отсутствующие
`python3-yaml`, `restic`, `parted` и `nfs-common` через APT.
Проверка оборудования `inspect` не требует установки пакетов.

## 3. Разовая подготовка после проверки оборудования

Все команды выполняются в доверенном root-терминале **физического PVE**.

### Просмотр SSD без изменений

```bash
infra-manager-backup inspect
infra-manager-backup plan-ssd --disk /dev/disk/by-id/<проверенная-ссылка> --serial <серийный-номер>
```

Вторая команда требует совершенно пустой физический SSD около 240 ГБ,
проверяет структуру диска, сигнатуры и имя устройства и печатает
контрольную фразу. Если есть хоть одна подпись или раздел, программа
останавливается. Пустой SSD может не иметь таблицы разделов — это допустимо.

Только после сверки накопителя разрешается:

```bash
infra-manager-backup prepare-ssd --disk /dev/disk/by-id/<ссылка> --serial <номер> --confirm <фраза>
```

Это **изменяющая** команда. Она создаёт GPT и ext4, повторно проверяет
идентичность и не продолжает очистку при обнаружении старой разметки.
Существующие NTFS, ext4, разделы и неизвестные данные не форматируются.
Если команда оборвалась после записи разметки, повторный запуск не
предполагает, что диск пуст: требуется ручная проверка состояния.

После появления UUID:

```bash
infra-manager-backup mount-ssd --partition /dev/disk/by-id/<ссылка>-part1 --serial <номер> --uuid <UUID>
```

Это создаёт только собственную запись `/etc/fstab` и локальное
назначение в защищённом `backup.yaml`. Каталог назначения не может
подменять корневую файловую систему.

### NAS

На NAS нужно предварительно создать ограниченную область **на
`nas-backup`**, настроить NFSv4 для адреса PVE и проверить права записи.
Работа PVE на этом этапе не должна создавать или форматировать NAS-диски.

После проверки точного пути экспорта:

```bash
infra-manager-backup mount-nas --source <сервер>:/<экспорт-на-NAS>
```

Локальный путь `/mnt/pve/nas-backup` должен быть реальной
точкой подключения NFSv4. Символьная ссылка или пустая папка на системном
диске вместо NAS запрещены. Без доступного NAS резервирование не сообщает
успех даже при наличии копии на SSD.

### Секреты и хранилища restic

```bash
infra-manager-backup openbao-access
infra-manager-backup init
```

Первая команда один раз выпускает отдельный AppRole с правом только
снимка Raft и PVE-only `backup-access.json`; при этом временный root
token выпускается и отзывается согласно существующей процедуре OpenBao.
Во время первичной настройки OpenBao может кратковременно перезапуститься,
поэтому нельзя выполнять эту операцию посреди других заданий.

`init` создаёт 56-байтовый случайный пароль restic в
`/etc/infra-manager/backup/restic-password` (0600) и инициализирует
уже проверенные места хранения. Существующий пароль не перезаписывается.

**Ключ обязательно сохранить вне PVE, 910, SSD с копиями и NAS:**

```bash
infra-manager-backup export-key --to /<отдельный-смонтированный-носитель>/backup-recovery.key
```

Место назначения должно быть корнем третьего отдельного физически
подключённого носителя; файл создаётся один раз с правами 0600.
Ключ не отправляется в чат, Git или журнал.

### Первая копия и проверка

```bash
infra-manager-backup run
infra-manager-backup status
infra-manager-backup verify --repo fast-ssd
infra-manager-backup verify --repo nas-backup
```

Две независимые копии должны завершиться успешно вместе с VM 100 и
полной проверкой restic. Для пробного извлечения создать отдельный
пустой каталог с правами 0700 и применить:

```bash
infra-manager-backup verify --repo fast-ssd --extract-to <пустой-каталог> --confirm ИЗОЛИРОВАННО
```

Повторить на отдельном пустом каталоге для NAS. Восстановление не заменяет
действующие PVE, Raft и 910. Затем в изолированной среде проверить ключи,
SQLite, Raft и состояние VM 100. Проверка `restic check` или извлечение
без запуска служб **не заменяет** испытание восстановления.

После подтверждённого восстановления администратор разрешает очистку
истории отдельной командой:

```bash
infra-manager-backup approve-restore --confirm ПРОВЕРИЛ-ВОССТАНОВЛЕНИЕ
```

До этого программа **не удаляет архивы**.

## 4. Расписание, отказы и восстановление

```bash
infra-manager-backup enable
infra-manager-backup status
```

Включение допустимо только если ключ сохранён независимо и есть
полный успешный комплект на обоих местах. Systemd запускает
`infra-manager-backup.service` четыре раза в день с небольшим
случайным смещением. Архивы VM 100 пока также включаются в каждый полный
запуск, что нужно учесть при проверке времени и места; после измерений
расписание VM можно выделить отдельно.

Журнал — `journalctl -u infra-manager-backup.service`. Ошибки дисков,
ключей, блокировок или служб прерывают задание, не создавая запись об
успехе. Неуспешная копия не означает автоматически, что старая
восстановимая копия удалена.

```bash
infra-manager-backup disable
```

Немедленно отключает расписание, но не стирает данные.

После подтверждённого восстановления применяется правило хранения:
SSD — две последние точки, NAS — семь ежедневных и четыре еженедельные.
Для обеих категорий (`infra-core` и `haos`) удаление разрешается только
после создания и проверки нового комплекта.

## 5. Что не следует считать готовым до проверки оборудования

Наличие кода в Git и зелёных тестов не подтверждает фактических UUID SSD,
наличие NFS-раздела NAS, получение Raft-снимка ограниченным AppRole,
возможность гостевого `vzdump 100` или восстановление из копии.
Все эти пункты подтверждаются только на настоящем оборудовании после
слияния и установки кода. Новая программа никогда не должна удалять
действующие диски, повторно инициализировать OpenBao или перезаписывать
существующую конфигурацию PVE.
