## 1. Перед плановым изменением

Нужно определить владельца изменяемого состояния:

- PVE object → `guest.yaml` / OpenTofu;
- Linux packages и services → `provision.yaml` / Ansible;
- межсистемное право → `access.yaml` / OpenBao и конечная ACL;
- secret value → OpenBao KV;
- сетевое правило → раздел сетевой конфигурации.

Прямое ручное изменение допустимо только как диагностика или аварийное действие и затем должно быть либо отменено, либо перенесено в воспроизводимый источник.

## 2. Проверка управляющего контура

Перед значимым применением следует проверить:

- готовность 910;
- доступность PVE API и root SSH;
- состояние OpenTofu;
- доступность Semaphore и runtime;
- отсутствие другого выполняющегося изменения того же состояния.

Для 910 используется полная проверка `infra-manager-status --full`.

## 3. Проверка OpenBao и доступов

Следует контролировать:

- `sealed=false`;
- доступность KV;
- оба SSH CA;
- срок и состояние machine credentials;
- отсутствие лишних OpenBao policies относительно `access.yaml`;
- работу штатного SSH и отсутствие автоматического fallback на recovery key.

Recovery private keys не используются для обычной проверки доступности.

## 4. Проверка резервных копий

Наличие успешного задания не заменяет проверку пригодности восстановления.

Регулярно проверяются:

- наличие внешней копии канонического PVE-корня;
- согласованность OpenBao Raft и unseal data;
- OpenTofu state;
- копии критичных прикладных данных;
- доступность ключа расшифрования архива;
- периодическое практическое восстановление.

Точная периодичность и сроки хранения определяются политикой резервного копирования.

## 5. Обновление гостей

Обычное обновление гостя выполняется общим `deploy-guest` и Ansible, а не набором ручных SSH-команд.

До изменения проверяется plan OpenTofu. После изменения проверяется готовность гостя и ожидаемые сервисы.

## 6. Изменение access.yaml

Изменение технических прав проходит:

~~~text
изменить access.yaml
→ проверить схему и ссылки
→ построить access plan
→ проверить, какие capabilities изменятся
→ применить
→ проверить разрешённый и запрещённый сценарий
~~~

Обычная смена guest-to-guest SSH-права должна менять policy OpenBao, а не запускать обновление всех Linux-гостей.

## 7. После изменения

После применения нужно:

- повторить профильную проверку;
- убедиться в отсутствии незапланированного изменения соседних объектов;
- при изменении невоспроизводимого состояния создать новую пригодную резервную копию;
- при ротации credentials проверить отзыв старых полномочий.
