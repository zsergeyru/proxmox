# Файловая структура Linux-сервисов

**Type:** Policy  
**Status:** Active  
**Source of truth:** Yes — для размещения кода, конфигурации, persistent data, логов, cache и runtime-файлов внутри Linux-гостей проекта.

Этот документ относится ко всем Linux VM/LXC проекта. Он не является частью контракта template `9000`: шаблон не создаёт каталоги будущих сервисов заранее.

## 1. Базовая модель

Для собственного сервиса используется следующая смысловая схема:

```text
/opt/<service>       → приложение, наш код, deploy и административные скрипты
/etc/<service>       → конфигурация
/var/lib/<service>   → внутреннее постоянное состояние приложения
/srv/<service>       → данные, которые сервис предоставляет наружу
/var/log/<service>   → файловые логи
/var/cache/<service> → пересоздаваемый кэш
/run/<service>       → runtime-файлы текущего запуска
/tmp, /var/tmp       → временные файлы
```

Создаются только реально необходимые каталоги. Разделение нужно не ради формальности, а чтобы сущности с разным жизненным циклом можно было независимо обновлять, резервировать, очищать и восстанавливать.

## 2. `/opt/<service>` — приложение и deploy

`/opt` используется для собственного кода, вручную устанавливаемых приложений и проектной deploy-обвязки, которые не являются штатными Debian-пакетами.

Пример:

```text
/opt/my-service/
├── app/
├── scripts/
├── deploy/
└── README.md
```

В `/opt/<service>` допустимы:

- собственный код;
- shell/Python-скрипты;
- deploy-файлы;
- вручную поставляемые бинарники;
- Docker Compose-файлы, если они являются частью deploy сервиса;
- административные инструменты проекта.

Содержимое `/opt/<service>` должно по возможности восстанавливаться из Git, release-архива, пакета или другого воспроизводимого источника.

Не хранить там как единственную копию:

- базы данных;
- пользовательские файлы;
- большие persistent volumes;
- секреты;
- постоянно растущие логи;
- кэш.

## 3. `/etc/<service>` — конфигурация

`/etc/<service>` хранит конфигурацию, которая должна жить отдельно от кода и обновляться независимо от приложения.

```text
/etc/my-service/
├── config.yaml
└── policy.conf
```

Конфигурация часто входит в backup/recovery contract. Секреты, пароли, токены и private keys не должны попадать в Git даже тогда, когда несекретная часть конфигурации версионируется.

## 4. `/var/lib/<service>` — внутреннее persistent state

`/var/lib` предназначен для изменяемого постоянного состояния приложения:

- базы данных;
- индексы;
- очереди;
- metadata;
- state-файлы;
- внутренние реестры и служебные данные.

Примеры штатных каталогов:

```text
/var/lib/postgresql/
/var/lib/docker/
/var/lib/prometheus/
```

Если без этих данных сервис теряет состояние, `/var/lib/<service>` обычно входит в backup.

## 5. `/srv/<service>` — обслуживаемые данные

`/srv` используется для данных, ради которых работает сервис и которые он предоставляет пользователям или другим системам.

```text
/srv/files/
/srv/www/
/srv/media/
/srv/backups/
```

Разница:

```text
/var/lib → внутреннее состояние приложения
/srv     → содержимое, которое сервис предоставляет наружу
```

Такое разделение удобно и для последующего переноса больших данных на отдельный storage.

## 6. Логи, кэш и runtime

### `/var/log/<service>`

Используется только если сервис пишет файловые логи. Для них применяется retention/logrotate. Если сервис использует только journald, отдельный каталог создавать не нужно.

### `/var/cache/<service>`

Хранит данные, которые можно безопасно пересоздать. Потеря cache не должна означать потерю пользовательских или рабочих данных. Обычно cache не включается в backup.

### `/run/<service>`

PID-файлы, Unix sockets, lock-файлы и другое состояние текущего запуска. Не является persistent data и не восстанавливается из backup.

### `/tmp` и `/var/tmp`

Только временные данные. Важные данные там не хранятся.

## 7. Сводка backup semantics

| Каталог | Назначение | Обычно backup |
|---|---|---|
| `/opt/<service>` | код, deploy, scripts | нет, если воспроизводится из Git/release |
| `/etc/<service>` | конфигурация | да |
| `/var/lib/<service>` | внутреннее persistent state | да, если состояние важно |
| `/srv/<service>` | пользовательские/обслуживаемые данные | по ценности данных |
| `/var/log/<service>` | журналы | обычно нет |
| `/var/cache/<service>` | пересоздаваемый cache | нет |
| `/run/<service>` | runtime state | нет |
| `/tmp`, `/var/tmp` | временные данные | нет |

## 8. Небольшие собственные сервисы

Для небольшого сервиса допустим упрощённый старт:

```text
/opt/my-service/
├── app/
├── config/
├── data/
└── scripts/
```

Разделять каталоги следует, когда появляются разные требования к backup, storage, правам, retention или обновлению.

Например:

```text
/opt/my-service/data
→ /var/lib/my-service
```

если это внутреннее состояние приложения, либо:

```text
/opt/my-service/files
→ /srv/my-service
```

если это обслуживаемые файлы.

## 9. Пакетные сервисы Debian

Для программ, установленных из Debian-пакетов или официальных сторонних пакетов, используется штатная структура самого приложения. Не нужно искусственно переносить её в проектные каталоги.

Примеры:

```text
/var/lib/postgresql
/var/lib/docker
/etc/ssh
```

Это упрощает обновление, диагностику и использование upstream-документации.

## 10. Отношение к template `9000`

Базовый `tpl-debian13` не создаёт `/opt/<service>`, `/etc/<service>`, `/var/lib/<service>` или `/srv/<service>` для будущих ролей.

Template отвечает только за универсальный Debian baseline. Конкретная структура сервиса создаётся provisioning-слоем при развёртывании соответствующей роли.

Канонический template contract находится в [`../templates/debian13/build-policy.md`](../templates/debian13/build-policy.md), а граница deployer ↔ provisioning — в [`33-guest-bootstrap-and-provisioning.md`](33-guest-bootstrap-and-provisioning.md).

## 11. Recovery model

Для собственного сервиса целевой сценарий восстановления:

```text
1. Развернуть чистый Linux guest.
2. Получить приложение/deploy из Git → /opt.
3. Восстановить конфигурацию → /etc.
4. Восстановить persistent state → /var/lib.
5. Восстановить обслуживаемые данные → /srv.
6. Запустить и проверить сервис.
7. Cache, runtime и обычные логи создать заново.
```

Главный принцип: **код должен быть воспроизводим, persistent data — явно отделены, а backup должен сохранять только то, что нельзя безопасно получить заново.**
