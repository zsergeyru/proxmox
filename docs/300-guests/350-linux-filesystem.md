# Файловая структура Linux-гостей

**Тип:** политика  
**Статус:** действующий  
**Назначение:** определить, где внутри Linux-гостей размещаются файлы проекта, конфигурация, постоянные данные и временное состояние, а также задать правила каталога `rootfs/`.

Этот документ отвечает на вопрос:

> Какие файлы должны храниться в Git и разворачиваться в гостевую систему, куда они должны попадать и какие данные нельзя помещать в `rootfs/`?

## 1. Основной принцип

Файлы внутри Linux-гостя делятся по назначению и жизненному циклу.

Базовая модель проекта:

~~~text
/opt/<service>          → приложение, проектные файлы и служебные сценарии
/etc/<service>          → воспроизводимая конфигурация
/var/lib/persistent/    → единый корень невоспроизводимых постоянных данных гостя
/srv/<service>          → крупные или специально обслуживаемые данные с отдельной политикой
/var/log/<service>      → файловые журналы
/var/cache/<service>    → пересоздаваемый кэш
/run/<service>          → состояние текущего запуска
/tmp, /var/tmp          → временные файлы
~~~

Создаются только реально необходимые каталоги.

Главное правило:

> В Git хранится то, что проект должен уметь воспроизвести. Все невоспроизводимые постоянные данные обычного управляемого Linux-гостя должны физически находиться под единым корнем `/var/lib/persistent/`, чтобы резервное копирование всех гостей использовало один и тот же путь.

Имя гостя в этот путь не включается: сама VM/LXC уже является границей данных. Внутри `/var/lib/persistent/` сервисы могут создавать собственные подкаталоги.

Поэтому файлы конфигурации и проектные сценарии могут находиться в Git, а базы данных, пользовательские файлы и текущее состояние работающих приложений обычно не должны туда попадать.

## 2. Каталог `rootfs/`

### 2.1. Назначение

Каталог:

~~~text
infrastructure/guests/<VMID>-<name>/rootfs/
~~~

содержит файлы, которыми проект управляет внутри конкретного Linux-гостя.

Структура `rootfs/` повторяет абсолютную структуру файловой системы гостя.

Правило отображения:

~~~text
rootfs/<путь>
→
/<путь> внутри гостевой системы
~~~

Например:

~~~text
infrastructure/guests/310-dev-services/rootfs/etc/my-service/config.yaml
↓
/etc/my-service/config.yaml
~~~

Другой пример:

~~~text
rootfs/
├── etc/
│   ├── my-service/
│   │   └── config.yaml
│   └── systemd/
│       └── system/
│           └── my-service.service
├── opt/
│   └── my-service/
│       └── compose.yaml
└── usr/
    └── local/
        └── bin/
            └── my-service-check
~~~

После применения эти файлы должны находиться соответственно по путям:

~~~text
/etc/my-service/config.yaml
/etc/systemd/system/my-service.service
/opt/my-service/compose.yaml
/usr/local/bin/my-service-check
~~~

### 2.2. Что считается управляемым файлом

Файл следует помещать в `rootfs/`, если одновременно выполняются условия:

- его содержимое является частью требуемой конфигурации гостя;
- содержимое допустимо хранить в Git;
- файл должен воспроизводиться при повторной настройке гостя;
- изменение файла в проекте должно приводить к соответствующему изменению внутри гостя.

Типичные примеры:

- конфигурационные файлы без секретов;
- файлы systemd;
- Docker Compose-файлы;
- проектные сценарии;
- небольшие служебные программы;
- статические правила и политики;
- файлы собственного приложения, если Git является их источником.

### 2.3. Кто применяет `rootfs/`

`rootfs/` относится к состоянию **внутри гостевой операционной системы**.

Его содержимое применяет Ansible или другой явно определённый повторяемый механизм настройки гостя.

OpenTofu не копирует файлы из `rootfs/` и не должен знать их содержимое.

Общий жизненный цикл:

~~~text
OpenTofu
→ создаёт или изменяет VM/LXC

Ansible
→ подключается к гостю
→ создаёт необходимые каталоги
→ размещает управляемые файлы из rootfs/
→ применяет владельцев и права
→ при необходимости перезапускает связанные службы
~~~

### 2.4. `rootfs/` не является образом диска

Каталог не должен пытаться отражать всю файловую систему Linux.

В нём присутствуют только те пути, которыми проект действительно управляет.

Например, наличие:

~~~text
rootfs/etc/my-service/config.yaml
~~~

не требует хранить в Git остальные файлы каталога `/etc`.

### 2.5. Пустые каталоги

Пустые каталоги не следует создавать в Git только ради описания будущей структуры.

Если приложению нужен пустой каталог, его создание должно быть явно задано механизмом настройки гостя.

Файлы вроде `.gitkeep` только для сохранения пустой структуры не нужны.

## 3. Размещение файлов внутри Linux

### 3.1. `/opt/<service>` — приложение и проектные файлы

`/opt` используется для собственного кода, вручную поставляемых приложений и проектных файлов, которые не являются обычными файлами Debian-пакета.

Там могут находиться:

- собственный код;
- административные сценарии;
- файлы запуска;
- Docker Compose-файлы;
- небольшие поставляемые вместе с проектом программы;
- другие воспроизводимые файлы службы.

Пример:

~~~text
/opt/my-service/
├── app/
├── scripts/
└── compose.yaml
~~~

Содержимое `/opt/<service>` должно по возможности полностью восстанавливаться из Git, пакета или другого воспроизводимого источника.

### 3.2. `/etc/<service>` — конфигурация

`/etc` используется для постоянной конфигурации системы и приложений.

Пример:

~~~text
/etc/my-service/
├── config.yaml
└── policy.conf
~~~

Несекретная конфигурация может храниться в `rootfs/`.

Секретная часть конфигурации должна поступать из отдельного механизма управления секретами.

### 3.3. `/var/lib/persistent/` — единый корень постоянного состояния

Все невоспроизводимые постоянные данные, которыми владеет проект внутри обычного управляемого Linux-гостя, физически размещаются под:

~~~text
/var/lib/persistent/
~~~

Типичная структура:

~~~text
/var/lib/persistent/
├── <service-a>/
├── <service-b>/
└── secrets/
~~~

Конкретные подкаталоги определяются составом гостя. Общим контрактом является только корень `/var/lib/persistent/`.

К таким данным относятся:

- базы данных;
- состояние приложений;
- индексы и внутренние реестры, если их потеря недопустима;
- состояние средств управления, например OpenTofu state;
- локальные секреты, которые пока нельзя безопасно перевыпустить или получить из отдельного хранилища секретов.

Приложение не обязано само использовать путь `/var/lib/persistent/`. Если оно ожидает штатный путь, например:

~~~text
/var/lib/openbao/
/var/lib/postgresql/
/var/lib/semaphore/
~~~

проект должен настроить приложение или использовать явную привязку так, чтобы физически сохраняемые данные находились под `/var/lib/persistent/`, а приложение продолжало видеть ожидаемый им путь.

Для Docker постоянные данные проектных контейнеров должны использовать явные bind mount из `/var/lib/persistent/`. Анонимные Docker volumes и именованные volumes не должны быть единственным местом хранения критичных данных, которые входят в стандартную резервную копию.

Содержимое `/var/lib/persistent/` не хранится в `rootfs/` и является стандартным объектом резервного копирования гостя.

### 3.4. `/srv/<service>` — обслуживаемые данные

`/srv` используется для данных, ради которых работает служба и которые она предоставляет пользователям или другим системам.

Примеры:

~~~text
/srv/files/
/srv/www/
/srv/media/
~~~

Различие:

~~~text
/var/lib/persistent → обязательное невоспроизводимое состояние гостя
/srv                → крупные или специально обслуживаемые данные с отдельной политикой
~~~

`/srv` не является частью единого обязательного пути резервного копирования. Если сервис использует `/srv`, для этих данных должна быть явно определена отдельная политика: резервировать, хранить другим способом или сознательно не сохранять.

Рабочее содержимое `/srv` обычно не хранится в `rootfs/`.

### 3.5. `/var/log/<service>` — файловые журналы

Каталог используется только тогда, когда приложение действительно пишет отдельные файловые журналы.

Если служба использует только `journald`, создавать отдельный каталог журналов не нужно.

Журналы являются фактическим состоянием работающей системы и не хранятся в `rootfs/`.

### 3.6. `/var/cache/<service>` — кэш

Здесь находятся данные, которые можно безопасно пересоздать.

Потеря кэша не должна означать потерю пользовательских или рабочих данных.

Кэш не хранится в `rootfs/` и обычно не включается в резервную копию.

### 3.7. `/run/<service>` — состояние текущего запуска

Здесь могут находиться:

- PID-файлы;
- Unix-сокеты;
- файлы блокировок;
- другое состояние текущего процесса.

`/run` не является постоянным хранилищем.

Его содержимое не хранится в Git и не восстанавливается из резервной копии.

### 3.8. `/tmp` и `/var/tmp`

Эти каталоги предназначены для временных файлов.

Важные данные и единственные копии файлов там не хранятся.

## 4. Что не должно храниться в `rootfs/`

В `rootfs/` не следует помещать:

- базы данных;
- пользовательские файлы;
- рабочие тома приложений;
- содержимое Docker volumes;
- кэш;
- журналы работы;
- PID-файлы и сокеты;
- временные файлы;
- резервные копии;
- выгрузки фактического состояния работающей системы;
- секреты, пароли, токены и закрытые ключи.

Также не следует копировать в `rootfs/` файлы только потому, что они существуют внутри работающего гостя.

Критерий должен быть обратным:

> Если гостевую систему создать заново, нужен ли именно этот файл из Git для воспроизведения требуемой конфигурации?

Если нет, файл обычно не относится к `rootfs/`.

## 5. Права, владельцы и изменение файлов

### 5.1. Путь не определяет владельца и права

Расположение файла в `rootfs/` определяет его целевой путь, но не полностью описывает его свойства в Linux.

Например:

~~~text
rootfs/usr/local/bin/my-script
~~~

говорит только о целевом пути:

~~~text
/usr/local/bin/my-script
~~~

Владелец, группа и режим доступа задаются механизмом повторяемой настройки.

Они не должны угадываться только по расположению файла.

### 5.2. Исполняемые файлы

Если файл должен быть исполняемым, это должно быть явно обеспечено настройкой гостя.

Нельзя полагаться только на то, как права файла случайно сохранились в рабочей копии Git.

### 5.3. Шаблонные и вычисляемые файлы

`rootfs/` предназначен прежде всего для файлов с содержимым, которое можно хранить в Git напрямую.

Если содержимое должно собираться из переменных конкретного гостя или секретов, его формирование должно быть явно описано средствами Ansible.

Нельзя незаметно вводить собственный язык подстановок внутри `rootfs/`.

### 5.4. Изменения вручную

Если файл находится под управлением проекта, ручное изменение его содержимого внутри гостя не становится новым требуемым состоянием.

Следующее применение настройки имеет право вернуть файл к содержимому, определённому проектом.

Постоянное изменение такого файла сначала вносится в проект.

## 6. Постоянные данные и резервное копирование

Для обычных управляемых Linux-гостей действует единый контракт:

~~~text
резервировать /var/lib/persistent/
~~~

Система резервного копирования не должна знать имя гостя, внутренние пути конкретного приложения или перечень его контейнеров.

Обычная политика:

| Каталог | Назначение | Стандартная политика |
|---|---|---|
| `/opt/<service>` | воспроизводимые файлы приложения и проекта | не резервировать |
| `/etc/<service>` | воспроизводимая конфигурация | восстанавливать из Git и Ansible |
| `/var/lib/persistent/` | невоспроизводимое постоянное состояние | резервировать всегда |
| `/srv/<service>` | крупные или отдельно обслуживаемые данные | отдельная явная политика |
| `/var/log/<service>` | журналы | обычно не резервировать |
| `/var/cache/<service>` | пересоздаваемый кэш | не резервировать |
| `/run/<service>` | состояние текущего запуска | не резервировать |
| `/tmp`, `/var/tmp` | временные данные | не резервировать |

Если важный локальный файл в `/etc` нельзя воспроизвести из Git, Ansible, OpenBao или другого нормативного источника, он не должен оставаться скрытым исключением. Его необходимо либо сделать воспроизводимым, либо перенести его сохраняемую часть под `/var/lib/persistent/`.

Наличие файла в Git и резервное копирование решают разные задачи.

Git хранит требуемую конфигурацию и воспроизводимые файлы.

Резервная копия `/var/lib/persistent/` сохраняет данные, которые нельзя безопасно получить заново только из проекта.

## 7. Пакетные и небольшие собственные службы

### 7.1. Пакетные службы Debian

Для программ, установленных из Debian-пакетов или официальных сторонних пакетов, используется штатная структура самого приложения.

Например:

~~~text
/etc/ssh/
/var/lib/postgresql/
/var/lib/docker/
~~~

Не нужно искусственно переносить их файлы в `/opt` только ради единообразия.

Если проект управляет отдельным несекретным конфигурационным файлом пакетной службы, этот файл может быть представлен соответствующим путём в `rootfs/`.

### 7.2. Небольшие собственные службы

Для небольшого собственного приложения допустима компактная структура в `/opt/<service>`, пока разные виды данных имеют одинаковый жизненный цикл.

Например:

~~~text
/opt/my-service/
├── app/
├── scripts/
└── compose.yaml
~~~

Если появляются изменяемые постоянные данные, их следует отделить:

~~~text
обязательное невоспроизводимое состояние → /var/lib/persistent/my-service
крупные отдельно обслуживаемые данные    → /srv/my-service
~~~

Нельзя оставлять важные рабочие данные внутри каталога приложения только потому, что так было проще на первом этапе.

## 8. Восстановление гостевой системы

Целевая модель восстановления Linux-гостя:

~~~text
1. Создать VM/LXC заново.
2. Подготовить административный доступ.
3. Установить требуемые пакеты и службы.
4. Развернуть управляемые файлы проекта, включая rootfs/.
5. Получить секреты из их отдельного источника.
6. Восстановить `/var/lib/persistent/` из резервной копии и отдельно восстановить данные `/srv`, если для них задана собственная политика.
7. Запустить и проверить службы.
8. Пересоздать кэш и временное состояние автоматически.
~~~

Эта модель определяет важную границу:

~~~text
Git + Ansible
→ воспроизводимая конфигурация

резервные копии
→ невоспроизводимые постоянные данные
~~~

Чем яснее эта граница для каждой службы, тем проще её обновлять, переносить и восстанавливать.
