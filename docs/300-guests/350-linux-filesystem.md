# Файловая структура Linux-гостей

**Тип:** политика  
**Статус:** действующий  
**Назначение:** определить назначение каталогов внутри Linux-гостей и отделить воспроизводимую конфигурацию от изменяемых данных.

Каталог `rootfs/` является необязательной частью каталога гостя для воспроизводимых файлов, которые устанавливаются внутрь Linux. Он повторяет конечные пути файловой системы, но проект по-прежнему не поддерживает универсальное зеркалирование `rootfs/` поверх `/`.

## 1. Основной принцип

Файл или каталог размещается по смыслу и жизненному циклу, а не по удобству конкретного сценария установки.

Базовая модель:

```text
/opt/<service>       → приложение и проектные файлы
/etc/<service>       → конфигурация
/var/lib/<service>   → внутреннее постоянное состояние
/srv/<service>       → обслуживаемые данные
/var/log/<service>   → файловые журналы
/var/cache/<service> → пересоздаваемый кэш
/run/<service>       → состояние текущего запуска
/tmp, /var/tmp       → временные файлы
```

Создаются только реально необходимые каталоги.

Главное разделение:

```text
Git + Ansible
→ воспроизводимая конфигурация

резервные копии
→ невоспроизводимые постоянные данные
```

## 2. Стандартные области Linux

### 2.1. `/opt/<service>`

Используется для собственного кода, поставляемых проектом приложений, Compose-файлов и других воспроизводимых файлов, которые не относятся к штатному Debian-пакету.

Изменяемые пользовательские данные внутри каталога приложения хранить не следует.

### 2.2. `/etc/<service>`

Используется для конфигурации.

Несекретные значения могут формироваться проектом.

Секреты должны поступать из отдельного механизма и не храниться в Git.

### 2.3. `/var/lib/<service>`

Используется для внутреннего изменяемого состояния приложения:

- базы данных;
- индексы;
- очереди;
- реестры;
- метаданные.

Если это состояние важно, оно требует резервного копирования.

### 2.4. `/srv/<service>`

Используется для данных, которые служба предоставляет пользователям или другим системам.

Различие:

```text
/var/lib → внутреннее состояние программы
/srv     → обслуживаемые данные
```

### 2.5. `/var/log/<service>`

Создаётся только если приложение действительно пишет отдельные файловые журналы.

Если достаточно `journald`, отдельный каталог не требуется.

### 2.6. `/var/cache/<service>`

Содержит только данные, которые можно безопасно пересоздать.

### 2.7. `/run/<service>`

Содержит PID-файлы, сокеты, блокировки и другое состояние текущего запуска.

Не является постоянным хранилищем.

## 3. Как проект управляет файлами

Управляемые файлы Linux устанавливаются явной автоматизацией.

Допустимые источники:

- общий статический файл Ansible-роли;
- общий шаблон Ansible;
- файл конкретного гостя из `rootfs/`;
- генерация из данных `provision.yaml`;
- другой явно описанный воспроизводимый источник.

Для `rootfs/` действует строгий контракт:

```text
<guest>/rootfs/etc/example.conf
→ предназначен для /etc/example.conf

<guest>/rootfs/opt/service/file
→ предназначен для /opt/service/file
```

Совпадение пути не означает автоматического копирования. Ansible или другой явный механизм всё равно обязан назвать исходный файл, конечный путь, владельца, группу и права.

Запрещены универсальные операции:

```text
cp -a rootfs/* /
rsync rootfs/ /
```

В `rootfs/` не хранятся изменяемые базы, состояние служб, журналы, кэш, содержимое `/run` и секреты.

Общие файлы, нужные нескольким гостям, остаются в общих Ansible-ролях.

Если новой службе нужен конфигурационный файл, способ его установки должен быть понятен из Ansible-роли или другого явно указанного повторяемого механизма.

Произвольное ручное изменение управляемого файла внутри гостя не становится новым требуемым состоянием.

## 4. Постоянные и воспроизводимые данные

Для каждого важного каталога нужно определить один из двух основных классов.

**Воспроизводимый** — содержимое можно получить заново из Git, пакета, образа или другого надёжного источника.

**Постоянный** — содержимое изменяется во время работы и не может быть восстановлено только из проекта.

`provision.yaml` может машинно фиксировать такие границы, например через сведения о данных, требующих резервного копирования, и данных, которые можно воспроизвести.

Размещение на отдельном физическом носителе само по себе не заменяет резервную копию.

## 5. Права и владельцы

Целевой путь не определяет автоматически владельца, группу и режим доступа.

Эти свойства должны задаваться явной автоматизацией.

Исполняемый файл должен получать право исполнения из повторяемой настройки, а не полагаться на случайные права рабочей копии Git.

Для секретных каталогов применяются минимально необходимые разрешения.

## 6. Временные данные и журналы

Не являются частью требуемого содержимого Git:

- кэш;
- журналы работы;
- PID-файлы;
- сокеты;
- временные файлы;
- одноразовые ключи;
- результаты диагностики.

Если такой файл нужен для работы службы, автоматизация должна уметь создать его заново или позволить самой службе сформировать его при запуске.

## 7. Восстановление

Нормальная модель восстановления Linux-гостя:

```text
создать VM/LXC
↓
получить административный доступ
↓
применить provision.yaml через Ansible
↓
восстановить секреты
↓
восстановить невоспроизводимые постоянные данные
↓
запустить и проверить службы
```

Кэш и состояние текущего запуска восстанавливать из резервной копии не требуется.

Чем точнее отделены воспроизводимые файлы от постоянных данных, тем безопаснее пересоздание гостя.
