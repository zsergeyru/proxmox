# Развёртывание гостевой системы

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** определить безопасный и однозначный порядок работы команды `deploy-guest` для одной VM/LXC.

Этот документ отвечает на вопрос:

> Как `deploy-guest` должен построить план изменений, безопасно применить требуемое состояние гостя и проверить результат?

Модель требуемого состояния определяется в [`310-guest-state.md`](310-guest-state.md), а формат и поля `guest.yaml` — в [`320-guest-manifest.md`](320-guest-manifest.md). Этот документ описывает только применение состояния и не создаёт параллельную модель.

> **Статус реализации:** существующий `scripts/pve/deploy-guest.py` относится к более раннему контракту и должен быть переработан по этой спецификации.

## 1. Назначение и границы

### 1.1. Назначение `deploy-guest`

`deploy-guest` — локальная команда PVE-хоста для управляемого развёртывания одной гостевой системы.

Общая последовательность:

```text
итоговое состояние из 310
+ фактическое состояние
→ планирование (`PLAN`)
→ применение (`APPLY`)
→ подготовка гостевой ОС
→ итоговая проверка (`VERIFY`)
```

По умолчанию команда только сравнивает требуемое и фактическое состояние и показывает план. С флагом `--apply` она выполняет разрешённые изменения и не считает операцию успешной до итоговой проверки.

### 1.2. Область ответственности

`deploy-guest` отвечает за:

- создание новой VM/LXC;
- изменение поддерживаемых параметров существующего объекта;
- ресурсы, основной диск и административную сеть;
- `onboot` и `protection`;
- членство в пуле `managed` по `pve_management`;
- запуск гостя, если он нужен для завершения развёртывания;
- административный SSH;
- запрошенные возможности `management`;
- запрошенную первоначальную подготовку `bootstrap`;
- итоговую проверку результата.

### 1.3. Что не входит в ответственность

`deploy-guest` не должен:

- удалять VM/LXC как обычную операцию приведения состояния;
- автоматически пересоздавать объект;
- автоматически принимать под управление неизвестный объект только по совпадению VMID;
- выполнять произвольные команды из `guest.yaml`;
- заменять Ansible;
- управлять постоянной конфигурацией PVE-хоста;
- самостоятельно строить параллельную модель требуемого состояния.

### 1.4. Связь с `310` и `320`

`310-guest-state.md` определяет построение требуемого состояния, а `320-guest-manifest.md` — поля и ограничения `guest.yaml`. `deploy-guest` использует общий `scripts/guests/resolver.py` и итоговую схему `schemas/guest-effective.schema.yaml`.

Если итоговое состояние не может быть построено или не проходит проверку, применение не начинается.

## 2. Интерфейс и входные данные

### 2.1. Интерфейс команды

Базовый интерфейс:

```bash
deploy-guest <VMID>
deploy-guest <VMID> --apply
```

VMID находится в диапазоне `100–999`.

Без `--apply` выполняется только планирование (`PLAN`). С `--apply` команда сначала строит тот же план, затем применяет его (`APPLY`) и выполняет итоговую проверку (`VERIFY`).

Лишние пользовательские переключатели не добавляются, если поведение является обязательной частью нормального развёртывания.

### 2.2. Планирование (`PLAN`) и применение (`APPLY`)

Планирование и применение используют одно итоговое состояние и одну зафиксированную ревизию Git.

Режим планирования (`PLAN`) не должен изменять PVE, гостевую ОС, доверие к SSH-ключам, реестр управляющих ключей или служебные признаки развёртывания.

Если ревизия Git изменилась, должен начинаться новый запуск с новым планом.

### 2.3. Требуемое состояние

Требуемое состояние строится только через `scripts/guests/resolver.py`.

Для VMID должен существовать ровно один `guest.yaml`, а гость должен содержать `profile`. Объекты без `profile` универсальным контуром развёртывания не управляются.

### 2.4. Фактическое состояние

На уровне Proxmox проверяются наличие и тип объекта, узел, состояние запуска, ресурсы, диск, сеть, `onboot`, `protection`, пул `managed` и служебный признак принадлежности объекта проекту.

На уровне гостевой ОС, когда она доступна, проверяются административный SSH, ключ узла SSH, `management` и `bootstrap`.

### 2.5. Доверенная ревизия Git

Используется доверенная копия проекта `/var/lib/proxmox-deployer/repo/`.

Перед запуском основной логики обёртка должна проверить владельца и права локальной копии, убедиться в отсутствии неразрешённых изменений, получить разрешённую ветку и определить точный SHA коммита. Новая ревизия считается принятой только после успешного `scripts/validate_repo.py`.

Если полученная ревизия не проходит проверку, каноническая копия возвращается на предыдущую принятую ревизию, а `last-revision` не изменяется.

Основная логика должна убедиться, что исполняется код именно принятой ревизии.

### 2.6. Локальная среда выполнения

Стабильный интерфейс — `/usr/local/sbin/deploy-guest`, установленный PVE Configuration.

Обёртка запускается от `root`, а основная логика выполняется от системного пользователя `pvedeploy` там, где права `root` не требуются.

Для PVE API используется `deployer@pve!host-deploy`.

Общая блокировка операций:

```text
/run/lock/proxmox-orchestration.lock
```

Секреты не передаются через аргументы командной строки и не выводятся в журнал.

## 3. Подготовка и построение плана

### 3.1. Предварительные проверки

До построения плана проверяются доверенная локальная копия Git и её ревизия, успешная проверка репозитория, единственный манифест для VMID, наличие `profile`, корректное итоговое состояние, локальная конфигурация PVE и API-токен, источник создания, требуемые сеть и хранилище, административный SSH-контур и реестр управляющих ключей.

### 3.2. Источник создания

Для VM проверяется `template_vmid`: источник существует, является шаблоном и соответствует поддерживаемому контракту проекта.

Для LXC селектор `ostemplate` разрешается в конкретный доступный образ поддерживаемого семейства.

Неоднозначный или отсутствующий источник блокирует создание.

### 3.3. Принадлежность существующего объекта

Совпадение VMID не означает, что существующий объект принадлежит проекту.

`deploy-guest` должен проверять внутренний служебный признак принадлежности. Если принадлежность не подтверждена, результат — `BLOCKED`.

Обычное применение (`APPLY`) не должно автоматически принимать такой объект под управление. Конкретное представление служебного признака не является полем `guest.yaml`.

### 3.4. Построение плана (`PLAN`)

План строится полностью до первого изменения и для каждого элемента показывает фактическое значение, требуемое значение, действие и причину блокировки.

Минимально сравниваются объект и тип, PVE-узел, CPU и память, диск и хранилище, сеть, `onboot`, `protection`, пул `managed`, административный SSH, `management` и `bootstrap`.

### 3.5. Действия плана

| Действие | Значение |
|---|---|
| `CREATE` | управляемый элемент отсутствует и должен быть создан |
| `UPDATE` | поддерживаемое значение должно быть изменено |
| `REMOVE` | управляемый проектом вспомогательный элемент должен быть удалён |
| `NO CHANGE` | фактическое состояние соответствует требуемому |
| `BLOCKED` | безопасное автоматическое продолжение невозможно |

`REMOVE` не означает автоматическое удаление VM/LXC.

### 3.6. Блокирующие условия

Обычное развёртывание блокируется при попытке автоматически принять под управление неизвестный объект, смене типа VM ↔ LXC, уменьшении диска, смене хранилища существующего диска, неподдерживаемой миграции между PVE-узлами, пересоздании или удалении гостя, конфликте SSH-ключа узла или управляющей SSH-идентичности, а также если изменение работающего гостя требует остановки без определённой безопасной политики.

Статус `BLOCKED` означает, что для продолжения требуется отдельное осознанное действие человека.

## 4. Применение состояния Proxmox

### 4.1. Создание VM

Новая VM создаётся из `template_vmid` полным клонированием.

До запуска применяются поддерживаемые ресурсы, основной сетевой интерфейс, `onboot`, `protection`, членство в `managed` и внутренний признак принадлежности проекту.

VM наследует от шаблона технические свойства, которые не являются индивидуальными параметрами состояния, включая BIOS/UEFI и поддержку гостевого агента QEMU.

### 4.2. Создание LXC

Новый LXC создаётся из разрешённого образа `ostemplate` и является непривилегированным.

Если профиль содержит `container-host`, включаются необходимые внутренние возможности контейнера для вложенной среды выполнения контейнеров.

После создания применяются ресурсы, сеть, `onboot`, `protection`, членство в `managed` и внутренний признак принадлежности.

### 4.3. Изменение существующего объекта

Для существующей VM/LXC применение (`APPLY`) изменяет только параметры, которые входят в контракт состояния, поддерживаются реализацией и имеют однозначное безопасное действие.

Неуправляемые параметры Proxmox не должны сбрасываться только потому, что отсутствуют в `guest.yaml`.

### 4.4. Ресурсы и диск

CPU и память приводятся к требуемым значениям, если изменение поддерживается для текущего состояния гостя.

Для основного диска: достигнутый размер означает `NO CHANGE`, поддерживаемое увеличение — `UPDATE`, уменьшение — `BLOCKED`, а смена хранилища существующего диска — `BLOCKED` до появления отдельного контракта миграции.

### 4.5. Сеть

Управляется один основной административный интерфейс по итоговому состоянию из `310`.

Несколько интерфейсов, VLAN и другие расширенные сценарии не должны угадываться из текущего простого контракта.

### 4.6. `onboot` и `protection`

`boot.onboot` управляет только постоянным автозапуском вместе с PVE и не определяет, должен ли текущий запуск `deploy-guest` запустить гостя для завершения развёртывания.

`protection` приводится к требуемому состоянию как встроенная защита PVE.

### 4.7. `pve_management` и пул `managed`

```text
pve_management: true  → объект должен находиться в managed
pve_management: false → объект не должен находиться в managed
```

Изменение членства в пуле не изменяет административный SSH и отдельные полномочия `deployer@pve!host-deploy`.

### 4.8. Запрещённые и неподдерживаемые изменения

Без отдельного контракта обычное применение (`APPLY`) не выполняет удаление или пересоздание гостя, смену типа, уменьшение диска, миграцию хранилища, миграцию между PVE-узлами и автоматическую остановку работающего гостя для неподдерживаемого изменения.

План должен показать `BLOCKED` и причину блокировки, а не скрывать такое действие.

## 5. Подготовка гостевой системы

### 5.1. Запуск и ожидание готовности

После применения изменений на уровне PVE гостевая система запускается, если это необходимо для административной проверки и первоначальной подготовки.

Отдельного `start_after_deploy` в состоянии нет.

Состояние `running` не является доказательством готовности: требуется дождаться административного SSH в ограниченный срок.

### 5.2. Административный SSH

Для любого гостя с `profile` используется фиксированный контракт `root:22`.

Для подключения используется отдельная пара SSH-ключей PVE-хоста, подготовленная PVE Configuration. Проверка TCP-порта недостаточна — требуется полноценное SSH-подключение.

### 5.3. Доверие к ключу узла SSH

Для нового гостя первоначальное доверие к ключу узла может устанавливаться только в контролируемом сценарии его создания.

Для существующего гостя несовпадение ранее доверенного ключа означает `BLOCKED`; автоматическая замена запрещена.

### 5.4. `management.ssh_identity`

Если запрошен `ssh_identity`, средство обеспечивает гостю собственную исходящую пару SSH-ключей, проверяет её, регистрирует открытый ключ и запускает общую синхронизацию управляющих ключей.

Конфликт отпечатков или неоднозначное состояние реестра → `BLOCKED`.

Автоматический отзыв и удаление этой идентичности допускается только после отдельного безопасного контракта отзыва.

### 5.5. `management.project_repo_read`

Если запрошен `project_repo_read`, гостю предоставляется управляемый доступ только для чтения к `zsergeyru/proxmox` через отдельную эталонную копию ключа развёртывания GitHub (`Deploy Key`).

Если возможность больше не нужна, удаляются только проектные ключи и настройки этого механизма. Пользовательские репозитории и произвольные SSH/Git-настройки не удаляются.

### 5.6. Первоначальная подготовка `bootstrap`

Для `git`, `docker` и `ansible` используется модель:

```text
проверить
→ при отсутствии установить
→ повторно проверить
```

Необходимые базовые предпосылки гостевой ОС обеспечивает сам контур развёртывания.

### 5.7. Граница `bootstrap`

Исчезновение `git`, `docker` или `ansible` из списка `bootstrap` не означает автоматическое удаление уже установленной программы.

Прикладные сервисы, Docker Compose-проекты, Jenkins, Semaphore, Gitea/Gogs и аналогичные приложения к `bootstrap` не относятся.

### 5.8. Передача дальнейшей настройки Ansible

После того как `deploy-guest` создал или обновил VM/LXC, обеспечил административный SSH и выполнил минимальную первоначальную подготовку, дальнейшая повторяемая настройка гостевой операционной системы передаётся Ansible.

Каталог:

```text
guests/<VMID>-<name>/rootfs/
```

не применяется самим `deploy-guest`.

Файлы из `rootfs/` разворачиваются Ansible в соответствующие абсолютные пути внутри гостевой ОС.

Такое разделение сохраняет границу ответственности:

```text
deploy-guest
→ объект Proxmox
→ базовый административный доступ
→ минимальная первоначальная готовность

Ansible
→ rootfs/
→ постоянная настройка ОС
→ пакеты и службы
→ прикладная конфигурация
```

Повторное применение Ansible должно быть штатной операцией и не должно уничтожать данные, которые не входят в управляемую проектом область.

## 6. Завершение и повторный запуск

### 6.1. Признак незавершённого развёртывания

Перед первым изменением режим применения (`APPLY`) устанавливает внутренний признак незавершённого развёртывания.

Он не является полем требуемого состояния и снимается только после полной итоговой проверки (`VERIFY`).

### 6.2. Итоговая проверка

Итоговая проверка (`VERIFY`) повторно получает фактическое состояние и подтверждает существование и тип объекта, PVE-узел, ресурсы, диск, сеть, `onboot`, `protection`, членство в `managed`, административный SSH, запрошенные `management` и `bootstrap`.

Успешная отдельная API-команда не заменяет итоговую проверку.

### 6.3. Успешное завершение

Только после успешной итоговой проверки снимается признак незавершённости, повторно подтверждается его отсутствие и операция фиксируется как успешная.

### 6.4. Поведение после ошибки

При ошибке режим применения не удаляет автоматически созданную гостевую систему, не выполняет разрушительный общий откат и не скрывает частично выполненное состояние.

Если изменения уже начались, признак незавершённости сохраняется.

### 6.5. Повторный запуск и идемпотентность

Повторный запуск заново читает актуальное требуемое и фактическое состояние и строит новый план.

Уже выполненные корректные действия не должны выполняться с новыми побочными эффектами.

Если всё соответствует требованиям, результат — `NO CHANGE`.

## 7. Результаты, ошибки и аудит

### 7.1. Успех и `NO CHANGE`

Успех означает либо отсутствие требуемых изменений, либо завершённое применение с полной итоговой проверкой.

### 7.2. `BLOCKED`

`BLOCKED` используется, когда состояние понятно, но обычное развёртывание не имеет права безопасно выполнить необходимое действие.

Если блокирующее условие обнаружено на стадии планирования, применение не начинается.

### 7.3. Ошибка выполнения

Ошибка означает, что разрешённая операция не смогла завершиться или итоговая проверка обнаружила несоответствие.

### 7.4. Коды завершения

```text
0 — успех или NO CHANGE
2 — BLOCKED
3 — ошибка выполнения
```

### 7.5. Аудит

Каждый запуск оставляет структурированную запись: время, VMID, SHA коммита Git, режим (`PLAN` или `APPLY`), стадию, итог и безопасное краткое описание.

### 7.6. Защита секретов

В вывод и аудит запрещено записывать секрет API-токена, закрытые SSH-ключи, ключ развёртывания GitHub (`Deploy Key`), пароли, секретные переменные окружения и содержимое файлов учётных данных.

## 8. Границы с другими механизмами и связанные документы

### 8.1. Разделение ответственности

| Механизм | Ответственность |
|---|---|
| `310-guest-state.md` | описание и проверка требуемого состояния |
| `deploy-guest` | планирование, применение и итоговая проверка одной VM/LXC |
| PVE Configuration | постоянная конфигурация PVE-хоста и служебное окружение |
| `sync-management-keys` | общая синхронизация административных SSH-ключей |
| Ansible | развёртывание управляемых файлов из `rootfs/` и последующая повторяемая настройка ОС и приложений |
| AI API/MCP-контур | прямое управление разрешёнными объектами Proxmox через отдельную PVE-идентичность |

### 8.2. `sync-management-keys`

`deploy-guest` может запускать синхронизацию после изменения `ssh_identity`, но алгоритм общей синхронизации остаётся отдельным механизмом.

### 8.3. PVE Configuration

PVE Configuration заранее подготавливает `pvedeploy`, учётную запись и API-токен, локальную конфигурацию, доверенную Git-копию, SSH-данные, эталонный ключ чтения проекта, реестр открытых ключей, пул `managed`, базовый шаблон, `/usr/local/sbin/deploy-guest`, блокировку и каталог аудита.

`deploy-guest` проверяет эти предпосылки, но не создаёт постоянную конфигурацию PVE-хоста заново.

### 8.4. AI API/MCP-контур

`deploy-guest` и AI-агент — разные интерфейсы управления.

`deploy-guest` использует локальную учётную запись прямого развёртывания. AI-агент использует собственную учётную запись PVE и получает обычные права на объекты через ACL пула `managed`.

`pve_management` определяет доступность объекта для AI через PVE, а не возможность `deploy-guest` применить требуемое состояние.

### 8.5. Последующая настройка

После развёртывания повторяемая настройка ОС и приложений относится к специализированным механизмам, прежде всего Ansible.

`bootstrap` остаётся ограниченной первоначальной подготовкой и не заменяет Ansible.
