## 1. Решения по модели состояния

### 1.1. Почему используются общие настройки, профиль и индивидуальный манифест

**Проблема.**  
Параметры гостя имеют разный смысл: часть одинакова для большинства объектов, часть определяет технический класс, а часть относится только к конкретному экземпляру.

**Рассмотренные варианты.**

- хранить полное описание в каждом госте;
- переносить почти всё в профили;
- разделить общие, типовые и индивидуальные значения.

**Принятое решение.**  
Используются три уровня: общие настройки, профиль и индивидуальный `guest.yaml`.

**Почему.**

- общие значения не копируются;
- профиль не превращается в описание конкретной машины;
- индивидуальный манифест показывает реальные отличия;
- изменение общего правила не требует массового редактирования.

**Последствия и ограничения.**

- итоговое состояние нельзя получить простым чтением одного файла;
- нужен единый механизм объединения;
- для каждого поля должна быть определена его область ответственности.

**Когда пересматривать.**  
Если появится более простой способ сохранить те же границы без дублирования данных.

### 1.2. Почему профиль описывает техническую основу, а не владельца жизненного цикла

**Проблема.**  
Один и тот же технический класс гостя может создаваться обычным или специальным контуром.

**Рассмотренные варианты.**

- делать отдельные профили для каждого владельца;
- отказаться от общего профиля для специальных гостей;
- отделить техническую основу от владения жизненным циклом.

**Принятое решение.**  
Профиль определяет тип и технический способ создания, но не решает, какой OpenTofu-контур владеет объектом.

**Почему.**

- специальный жизненный цикл не требует второго формата гостя;
- общие ограничения VM/LXC остаются едиными;
- различия владения описываются там, где они действительно существуют.

**Последствия и ограничения.**

- наличие профиля нельзя трактовать как доказательство обычного жизненного цикла;
- специальные объекты должны явно описывать владельца своего состояния.

**Когда пересматривать.**  
Если технический профиль и владение объектом станут неразделимыми по самой технологии.

## 2. Решения по разделению YAML

### 2.1. Почему объект Proxmox и содержимое ОС описываются отдельно

**Проблема.**  
Ресурсы VM/LXC и пакеты внутри Linux относятся к разным уровням управления.

**Рассмотренные варианты.**

- один большой YAML;
- хранить всё в Ansible;
- разделить объект виртуализации и состояние ОС.

**Принятое решение.**  
`guest.yaml` описывает объект Proxmox, а `provision.yaml` — содержимое поддерживаемой Linux-системы.

**Почему.**

- OpenTofu и Ansible получают чёткие области ответственности;
- изменение приложения не требует менять модель объекта;
- один общий Ansible-контракт может обслуживать разные гости.

**Последствия и ограничения.**

- требуется согласованность двух описаний;
- зависимости между возможностями виртуализации и ПО должны проверяться отдельно.

**Когда пересматривать.**  
Если появится единый декларативный механизм, который сохранит те же границы ответственности.

### 2.2. Почему описание проверок готовности является отдельным

**Проблема.**  
Не каждому гостю нужен сложный итоговый экран и одинаковый набор проверок.

**Рассмотренные варианты.**

- зашить проверки в код;
- хранить их в README;
- использовать необязательное машинное описание.

**Принятое решение.**  
Для гостей, которым это нужно, используется отдельный `status.yaml`.

**Почему.**

- требуемая конфигурация не смешивается с представлением фактического состояния;
- набор проверок можно расширять независимо;
- человекочитаемая документация не становится машинным контрактом.

**Последствия и ограничения.**

- каждый новый тип проверки должен поддерживаться исполняющим механизмом;
- наличие `status.yaml` не делает его универсальным для всех гостей автоматически.

**Когда пересматривать.**  
Если проверки будут полностью стандартизованы для всех классов гостей.

### 2.3. Почему нет универсального зеркала файловой системы из Git

**Проблема.**  
Зеркалирование дерева Linux из каталога репозитория выглядит простым, но скрывает права, шаблонизацию, секреты и порядок применения.

**Рассмотренные варианты.**

- копировать дерево файлов поверх гостя;
- использовать отдельные сценарии для каждого файла;
- создавать управляемые файлы через Ansible-роли и явные источники.

**Принятое решение.**  
Универсальное зеркало файловой системы не используется. Управляемые файлы создаются явной повторяемой автоматизацией.

**Почему.**

- владелец и права задаются осознанно;
- секреты не смешиваются с обычными файлами;
- видно, какой компонент отвечает за конкретный файл;
- шаблонные значения формируются стандартным механизмом.

**Последствия и ограничения.**

- добавление нового файла требует изменить соответствующую роль;
- нельзя просто положить файл в специальный каталог и ожидать автоматического копирования.

**Когда пересматривать.**  
Если появится формальный декларативный механизм управления файлами с не меньшей прозрачностью.

## 3. Решения по безопасному применению

### 3.1. Почему сначала строится план

**Проблема.**  
Непосредственное изменение виртуализации после чтения YAML скрывает последствия до момента фактической операции.

**Рассмотренные варианты.**

- применять сразу;
- выполнять изменения вручную;
- сначала строить план, затем отдельно применять его.

**Принятое решение.**  
Изменения объекта проходят через предварительный план.

**Почему.**

- опасные действия видны заранее;
- можно проверить, что операция относится только к выбранному объекту;
- не нужен собственный параллельный формат плана.

**Последствия и ограничения.**

- план нельзя применять после изменения исходных данных;
- область изменения должна проверяться перед применением.

**Когда пересматривать.**  
Если основной механизм управления получит другой равноценный способ безопасного предварительного просмотра.

### 3.2. Почему совпадения идентификатора недостаточно для принятия объекта

**Проблема.**  
В гипервизоре может существовать посторонний объект с тем же номером, который появился в проекте.

**Рассмотренные варианты.**

- считать номер достаточным доказательством;
- автоматически импортировать любой найденный объект;
- требовать отдельную явную процедуру принятия.

**Принятое решение.**  
Существующий объект, отсутствующий в ожидаемом состоянии управления, не принимается автоматически.

**Почему.**

- номер идентифицирует объект, но не подтверждает его происхождение;
- ошибочный манифест не должен захватывать чужую систему;
- отдельный импорт позволяет сначала проверить соответствие.

**Последствия и ограничения.**

- ручные и старые объекты требуют явного принятия;
- состояние инструмента управления становится важным восстановительным данным.

**Когда пересматривать.**  
Если появится надёжная встроенная идентичность происхождения объектов.

### 3.3. Почему нет общего разрушительного отката

**Проблема.**  
После частичной ошибки автоматическое возвращение «назад» может само уничтожить полезные данные.

**Рассмотренные варианты.**

- всегда удалять созданное;
- хранить сложную пошаговую транзакцию;
- сохранить фактическое состояние и повторно сверить его при следующем запуске.

**Принятое решение.**  
Общий разрушительный откат не выполняется. Следующий запуск заново сравнивает фактическое и требуемое состояние.

**Почему.**

- обратная операция не всегда восстанавливает прежнее состояние;
- фактическое состояние надёжнее старого номера шага;
- повторяемые инструменты рассчитаны на повторное применение.

**Последствия и ограничения.**

- после ошибки может остаться частично изменённый объект;
- узкая очистка допустима только при доказанной принадлежности незавершённого объекта текущей операции.

**Когда пересматривать.**  
Если весь жизненный цикл станет действительно транзакционным и безопасно обратимым.

## 4. Решения по сети и административным возможностям

### 4.1. Почему поддерживаются и статический адрес, и DHCP

**Проблема.**  
Часть инфраструктурных гостей удобнее адресовать предсказуемо, а для других разумнее получать адрес динамически.

**Рассмотренные варианты.**

- только статические адреса;
- только DHCP;
- оба режима с единым способом дальнейшего определения административного адреса.

**Принятое решение.**  
Контракт гостя поддерживает вычисляемый статический адрес, явный статический адрес и DHCP.

**Почему.**

- статический режим остаётся простым и предсказуемым;
- DHCP не требует искусственной фиксации адреса в Git;
- одна модель гостя подходит разным классам систем.

**Последствия и ограничения.**

- при DHCP адрес нужно определить после запуска;
- автоматизация должна уметь ждать появление адреса;
- неоднозначность нескольких подходящих адресов должна считаться ошибкой.

**Когда пересматривать.**  
Если проект перейдёт на другой единый механизм адресации.

### 4.2. Почему DHCP-адрес определяется через гипервизор

**Проблема.**  
При DHCP управляющему контуру нужен фактический адрес, но зависимость от конкретного роутера или DHCP-сервера усложняет переносимость.

**Рассмотренные варианты.**

- обращаться к DHCP-серверу;
- искать по DNS;
- получать сведения об интерфейсах через платформу виртуализации.

**Принятое решение.**  
Фактический административный IPv4 определяется через сведения о работающем госте, доступные управляющему контуру через гипервизор.

**Почему.**

- не возникает зависимости от марки маршрутизатора;
- используется уже существующий доверенный канал управления;
- одинаковый принцип применим к разным способам выдачи DHCP.

**Последствия и ограничения.**

- VM должна предоставлять сведения о своих интерфейсах;
- сразу после запуска адрес может отсутствовать;
- выбор должен ограничиваться административной сетью.

**Когда пересматривать.**  
Если появится более надёжный единый сетевой источник истины.

### 4.3. Почему дополнительные административные возможности выдаются явно

**Проблема.**  
Не каждому гостю нужны собственные исходящие SSH-удостоверения или доступ к репозиторию проекта.

**Рассмотренные варианты.**

- выдавать одинаковые доступы всем;
- наследовать их из профиля;
- хранить права в каждом `guest.yaml`;
- использовать отдельный единый контракт доступа.

**Принятое решение.**  
Права задаются централизованно только в `infrastructure/security/access.yaml`. `guest.yaml` не содержит второго списка административных возможностей.

**Почему.**

- используется принцип минимальных полномочий;
- профиль не расширяет доверие всем гостям одновременно;
- разные удостоверения можно независимо выдавать и отзывать.

**Последствия и ограничения.**

- каждая возможность требует отдельного поддерживаемого жизненного цикла;
- базовый административный канал управляющей среды не должен смешиваться с этими дополнительными возможностями.

**Когда пересматривать.**  
Если единый контракт перестанет позволять независимо ограничивать и отзывать разные виды доступа.
