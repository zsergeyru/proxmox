## 1. Решения по модели состояния гостя

### 1.1. Почему `profile` является единственным признаком управляемого гостя

**Проблема.**  
Нужно было однозначно отличать гостевые системы, которыми универсальный контур может управлять, от объектов, которые пока только описаны в Git.

**Рассмотренные варианты.**

- отдельное поле `deployable`;
- отдельное поле `managed`;
- отдельное поле состояния;
- определять управляемость по диапазону VMID;
- считать наличие `profile` достаточным признаком.

**Принятое решение.**  
Наличие `profile` является единственным признаком участия гостя в универсальной модели построения и развёртывания состояния.

**Почему.**

- профиль уже необходим для определения типа и способа создания гостя;
- дополнительный логический флаг дублировал бы ту же информацию;
- невозможно получить противоречивые сочетания вроде «профиль есть, но гость не развёртываемый»;
- проверяющий модуль и средство развёртывания используют одно простое условие.

**Последствия и ограничения.**

- объект без `profile` может быть описан в Git, но полное итоговое состояние для него не строится;
- поля, имеющие смысл только для управляемого гостя, требуют `profile`;
- если в будущем появится новый вид управляемого объекта, нужно будет решить, вписывается ли он в профильную модель.

**Когда пересматривать.**  
Если появятся управляемые объекты, для которых профиль технически не нужен, либо потребуется несколько независимых режимов управления одним и тем же гостем.

### 1.2. Почему общие настройки, профиль и `guest.yaml` разделены

**Проблема.**  
Параметры гостевой системы имеют разный смысл: часть одинакова для большинства гостей, часть описывает типовую основу класса, а часть относится только к конкретному экземпляру.

**Рассмотренные варианты.**

- хранить все параметры целиком в каждом `guest.yaml`;
- хранить почти всё в профилях;
- использовать несколько уровней с разной ответственностью.

**Принятое решение.**  
Используются три уровня:

```text
общие настройки
→ профиль
→ guest.yaml
```

Общие настройки содержат инфраструктурные значения проекта, профиль — типовую техническую основу, а `guest.yaml` — параметры конкретного экземпляра и осознанные переопределения.

**Почему.**

- одинаковые параметры не копируются во множество файлов;
- изменение общего правила не требует массового редактирования гостей;
- профиль не превращается в описание конкретной VM/LXC;
- индивидуальный манифест остаётся коротким и понятным.

**Последствия и ограничения.**

- итоговое состояние нельзя получить простым чтением одного файла;
- требуется общий сборщик, который однозначно объединяет уровни;
- нужно чётко определять, на каком уровне разрешено каждое поле.

**Когда пересматривать.**  
Если количество уровней начнёт создавать больше сложности, чем устранять дублирование, либо появится другой способ типизации гостей с такой же прозрачностью.

### 1.3. Почему индивидуальный `guest.yaml` содержит параметры конкретного экземпляра

**Проблема.**  
Возникал риск переносить в профиль ресурсы и другие значения только потому, что несколько гостей временно имеют одинаковую конфигурацию.

**Рассмотренные варианты.**

- хранить CPU, память и размер диска в профиле;
- создавать отдельный профиль почти для каждой комбинации ресурсов;
- отделить способ создания от параметров конкретного экземпляра.

**Принятое решение.**  
Ресурсы и другие свойства конкретной VM/LXC задаются в `guest.yaml`, а профиль описывает только типовую основу и способ создания.

**Почему.**

- два гостя одного типа могут иметь разные ресурсы;
- изменение памяти не требует создания нового профиля;
- профиль остаётся переиспользуемым;
- из имени профиля не приходится кодировать параметры конкретной машины.

**Последствия и ограничения.**

- несколько гостей могут содержать одинаковые числовые значения ресурсов;
- намеренно не вводится отдельный слой «размеров VM» до появления реальной необходимости.

**Когда пересматривать.**  
Если появятся устойчивые классы размеров, которые используются массово и действительно требуют отдельного управляемого уровня.

### 1.4. Почему итоговое состояние строится одним общим сборщиком

**Проблема.**  
Проверяющий модуль и средство развёртывания могли бы независимо объединять общие настройки, профиль и `guest.yaml`. Со временем такие реализации неизбежно начали бы различаться.

**Рассмотренные варианты.**

- отдельная логика объединения в каждом инструменте;
- предварительно хранить полностью развёрнутое состояние в Git;
- использовать один общий сборщик.

**Принятое решение.**  
Все инструменты получают итоговое состояние через общий `scripts/guests/guest_config.py`.

**Почему.**

- одно поле не может трактоваться по-разному проверкой и развёртыванием;
- вычисляемые значения находятся в одном месте;
- проще тестировать правила наследования;
- изменение модели состояния выполняется один раз.

**Последствия и ограничения.**

- общий сборщик становится важной частью контракта;
- ошибка в нём влияет сразу на несколько инструментов;
- новые средства управления должны использовать этот же интерфейс, а не копировать его логику.

**Когда пересматривать.**  
Если модель состояния будет перенесена в отдельную библиотеку или сервис с тем же единым контрактом.

### 1.5. Почему административный IPv4 по умолчанию вычисляется из VMID

**Проблема.**  
Нужно было назначать гостям предсказуемые административные адреса без ручного ведения отдельной таблицы для каждого объекта.

**Рассмотренные варианты.**

- задавать IPv4 вручную каждому гостю;
- использовать только DHCP;
- хранить отдельный централизованный список адресов;
- вычислять адрес из уже уникального VMID.

**Принятое решение.**  
В основной административной подсети адрес по умолчанию вычисляется из VMID. Явное значение используется только как исключение.

**Почему.**

- VMID уже уникален внутри проекта;
- по номеру гостя можно заранее определить его обычный адрес;
- уменьшается количество индивидуальных параметров;
- проще находить ошибки и конфликты адресации.

**Последствия и ограничения.**

- формула зависит от выбранной структуры административной подсети;
- нестандартные адреса требуют явного переопределения;
- правило не заменяет общую сетевую архитектуру и не предназначено для всех возможных сетевых интерфейсов гостя.

**Когда пересматривать.**  
Если административная сеть изменится так, что VMID больше нельзя будет однозначно и удобно отображать в IPv4, либо основным механизмом адресации станет другой централизованный источник.

## 2. Решения по профилям VM и LXC

### 2.1. Почему тип VM/LXC определяется профилем

**Проблема.**  
Тип объекта можно было задавать отдельно в каждом `guest.yaml`, но тогда одновременно пришлось бы задавать и связанные с типом параметры создания.

**Рассмотренные варианты.**

- отдельное поле `type` в каждом госте;
- определять тип по имени профиля;
- хранить `type` внутри профиля.

**Принятое решение.**  
Технический тип `vm` или `lxc` задаётся полем `type` внутри выбранного профиля.

**Почему.**

- тип и источник создания находятся рядом;
- индивидуальный манифест не повторяет параметры профиля;
- машинная логика не зависит от разбора имени профиля;
- невозможно выбрать VM-профиль и отдельно указать противоречащий ему тип LXC.

**Последствия и ограничения.**

- смена профиля может означать смену технического типа и поэтому требует особой осторожности;
- тип существующего объекта не должен автоматически изменяться пересозданием.

**Когда пересматривать.**  
Если профиль перестанет определять способ создания гостя или появится тип объекта, который должен выбираться независимо от профиля.

### 2.2. Почему низкоуровневые параметры Proxmox скрыты за высокоуровневыми возможностями

**Проблема.**  
Для некоторых сценариев LXC нужны низкоуровневые параметры Proxmox. Если разрешить задавать их напрямую, индивидуальные манифесты быстро станут зависеть от внутренних деталей реализации.

**Рассмотренные варианты.**

- разрешить произвольные флаги Proxmox в `guest.yaml`;
- перечислить каждый низкоуровневый параметр как отдельное публичное поле;
- публиковать только высокоуровневые возможности профиля.

**Принятое решение.**  
Публичный контракт использует высокоуровневые возможности, например `container-host`, а конкретные низкоуровневые настройки остаются внутренней реализацией профиля.

**Почему.**

- манифест описывает требуемую способность, а не способ её реализации;
- внутренние параметры можно изменить без массовой правки гостей;
- уменьшается риск небезопасных сочетаний флагов;
- профиль остаётся понятным человеку, который не знает всех деталей Proxmox.

**Последствия и ограничения.**

- нельзя произвольно настроить любой флаг через `guest.yaml`;
- новая действительно необходимая возможность должна сначала получить понятный высокоуровневый контракт.

**Когда пересматривать.**  
Если проекту потребуется большое количество независимых низкоуровневых настроек, которые невозможно разумно представить как ограниченный набор высокоуровневых возможностей.

### 2.3. Почему управляемые LXC создаются непривилегированными

**Проблема.**  
Proxmox позволяет создавать привилегированные и непривилегированные LXC. Поддержка обоих вариантов увеличивает число сочетаний и меняет границу безопасности контейнера.

**Рассмотренные варианты.**

- разрешить выбор для каждого гостя;
- использовать привилегированные LXC по умолчанию;
- зафиксировать непривилегированные LXC для управляемого контура.

**Принятое решение.**  
Все LXC, создаваемые универсальным гостевым контуром, являются непривилегированными.

**Почему.**

- это безопаснее как общий режим;
- не требуется ещё одно индивидуальное поле;
- одинаковая базовая модель упрощает создание и проверку контейнеров;
- исключения не должны появляться незаметно через обычный манифест.

**Последствия и ограничения.**

- сервис, которому действительно требуется привилегированный контейнер, не сможет быть описан текущим стандартным профилем;
- для такого исключения потребуется отдельное архитектурное решение, а не просто логический переключатель.

**Когда пересматривать.**  
Если появится обоснованный класс сервисов, который невозможно поддержать в непривилегированном LXC и для которого VM также не подходит.

### 2.4. Почему `container-host` и `bootstrap: docker` разделены

**Проблема.**  
LXC может быть технически способен запускать вложенную среду контейнеров, но это не означает, что Docker обязательно должен быть установлен в каждом таком госте.

**Рассмотренные варианты.**

- профиль с поддержкой контейнеров автоматически устанавливает Docker;
- `bootstrap: docker` автоматически меняет низкоуровневые параметры LXC;
- разделить техническую возможность профиля и установку программы.

**Принятое решение.**  
`container-host` определяет техническую возможность LXC, а `bootstrap: docker` отдельно требует установить Docker в конкретный экземпляр.

**Почему.**

- профиль отвечает за возможности среды виртуализации;
- `bootstrap` отвечает за программное обеспечение внутри гостевой ОС;
- одна возможность не скрывает действие другого уровня;
- Docker можно устанавливать и в VM, где `container-host` не нужен.

**Последствия и ограничения.**

- для Docker в LXC нужно согласованное сочетание профиля и `bootstrap`;
- проверяющий модуль должен контролировать эту зависимость.

**Когда пересматривать.**  
Если способ запуска контейнеров внутри LXC изменится или появится другой механизм, которому нужны иные технические возможности.

## 3. Решения по безопасному развёртыванию

### 3.1. Почему планирование и применение разделены

**Проблема.**  
Автоматическое применение сразу после чтения манифеста не даёт человеку увидеть, какие изменения средство собирается выполнить.

**Рассмотренные варианты.**

- сразу применять все допустимые изменения;
- требовать отдельной команды для каждого изменения;
- сначала строить полный план, а применение включать явно.

**Принятое решение.**  
`deploy-guest` по умолчанию только строит план, а изменения выполняются только при явном `--apply`.

**Почему.**

- можно увидеть изменения до их выполнения;
- блокирующие условия обнаруживаются до первого изменения;
- один и тот же механизм сравнения используется для проверки и применения;
- интерфейс остаётся простым.

**Последствия и ограничения.**

- обычное изменение требует явного запуска режима применения;
- план должен быть достаточно понятным, иначе разделение теряет смысл;
- план и применение должны использовать одну зафиксированную ревизию состояния.

**Когда пересматривать.**  
Если появится другой интерфейс подтверждения изменений, который сохраняет такую же прозрачность и безопасность.

### 3.2. Почему существующий объект не принимается под управление только по VMID

**Проблема.**  
В Proxmox может уже существовать VM/LXC с VMID, который появился в Git. Автоматическое принятие такого объекта может изменить или повредить чужую систему.

**Рассмотренные варианты.**

- считать совпадение VMID достаточным;
- автоматически добавлять объекту признак управления проектом;
- требовать подтверждённую принадлежность проекту.

**Принятое решение.**  
Совпадение VMID недостаточно. Для изменения существующего объекта его принадлежность проекту должна быть подтверждена отдельным внутренним признаком.

**Почему.**

- VMID сам по себе не доказывает происхождение объекта;
- средство развёртывания не должно незаметно менять вручную созданную VM;
- ошибка в манифесте не должна автоматически превращаться в захват существующего объекта.

**Последствия и ограничения.**

- принятие старого или вручную созданного объекта под управление требует отдельной осознанной процедуры;
- конкретный служебный признак является внутренней частью реализации и не должен становиться пользовательским полем состояния.

**Когда пересматривать.**  
Если Proxmox или проект получит более надёжный встроенный механизм идентификации происхождения управляемых объектов.

### 3.3. Почему разрушительные и неоднозначные изменения блокируются

**Проблема.**  
Некоторые различия между требуемым и фактическим состоянием невозможно безопасно исправить обычной автоматической операцией.

**Рассмотренные варианты.**

- всегда пытаться автоматически привести объект к требуемому виду;
- автоматически пересоздавать объект при сложных изменениях;
- блокировать действия, для которых нет однозначного безопасного пути.

**Принятое решение.**  
Обычный `deploy-guest` блокирует разрушительные и неподдерживаемые изменения.

К таким случаям относятся, например:

- уменьшение диска;
- смена VM на LXC или наоборот;
- автоматическое пересоздание;
- неподдерживаемая миграция диска или PVE-узла;
- конфликт доверенного SSH-ключа.

**Почему.**

- формальное совпадение с манифестом не важнее сохранности данных;
- скрытое пересоздание трудно отличить от потери объекта;
- редкие сложные операции лучше выполнять отдельным осознанным процессом.

**Последствия и ограничения.**

- часть изменений нельзя выполнить одной обычной командой;
- оператор должен видеть понятную причину `BLOCKED`;
- для часто повторяющегося заблокированного сценария можно спроектировать отдельный безопасный контракт.

**Когда пересматривать.**  
Когда для конкретного класса изменений появится надёжная, проверяемая и обратимо управляемая процедура.

### 3.4. Почему после частичной ошибки не выполняется общий автоматический откат

**Проблема.**  
Развёртывание состоит из операций разных уровней. После ошибки некоторые из них могут быть необратимыми или иметь побочные эффекты, которые нельзя безопасно отменить автоматически.

**Рассмотренные варианты.**

- всегда удалять всё созданное и возвращаться к исходному состоянию;
- пытаться написать обратную операцию для каждого шага;
- сохранять фактическое состояние и продолжать новым запуском после устранения причины ошибки.

**Принятое решение.**  
После начала изменений общий разрушительный откат автоматически не выполняется.

**Почему.**

- автоматическое удаление созданного гостя может уничтожить полезные диагностические данные;
- обратная операция не всегда равнозначна возврату в исходное состояние;
- повторное чтение фактического состояния надёжнее предположений о том, какие шаги успели выполниться.

**Последствия и ограничения.**

- после ошибки может остаться частично подготовленный объект;
- такой объект должен явно отмечаться как незавершённый;
- оператору иногда потребуется устранить причину ошибки перед повторным запуском.

**Когда пересматривать.**  
Если операции будут выполняться в транзакционной среде с доказуемо безопасным откатом всех поддерживаемых изменений.

### 3.5. Почему повторный запуск является штатным способом продолжения

**Проблема.**  
После частичного выполнения нужно либо хранить сложный сценарий продолжения с конкретного шага, либо снова сравнить требуемое и фактическое состояние.

**Рассмотренные варианты.**

- сохранять точный номер последнего шага и продолжать с него;
- требовать ручного восстановления;
- каждый раз заново строить план из актуального фактического состояния.

**Принятое решение.**  
Повторный запуск заново получает фактическое состояние и строит новый план. Уже выполненные корректные действия должны давать `NO CHANGE`.

**Почему.**

- фактическое состояние важнее старой записи о ходе выполнения;
- один и тот же механизм используется после ошибки и при обычном повторном применении;
- меньше скрытого локального состояния;
- проще восстанавливаться после прерванного процесса.

**Последствия и ограничения.**

- все действия средства должны быть идемпотентными или безопасно проверяться до выполнения;
- нельзя полагаться только на сохранённый номер шага.

**Когда пересматривать.**  
Если появится операция, которую невозможно безопасно определить по фактическому состоянию и которая требует отдельного журнала транзакции.

### 3.6. Почему удаление элемента из `bootstrap` не удаляет установленную программу

**Проблема.**  
Список `bootstrap` задаёт, какие инструменты нужно обеспечить при первоначальной подготовке. Исчезновение элемента можно трактовать либо как «больше не требуется устанавливать», либо как приказ удалить программу.

**Рассмотренные варианты.**

- автоматически удалять программу;
- считать список полноценным управлением пакетами;
- использовать `bootstrap` только как требование наличия.

**Принятое решение.**  
`bootstrap` имеет смысл «обеспечить наличие». Удаление элемента из списка не означает автоматическое удаление уже установленной программы.

**Почему.**

- Docker, Git или Ansible могут уже использоваться приложениями и последующей конфигурацией;
- автоматическое удаление может разрушить рабочий сервис;
- `bootstrap` не является системой полного управления пакетами.

**Последствия и ограничения.**

- фактическая система может содержать инструмент, которого больше нет в `bootstrap`;
- удаление программ требует отдельного явного механизма.

**Когда пересматривать.**  
Если появится полноценный контракт управления пакетами гостевой ОС, который безопасно описывает как установку, так и удаление.

## 4. Решения по административному управлению гостями

### 4.1. Почему административный SSH имеет фиксированный контракт `root:22`

**Проблема.**  
Можно было разрешить каждому гостю задавать собственного административного пользователя и порт SSH, но это увеличило бы число вариантов и усложнило все инструменты управления.

**Рассмотренные варианты.**

- пользователь и порт в каждом `guest.yaml`;
- несколько заранее определённых SSH-профилей;
- один фиксированный внутренний контракт.

**Принятое решение.**  
Для управляемых Linux-гостей административный SSH использует `root:22`.

**Почему.**

- средство развёртывания и синхронизация ключей используют одинаковый адрес назначения;
- в манифестах нет повторяющихся служебных параметров;
- проще проверять и тестировать административный доступ;
- это внутренний административный контракт, а не пользовательский интерфейс сервиса.

**Последствия и ограничения.**

- гость, который принципиально не допускает такой способ управления, не подходит под текущий универсальный Linux-контур без отдельного решения;
- безопасность должна обеспечиваться ключами, ограничением источников доступа и общей архитектурой административной сети.

**Когда пересматривать.**  
Если проект перейдёт на другой единый механизм удалённого управления Linux-гостями либо появится существенный класс систем, для которых `root:22` неприемлем.

### 4.2. Почему `management` содержит только дополнительные возможности

**Проблема.**  
Можно было включить сам базовый административный SSH в список `management`, но тогда отсутствие элемента могло бы означать, что средство развёртывания не имеет доступа к гостю, хотя этот доступ необходим самому контуру.

**Рассмотренные варианты.**

- `management` полностью описывает все административные каналы;
- добавить обязательный элемент вроде `root_ssh`;
- считать административный SSH базовым контрактом, а в список включать только дополнительные возможности.

**Принятое решение.**  
Базовый SSH-доступ PVE → гость не является элементом `management`. Список содержит только дополнительные возможности конкретного гостя.

**Почему.**

- базовый доступ необходим самому механизму развёртывания;
- не требуется повторять обязательный элемент во всех манифестах;
- отсутствие `management` означает отсутствие дополнительных возможностей, а не потерю базового управления.

**Последствия и ограничения.**

- смысл `management` нельзя трактовать как полный список всех способов управления гостем;
- базовый SSH-контракт описывается отдельно.

**Когда пересматривать.**  
Если базовый административный доступ перестанет быть обязательным для всех управляемых Linux-гостей.

### 4.3. Почему `ssh_identity` и `project_repo_read` разделены

**Проблема.**  
Обе возможности используют SSH-ключи, поэтому их можно было объединить в одну общую возможность доступа. На деле они дают разные полномочия и имеют разные жизненные циклы.

**Рассмотренные варианты.**

- один общий ключ и одна возможность;
- автоматически выдавать обе возможности вместе;
- разделить их по назначению.

**Принятое решение.**  
`ssh_identity` и `project_repo_read` являются независимыми элементами `management`.

**Почему.**

- `ssh_identity` нужен гостю для управления другими разрешёнными гостями;
- `project_repo_read` даёт только чтение конкретного закрытого репозитория;
- разные ключи не смешивают разные области доверия;
- гостю можно выдать только действительно нужную возможность.

**Последствия и ограничения.**

- для гостя с обеими возможностями существует несколько отдельных SSH-данных;
- средство развёртывания должно управлять их жизненным циклом независимо.

**Когда пересматривать.**  
Если обе задачи будут переведены на другой общий механизм удостоверения с не меньшим разделением полномочий.

### 4.4. Почему `pve_management` не управляет SSH-доступом

**Проблема.**  
Возникало желание одним флагом определить, может ли AI управлять гостем вообще. Но управление объектом Proxmox и администрирование гостевой ОС — разные контуры с разными правами.

**Рассмотренные варианты.**

- один общий флаг отключает и PVE API, и SSH;
- отдельные поля для каждого возможного канала;
- ограничить `pve_management` только управлением объектом Proxmox.

**Принятое решение.**  
`pve_management` определяет только доступность объекта для AI через PVE API/MCP. Он не отключает административный SSH.

**Почему.**

- PVE API управляет жизненным циклом и виртуальным оборудованием;
- SSH управляет операционной системой внутри гостя;
- один флаг не должен неявно менять два независимых контура безопасности;
- гостю можно запретить AI менять объект Proxmox, сохранив административное обслуживание ОС.

**Последствия и ограничения.**

- `pve_management: false` не означает полную изоляцию гостя от всех механизмов управления;
- при необходимости ограничить SSH потребуется отдельное явное решение, а не переиспользование этого поля.

**Когда пересматривать.**  
Если проект введёт единую модель полномочий, которая явно и безопасно объединит PVE и SSH-доступ.

### 4.5. Почему пул `managed` фиксирован и не задаётся в `guest.yaml`

**Проблема.**  
PVE-пул используется как область ACL для AI. Можно было разрешить каждому гостю выбирать произвольный пул, но тогда пользовательский манифест начал бы управлять внутренней схемой полномочий Proxmox.

**Рассмотренные варианты.**

- поле `pool` в каждом госте;
- список допустимых пулов;
- фиксированный внутренний пул, производный от `pve_management`.

**Принятое решение.**  
Имя пула `managed` является внутренней частью PVE-контракта и не задаётся в `guest.yaml`.

`pve_management` определяет только требуемое участие объекта в этой области:

```text
true  → объект в managed
false → объект вне managed
```

**Почему.**

- пользователь описывает желаемую возможность управления, а не внутреннюю реализацию ACL;
- невозможно случайно выбрать пул с другими правами;
- схема безопасности PVE может изменяться независимо от формата гостевого манифеста.

**Последствия и ограничения.**

- текущая гостевая модель не предназначена для произвольной классификации VM по PVE-пулам;
- если пул потребуется для другой организационной цели, это нужно моделировать отдельно и не смешивать с `pve_management`.

**Когда пересматривать.**  
Если проекту действительно потребуется несколько независимых областей PVE-управления с разными политиками доступа.
