## 1. Решения по модели состояния гостя

### 1.1. Почему `profile` является единственным признаком управляемого гостя

**Проблема.**  
Нужно было однозначно отличать гостевые системы, которыми универсальный контур может управлять, от объектов, которые пока только описаны в Git.

**Рассмотренные варианты.**

- отдельное поле `deployable`;
- отдельное поле `managed`;
- отдельное поле состояния;
- определять управляемость по диапазону VMID;
- считать наличие `profile` достаточным признаком.

**Принятое решение.**  
Наличие `profile` является единственным признаком участия гостя в универсальной модели построения и развёртывания состояния.

**Почему.**

- профиль уже необходим для определения типа и способа создания гостя;
- дополнительный логический флаг дублировал бы ту же информацию;
- невозможно получить противоречивые сочетания вроде «профиль есть, но гость не развёртываемый»;
- проверяющий модуль и средство развёртывания используют одно простое условие.

**Последствия и ограничения.**

- объект без `profile` может быть описан в Git, но полное итоговое состояние для него не строится;
- поля, имеющие смысл только для управляемого гостя, требуют `profile`;
- если в будущем появится новый вид управляемого объекта, нужно будет решить, вписывается ли он в профильную модель.

**Когда пересматривать.**  
Если появятся управляемые объекты, для которых профиль технически не нужен, либо потребуется несколько независимых режимов управления одним и тем же гостем.

### 1.2. Почему общие настройки, профиль и `guest.yaml` разделены

**Проблема.**  
Параметры гостевой системы имеют разный смысл: часть одинакова для большинства гостей, часть описывает типовую основу класса, а часть относится только к конкретному экземпляру.

**Рассмотренные варианты.**

- хранить все параметры целиком в каждом `guest.yaml`;
- хранить почти всё в профилях;
- использовать несколько уровней с разной ответственностью.

**Принятое решение.**  
Используются три уровня:

```text
общие настройки
→ профиль
→ guest.yaml
```

Общие настройки содержат инфраструктурные значения проекта, профиль — типовую техническую основу, а `guest.yaml` — параметры конкретного экземпляра и осознанные переопределения.

**Почему.**

- одинаковые параметры не копируются во множество файлов;
- изменение общего правила не требует массового редактирования гостей;
- профиль не превращается в описание конкретной VM/LXC;
- индивидуальный манифест остаётся коротким и понятным.

**Последствия и ограничения.**

- итоговое состояние нельзя получить простым чтением одного файла;
- требуется общий сборщик, который однозначно объединяет уровни;
- нужно чётко определять, на каком уровне разрешено каждое поле.

**Когда пересматривать.**  
Если количество уровней начнёт создавать больше сложности, чем устранять дублирование, либо появится другой способ типизации гостей с такой же прозрачностью.

### 1.3. Почему индивидуальный `guest.yaml` содержит параметры конкретного экземпляра

**Проблема.**  
Возникал риск переносить в профиль ресурсы и другие значения только потому, что несколько гостей временно имеют одинаковую конфигурацию.

**Рассмотренные варианты.**

- хранить CPU, память и размер диска в профиле;
- создавать отдельный профиль почти для каждой комбинации ресурсов;
- отделить способ создания от параметров конкретного экземпляра.

**Принятое решение.**  
Ресурсы и другие свойства конкретной VM/LXC задаются в `guest.yaml`, а профиль описывает только типовую основу и способ создания.

**Почему.**

- два гостя одного типа могут иметь разные ресурсы;
- изменение памяти не требует создания нового профиля;
- профиль остаётся переиспользуемым;
- из имени профиля не приходится кодировать параметры конкретной машины.

**Последствия и ограничения.**

- несколько гостей могут содержать одинаковые числовые значения ресурсов;
- намеренно не вводится отдельный слой «размеров VM» до появления реальной необходимости.

**Когда пересматривать.**  
Если появятся устойчивые классы размеров, которые используются массово и действительно требуют отдельного управляемого уровня.

### 1.4. Почему итоговое состояние строится одним общим сборщиком

**Проблема.**  
Проверяющий модуль и средство развёртывания могли бы независимо объединять общие настройки, профиль и `guest.yaml`. Со временем такие реализации неизбежно начали бы различаться.

**Рассмотренные варианты.**

- отдельная логика объединения в каждом инструменте;
- предварительно хранить полностью развёрнутое состояние в Git;
- использовать один общий сборщик.

**Принятое решение.**  
Все инструменты получают итоговое состояние через общий `scripts/guests/resolver.py`.

**Почему.**

- одно поле не может трактоваться по-разному проверкой и развёртыванием;
- вычисляемые значения находятся в одном месте;
- проще тестировать правила наследования;
- изменение модели состояния выполняется один раз.

**Последствия и ограничения.**

- общий сборщик становится важной частью контракта;
- ошибка в нём влияет сразу на несколько инструментов;
- новые средства управления должны использовать этот же интерфейс, а не копировать его логику.

**Когда пересматривать.**  
Если модель состояния будет перенесена в отдельную библиотеку или сервис с тем же единым контрактом.

### 1.5. Почему административный IPv4 по умолчанию вычисляется из VMID

**Проблема.**  
Нужно было назначать гостям предсказуемые административные адреса без ручного ведения отдельной таблицы для каждого объекта.

**Рассмотренные варианты.**

- задавать IPv4 вручную каждому гостю;
- использовать только DHCP;
- хранить отдельный централизованный список адресов;
- вычислять адрес из уже уникального VMID.

**Принятое решение.**  
В основной административной подсети адрес по умолчанию вычисляется из VMID. Явное значение используется только как исключение.

**Почему.**

- VMID уже уникален внутри проекта;
- по номеру гостя можно заранее определить его обычный адрес;
- уменьшается количество индивидуальных параметров;
- проще находить ошибки и конфликты адресации.

**Последствия и ограничения.**

- формула зависит от выбранной структуры административной подсети;
- нестандартные адреса требуют явного переопределения;
- правило не заменяет общую сетевую архитектуру и не предназначено для всех возможных сетевых интерфейсов гостя.

**Когда пересматривать.**  
Если административная сеть изменится так, что VMID больше нельзя будет однозначно и удобно отображать в IPv4, либо основным механизмом адресации станет другой централизованный источник.

## 2. Решения по профилям VM и LXC

### 2.1. Почему тип VM/LXC определяется профилем

**Проблема.**  
Тип объекта можно было задавать отдельно в каждом `guest.yaml`, но тогда одновременно пришлось бы задавать и связанные с типом параметры создания.

**Рассмотренные варианты.**

- отдельное поле `type` в каждом госте;
- определять тип по имени профиля;
- хранить `type` внутри профиля.

**Принятое решение.**  
Технический тип `vm` или `lxc` задаётся полем `type` внутри выбранного профиля.

**Почему.**

- тип и источник создания находятся рядом;
- индивидуальный манифест не повторяет параметры профиля;
- машинная логика не зависит от разбора имени профиля;
- невозможно выбрать VM-профиль и отдельно указать противоречащий ему тип LXC.

**Последствия и ограничения.**

- смена профиля может означать смену технического типа и поэтому требует особой осторожности;
- тип существующего объекта не должен автоматически изменяться пересозданием.

**Когда пересматривать.**  
Если профиль перестанет определять способ создания гостя или появится тип объекта, который должен выбираться независимо от профиля.

### 2.2. Почему низкоуровневые параметры Proxmox скрыты за высокоуровневыми возможностями

**Проблема.**  
Для некоторых сценариев LXC нужны низкоуровневые параметры Proxmox. Если разрешить задавать их напрямую, индивидуальные манифесты быстро станут зависеть от внутренних деталей реализации.

**Рассмотренные варианты.**

- разрешить произвольные флаги Proxmox в `guest.yaml`;
- перечислить каждый низкоуровневый параметр как отдельное публичное поле;
- публиковать только высокоуровневые возможности профиля.

**Принятое решение.**  
Публичный контракт использует высокоуровневые возможности, например `container-host`, а конкретные низкоуровневые настройки остаются внутренней реализацией профиля.

**Почему.**

- манифест описывает требуемую способность, а не способ её реализации;
- внутренние параметры можно изменить без массовой правки гостей;
- уменьшается риск небезопасных сочетаний флагов;
- профиль остаётся понятным человеку, который не знает всех деталей Proxmox.

**Последствия и ограничения.**

- нельзя произвольно настроить любой флаг через `guest.yaml`;
- новая действительно необходимая возможность должна сначала получить понятный высокоуровневый контракт.

**Когда пересматривать.**  
Если проекту потребуется большое количество независимых низкоуровневых настроек, которые невозможно разумно представить как ограниченный набор высокоуровневых возможностей.

### 2.3. Почему управляемые LXC создаются непривилегированными

**Проблема.**  
Proxmox позволяет создавать привилегированные и непривилегированные LXC. Поддержка обоих вариантов увеличивает число сочетаний и меняет границу безопасности контейнера.

**Рассмотренные варианты.**

- разрешить выбор для каждого гостя;
- использовать привилегированные LXC по умолчанию;
- зафиксировать непривилегированные LXC для управляемого контура.

**Принятое решение.**  
Все LXC, создаваемые универсальным гостевым контуром, являются непривилегированными.

**Почему.**

- это безопаснее как общий режим;
- не требуется ещё одно индивидуальное поле;
- одинаковая базовая модель упрощает создание и проверку контейнеров;
- исключения не должны появляться незаметно через обычный манифест.

**Последствия и ограничения.**

- сервис, которому действительно требуется привилегированный контейнер, не сможет быть описан текущим стандартным профилем;
- для такого исключения потребуется отдельное архитектурное решение, а не просто логический переключатель.

**Когда пересматривать.**  
Если появится обоснованный класс сервисов, который невозможно поддержать в непривилегированном LXC и для которого VM также не подходит.

### 2.4. Почему `container-host` и установка Docker разделены

**Проблема.**  
LXC может быть технически способен запускать вложенную среду контейнеров, но это не означает, что Docker обязательно должен быть установлен в каждом таком госте.

**Рассмотренные варианты.**

- профиль с поддержкой контейнеров автоматически устанавливает Docker;
- требование Docker в `provision.yaml` автоматически меняет низкоуровневые параметры LXC;
- разделить техническую возможность профиля и установку программы.

**Принятое решение.**  
`container-host` определяет техническую возможность LXC, а `provision.yaml` отдельно описывает требование установить Docker в конкретный экземпляр.

**Почему.**

- профиль отвечает за возможности среды виртуализации;
- `provision.yaml` отвечает за требуемое программное обеспечение внутри гостевой ОС;
- одна возможность не скрывает действие другого уровня;
- Docker можно устанавливать и в VM, где `container-host` не нужен.

**Последствия и ограничения.**

- для Docker в LXC нужно согласованное сочетание профиля и `provision.yaml`;
- проверка `provision.yaml` должна контролировать эту зависимость.

**Когда пересматривать.**  
Если способ запуска контейнеров внутри LXC изменится или появится другой механизм, которому нужны иные технические возможности.

### 2.5. Почему порядок запуска описывается высокоуровневыми полями

**Проблема.**  
Proxmox хранит порядок запуска одной технической настройкой `startup` с параметрами `order`, `up` и `down`. Если разрешить записывать эту строку напрямую в каждом `guest.yaml`, манифесты начнут зависеть от синтаксиса конкретного API.

**Рассмотренные варианты.**

- не управлять порядком запуска из проекта;
- хранить сырой параметр Proxmox `startup`;
- расширить существующую группу `boot` понятными полями проекта.

**Принятое решение.**  
Порядок запуска относится к общей модели гостя и при реализации выражается полями:

~~~yaml
boot:
  onboot: true
  order: 10
  startup_delay_seconds: 30
~~~

При необходимости отдельно используется `shutdown_delay_seconds`.

Средство применения переводит их в штатные параметры Proxmox:

~~~text
order                  → startup.order
startup_delay_seconds  → startup.up
shutdown_delay_seconds → startup.down
~~~

**Почему.**

- одинаковая модель работает для VM и LXC;
- `guest.yaml` не зависит от строкового синтаксиса Proxmox;
- значения проходят общую проверку;
- можно централизованно проверять конфликты и правила порядка.

**Последствия и ограничения.**

- текущую схему `guest.yaml`, resolver и OpenTofu нужно расширить согласованно;
- до этой реализации документация о порядке 910 является целевым контрактом, а не фактическим применённым состоянием;
- задержка запуска является только временной паузой, а не проверкой готовности приложения.

**Когда пересматривать.**  
Если Proxmox изменит модель запуска либо проекту потребуется полноценный граф зависимостей вместо линейного порядка.


## 3. Решения по безопасному применению состояния

### 3.1. Почему планирование отделено от применения

**Проблема.**  
Автоматическое изменение Proxmox сразу после чтения требуемого состояния не позволяет заранее увидеть последствия.

**Рассмотренные варианты.**

- сразу применять все изменения;
- выполнять каждое изменение отдельной ручной командой;
- сначала строить полный план OpenTofu, а затем отдельно применять его.

**Принятое решение.**  
Изменения объекта VM/LXC проходят через отдельные этапы `tofu plan` и `tofu apply`.

**Почему.**

- план показывает создаваемые, изменяемые и заменяемые объекты до фактического изменения;
- опасное действие можно обнаружить до обращения к PVE;
- план и применение используют один механизм сравнения состояния;
- не требуется собственный параллельный формат плана.

**Последствия и ограничения.**

- применение не должно происходить по устаревшему плану после изменения входных данных;
- оператор или управляющее задание должны различать просмотр плана и фактическое применение;
- качество защиты зависит от того, насколько полно ресурсы OpenTofu описывают управляемую часть объекта.

**Когда пересматривать.**  
Если основной механизм управления объектами Proxmox будет заменён средством с другой, но не менее прозрачной моделью предварительного просмотра изменений.

### 3.2. Почему существующий объект не принимается под управление только по VMID

**Проблема.**  
В Proxmox может существовать вручную созданная VM/LXC с тем же VMID, который появился в Git. Автоматическое принятие такого объекта способно повредить чужую систему.

**Рассмотренные варианты.**

- считать совпадение VMID достаточным;
- автоматически создавать запись состояния OpenTofu для любого найденного объекта;
- принимать существующий объект только отдельной явной процедурой.

**Принятое решение.**  
Совпадение VMID недостаточно. Существующий объект, отсутствующий в состоянии OpenTofu, принимается под управление только через отдельный осознанный импорт.

**Почему.**

- VMID идентифицирует объект, но не доказывает его происхождение;
- состояние OpenTofu фиксирует, какие объекты уже находятся под управлением данного контура;
- ошибка в новом `guest.yaml` не должна автоматически превращаться в захват существующей VM/LXC;
- импорт позволяет сначала сравнить фактический объект с требованиями.

**Последствия и ограничения.**

- старые или созданные вручную объекты требуют отдельной процедуры принятия под управление;
- состояние OpenTofu становится важной частью управляющей инфраструктуры и должно резервироваться;
- потеря состояния не должна решаться массовым автоматическим импортом всех совпавших VMID.

**Когда пересматривать.**  
Если появится более надёжный встроенный механизм подтверждения происхождения объектов, который можно безопасно использовать вместо состояния OpenTofu.

### 3.3. Почему разрушительные и неоднозначные изменения не выполняются как обычное обслуживание

**Проблема.**  
Некоторые различия между требуемым и фактическим состоянием нельзя безопасно исправить обычным автоматическим применением.

**Рассмотренные варианты.**

- всегда приводить объект к описанию любой ценой;
- автоматически пересоздавать объект при сложных изменениях;
- отделить разрушительные действия от обычного обслуживания.

**Принятое решение.**  
Изменения с риском потери данных, пересоздания или неоднозначного результата требуют отдельной явной процедуры.

К таким изменениям относятся, например:

- уменьшение диска;
- смена VM на LXC или наоборот;
- пересоздание объекта;
- перенос диска между хранилищами без отдельного безопасного порядка;
- удаление гостя;
- принятие неизвестного существующего объекта под управление.

**Почему.**

- совпадение с требуемым состоянием не важнее сохранности данных;
- скрытое пересоздание практически неотличимо от потери объекта;
- редкие опасные действия можно проверять строже, чем обычное обслуживание.

**Последствия и ограничения.**

- часть изменений не выполняется одним обычным запуском;
- наличие такого изменения должно быть видно в плане OpenTofu;
- для регулярно требующегося сценария нужен отдельный проверяемый порядок действий.

**Когда пересматривать.**  
Когда для конкретного класса изменений будет создана надёжная процедура с понятными предварительными проверками и восстановлением.

### 3.4. Почему после частичной ошибки нет общего разрушительного отката

**Проблема.**  
Жизненный цикл состоит из операций разных уровней: Proxmox, запуск гостя, сеть, SSH и настройка ОС. Не каждую уже выполненную операцию можно безопасно обратить.

**Рассмотренные варианты.**

- при любой ошибке удалять всё созданное;
- иметь обратную операцию для каждого шага;
- сохранить фактическое состояние и при следующем запуске снова сравнить его с требованиями.

**Принятое решение.**  
Общий автоматический разрушительный откат после частичной ошибки не выполняется.

**Почему.**

- удаление уже созданного гостя может уничтожить данные и полезное состояние для диагностики;
- обратная операция не всегда возвращает систему в действительно прежнее состояние;
- OpenTofu и Ansible предназначены для повторного сравнения требуемого и фактического состояния.

**Последствия и ограничения.**

- после ошибки может остаться частично изменённый объект;
- причина ошибки должна быть видна оператору;
- следующий запуск должен начинаться с нового чтения фактического состояния.

**Когда пересматривать.**  
Если все поддерживаемые операции будут выполняться в среде с доказуемо безопасным транзакционным откатом.

### 3.5. Почему повторный запуск является штатным способом продолжения

**Проблема.**  
После прерванной операции можно либо хранить сложное состояние пошагового продолжения, либо снова определить, что реально требуется изменить.

**Рассмотренные варианты.**

- сохранять номер последнего выполненного шага;
- требовать ручного продолжения;
- заново строить план из текущего фактического состояния.

**Принятое решение.**  
Повторный запуск заново проверяет проект, строит итоговое состояние, план OpenTofu и повторяемую настройку Ansible.

**Почему.**

- фактическое состояние надёжнее старой записи о ходе операции;
- OpenTofu и Ansible рассчитаны на повторное применение;
- уменьшается объём собственного служебного состояния проекта;
- один механизм используется и при обычном обслуживании, и после сбоя.

**Последствия и ограничения.**

- все собственные действия вокруг OpenTofu и Ansible также должны быть безопасны при повторении;
- нельзя считать старый номер шага достаточным доказательством состояния системы.

**Когда пересматривать.**  
Если появится операция, состояние которой невозможно надёжно восстановить из фактической системы и которая требует отдельного журнала транзакции.

### 3.6. Почему состояние ОС вынесено в `provision.yaml`

**Проблема.**  
Пакеты, службы и приложения можно было описывать прямо в `guest.yaml`, но тогда один файл одновременно управлял бы объектом Proxmox и содержимым гостевой ОС.

**Рассмотренные варианты.**

- хранить всё в `guest.yaml`;
- зашить список пакетов и служб непосредственно в Ansible roles;
- хранить требования конкретного гостя отдельно в `provision.yaml`, а общую логику — в Ansible.

**Принятое решение.**  
`guest.yaml` описывает объект VM/LXC, а `provision.yaml` — требуемое состояние операционной системы и приложений конкретного гостя.

**Почему.**

- OpenTofu и Ansible получают чёткие разные области ответственности;
- требования конкретного гостя не смешиваются с общей логикой Ansible;
- один и тот же playbook может применять разные `provision.yaml`;
- пакеты и службы не засоряют инфраструктурный манифест VM/LXC.

**Последствия и ограничения.**

- для обычного Linux-гостя существуют два разных файла требований;
- между профилем виртуализации и `provision.yaml` могут возникать зависимости, которые необходимо проверять;
- формат `provision.yaml` должен иметь собственный однозначный контракт.

**Когда пересматривать.**  
Если Ansible-модель станет достаточно декларативной, чтобы хранить индивидуальные требования без отдельного файла и без дублирования между roles.

## 4. Решения по административному управлению и адресации

### 4.1. Почему административный SSH имеет фиксированный контракт `root:22`

**Проблема.**  
Разные административные пользователи и порты для каждого гостя увеличили бы число вариантов подключения и усложнили повторяемую настройку.

**Рассмотренные варианты.**

- пользователь и порт в каждом `guest.yaml`;
- несколько SSH-профилей;
- один внутренний контракт для обычных управляемых Linux-гостей.

**Принятое решение.**  
Для обычных управляемых Linux-гостей административное подключение использует `root:22`.

**Почему.**

- `910 infra-manager` и Ansible используют единый способ подключения;
- служебные параметры не повторяются в каждом манифесте;
- проще проверять готовность и диагностировать ошибки доступа;
- это внутренний административный канал, а не интерфейс прикладного сервиса.

**Последствия и ограничения.**

- гость, который принципиально не допускает такой модели, требует отдельного решения;
- безопасность должна обеспечиваться ключами, сетевыми ограничениями и политикой административного доступа.

**Когда пересматривать.**  
Если проект перейдёт на другой единый способ удалённого управления Linux-гостями или появится значимый класс систем, для которых `root:22` неприемлем.

### 4.2. Почему `management` содержит только дополнительные возможности

**Проблема.**  
Если включить базовый административный SSH в `management`, отсутствие элемента будет выглядеть как возможность полностью отключить канал, который нужен самому стандартному жизненному циклу.

**Рассмотренные варианты.**

- описывать в `management` все каналы доступа;
- добавить обязательный элемент вроде `root_ssh`;
- считать базовый SSH частью общего контракта, а `management` использовать только для дополнительных возможностей.

**Принятое решение.**  
Базовый доступ `910 infra-manager → гость` не является элементом `management`. Список содержит только дополнительные возможности конкретного гостя.

**Почему.**

- базовый канал нужен для стандартной повторяемой настройки Linux-гостя;
- не требуется копировать обязательный элемент во все манифесты;
- отсутствие `management` означает отсутствие дополнительных возможностей, а не потерю базового управления.

**Последствия и ограничения.**

- `management` нельзя трактовать как полный список всех каналов администрирования;
- базовый SSH-контракт должен оставаться явно описанным в жизненном цикле.

**Когда пересматривать.**  
Если административный SSH перестанет быть общей предпосылкой стандартного Linux-контура.

### 4.3. Почему `ssh_identity` и `project_repo_read` разделены

**Проблема.**  
Обе возможности используют SSH-ключи, но дают разные полномочия и имеют разные области доверия.

**Рассмотренные варианты.**

- один общий ключ;
- автоматически выдавать обе возможности вместе;
- разделить ключи и возможности по назначению.

**Принятое решение.**  
`ssh_identity` и `project_repo_read` являются независимыми элементами `management`.

**Почему.**

- `ssh_identity` предназначен для исходящего административного доступа гостя к разрешённым системам;
- `project_repo_read` даёт только чтение закрытого репозитория проекта;
- разделение ключей ограничивает последствия компрометации;
- гостю можно предоставить только действительно необходимое право.

**Последствия и ограничения.**

- гость с обеими возможностями имеет несколько отдельных SSH-идентичностей;
- их выдача, замена и отзыв должны управляться независимо.

**Когда пересматривать.**  
Если обе задачи будут переведены на другой общий механизм удостоверения, который сохраняет не меньшее разделение полномочий.

### 4.4. Почему `pve_management` не управляет SSH и не задаёт права API-токена

**Проблема.**  
Одно логическое поле легко ошибочно превратить в общий переключатель всех способов управления гостем.

**Рассмотренные варианты.**

- одним полем включать и PVE API, и SSH;
- хранить фактические права PVE непосредственно в `guest.yaml`;
- использовать `pve_management` только как требуемую принадлежность объекта к управляемой области Proxmox.

**Принятое решение.**  
`pve_management` относится только к классификации объекта на уровне Proxmox. Оно не отключает административный SSH и не определяет фактический набор прав API-токена `910 infra-manager`.

**Почему.**

- PVE API управляет объектом виртуализации, а SSH — операционной системой внутри него;
- права API являются политикой безопасности и должны задаваться отдельно от описания конкретного гостя;
- один флаг не должен неявно расширять или сокращать полномочия управляющей учётной записи.

**Последствия и ограничения.**

- `pve_management: false` не означает полную изоляцию гостя от всех механизмов управления;
- изменение ACL `910` не должно требовать массового изменения `guest.yaml`;
- смысл поля должен оставаться одинаковым независимо от конкретной схемы прав PVE.

**Когда пересматривать.**  
Если появится единая модель полномочий, которая явно объединит управление объектом Proxmox и операционной системой гостя.

### 4.5. Почему пул `managed` не задаётся в `guest.yaml`

**Проблема.**  
Пул нужен внутренней архитектуре проекта, но разрешение произвольного имени пула в каждом манифесте связало бы описание гостя с конкретной внутренней схемой Proxmox.

**Рассмотренные варианты.**

- поле `pool` в `guest.yaml`;
- список разрешённых пулов;
- фиксированная внутренняя область, производная от `pve_management`.

**Принятое решение.**  
Имя пула `managed` является внутренней частью PVE-контракта и не задаётся гостем.

`pve_management` может определять требуемое участие объекта в этой области:

~~~text
true  → объект относится к managed
false → объект не относится к managed
~~~

**Почему.**

- манифест описывает требуемое свойство объекта, а не внутреннее имя служебного пула;
- нельзя случайно указать произвольный пул с другим назначением;
- внутреннюю организацию PVE можно менять отдельно от формата `guest.yaml`.

**Последствия и ограничения.**

- пул `managed` не следует считать единственной границей прав API-токена `910`;
- фактические ACL определяются отдельной политикой безопасности;
- если проекту понадобятся пользовательские организационные пулы, их нельзя автоматически смешивать с этим полем.

**Когда пересматривать.**  
Если `managed` перестанет использоваться как внутренняя классификация или появится несколько независимых управляемых областей с разным смыслом.

### 4.6. Почему DHCP-адрес определяется через PVE, а не через DHCP-сервер

**Проблема.**  
При `network.ipv4: dhcp` адрес заранее неизвестен, но `910 infra-manager` должен найти гостя для SSH и Ansible.

**Рассмотренные варианты.**

- обращаться к API конкретного роутера или DHCP-сервера;
- требовать обязательную постоянную аренду для каждого гостя;
- искать адрес по DNS;
- получать фактические интерфейсы гостя через PVE.

**Принятое решение.**  
Для DHCP-гостя фактический IPv4 определяется через PVE API: для VM — через QEMU Guest Agent, для LXC — через сведения интерфейсов контейнера.

**Почему.**

- `910` уже имеет доверенный PVE API и знает VMID, тип и узел гостя;
- механизм не зависит от марки роутера или реализации DHCP;
- один подход работает и при замене DHCP-сервера;
- можно выбрать адрес именно из административной подсети и не принять адрес Docker или другой служебной сети.

**Последствия и ограничения.**

- для VM с DHCP требуется работающий QEMU Guest Agent;
- сразу после запуска адрес может ещё отсутствовать, поэтому жизненный цикл должен ограниченное время повторять проверку;
- несколько подходящих IPv4 считаются неоднозначностью, а не поводом выбирать первый.

**Когда пересматривать.**  
Если PVE перестанет предоставлять достаточные сведения об интерфейсах либо проект введёт единый сетевой источник истины, который надёжнее и не создаёт зависимости от конкретного DHCP-сервера.
