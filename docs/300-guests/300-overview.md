## 1. Что считается гостевой системой

Гостевая система — это VM или LXC-контейнер в Proxmox VE.

Для проекта важно разделять несколько уровней:

```text
объект Proxmox
↓
операционная система
↓
службы и приложения
↓
изменяемые данные
```

OpenTofu отвечает за поддерживаемую часть объекта Proxmox: тип, ресурсы, диск, сеть, запуск и другие параметры виртуализации.

Ansible отвечает за повторяемую настройку поддерживаемых Linux-гостей после появления административного доступа.

Постоянные данные приложений не становятся автоматически частью ни OpenTofu, ни Git. Для них действует отдельная политика хранения и резервного копирования.

## 2. Как описывается гость

Требуемое состояние разделено на несколько машинных описаний.

`defaults.yaml` хранит общие значения проекта и технические профили.

`guest.yaml` описывает конкретный объект VM/LXC и его индивидуальные отличия.

`provision.yaml` описывает требуемое состояние поддерживаемой Linux-системы внутри гостя: базовую ОС, пакеты, службы, компоненты и другие параметры, которые должен применить Ansible.

`status.yaml` является необязательным описанием проверок готовности и итогового вывода состояния, если для конкретного гостя такой механизм предусмотрен.

Точные поля всех этих YAML находятся в одном справочнике:

[`320-guest-manifest.md`](320-guest-manifest.md).

Для объекта Proxmox итоговое состояние строится по схеме:

```text
defaults.yaml
+
профиль
+
guest.yaml
↓
единое итоговое состояние
```

Профиль определяет техническую основу гостя, но сам по себе не определяет, кто владеет полным жизненным циклом этого объекта.

## 3. Как применяется состояние

Обычный путь Linux-гостя:

```text
описание в Git
↓
проверка проекта
↓
построение итогового состояния
↓
план OpenTofu
↓
создание или изменение VM/LXC
↓
определение административного адреса
↓
Ansible
↓
проверка готовности
```

Для административной сети поддерживаются:

- вычисляемый статический IPv4;
- явно заданный статический IPv4;
- DHCP.

DHCP является частью принятого контракта гостя. После запуска фактический адрес должен определяться через PVE, а не через API конкретного DHCP-сервера.

Дополнительные возможности `management` также являются частью контракта гостя и выдаются только при явном запросе конкретного гостя.

Повторное применение считается штатной операцией. Если фактическое состояние уже соответствует требуемому, лишних изменений быть не должно.

## 4. Особые жизненные циклы

Наличие обычного профиля не означает, что объект обязательно создаётся постоянным OpenTofu-состоянием стандартного гостевого контура.

Например, `910 infra-manager` использует общий профиль, общий механизм построения состояния, `provision.yaml` и общий Ansible.

Его отличие находится не в формате гостя, а во владении объектом Proxmox:

- первоначальное создание выполняет отдельный временный контур;
- объект 910 принадлежит отдельному первоначальному состоянию OpenTofu;
- постоянный 910 не включает собственный объект в своё постоянное состояние;
- последующая настройка ОС выполняется тем же общим Ansible-контрактом.

Такие исключения должны быть явно описаны в жизненном цикле и паспорте конкретного гостя.

## 5. Границы раздела

Раздел `300-guests` определяет:

- модель состояния VM/LXC;
- формат машинных описаний гостей;
- общий жизненный цикл VM/LXC;
- правила нумерации;
- общие правила размещения файлов и данных внутри Linux-гостей;
- причины ключевых решений гостевого контура.

Он не заменяет:

- устройство PVE-хоста — раздел `200-pve`;
- общую сетевую архитектуру — раздел `400-network`;
- хранение и резервное копирование — раздел `600-storage`;
- политику ключей и административного доступа — раздел `700-security`;
- пошаговые действия оператора — раздел `800-operations`;
- локальную документацию конкретного гостя в `infrastructure/guests/`.
