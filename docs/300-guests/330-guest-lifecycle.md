# Жизненный цикл гостевой системы

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** определить единый порядок создания, изменения, подготовки, обслуживания и удаления обычных управляемых VM/LXC.

Этот документ отвечает на вопрос:

> Как уже построенное требуемое состояние гостя применяется к Proxmox и как после этого гостевая система передаётся дальнейшему управлению?

Документ не определяет поля `guest.yaml` и не повторяет правила построения требуемого состояния. Эти темы относятся к `310-guest-state.md` и `320-guest-manifest.md`.

## 1. Общая схема

Обычная управляемая гостевая система проходит следующий путь:

~~~text
описание в Git
↓
проверка репозитория
↓
построение итогового состояния
↓
подготовка входных данных OpenTofu
↓
план изменений
↓
применение изменений через PVE API
↓
VM/LXC в Proxmox
↓
запуск гостя при необходимости
↓
определение административного IPv4
↓
проверка SSH
↓
Ansible
↓
настроенная гостевая ОС и приложения
~~~

Все средства управления выполняются из `910 infra-manager`.

На физический PVE-хост не устанавливаются OpenTofu, Ansible, Packer, Semaphore или другие средства управления проектом.

## 2. Участники жизненного цикла

### 2.1. `910 infra-manager`

`910 infra-manager` является постоянной управляющей средой проекта.

Он:

- получает доверенную версию проекта из Git;
- запускает проверки;
- предоставляет среду выполнения средств автоматизации;
- обращается к PVE через выделенный API-токен;
- запускает задания Semaphore;
- хранит рабочее состояние средств управления, которое должно резервироваться.

`910` не управляет собственным созданием через обычный гостевой контур.

### 2.2. Semaphore

Semaphore является основным местом запуска и упорядочивания операций управления.

Он не определяет требуемое состояние сам по себе.

Задания Semaphore вызывают средства проекта с данными из репозитория и не должны создавать собственную параллельную конфигурацию VM/LXC.

### 2.3. OpenTofu

OpenTofu отвечает за объект VM/LXC на уровне Proxmox.

К его области относятся:

- наличие объекта;
- тип VM или LXC;
- PVE-узел;
- процессор и память;
- основной диск;
- сетевой интерфейс;
- постоянный режим автоматического запуска;
- защита объекта;
- другие параметры Proxmox, которые явно включены в контракт проекта.

OpenTofu получает уже построенное итоговое состояние и не читает `guest.yaml` напрямую.

### 2.4. Packer

Packer отвечает за подготовку базовых шаблонов VM.

Он не создаёт обычные пользовательские VM при каждом запуске жизненного цикла.

Для VM профиль указывает, из какого подготовленного шаблона должна создаваться новая машина.

### 2.5. Ansible

Ansible отвечает за повторяемое состояние внутри гостевой операционной системы.

К его области относятся:

- пакеты;
- службы;
- управляемые файлы;
- настройки операционной системы;
- прикладная конфигурация;
- подготовка, описанная индивидуальными требованиями гостя.

Ansible не должен использоваться для параллельного изменения тех параметров VM/LXC, которыми управляет OpenTofu.

## 3. Подготовка изменения

### 3.1. Проверка проекта

До обращения к Proxmox выполняется общая проверка репозитория:

~~~bash
python scripts/validate_repo.py
~~~

Ошибка проверки блокирует дальнейшее применение состояния.

Предупреждение не блокирует операцию автоматически, но должно оставаться видимым оператору.

### 3.2. Построение итогового состояния

Для гостя с `profile` итоговое состояние строится единым механизмом, определённым в `310-guest-state.md`.

Следующий слой получает уже готовый набор значений.

Он не должен заново:

- объединять `defaults`, профиль и `guest.yaml`;
- вычислять адрес по VMID;
- самостоятельно нормализовать `management` или `features`.

### 3.3. Вход OpenTofu

Итоговые состояния управляемых гостей преобразуются в единый вход OpenTofu.

Общий поток:

~~~text
guest.yaml
+
defaults.yaml
↓
единый сборщик состояния
↓
итоговое состояние
↓
вход OpenTofu
↓
OpenTofu
~~~

Гости без `profile` в обычный вход OpenTofu не включаются.

### 3.4. Одна ревизия проекта на одну операцию

Планирование и применение должны относиться к одной и той же версии проекта.

Если содержимое проекта изменилось после построения плана, прежний план не должен применяться к новой ревизии.

Для нового состояния строится новый план.

## 4. Планирование и применение состояния Proxmox

### 4.1. Планирование

До изменения Proxmox выполняется планирование OpenTofu.

Основная команда:

~~~bash
tofu plan
~~~

План должен позволять увидеть:

- какие объекты будут созданы;
- какие параметры будут изменены;
- какие объекты или параметры затрагиваться не будут;
- требует ли изменение замены существующего объекта.

Планирование не должно изменять Proxmox.

### 4.2. Применение

После проверки плана состояние применяется OpenTofu:

~~~bash
tofu apply
~~~

OpenTofu обращается к PVE через HTTPS API от имени выделенного API-токена `infra-manager`.

Прямой SSH-доступ к PVE для изменения объектов VM/LXC не является частью этого механизма.

### 4.3. Создание VM

Новая VM создаётся из шаблона, определённого выбранным профилем.

После создания к ней применяются индивидуальные параметры итогового состояния.

Шаблон определяет базовые технические свойства VM, а `guest.yaml` — свойства конкретного экземпляра.

### 4.4. Создание LXC

Новый LXC создаётся из системного образа, определённого профилем.

Контейнер получает ресурсы, сеть и другие поддерживаемые параметры из итогового состояния.

Технические возможности LXC, например `container-host`, определяются профилем.

### 4.5. Изменение существующего объекта

При повторном применении OpenTofu сравнивает своё состояние с фактическим состоянием Proxmox.

Если поддерживаемый параметр отличается, формируется изменение.

Если объект уже соответствует требованиям, лишнее изменение не выполняется.

OpenTofu не должен использовать отсутствие поля в `guest.yaml` как основание для сброса параметров, которые вообще не входят в контракт проекта.

### 4.6. `pve_management`

`pve_management` определяет участие объекта в управляемой области проекта на уровне Proxmox.

Членство в соответствующем PVE-пуле может быть частью применяемого состояния.

При этом само поле `pve_management` не определяет фактический набор прав API-токена `910 infra-manager`. Права задаются отдельной политикой PVE и безопасности.

## 5. Запуск и определение административного адреса

### 5.1. Когда нужен запуск

Создание или изменение объекта Proxmox и настройка операционной системы являются разными этапами.

Если для следующего этапа требуется подключение к гостю, VM/LXC должен быть запущен и перейти в состояние, в котором доступно административное подключение.

Постоянное значение `boot.onboot` не определяет, должен ли гость быть временно запущен для выполнения обслуживания.

### 5.2. Статический адрес

Если итоговое состояние содержит статический IPv4, `910 infra-manager` заранее знает адрес административного подключения.

Статический адрес может быть:

- автоматически вычислен из VMID;
- явно указан в `guest.yaml`.

В обоих случаях фактическое подключение должно использовать адрес из итогового состояния.

### 5.3. DHCP

Если итоговое состояние содержит:

~~~yaml
network:
  ipv4: dhcp
~~~

конкретный IPv4 заранее неизвестен и не считается частью требуемого состояния.

После запуска `910 infra-manager` получает сведения об интерфейсах гостя через PVE API.

Для VM используется QEMU Guest Agent:

~~~text
/nodes/{node}/qemu/{vmid}/agent/network-get-interfaces
~~~

Для LXC используются сведения интерфейсов контейнера:

~~~text
/nodes/{node}/lxc/{vmid}/interfaces
~~~

Из полученных адресов выбирается IPv4, принадлежащий административной подсети проекта.

### 5.4. Правило выбора DHCP-адреса

Алгоритм не должен выбирать первый попавшийся адрес.

Используются следующие правила:

1. рассматриваются только IPv4;
2. адрес должен принадлежать административной подсети проекта;
3. адреса других сетей, например внутренних сетей Docker, не подходят;
4. если подходящий адрес отсутствует, гость ещё не готов к подключению;
5. если найден ровно один подходящий адрес, он используется;
6. если найдено несколько подходящих адресов, результат считается неоднозначным.

При неоднозначности автоматическое управление не должно угадывать нужный интерфейс.

### 5.5. Ожидание DHCP-адреса

Получение адреса через PVE выполняется повторно в течение ограниченного времени.

Временная недоступность QEMU Guest Agent или отсутствие адреса сразу после запуска не считается причиной выбирать другой источник данных.

Если адрес не появился за установленный срок, операция завершается ошибкой готовности гостя.

Для VM с DHCP работающий QEMU Guest Agent является обязательной предпосылкой дальнейшего автоматического управления.

### 5.6. Граница с DHCP-сервером

`910 infra-manager` не должен обращаться к API роутера или DHCP-сервера ради определения адреса обычного гостя.

Это сохраняет управление гостями независимым от конкретной реализации DHCP.

## 6. Настройка гостевой операционной системы

### 6.1. Административное подключение

После определения адреса проверяется административный SSH.

Базовый проектный контракт для обычного Linux-гостя:

~~~text
root:22
~~~

Факт открытия TCP-порта сам по себе не считается достаточной проверкой.

Необходимо успешное SSH-подключение с ожидаемой управляющей идентичностью.

### 6.2. Требуемое состояние операционной системы

Пакеты, службы и прикладные компоненты конкретного гостя описываются в его `provision.yaml`.

`provision.yaml` задаёт, **что** должно присутствовать внутри гостевой операционной системы. Он не содержит пошаговый сценарий установки.

Применение этого состояния выполняет централизованный Ansible из `automation/ansible/`.

OpenTofu не устанавливает пакеты и приложения внутри гостя.

### 6.3. `management`

Дополнительные возможности `management` применяются только к тем гостям, у которых они явно запрошены.

Например:

- `ssh_identity` — собственная исходящая SSH-идентичность гостя;
- `project_repo_read` — управляемый доступ на чтение репозитория проекта.

Эти возможности не должны появляться у гостя только из-за принадлежности к общему профилю.

### 6.4. Постоянная настройка

После первоначальной готовности тот же Ansible используется для повторяемого обслуживания операционной системы и приложений.

Изменение внутри гостя не должно требовать пересоздания VM/LXC, если сам объект Proxmox не изменяется.

## 7. Повторное обслуживание

### 7.1. Повторный запуск

Повторное применение является штатной операцией.

Каждый запуск заново:

1. проверяет проект;
2. строит итоговое требуемое состояние;
3. строит план OpenTofu;
4. применяет разрешённые изменения;
5. при необходимости определяет административный адрес;
6. применяет повторяемую настройку Ansible;
7. проверяет итоговый результат.

### 7.2. Отсутствие изменений

Если объект Proxmox и гостевая ОС уже соответствуют требованиям, повторный запуск не должен создавать искусственных изменений.

Это относится как к OpenTofu, так и к Ansible.

### 7.3. Разделение состояния

OpenTofu хранит собственное состояние управления объектами Proxmox.

Это состояние является служебной частью инфраструктуры и должно резервироваться.

Git остаётся источником требований, но не заменяет состояние OpenTofu.

Фактические данные приложений внутри гостей также не становятся частью состояния OpenTofu.

## 8. Опасные изменения, принятие под управление и удаление

### 8.1. Опасные изменения

Не каждое технически возможное изменение должно выполняться автоматически.

Особого контроля требуют действия, которые могут привести к:

- пересозданию VM/LXC;
- потере данных;
- уменьшению диска;
- смене типа VM ↔ LXC;
- переносу диска между хранилищами;
- неожиданной остановке работающего сервиса.

Если план содержит такое действие, оно должно быть явно видно до применения.

### 8.2. Существующий объект вне состояния OpenTofu

Совпадение VMID само по себе не означает, что объект можно автоматически принять под управление.

Если VM/LXC существует в Proxmox, но отсутствует в состоянии OpenTofu, обычное применение не должно молча считать её своей.

Принятие существующего объекта выполняется отдельной явной процедурой импорта с предварительной проверкой соответствия.

### 8.3. Удаление

Удаление гостевой системы является отдельной явной операцией жизненного цикла.

Простое исчезновение `guest.yaml` из Git не должно само по себе незаметно уничтожать VM/LXC с данными.

Перед удалением должны быть отдельно определены:

- какой объект удаляется;
- какие данные должны быть сохранены;
- существуют ли резервные копии;
- должны ли удаляться связанные ключи и права;
- должно ли удаляться состояние приложений;
- требуется ли сохранить диск или другой ресурс.

### 8.4. Ошибка во время применения

При ошибке уже выполненные изменения не должны скрываться.

Общий автоматический разрушительный откат не выполняется, если он сам способен привести к потере данных.

Следующий запуск должен заново получить фактическое состояние и построить новый план.

## 9. Особый жизненный цикл 910

`910 infra-manager` не является обычным гостем этого контура.

Причина проста: внутри него выполняются средства, которые управляют остальными гостями.

Его жизненный цикл начинается с отдельного публичного начального сценария:

~~~text
публичный начальный сценарий
↓
PVE
↓
создание 910 infra-manager
↓
получение основного закрытого репозитория
↓
подготовка управляющей среды
↓
управление остальной инфраструктурой
~~~

В `guest.yaml` объекта `910` отсутствует `profile`, поэтому он не попадает в обычный вход OpenTofu для управляемых гостей.

Обновление, восстановление и удаление `910` должны выполняться через его собственный установленный жизненный цикл, а не через механизм обычной VM/LXC.
