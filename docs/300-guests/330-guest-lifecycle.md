## 1. Общая схема

Для поддерживаемого Linux-гостя общий контракт выглядит так:

```text
YAML проекта
↓
проверка
↓
итоговое состояние VM/LXC
↓
план OpenTofu
↓
создание или изменение объекта
↓
определение административного адреса
↓
Ansible
↓
применение правил access.yaml
↓
проверка готовности
```

Создание объекта Proxmox и настройка содержимого ОС являются разными этапами.

## 2. Участники

### 2.1. Управляющая среда

Постоянная управляющая среда:

- читает проект;
- запускает общую проверку;
- строит итоговое состояние;
- управляет OpenTofu;
- определяет адрес гостя;
- выполняет Ansible;
- получает необходимые временные административные удостоверения;
- применяет дополнительные возможности, явно запрошенные гостем.

### 2.2. OpenTofu

OpenTofu управляет поддерживаемой частью объекта Proxmox:

- VM/LXC;
- ресурсами;
- основным диском;
- сетью;
- запуском;
- параметрами, выраженными общим профилем.

OpenTofu не устанавливает пакеты и приложения внутри гостевой ОС.

### 2.3. Ansible

Ansible приводит поддерживаемую Linux-систему к состоянию `provision.yaml`.

Он выполняет общую базовую настройку и подключает только те роли, которые нужны конкретному гостю.

### 2.4. Packer

Packer отвечает за подготовку базовых VM-шаблонов и не является механизмом настройки конкретного работающего гостя.

## 3. Подготовка

Перед изменением гостя обязательно:

1. проверить репозиторий;
2. найти ровно один каталог выбранного VMID;
3. построить итоговое состояние общей моделью;
4. проверить необходимые машинные описания;
5. определить область изменения только выбранного гостя.

Одна операция должна использовать одну согласованную ревизию проекта.

Нельзя строить план по одной версии описаний, а применять настройку ОС уже по другой.

## 4. Состояние Proxmox

### 4.1. Планирование

До изменения объекта строится план OpenTofu.

План должен относиться только к выбранному гостю.

Неожиданное изменение другого ресурса является ошибкой.

### 4.2. Существующий объект

Совпадение VMID недостаточно для автоматического принятия объекта под управление.

Если объект существует в PVE, но отсутствует в ожидаемом OpenTofu-state, обычное применение не должно автоматически импортировать его.

Импорт является отдельной осознанной процедурой.

### 4.3. Создание VM

VM создаётся из шаблона выбранного профиля.

Защита шаблона может временно изменяться только на время необходимой операции и должна быть восстановлена независимо от результата.

### 4.4. Создание LXC

LXC создаётся из системного образа выбранного профиля.

Низкоуровневые свойства, которые являются реализацией высокоуровневой возможности профиля и требуют полномочий PVE-хоста, могут применяться отдельным узким хостовым шагом.

### 4.5. `pve_management`

`pve_management` относится к требуемой классификации объекта на уровне PVE.

Оно не заменяет:

- `profile`;
- OpenTofu-state;
- SSH-контракт;
- политику API-доступа;
- специальное правило владения жизненным циклом.

## 5. Административный адрес

После создания или изменения объект должен иметь адрес, по которому можно выполнить дальнейшую настройку.

### 5.1. Статический режим

Если итоговое состояние содержит статический IPv4, адрес известен заранее.

Он используется для:

- проверки SSH;
- настройки Ansible;
- последующих проверок гостя.

### 5.2. DHCP

Если итоговое состояние содержит:

```yaml
network:
  ipv4: dhcp
```

конкретный адрес определяется после запуска объекта.

Управляющая среда должна получать интерфейсы через PVE.

Для VM используется QEMU Guest Agent.

Для LXC используются сведения интерфейсов контейнера.

### 5.3. Выбор адреса DHCP

Из фактических интерфейсов выбирается IPv4, который:

- принадлежит административной подсети;
- не является адресом сети или широковещательным адресом;
- является единственным подходящим кандидатом.

Если адрес ещё не появился, проверка повторяется ограниченное время.

Если найдено несколько подходящих адресов, автоматическое подключение запрещено как неоднозначное.

DHCP-сервер или маршрутизатор не являются обязательным источником данных для определения фактического адреса.

## 6. Настройка Linux-гостя

### 6.1. Административный SSH

До запуска Ansible должно быть подтверждено реальное административное SSH-подключение.

Факт открытого TCP-порта не является достаточной проверкой.

Политика ключей и сертификатов относится к разделу безопасности.

### 6.2. `provision.yaml`

Ansible получает индивидуальные требования из `provision.yaml`.

Минимальный поддерживаемый Linux-контракт и действующие разделы файла описаны в [`320-guest-manifest.md`](320-guest-manifest.md).

Изменение пакета, каталога или приложения внутри гостя не должно требовать пересоздания VM/LXC, если объект Proxmox менять не нужно.

### 6.3. Повторяемость

Повторный Ansible-запуск должен быть безопасным.

Если требуемое состояние уже достигнуто, роль не должна создавать искусственных изменений.

## 7. Требования доступа

Нормативные права конкретного гостя читаются из:

```text
infrastructure/security/access.yaml
```

Они не выводятся из профиля и не выдаются автоматически всем гостям.

### 7.1. SSH

Правило SSH отдельно определяет:

- нужна ли гостю собственная исходящая identity;
- к каким целям разрешено подключение;
- какой класс входа разрешён.

Выдача identity сама по себе не означает разрешение подключаться ко всем гостям.

### 7.2. Git

Чтение проектного репозитория задаётся отдельным правилом Git.

Оно:

- не означает право записи;
- не означает административный SSH;
- не означает PVE API;
- отзывается независимо от других доступов.

### 7.3. Другие подсистемы

PVE API, Semaphore и OpenBao используют тот же общий принцип: субъект, ресурс, цели и действия должны быть явно представлены в `access.yaml`.

Старые `management` пока остаются только совместимым входом resolver. Проверка проекта не позволяет им расходиться с новым контрактом.

## 8. Повторное обслуживание и ошибки

### 8.1. Повторный запуск

Каждый штатный повторный запуск заново:

1. читает текущий проект;
2. проверяет его;
3. строит итоговое состояние;
4. сравнивает его с PVE;
5. применяет разрешённые изменения;
6. определяет фактический адрес;
7. применяет Ansible;
8. проверяет результат.

Старый номер выполненного шага не считается источником истины.

### 8.2. Частичная ошибка

Общий разрушительный откат после любой ошибки запрещён.

Уже выполненные изменения должны оставаться видимыми.

Следующий запуск обязан заново прочитать фактическое состояние.

### 8.3. Незавершённое создание

Узкий автоматический cleanup допустим только для объекта, который:

- однозначно принадлежит текущей операции;
- находится в специальном состоянии незавершённого создания;
- совпадает с ожидаемыми идентичностью и типом.

Перед автоматическим удалением такая принадлежность должна быть доказана.

Этот механизм не является общим разрешением удалять любой расходящийся объект.

## 9. Опасные операции

Изменения, которые могут:

- пересоздать объект;
- уничтожить диск;
- сменить технический тип;
- заменить источник создания;
- привести к потере постоянных данных,

не должны маскироваться под обычное обслуживание.

Удаление гостя является отдельной явной операцией.

Простое удаление описания из Git не должно незаметно уничтожать фактический объект и данные.

Перед удалением необходимо отдельно определить судьбу:

- VM/LXC;
- дисков;
- постоянных данных;
- резервных копий;
- выданных удостоверений;
- OpenTofu-state.

## 10. Специальное владение жизненным циклом

Специальный объект может использовать обычный профиль и общий Ansible, но иметь отдельного владельца объекта Proxmox.

Главный пример — управляющий LXC.

Его общий технический контракт остаётся обычным:

```text
profile
→ итоговое состояние
→ provision.yaml
→ общий Ansible
```

Особенность состоит в другом:

- первоначальный объект создаётся временным контуром;
- объект принадлежит отдельному первоначальному OpenTofu-state;
- постоянная управляющая среда не владеет собственным объектом через своё штатное OpenTofu-state;
- самообновление содержимого ОС использует общий Ansible-контракт без принятия собственного объекта в постоянное состояние.

Таким образом, специальный жизненный цикл не требует второго формата `guest.yaml`.
