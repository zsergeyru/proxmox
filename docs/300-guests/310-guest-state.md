# Требуемое состояние гостевой системы

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить, из каких источников строится требуемое состояние VM/LXC, как объединяются значения и какие проверки выполняются до получения итогового состояния.

Этот документ отвечает на вопрос:

> Как из общих настроек, профиля и `guest.yaml` получается однозначное итоговое состояние конкретной гостевой системы?

Документ описывает именно построение состояния. Значение отдельных полей `guest.yaml` вынесено в справочник `320-guest-manifest.md`, а применение уже построенного состояния относится к отдельному документу жизненного цикла гостя.

## 1. Модель состояния

### 1.1. Исходное состояние

Человек не описывает полную конфигурацию VM/LXC в одном файле.

Для обычного управляемого гостя исходное состояние складывается из нескольких частей:

~~~text
общие настройки проекта
+
выбранный профиль
+
guest.yaml конкретного гостя
~~~

Такое разделение позволяет хранить общие правила один раз и не повторять одинаковые значения во всех гостевых системах.

Индивидуальный файл гостя находится по пути:

~~~text
infrastructure/guests/<VMID>-<name>/guest.yaml
~~~

Общие настройки и профили находятся в:

~~~text
infrastructure/guests/defaults.yaml
~~~

Исходное состояние может быть неполным само по себе. Например, в `guest.yaml` не требуется повторять PVE-узел, хранилище диска или сетевой мост, если они уже определены общими настройками.

### 1.2. Итоговое состояние

Перед использованием исходные данные преобразуются в полное итоговое состояние.

Итоговое состояние должно быть:

- однозначным;
- полным для выбранного типа гостя;
- проверенным;
- одинаковым для всех средств, которые читают состояние проекта.

Общая схема:

~~~text
общие настройки
        +
      профиль
        +
    guest.yaml
        ↓
объединение значений
        ↓
специальные правила
        ↓
вычисляемые значения
        ↓
итоговое требуемое состояние
        ↓
проверка
~~~

Следующие средства проекта не должны самостоятельно придумывать собственные правила наследования или вычисления одних и тех же значений.

Для построения состояния существует один общий механизм.

### 1.3. Обычный и специальный гость

Наличие `profile` определяет участие гостя в общей модели построения состояния.

Если `profile` указан:

- профиль должен существовать;
- применяются общие настройки проекта;
- применяются правила выбранного профиля;
- строится полное итоговое состояние;
- гость считается участником обычного управляемого контура.

Если `profile` отсутствует:

- объект всё ещё может быть описан в проекте;
- общее итоговое состояние для него не строится;
- общие настройки и профиль к нему автоматически не применяются;
- его жизненный цикл должен быть определён отдельно.

Такой вариант допускается для специальных объектов, которые действительно нельзя безопасно включить в общий механизм. `910 infra-manager` больше не является таким исключением: он имеет обычный LXC-профиль, а отдельность его жизненного цикла определяется владельцем OpenTofu state.

Поля, смысл которых существует только внутри общего управляемого контура, нельзя использовать у гостя без `profile`.

## 2. Источники значений

### 2.1. Общие настройки

Раздел `defaults` в `infrastructure/guests/defaults.yaml` содержит значения, которые являются общими для обычных управляемых гостей.

К ним относятся общие параметры:

- PVE-узла;
- защиты объекта;
- участия в управляемом контуре;
- хранилища диска;
- сети;
- автоматического запуска.

Общие настройки задают основу состояния, но не должны содержать свойства, которые по смыслу относятся только к одному конкретному гостю.

Например, индивидуальные возможности `management` в общих настройках запрещены.

### 2.2. Профиль

Профиль задаёт типовую техническую основу определённого класса гостей.

Именно профиль определяет тип:

~~~text
vm
или
lxc
~~~

Для VM профиль также определяет источник создания в виде `template_vmid`.

Для LXC профиль определяет `ostemplate` и при необходимости технические возможности контейнера через `features`.

Профиль не должен содержать индивидуальные возможности конкретного экземпляра гостя.

В частности, `management` в профиле запрещён.

### 2.3. Индивидуальный `guest.yaml`

`guest.yaml` описывает конкретный экземпляр.

Он содержит идентичность гостя и значения, которые нельзя или не нужно получать из общих настроек.

Для гостя с `profile` именно `guest.yaml` выбирает профиль и задаёт индивидуальные ресурсы.

Он также может явно переопределить часть разрешённых общих значений.

Если значение уже однозначно приходит из общих настроек или профиля, повторять его без причины не следует.

Такое повторение не меняет результат, но усложняет сопровождение и скрывает реальные отличия конкретного гостя.

### 2.4. Приоритет источников

Обычное объединение выполняется в фиксированном порядке:

~~~text
defaults
↓
profile
↓
guest.yaml
~~~

Более поздний источник имеет приоритет над более ранним.

Например, если одно и то же разрешённое значение задано в общих настройках и в `guest.yaml`, итоговое состояние получает значение из `guest.yaml`.

При этом не каждое поле разрешено задавать на каждом уровне. Допустимые места хранения определяются схемами и специальными правилами проекта.

## 3. Правила построения итогового состояния

### 3.1. Рекурсивное объединение

Вложенные группы параметров объединяются рекурсивно.

Например, если общие настройки содержат:

~~~yaml
resources:
  disk_storage: local-lvm
~~~

а конкретный гость содержит:

~~~yaml
resources:
  cores: 2
  memory_mb: 4096
  disk_size_gb: 32
~~~

то итоговая группа `resources` содержит значения из обоих источников:

~~~yaml
resources:
  disk_storage: local-lvm
  cores: 2
  memory_mb: 4096
  disk_size_gb: 32
~~~

Отсутствие отдельного вложенного значения в более позднем источнике не удаляет значение, полученное ранее.

### 3.2. Замена простого значения

Если более поздний источник явно задаёт обычное значение, оно заменяет унаследованное.

Например:

~~~text
defaults: protection = true
guest.yaml: protection = false
~~~

даёт в итоговом состоянии:

~~~text
protection = false
~~~

Такое переопределение допустимо только для полей, которым это разрешено.

Некоторые отклонения от общих проектных значений считаются допустимыми, но требуют внимания и поэтому отмечаются предупреждением при проверке.

### 3.3. Списки не объединяются автоматически

Списки не следует считать обычным наследуемым набором значений.

Для специальных списков проекта действуют отдельные правила.

`management`:

- задаётся только конкретному гостю;
- не наследуется из `defaults`;
- не наследуется из профиля;
- не объединяется с другими источниками;
- при отсутствии превращается в пустой список итогового состояния;
- при наличии проверяется и приводится к установленному порядку.

Это гарантирует, что индивидуальная возможность не появится у гостя только потому, что была случайно добавлена в общий профиль.

### 3.4. Возможности профиля

`features` относится к профилю LXC и описывает технические возможности среды контейнера.

Список проверяется отдельно и приводится к установленному порядку.

Для VM `features` не используется.

Индивидуальный `guest.yaml` не должен подменять технические возможности профиля собственным набором низкоуровневых параметров.

### 3.5. Отсутствующее и переопределённое значение

Отсутствие поля и явное значение — разные состояния.

Если разрешённое поле отсутствует в `guest.yaml`, оно может быть получено из более раннего источника.

Если поле присутствует, его значение считается осознанным указанием конкретного гостя.

Поэтому избыточное явное повторение уже унаследованного значения отмечается предупреждением.

Это помогает отличать реальные исключения от случайного копирования общих настроек.

## 4. Вычисляемые и специальные значения

### 4.1. Режим адресации

Для административного интерфейса поддерживаются три варианта:

| Исходное значение | Итоговое значение | Поведение |
|---|---|---|
| `network.ipv4` отсутствует | вычисленный `IPv4/16` | статический адрес по правилу VMID |
| указан IPv4 без префикса | указанный `IPv4/16` | явный статический адрес |
| `network.ipv4: dhcp` | `dhcp` | адрес выдаётся DHCP |

Общая административная подсеть, шлюз и сетевой мост продолжают задаваться централизованно независимо от выбранного режима.

### 4.2. Автоматический статический IPv4

Если `network.ipv4` не задан, адрес вычисляется из VMID и общей административной подсети.

Для сети вида:

~~~text
A.B.0.0/16
~~~

используется правило:

~~~text
VMID XYZ → A.B.X.YZ
~~~

Например:

~~~text
VMID 310 → A.B.3.10
VMID 410 → A.B.4.10
VMID 510 → A.B.5.10
~~~

Общая административная сеть для этой схемы должна иметь маску `/16`.

В итоговом состоянии к вычисленному адресу добавляется префикс общей сети.

### 4.3. Явный статический IPv4

Если конкретному гостю нужен адрес, отличающийся от вычисляемого, `network.ipv4` задаётся явно.

В исходном `guest.yaml` адрес записывается без маски:

~~~yaml
network:
  ipv4: 192.168.10.50
~~~

Маска берётся из общей сети и добавляется при построении итогового состояния.

Явный адрес должен:

- быть IPv4;
- находиться внутри общей административной подсети;
- не совпадать с адресом сети;
- не совпадать с широковещательным адресом;
- не совпадать со шлюзом;
- не совпадать с адресом другого гостя.

Если явно заданный адрес отличается от адреса по правилу VMID, состояние остаётся допустимым, но проверка выдаёт предупреждение.

Если явно задан тот же адрес, который и так был бы вычислен из VMID, проверка сообщает об избыточном переопределении.

### 4.4. DHCP

Для получения адреса от DHCP в `guest.yaml` указывается:

~~~yaml
network:
  ipv4: dhcp
~~~

В итоговом состоянии сохраняется значение:

~~~yaml
network:
  ipv4: dhcp
~~~

Для такого гостя проект не считает конкретный IPv4 частью требуемого состояния.

Поэтому для DHCP-гостя не выполняются:

- сравнение адреса с формулой VMID;
- проверка уникальности статического IPv4;
- проверка принадлежности фактического выданного адреса на этапе построения состояния.

После запуска фактический административный IPv4 определяет `910 infra-manager` через PVE API.

Для VM адрес получается из сведений QEMU Guest Agent.

Для LXC адрес получается из сведений о сетевых интерфейсах контейнера, доступных через PVE.

Из полученных адресов выбирается IPv4, принадлежащий общей административной подсети проекта. Служебные, локальные и адреса других сетей не используются.

Если подходящий адрес не найден, управление гостем должно дождаться его появления. Если одновременно найдено несколько подходящих адресов, состояние считается неоднозначным и автоматическое подключение не должно угадывать нужный адрес.

Таким образом, `910` не зависит от API конкретного DHCP-сервера и не хранит отдельную таблицу выданных адресов.

### 4.5. Тип гостя и источник создания

Тип гостя не задаётся отдельно в каждом `guest.yaml`.

Он определяется выбранным профилем.

Для профиля VM обязательным источником создания является `template_vmid`.

Для профиля LXC обязательным источником является `ostemplate`.

Параметры VM и LXC не должны смешиваться:

- VM не использует `ostemplate` и LXC-`features`;
- LXC не использует `template_vmid`.

Дополнительные ограничения конкретных полей описаны в справочнике манифеста.

### 4.6. Граница с состоянием гостевой ОС

Требуемое состояние объекта VM/LXC не описывает пакеты, службы и приложения внутри гостевой операционной системы.

Такие требования хранятся отдельно в `provision.yaml` конкретного гостя и применяются Ansible после создания объекта и появления административного доступа.

Поэтому установка Git, Docker, Ansible и другого программного обеспечения не является частью итогового состояния `guest.yaml`.

## 5. Проверка состояния

### 5.1. Проверка исходных данных

До построения итогового состояния проверяются исходные файлы.

Для них определяются:

- допустимые поля;
- типы значений;
- обязательные поля;
- допустимые значения;
- зависимости между полями;
- отсутствие неизвестных полей.

Отдельно проверяются общие настройки и определения профилей.

Машинные правила находятся в:

~~~text
infrastructure/schemas/guest.schema.yaml
infrastructure/schemas/guest-defaults.schema.yaml
~~~

Наличие корректного YAML само по себе недостаточно: данные должны также соответствовать правилам проекта.

### 5.2. Проверки во время построения

Во время построения проверяются правила, которые нельзя выразить только формой YAML.

В частности:

- существование выбранного профиля;
- соответствие профиля типу VM или LXC;
- допустимость источника создания;
- запрет `management` в общих настройках и профилях;
- допустимые значения специальных списков;
- отсутствие дубликатов в списках;
- корректность административной сети;
- вычисление статического IPv4, разбор явного адреса или выбор режима DHCP.

Если состояние нельзя однозначно построить, оно считается ошибочным.

### 5.3. Проверка итогового состояния

После объединения и вычислений итоговое состояние проверяется повторно.

Оно должно содержать полный набор значений, необходимый для выбранного типа гостя.

Машинная схема итогового состояния находится в:

~~~text
infrastructure/schemas/guest-effective.schema.yaml
~~~

Дополнительно проверяются взаимосвязи, которые выходят за рамки одного гостя или одного поля.

Например:

- VMID должен совпадать с номером в имени каталога;
- имя гостя должно совпадать с именем каталога;
- VMID не должны повторяться;
- статические административные IPv4 не должны повторяться;
- VM не может использовать саму себя как шаблон;
- размер динамической памяти VM не должен превышать общий объём памяти;
- параметры памяти VM и LXC не должны смешиваться;
- LXC должен использовать допустимый источник системного образа;
- в конфигурации не должны храниться секреты и закрытые ключи.

### 5.4. Ошибка и предупреждение

Проверка различает ошибки и предупреждения.

**Ошибка** означает, что состояние нельзя считать корректным входом для автоматического управления.

Примеры:

- неизвестный профиль;
- несовместимые параметры VM и LXC;
- статический адрес вне административной сети;
- повторяющийся VMID или IPv4;
- недопустимое сочетание возможностей;
- секрет в файле конфигурации.

**Предупреждение** означает, что состояние допустимо, но отличается от обычных правил проекта или содержит избыточность.

Примеры:

- явный IPv4 отличается от адреса по правилу VMID;
- значение в `guest.yaml` повторяет уже унаследованное значение;
- отдельное проектное значение осознанно переопределено;
- определён профиль, который пока не используется ни одним гостем.

Предупреждение не делает итоговое состояние недопустимым, но должно быть понятно, почему отклонение существует.

### 5.5. Единая проверка проекта

Проверка всех описаний гостей выполняется общей командой:

~~~bash
python scripts/validate_repo.py
~~~

Она проверяет не только каждый файл отдельно, но и связи между гостями.

Поэтому успешная проверка отдельного `guest.yaml` не заменяет проверку всего проекта.

## 6. Результат построения

### 6.1. Что содержит итоговое состояние

Для обычного гостя с `profile` результат содержит уже разрешённое и однозначное состояние объекта VM/LXC.

В нём присутствуют:

- идентичность гостя;
- выбранный профиль и определённый им тип;
- размещение;
- защита;
- участие в управляемом контуре;
- полный набор ресурсов;
- полные сетевые параметры;
- правило автоматического запуска;
- индивидуальные возможности управления;
- параметры, специфичные для VM или LXC.

Следующий слой проекта получает именно это итоговое состояние, а не самостоятельно объединяет `defaults.yaml`, профиль и `guest.yaml`.

### 6.2. Единый владелец правил построения

Правила объединения и вычисления должны иметь одну реализацию.

В проекте эту роль выполняет:

~~~text
scripts/guests/resolver.py
~~~

Средства проверки и преобразования данных должны использовать общий механизм, а не повторять его правила самостоятельно.

Так сохраняется одинаковый результат независимо от того, кто использует итоговое состояние дальше.

### 6.3. Что не входит в это состояние

Итоговое состояние, описанное в этом документе, относится прежде всего к объекту VM/LXC и инфраструктурным возможностям, необходимым для его дальнейшего управления.

Оно не является полным описанием:

- всех пакетов внутри операционной системы;
- всех конфигурационных файлов приложений;
- рабочих данных сервисов;
- текущих журналов;
- резервных копий;
- фактического состояния запущенных приложений.

Эти области имеют собственных владельцев и не должны незаметно становиться частью модели состояния VM/LXC.
