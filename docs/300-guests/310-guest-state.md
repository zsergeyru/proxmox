## 1. Уровни состояния

Проект различает минимум три независимых слоя требований:

```text
объект VM/LXC        → defaults.yaml + profile + guest.yaml
содержимое Linux ОС  → provision.yaml
проверка готовности  → status.yaml, если она определена
```

Эти слои не должны подменять друг друга.

`guest.yaml` не описывает пакеты и приложения.

`provision.yaml` не определяет ресурсы Proxmox.

`status.yaml` не становится вторым источником требуемой конфигурации.

## 2. Источники состояния объекта Proxmox

### 2.1. Общие настройки

Раздел `defaults` в:

```text
infrastructure/guests/defaults.yaml
```

содержит значения, общие для нескольких гостей:

- PVE-узел;
- защиту объекта;
- принадлежность к управляемой области PVE;
- хранилище основного диска;
- административную сеть;
- правило автоматического запуска.

Индивидуальные возможности конкретного гостя не должны появляться здесь.

### 2.2. Профиль

Профиль задаёт техническую основу класса гостей.

Он определяет:

- тип `vm` или `lxc`;
- для VM — источник клонирования;
- для LXC — системный образ;
- высокоуровневые технические возможности LXC.

Наличие `profile` означает, что для объекта можно построить полное итоговое состояние общей моделью.

Это **не означает**, что жизненный цикл объекта обязательно принадлежит обычному постоянному OpenTofu-состоянию. Специальный объект может использовать общий профиль, но иметь отдельного владельца жизненного цикла.

### 2.3. Индивидуальный `guest.yaml`

`guest.yaml` содержит идентичность конкретного гостя, выбор профиля, индивидуальные ресурсы и осознанные переопределения разрешённых общих значений.

Обычный порядок приоритета:

```text
defaults
↓
profile
↓
guest.yaml
```

Поздний источник заменяет более ранний только для тех полей, где такое переопределение разрешено.

## 3. Правила объединения

### 3.1. Вложенные группы

Словари объединяются рекурсивно.

Если общие настройки задают хранилище, а конкретный гость задаёт процессор, память и размер диска, итоговая группа ресурсов содержит оба набора значений.

### 3.2. Избыточные переопределения

Если `guest.yaml` повторяет уже унаследованное значение, это не меняет результат и должно отмечаться предупреждением.

Такой сигнал помогает отличать реальные исключения от случайного копирования общих настроек.

### 3.3. Списки

Списки не объединяются автоматически.

`features` принадлежит профилю LXC, задаётся профилем и имеет собственный ограниченный набор значений.

Требования доступа не входят в результат resolver и читаются отдельно из `infrastructure/security/access.yaml`.

## 4. Специальные значения

### 4.1. Административный IPv4

В простом сетевом режиме административный адрес определяется через `network.ipv4`.

| Исходное значение | Итоговое состояние | Смысл |
|---|---|---|
| поле отсутствует | вычисленный статический IPv4 | обычная адресация по VMID |
| указан IPv4 без префикса | явный статический IPv4 | осознанное исключение |
| `dhcp` | `dhcp` | конкретный адрес определяется после запуска |

Для статического простого режима префикс берётся из общей административной сети.

Для целевого расширенного режима с `network.interfaces` административным считается интерфейс с `management: true`.

У такого интерфейса:

- статический IPv4 хранится вместе с префиксом;
- либо используется `dhcp`;
- gateway может находиться на другом интерфейсе;
- управляющий контур не должен считать первый интерфейс или интерфейс с default route административным автоматически.

Простой `network.ipv4` и расширенный `network.interfaces` являются взаимоисключающими режимами.

### 4.2. Автоматический статический адрес

При отсутствии `network.ipv4` адрес вычисляется из VMID по общему правилу административной сети.

Точное правило вычисления является частью единого сборщика состояния. Индивидуальные инструменты не должны реализовывать собственную формулу.

### 4.3. DHCP

При простом режиме:

```yaml
network:
  ipv4: dhcp
```

или при `ipv4: dhcp` на интерфейсе с `management: true` в расширенном режиме конкретный административный IPv4 не является частью требуемого состояния.

После запуска фактический административный IPv4 должен определяться через PVE:

- для VM — по данным QEMU Guest Agent;
- для LXC — по данным интерфейсов контейнера.

Используется единственный адрес общей административной подсети.

Если подходящего адреса ещё нет, управление должно ждать его появления ограниченное время.

Если одновременно найдены несколько подходящих адресов, автоматический выбор запрещён как неоднозначный.

Обращение к API конкретного DHCP-сервера для этой задачи не требуется.

### 4.4. `pve_management`

`pve_management` описывает требуемую принадлежность объекта к управляемой области PVE.

Поле не определяет:

- наличие или отсутствие профиля;
- административный SSH;
- фактический набор прав API-токена;
- владельца OpenTofu-state специального объекта.

Особый жизненный цикл, например отдельное владение объектом управляющего контейнера, задаётся жизненным циклом этого объекта, а не выводится только из `pve_management`.

## 5. Граница с состоянием ОС

После построения объекта VM/LXC содержимое поддерживаемой Linux-системы определяется отдельно:

```text
provision.yaml
→ общий Ansible
```

`provision.yaml` содержит требуемые пакеты, службы, компоненты, каталоги и другие поддерживаемые параметры ОС.

Файлы и поля `provision.yaml` описаны в том же справочнике, что и `guest.yaml`:

[`320-guest-manifest.md`](320-guest-manifest.md).

Если для гостя определён `status.yaml`, он задаёт машинное описание проверки готовности и итогового представления состояния, но не участвует в построении объекта Proxmox.

## 6. Проверка

### 6.1. Исходные YAML

До построения состояния проверяются:

- допустимые поля;
- типы;
- обязательность;
- зависимости между полями;
- допустимые значения;
- отсутствие неизвестных полей там, где действует машинная схема.

Машинные схемы объекта находятся в:

```text
infrastructure/schemas/guest.schema.yaml
infrastructure/schemas/guest-defaults.schema.yaml
infrastructure/schemas/guest-effective.schema.yaml
```

### 6.2. Связи между гостями

Общая проверка дополнительно подтверждает:

- соответствие VMID имени каталога;
- соответствие имени гостя каталогу;
- отсутствие повторяющихся VMID;
- отсутствие конфликтов статических административных IPv4;
- допустимость выбранного профиля;
- согласованность параметров VM и LXC;
- отсутствие секретов в машинных описаниях Git.

### 6.3. Ошибка и предупреждение

Ошибка означает, что состояние нельзя безопасно использовать для автоматического управления.

Предупреждение означает допустимое, но нетипичное или избыточное состояние.

Проверка всего проекта выполняется одной командой:

```bash
python scripts/validate_repo.py
```

## 7. Результат

Итоговое состояние объекта VM/LXC содержит уже разрешённые значения:

- идентичность;
- профиль и тип;
- PVE-узел;
- защиту;
- принадлежность к управляемой области;
- ресурсы;
- сеть;
- запуск;
- параметры источника создания и технических возможностей, пришедшие из профиля.

Единый механизм построения состояния является владельцем правил объединения и вычислений.

OpenTofu и другие потребители получают готовое итоговое состояние и не должны повторно интерпретировать `defaults.yaml`, профиль и `guest.yaml` собственными правилами.
