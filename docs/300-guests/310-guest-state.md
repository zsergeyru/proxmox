# Требуемое состояние гостевой системы

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить источники, параметры, правила построения и проверки требуемого состояния VM/LXC.

Этот документ отвечает на вопрос:

> Как в проекте описывается требуемое состояние конкретной гостевой системы и как из исходных файлов получается итоговое состояние?

Документ не описывает порядок применения изменений к Proxmox. Контракт планирования и применения (`PLAN/APPLY`) и жизненный цикл команды `deploy-guest` относятся к отдельной спецификации развёртывания.

## 1. Назначение и модель состояния

### 1.1. Назначение документа

Для управляемой VM/LXC проект хранит не готовую конфигурацию Proxmox, а исходное описание требуемого состояния.

Оно должно быть:

- компактным;
- проверяемым;
- воспроизводимым;
- однозначно преобразуемым в итоговое состояние;
- пригодным для сравнения с фактическим состоянием Proxmox.

Основной индивидуальный файл гостя:

```text
guests/<VMID>-<name>/guest.yaml
```

Общие значения и профили находятся в:

```text
guests/defaults.yaml
```

Машинные ограничения формата задаются схемами в `schemas/`.

### 1.2. Что считается требуемым состоянием

Требуемое состояние определяет, каким должен быть объект VM/LXC с точки зрения проекта.

К нему относятся, в частности:

- идентификатор и имя;
- тип гостевой системы;
- размещение;
- процессор, память и диск;
- сеть;
- правила запуска;
- контур административного управления;
- явно запрошенная первоначальная подготовка;
- параметры, специфичные для VM или LXC.

Работающая VM/LXC в Proxmox хранит фактическое состояние, но сама по себе не становится источником требований.

Изменение требуемого состояния выполняется через соответствующие файлы проекта.

### 1.3. Исходное и итоговое состояние

В проекте различаются два представления состояния.

**Исходное состояние** — компактные данные, которые человек редактирует в Git:

```text
guests/defaults.yaml
+
профиль
+
guests/<VMID>-<name>/guest.yaml
```

**Итоговое состояние** — полное состояние после наследования, объединения, нормализации и вычисления производных значений.

Общая схема:

```text
исходные данные
→ schema validation
→ resolver
→ effective state
→ проверка effective state
```

Средства проверки и развёртывания должны использовать одно и то же итоговое состояние и не реализовывать собственные параллельные правила его построения.

## 2. Источники и построение состояния

### 2.1. Источники состояния

Требуемое состояние строится из трёх основных источников.

`guests/defaults.yaml` содержит:

- общие значения проекта;
- параметры, одинаковые для большинства гостей;
- определения профилей VM/LXC.

Профиль определяет типовую основу конкретного класса гостевых систем.

Например:

```yaml
profiles:
  debian-vm:
    type: vm
    template_vmid: 9000

  debian-lxc:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard

  debian-lxc-docker:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard
    features:
      - container-host
```

Индивидуальный `guest.yaml` содержит параметры конкретной VM/LXC и осознанные отклонения от общих значений.

Обычный гость с `profile` не должен копировать в свой `guest.yaml` значения, которые уже однозначно приходят из `defaults.yaml` или выбранного профиля.

### 2.2. Порядок объединения и переопределения

Порядок построения состояния фиксирован:

```text
defaults
→ profile
→ guest.yaml
→ специальные правила
→ вычисляемые значения
→ effective state
```

Словари объединяются рекурсивно.

Более позднее простое значение заменяет более раннее.

Избыточное повторение унаследованного значения нежелательно: оно усложняет чтение манифеста и может скрывать последующие изменения общих настроек.

### 2.3. Специальные и вычисляемые значения

Не все поля следуют обычному наследованию.

Некоторые параметры разрешено задавать только конкретному гостю.

К таким индивидуальным возможностям относятся элементы списков `management` и `bootstrap`.

Они не должны появляться в общих настройках или профилях.

Некоторые значения вообще не хранятся в обычном `guest.yaml`, а вычисляются из других параметров.

Главный пример — административный IPv4.

Если индивидуальное переопределение отсутствует, адрес вычисляется из VMID и центральной административной подсети.

### 2.4. Итоговое состояние

Общий сборщик итогового состояния проекта:

```text
scripts/guest_config.py
```

строит однозначное итоговое состояние.

Для гостя с `profile` итоговое состояние должно содержать все обязательные параметры, необходимые следующим слоям проекта.

В частности, сборщик итогового состояния:

- объединяет общие настройки, профиль и индивидуальный манифест;
- нормализует список индивидуальных возможностей административного управления;
- вычисляет административный IP;
- проверяет и нормализует запрошенную первоначальную подготовку;
- возвращает запрошенные инструменты первоначальной подготовки в каноническом порядке.

Машинный формат итогового состояния проверяется схемой:

```text
schemas/guest-effective.schema.yaml
```

Итоговое состояние является интерфейсом между описанием гостя и средствами, которые сравнивают или применяют это состояние.

## 3. Параметры гостевой системы

Этот раздел является подробным справочником параметров требуемого состояния.

Для каждого параметра указано:

- где он используется;
- для чего нужен;
- что происходит, если его задать;
- что происходит, если его не задавать;
- пример применения.

Здесь описывается смысл отдельных параметров. Правила, связывающие несколько параметров между собой, собраны в разделе 4.

### 3.1. Основные параметры

#### 3.1.1. `schema_version`

**Тип:** целое число с фиксированным допустимым значением.

В обычном `guest.yaml` используется:

```yaml
schema_version: 10
```

Для всего состояния гостевой системы используется единая версия контракта. Поэтому и обычный `guest.yaml`, и `guests/defaults.yaml`, и итоговое состояние используют один номер:

```yaml
schema_version: 10
```

Параметр нужен для того, чтобы проверяющий модуль однозначно понимал, по какой версии общего контракта состояния гостевой системы проверять файл.

Если указано поддерживаемое значение, файл проверяется по соответствующему текущему контракту.

Если поле отсутствует или указана другая версия, проверка по схеме завершается ошибкой. Автоматического преобразования старой версии в новую нет.

#### 3.1.2. `vmid`

**Тип:** целое число от `100` до `999`.

Используется в каждом `guest.yaml`.

Пример:

```yaml
vmid: 311
```

Параметр задаёт VMID для VM или CTID для LXC. Он также участвует в имени каталога и по умолчанию используется для вычисления административного IPv4.

Для:

```text
guests/311-dev-services/
```

манифест должен содержать:

```yaml
vmid: 311
```

Если `vmid` задан, но не совпадает с числовой частью имени каталога, проверка репозитория завершается ошибкой.

Если тот же VMID использован ещё одним гостем, проверка также завершается ошибкой.

Если поле не задано, исходный манифест не проходит проверку по схеме.

#### 3.1.3. `name`

**Тип:** строка вида `[a-z0-9][a-z0-9-]*`.

Используется в каждом `guest.yaml`.

Пример:

```yaml
name: dev-services
```

Имя идентифицирует гостя внутри проекта и должно совпадать с частью имени каталога после `<VMID>-`.

Для:

```text
311-dev-services
```

допустимо:

```yaml
name: dev-services
```

Если имя в манифесте не совпадает с каталогом, валидатор выдаёт ошибку.

Если поле отсутствует, манифест не проходит проверку по схеме.

#### 3.1.4. `description`

**Тип:** непустая строка.

Используется в каждом `guest.yaml`.

Пример:

```yaml
description: Ansible, Semaphore, Git, CI and development services
```

Поле кратко объясняет назначение гостя. Это описание для человека, но оно также участвует в проверках качества манифеста.

Для гостя с `profile` текст с маркерами незавершённости вроде `todo`, `tbd`, `unknown` и аналогичными формулировками вызывает предупреждение.

Если `description` отсутствует или пуст, исходный манифест не проходит проверку по схеме.

#### 3.1.5. `profile`

**Тип:** строка — имя профиля из `guests/defaults.yaml`.

Пример:

```yaml
profile: debian-lxc-docker
```

Параметр выбирает типовую основу гостя.

Например, профиль:

```yaml
profiles:
  debian-lxc-docker:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard
    features:
      - container-host
```

передаёт гостю тип `lxc` и параметры LXC.

Наличие `profile` означает, что гость участвует в универсальном контуре построения итогового состояния и может передаваться `deploy-guest`.

Если профиль указан, он должен существовать в `guests/defaults.yaml`. Неизвестное имя профиля приводит к ошибке сборщика итогового состояния.

Если `profile` отсутствует, объект может оставаться описанным в Git, но полное итоговое состояние для него не строится и универсальный контур развёртывания не должен им управлять.

#### 3.1.6. `node`

**Тип:** непустая строка.

Определяет PVE-узел, на котором должен находиться гость.

Общее значение сейчас задаётся в `guests/defaults.yaml`:

```yaml
defaults:
  node: pve
```

Обычному гостю не нужно повторять:

```yaml
node: pve
```

Если `node` не задан в индивидуальном `guest.yaml`, он наследуется из общих настроек или профиля.

Если гостю осознанно нужен другой узел, поле можно переопределить:

```yaml
node: pve2
```

Такое отклонение от общего значения проверяющий модуль отмечает предупреждением.

Если после объединения значение `node` отсутствует, итоговое состояние гостя с `profile` не проходит проверку.

#### 3.1.7. `protection`

**Тип:** логическое значение.

Определяет желаемое состояние встроенной защиты PVE для VM/LXC.

Общее значение:

```yaml
defaults:
  protection: true
```

Поэтому обычный гость с `profile` защищён по умолчанию. Это дополнительный предохранитель от случайных разрушительных операций на уровне Proxmox; параметр не ограничивает настройку гостевой ОС по SSH.

Если для конкретного гостя встроенная защита PVE осознанно не требуется, допускается индивидуальное переопределение:

```yaml
protection: false
```

Такое переопределение проверяющий модуль отмечает предупреждением, потому что оно снимает стандартную защиту проекта.

Если параметр отсутствует во всех источниках, итоговое состояние не соответствует действующей схеме.

#### 3.1.8. `pve_management`

**Тип:** логическое значение.

Определяет, разрешено ли AI-агенту управлять VM/LXC **как объектом Proxmox** через PVE API/MCP.

Общее значение:

```yaml
defaults:
  pve_management: true
```

При `pve_management: true` гость должен находиться в фиксированном пуле PVE `managed`. Права `ai-agent@pve!infra` на управление жизненным циклом и конфигурацией VM/LXC выдаются через ACL этого пула.

Редкое индивидуальное исключение задаётся так:

```yaml
pve_management: false
```

В этом случае гость не должен находиться в пуле `managed`, поэтому AI-агент не получает обычные PVE/MCP-права на его запуск, остановку, изменение виртуального оборудования, снапшоты или удаление как объекта Proxmox.

`pve_management` **не управляет SSH-доступом**. При `false` AI и остальные участники административного SSH-доступа могут продолжать администрировать гостевую ОС, если их ключи разрешены общим SSH-контрактом. Учётная запись `deployer` также сохраняет собственные PVE-права, необходимые контуру развёртывания.

Имя пула `managed` является фиксированной внутренней частью PVE-контракта и не задаётся в `guest.yaml`. Списка произвольных пулов в состоянии гостевой системы нет.

Индивидуальное `pve_management: false` проверяющий модуль отмечает предупреждением как осознанное отклонение от общей политики.

> **Статус реализации:** общие настройки, схемы, сборщик итогового состояния и проверяющий модуль используют `pve_management`. Текущий `deploy-guest` всё ещё относится к старому контракту `placement.pool` и будет заменён при отдельной полной переработке контура развёртывания.

### 3.2. Ресурсы

Раздел `resources` описывает ресурсы **конкретной** VM/LXC.

Принцип разделения ответственности:

```text
profile
→ определяет тип гостя и способ его создания

resources
→ определяет ресурсы конкретного экземпляра
```

Поэтому профили не должны задавать индивидуальные `cores`, `memory_mb`, `ballooning_mb`, `swap_mb` или `disk_size_gb`.

Общие инфраструктурные значения, одинаковые для большинства гостей, могут находиться в `defaults`. Основной пример — `disk_storage`.

Целевая структура ресурсов плоская:

```yaml
resources:
  cores: 2
  memory_mb: 4096
  ballooning_mb: 2048
  swap_mb: 1024
  disk_size_gb: 32
  disk_storage: local-lvm
```

Конкретная VM или LXC содержит только применимые к ней параметры.

> **Статус реализации:** схемы, сборщик итогового состояния, проверяющий модуль и манифесты гостей уже используют эту плоскую модель ресурсов. Старый `deploy-guest` будет переведён на неё при отдельной полной переработке.

#### 3.2.1. `resources.cores`

**Тип:** целое число, минимум `1`.

Задаёт количество CPU, доступных конкретному гостю.

Для VM значение определяет число виртуальных CPU.

Для LXC значение определяет число ядер CPU, доступных контейнеру средствами Proxmox.

Пример:

```yaml
resources:
  cores: 2
```

Для любого гостя с `profile` параметр обязателен непосредственно в его `guest.yaml`.

Параметр не должен задаваться профилем: разные гости одного профиля могут иметь разное количество CPU.

Если поле отсутствует у гостя с `profile`, конфигурация должна считаться неполной и не проходить проверку.

#### 3.2.2. `resources.memory_mb`

**Тип:** целое число, минимум `256`.

Задаёт объём оперативной памяти в MiB.

Для VM это объём RAM виртуальной машины.

Для LXC это лимит памяти контейнера.

Пример:

```yaml
resources:
  memory_mb: 4096
```

Для любого гостя с `profile` параметр обязателен непосредственно в его `guest.yaml`.

Параметр не должен задаваться профилем.

Если поле отсутствует, конфигурация гостя с `profile` должна завершать проверку ошибкой.

#### 3.2.3. `resources.ballooning_mb`

**Тип:** целое число, минимум `0`.

Параметр применяется **только к VM** и используется только тогда, когда для конкретной VM требуется явно управлять динамическим выделением памяти.

Обычной VM этот параметр не требуется.

Пример:

```yaml
resources:
  cores: 2
  memory_mb: 4096
  ballooning_mb: 2048
  disk_size_gb: 32
```

Если `ballooning_mb` указан, проект должен сравнивать и применять соответствующий параметр VM.

Если поле отсутствует, это не является ошибкой и означает, что проект не задаёт отдельного требования к динамическому выделению памяти этой VM.

Значение не может превышать `memory_mb`.

Например:

```yaml
resources:
  memory_mb: 4096
  ballooning_mb: 8192
```

должно завершать проверку ошибкой.

Для LXC параметр запрещён. Наличие `ballooning_mb` у LXC должно считаться ошибкой конфигурации.

Параметр не должен задаваться в профиле или общих настройках: это редкая индивидуальная настройка конкретной VM.

#### 3.2.4. `resources.swap_mb`

**Тип:** целое число, минимум `0`.

Параметр применяется **только к LXC** и задаёт объём подкачки контейнера в MiB.

Пример:

```yaml
resources:
  cores: 2
  memory_mb: 4096
  swap_mb: 1024
  disk_size_gb: 32
```

Значение `0` является допустимым и означает явное требование создать LXC без подкачки:

```yaml
resources:
  swap_mb: 0
```

Для LXC с `profile` параметр должен быть задан непосредственно в `guest.yaml`.

Параметр не должен задаваться профилем: размер подкачки является настройкой конкретного контейнера.

Если `swap_mb` отсутствует у LXC с `profile`, проверка должна завершаться ошибкой.

Для VM параметр запрещён. Наличие `swap_mb` у VM должно считаться ошибкой конфигурации.

#### 3.2.5. `resources.disk_size_gb`

**Тип:** целое число, минимум `1`.

Определяет требуемый размер основного диска VM или корневой файловой системы LXC в GiB.

Пример:

```yaml
resources:
  disk_size_gb: 32
```

Для любого гостя с `profile` параметр обязателен непосредственно в его `guest.yaml`.

Параметр не должен задаваться профилем, потому что размер диска относится к конкретному экземпляру.

Для VM значение описывает требуемый размер основного диска после создания из шаблона.

Для LXC значение используется как требуемый размер корневой файловой системы.

Увеличение размера может выполняться автоматически средствами развёртывания.

Уменьшение диска не должно выполняться автоматически и должно приводить к блокировке изменения.

#### 3.2.6. `resources.disk_storage`

**Тип:** непустая строка.

Определяет хранилище PVE для основного диска VM или корневой файловой системы LXC.

Это инфраструктурный параметр, который обычно одинаков для большинства гостей, поэтому его нормальное место — общие настройки.

Целевая запись:

```yaml
defaults:
  resources:
    disk_storage: local-lvm
```

Обычный `guest.yaml` тогда не повторяет хранилище:

```yaml
resources:
  cores: 2
  memory_mb: 4096
  disk_size_gb: 32
```

Если конкретному гостю требуется другое хранилище, допускается индивидуальное переопределение:

```yaml
resources:
  disk_storage: fast-storage
```

Если `disk_storage` отсутствует и у гостя, и в общих настройках, итоговое состояние должно считаться неполным.

Профиль не должен определять хранилище конкретного гостя: выбор общего хранилища относится к инфраструктурным общим настройкам, а индивидуальное исключение — к `guest.yaml`.

#### 3.2.7. Проверка применимости ресурсов

Тип гостя определяется выбранным профилем, после чего проверяющий модуль должен дополнительно проверять применимость полей ресурсов.

Для VM обязательны:

```text
resources.cores
resources.memory_mb
resources.disk_size_gb
```

Для VM разрешён, но не обязателен:

```text
resources.ballooning_mb
```

Для VM запрещён:

```text
resources.swap_mb
```

Для LXC обязательны:

```text
resources.cores
resources.memory_mb
resources.swap_mb
resources.disk_size_gb
```

Для LXC запрещён:

```text
resources.ballooning_mb
```

Для обоих типов итоговое состояние должно содержать:

```text
resources.disk_storage
```

Значение может прийти из общих настроек или быть индивидуально переопределено.

Дополнительно проверяются:

- `cores >= 1`;
- `memory_mb >= 256`;
- `disk_size_gb >= 1`;
- `swap_mb >= 0`;
- `ballooning_mb >= 0`;
- `ballooning_mb <= memory_mb`;
- хранилище должно существовать и быть доступен на выбранном узле PVE при развёртывании.

Параметр `resources.cpu.type` в целевой модели ресурсов отсутствует.

Он не должен храниться как декларативное поле, пока средство развёртывания не умеет им управлять. Если управление моделью CPU для VM действительно понадобится, для него должен быть введён отдельный осмысленный контракт.

Ограничение и вес CPU, ограничения IOPS и пропускной способности, NUMA, большие страницы памяти, дополнительные диски и устройства сквозного доступа в базовый `resources` сейчас не добавляются.

Они должны появляться только при реальной необходимости и с одновременной реализацией проверки и применения.

### 3.3. Сеть

Сетевой раздел описывает базовую административную сеть гостевой системы.

Для обычного управляемого гостя сеть почти полностью определяется общими настройками. В индивидуальном `guest.yaml` сетевой блок нужен только для редкого осознанного исключения по IPv4.

Целевая общая конфигурация:

```yaml
defaults:
  network:
    bridge: vmbr0
    subnet: 192.168.0.0/16
    gateway: 192.168.1.1
```

Обычный `guest.yaml` вообще не содержит раздел `network`.

> **Статус реализации:** схемы, сборщик итогового состояния, проверяющий модуль и манифесты гостей уже используют эту модель без `network.addressing` и с простым `network.ipv4`. Старый `deploy-guest` будет переведён отдельно.

#### 3.3.1. `network.bridge`

**Тип:** непустая строка.

Определяет сетевой мост PVE для основного административного интерфейса гостя.

Центральное значение:

```yaml
defaults:
  network:
    bridge: vmbr0
```

В текущем базовом контракте сетевой мост задаётся только в `defaults`.

Индивидуальный `guest.yaml` не должен переопределять `network.bridge`.

Причина проста: первая версия универсального развёртывания работает с одним общим административным сетевым мостом. Поддержку других сетевых мостов, VLAN или нескольких интерфейсов следует вводить только вместе с отдельной моделью сетевых интерфейсов.

Если `bridge` отсутствует в общих настройках, итоговое состояние управляемого гостя считается неполным.

#### 3.3.2. `network.subnet`

**Тип:** сеть IPv4.

Задаётся только в центральных `defaults`.

Пример:

```yaml
defaults:
  network:
    subnet: 192.168.0.0/16
```

Подсеть используется для вычисления административного IPv4 и его префикса.

В текущей модели подсеть должна быть IPv4 `/16`, потому что проект использует фиксированное правило вычисления адреса из VMID.

Индивидуальный `guest.yaml` не может переопределить `network.subnet`.

Если параметр отсутствует, имеет неверный формат или не является поддерживаемой административной подсетью, итоговое состояние не строится.

#### 3.3.3. `network.gateway`

**Тип:** адрес IPv4.

Задаётся только в центральных общих настройках.

Пример:

```yaml
defaults:
  network:
    gateway: 192.168.1.1
```

Шлюз должен находиться внутри `network.subnet` и не может совпадать с адресом сети или широковещательным адресом.

Все обычные управляемые гости получают один и тот же шлюз из общих настроек.

Индивидуальный `guest.yaml` не должен задавать собственный шлюз.

Если в будущем появится гость с другой L3-сетью или отдельным шлюзом, это потребует расширенной модели сетевых интерфейсов, а не одиночного переопределения этого поля.

#### 3.3.4. `network.ipv4`

В исходном `guest.yaml` это **необязательная строка IPv4 без префикса**.

Поле используется только как индивидуальное исключение из стандартной VMID-адресации.

Пример:

```yaml
network:
  ipv4: 192.168.8.50
```

Если поле отсутствует, административный IPv4 вычисляется автоматически из VMID и центральной `network.subnet`.

Для VMID `311` и подсети:

```text
192.168.0.0/16
```

получается:

```text
192.168.3.11
```

Отдельный параметр выбора алгоритма адресации не нужен: VMID-адресация является правилом проекта.

Если `network.ipv4` задан, сборщик итогового состояния использует этот адрес вместо вычисленного.

Префикс в исходном `guest.yaml` не указывается. Он берётся из `network.subnet`.

Поэтому допустимо:

```yaml
network:
  ipv4: 192.168.8.50
```

и недопустимо:

```yaml
network:
  ipv4: 192.168.8.50/16
```

В итоговом состоянии адрес уже содержит префикс:

```yaml
network:
  ipv4: 192.168.8.50/16
```

Индивидуальный адрес должен:

- находиться внутри административной подсети;
- не совпадать со шлюзом;
- не быть адресом сети или широковещательным адресом;
- не дублировать адрес другого гостя.

Если переопределение совпадает с автоматически вычисляемым адресом, он избыточен и должен отмечаться предупреждением.

Если переопределение отличается от VMID-адресации, это допустимое осознанное исключение.

#### 3.3.5. Границы базового сетевого контракта

В базовый контракт гостевой системы сейчас не входят:

- несколько сетевых интерфейсов;
- индивидуальный сетевой мост;
- тег VLAN / транковый режим;
- индивидуальный шлюз;
- MTU;
- ограничение скорости;
- флаг межсетевого экрана интерфейса;
- индивидуальная MAC-адресация;
- отдельные параметры DNS и поискового домена;
- IPv6-конфигурация гостя.

Это не запрещает добавить такие возможности позже.

Но они должны появляться только при реальном сценарии использования и, если потребуется несколько интерфейсов или сетевых сегментов, через отдельную явную модель интерфейсов, а не через разрастание текущего простого `network`.

### 3.4. Запуск

Запуск гостя после создания и автоматический запуск вместе с PVE — разные вещи.

В требуемом состоянии конкретного гостя нужен только параметр, который описывает постоянную политику Proxmox.

#### 3.4.1. `boot.onboot`

**Тип:** логическое значение.

Определяет, должен ли Proxmox автоматически запускать гостя при старте PVE.

Общая политика:

```yaml
defaults:
  boot:
    onboot: true
```

Обычный гость наследует `true` и не повторяет это значение.

Если конкретный объект не должен автоматически запускаться вместе с PVE:

```yaml
boot:
  onboot: false
```

это является осознанным индивидуальным переопределением.

Если `onboot` отсутствует и у гостя, и в общих настройках, итоговое состояние управляемого гостя считается неполным.

Параметры порядка запуска, задержек и тайм-аут завершения работы в базовый контракт пока не добавляются. Они должны появиться только при реальной необходимости управлять зависимостями запуска между гостями.

#### 3.4.2. Запуск после развёртывания

Отдельного параметра `boot.start_after_deploy` в целевой модели нет.

Управляемый `deploy-guest` сам отвечает за жизненный цикл развёртывания:

```text
создание или изменение гостя
→ запуск
→ проверка административного SSH
→ первоначальные действия после развёртывания
→ финальная проверка
```

Поэтому запуск после развёртывания является частью контракта средства развёртывания, а не настраиваемым свойством конкретной VM/LXC.

Если в будущем потребуется поддержать сценарий «создать гостя и оставить выключенным», для него должен быть спроектирован отдельный понятный жизненный цикл, включая способ финальной проверки без работающего SSH.

> **Статус реализации:** `boot.start_after_deploy` уже удалён из схем, сборщика итогового состояния и манифестов гостей. Он остаётся только в старом `deploy-guest`, который будет переработан отдельно.

### 3.5. Административное управление (`management`)

Раздел `management` описывает дополнительные права и возможности конкретного управляемого гостя.

Административный SSH при этом не является настраиваемым параметром гостя.

Для любого гостя с `profile` действует фиксированный контракт административного управления:

```text
пользователь SSH: root
порт SSH: 22
```

Поэтому `management.ssh.user` и `management.ssh.port` в целевой модели отсутствуют.

Средство развёртывания, синхронизация административных SSH-ключей и остальные средства управления должны использовать `root:22` как единое правило проекта.

> **Статус реализации:** общие настройки, схемы, сборщик итогового состояния, проверяющий модуль, `sync-management-keys` и манифесты гостей уже используют новый контракт административного управления. Старый `deploy-guest` будет переведён отдельно.

В целевом исходном контракте `management` — это список дополнительных возможностей административного управления.

Пример:

```yaml
management:
  - ssh_identity
  - project_repo_read
```

Допустимы только:

```text
ssh_identity
project_repo_read
```

Если гостю не требуется ни одна дополнительная возможность административного управления, поле `management` вообще не создаётся.

Пустой список, логические значения, неизвестные элементы и дубликаты не допускаются.

В итоговом состоянии `management` также должен быть представлен каноническим списком запрошенных возможностей, а не набором логических полей.

#### 3.5.1. `ssh_identity`

Элемент:

```yaml
management:
  - ssh_identity
```

означает, что этому гостю требуется собственная **исходящая** пара SSH-ключей для административного доступа к другим управляемым гостям.

Это не ключ, которым PVE подключается к данному гостю.

Возможность задаётся только в индивидуальном `guest.yaml` и требует `profile`, потому что создание, регистрация и проверка пары SSH-ключей относятся к управляемому контуру развёртывания.

Если элемента `ssh_identity` в списке нет, собственная исходящая пара SSH-ключей этому гостю не требуется.

#### 3.5.2. `project_repo_read`

Элемент:

```yaml
management:
  - project_repo_read
```

означает, что гостю нужен управляемый доступ только для чтения к приватному репозиторию проекта.

Элемент не содержит имя ключа, путь к закрытому ключу, URL репозитория или произвольные учётные данные Git. Он только включает заранее определённую проектную возможность.

Возможность задаётся только в индивидуальном `guest.yaml` и требует `profile`.

Если элемента `project_repo_read` в списке нет, проектный доступ к Git только для чтения этому гостю не требуется.

`project_repo_read` не устанавливает клиент Git. Наличие Git как программы определяется отдельно через первоначальную подготовку.

Точный жизненный цикл применения и удаления (`APPLY/REMOVE`) возможностей административного управления относится к спецификации `deploy-guest`.

### 3.6. Первоначальная подготовка (`bootstrap`)

Первоначальная подготовка (`bootstrap`) используется только для минимальной первоначальной установки инфраструктурных инструментов внутри конкретной VM/LXC.

**Тип:** список заранее определённых инструментов первоначальной подготовки.

Целевая форма:

```yaml
bootstrap:
  - git
  - docker
  - ansible
```

Допустимы только:

```text
git
docker
ansible
```

Если первоначальная подготовка этому гостю не нужна, поле `bootstrap` вообще не создаётся.

Пустой список, произвольные имена, значения `true/false`, списки пакетов и команды оболочки в исходный контракт не входят.

> **Статус реализации:** схемы, сборщик итогового состояния, проверяющий модуль, тесты и манифесты гостей уже используют список `bootstrap`. Старый `deploy-guest` пока использует прежний контракт первоначальной подготовки и будет переработан отдельно.

Базовая техническая готовность больше не является выбираемой возможностью.

Для каждого управляемого Debian-гостя контур развёртывания сам должен обеспечить необходимые базовые предпосылки для дальнейшего управления, например Python, сертификаты центров сертификации (CA) и `rsync`, и проверить их перед выполнением запрошенной первоначальной подготовки.

Поэтому в `guest.yaml` больше не требуется писать:

```yaml
bootstrap:
  capabilities:
    base: true
```

#### 3.6.1. `git`

`git` означает, что внутри гостевой ОС должен быть установлен и работать клиент Git.

Пример:

```yaml
bootstrap:
  - git
```

Эта возможность не выдаёт учётные данные Git, не выбирает репозиторий и не клонирует произвольный репозиторий.

Доступ к приватному репозиторию проекта является отдельной возможностью административного управления:

```yaml
management:
  - project_repo_read
```

#### 3.6.2. `docker`

`docker` означает, что непосредственно внутри гостевой ОС должен быть установлен и работать проектно поддерживаемый Docker Engine вместе с Docker Compose.

Пример:

```yaml
bootstrap:
  - docker
```

Для LXC это не заменяет требование выбрать профиль с возможностью `container-host`.

`container-host` означает, что LXC технически подготовлен для запуска вложенной среды выполнения контейнеров. Первоначальная подготовка `docker` отдельно определяет, **нужно ли установить Docker** в конкретный экземпляр.

#### 3.6.3. `ansible`

`ansible` означает, что непосредственно внутри VM/LXC должен быть установлен и работать Ansible, в базовой реализации — `ansible-core`.

Пример:

```yaml
bootstrap:
  - ansible
```

Ansible устанавливается **не в Docker-контейнер и не через Docker**, а непосредственно в гостевую операционную систему развёрнутой VM или LXC.

`ansible` не требует `docker`.

`ansible` также не требует `git` как техническую зависимость первоначальной подготовки.

Если конкретному гостю нужны все три инструмента, они указываются независимо:

```yaml
bootstrap:
  - git
  - docker
  - ansible
```

Если Docker не нужен:

```yaml
bootstrap:
  - git
  - ansible
```

Первоначальная подготовка не устанавливает Semaphore, Gitea/Gogs, Jenkins, прикладные наборы Docker Compose или другие сервисы.

После минимальной первоначальной подготовки дальнейшая повторяемая конфигурация ОС и приложений должна выполняться отдельным контуром последующей настройки, прежде всего Ansible.

### 3.7. Параметры профилей VM и LXC

Параметры этого раздела задаются в `guests/defaults.yaml` внутри определения профиля.

Они описывают **тип и способ создания** класса гостей, а не индивидуальные настройки конкретной VM/LXC.

В индивидуальном `guest.yaml` гостя с `profile` эти параметры не повторяются.

Целевая модель профилей:

```yaml
profiles:
  debian-vm:
    type: vm
    template_vmid: 9000

  debian-lxc:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard

  debian-lxc-docker:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard
    features:
      - container-host
```

Имя профиля выбирается для удобства человека и может отражать ОС, тип гостя и назначение, например:

```text
debian-vm
debian-lxc
debian-lxc-docker
ubuntu-vm
ubuntu-lxc
ubuntu-lxc-docker
```

Машинная логика не должна определяться разбором имени профиля. Она определяется только его полями.

> **Статус реализации:** общие настройки, схемы, сборщик итогового состояния и проверяющий модуль уже используют `type`, `template_vmid` / `ostemplate` и высокоуровневый список `features`. Низкоуровневые VM/LXC-флаги остаются только в старом `deploy-guest` до его переработки.

#### 3.7.1. `type`

**Тип:** перечисление:

```text
vm
lxc
```

`type` определяет технический тип объекта Proxmox, создаваемого этим профилем.

Пример VM:

```yaml
debian-vm:
  type: vm
  template_vmid: 9000
```

Пример LXC:

```yaml
debian-lxc:
  type: lxc
  ostemplate: local:vztmpl/debian-13-standard
```

Дополнительные особенности профиля не создают новые технические типы.

Например профиль `debian-lxc-docker` всё равно имеет:

```yaml
type: lxc
```

а способность запускать вложенную среду выполнения контейнеров описывается через `features`.

#### 3.7.2. `template_vmid`

**Тип:** целое число от `100` до `9999`.

Параметр допустим только для профиля с:

```yaml
type: vm
```

Он определяет шаблон VM, из которого создаются VM этого профиля.

Пример:

```yaml
profiles:
  debian-vm:
    type: vm
    template_vmid: 9000
```

Для управляемой VM используется полное клонирование как фиксированное правило проекта.

Отдельного параметра `clone` в целевой модели нет.

Гостевой агент QEMU также является обязательной частью контракта каждой управляемой VM и не задаётся отдельным логическим полем профиля.

BIOS/UEFI наследуется от выбранного шаблона VM и отдельно профилем не переопределяется.

Если `template_vmid` совпадает с VMID создаваемого гостя, проверка должна завершаться ошибкой: VM не может клонироваться сама из себя.

#### 3.7.3. `ostemplate`

**Тип:** строка — селектор семейства Proxmox `vztmpl`.

Параметр допустим только для профиля с:

```yaml
type: lxc
```

Он определяет семейство системного образа LXC.

Пример:

```yaml
profiles:
  debian-lxc:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard
```

В Git хранится стабильный селектор семейства, а не конкретное имя архива конкретной версии.

Допустимо:

```text
local:vztmpl/debian-13-standard
```

Не допускаются шаблоны с подстановочными знаками, `latest`, `13.x`, `tbd` и конкретное имя загруженного архивного файла.

Все LXC, создаваемые универсальным контуром развёртывания, являются **непривилегированными**.

Это фиксированная политика проекта, поэтому отдельного параметра `unprivileged` в целевом профиле нет.

#### 3.7.4. `features`

**Тип:** необязательный список высокоуровневых возможностей профиля.

`features` используется тогда, когда конкретному классу гостя требуется дополнительная техническая подготовка на уровне Proxmox.

Первая поддерживаемая возможность профиля:

```text
container-host
```

Пример:

```yaml
profiles:
  debian-lxc-docker:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard
    features:
      - container-host
```

`container-host` означает:

> LXC технически подготовлен для запуска вложенной среды выполнения контейнеров.

Эта возможность не означает, что Docker уже установлен, и не привязана к конкретному продукту Docker.

В текущей реализации для LXC она разворачивается во внутренние Proxmox-настройки:

```text
unprivileged = true
nesting = true
keyctl = true
```

При этом `unprivileged=true` является общей политикой всех управляемых LXC, а `nesting` и `keyctl` добавляются именно для `container-host`.

Низкоуровневые параметры `nesting` и `keyctl` не являются публичными полями профиля и не задаются по отдельности.

Если конкретному LXC действительно нужно установить Docker, это задаётся отдельно в индивидуальном госте:

```yaml
profile: debian-lxc-docker

bootstrap:
  - docker
```

Таким образом:

```text
возможность профиля: container-host
→ LXC способен корректно запускать среду выполнения контейнеров

bootstrap: docker
→ Docker Engine действительно должен быть установлен внутри гостя
```

Если у LXC запрошена первоначальная подготовка `docker`, выбранный профиль должен содержать `container-host`. Иначе проверка должна завершаться ошибкой.

Список `features` сделан расширяемым: в будущем в него могут быть добавлены другие высокоуровневые технические возможности профиля без публикации низкоуровневых Proxmox-флагов в пользовательский контракт.

## 4. Правила и ограничения

Раздел 3 описывает смысл отдельных параметров. Здесь собраны только правила, которые связывают несколько параметров или источников состояния между собой.

### 4.1. Идентичность гостя и адресация

Для управляемых VM/LXC действуют следующие общие правила:

- VMID/CTID находится в диапазоне `100–999`;
- VMID уникален в репозитории;
- `vmid` и `name` должны совпадать с именем каталога `<VMID>-<name>`;
- административный IPv4 по умолчанию вычисляется из VMID и общей подсети;
- явно заданный `network.ipv4` должен находиться в общей подсети и не конфликтовать со шлюзом, адресом сети, широковещательным адресом или адресом другого гостя;
- префикс сети всегда берётся из `defaults.network.subnet` и индивидуально не задаётся.

Для подсети `A.B.0.0/16` используется правило:

```text
VMID XYZ
→ A.B.X.YZ
```

Например:

```text
311 + 192.168.0.0/16 → 192.168.3.11
```

Функциональная группировка VMID является соглашением проекта, а не отдельным машинным ограничением схемы:

| Диапазон | Назначение |
|---|---|
| `100–199` | сеть и базовая инфраструктура |
| `200–299` | Home Assistant и автоматика |
| `300–399` | прикладные, DevOps- и AI-сервисы |
| `400–499` | мониторинг и обслуживание |
| `500–599` | видео и камеры |
| `600–699` | временные и экспериментальные VM/LXC |
| `900–999` | устаревшие и служебные объекты |

Таблица перечисляет только уже закреплённые назначения. Отсутствие диапазона в таблице не делает его запрещённым. Проверяющий модуль не определяет назначение гостя по диапазону; для машинной проверки важны допустимый VMID, уникальность и соответствие имени каталога.

### 4.2. Участие в управляемом контуре

Поле `profile` определяет участие гостя в универсальной модели развёртывания.

Если `profile` указан:

- профиль должен существовать в `guests/defaults.yaml`;
- из профиля определяется тип VM/LXC;
- сборщик строит полное итоговое состояние;
- гость может передаваться универсальному контуру развёртывания.

Если `profile` отсутствует:

- объект может оставаться описанным в Git;
- полное итоговое состояние общим сборщиком не строится;
- универсальный контур развёртывания не должен считать объект управляемым.

Поля `management`, `bootstrap` и индивидуальное `pve_management` допустимы только для гостя с `profile`.

Для гостя с `profile` значение `pve_management` по умолчанию равно `true`:

- `true` — объект должен находиться в пуле PVE `managed` и доступен AI-агенту через PVE API/MCP в пределах выданных прав;
- `false` — объект не должен находиться в пуле `managed`, поэтому обычные PVE API/MCP-права AI-агента на него не распространяются.

`pve_management` не определяет административный SSH-доступ и не ограничивает права учётной записи `deployer`.

### 4.3. Совместимость VM и LXC

Тип гостя определяется полем `type` выбранного профиля. Параметры должны соответствовать этому типу.

| Правило | VM | LXC |
|---|---|---|
| `template_vmid` | обязателен | запрещён |
| `ostemplate` | запрещён | обязателен |
| `features` | запрещены | необязательны |
| `resources.cores` | обязателен | обязателен |
| `resources.memory_mb` | обязателен | обязателен |
| `resources.disk_size_gb` | обязателен | обязателен |
| `resources.swap_mb` | запрещён | обязателен |
| `resources.ballooning_mb` | необязателен | запрещён |

Дополнительно действуют два ограничения:

- VM не может использовать собственный VMID как `template_vmid`;
- если для LXC запрошен `bootstrap: docker`, выбранный профиль должен содержать возможность `container-host`.

Низкоуровневые параметры Proxmox, являющиеся внутренней реализацией профиля, не задаются непосредственно в индивидуальном `guest.yaml`.

### 4.4. Централизованные и индивидуальные параметры

Общие значения должны задаваться централизованно, если для конкретного гостя не требуется осознанное исключение.

| Параметр | Общее значение | Индивидуальное переопределение |
|---|---|---|
| `node` | да | разрешено |
| `protection` | да | разрешено |
| `pve_management` | да | разрешено |
| `boot.onboot` | да | разрешено |
| `resources.disk_storage` | да | разрешено |
| `network.bridge` | да | запрещено |
| `network.subnet` | да | запрещено |
| `network.gateway` | да | запрещено |
| `network.ipv4` | вычисляется | разрешено |

Списки `management` и `bootstrap` являются индивидуальными параметрами гостя: они не задаются в общих настройках или профилях.

Параметры профиля `type`, `template_vmid`, `ostemplate` и `features` задаются только в профиле и не повторяются в индивидуальном манифесте.

## 5. Проверка состояния

### 5.1. Схемы и общий сборщик итогового состояния

Используются три машинные схемы:

```text
schemas/guest.schema.yaml
→ исходный `guest.yaml`

schemas/guest-defaults.schema.yaml
→ `guests/defaults.yaml` и профили

schemas/guest-effective.schema.yaml
→ итоговое состояние
```

Схемы проверяют форму данных, допустимые значения и обязательные зависимости, которые можно выразить декларативно.

Общий сборщик итогового состояния:

```text
scripts/guest_config.py
```

отвечает за правила, требующие вычисления или объединения данных.

Проверяющий модуль и средство развёртывания должны использовать этот общий модуль, а не создавать собственную реализацию объединения, адресации или зависимостей первоначальной подготовки.

### 5.2. Проверка исходного и итогового состояния

Проверка выполняется в двух стадиях.

Сначала проверяются исходные файлы:

- формат `guests/defaults.yaml`;
- формат конкретного `guest.yaml`;
- допустимые поля и значения;
- отсутствие запрещённых неизвестных полей.

После этого сборщик итогового состояния строит итоговое состояние.

Затем проверяются:

- полнота итогового состояния;
- соответствие типу VM/LXC;
- обязательные ресурсы;
- сеть;
- контракт административного управления;
- параметры VM/LXC;
- корректность первоначальной подготовки.

Некоторые проверки нельзя выразить только YAML-схемой и выполняются программно.

### 5.3. Проверка репозитория

Основная команда проверки:

```bash
python scripts/validate_repo.py
```

Она проверяет не только отдельный YAML-файл, но и взаимосвязи между объектами проекта.

В частности, проверяются:

- соответствие `vmid` и `name` имени каталога;
- уникальность VMID;
- корректность профилей;
- корректность административной сети;
- вычисляемые и явно заданные IP;
- отсутствие конфликтующих адресов;
- допустимость переопределений;
- требования к гостям с `profile`;
- VM- и LXC-ограничения;
- корректность первоначальной подготовки;
- отсутствие секретоподобных полей и закрытых ключей.

Ошибка проверки означает, что состояние нельзя считать корректным входом для автоматического развёртывания.

Предупреждение означает состояние, которое формально допустимо, но требует внимания, например осознанное отклонение IP от формулы VMID или избыточное переопределение общего значения.
