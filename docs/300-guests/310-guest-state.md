# Требуемое состояние гостевой системы

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить источники, параметры, правила построения и проверки требуемого состояния VM/LXC.

Этот документ отвечает на вопрос:

> Как в проекте описывается требуемое состояние конкретной гостевой системы и как из исходных файлов получается итоговое состояние?

Документ не описывает порядок применения изменений к Proxmox. Контракт планирования и применения (`PLAN/APPLY`) и жизненный цикл команды `deploy-guest` относятся к отдельной спецификации развёртывания.

## 1. Назначение и модель состояния

### 1.1. Назначение документа

Для управляемой VM/LXC проект хранит не готовую конфигурацию Proxmox, а исходное описание требуемого состояния.

Оно должно быть:

- компактным;
- проверяемым;
- воспроизводимым;
- однозначно преобразуемым в итоговое состояние;
- пригодным для сравнения с фактическим состоянием Proxmox.

Основной индивидуальный файл гостя:

```text
guests/<VMID>-<name>/guest.yaml
```

Общие значения и профили находятся в:

```text
guests/defaults.yaml
```

Машинные ограничения формата задаются схемами в `schemas/`.

### 1.2. Что считается требуемым состоянием

Требуемое состояние определяет, каким должен быть объект VM/LXC с точки зрения проекта.

К нему относятся, в частности:

- идентификатор и имя;
- тип гостевой системы;
- размещение;
- процессор, память и диск;
- сеть;
- правила запуска;
- контур административного управления;
- явно запрошенная первоначальная подготовка;
- параметры, специфичные для VM или LXC.

Работающая VM/LXC в Proxmox хранит фактическое состояние, но сама по себе не становится источником требований.

Изменение требуемого состояния выполняется через соответствующие файлы проекта.

### 1.3. Исходное и итоговое состояние

В проекте различаются два представления состояния.

**Исходное состояние** — компактные данные, которые человек редактирует в Git:

```text
guests/defaults.yaml
+
профиль
+
guests/<VMID>-<name>/guest.yaml
```

**Итоговое состояние** — полное состояние после наследования, объединения, нормализации и вычисления производных значений.

Общая схема:

```text
исходные данные
→ проверка по схеме
→ сборщик итогового состояния
→ итоговое состояние
→ проверка итогового состояния
```

Средства проверки и развёртывания должны использовать одно и то же итоговое состояние и не реализовывать собственные параллельные правила его построения.

## 2. Источники и построение состояния

### 2.1. Источники состояния

Требуемое состояние строится из трёх основных источников.

`guests/defaults.yaml` содержит:

- общие значения проекта;
- параметры, одинаковые для большинства гостей;
- определения профилей VM/LXC.

Профиль определяет типовую основу конкретного класса гостевых систем.

Например:

```yaml
profiles:
  debian-vm:
    type: vm
    template_vmid: 9000

  debian-lxc:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard

  debian-lxc-docker:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard
    features:
      - container-host
```

Индивидуальный `guest.yaml` содержит параметры конкретной VM/LXC и осознанные отклонения от общих значений.

Обычный гость с `profile` не должен копировать в свой `guest.yaml` значения, которые уже однозначно приходят из `defaults.yaml` или выбранного профиля.

### 2.2. Порядок объединения и переопределения

Порядок построения состояния фиксирован:

```text
общие настройки
→ профиль
→ guest.yaml
→ специальные правила
→ вычисляемые значения
→ итоговое состояние
```

Словари объединяются рекурсивно.

Более позднее простое значение заменяет более раннее.

Избыточное повторение унаследованного значения нежелательно: оно усложняет чтение манифеста и может скрывать последующие изменения общих настроек.

### 2.3. Специальные и вычисляемые значения

Не все поля следуют обычному наследованию.

Некоторые параметры разрешено задавать только конкретному гостю.

К таким индивидуальным возможностям относятся элементы списков `management` и `bootstrap`.

Они не должны появляться в общих настройках или профилях.

Некоторые значения вообще не хранятся в обычном `guest.yaml`, а вычисляются из других параметров.

Главный пример — административный IPv4.

Если индивидуальное переопределение отсутствует, адрес вычисляется из VMID и центральной административной подсети.

### 2.4. Итоговое состояние

Общий сборщик итогового состояния проекта:

```text
scripts/guest_config.py
```

строит однозначное итоговое состояние.

Для гостя с `profile` итоговое состояние должно содержать все обязательные параметры, необходимые следующим слоям проекта.

В частности, сборщик итогового состояния:

- объединяет общие настройки, профиль и индивидуальный манифест;
- нормализует список индивидуальных возможностей административного управления;
- вычисляет административный IP;
- проверяет и нормализует запрошенную первоначальную подготовку;
- возвращает запрошенные инструменты первоначальной подготовки в каноническом порядке.

Машинный формат итогового состояния проверяется схемой:

```text
schemas/guest-effective.schema.yaml
```

Итоговое состояние является интерфейсом между описанием гостя и средствами, которые сравнивают или применяют это состояние.

## 3. Параметры гостевой системы

Этот раздел является справочником полей состояния. Здесь описывается только назначение параметров и их формат.

Правила обязательности, наследования, совместимости и взаимных зависимостей собраны в разделе 4.

### 3.1. Основные параметры

#### 3.1.1. `schema_version`

**Тип:** целое число.

Версия общего контракта состояния гостевой системы.

Текущее значение:

```yaml
schema_version: 10
```

Один номер версии используется для `guest.yaml`, `guests/defaults.yaml` и итогового состояния.

#### 3.1.2. `vmid`

**Тип:** целое число.

Идентификатор объекта Proxmox: VMID для VM или CTID для LXC.

Пример:

```yaml
vmid: 311
```

VMID также используется проектом при формировании имени каталога и вычислении административного IPv4.

#### 3.1.3. `name`

**Тип:** строка.

Короткое машинное имя гостевой системы.

Пример:

```yaml
name: dev-services
```

Имя используется в каталоге гостя и при идентификации объекта внутри проекта.

#### 3.1.4. `description`

**Тип:** строка.

Краткое понятное человеку описание назначения гостевой системы.

Пример:

```yaml
description: Сервисы разработки и автоматизации
```

#### 3.1.5. `profile`

**Тип:** строка.

Имя профиля из `guests/defaults.yaml`.

Пример:

```yaml
profile: debian-lxc-docker
```

Профиль выбирает типовую основу гостя: его тип, источник создания и дополнительные технические возможности.

#### 3.1.6. `node`

**Тип:** строка.

Имя PVE-узла, на котором должен находиться гость.

Пример:

```yaml
node: pve
```

#### 3.1.7. `protection`

**Тип:** логическое значение.

Желаемое состояние встроенной защиты объекта Proxmox от случайных разрушительных операций.

Пример:

```yaml
protection: true
```

Параметр относится к объекту Proxmox и не определяет права внутри гостевой ОС.

#### 3.1.8. `pve_management`

**Тип:** логическое значение.

Определяет участие гостя в контуре управления объектами Proxmox через PVE API/MCP для AI-агента.

Пример:

```yaml
pve_management: true
```

Параметр не определяет административный SSH-доступ.

### 3.2. Ресурсы

Раздел `resources` описывает вычислительные ресурсы конкретной VM/LXC.

Пример VM:

```yaml
resources:
  cores: 2
  memory_mb: 4096
  ballooning_mb: 2048
  disk_size_gb: 32
```

Пример LXC:

```yaml
resources:
  cores: 2
  memory_mb: 4096
  swap_mb: 1024
  disk_size_gb: 32
```

#### 3.2.1. `resources.cores`

**Тип:** целое число.

Количество процессорных ядер, доступных гостю.

#### 3.2.2. `resources.memory_mb`

**Тип:** целое число, MiB.

Объём оперативной памяти гостя.

#### 3.2.3. `resources.ballooning_mb`

**Тип:** целое число, MiB.

Параметр динамического выделения памяти VM.

Если отдельное значение не задано, проект не задаёт самостоятельного требования к динамическому выделению памяти.

#### 3.2.4. `resources.swap_mb`

**Тип:** целое число, MiB.

Объём подкачки LXC.

Значение `0` означает отсутствие подкачки.

#### 3.2.5. `resources.disk_size_gb`

**Тип:** целое число, GiB.

Требуемый размер основного диска VM или корневой файловой системы LXC.

#### 3.2.6. `resources.disk_storage`

**Тип:** строка.

Идентификатор хранилища PVE для основного диска VM или корневой файловой системы LXC.

Пример:

```yaml
resources:
  disk_storage: local-lvm
```

### 3.3. Сеть

Раздел `network` описывает административное сетевое подключение гостя.

#### 3.3.1. `network.bridge`

**Тип:** строка.

Сетевой мост PVE для основного административного интерфейса.

Пример общего значения:

```yaml
network:
  bridge: vmbr0
```

#### 3.3.2. `network.subnet`

**Тип:** сеть IPv4.

Административная подсеть проекта.

Пример:

```yaml
network:
  subnet: 192.168.0.0/16
```

#### 3.3.3. `network.gateway`

**Тип:** адрес IPv4.

Шлюз административной сети.

Пример:

```yaml
network:
  gateway: 192.168.1.1
```

#### 3.3.4. `network.ipv4`

**Тип:** адрес IPv4.

Индивидуальный административный адрес гостя, если требуется отклонение от автоматической VMID-адресации.

Пример исходного значения:

```yaml
network:
  ipv4: 192.168.8.50
```

В итоговом состоянии адрес содержит префикс общей подсети.

### 3.4. Запуск

#### 3.4.1. `boot.onboot`

**Тип:** логическое значение.

Определяет, должен ли Proxmox автоматически запускать гостя при запуске PVE-узла.

Пример:

```yaml
boot:
  onboot: true
```

### 3.5. Административное управление (`management`)

`management` — список дополнительных возможностей административного управления конкретного гостя.

Пример:

```yaml
management:
  - ssh_identity
  - project_repo_read
```

#### 3.5.1. `ssh_identity`

Запрашивает для гостя собственную исходящую пару SSH-ключей для административного доступа к другим управляемым гостям.

Это не ключ, которым PVE подключается к самому гостю.

#### 3.5.2. `project_repo_read`

Запрашивает для гостя управляемый доступ к закрытому репозиторию проекта `zsergeyru/proxmox` только для чтения.

Эта возможность не устанавливает Git и не предоставляет произвольные учётные данные Git.

### 3.6. Первоначальная подготовка (`bootstrap`)

`bootstrap` — список инфраструктурных инструментов, которые требуется установить непосредственно в гостевую ОС при первоначальной подготовке.

Поддерживаемые значения:

```text
git
docker
ansible
```

#### 3.6.1. `git`

Требует установленный и работающий клиент Git.

#### 3.6.2. `docker`

Требует установленный Docker Engine вместе с Docker Compose.

#### 3.6.3. `ansible`

Требует установленный Ansible, в базовой реализации — `ansible-core`.

### 3.7. Параметры профилей VM и LXC

Профили находятся в `guests/defaults.yaml` и описывают типовую техническую основу класса гостей.

Пример:

```yaml
profiles:
  debian-vm:
    type: vm
    template_vmid: 9000

  debian-lxc-docker:
    type: lxc
    ostemplate: local:vztmpl/debian-13-standard
    features:
      - container-host
```

Имя профиля предназначено для человека и обычно отражает ОС, тип гостя и дополнительную возможность, например `debian-vm` или `debian-lxc-docker`. Машинная логика определяется полями профиля, а не разбором его имени.

#### 3.7.1. `type`

**Тип:** перечисление.

Поддерживаемые значения:

```text
vm
lxc
```

Определяет технический тип объекта Proxmox.

#### 3.7.2. `template_vmid`

**Тип:** целое число.

VMID шаблона, используемого как источник для профиля VM.

#### 3.7.3. `ostemplate`

**Тип:** строка.

Селектор семейства системного образа LXC.

Пример:

```text
local:vztmpl/debian-13-standard
```

#### 3.7.4. `features`

**Тип:** список.

Высокоуровневые технические возможности профиля.

Сейчас поддерживается:

```text
container-host
```

`container-host` означает, что LXC технически подготовлен для запуска вложенной среды выполнения контейнеров.

## 4. Правила и ограничения

Раздел 3 описывает поля по отдельности. Здесь собраны правила, определяющие допустимость, обязательность, наследование и взаимные зависимости этих полей.

### 4.1. Общий контракт и идентичность гостя

Для текущего контракта действуют следующие правила:

- `schema_version` равен `10`;
- исходный `guest.yaml` содержит `schema_version`, `vmid`, `name` и `description`;
- VMID/CTID находится в диапазоне `100–999`;
- VMID уникален в репозитории;
- `name` соответствует шаблону `[a-z0-9][a-z0-9-]*`;
- `vmid` и `name` совпадают с именем каталога `<VMID>-<name>`;
- `description` является непустой строкой.

Функциональная группировка VMID является соглашением проекта, а не отдельным ограничением схемы:

| Диапазон | Назначение |
|---|---|
| `100–199` | сеть и базовая инфраструктура |
| `200–299` | Home Assistant и автоматика |
| `300–399` | прикладные, DevOps- и AI-сервисы |
| `400–499` | мониторинг и обслуживание |
| `500–599` | видео и камеры |
| `600–699` | временные и экспериментальные VM/LXC |
| `900–999` | устаревшие и служебные объекты |

Отсутствие диапазона в таблице не делает его запрещённым. Проверяющий модуль не определяет назначение гостя по номеру VMID.

Для гостя с `profile` маркеры незавершённости в `description`, например `todo`, `tbd` или `unknown`, вызывают предупреждение.

### 4.2. Источники, наследование и переопределения

Итоговое состояние строится в порядке:

```text
общие настройки
→ профиль
→ guest.yaml
→ специальные правила
→ вычисляемые значения
→ итоговое состояние
```

Основные источники параметров:

| Параметр | Общие настройки | Профиль | `guest.yaml` |
|---|---:|---:|---:|
| `schema_version` | да | нет | да |
| `vmid`, `name`, `description` | нет | нет | да |
| `profile` | нет | нет | да |
| `node` | да | нет | допускается переопределение |
| `protection` | да | нет | допускается переопределение |
| `pve_management` | да | нет | допускается переопределение |
| `resources.cores` | нет | нет | да |
| `resources.memory_mb` | нет | нет | да |
| `resources.ballooning_mb` | нет | нет | да |
| `resources.swap_mb` | нет | нет | да |
| `resources.disk_size_gb` | нет | нет | да |
| `resources.disk_storage` | да | нет | допускается переопределение |
| `network.bridge` | да | нет | нет |
| `network.subnet` | да | нет | нет |
| `network.gateway` | да | нет | нет |
| `network.ipv4` | вычисляется | нет | допускается переопределение |
| `boot.onboot` | да | нет | допускается переопределение |
| `management` | нет | нет | да |
| `bootstrap` | нет | нет | да |
| `type`, `template_vmid`, `ostemplate`, `features` | нет | да | нет |

Повторение в `guest.yaml` уже унаследованного значения считается избыточным.

Индивидуальное переопределение `node`, `protection`, `pve_management` или `resources.disk_storage` является допустимым, но проверяющий модуль отмечает отклонение от общего значения предупреждением.

### 4.3. Участие в управляемом контуре

Поле `profile` является признаком участия гостя в универсальной модели построения и применения состояния.

Если `profile` указан:

- профиль должен существовать;
- в исходном манифесте должен существовать раздел `resources`;
- сборщик строит полное итоговое состояние;
- гость может участвовать в универсальном контуре развёртывания.

Если `profile` отсутствует:

- объект может оставаться описанным в Git;
- полное итоговое состояние общим сборщиком не строится;
- универсальный контур развёртывания не должен считать объект управляемым.

Индивидуальные поля `management`, `bootstrap` и `pve_management` требуют наличия `profile`.

Для любого гостя с `profile` административный SSH использует фиксированный проектный контракт:

```text
root:22
```

Поля пользователя и порта SSH в `guest.yaml` не задаются.

`pve_management` относится только к управлению объектом на уровне Proxmox:

- `true` — объект должен находиться в пуле PVE `managed`, и права AI-агента на PVE API/MCP распространяются на него через ACL этого пула;
- `false` — объект не должен находиться в пуле `managed`, и обычные PVE API/MCP-права AI-агента на него не распространяются.

`pve_management` не отключает административный SSH и не ограничивает отдельные PVE-права учётной записи `deployer`.

### 4.4. Совместимость VM и LXC

Тип гостя определяется полем `type` выбранного профиля.

| Правило | VM | LXC |
|---|---|---|
| `template_vmid` | обязателен | запрещён |
| `ostemplate` | запрещён | обязателен |
| `features` | запрещены | необязательны в профиле |
| `resources.cores` | обязателен | обязателен |
| `resources.memory_mb` | обязателен | обязателен |
| `resources.disk_size_gb` | обязателен | обязателен |
| `resources.swap_mb` | запрещён | обязателен |
| `resources.ballooning_mb` | необязателен | запрещён |

Дополнительно:

- `template_vmid` находится в диапазоне `100–9999`;
- VM не может использовать собственный VMID как `template_vmid`;
- селектор `ostemplate` задаёт семейство образа, а не конкретное имя архива; конкретный архив, `latest`, шаблоны с подстановочными знаками и неопределённые значения не допускаются;
- все управляемые LXC создаются непривилегированными;
- возможность `container-host` для LXC означает внутренние настройки `nesting=true` и `keyctl=true`;
- если для LXC запрошен `bootstrap: docker`, выбранный профиль должен содержать `container-host`;
- для управляемой VM поле `template_vmid` определяет источник создания; способ клонирования и проверки готовности относится к контракту развёртывания.

### 4.5. Ограничения ресурсов

Для гостя с `profile` исходный манифест содержит:

```text
resources.cores
resources.memory_mb
resources.disk_size_gb
```

Числовые ограничения:

- `resources.cores >= 1`;
- `resources.memory_mb >= 256`;
- `resources.disk_size_gb >= 1`;
- `resources.ballooning_mb >= 0`;
- `resources.swap_mb >= 0`;
- `resources.ballooning_mb <= resources.memory_mb`.

В итоговом состоянии также обязательно `resources.disk_storage`. Обычное значение берётся из общих настроек; индивидуальное хранилище допускается как явное переопределение.

Ресурсы конкретного экземпляра не задаются в профиле.

### 4.6. Сеть и адресация

Общие сетевые параметры задаются централизованно:

```text
network.bridge
network.subnet
network.gateway
```

Индивидуальный `guest.yaml` может задавать только `network.ipv4`.

Текущий базовый контракт использует одну административную сеть IPv4 `/16`.

Если индивидуальный адрес не задан, он вычисляется из VMID:

```text
VMID XYZ + A.B.0.0/16
→ A.B.X.YZ
```

Например:

```text
311 + 192.168.0.0/16
→ 192.168.3.11
```

Индивидуальный `network.ipv4` в исходном манифесте задаётся без префикса. Префикс берётся из `network.subnet`.

Адрес должен:

- находиться внутри административной подсети;
- не совпадать со шлюзом;
- не быть адресом сети или широковещательным адресом;
- не дублировать адрес другого гостя.

Если индивидуальный адрес совпадает с автоматически вычисленным, такое переопределение считается избыточным. Если адрес отличается, это допустимое осознанное исключение.

Несколько интерфейсов, индивидуальные сетевые мосты и шлюзы, VLAN, MTU, ограничения скорости, отдельные параметры DNS и IPv6 в текущий базовый контракт не входят.

### 4.7. Запуск, административные возможности и первоначальная подготовка

Общие значения:

```yaml
defaults:
  node: pve
  protection: true
  pve_management: true
  boot:
    onboot: true
  resources:
    disk_storage: local-lvm
```

`boot.onboot` описывает только постоянную политику автоматического запуска вместе с PVE. Запуск гостя непосредственно после создания не является параметром состояния.

Список `management`:

- задаётся только индивидуально;
- не наследуется;
- не может быть пустым, если поле присутствует;
- не содержит дубликатов;
- допускает только `ssh_identity` и `project_repo_read`.

Список `bootstrap`:

- задаётся только индивидуально;
- не наследуется;
- не может быть пустым, если поле присутствует;
- не содержит дубликатов;
- допускает только `git`, `docker` и `ansible`.

Элементы `bootstrap` независимы: `ansible` не требует `git` или `docker`.

### 4.8. Граница состояния и развёртывания

Этот документ определяет **каким должен быть гость**, но не описывает пошаговый алгоритм применения изменений.

К контракту состояния не относятся:

- порядок выполнения операций создания и изменения;
- способ клонирования VM из шаблона и проверка её готовности;
- политика применения изменения размера диска;
- запуск гостя сразу после создания;
- ожидание готовности SSH;
- порядок установки базовых пакетов;
- последовательность применения и удаления дополнительных административных возможностей;
- восстановление после частично выполненного развёртывания.

Эти вопросы относятся к отдельной спецификации средства развёртывания и не должны дублироваться в описании параметров состояния.

## 5. Проверка состояния

### 5.1. Схемы и общий сборщик итогового состояния

Используются три машинные схемы:

```text
schemas/guest.schema.yaml
→ исходный `guest.yaml`

schemas/guest-defaults.schema.yaml
→ `guests/defaults.yaml` и профили

schemas/guest-effective.schema.yaml
→ итоговое состояние
```

Схемы проверяют форму данных, допустимые значения и обязательные зависимости, которые можно выразить декларативно.

Общий сборщик итогового состояния:

```text
scripts/guest_config.py
```

отвечает за правила, требующие вычисления или объединения данных.

Проверяющий модуль и средство развёртывания должны использовать этот общий модуль, а не создавать собственную реализацию объединения, адресации или зависимостей первоначальной подготовки.

### 5.2. Проверка исходного и итогового состояния

Проверка выполняется в двух стадиях.

Сначала проверяются исходные файлы:

- формат `guests/defaults.yaml`;
- формат конкретного `guest.yaml`;
- допустимые поля и значения;
- отсутствие запрещённых неизвестных полей.

После этого сборщик итогового состояния строит итоговое состояние.

Затем проверяются:

- полнота итогового состояния;
- соответствие типу VM/LXC;
- обязательные ресурсы;
- сеть;
- контракт административного управления;
- параметры VM/LXC;
- корректность первоначальной подготовки.

Некоторые проверки нельзя выразить только YAML-схемой и выполняются программно.

### 5.3. Проверка репозитория

Основная команда проверки:

```bash
python scripts/validate_repo.py
```

Она проверяет не только отдельный YAML-файл, но и взаимосвязи между объектами проекта.

В частности, проверяются:

- соответствие `vmid` и `name` имени каталога;
- уникальность VMID;
- корректность профилей;
- корректность административной сети;
- вычисляемые и явно заданные IP;
- отсутствие конфликтующих адресов;
- допустимость переопределений;
- требования к гостям с `profile`;
- VM- и LXC-ограничения;
- корректность первоначальной подготовки;
- отсутствие секретоподобных полей и закрытых ключей.

Ошибка проверки означает, что состояние нельзя считать корректным входом для автоматического развёртывания.

Предупреждение означает состояние, которое формально допустимо, но требует внимания, например осознанное отклонение IP от формулы VMID или избыточное переопределение общего значения.
