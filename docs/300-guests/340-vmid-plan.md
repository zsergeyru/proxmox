# План нумерации VMID / CTID

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** задать единую функциональную нумерацию постоянных VM и LXC проекта.

Этот документ отвечает на вопрос:

> Как выбирается VMID или CTID новой постоянной гостевой системы и какие диапазоны закреплены за разными областями проекта?

Документ описывает целевое правило нумерации. Фактические номера уже существующих гостей могут временно отличаться до отдельной перенумерации.

## 1. Правило номера

Для постоянных гостевых систем используется трёхзначный VMID/CTID:

~~~text
XYZ

X — функциональная область
Y — служба внутри области
Z — экземпляр службы
~~~

Основной экземпляр службы получает номер с последней цифрой `0`.

Примеры:

~~~text
210 — основной экземпляр службы
211 — второй экземпляр той же службы
212 — третий экземпляр той же службы
~~~

Поэтому основные VM/LXC обычно получают VMID/CTID, кратный `10`.

Номера `100`, `200`, `300` и другие номера, кратные `100`, не используются для обычных гостевых систем. Они обозначают границы функциональных областей.

## 2. Функциональные области

| Диапазон | Назначение |
|---|---|
| `100–190` | сеть и сетевые службы |
| `200–290` | умный дом и домашняя автоматизация |
| `300–390` | приложения и разработка |
| `400–490` | AI и голосовые службы |
| `500–590` | видео и наблюдение |
| `600–699` | резерв: новые гости не размещаются без отдельного пересмотра нумерации |
| `700–799` | резерв: новые гости не размещаются без отдельного пересмотра нумерации |
| `800–899` | резерв для будущих функциональных областей |
| `900–999` | системные службы и управление инфраструктурой; основные роли — `910`, `920`, `930`, специальный временный гость — `990` |

В области AI закреплён основной управляющий гость:

~~~text
410 — ai-control
~~~

Номера `411–419` резервируются для дополнительных или проверочных экземпляров AI Control.

Остальные номера диапазона `400–490` распределяются между отдельными AI- и голосовыми службами по мере утверждения их назначения.

В области приложений закреплён основной гость:

~~~text
340 — photo-archive (Immich)
~~~

Номера `341–349` резервируются для дополнительных экземпляров этой службы.

## 3. Системные службы и управление инфраструктурой

Диапазон `900–999` объединяет системные службы обслуживания инфраструктуры, резервирование, мониторинг и управляющий контур. Резервирование и мониторинг не занимают отдельных функциональных сотен номеров. Основные экземпляры получают номера, кратные `10`, дополнительные экземпляры — следующие номера той же десятки.

Закреплены три постоянные роли и один временный технический объект:

~~~text
910 — infra-manager (управление и развёртывание)
920 — backup-manager (резервное копирование UrBackup)
930 — monitoring (мониторинг инфраструктуры)
990 — bootstrap-runner (первичная установка и восстановление 910)
~~~

`920 backup-manager` — целевой отдельный исполнитель резервирования PVE. Он развёртывается и обновляется через 910, но выполняет задания независимо от него. Автономный UrBackup Server на физическом NAS не имеет VMID. Выбор UrBackup и два независимых назначения закреплены в [решениях о резервировании](../600-storage/690-decisions.md). Существование записи в плане не означает, что гость уже создан.

`930 monitoring` — целевая отдельная система наблюдения за инфраструктурой, включая 910 и 920. Прежний каталог `infrastructure/guests/401-monitoring/` содержит исторический VMID `401`: до отдельной проверки физического PVE и безопасной миграции этот манифест не переименовывается и существующий объект не перенумеровывается автоматически. Новому экземпляру мониторинга назначается `930`.

`910 infra-manager` — постоянный управляющий LXC проекта.

`infra-manager` является ролью гостя, а `910` — текущим назначенным VMID. Номер не является признаком роли и не должен использоваться как единственный способ определить управляющий гость в программной логике. Целевым источником VMID и сетевого адреса является машинное описание самого гостя.

В нём выполняются средства, через которые создаётся, изменяется, обслуживается и удаляется управляемая инфраструктура. Сам 910 имеет обычное описание LXC, но его объект Proxmox принадлежит отдельному первоначальному состоянию OpenTofu и исключён из постоянного состояния infra-manager.

Текущая реализация ещё содержит несколько технических привязок к числу `910`. Это считается ограничением реализации, а не частью схемы нумерации; целевое правило зафиксировано в локальном документе решений infra-manager.

`990 bootstrap-runner` — временный LXC первоначального развёртывания. Он создаётся только для создания или полного восстановления 910, владеет отдельным состоянием OpenTofu только для VMID 910 и удаляется после подтверждения готовности 910. 990 не является постоянной службой и не входит в обычный пул управляемых гостей.

Номера `911–919` резервируются для дополнительных или проверочных экземпляров 910, `921–929` — для 920, `931–939` — для мониторинга 930. Номера `940–989` свободны для других системных служб. Номера `991–999` резервируются для дополнительных временных технических объектов первоначального контура, если они когда-либо понадобятся.

## 4. Технические объекты

Четырёхзначные технические VMID не входят в функциональную трёхзначную нумерацию постоянных служб.

Например:

~~~text
9000 — базовый шаблон Debian VM
~~~

Такие номера предназначены для шаблонов, сборочных VM и других технических объектов, которые не являются постоянными прикладными гостями.

Технические объекты не должны занимать номера из функционального диапазона `100–990`.

## 5. Применение правила

Этот документ задаёт целевую нумерацию проекта.

Новый постоянный гость должен получать номер из диапазона, соответствующего его основной функции. Для новых средств резервирования и мониторинга используются десятки `920` и `930`, а не зарезервированные `600–699`/`700–799` и не исторический `401`.

Статус «резерв» относится к номерам VMID/CTID, а не к каталогам документации: разделы `docs/600-storage/` и `docs/700-security/` сохраняют свои номера и назначения.

Если существующий каталог в `infrastructure/guests/` или фактическая VM/LXC пока имеет номер, не соответствующий этому правилу, это считается переходным состоянием.

Перенумерация существующих объектов выполняется отдельно, потому что изменение VMID/CTID может затрагивать:

- каталог гостя;
- `guest.yaml`;
- сетевую адресацию;
- состояние OpenTofu;
- ссылки из других частей проекта;
- фактический объект в Proxmox.

Само наличие целевого номера в этом документе не означает автоматическую перенумерацию существующего объекта.
