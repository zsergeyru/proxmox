# Справочник `guest.yaml`

**Тип:** справочник  
**Статус:** действующий  
**Назначение:** дать точное описание полей индивидуального файла `guest.yaml`: их типа, обязательности, источника значения и ограничений.

Этот документ отвечает на вопрос:

> Что можно записать в `guest.yaml` конкретной VM/LXC и что означает каждое поле?

Правила объединения `defaults`, профиля и `guest.yaml` описаны в `310-guest-state.md`. Здесь эти правила не повторяются, а для каждого поля указывается только то, что нужно для правильного заполнения манифеста.

## 1. Общий контракт файла

Каждая гостевая система имеет индивидуальный файл:

~~~text
infrastructure/guests/<VMID>-<name>/guest.yaml
~~~

Файл содержит только поля, разрешённые схемой проекта.

Неизвестные поля запрещены.

Для любого `guest.yaml` обязательны:

~~~text
schema_version
vmid
name
description
~~~

Обычный гость, который участвует в общем управляемом контуре, дополнительно имеет:

~~~text
profile
resources
~~~

Для гостя с `profile` в `resources` обязательны:

~~~text
cores
memory_mb
disk_size_gb
~~~

Некоторые значения могут не присутствовать в `guest.yaml`, потому что приходят из общих настроек или вычисляются автоматически.

Точное построение итогового состояния описано в `310-guest-state.md`.

## 2. Краткий справочник полей

| Поле | Тип | В `guest.yaml` | Значение по умолчанию / источник | Назначение |
|---|---|---|---|---|
| `schema_version` | целое число | обязательно | нет | версия контракта |
| `vmid` | целое число | обязательно | нет | VMID/CTID гостя |
| `name` | строка | обязательно | нет | машинное имя |
| `description` | строка | обязательно | нет | понятное описание |
| `profile` | строка | для обычного управляемого гостя | нет | выбор типа и технической основы |
| `node` | строка | необязательно | общие настройки | PVE-узел |
| `protection` | логическое значение | необязательно | общие настройки | защита объекта Proxmox |
| `pve_management` | логическое значение | необязательно, только с `profile` | общие настройки | участие объекта в управляемом PVE-контуре |
| `resources.cores` | целое число | обязательно с `profile` | нет | процессорные ядра |
| `resources.memory_mb` | целое число | обязательно с `profile` | нет | оперативная память |
| `resources.ballooning_mb` | целое число | только VM, необязательно | нет | динамическая память VM |
| `resources.swap_mb` | целое число | для LXC обязательно | нет | подкачка LXC |
| `resources.disk_size_gb` | целое число | обязательно с `profile` | нет | размер основного диска |
| `resources.disk_storage` | строка | необязательно | общие настройки | хранилище основного диска |
| `network.ipv4` | IPv4 без префикса или `dhcp` | необязательно | вычисляется из VMID | режим административной адресации |
| `boot.onboot` | логическое значение | необязательно | общие настройки | автоматический запуск с PVE |
| `management` | список | необязательно, только с `profile` | пустой список | дополнительные возможности управления |

Поля профиля `type`, `template_vmid`, `ostemplate` и `features` в `guest.yaml` не задаются.

## 3. Основные поля

### 3.1. `schema_version`

**Тип:** целое число.  
**Обязательно:** да.  
**Допустимое значение:** `11`.  
**Наследование:** нет.

Пример:

~~~yaml
schema_version: 11
~~~

Поле определяет версию контракта данных.

Одинаковая версия используется для индивидуального манифеста, общих настроек и итогового состояния.

### 3.2. `vmid`

**Тип:** целое число.  
**Обязательно:** да.  
**Допустимый диапазон:** `100–999`.  
**Наследование:** нет.

Пример:

~~~yaml
vmid: 311
~~~

Это VMID для виртуальной машины или CTID для LXC.

Значение должно совпадать с числовой частью имени каталога:

~~~text
311-dev-services/
^^^
~~~

VMID должен быть уникальным среди гостевых систем проекта.

Он также используется для автоматического вычисления административного IPv4, если адрес не задан явно.

Правила распределения номеров по функциональным областям находятся в `340-vmid-plan.md`.

### 3.3. `name`

**Тип:** строка.  
**Обязательно:** да.  
**Наследование:** нет.

Допустимы строчные латинские буквы, цифры и дефис.

Имя должно соответствовать правилу:

~~~text
[a-z0-9][a-z0-9-]*
~~~

Пример:

~~~yaml
name: dev-services
~~~

Значение должно совпадать с частью имени каталога после VMID:

~~~text
311-dev-services/
    ^^^^^^^^^^^^
~~~

### 3.4. `description`

**Тип:** непустая строка.  
**Обязательно:** да.  
**Наследование:** нет.

Пример:

~~~yaml
description: Сервисы разработки и автоматизации
~~~

Поле предназначено для человека и кратко объясняет назначение гостя.

Для обычного гостя с `profile` маркеры незавершённости вроде `todo`, `tbd`, `pending` или `unknown` вызывают предупреждение проверки.

### 3.5. `profile`

**Тип:** строка.  
**Обязательно:** для обычного управляемого гостя.  
**Наследование:** нет.

Пример:

~~~yaml
profile: debian-lxc-docker
~~~

Значение должно совпадать с именем существующего профиля в:

~~~text
infrastructure/guests/defaults.yaml
~~~

Профиль определяет тип гостя и его техническую основу.

Наличие `profile` включает гостя в общую модель построения итогового состояния.

Отсутствие `profile` означает, что объект имеет специальный жизненный цикл и общий сборщик не строит для него обычное итоговое состояние.

### 3.6. `node`

**Тип:** непустая строка.  
**Обязательно в `guest.yaml`:** нет.  
**Обычный источник:** общие настройки.  
**Переопределение:** допускается.

Пример:

~~~yaml
node: pve
~~~

Поле задаёт PVE-узел, на котором должен находиться объект.

Для обычного гостя его обычно не нужно указывать индивидуально, если используется общее значение проекта.

Явное отклонение от общего значения отмечается предупреждением.

### 3.7. `protection`

**Тип:** логическое значение.  
**Обязательно в `guest.yaml`:** нет.  
**Обычный источник:** общие настройки.  
**Переопределение:** допускается.

Пример:

~~~yaml
protection: true
~~~

Поле задаёт требуемое состояние встроенной защиты объекта Proxmox от случайных разрушительных операций.

Оно не описывает права пользователей и не заменяет правила безопасности.

Явное отклонение от общего значения отмечается предупреждением.

### 3.8. `pve_management`

**Тип:** логическое значение.  
**Обязательно в `guest.yaml`:** нет.  
**Обычный источник:** общие настройки.  
**Можно задавать:** только гостю с `profile`.

Пример:

~~~yaml
pve_management: true
~~~

Поле обозначает требуемое участие объекта в управляемом PVE-контуре проекта.

Конкретные права API, устройство PVE-пулов и полномочия управляющих компонентов не определяются этим справочником и описываются в разделе безопасности.

Явное отклонение от общего значения отмечается предупреждением.

## 4. Ресурсы

Раздел `resources` описывает ресурсы конкретного экземпляра VM/LXC.

Для гостя с `profile` сам раздел обязателен.

Минимальная форма:

~~~yaml
resources:
  cores: 2
  memory_mb: 4096
  disk_size_gb: 32
~~~

### 4.1. `resources.cores`

**Тип:** целое число.  
**Минимум:** `1`.  
**Обязательно:** для гостя с `profile`.  
**Наследование:** нет.

Количество процессорных ядер, доступных гостю.

### 4.2. `resources.memory_mb`

**Тип:** целое число, MiB.  
**Минимум:** `256`.  
**Обязательно:** для гостя с `profile`.  
**Наследование:** нет.

Основной объём оперативной памяти гостя.

### 4.3. `resources.ballooning_mb`

**Тип:** целое число, MiB.  
**Минимум:** `0`.  
**Обязательно:** нет.  
**Допустимо:** только для VM.

Пример:

~~~yaml
resources:
  ballooning_mb: 2048
~~~

Поле задаёт минимальный объём памяти при использовании динамического выделения памяти VM.

Значение не может превышать `resources.memory_mb`.

Для LXC это поле запрещено.

### 4.4. `resources.swap_mb`

**Тип:** целое число, MiB.  
**Минимум:** `0`.  
**Обязательно:** для LXC.  
**Допустимо:** только для LXC.

Пример:

~~~yaml
resources:
  swap_mb: 1024
~~~

Значение `0` означает отсутствие подкачки.

Для VM это поле запрещено.

### 4.5. `resources.disk_size_gb`

**Тип:** целое число, GiB.  
**Минимум:** `1`.  
**Обязательно:** для гостя с `profile`.  
**Наследование:** нет.

Для VM поле задаёт требуемый размер основного диска.

Для LXC — размер корневой файловой системы.

### 4.6. `resources.disk_storage`

**Тип:** непустая строка.  
**Обязательно в `guest.yaml`:** нет.  
**Обычный источник:** общие настройки.  
**Переопределение:** допускается.

Пример:

~~~yaml
resources:
  disk_storage: local-lvm
~~~

Поле задаёт хранилище основного диска VM или корневой файловой системы LXC.

Явное отклонение от общего значения отмечается предупреждением.

## 5. Сеть и запуск

### 5.1. `network.ipv4`

**Тип:** IPv4 без префикса или строка `dhcp`.  
**Обязательно:** нет.  
**Обычный источник:** вычисляется из VMID.

Поле поддерживает три режима.

**Автоматический статический адрес** — поле отсутствует:

~~~yaml
# network.ipv4 не задан
~~~

Адрес вычисляется из VMID по общему правилу проекта.

**Явный статический адрес:**

~~~yaml
network:
  ipv4: 192.168.8.50
~~~

Статический адрес в `guest.yaml` записывается без префикса:

~~~text
192.168.8.50      ← допустимо
192.168.8.50/16   ← недопустимо
~~~

**DHCP:**

~~~yaml
network:
  ipv4: dhcp
~~~

В режиме DHCP конкретный IPv4 не является частью требуемого состояния гостя.

После запуска `910 infra-manager` определяет фактический адрес через PVE:

- для VM — по данным QEMU Guest Agent;
- для LXC — по данным сетевых интерфейсов контейнера.

Из доступных адресов выбирается IPv4 общей административной подсети проекта.

Для статического адреса выполняются проверки принадлежности подсети и конфликтов. Для `dhcp` эти проверки к заранее неизвестному адресу не применяются.

Подробная механика адресации описана в `310-guest-state.md`.

### 5.2. `boot.onboot`

**Тип:** логическое значение.  
**Обязательно в `guest.yaml`:** нет.  
**Обычный источник:** общие настройки.  
**Переопределение:** допускается.

Пример:

~~~yaml
boot:
  onboot: true
~~~

Поле определяет, должен ли Proxmox автоматически запускать гостя вместе с PVE-узлом.

Оно не определяет, нужно ли запускать объект непосредственно во время его создания или обслуживания.

## 6. Дополнительные возможности гостя

### 6.1. `management`

**Тип:** список строк.  
**Обязательно:** нет.  
**Можно задавать:** только гостю с `profile`.  
**Наследование:** нет.  
**Пустой список в исходном файле:** запрещён.

Пример:

~~~yaml
management:
  - ssh_identity
  - project_repo_read
~~~

Поддерживаются два значения.

#### `ssh_identity`

Гостю требуется собственная исходящая SSH-идентичность для доступа к другим разрешённым гостям.

Это не ключ для входа в сам этот гость.

#### `project_repo_read`

Гостю требуется управляемый доступ на чтение закрытого репозитория проекта `zsergeyru/proxmox`.

Эта возможность сама по себе не означает установку Git.

В списке не допускаются неизвестные значения и дубликаты.

Если поле отсутствует, в итоговом состоянии используется пустой список.

## 7. Различия VM и LXC

Тип гостя определяется профилем, а не отдельным полем в `guest.yaml`.

Для самого индивидуального манифеста действуют следующие различия:

| Поле | VM | LXC |
|---|---|---|
| `resources.cores` | обязательно | обязательно |
| `resources.memory_mb` | обязательно | обязательно |
| `resources.disk_size_gb` | обязательно | обязательно |
| `resources.ballooning_mb` | необязательно | запрещено |
| `resources.swap_mb` | запрещено | обязательно |

Параметры источника создания не задаются в `guest.yaml`:

- VM получает `template_vmid` из профиля;
- LXC получает `ostemplate` из профиля;
- технические возможности LXC `features` также принадлежат профилю.

Это не позволяет индивидуальному гостю незаметно менять собственный технический тип или источник создания.

## 8. Примеры

### 8.1. Обычная VM

~~~yaml
schema_version: 11
vmid: 410
name: ai-control
description: Управляющая среда AI
profile: debian-vm

resources:
  cores: 4
  memory_mb: 8192
  disk_size_gb: 64
~~~

В этом примере PVE-узел, защита, хранилище диска, сеть и автоматический запуск приходят из общих настроек.

### 8.2. LXC

~~~yaml
schema_version: 11
vmid: 321
name: app-services
description: Прикладные сервисы
profile: debian-lxc-docker

resources:
  cores: 2
  memory_mb: 4096
  swap_mb: 1024
  disk_size_gb: 32
~~~

Тип LXC, системный образ и техническая возможность запуска вложенной контейнерной среды приходят из выбранного профиля.

Требование установить Docker внутри этого гостя относится не к `guest.yaml`, а к его `provision.yaml`.

### 8.3. Явное отклонение от общего адреса

~~~yaml
schema_version: 11
vmid: 501
name: frigate
description: Видеонаблюдение
profile: debian-vm

resources:
  cores: 4
  memory_mb: 8192
  disk_size_gb: 64

network:
  ipv4: 192.168.8.50
~~~

Такой адрес является осознанным исключением из автоматической адресации по VMID и будет отмечен предупреждением проверки.

### 8.4. DHCP

~~~yaml
schema_version: 11
vmid: 321
name: app-services
description: Прикладные сервисы
profile: debian-lxc-docker

resources:
  cores: 2
  memory_mb: 4096
  swap_mb: 1024
  disk_size_gb: 32

network:
  ipv4: dhcp
~~~

Конкретный адрес такого гостя не фиксируется в Git. После запуска `910 infra-manager` получает его через PVE и использует найденный адрес административной сети для SSH и Ansible.

## 9. Что не задаётся в `guest.yaml`

Следующие параметры являются частью других источников и не должны добавляться в индивидуальный манифест.

### 9.1. Общие сетевые параметры

В `guest.yaml` нельзя задавать:

~~~text
network.bridge
network.subnet
network.gateway
~~~

Они принадлежат общим настройкам проекта.

### 9.2. Параметры профиля

В `guest.yaml` нельзя задавать:

~~~text
type
template_vmid
ostemplate
features
~~~

Они принадлежат выбранному профилю.

### 9.3. Пакеты, службы и приложения

В `guest.yaml` не задаются пакеты, Docker, Ansible, службы и прикладные компоненты гостевой операционной системы.

Их требуемое состояние хранится в `provision.yaml` конкретного гостя и применяется Ansible.

### 9.4. Низкоуровневые параметры Proxmox

Индивидуальный манифест не предназначен для произвольной передачи всех параметров Proxmox.

Если проекту требуется новая поддерживаемая возможность, она сначала должна получить понятное поле или высокоуровневое правило общего контракта.

### 9.5. Секреты

В `guest.yaml` нельзя хранить:

- пароли;
- токены;
- закрытые ключи;
- предварительно согласованные ключи;
- другие секретные данные.

Такие данные имеют отдельный жизненный цикл и не должны попадать в Git вместе с требуемым состоянием гостя.
