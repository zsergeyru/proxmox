# Справочник YAML гостевого контура

**Тип:** справочник  
**Статус:** действующий

## 1. Какие YAML используются

В проекте используются пять разных машинных описаний, четыре из них относятся к конкретному гостю.

| Файл | Область ответственности |
|---|---|
| `infrastructure/guests/defaults.yaml` | общие значения и технические профили |
| `<guest>/guest.yaml` | объект VM/LXC в Proxmox |
| `<guest>/provision.yaml` | требуемое состояние поддерживаемой Linux-системы внутри гостя |
| `<guest>/status.yaml` | необязательные проверки готовности и итоговое представление состояния |
| `infrastructure/security/access.yaml` | единые требования доступа между субъектами и ресурсами |

Один файл не должен подменять другой.

`guest.yaml` не содержит список пакетов и приложений.

`provision.yaml` не задаёт процессор, память или диск Proxmox.

`status.yaml` не является источником требуемой конфигурации.

`access.yaml` не описывает устройство VM/LXC или состав ОС.

## 2. `defaults.yaml`

Файл:

```text
infrastructure/guests/defaults.yaml
```

задаёт общие значения и профили, которые используются при построении итогового состояния объекта VM/LXC.

### 2.1. Верхний уровень

Обязательные поля:

| Поле | Тип | Назначение |
|---|---|---|
| `schema_version` | `12` | версия контракта |
| `defaults` | объект | общие значения |
| `profiles` | объект | технические профили |

### 2.2. `defaults`

Текущие поля:

| Поле | Тип | Назначение |
|---|---|---|
| `node` | строка | PVE-узел по умолчанию |
| `protection` | логическое | защита объекта Proxmox |
| `pve_management` | логическое | принадлежность к управляемой области PVE |
| `resources.disk_storage` | строка | хранилище основного диска |
| `network.bridge` | строка | административный сетевой мост |
| `network.subnet` | IPv4-сеть | административная подсеть |
| `network.gateway` | IPv4 | шлюз |
| `boot.onboot` | логическое | автозапуск с PVE |
| `boot.order` | целое, необязательно | порядок запуска |
| `boot.startup_delay_seconds` | целое, необязательно | задержка после запуска |

Требования доступа не задаются в `defaults.yaml` или `guest.yaml`. Для них используется единый `infrastructure/security/access.yaml`.

### 2.3. `profiles`

Каждый профиль имеет собственное имя и поле:

```yaml
type: vm
```

или:

```yaml
type: lxc
```

Для VM обязательно:

| Поле | Назначение |
|---|---|
| `template_vmid` | базовый VM-шаблон |

Для LXC обязательно:

| Поле | Назначение |
|---|---|
| `ostemplate` | системный LXC-образ |

Дополнительно LXC-профиль может содержать:

```yaml
features:
  - container-host
```

`container-host` означает, что LXC должен иметь технические возможности для вложенной контейнерной среды. Сам Docker от этого автоматически не устанавливается.

## 3. `guest.yaml`

Файл:

```text
infrastructure/guests/<VMID>-<name>/guest.yaml
```

описывает конкретный объект VM/LXC.

### 3.1. Общий контракт

Обязательные поля любого исходного `guest.yaml`:

| Поле | Тип | Назначение |
|---|---|---|
| `schema_version` | `12` | версия контракта |
| `vmid` | целое число | VMID/CTID |
| `name` | строка | машинное имя |
| `description` | строка | понятное описание |

Для объекта, который должен участвовать в общей профильной модели, указывается:

```yaml
profile: <имя-профиля>
```

Наличие профиля означает, что общий механизм может построить полное техническое состояние объекта.

Профиль не определяет владельца полного жизненного цикла. Специальный объект может использовать общий профиль, но создаваться отдельным контуром.

### 3.2. `role`

Необязательная строка для особой системной роли, от которой действительно зависит поведение общих механизмов проекта.

Обычным гостям поле `role` не требуется. Назначение приложения или службы не нужно дублировать через роли, если оно уже понятно из `name`, `profile` и `provision.yaml`.

Сейчас используются специальные системные роли:

```yaml
role: infra-manager
role: ai-control
```

`infra-manager` обозначает постоянный инфраструктурный исполнитель проекта.

`ai-control` обозначает центральный интеллектуальный управляющий контур квартиры. Общий Ansible-механизм использует эту роль для подключения специализированной роли настройки AI Control без проверки конкретного VMID.

VMID не является частью системной роли: код должен находить специальный гость по `role`, а текущий VMID, имя и адрес брать из его машинного описания.

Одна системная роль может принадлежать только одному гостю. Проверка проекта отклоняет повторное использование той же роли.

### 3.3. `profile`

Тип: строка.

Значение должно соответствовать имени профиля из `defaults.yaml`.

Тип VM/LXC и источник создания не задаются отдельно в `guest.yaml`, а приходят из профиля.

### 3.4. `node`

Необязательное переопределение PVE-узла.

Обычно наследуется из `defaults.yaml`.

### 3.5. `protection`

Необязательное логическое переопределение встроенной защиты объекта Proxmox.

Поле не описывает права пользователей или API.

### 3.6. `pve_management`

Необязательное логическое значение для гостя с профилем.

Описывает требуемую принадлежность объекта к управляемой области PVE.

Поле само по себе не задаёт:

- SSH-доступ;
- права API-токена;
- владельца OpenTofu-state специального объекта.

### 3.7. `resources`

Для гостя с профилем раздел обязателен.

Общие поля:

| Поле | Тип | Правило |
|---|---|---|
| `resources.cores` | целое >= 1 | обязательно |
| `resources.memory_mb` | целое >= 256 | обязательно |
| `resources.disk_size_gb` | целое >= 1 | обязательно |
| `resources.disk_storage` | строка | обычно наследуется |

Только для VM:

| Поле | Тип | Назначение |
|---|---|---|
| `resources.ballooning_mb` | целое >= 0 | динамическая память |

Только для LXC:

| Поле | Тип | Назначение |
|---|---|---|
| `resources.swap_mb` | целое >= 0 | подкачка |

### 3.8. `network`

Сетевой раздел имеет два режима.

**Простой режим** используется большинством гостей с одним административным интерфейсом.

**Расширенный режим** предназначен для гостей, которым нужны несколько сетевых интерфейсов, разные VLAN или отдельный маршрут по умолчанию.

Оба режима одновременно не используются.

#### Простой режим: `network.ipv4`

Этот режим действует сейчас и сохраняется для обратной совместимости.

Поле `network.ipv4` необязательно.

Поддерживаются три варианта.

**Поле отсутствует:**

```yaml
# network.ipv4 не задан
```

Используется вычисляемый статический адрес по общему правилу проекта.

**Явный статический адрес:**

```yaml
network:
  ipv4: 192.168.8.50
```

В исходном YAML адрес указывается без префикса сети. Префикс, bridge и gateway приходят из общей административной сети `defaults.yaml`.

**DHCP:**

```yaml
network:
  ipv4: dhcp
```

В этом режиме конкретный IPv4 не хранится как требуемое значение. После запуска фактический административный адрес определяется через PVE.

Для VM источником являются данные QEMU Guest Agent.

Для LXC используются сведения об интерфейсах контейнера.

#### Расширенный режим: `network.interfaces`

Этот режим поддерживается общей схемой, resolver, проверкой проекта и OpenTofu.

Формат:

```yaml
network:
  interfaces:
    - name: wan
      bridge: vmbr0
      vlan: 10
      ipv4: 10.0.0.2/30
      gateway: 10.0.0.1

    - name: lan
      bridge: vmbr0
      vlan: 20
      ipv4: 192.168.1.9/16
      management: true
```

Каждая запись описывает отдельный интерфейс объекта Proxmox.

Поддерживаемые поля:

| Поле | Тип | Назначение |
|---|---|---|
| `name` | строка | логическое имя интерфейса внутри машинного контракта |
| `bridge` | строка | PVE bridge; если не задан, используется общий `defaults.network.bridge` |
| `vlan` | целое 1–4094 | необязательный VLAN tag |
| `ipv4` | строка | статический IPv4 с префиксом либо `dhcp` |
| `gateway` | IPv4 | необязательный gateway данного интерфейса |
| `management` | логическое | интерфейс, адрес которого используется управляющим контуром |

Правила расширенного режима:

- список содержит хотя бы один интерфейс;
- имена интерфейсов уникальны;
- VLAN не является обязательным;
- статический `ipv4` указывается с префиксом, потому что разные интерфейсы могут принадлежать разным подсетям;
- gateway может быть задан не более чем у одного интерфейса, если гость использует обычный единый маршрут по умолчанию;
- расширенная маршрутизация внутри гостя остаётся задачей `provision.yaml` и ОС, а не `guest.yaml`;
- ровно один интерфейс должен иметь `management: true`, если у гостя несколько интерфейсов;
- административный интерфейс и интерфейс с gateway могут быть разными;
- порядок записей должен сохраняться: он определяет порядок сетевых устройств объекта Proxmox;
- изменение порядка существующих записей считается изменением сетевого устройства и не должно выполняться без проверки плана.

Пример для сетевого шлюза:

```yaml
network:
  interfaces:
    - name: wan
      bridge: vmbr0
      vlan: 10
      ipv4: 10.0.0.2/30
      gateway: 10.0.0.1

    - name: lan
      bridge: vmbr0
      vlan: 20
      ipv4: 192.168.1.9/16
      management: true
```

Здесь:

- `wan` даёт обычный маршрут по умолчанию;
- `lan` используется для административного доступа;
- наличие двух интерфейсов не означает, что OpenTofu должен настраивать PBR, VPN или `nftables`;
- такие правила относятся к состоянию ОС и задаются через `provision.yaml`.

#### Совместимость режимов

Для обычного гостя сохраняется короткая запись:

```yaml
network:
  ipv4: 192.168.4.10
```

Такой гость продолжает наследовать общую административную сеть из `defaults.yaml`.

Для многосетевого гостя используется только `network.interfaces`.

Одновременное наличие:

```yaml
network:
  ipv4: ...
  interfaces: ...
```

запрещается как неоднозначное состояние.

### 3.9. `boot`

Поддерживаются:

| Поле | Тип | Назначение |
|---|---|---|
| `onboot` | логическое | автозапуск |
| `order` | целое >= 0 | порядок запуска |
| `startup_delay_seconds` | целое >= 0 | задержка после запуска |

`onboot` обычно наследуется из общих настроек.

### 3.10. Что запрещено в `guest.yaml`

Не задаются напрямую:

- `type`;
- `template_vmid`;
- `ostemplate`;
- `features`;
- низкоуровневые параметры сетевой карты, для которых нет поля общего контракта;
- параметры маршрутизации ОС, PBR, VPN и межсетевого экрана;
- пакеты и приложения;
- секреты;
- произвольные низкоуровневые параметры Proxmox.

## 4. `provision.yaml`

Файл:

```text
infrastructure/guests/<VMID>-<name>/provision.yaml
```

описывает требуемое состояние поддерживаемой Linux-системы внутри гостя.

Он применяется общим Ansible-механизмом.

### 4.1. Общий обязательный заголовок

Для поддерживаемого Linux-гостя используются:

```yaml
schema_version: 1
guest_vmid: 410

system:
  distribution: debian
  version: "13"
  architecture: amd64
```

Обязательные поля:

| Поле | Назначение |
|---|---|
| `schema_version` | текущая версия `1` |
| `guest_vmid` | связь с каталогом и `guest.yaml` |
| `system.distribution` | требуемое семейство ОС |
| `system.version` | основная версия ОС |
| `system.architecture` | архитектура |

Общий Ansible-контракт Linux-гостей требует Debian 13 amd64.

### 4.2. `system`

Обязательная группа описывает базовую операционную систему:

| Поле | Требование |
|---|---|
| `distribution` | `debian` |
| `version` | `"13"` |
| `architecture` | `amd64` |

В этой же группе может находиться индивидуальный список `required_packages`.

### 4.3. `system.required_packages`

Необязательный список базовых пакетов конкретного гостя.

Пример:

```yaml
system:
  required_packages:
    - git
    - jq
```

Пакет должен находиться здесь, если его наличие является индивидуальным требованием гостя, а не безусловной частью общей Linux-роли.

### 4.4. `docker`

Раздел используется, если гостю требуется Docker.

Поддерживаемые действующей моделью группы данных:

| Поле | Назначение |
|---|---|
| `required` | явное требование Docker, если используется таким гостем |
| `source` | источник пакетов |
| `service.name` | имя службы, если требуется явное |
| `service.enabled` | включение службы |
| `service.state` | требуемое состояние |
| `required_packages` | набор пакетов Docker |
| `compose_file` | файл Compose относительно каталога гостя |
| `services` | описание специальных контейнерных служб гостя |

Наличие технической возможности `container-host` в LXC-профиле и наличие Docker в `provision.yaml` — разные требования.

### 4.5. `network_gateway`

Специализированный раздел гостя с системной ролью `network-gateway`.

Его потребителем является Ansible-роль `network_gateway`.

Раздел описывает состояние сетевого шлюза внутри Linux и не дублирует параметры объекта Proxmox из `guest.yaml`.

Поддерживаемые группы:

| Поле | Назначение |
|---|---|
| `interfaces.wan` | логическое имя WAN-интерфейса из `guest.yaml` |
| `interfaces.lan` | логическое имя LAN-интерфейса из `guest.yaml` |
| `forwarding.enabled` | требование IPv4 forwarding |
| `adguard_home.enabled` | требование AdGuard Home |
| `adguard_home.interface` | логический LAN-интерфейс DHCP/DNS |
| `adguard_home.domain` | локальный домен HOME |
| `adguard_home.dhcp.*` | диапазон и срок DHCP-аренды |
| `adguard_home.upstream` | локальный SmartDNS, которому передаются внешние запросы |
| `smartdns.enabled` | требование SmartDNS |
| `smartdns.listen` | локальный адрес и порт SmartDNS |
| `smartdns.domain_sets.enabled` | связь доменных групп с nftables sets |
| `routing.default` | маршрут по умолчанию; сейчас `direct` |
| `routing.sources` | независимые локальные и внешние источники списков |
| `routing.update` | период обновления и использование последней рабочей копии |
| `routing.targets` | допустимые назначения правил |
| `nfqws2.enabled` | требование DPI-обработчика |
| `nfqws2.target` | логическая группа, передаваемая в NFQUEUE |
| `firewall.enabled` | включение nftables |
| `firewall.direct_wan_nat` | допустимость NAT на обычном WAN |

Каждая запись `routing.sources` имеет независимое имя и содержит:

| Поле | Назначение |
|---|---|
| `name` | уникальное имя источника |
| `type` | `file` или `http` |
| `path` / `url` | путь или адрес источника |
| `format` | `domain-list`, `hosts`, `ip-list` или `cidr-list` |
| `target` | назначение, например `direct`, `vpn1`, `vpn2`, `zapret` |
| `priority` | приоритет при пересечении правил |

Поставщик списка не является частью машинного контракта. Новый источник подключается новой записью и не требует изменения роли только из-за имени поставщика.

Текущая реализация роли:

- находит реальные Linux-интерфейсы по IPv4 из `guest.yaml`;
- включает IPv4 forwarding;
- формирует базовый `nftables` без NAT на обычном WAN;
- проверяет описание источников списков;
- загружает локальные или HTTP-источники;
- нормализует домены, hosts, IP и CIDR;
- удаляет дубликаты;
- применяет приоритеты и отклоняет неоднозначный конфликт одинакового приоритета;
- хранит последнюю рабочую копию внешнего источника;
- атомарно заменяет сформированные списки.

AdGuard Home, SmartDNS, PBR, `nfqws2` и VPN должны исполняться этой же ролью по мере реализации соответствующих шагов.

Параметры VLAN, IPv4 и gateway повторно в `provision.yaml` не задаются. Их источником остаётся `guest.yaml`.

### 4.6. `ai_control`

Специализированный раздел гостя с системной ролью `ai-control`.

Его потребителем является Ansible-роль `ai_control`.

Раздел фиксирует:

| Поле | Назначение |
|---|---|
| `agent.primary` | основной программный агент |
| `agent.replaceable` | возможность заменить агентную среду без смены роли гостя |
| `agent.image` | закреплённый контейнерный образ агента |
| `agent.api` | параметры локального API агента |
| `agent.dashboard` | параметры дополнительного административного интерфейса агента |
| `web.provider` | пользовательский веб-интерфейс |
| `web.image` | закреплённый образ веб-интерфейса |
| `web.port` | пользовательский порт |
| `paths` | Compose, состояние и локальные секреты |
| `integrations` | логические связи с внешними исполнителями |

Раздел не хранит сами секреты.

Конкретные токены и пароли создаются или материализуются на госте. Внешние полномочия задаются через `infrastructure/security/access.yaml`.

### 4.7. `integrations`

Раздел описывает внешние связи гостя.

В действующих описаниях встречаются:

- связь с Proxmox;
- исходящий SSH;
- обращение к инфраструктурному исполнителю.

Это декларативное описание назначения интеграции. Реальная выдача доступа должна следовать политике безопасности и явно поддерживаться автоматизацией.

### 4.8. `paths`

Раздел используется, когда конкретному гостю требуется машинно зафиксировать набор рабочих и постоянных путей.

Он применяется специализированной ролью этого гостя и не является общим способом зеркалировать всю Linux-файловую систему.

### 4.9. `access_materialization`

Специализированный раздел 910 с техническими путями, которые нужны Ansible для материализации уже разрешённых доступов.

Он может содержать пути к:

- PVE CA;
- временной и рабочей копии PVE API credential;
- отдельной root SSH-идентичности PVE;
- Git SSH `known_hosts`;
- временно материализованному Git credential.

Этот раздел **не является источником права**. Субъект, область и допустимые действия задаются только в `infrastructure/security/access.yaml`.

Секретные значения в Git не помещаются.

### 4.10. `semaphore`

Специализированный раздел управляющей среды.

Описывает требуемые объекты Semaphore на уровне машинного контракта гостя.

Он не является обязательной частью обычного Linux-гостя.

### 4.11. `persistence`

Описывает постоянные и воспроизводимые данные конкретного гостя.

В действующих описаниях используются три основные идеи:

- `backup_required` — данные, которые нельзя потерять и нужно резервировать;
- `reproducible` — данные, которые можно получить заново из проекта или другого источника;
- `ephemeral` — временные данные, которые не требуется резервировать.

Для специализированных гостей раздел может дополнительно описывать внешнюю постоянную структуру и связи каталогов.

### 4.12. `boundaries`

Раздел фиксирует машинно проверяемые границы ответственности конкретного гостя.

Например:

- допустимость прикладной нагрузки;
- право управлять собственным объектом;
- принадлежность к управляемой области;
- разрешённые классы сервисов.

Это не общий список обязательных полей для всех гостей. Используются только границы, которые имеют смысл и поддерживаются проверкой конкретного гостя.

### 4.13. `portal`

Необязательный раздел описывает публикацию веб-служб гостя.

Верхнеуровневая настройка локального портала:

```yaml
portal:
  local:
    enabled: true
    title: Службы ИИ
    port: 3001
    trusted_ca: /etc/example/internal-ca.crt
```

Если локальный портал включён, автоматизация разворачивает Homepage для этого гостя. Поле `portal.local.port` необязательно; если оно не задано, используется порт `3001`. Адрес панели строится из административного IPv4 гостя и этого порта. Необязательное поле `portal.local.trusted_ca` задаёт абсолютный путь к дополнительному TLS CA внутри гостя. Общая роль проверяет существование файла и подключает его в Homepage только для доверия внутренним HTTPS-службам.

Homepage автоматически добавляет поддерживаемые для гостя стандартные действия обслуживания из общего каталога операций:

- `status` — проверить состояние;
- `sync` — синхронизировать требуемое состояние без полного развёртывания: для обычного Linux-гостя повторно применить фазу `provision`, для `infra-manager` выполнить его узкую синхронизацию;
- `repair` — исправить обнаруженные расхождения.

Отдельный флаг включения этих действий не используется. Особенности жизненного цикла конкретной роли учитываются исполнителем соответствующей операции, а не конфигурацией портала.

Публикация службы описывается рядом с самой службой. Для контейнерной службы пример выглядит так:

```yaml
docker:
  services:
    open-webui:
      container_name: open-webui

      portal:
        name: Open WebUI
        icon: mdi-robot
        scheme: https
        port: 443
        path: /
        targets:
          - local
          - home
```

Поддерживаемые поля службы:

| Поле | Назначение |
|---|---|
| `name` | отображаемое имя |
| `icon` | необязательная иконка Homepage: имя Dashboard Icons или поддерживаемый префикс, например `mdi-robot` |
| `scheme` | протокол, обычно `http` или `https` |
| `port` | порт службы |
| `path` | необязательный путь, по умолчанию `/` |
| `targets` | список мест публикации |

Логические назначения:

- `local` — локальный Homepage этого гостя;
- `home` — общий Homarr квартиры. На текущем этапе машинное описание уже формирует этот набор служб; развёртывание и обновление общего Homarr выполняется отдельным контуром.

Названия конкретных программ портала не используются в `targets`. Поэтому замена Homepage или общего портала не требует изменения описаний служб.

Административный IPv4 не повторяется в каждой службе. Автоматизация берёт его из `guest.yaml` и строит адрес из `scheme + IPv4 + port + path`. Homepage использует тот же адрес как `siteMonitor`, поэтому индикатор состояния отражает доступность конкретной HTTP(S)-службы. Для HTTPS с внутренним CA этот CA должен быть задан через `portal.local.trusted_ca`.

Оформление локального Homepage задаётся общей Ansible-ролью, а не каждым гостем отдельно. Текущий единый стиль использует тёмную палитру `slate`, чистые заголовки, одинаковую высоту карточек, локальный фон и размытие карточек. Гость задаёт только содержимое: заголовок, службы и их иконки.

Если раздел `portal` у службы отсутствует, эта служба не публикуется.

Стандартные действия локального портала не должны напрямую выполнять команды Proxmox, SSH или Ansible из браузера. Ссылка открывает ограниченный посредник на управляющем госте. Посредник проверяет действующую пользовательскую сессию Semaphore, показывает подтверждение и только после POST создаёт штатное задание Semaphore с VMID выбранного гостя. Право запуска задачи повторно проверяется самим Semaphore; секрет или API-токен Semaphore в Homepage не передаётся.

### 4.14. Расширение `provision.yaml`

У `provision.yaml` есть общий обязательный заголовок, а остальные разделы зависят от поддерживаемых Ansible-ролей.

Нельзя добавлять произвольное поле только как комментарий о намерении.

Новое машинное поле должно иметь:

1. понятный смысл;
2. владельца в Ansible или другой повторяемой автоматизации;
3. проверку допустимых значений;
4. документацию в этом справочнике.

## 5. `status.yaml`

`status.yaml` необязателен. Если его нет, общий `Status Guest` всё равно проверяет базовое состояние гостя: соответствие объекта Proxmox, запуск, административный адрес, SSH и доступность опубликованных служб из `provision.yaml`.

Файл нужен только для дополнительных проверок, специфичных для конкретного гостя. Он не описывает URL, логины или пароли служб и не является вторым источником конфигурации.

Текущая машинная схема находится в:

```text
infrastructure/schemas/guest-status.schema.yaml
```

### 5.1. Общий формат

Для всех обычных гостей используется версия `2`:

```yaml
schema_version: 2
guest_vmid: 410

checks:
  - type: docker
    container: open-webui
    message: "Open WebUI запущен"
```

Обязательные поля:

| Поле | Назначение |
|---|---|
| `schema_version` | версия общего контракта, сейчас `2` |
| `guest_vmid` | связь с `guest.yaml` |
| `checks` | дополнительные проверки готовности |

Общий исполнитель не принимает произвольные команды оболочки. Допустимы только явно поддержанные типы проверок.

### 5.2. Поддерживаемые проверки

| Тип | Обязательное поле | Назначение |
|---|---|---|
| `docker` | `container` | контейнер существует и находится в состоянии `running` |
| `systemd` | `unit` | служба systemd активна |
| `file` | `path` | абсолютный путь существует и содержит данные |
| `tcp` | `port` | порт доступен на административном адресе гостя |
| `http` | `url` | HTTP(S)-адрес отвечает успешным кодом |
| `local_status` | `command` | запускается заранее установленная абсолютная техническая команда с `--full --quiet` |

`local_status` предназначен для сложной внутренней проверки специального гостя, если такая проверка уже реализована как отдельная безопасная команда. Он не разрешает помещать строку shell в YAML.

Каждая проверка также содержит понятное поле `message`, которое выводится после успешного выполнения.

### 5.3. Службы и данные входа

Опубликованная служба описывается один раз рядом с самой службой в `provision.yaml`:

```yaml
portal:
  name: Open WebUI
  scheme: http
  port: 4100
  targets:
    - local
    - home
  operator:
    username: admin@ai-control.local
    password:
      source: guest_env
      path: /etc/ai-control/open-webui.env
      key: WEBUI_ADMIN_PASSWORD
```

Общий механизм использует это описание одновременно для Homepage и итогового состояния. Пароль в Git не хранится — указывается только способ получить фактическое значение.

Разрешённые источники пароля:

| `source` | Назначение |
|---|---|
| `guest_file` | весь непустой файл внутри гостя является значением |
| `guest_env` | значение ключа `key` читается из файла окружения внутри гостя |
| `pve_json` | строковое поле `key` читается из root-only JSON на PVE |

Пути должны быть абсолютными. Для `guest_env` и `pve_json` поле `key` обязательно.

### 5.4. Режимы вывода и секреты

Общий движок имеет краткий и полный режимы.

Краткий режим показывает только итоговое состояние гостя и не читает пароли.

Полный операторский вывод используется `Status Guest` и после успешного `Deploy Guest`; он показывает параметры гостя, адрес локальной панели Homepage, фактическую Git-ветку и короткую версию проекта, а также адреса опубликованных служб, логины и фактические операторские пароли, если для службы объявлен `operator`.

Внутренние автоматические проверки и `Test Guest` выполняют проверки без вывода секретов.

### 5.5. Внутренний формат infra-manager

Файл `infrastructure/guests/910-infra-manager/infra-manager-status.yaml` остаётся отдельным внутренним описанием глубокой проверки 910 и имеет прежний формат версии `1`. Он не входит в общую схему `guest-status.schema.yaml`, устанавливается как `/etc/infra-manager/status.yaml` и используется только технической командой `infra-manager-status`.

Обычный `infrastructure/guests/910-infra-manager/status.yaml` имеет тот же общий формат версии `2`, что и остальные гости, и подключает внутреннюю проверку через тип `local_status`.

## 6. `access.yaml`

Файл:

```text
infrastructure/security/access.yaml
```

является единым машинным источником требований доступа проекта.

Он описывает:

- субъект;
- подсистему доступа;
- класс ресурса;
- разрешённые цели;
- разрешённые действия.

Секреты и пути их хранения в этот файл не помещаются.

Машинная схема:

```text
infrastructure/schemas/access.schema.yaml
```

Подробная спецификация находится в `docs/700-security/750-access-contract.md`.

## 7. Что не хранится в этих YAML

В машинных описаниях Git запрещено хранить:

- пароли;
- API secrets;
- закрытые SSH-ключи;
- ключи разблокировки;
- другие секреты.

Также не следует хранить там:

- журналы работы;
- кэш;
- фактическое содержимое баз данных;
- пользовательские файлы;
- временное состояние текущего запуска.

Требуемые пути для таких данных можно описывать в `provision.yaml`, но сами данные должны иметь отдельный жизненный цикл.

## 8. Проверка

Основная проверка:

```bash
python scripts/validate_repo.py
```

Для `defaults.yaml`, `guest.yaml`, итогового состояния, `status.yaml` и `access.yaml` используются машинные схемы проекта.

Общий Ansible дополнительно проверяет базовый контракт `provision.yaml` перед настройкой Linux-гостя.

Правила построения итогового состояния из `defaults.yaml + profile + guest.yaml` находятся в [`310-guest-state.md`](310-guest-state.md).
