# Обзор PVE-хоста

**Тип:** обзор  
**Статус:** проектируется  
**Назначение:** описать роль PVE-хоста после переноса постоянного развёртывания в `910 infra-manager`.

## 1. Роль PVE

PVE остаётся платформой виртуализации и владельцем фактического состояния VM/LXC, хранилищ, сетей и ACL Proxmox.

Проектная логика на самом PVE минимальна:

```text
чистый PVE
→ public bootstrap
→ 910 infra-manager
→ закрытый проект внутри 910
→ остальная инфраструктура
```

## 2. Что остаётся на PVE

Обязательны только:

- штатная установка Proxmox VE;
- `vmbr0`;
- `local` и `local-lvm`;
- Debian 13 LXC template для создания 910;
- LXC `910 infra-manager`;
- pool `managed`;
- API token `root@pam!infra-manager` с `privsep=0`;
- отдельный root SSH-ключ управляющего контура;
- постоянный каталог bootstrap с ключами, необходимыми для восстановления 910;
- временная блокировка bootstrap во время запуска.

На PVE не требуются:

- постоянная закрытая Git-копия проекта;
- Docker, Semaphore, OpenTofu, Ansible или Packer;
- `pvedeploy`;
- `deploy-guest`;
- `sync-management-keys`;
- отдельный механизм PVE Configuration;
- отдельное проектное состояние конфигурации PVE.

## 3. Роль public bootstrap

`bootstrap-pve.sh` — единственный проектный сценарий, который выполняется непосредственно на PVE от `root`.

Он отвечает только за минимальную основу, необходимую для запуска 910:

```text
временный LXC 990
+ создание виртуального объекта 910 общим deploy-guest
+ PVE CA
+ полный PVE API token
+ root SSH hand-off
+ GitHub hand-off
+ запуск общего Ansible-развёртывания
```

Он не управляет обычными гостями и не содержит внутреннюю конфигурацию 910.

## 4. Роль 910

`910 infra-manager` — постоянный специальный LXC, который не входит в собственное состояние OpenTofu и находится вне pool `managed`.

Именно внутри 910 находятся:

- закрытый Git-репозиторий;
- Semaphore;
- Runner;
- OpenTofu;
- Ansible;
- Packer;
- инфраструктурные секреты и состояние.

## 5. Обычные гости

Обычные VM/LXC описываются в `infrastructure/guests/` и управляются из 910.

910 считается доверенным административным контуром PVE. Pool `managed` сохраняется как организационная область и будущая граница для менее доверенных контуров, но не ограничивает права самого 910.

AI Control и прикладные гости не получают административные данные 910 напрямую.

## 6. Безопасность

910 является доверенным управляющим контуром домашнего PVE.

Для HTTPS API используется:

```text
root@pam!infra-manager
privsep=0
```

Для операций, которые Proxmox запрещает API token, 910 имеет отдельный root SSH-ключ.

Это осознанная модель доверия: компрометация 910 рассматривается как компрометация административного контура PVE. Поэтому root-доступ не передаётся AI Control и прикладным гостям.

## 7. Жизненный цикл

```text
установка PVE
→ public bootstrap
→ создание 910
→ автоматическая внутренняя настройка 910
→ штатная эксплуатация из 910
```

Единственное ручное действие первого запуска — добавление read-only GitHub Deploy Key.
