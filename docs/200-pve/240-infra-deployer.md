# Контракт 910 infra-deployer

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** зафиксировать точное назначение, состав, границы доверия и постоянные данные LXC `910 infra-deployer`.

`910` — постоянный системный LXC, из которого выполняется штатное развёртывание и настройка инфраструктуры проекта.

## 1. Место в архитектуре

Схема управления:

```text
PVE
└─ bootstrap-pve.sh
   └─ владеет объектом 910

910 infra-deployer
├─ Semaphore
├─ инфраструктурный исполнитель
│  ├─ OpenTofu
│  ├─ Ansible
│  └─ Packer
└─ Git
   └─ zsergeyru/proxmox
```

`910` создаётся и восстанавливается только публичным bootstrap.

`910` не создаётся OpenTofu, не входит в собственное OpenTofu state и не является обычным управляемым гостем.

## 2. Контракт объекта Proxmox

| Параметр | Значение |
|---|---|
| VMID / CTID | `910` |
| Имя | `infra-deployer` |
| Тип | LXC |
| ОС | Debian 13 standard |
| Привилегированность | unprivileged |
| PVE node | `pve` |
| CPU | 2 cores |
| RAM | 2048 MiB |
| Swap | 512 MiB |
| Root disk | 32 GiB |
| Storage | `local-lvm` |
| Bridge | `vmbr0` |
| Автозапуск | включён |
| Protection | включён |
| Nesting | включён |
| Keyctl | включён |

Для `910` не предусматриваются:

- проброс физических устройств;
- bind mount данных PVE-хоста;
- привилегированный LXC;
- Docker socket PVE-хоста;
- доступ к `/etc/pve` как файловой системе;
- root SSH обратно на PVE.

Увеличение CPU, RAM и диска в будущем допустимо отдельным осознанным изменением контракта. Уменьшение диска автоматически не выполняется.

## 3. Сетевой контракт

`910` использует постоянный адрес в административной сети и следует общей формуле VMID.

Для сети `A.B.0.0/16`:

```text
VMID XYZ → A.B.X.YZ
910      → A.B.9.10
```

Например:

```text
192.168.0.0/16 → 192.168.9.10/16
10.0.0.0/16    → 10.0.9.10/16
```

Шлюз совпадает с основным шлюзом административной сети.

Bootstrap получает активную сеть из `vmbr0` и маршрута по умолчанию. Автоматический расчёт допускается только при однозначной IPv4-сети `/16`. Если сеть неоднозначна или имеет другой префикс, bootstrap должен остановиться и потребовать явные параметры сети, а не угадывать их.

## 4. Базовая ОС

В Debian самого LXC устанавливается только необходимая основа:

- `ca-certificates`;
- `curl`;
- `git`;
- `openssh-server`;
- Docker Engine;
- Docker Compose plugin;
- системные средства диагностики, необходимые эксплуатации.

OpenTofu, Ansible и Packer не обязаны устанавливаться как системные пакеты Debian. Они входят в среду инфраструктурного исполнителя.

SSH внутри `910` допускает только аутентификацию по ключам. Парольный вход root не является штатным способом управления.

## 5. Состав Semaphore

Для первой версии используются:

```text
Semaphore Server
SQLite
Semaphore Runner
```

Отдельный PostgreSQL для одного домашнего сервера не является обязательным.

Semaphore Server отвечает за:

- веб-интерфейс;
- проекты и шаблоны заданий;
- историю запусков;
- расписания;
- Key Store;
- SQLite-базу.

Semaphore Runner отвечает за фактический запуск инфраструктурных задач.

В образ исполнителя входят как минимум:

- Git;
- OpenSSH client;
- Python 3;
- Ansible;
- коллекции Ansible проекта;
- `proxmoxer` и необходимые Python-зависимости;
- OpenTofu;
- Packer;
- вспомогательные сценарии проекта.

Веб-сервис Semaphore не получает Docker socket PVE и не выполняет команды на физическом PVE через SSH.

## 6. Постоянные каталоги

Основная структура внутри `910`:

```text
/etc/infra-deployer/
├─ config/
├─ ca/
└─ secrets/

/var/lib/infra-deployer/
├─ semaphore/
├─ opentofu/
│  └─ state/
├─ runner/
└─ public-keys/

/opt/infra-deployer/
└─ compose/
```

Назначение:

- `/etc/infra-deployer/` — локальная конфигурация и чувствительные данные;
- `/var/lib/infra-deployer/semaphore/` — постоянные данные Semaphore;
- `/var/lib/infra-deployer/opentofu/state/` — OpenTofu state;
- `/var/lib/infra-deployer/runner/` — постоянные данные исполнителя;
- `/var/lib/infra-deployer/public-keys/` — открытые ключи, необходимые развёртыванию;
- `/opt/infra-deployer/compose/` — описание контейнеров инфраструктурного контура.

Временные Git-копии и рабочие каталоги заданий не считаются постоянными данными.

## 7. Git и исходный код

Закрытый репозиторий:

```text
git@github.com:zsergeyru/proxmox.git
```

GitHub Deploy Key создаётся внутри `910` и имеет только право чтения.

При первоначальной подготовке закрытый ключ может временно использоваться для первого получения проекта. После настройки Semaphore рабочий доступ к Git хранится в Key Store Semaphore.

PVE-хост не хранит копию этого закрытого ключа.

Локальные изменения в рабочей копии, используемой автоматизацией, не являются новым источником требований. Требуемое состояние приходит из Git.

## 8. PVE API

Основная техническая идентичность:

```text
infra-deployer@pve!automation
```

Токен использует `privsep=1`.

Назначение токена:

- читать требуемое фактическое состояние Proxmox;
- создавать разрешённые VM/LXC;
- изменять обычные управляемые VM/LXC;
- использовать разрешённые storage;
- использовать `vmbr0`;
- включать обычные гости в управляемую область;
- работать с разрешёнными шаблонами.

Токен не должен иметь возможность:

- изменять пользователей, роли и ACL Proxmox;
- изменять или ротировать собственный токен;
- изменять PVE repository;
- менять сетевую конфигурацию физического PVE;
- менять определения storage;
- выключать или перезагружать PVE-хост;
- изменять `910` как обычный управляемый гость.

`910` не входит в пул обычных управляемых гостей.

Точный набор привилегий и ACL является частью [`../700-security/710-pve-access.md`](../700-security/710-pve-access.md) и должен проверяться не только по разрешённым, но и по запрещённым операциям.

Если Packer в будущем потребует более широких прав, для него создаётся отдельная идентичность вместо расширения постоянного токена `automation` без необходимости.

## 9. TLS и доступ к PVE

Bootstrap устанавливает в `910` доверенный корневой сертификат PVE.

Штатный OpenTofu и другие средства обращаются к:

```text
https://<имя-pve>:8006/
```

с проверкой сертификата.

Постоянный `insecure=true` не является частью целевого контракта.

SSH с `910` на PVE не входит в обычный путь управления. Если конкретная будущая возможность провайдера действительно потребует SSH, она проектируется отдельно и не должна автоматически давать `910` полный root-доступ к хосту.

## 10. OpenTofu state

Для первой версии используется локальное постоянное состояние внутри `910`:

```text
/var/lib/infra-deployer/opentofu/state/proxmox.tfstate
```

State:

- не хранится в Git;
- считается чувствительным;
- доступен только инфраструктурному исполнителю и резервному копированию;
- резервируется после успешных изменений;
- не должен одновременно изменяться несколькими заданиями.

Задания, выполняющие `tofu apply`, сериализуются. Одновременно допускается только одно изменение основного состояния Proxmox.

Переход на внешний backend допускается позже без изменения роли `910`.

## 11. Ansible и SSH к гостям

Для первой версии используется одна техническая SSH-идентичность Ansible для управляемых Linux-гостей.

Закрытая часть хранится в Semaphore Key Store.

Открытая часть используется при первоначальном создании Linux-гостя, чтобы Ansible мог подключиться после запуска.

Собственный центральный реестр `<VMID>.pub` и `management-authorized-keys` для этого не требуется.

Для SSH host keys используется строгая проверка. Переход на SSH CA допускается отдельным будущим решением.

## 12. Секреты

Постоянные секреты не хранятся в Git.

В Semaphore Key Store должны находиться как минимум:

- PVE API credential;
- GitHub Deploy Key;
- Ansible SSH private key;
- другие учётные данные, необходимые конкретным заданиям.

Ключ шифрования Semaphore хранится отдельно от SQLite-базы и обязательно входит в резервную копию.

Временные секреты bootstrap после переноса в постоянное хранилище удаляются.

## 13. Самоуправление 910

Разделение ответственности:

```text
bootstrap-pve.sh
→ VMID, тип LXC, ресурсы, сеть, protection, запуск 910

проект внутри 910
→ Debian, Docker, Semaphore, Runner и инфраструктурные инструменты
```

OpenTofu внутри `910` не управляет виртуальным объектом `910`.

Настройка программ внутри `910` должна быть повторяемой. Она может выполняться локальным Ansible или отдельным проектным сценарием, но не должна требовать root SSH обратно на PVE.

## 14. Резервное копирование

`910` считается полностью восстанавливаемым только при наличии резервной копии постоянных данных.

Обязательно сохраняются:

- SQLite-база Semaphore;
- ключ шифрования Semaphore;
- OpenTofu state;
- постоянные секреты, если они не находятся в другом резервируемом хранилище;
- конфигурация, которая по природе не может быть восстановлена из Git.

Git-копии, кэш заданий, пакеты и образы контейнеров не являются критичными: они должны восстанавливаться повторным развёртыванием.

Резервная копия всего LXC средствами PVE желательна, но не заменяет понимание перечисленных критичных данных.

## 15. Проверка готовности

`910` считается готовым только если одновременно выполняются условия:

```text
LXC 910 существует
тип и признаки владения корректны
protection=1
контейнер запущен
сеть работает
DNS работает
PVE CA доверен
GitHub доступен
закрытый репозиторий читается
Semaphore Server готов
Semaphore Runner зарегистрирован и готов
PVE API credential проходит авторизацию
токен не имеет запрещённых административных прав
OpenTofu state доступен исполнителю
```

Проверка готовности не должна выполнять `tofu apply` или менять обычные VM/LXC.

## 16. Восстановление

Если `910` потерян:

```text
PVE
→ bootstrap-pve.sh --recover
→ новый 910
→ новый или восстановленный API credential
→ новый GitHub Deploy Key либо восстановленный секрет
→ восстановление постоянных данных
→ проверка OpenTofu state
→ проверка Semaphore
→ возврат к обычной работе
```

Если OpenTofu state утрачен, автоматическое создание нового пустого state поверх существующей инфраструктуры запрещено. Сначала требуется восстановление state или осознанный импорт существующих объектов.

## 17. Границы

`910` не предназначен для:

- пользовательских приложений;
- Git-сервера разработки;
- CI обычных программных проектов;
- Home Assistant;
- MQTT/Zigbee2MQTT/ESPHome;
- AI-сервисов;
- Frigate;
- общего файлового хранилища.

Эти задачи принадлежат другим функциональным группам VMID.

`311/330 dev-services` и другие средства разработки не получают инфраструктурные секреты только потому, что относятся к DevOps.
