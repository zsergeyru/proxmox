# Первоначальная подготовка PVE-хоста

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить контракт первоначального создания и полного восстановления `910 infra-manager` на PVE.

Документ отвечает на вопрос:

> Какие границы и гарантии должен соблюдать первоначальный контур, чтобы получить работающий 910?

Он не является пошаговой инструкцией оператора и не описывает внутреннюю настройку сервисов 910.

## 1. Основной принцип

Постоянные средства управления инфраструктурой работают внутри `910 infra-manager`, а не на физическом PVE.

Поскольку 910 не может создать сам себя, используется временный `990 bootstrap-runner`.

```text
чистый PVE
→ временный 990
→ создание и настройка 910
→ проверка 910
→ удаление 990
```

**990 всегда одноразовый.** Он удаляется и после успешного завершения, и при
контролируемой ошибке. При повторном запуске публичный загрузчик создаёт
чистый 990; прежние файлы, временные доступы и состояние OpenTofu не
используются. Журналы диагностики остаются на PVE, а не в 990.

## 2. Участники первоначального контура

### 2.1. PVE

PVE отвечает только за действия, которые нельзя поручить ещё не существующему 910:

- проверяет минимальные предварительные условия;
- предоставляет основу для создания временного 990;
- хранит постоянные данные, необходимые для восстановления 910;
- предоставляет временные и постоянные доступы в строго определённых границах;
- выполняет узкие операции, которые намеренно остаются только на стороне PVE;
- удаляет временный контур после успеха и при контролируемом отказе.

PVE не становится постоянным узлом автоматизации.

### 2.2. 990 bootstrap-runner

990 является временным техническим LXC.

Он:

- получает доверенную копию проекта;
- использует отдельное состояние OpenTofu, относящееся только к объекту 910;
- запускает общий механизм развёртывания гостя;
- применяет к 910 общий Ansible-контракт;
- выполняет проверки, необходимые до передачи управления;
- не сохраняется после успешного завершения **или контролируемого отказа**.

990 не должен владеть постоянными секретами или состоянием 910 после передачи управления.

### 2.3. 910 infra-manager

910 является постоянным результатом первоначального контура.

После готовности он:

- содержит постоянные средства управления инфраструктурой;
- использует общий механизм настройки Linux-гостей;
- управляет обычными гостями;
- может обновлять собственное содержимое;
- не управляет своим объектом Proxmox через собственное постоянное состояние OpenTofu.

## 3. Владение объектом 910

Объект Proxmox для 910 принадлежит отдельному первоначальному состоянию OpenTofu.

Постоянное состояние OpenTofu, используемое самим 910, никогда не должно содержать ресурс 910.

Это устраняет циклическую зависимость, при которой управляющий контур должен был бы существовать, чтобы создать самого себя.

Одновременно два состояния OpenTofu не должны владеть одним объектом Proxmox.

Параметры объекта 910 задаются его обычным `guest.yaml`; первоначальный контур не поддерживает отдельное второе описание гостя.

## 4. Контракт первоначального создания

До создания 910 должен быть доступен подходящий стандартный LXC-шаблон Debian 13. Если его нет, первоначальный контур может получить его автоматически. Шаблон, скачанный только для первоначального запуска, является временным техническим ресурсом и после успешного завершения может быть удалён.

Первоначальный контур должен обеспечить следующий результат:

```text
проверенная основа PVE
→ временная среда 990
→ доверенный проект
→ объект 910
→ подключённые постоянные данные
→ общий Ansible-контракт 910
→ проверка готовности
→ удаление временной среды
```

910 настраивается тем же общим путём, что и остальные Linux-гости:

```text
guest.yaml
→ OpenTofu
→ provision.yaml
→ Ansible
```

Отдельный полный сценарий настройки только для 910 не допускается.

Если для 910 требуется новая системная возможность, она должна добавляться в общий механизм гостя или в узкую специализированную операцию с явной границей ответственности.

## 5. Постоянные данные

Уникальные данные 910 не должны зависеть от его корневой файловой системы.

До завершения первоначального создания PVE обязан подготовить постоянные области данных и подключить их к 910 с требуемыми режимами доступа.

Первоначальный контур не должен копировать постоянное состояние в корневую файловую систему как единственное место хранения.

Точный состав обязательного состояния определяет спецификация PVE-хоста, а точные пути — справочник структуры PVE.

Инициализация и использование OpenBao, SSH-сертификатов и других механизмов безопасности относятся к разделу безопасности и не являются частью этого документа.

## 6. Повторный запуск и отказ

Публичный загрузчик знает только о временном 990 и способе получения проекта.
Он не содержит VMID, роли или проверок существования постоянного управляющего
гостя. Эти сведения и решения принадлежат сценарию 990 после получения
актуального `guest.yaml`. Даже если управляющий объект существует, 990 может
быть создан; сам этот факт не разрешает изменение или пересоздание объекта.

Повторный запуск должен быть безопасным и однозначным.

Обычный запуск выбирает создание только при отсутствии 910 и постоянного
каталога. Если присутствует собственный маркер `installing`, разрешается
безопасное продолжение лишь до появления невоспроизводимых постоянных
данных. При наличии маркера `ready` и готового 910 выполняются только
проверка и окончательная очистка временного контура без нового создания.
При отсутствии 910 и наличии прежних постоянных данных требуется строгая
проверка восстановления; неполнота данных запрещает пересоздание.

Существующий 910 нельзя пересоздавать при обычном запуске. Полное
пересоздание rootfs разрешено только в явном режиме восстановления, после
проверки принадлежности объекта и пригодности сохранённого состояния.

Закрытый первоначальный загрузчик обязан различать как минимум:

- 910 отсутствует и его можно создать;
- 910 существует и принадлежит ожидаемому проектному контуру;
- 910 существует, но его принадлежность не подтверждена;
- предыдущая попытка завершилась ошибкой и временный 990 или его токен
  не удалось удалить;
- идентификатор временного или постоянного объекта занят посторонним объектом.

Принадлежность существующего 910 должна подтверждаться не только его номером и именем. Перед восстановлением доступа, изменением хостовых параметров или удалением первоначальный контур обязан проверить проектные метки владения объекта. Точные метки задаются `guest.yaml` 910.

Если существующий 910 не подключён к ожидаемым постоянным областям данных, автоматическая миграция запрещена. Такой случай должен завершаться до изменения данных и переводиться в явную процедуру миграции или восстановления.

Посторонний или неоднозначный объект автоматически не удаляется.

При контролируемой ошибке сначала отзываются временные полномочия 990,
затем после строгой проверки принадлежности удаляется сам временный LXC.
Временные копии постоянных ключей нельзя оставлять в 990. Если очистка
не удалась, ошибка выводится явно, а оставшиеся полномочия необходимо
отозвать; чужой или неоднозначный объект не удаляется. Технический журнал
для диагностики сохраняется на физическом PVE.

При каждом **создании нового rootfs 910** токен
`root@pam!infra-manager` перевыпускается: прежний отзывается, новый
создаётся, и его секрет передаётся в новый гость. Повторно использовать
существующий токен без его секрета запрещено. Это правило не означает
переиздание токена при обычном обновлении работающего 910.

Изменение `/root/.ssh/authorized_keys` на PVE выполняется атомарной
заменой с сохранением остальных записей. При неудачном удалении 910
его защита `protection` восстанавливается, если объект остался.
Временный шаблон удаляется только средствами хранилища PVE:
если `pvesm free` не удался, прямое удаление файла запрещено.

## 7. Полное восстановление 910

Полное восстановление использует тот же общий контракт создания, но должно повторно подключать сохранённое постоянное состояние.

Восстановление не должно:

- молча создавать новое пустое состояние поверх существующей инфраструктуры;
- повторно инициализировать защищённое хранилище при неоднозначном состоянии;
- уничтожать сохранённые данные только ради получения «чистой» установки.

Подробная последовательность восстановления относится к эксплуатационной документации.

## 8. Жизненный цикл первоначального контура

Первоначальный контур поддерживает несколько разных операций с одной и той же границей ответственности:

- первоначальное создание или полное аварийное восстановление;
- проверку уже созданного управляющего контура без повторного развёртывания;
- завершение очистки временных доступов после прерванного запуска;
- удаление управляющего LXC и связанных с ним активных доступов;
- полную очистку служебных данных первоначального контура.

Операция удаления должна убирать сам 910 только после строгой проверки его принадлежности проекту. Вместе с ним удаляются активный API-доступ 910, разрешение проектного root SSH-доступа на PVE и хостовые служебные файлы, которые имеют смысл только при существующем управляющем контуре.

Удаление 910 **не должно** удалять канонический постоянный корень управляющего контура. Точный путь этого корня задаётся справочником `230-host-layout.md`.

Полная очистка первоначального контура может дополнительно удалить его собственный служебный каталог на PVE, но также обязана сохранить области `pve-only/`, `access/` и `state/`.

Удаление самих постоянных данных является отдельной разрушительной операцией и не должно происходить неявно ни при обычном удалении, ни при полной очистке первоначального контура.

После завершения **или контролируемой ошибки** временный 990 и его
полномочия должны удаляться. Временный шаблон освобождается штатной
командой PVE, если он был создан загрузчиком; отказ освобождения
сообщается оператору, но не обходится прямым удалением файла.

## 9. Критерий готовности

Первоначальный контур считается успешным только после подтверждения, что:

- 910 существует и работает;
- постоянные области данных подключены в правильных режимах;
- общий Ansible-контракт применён;
- управляющая среда 910 готова выполнять инфраструктурные задания;
- административный доступ 910 к PVE соответствует принятому контракту безопасности;
- состояние сервисов 910 пригодно для дальнейшей штатной работы;
- постоянное состояние OpenTofu 910 не содержит сам объект 910.

Сам факт создания LXC не является достаточным признаком успеха.
