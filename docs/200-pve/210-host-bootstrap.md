# Первоначальная подготовка PVE-хоста

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** определить минимальную ответственность публичного сценария первоначальной подготовки.

Этот документ отвечает на вопрос:

> Что должен сделать `bootstrap-pve.sh` на чистом Proxmox VE, чтобы запустить постоянный разворачиватель `910 infra-deployer` и передать ему дальнейшее управление?

## 1. Главный принцип

Публичная первоначальная подготовка должна оставаться минимальной.

Её задача:

```text
чистый PVE
→ проверить минимальную основу
→ создать или найти 910
→ запустить 910
→ выдать 910 ограниченный доступ к PVE API
→ подготовить доступ к закрытому Git
→ запустить настройку внутри 910
→ проверить результат
```

Docker, Semaphore, OpenTofu, Ansible и Packer не являются частью логики публичного сценария. Их устанавливает и настраивает закрытый проект уже внутри `910`.

## 2. Исходные условия

Перед запуском требуется только:

- установленный Proxmox VE;
- запуск от `root`;
- существующий мост `vmbr0`;
- хранилище `local` для шаблона LXC;
- хранилище `local-lvm` для корневого диска 910;
- работающие сеть и DNS.

OpenTofu, Ansible, Packer, Docker и Semaphore на PVE заранее не требуются.

## 3. Что делает публичный сценарий

Первый запуск выполняет:

```text
1. проверить root и PVE
2. получить локальную блокировку
3. проверить vmbr0, local и local-lvm
4. найти или скачать Debian 13 LXC template
5. убедиться, что VMID 910 свободен либо принадлежит bootstrap
6. создать 910 при необходимости
7. запустить 910 и дождаться сети
8. установить внутри 910 минимальные Git/SSH/curl зависимости
9. создать или повторно использовать постоянный read-only GitHub Deploy Key на PVE
10. передать копию этого ключа внутрь 910
11. при первом запуске показать public key и дождаться его добавления в GitHub
12. получить закрытый проект внутри 910
13. передать из закрытого проекта pve-bootstrap-access.sh на выполнение от root на PVE
14. этим сценарием передать PVE CA и подготовить ограниченный API token
15. запустить scripts/infra-deployer/setup.sh
16. удалить staging-файл PVE API secret после его сохранения внутри 910
17. выполнить внутреннюю проверку 910
```

Единственное обязательное ручное действие — добавить показанный GitHub Deploy Key в репозиторий как read-only.

## 4. Владение VMID 910

VMID `910` зарезервирован за:

```text
hostname: infra-deployer
type: LXC
owner: public bootstrap
```

Дополнительно используются технические метки:

```text
infra-deployer
proxmox-bootstrap
```

Если 910 занят виртуальной машиной, чужим LXC или LXC без ожидаемых признаков владения, автоматическая замена запрещена.

`910` не входит в пул `managed` и не входит в собственное состояние OpenTofu.

## 5. Параметры 910

Публичный сценарий определяет только параметры виртуального объекта, необходимые до получения закрытого проекта:

```text
Debian 13
unprivileged=1
cores=2
memory=2048 MiB
swap=512 MiB
rootfs=local-lvm:32 GiB
bridge=vmbr0
onboot=1
protection=1
nesting=1
keyctl=1
```

Внутреннее программное наполнение 910 публичному сценарию не принадлежит.

## 6. Первоначальный доступ к PVE

Политика PVE-доступа не хранится в публичном bootstrap.

После получения закрытого проекта public bootstrap временно выполняет на PVE сценарий:

```text
scripts/infra-deployer/pve-bootstrap-access.sh
```

Именно он создаёт необходимую управляемую область, token и ACL.

Отдельный пользователь Proxmox для разворачивателя не создаётся.

Используется token существующего административного пользователя:

```text
root@pam!infra-deployer
```

Token создаётся с `privsep=1` и получает только собственные ACL. Полные права `root@pam` через token не передаются.

Текущий минимальный набор путей и штатных ролей:

| Путь | Роль |
|---|---|
| `/` | `PVEAuditor` |
| `/pool/managed` | `PVEVMAdmin` |
| `/storage/local-lvm` | `PVEDatastoreUser` |
| `/sdn/zones/localnetwork/vmbr0` | `PVESDNUser` |

Подробный контракт доступа находится в `700-security/710-pve-access.md`.

## 7. Доступ к закрытому проекту

Постоянный read-only GitHub Deploy Key создаётся публичным bootstrap и хранится на PVE:

```text
/root/.config/proxmox-bootstrap/github_proxmox_repo_ed25519
```

Публичный сценарий:

```text
создать или повторно использовать keypair на PVE
→ передать копию ключа внутрь 910
→ показать public key при отсутствии доступа
→ пользователь один раз добавляет его в GitHub
→ проверить read-only доступ из 910
→ получить закрытый репозиторий внутри 910
```

Отдельный Deploy Key внутри 910 не создаётся. При мягком удалении и повторном создании 910 постоянный ключ на PVE сохраняется и используется снова. При полном удалении bootstrap-состояния ключ удаляется.

Постоянная закрытая Git-копия проекта на PVE не хранится.

## 8. Передача управления

После получения закрытого проекта выполняется:

```text
scripts/infra-deployer/setup.sh
```

С этого момента именно закрытый проект отвечает за:

- Docker;
- Semaphore Server и Runner;
- OpenTofu;
- Ansible;
- Packer;
- внутренние секреты и постоянные данные 910;
- обновление конфигурации 910;
- проверку готовности 910.

Публичный сценарий не должен дублировать эту логику.

## 9. Повторный запуск

Повторный запуск:

- повторно использует существующий 910;
- не пересоздаёт его;
- повторно использует постоянный GitHub Deploy Key на PVE;
- не меняет API secret без явного восстановления;
- обновляет выбранную ветку закрытого проекта внутри 910;
- повторно запускает идемпотентный `setup.sh`;
- проверяет итоговое состояние.

Режим `--check` ничего не изменяет.

Режим `--recover` разрешает перевыпустить потерянный API token при восстановлении.

## 10. Что публичный сценарий не делает

Он не отвечает за:

- создание обычных VM/LXC;
- применение `guest.yaml`;
- работу OpenTofu;
- настройку Linux-гостей через Ansible;
- сборку шаблона 9000;
- конфигурацию Semaphore;
- хранение OpenTofu state;
- прикладные сервисы;
- отдельный механизм конфигурации PVE.

Старые `pvedeploy`, `deploy-guest`, `sync-management-keys` и PVE Configuration не входят в новую первоначальную подготовку.

## 11. Результат

После успешного запуска:

```text
910 существует и запущен
910 защищён от случайного удаления
910 доверяет PVE CA
на PVE сохранён постоянный read-only GitHub Deploy Key
910 имеет ограниченный PVE API token
910 имеет read-only доступ к закрытому Git через копию этого ключа
внутренняя настройка 910 завершена
infra-deployer-status проходит
```

Дальнейшее управление выполняется из 910.
