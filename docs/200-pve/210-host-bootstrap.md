# Bootstrap PVE-хоста

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** описать процесс первоначальной подготовки PVE-хоста, повторного запуска bootstrap и проверки результата.

Этот документ отвечает на вопрос:

> Как из установленного, но ещё не подготовленного Proxmox получить PVE-хост, готовый к дальнейшему управлению проектом?

## 1. Назначение bootstrap

### 1.1. Исходное состояние хоста

Bootstrap запускается на PVE-хосте, на котором уже установлен Proxmox VE, но ещё не подготовлена инфраструктура проекта.

До запуска bootstrap не предполагается наличие полной проектной конфигурации, локального checkout репозитория или всех служебных компонентов.

Хост должен находиться в состоянии, достаточном для запуска начального сценария подготовки.

### 1.2. Целевой результат

После успешного bootstrap хост должен быть подготовлен к дальнейшему управлению проектом.

Bootstrap должен обеспечить минимальную основу, необходимую для:

- получения проектной конфигурации;
- запуска последующих сценариев управления;
- хранения локального служебного состояния;
- выполнения проверок;
- дальнейшего применения постоянной конфигурации хоста.

Bootstrap не является полной эксплуатационной конфигурацией PVE.

### 1.3. Границы ответственности bootstrap

Bootstrap отвечает только за переход от чистого установленного PVE к состоянию, в котором хост может управляться средствами проекта.

Он не должен подменять:

- постоянную конфигурацию PVE;
- настройку гостевых систем;
- настройку приложений внутри VM и LXC;
- управление сетевой архитектурой;
- политику резервного копирования;
- подробную настройку безопасности и прав доступа.

Эти области описываются отдельно.

## 2. Запуск и входные данные

### 2.1. Как запускается bootstrap

Первоначальный запуск должен быть возможен на хосте, где ещё отсутствует локальная копия основного репозитория.

Поэтому начальная точка входа должна быть доступна отдельно от уже развёрнутой проектной структуры.

После минимальной подготовки дальнейшие действия выполняются уже средствами самого проекта.

### 2.2. Какие данные нужны до запуска

До запуска bootstrap должен быть известен минимальный набор данных, необходимый для получения доверенной версии проекта и начала подготовки.

В bootstrap не следует передавать параметры, которые относятся к обычной постоянной конфигурации PVE и могут быть получены после загрузки проекта.

Чем меньше обязательных внешних входных данных, тем проще и надёжнее первоначальная подготовка.

### 2.3. Как определяется доверенная версия проекта

Bootstrap не должен автоматически выполнять произвольный непроверенный код.

Версия проекта, которая используется для дальнейшей подготовки, должна определяться однозначно.

Механизм должен позволять понять, какой именно вариант проектного кода был использован при подготовке хоста.

Конкретный способ фиксации доверенной версии относится к реализации bootstrap и должен быть согласован с общей моделью безопасности проекта.

### 2.4. Какие данные создаются локально

В процессе первоначальной подготовки bootstrap может создавать локальные данные, без которых дальнейшая работа проекта невозможна.

К ним могут относиться:

- локальная копия репозитория;
- служебные каталоги;
- локальное состояние этапов подготовки;
- необходимые технические настройки;
- другие данные, которые по своей природе должны существовать непосредственно на хосте.

Точный состав и расположение этих данных описываются в документации конфигурации и структуры PVE-хоста.

## 3. Этапы первоначальной подготовки

### 3.1. Минимальная подготовка среды

Первый этап должен подготовить только то, что необходимо для дальнейшего выполнения bootstrap.

Сюда могут входить:

- проверка наличия Proxmox VE;
- установка минимального набора необходимых утилит;
- подготовка Git;
- подготовка SSH или другого механизма получения закрытого репозитория;
- создание необходимых служебных каталогов;
- получение эксклюзивной блокировки bootstrap.

На этом этапе не следует выполнять полную настройку PVE.

### 3.2. Получение репозитория

После подготовки минимальной среды хост получает доверенную версию проектного репозитория.

Локальная копия репозитория становится источником дальнейших сценариев и конфигурации.

Получение проекта должно выполняться предсказуемо и не зависеть от случайного текущего состояния рабочей ветки.

### 3.3. Подготовка локальных компонентов

После получения проекта bootstrap создаёт минимальный набор локальных компонентов, необходимых для дальнейшего управления хостом.

К ним относятся только компоненты, которые должны существовать до применения постоянной конфигурации.

Bootstrap не должен без необходимости копировать в этот этап логику, принадлежащую постоянной конфигурации.

### 3.4. Передача управления постоянной конфигурации

После завершения минимальной подготовки дальнейшее управление хостом передаётся механизму постоянной конфигурации.

Это является важной границей:

- bootstrap создаёт основу;
- постоянная конфигурация определяет, каким должен быть подготовленный PVE-хост в рабочем состоянии.

Bootstrap не должен самостоятельно становиться вторым независимым механизмом постоянной настройки.

### 3.5. Завершение bootstrap

Bootstrap считается завершённым только после того, как:

- обязательные этапы выполнены;
- локальное состояние сохранено;
- дальнейшие средства управления доступны;
- выполнены необходимые проверки результата.

Сам факт завершения сценария без проверки состояния не должен считаться достаточным подтверждением успешного bootstrap.

## 4. Повторный запуск и восстановление после ошибки

### 4.1. Идемпотентность

Bootstrap должен допускать повторный запуск.

Повторный запуск не должен:

- без причины создавать дублирующиеся данные;
- повреждать уже корректно подготовленный хост;
- повторять опасные одноразовые действия;
- изменять состояние только потому, что сценарий был запущен снова.

Если требуемое состояние уже достигнуто, соответствующий этап должен завершаться без ненужных изменений.

### 4.2. Уже выполненные этапы

Bootstrap должен уметь отличать:

- этап, который ещё не выполнялся;
- этап, который завершён успешно;
- этап, который выполнен частично;
- этап, состояние которого больше не соответствует требованиям.

Уже успешно завершённый этап не должен повторяться без необходимости.

### 4.3. Частично выполненный bootstrap

Ошибка в середине bootstrap не должна автоматически требовать полной переустановки PVE.

После устранения причины сценарий должен уметь продолжить подготовку с учётом уже выполненных безопасных действий.

Для этого локальное состояние bootstrap должно быть достаточным, чтобы понять, какие этапы завершены.

### 4.4. Повтор после ошибки

После ошибки оператор должен иметь возможность:

1. определить причину сбоя;
2. исправить внешнюю проблему;
3. повторно запустить bootstrap;
4. получить предсказуемое продолжение процесса.

Не следует требовать ручного удаления служебного состояния, если сценарий способен корректно определить текущее состояние самостоятельно.

### 4.5. Защита от параллельного запуска

Одновременный запуск нескольких экземпляров bootstrap на одном хосте не допускается.

Bootstrap должен использовать эксклюзивную блокировку.

Если другой процесс подготовки уже выполняется, новый запуск должен безопасно завершиться без внесения изменений.

## 5. Обновление bootstrap

### 5.1. Как обновляется механизм bootstrap

После первоначальной подготовки основная версия bootstrap должна храниться и сопровождаться вместе с проектом.

Это позволяет:

- версионировать изменения;
- проверять их через Git;
- повторно использовать тот же механизм на уже подготовленном хосте.

Начальная внешняя точка входа должна оставаться минимальной и стабильной.

### 5.2. Совместимость с уже подготовленным хостом

Новая версия bootstrap должна учитывать, что хост может быть подготовлен более ранней версией.

Изменения должны по возможности:

- сохранять существующее корректное состояние;
- выполнять только необходимые миграции;
- не требовать полной переустановки;
- уметь распознавать старую структуру служебного состояния.

Несовместимые изменения должны быть явными.

### 5.3. Когда требуется ручное вмешательство

Ручное вмешательство допускается, если изменение нельзя безопасно выполнить автоматически.

Например:

- требуется принять решение, которое невозможно вывести из текущего состояния;
- обнаружено противоречивое или повреждённое служебное состояние;
- автоматическая миграция может привести к потере доступа;
- изменился внешний механизм доверия или получения проекта.

Такие случаи должны быть исключением, а не обычным способом обновления.

## 6. Проверка результата

### 6.1. Что должно существовать после завершения

После успешного bootstrap должны существовать все минимальные компоненты, необходимые для дальнейшего управления PVE-хостом.

При этом bootstrap не обязан самостоятельно создавать всё, что относится к окончательной постоянной конфигурации.

Критерий должен проверять именно готовность хоста к следующему этапу.

### 6.2. Какие проверки выполняются

Проверка результата должна подтверждать как минимум:

- что bootstrap завершил обязательные этапы;
- что проект доступен локально;
- что необходимые служебные компоненты существуют;
- что локальное состояние непротиворечиво;
- что можно запустить дальнейший механизм управления;
- что нет незавершённого критического этапа.

Проверка не должна ограничиваться только существованием файлов, если важно также их состояние.

### 6.3. Когда хост считается подготовленным

PVE-хост считается подготовленным, когда:

- bootstrap завершён успешно;
- его обязательные проверки пройдены;
- дальнейшая постоянная конфигурация может быть применена;
- повторный запуск bootstrap безопасен;
- состояние хоста можно однозначно интерпретировать средствами проекта.

После этого дальнейшие требования к постоянному состоянию PVE определяются отдельной документацией конфигурации хоста.
