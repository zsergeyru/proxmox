# Первоначальная подготовка PVE-хоста

**Тип:** спецификация  
**Статус:** принято к реализации  
**Назначение:** определить минимальную ответственность публичного сценария первоначальной подготовки после перехода на временный LXC 990 bootstrap-runner.

Этот документ отвечает на вопрос:

> Как с чистого PVE запустить временный 990 и стандартными средствами закрытого проекта развернуть постоянный 910 infra-manager?

## 1. Главный принцип

Public bootstrap больше не должен самостоятельно создавать и настраивать виртуальный объект 910.

Его задача:

~~~text
чистый PVE
→ проверить минимальную основу
→ создать или найти временный 990 bootstrap-runner
→ запустить 990
→ дать 990 доступ к закрытому Git
→ выполнить закрытый helper для временного PVE API-доступа 990
→ запустить закрытый bootstrap-runner
→ стандартный OpenTofu + Ansible разворачивают 910
→ проверить 910
→ сохранить bootstrap-state 910 на PVE
→ отозвать временный PVE-доступ 990
→ удалить 990
~~~

Параметры 910, OpenTofu, Ansible, Docker, Semaphore, OpenBao и правила развёртывания принадлежат закрытому проекту.

## 2. Исходные условия

Перед запуском требуется только:

- установленный Proxmox VE;
- запуск от root;
- существующий мост vmbr0;
- хранилище local с поддержкой vztmpl;
- хранилище local-lvm с поддержкой rootdir;
- работающие сеть и DNS.

OpenTofu, Ansible, Packer и Docker на PVE не устанавливаются.

## 3. Что делает public bootstrap

Первый запуск выполняет:

~~~text
1. проверить root и PVE
2. получить локальную блокировку
3. проверить vmbr0, local и local-lvm
4. найти или скачать Debian 13 LXC template
5. убедиться, что VMID 990 свободен либо принадлежит bootstrap
6. создать 990 при необходимости
7. запустить 990 и дождаться сети
8. установить минимальные Git/SSH/curl зависимости
9. подготовить read-only доступ к закрытому Git
10. получить выбранную ревизию закрытого проекта внутри 990
11. выполнить из закрытого проекта helper выдачи временного PVE-доступа
12. передать в 990 PVE CA и временный API credential
13. передать сохранённый bootstrap-state 910, если он существует
14. запустить scripts/bootstrap-runner/run.sh deploy
15. выполнить закрытый helper постоянного PVE-доступа 910
16. запустить scripts/bootstrap-runner/run.sh configure
17. сохранить итоговый bootstrap-state 910 обратно на PVE
18. проверить готовность 910
19. отозвать временный API token 990
20. остановить и удалить 990
~~~

Public bootstrap не содержит:

- параметры виртуального объекта 910;
- OpenTofu-конфигурацию 910;
- Ansible-настройку 910;
- матрицу постоянных прав 910;
- Docker/Semaphore/OpenBao-логику;
- отдельный второй механизм развёртывания гостевой системы.

## 4. Временный LXC 990

Контракт 990 находится в 215-bootstrap-runner.md.

Основные свойства:

~~~text
VMID:         990
hostname:     bootstrap-runner
type:         unprivileged LXC
Debian:       13 amd64
cores:        2
memory:       2048 MiB
swap:         512 MiB
rootfs:       local-lvm:16 GiB
bridge:       vmbr0
network:      DHCP
onboot:       false
protection:   false
managed pool: нет
~~~

990 является временным исполнителем и не входит в infrastructure/guests/.

## 5. Владение виртуальным объектом 910

После перехода 910 становится обычным гостем с profile и описывается стандартным guest.yaml.

Его виртуальным объектом управляет отдельное bootstrap-состояние OpenTofu:

~~~text
990
→ bootstrap-state
→ только VMID 910
~~~

Основное состояние внутри 910 не содержит 910:

~~~text
910
→ main state
→ обычные VM/LXC
~~~

Таким образом 910 не управляет собственным виртуальным объектом, но создаётся теми же средствами OpenTofu и Ansible.

## 6. Bootstrap-state 910

Каноническая копия состояния виртуального объекта 910 хранится на PVE:

~~~text
/var/lib/proxmox-bootstrap/state/910.tfstate
~~~

Рабочая копия во время выполнения:

~~~text
990:
/var/lib/bootstrap-runner/opentofu/state/proxmox.tfstate
~~~

Правила:

- при создании нового 990 существующий state с PVE передаётся внутрь него;
- существующий после ошибки 990 не должен получать поверх своего state более старую копию;
- после успешного apply state сначала возвращается на PVE;
- только после подтверждённого сохранения state разрешается удалять 990;
- новый пустой state не применяется поверх существующего 910 без явной процедуры принятия под управление.

## 7. Временный PVE-доступ 990

990 использует отдельную временную идентичность:

~~~text
root@pam!bootstrap-runner
~~~

Она создаётся с разделением привилегий и существует только на время bootstrap.

Её права ограничиваются операциями, необходимыми для создания и изменения 910, чтения нужного LXC template, выделения rootfs и использования vmbr0.

Постоянная идентичность 910:

~~~text
root@pam!infra-manager
~~~

не используется 990 как собственный credential.

После успешного завершения token bootstrap-runner и его ACL удаляются.

## 8. Доступ к закрытому проекту

990 получает read-only доступ к выбранной ревизии zsergeyru/proxmox.

На переходном этапе public bootstrap может повторно использовать уже существующий bootstrap Deploy Key на PVE. Отдельное решение о дальнейшем хранении этого ключа не должно менять контракт 990.

Закрытая Git-копия внутри 990 временная и удаляется вместе с ним.

## 9. Передача управления закрытому runner

После получения проекта запускается:

~~~text
scripts/bootstrap-runner/run.sh
~~~

Он работает в двух закрытых фазах:

- `deploy` подготавливает Docker/infra-runtime, отдельный bootstrap-state и запускает общий deploy-guest 910;
- после выдачи постоянного PVE credential для 910 фаза `configure` передаёт проект и Git-доступ в 910, запускает существующий setup и выполняет полную проверку.

Public bootstrap знает только порядок вызова закрытых этапов, но не их внутреннюю реализацию.

Public bootstrap не задаёт версии OpenTofu, Ansible или Python-зависимостей.

## 10. Ошибка во время bootstrap

Если ошибка произошла после начала работы OpenTofu:

~~~text
990 не удаляется
его рабочий state не уничтожается
910 автоматически не удаляется
~~~

Повторный запуск сначала проверяет оставшийся 990 и незавершённое состояние.

Автоматическое разрушительное «начать заново» запрещено.

Временный API token 990 может оставаться до явного продолжения или отмены незавершённой операции; это должно быть видно оператору.

## 11. Успешное завершение

Удаление 990 разрешено только после выполнения всех условий:

- виртуальный объект 910 соответствует guest.yaml;
- настройка 910 завершена;
- проверки готовности 910 проходят;
- bootstrap-state сохранён на PVE;
- обязательные credentials переданы 910;
- временный PVE token 990 отозван.

После этого:

~~~text
stop 990
→ destroy 990
~~~

## 12. Режим проверки

Режим проверки не создаёт новый 990 только ради чтения состояния.

Он проверяет:

- наличие и фактическое состояние 910;
- наличие bootstrap-state;
- отсутствие оставшегося активного bootstrap token без незавершённой операции;
- готовность 910 штатными проверками.

## 13. Статус перехода

Публичный proxmox-bootstrap версии 3.2.0-dev1 ещё создаёт 910 напрямую.

Этот документ определяет следующую целевую схему. Переход считается завершённым только после реализации:

- LXC в общем OpenTofu-контуре;
- отдельного режима bootstrap-state для VMID 910;
- scripts/bootstrap-runner/run.sh;
- временного PVE token 990;
- обновлённого public bootstrap.
