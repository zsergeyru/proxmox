# Первоначальная подготовка PVE-хоста

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** зафиксировать реальный контракт первоначальной подготовки PVE-хоста и передачи управления постоянной конфигурации.

Этот документ отвечает на вопрос:

> Как установленный Proxmox VE подключается к проекту, получает доверенный исходный код и передаёт управление PVE Configuration?

## 1. Назначение и точки входа

### 1.1. Публичная точка входа

Первоначальная подготовка начинается из отдельного публичного репозитория:

```text
zsergeyru/proxmox-bootstrap
```

Актуальный сценарий:

```text
bootstrap-pve.sh
```

Он используется как для первого подключения нового PVE-хоста к проекту, так и для обычных последующих повторных запусков.

Публичный сценарий должен оставаться минимальным. Его задача — безопасно получить доверенную ревизию закрытого проекта и передать управление основной конфигурации PVE.

### 1.2. Основная закрытая точка входа

Постоянная конфигурация PVE находится в закрытом репозитории:

```text
zsergeyru/proxmox
```

Основная точка входа:

```text
scripts/pve/setup/configure-pve.sh
```

После получения и проверки требуемой ревизии публичный сценарий запускает именно этот файл.

### 1.3. Разделение ответственности

Публичная первоначальная подготовка отвечает за:

- проверку запуска от `root` на Proxmox VE;
- получение общей блокировки;
- наличие минимальных Git/SSH-инструментов;
- проверку доступности GitHub;
- создание или повторное использование постоянного ключа чтения закрытого репозитория;
- получение доверенной ревизии `zsergeyru/proxmox`;
- передачу точной ревизии в PVE Configuration.

PVE Configuration отвечает уже за постоянное требуемое состояние PVE-хоста.

Таким образом, публичная первоначальная подготовка не является вторым независимым механизмом постоянной конфигурации.

## 2. Исходное состояние и обязательные условия

### 2.1. Исходное состояние

Перед первым запуском должны выполняться следующие условия:

- Proxmox VE уже установлен;
- доступна оболочка `root`;
- работает DNS;
- доступен GitHub по HTTPS;
- возможен SSH-доступ к GitHub после регистрации ключа чтения закрытого репозитория;
- другой процесс первоначальной подготовки или PVE Configuration в этот момент не выполняется.

Наличие локальной копии закрытого репозитория заранее не требуется.

### 2.2. Минимальные пакеты

Публичный сценарий проверяет наличие минимального набора инструментов и при необходимости устанавливает:

```text
git
openssh-client
curl
jq
ca-certificates
util-linux
```

Обычный запуск не должен автоматически выполнять полное обновление Debian/Proxmox.

Полное обновление выполняется только при явном запросе параметром:

```text
--update-system
```

### 2.3. Проверка связи с GitHub

До работы с закрытым репозиторием проверяются:

- DNS-разрешение `github.com`;
- DNS-разрешение `api.github.com`;
- HTTPS-доступ к GitHub;
- HTTPS-доступ к GitHub API.

Если эти проверки не проходят, подготовка останавливается до изменения состояния хоста.

## 3. Первый запуск

### 3.1. Общая последовательность

Первый запуск выполняется в следующем порядке:

```text
проверка root и Proxmox VE
→ получение общей блокировки
→ проверка или установка минимальных пакетов
→ проверка DNS и HTTPS-доступа к GitHub
→ создание постоянного ключа чтения закрытого репозитория
→ настройка доверия к SSH-серверам GitHub
→ проверка доступа к zsergeyru/proxmox
→ создание временной локальной копии закрытого репозитория
→ определение точной Git-ревизии
→ запуск PVE Configuration на этой ревизии
→ после успешного завершения удаление временной области
→ фиксация успешного завершения первоначальной подготовки
```

### 3.2. Постоянный ключ чтения GitHub

С первого запуска создаётся один постоянный ключ Ed25519 для чтения закрытого репозитория.

Он хранится по пути:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
```

Открытая часть:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519.pub
```

Связанные файлы SSH:

```text
/etc/proxmox-deployer/ssh/config
/etc/proxmox-deployer/ssh/known_hosts
```

Закрытый ключ принадлежит `root` и имеет права `0600`.

Если постоянный ключ уже существует, обычный повторный запуск использует его и не создаёт новый.

Автоматическая ротация этого ключа как побочный эффект обычной подготовки запрещена.

### 3.3. Регистрация ключа

Если созданный ключ ещё не зарегистрирован для чтения закрытого репозитория GitHub, публичный сценарий показывает его открытую часть и ожидает подтверждения пользователя после регистрации.

Ключ предназначен только для чтения репозитория:

```text
git@github.com:zsergeyru/proxmox.git
```

Право записи этим ключом не требуется.

### 3.4. Временная локальная копия

До создания постоянной структуры PVE Configuration используется временная область:

```text
/var/lib/proxmox-bootstrap/
└── private-repo/
```

Она принадлежит `root` и предназначена только для первого запуска или продолжения незавершённого первого запуска.

Временная копия может безопасно приводиться к свежему состоянию репозитория, включая удаление старых временных файлов.

После успешной подготовки каталог `/var/lib/proxmox-bootstrap/` удаляется.

## 4. Передача управления PVE Configuration

### 4.1. Фиксация ревизии

Один запуск должен использовать одну точную Git-ревизию закрытого проекта.

Публичный сценарий определяет полный SHA выбранной ревизии и передаёт его PVE Configuration через:

```text
PVE_CONFIGURATION_SOURCE_REVISION=<40-значный SHA>
```

PVE Configuration до загрузки своих модулей проверяет, что исполняемый исходный код действительно находится на переданной ревизии.

Если это подтвердить нельзя, запуск останавливается.

### 4.2. Передача общей блокировки

Публичный сценарий передаёт информацию об уже удерживаемой блокировке через:

```text
PVE_ORCHESTRATION_LOCK_HELD=1
```

Открытый файловый дескриптор блокировки передаётся дочернему процессу.

PVE Configuration проверяет, что дескриптор действительно относится к ожидаемому файлу блокировки.

### 4.3. Проверка доверенного исходного кода

Перед выполнением PVE Configuration проверяется, что исходный код:

- находится в Git-репозитории;
- соответствует переданной ревизии;
- принадлежит `root`;
- не доступен на запись группе или остальным пользователям;
- не содержит локальных изменений, подготовленных изменений, неотслеживаемых или игнорируемых файлов.

Код с нарушенной границей доверия не исполняется с правами `root`.

### 4.4. Постоянная локальная копия проекта

После подготовки постоянная доверенная копия проекта находится по пути:

```text
/var/lib/proxmox-deployer/repo/
```

Каноническая точка входа PVE Configuration после этого:

```text
/var/lib/proxmox-deployer/repo/scripts/pve/setup/configure-pve.sh
```

Эта копия принадлежит контуру доверия `root` и не является рабочим каталогом пользователя `pvedeploy`.

## 5. Повторный запуск и продолжение после ошибки

### 5.1. Повторный запуск после успешной подготовки

После успешной первоначальной подготовки тот же публичный сценарий используется для повторного применения конфигурации.

Он использует:

- существующий постоянный ключ GitHub;
- существующую постоянную локальную копию проекта;
- ту же общую блокировку;
- актуальную ревизию ветки `main`.

Перед обновлением постоянной копии проверяется её граница доверия и отсутствие локальных изменений.

### 5.2. Локальные изменения в постоянной копии

Постоянная копия проекта не очищается разрушительно при обнаружении локальных изменений.

Если присутствуют изменения:

- отслеживаемых файлов;
- подготовленных к фиксации файлов;
- неотслеживаемых файлов;
- игнорируемых файлов,

автоматический запуск должен остановиться.

Оператор сначала должен определить происхождение расхождения.

### 5.3. Продолжение незавершённого первого запуска

После исправимой ошибки не требуется удалять:

```text
/etc/proxmox-deployer/
/var/lib/proxmox-deployer/
```

Повторный запуск должен использовать уже созданные корректные постоянные данные.

Существующие закрытые SSH-ключи и секреты API-токенов не удаляются и не меняются автоматически только из-за повторного запуска.

## 6. Защита доверия и параллельного запуска

### 6.1. Общая блокировка

Публичная первоначальная подготовка и PVE Configuration используют один файл блокировки:

```text
/run/lock/proxmox-orchestration.lock
```

Одновременно не допускаются:

```text
первоначальная подготовка + первоначальная подготовка
первоначальная подготовка + PVE Configuration
PVE Configuration + PVE Configuration
```

Блокировка удерживается до полного завершения PVE Configuration.

### 6.2. Граница доверия root

Доверенная локальная копия проекта и постоянный ключ чтения GitHub относятся к защищённому состоянию `root`.

Пользователь `pvedeploy` может получать только тот доступ, который необходим его задачам, но не должен иметь возможность:

- изменять доверенную локальную копию проекта;
- изменять каталог `.git`;
- заменять весь каталог репозитория через доступ на запись к его родителю;
- читать закрытый ключ GitHub, предназначенный только для `root`.

Эта граница нужна потому, что код из постоянной копии проекта исполняется с правами `root`.

### 6.3. Поведение при неоднозначном состоянии

При невозможности безопасно определить происхождение ключа, состояние постоянной копии проекта или доверенную ревизию сценарий должен остановиться.

Автоматическое удаление неоднозначного состояния ради продолжения запрещено.

## 7. Результат первоначальной подготовки

### 7.1. Признак успешного завершения

После успешного завершения создаётся отметка:

```text
/var/lib/proxmox-deployer/state/bootstrap-complete
```

Наличие этой отметки означает, что первоначальный переход к постоянной структуре проекта был успешно завершён.

Она не заменяет проверку текущего состояния всей конфигурации PVE.

### 7.2. Что должно существовать после первого успешного запуска

После успешной первоначальной подготовки должны существовать как минимум:

- постоянный ключ чтения закрытого репозитория;
- постоянная SSH-конфигурация доступа к GitHub;
- постоянная доверенная локальная копия `zsergeyru/proxmox`;
- постоянная область состояния `/var/lib/proxmox-deployer/state/`;
- отметка `bootstrap-complete`;
- возможность повторно запустить PVE Configuration из доверенной локальной копии.

Временный каталог `/var/lib/proxmox-bootstrap/` после успешного завершения существовать не должен.

### 7.3. Что не означает успешная первоначальная подготовка

Отметка `bootstrap-complete` не является самостоятельным доказательством того, что вся текущая конфигурация PVE соответствует требуемому состоянию.

Соответствие постоянной конфигурации проверяется средствами PVE Configuration и описывается в `220-host-configuration.md`.
