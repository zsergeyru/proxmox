# Первоначальная подготовка PVE-хоста

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** зафиксировать контракт первоначальной подготовки PVE-хоста и создания постоянного разворачивателя `910 infra-deployer`.

Этот документ отвечает на вопрос:

> Что должен сделать публичный `bootstrap-pve.sh` на чистом или уже работающем PVE-хосте, чтобы передать дальнейшее управление постоянному разворачивателю `910`?

## 1. Роль первоначальной подготовки

Первоначальная подготовка начинается из публичного репозитория `zsergeyru/proxmox-bootstrap` и запускается от `root` непосредственно на PVE.

Её единственная основная цель:

```text
PVE
→ проверить минимальную основу
→ создать или проверить 910 infra-deployer
→ подготовить первоначальный доступ 910 к PVE и Git
→ убедиться, что 910 принял управление
→ завершить работу
```

После этого обычное развёртывание VM/LXC, настройка Linux-гостей и сборка шаблонов выполняются из `910`.

Закрытый репозиторий проекта и постоянный GitHub Deploy Key проекта на PVE не хранятся.

## 2. Исходные условия

Перед запуском должны выполняться условия:

- Proxmox VE установлен;
- запуск выполняется от `root`;
- доступен `/dev/kvm`;
- существует `vmbr0`;
- доступны `local` и `local-lvm`;
- имя PVE-узла разрешается в локальный адрес;
- работают DNS и исходящий доступ в Интернет;
- другой экземпляр bootstrap не выполняется.

OpenTofu, Ansible, Packer и Semaphore на PVE заранее не требуются.

## 3. Ответственность bootstrap

Bootstrap отвечает только за:

- проверку PVE, сети и базовых хранилищ;
- рабочую политику APT-репозиториев PVE;
- минимальные пакеты, необходимые самому bootstrap;
- блокировку параллельного запуска;
- резервную копию критичной конфигурации перед первым изменением;
- наличие Debian 13 LXC template;
- создание и проверку `910 infra-deployer`;
- PVE-идентичность для постоянного разворачивателя;
- передачу одноразового секрета API-токена в `910`;
- передачу PVE CA в `910`;
- первоначальный запуск настройки `910`.

Используется локальная блокировка:

```text
/run/lock/proxmox-bootstrap.lock
```

Обычный bootstrap не выполняет `apt full-upgrade`. Обновление Proxmox является отдельной эксплуатационной операцией.

## 4. Первый запуск

Последовательность первого запуска:

```text
1. проверить root и Proxmox VE
2. получить блокировку
3. проверить hostname, KVM, vmbr0, local и local-lvm
4. проверить DNS и исходящий доступ
5. проверить принятую политику PVE repository
6. сохранить снимок критичной конфигурации
7. получить Debian 13 standard LXC template
8. проверить VMID 910
9. создать 910, если VMID свободен
10. запустить 910
11. выполнить минимальную подготовку Debian внутри 910
12. установить PVE CA внутри 910
13. создать или проверить PVE-идентичность разворачивателя
14. передать секрет API-токена в 910
15. создать GitHub Deploy Key внутри 910
16. получить закрытый репозиторий уже из 910
17. запустить настройку 910 из закрытого проекта
18. проверить Semaphore и инфраструктурный исполнитель
19. удалить временные секреты bootstrap на PVE
20. завершить работу
```

## 5. Владение VMID 910

VMID `910` зарезервирован за:

```text
name: infra-deployer
type: LXC
owner: Public Bootstrap
```

`910` не является обычным гостем OpenTofu и не входит в собственное OpenTofu-состояние.

Точный контракт находится в [`240-infra-deployer.md`](240-infra-deployer.md).

Bootstrap различает состояния:

```text
910 отсутствует
→ разрешено создать

910 существует как ожидаемый infra-deployer
→ повторно использовать и проверить

910 существует как VM
→ BLOCKED

910 существует как неизвестный LXC
→ BLOCKED
```

Обычный bootstrap не удаляет и не пересоздаёт `910`, не уменьшает его диск, не переносит хранилище и не сбрасывает постоянные данные.

## 6. Первоначальные учётные данные

Bootstrap локально на PVE создаёт:

```text
infra-deployer@pve!automation
```

Токен использует `privsep=1`.

Эта идентичность не должна получать права изменять пользователей, роли, ACL, собственные права, конфигурацию физического PVE, определения хранилищ или сеть хоста.

Секрет API-токена существует на PVE только временно:

```text
создать токен
→ получить одноразовый secret
→ временный root-only файл
→ передать в 910
→ подтвердить получение
→ удалить временный файл с PVE
```

GitHub Deploy Key создаётся внутри `910` и предназначен только для чтения `git@github.com:zsergeyru/proxmox.git`.

Bootstrap также передаёт в `910` публичный корневой сертификат PVE и добавляет его в доверенные CA Debian. Штатное подключение к PVE API должно проверять TLS.

## 7. Повторный запуск

Если `910` существует и соответствует контракту, bootstrap:

- повторно проверяет основу PVE;
- проверяет принадлежность `910`;
- при необходимости запускает контейнер;
- проверяет доступность основного сервиса управления;
- не меняет постоянные секреты;
- не разворачивает остальные VM/LXC.

Успешный повторный запуск должен по возможности завершаться без изменений.

## 8. Восстановление

Полная потеря `910` является отдельным сценарием:

```text
bootstrap-pve.sh --recover
```

Режим восстановления допускает создание нового `910`, создание нового GitHub Deploy Key и явную смену API-токена разворачивателя, но только если VMID `910` действительно свободен.

Если VMID занят неизвестным объектом, восстановление останавливается.

Из резервной копии должны восстанавливаться как минимум база Semaphore, ключ шифрования Semaphore, OpenTofu state и постоянные секреты.

## 9. Что bootstrap не делает

Bootstrap не отвечает за:

- создание обычных VM/LXC;
- применение `guest.yaml`;
- OpenTofu plan/apply обычной инфраструктуры;
- Ansible-настройку обычных Linux-гостей;
- сборку шаблона `9000`;
- проверочный клон шаблона;
- прикладные и AI-сервисы;
- постоянную Git-копию проекта на PVE;
- собственное состояние, дублирующее OpenTofu или Semaphore.

На PVE больше не требуется постоянный `pvedeploy`, `deploy-guest`, `sync-management-keys` или отдельный механизм PVE Configuration.

## 10. Результат

После успешного первого запуска:

```text
PVE готов
910 infra-deployer существует и защищён
910 запущен
910 доверяет PVE CA
910 имеет ограниченный PVE API credential
910 имеет read-only доступ к закрытому Git
Semaphore работает
инфраструктурный исполнитель готов принимать задания
```

После этого дальнейшее управление инфраструктурой выполняется из `910`.
