# Первоначальная подготовка PVE-хоста

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** определить минимальный первоначальный контур, который создаёт постоянный управляющий LXC `910 infra-manager` на чистом Proxmox VE.

Этот документ отвечает на вопрос:

> Как из чистого PVE получить полностью работающий 910, не устанавливая OpenTofu, Ansible, Docker и другие средства управления непосредственно на гипервизор?

## 1. Главный принцип

PVE должен оставаться максимально чистым.

Постоянные средства управления инфраструктурой работают внутри `910 infra-manager`, но 910 не может создавать сам себя. Для разрыва этой зависимости используется временный LXC:

~~~text
чистый PVE
    │
    ▼
990 bootstrap-runner
    │
    ├── временный доступ к PVE API
    ├── временный доступ к проекту
    ├── infra-runtime
    └── отдельное состояние OpenTofu только для 910
    │
    ▼
910 infra-manager
    │
    ├── постоянный infra-runtime
    ├── Semaphore
    ├── OpenTofu
    ├── Ansible
    ├── Packer
    └── OpenBao
    │
    ▼
удаление 990 и его временных прав
~~~

OpenTofu, Ansible, Docker, Packer и Semaphore на физический PVE не устанавливаются.

## 2. Ответственность PVE

На PVE остаются только действия, которые невозможно выполнить из ещё не существующего гостя:

- проверить минимальные предварительные условия;
- найти или получить образ Debian 13 LXC;
- создать временный LXC 990;
- передать 990 минимально необходимые временные полномочия;
- запустить первоначальный процесс внутри 990;
- после готовности 910 удалить 990 и временные полномочия;
- хранить ключ снятия блокировки OpenBao;
- хранить хостовый сценарий, который 910 вызывает при штатном запуске OpenBao.

PVE не становится постоянным узлом автоматизации.

## 3. Назначение 990

`990 bootstrap-runner` — временный технический LXC.

Он существует только во время первоначального создания или полного восстановления 910.

990:

- получает закрытый проект;
- запускает тот же набор средств OpenTofu и Ansible, который используется постоянным управляющим контуром;
- строит итоговое состояние только для VMID 910;
- хранит собственное локальное состояние OpenTofu;
- через `deploy-guest --bootstrap-scope 910` создаёт 910;
- передаёт общему Ansible-механизму необходимые первоначальные доступы;
- тем же `deploy-guest` полностью применяет `provision.yaml` 910;
- проверяет готовность 910;
- после успеха больше не нужен.

990 не является постоянной службой проекта и не должен оставаться работающим после успешной первоначальной подготовки.

## 3.1. Единый способ настройки гостей

910 не получает отдельного механизма настройки только потому, что является управляющим LXC.

Для него действует тот же путь, что и для остальных Linux-гостей:

~~~text
guest.yaml
→ OpenTofu
→ provision.yaml
→ общий Ansible playbook
~~~

Особенность 910 ограничивается владельцем OpenTofu state: объект 910 создаёт временный 990, а постоянное состояние самого 910 этот объект исключает.

Отдельный полный оркестратор настройки 910 удалён. Публичный первоначальный сценарий и 990 используют только общий `deploy-guest` и общий Ansible-контракт. Если общей автоматизации не хватает возможности для настройки 910, эта возможность добавляется в общий Ansible-механизм.

## 4. Разделение состояний OpenTofu

Для 910 используется отдельный владелец состояния.

~~~text
990:
  OpenTofu state → содержит только 910

910:
  основной OpenTofu state → никогда не содержит 910
~~~

Это правило обязательно даже несмотря на то, что 910 имеет обычный профиль `debian-lxc-docker`.

`pve_management: false` запрещает включать 910 в его собственную постоянную область управления PVE, но само по себе не заменяет разделение файлов состояния. Поэтому область входных данных OpenTofu задаётся явно:

- первоначальный контур 990 — только `910`;
- постоянный контур 910 — все обычные гости, кроме VMID первоначального контура.

Два состояния OpenTofu не должны одновременно владеть одним и тем же объектом Proxmox.

## 4.1. Постоянное состояние 910 вне rootfs

Целевая архитектура отделяет код и операционную систему 910 от состояния, которое должно переживать пересоздание LXC.

На PVE используется единый корень:

~~~text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
~~~

Назначение:

- `pve-only/` — данные только PVE; в 910 не монтируется;
- `access/` — постоянные данные PVE, которые 910 получает только для чтения;
- `state/` — состояние сервисов 910, которое подключается в 910 с правом записи.

В `access/` относятся GitHub Deploy Key, root SSH-ключ доступа к PVE, `known_hosts` PVE, PVE CA и постоянный PVE API credential. Это данные, которые нужны для первоначального создания или полного восстановления 910 и потому не должны зависеть от rootfs самого 910.

В `state/` относятся Raft-данные OpenBao, постоянный OpenTofu state, база Semaphore, постоянная Ansible-идентичность и секреты 910.

Git checkout проекта, Docker-образы, Compose-файлы, установленный служебный код и кэши остаются локальными внутри 910 и пересоздаются.

Ключ снятия блокировки OpenBao относится к `pve-only/` и никогда не должен становиться доступным 910 через общий mount point.

После реализации этой схемы восстановление должно выглядеть так:

~~~text
создать чистый 910
→ подключить access/ только для чтения
→ подключить state/ для чтения и записи
→ заново получить проект
→ заново установить и собрать воспроизводимую часть
→ продолжить работу с прежним состоянием
~~~

Сейчас это целевая архитектура, а не уже выполненная миграция. До отдельного переноса живых данных продолжают действовать текущие пути. Машинная фиксация цели находится в `provision.yaml:persistence.target_layout` с `implemented: false`.

Так как 910 непривилегированный LXC, при реализации bind mount необходимо отдельно проверить отображение UID/GID и владельцев файлов на PVE.

Вынос состояния из rootfs не заменяет резервное копирование. Каталог на PVE должен резервироваться отдельно.

## 5. Целевые параметры 910

910 описывается обычным `guest.yaml`:

~~~yaml
vmid: 910
name: infra-manager
profile: debian-lxc-docker
pve_management: false

resources:
  cores: 2
  memory_mb: 4096
  swap_mb: 1024
  disk_size_gb: 32

network:
  ipv4: 192.168.9.10

boot:
  onboot: true
  order: 10
  startup_delay_seconds: 30
~~~

Профиль `debian-lxc-docker` задаёт:

- тип LXC;
- Debian 13;
- непривилегированный контейнер;
- возможности, необходимые контейнерному хосту.

910 защищается от случайного удаления средствами Proxmox.

## 6. Порядок первоначального развёртывания

Целевой порядок:

~~~text
1.  root запускает публичный `bootstrap-pve.sh` на PVE
2.  короткая оболочка Bash получает и запускает `bootstrap-pve.py`
3.  при отсутствии Deploy Key Python создаёт его, показывает открытый ключ и завершает работу до создания 990
4.  после добавления ключа в GitHub повторный запуск проверяет PVE и подготавливает Debian 13 LXC template
5.  создаётся и запускается временный 990
6.  в 990 передаётся read-only Deploy Key и клонируется закрытый проект
7.  публичный Python передаёт управление `scripts/bootstrap-runner/bootstrap-host.py`
8.  закрытый сценарий создаёт временный PVE API-доступ 990 и передаёт 990 root SSH-ключ PVE
9.  внутри 990 подготавливается bootstrap-runtime
10. строится OpenTofu input только для 910
11. deploy-guest --infrastructure-only создаёт LXC 910 и применяет общие host-only требования
12. deploy-guest --provision-base-only применяет базовую часть provision.yaml
13. закрытый сценарий передаёт в 910 PVE CA, постоянный PVE token с privsep=0, root SSH, GitHub-доступ и проект
14. deploy-guest --provision-only полностью применяет provision.yaml 910
15. устанавливаются Docker и постоянный infra-runtime
16. настраиваются Semaphore, OpenTofu, Ansible и Packer
17. разворачивается пустой OpenBao с постоянным Raft-хранилищем без автоматической инициализации
18. выполняются проверки PVE API, root SSH и готовности 910
19. закрытый сценарий удаляет временное состояние и секреты 990
20. PVE отзывает временный API token 990
21. LXC 990 удаляется
~~~

Успех первоначальной подготовки фиксируется только после проверки постоянного 910. Сам факт создания LXC 910 успехом не является.

## 7. Повторный запуск

Если 910 уже существует и соответствует ожидаемому объекту, первоначальный процесс не должен создавать второй 910.

Повторный запуск обязан различать:

- 910 отсутствует — создать через 990;
- 910 существует и исправен — обновить/проверить штатным путём;
- 910 существует, но не принадлежит ожидаемой конфигурации — остановиться без разрушительных действий;
- предыдущий 990 остался после ошибки — определить его принадлежность первоначальному контуру и безопасно продолжить либо очистить только собственные временные артефакты.

Перед запуском Ansible текущий 990 получает временный SSH-доступ к 910. PVE добавляет открытый ключ текущего 990 только после строгой проверки принадлежности VMID 910 проекту. После успешной итоговой проверки этот ключ удаляется из `/root/.ssh/authorized_keys`; остальные ключи не изменяются.

Это необходимо потому, что каждый новый 990 создаёт новую временную пару SSH-ключей. Повторный запуск не должен зависеть от ключа предыдущего временного контейнера.

Чужой объект с VMID 910 или 990 автоматически не удаляется.

## 8. OpenBao

OpenBao является постоянной службой внутри 910 и работает отдельным контейнером Docker.

На текущем этапе используются:

- один узел;
- встроенное хранилище Raft;
- постоянные данные в `/var/lib/persistent/openbao/`;
- ручная первичная инициализация отдельным заданием Semaphore;
- автоматическое снятие блокировки со стороны PVE.

KV v2, политики и AppRole настраиваются следующим отдельным этапом. PKI, SSH CA, OpenBao Agent и динамические секреты пока не используются.

### 8.1. Инициализация

Первичная инициализация не является частью обычного `Deploy Guest 910`. Пустой OpenBao сначала разворачивается в состоянии:

~~~text
initialized=false
sealed=true
storage_type=raft
~~~

После проверки пустого хранилища один раз запускается задание Semaphore:

~~~text
Initialize OpenBao 910
~~~

Задание устанавливает хостовый сценарий на PVE и вызывает первичную инициализацию через доверенный root SSH-контур 910 → PVE.

Для домашнего одиночного узла создаётся один ключ снятия блокировки с порогом один. Ответ инициализации обрабатывается на PVE без вывода секретов в журнал.

Ключ сохраняется атомарно:

~~~text
/root/.config/proxmox-bootstrap/openbao/unseal.key
~~~

Права:

~~~text
/root/.config/proxmox-bootstrap/openbao/  0700
unseal.key                                0600 root:root
~~~

Первоначальный корневой токен намеренно не сохраняется, не выводится и сразу отзывается после успешного снятия блокировки. Для будущих административных настроек должен создаваться отдельный временный корневой токен штатным механизмом OpenBao.

Если OpenBao уже инициализирован, а файл ключа на PVE отсутствует, автоматическое продолжение запрещено.

Если OpenBao ещё не инициализирован, но файл ключа уже существует, его автоматическая перезапись также запрещена. Это защищает от потери ключа при неоднозначном восстановлении.

### 8.2. Снятие блокировки

На PVE устанавливается только хостовый сценарий:

~~~text
/usr/local/sbin/infra-manager-openbao-unseal
~~~

Постоянной systemd-службы и периодического задания на PVE нет.

Внутри 910 устанавливается одноразовая служба:

~~~text
/etc/systemd/system/infra-manager-openbao-startup-unseal.service
~~~

Она включена вместе с 910. После запуска Docker служба ждёт доступности OpenBao и проверяет `/v1/sys/seal-status`.

Порядок штатного запуска:

~~~text
PVE
→ запускает LXC 910
→ внутри 910 запускается Docker
→ контейнер OpenBao становится доступен
→ одноразовая служба 910 проверяет состояние
→ если initialized=true и sealed=true:
     через root SSH вызывает на PVE
     /usr/local/sbin/infra-manager-openbao-unseal
→ PVE временно передаёт ключ в /run внутри 910
→ OpenBao снимает блокировку
→ временная копия ключа удаляется
→ служба внутри 910 завершается
~~~

Хостовый сценарий не передаёт ключ аргументом командной строки. При необходимости он временно передаёт файл ключа в `/run/infra-manager/` внутри 910 с правами `0600`, выполняет запрос снятия блокировки и сразу удаляет временную копию.

Штатный `Deploy Guest 910` после перезапуска уже инициализированного OpenBao также сразу вызывает хостовый сценарий, не дожидаясь перезапуска 910.

Если перезапустился только контейнер OpenBao, а сам 910 не перезапускался, автоматическая разблокировка намеренно не выполняется. Состояние `initialized=true, sealed=true` считается ошибкой. Будущий мониторинг должен обнаруживать её и отправлять уведомление.

Если OpenBao ещё не инициализирован, запуск 910 ничего не изменяет.


### 8.3. Удаление

Обычный `--remove`:

- удаляет 910;
- удаляет хостовый сценарий OpenBao с PVE;
- удаляет оставшиеся от старой схемы службу и периодическое задание, если они ещё существуют;
- сохраняет каталог `/root/.config/proxmox-bootstrap/`, включая ключ снятия блокировки.

Это намеренно предотвращает молчаливое уничтожение критичного ключа.

Полный `--purge` дополнительно удаляет `/root/.config/proxmox-bootstrap/` вместе с ключом.

## 9. Граница секретов

Постоянные секреты инфраструктуры после завершения первоначальной подготовки принадлежат 910/OpenBao, а не 990.

990 может получать только секреты, необходимые для конкретного первоначального запуска.

После успешного перехода управления:

- временные секреты 990 удаляются;
- временный PVE API token 990 отзывается;
- локальное состояние OpenTofu 990 удаляется вместе с 990;
- постоянные секреты 910 не возвращаются в 990;
- закрытые ключи и токены не записываются в Git.

## 10. Критерий готовности 910

Перед удалением 990 должны быть подтверждены как минимум:

~~~text
910 существует и запущен
адрес 192.168.9.10 доступен
общий Ansible-контракт provision.yaml 910 полностью применён
Docker работает
infra-runtime работает
Semaphore отвечает
OpenTofu и Ansible доступны внутри infra-runtime
PVE API-доступ 910 соответствует контракту
OpenBao запущен
OpenBao возвращает корректное состояние; после инициализации обязательно sealed=false
основное состояние OpenTofu 910 не содержит ресурс 910
~~~

Если хотя бы одна обязательная проверка не пройдена, 990 нельзя считать успешно завершённым.

## 11. Реализованная хостовая часть

Публичный контур состоит из минимального `bootstrap-pve.sh` и `bootstrap-pve.py`. Shell только загружает и запускает Python. Python выполняет:

- проверку минимального окружения PVE;
- создание Deploy Key с остановкой первого запуска до создания 990;
- создание и проверку временного 990;
- подготовку read-only Deploy Key;
- установку Git внутри 990;
- получение закрытого проекта;
- запуск закрытой точки входа `scripts/bootstrap-runner/bootstrap-host.py`.

Вся остальная оркестрация находится в закрытом репозитории: временный PVE API-доступ, bootstrap-runtime, OpenTofu, создание или обновление 910, общий Ansible, проверки, восстановление и очистка временного контура.

При ошибке до успешной итоговой проверки 910 временный 990 сохраняется для диагностики.

Первичная инициализация и хостовый контур снятия блокировки OpenBao реализованы отдельным заданием Semaphore `Initialize OpenBao 910`. Пустой контейнер по-прежнему разворачивается общим `provision.yaml`, поэтому обычное обновление 910 не выполняет повторную инициализацию.
