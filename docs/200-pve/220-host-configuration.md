# Конфигурация PVE-хоста

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить, какие обязательные компоненты и свойства должны существовать на PVE-хосте после применения постоянной конфигурации.

Этот документ отвечает на вопрос:

> Что обязательно должно быть настроено на PVE-хосте?

Этот документ содержит конкретные идентификаторы, которые являются частью обязательного контракта. Полная карта расположения, владельцы и права собраны в [`230-host-layout.md`](230-host-layout.md).

## 1. Назначение постоянной конфигурации

### 1.1. Что относится к конфигурации PVE-хоста

Постоянная конфигурация PVE-хоста включает всё, что необходимо самому хосту для работы в проекте:

- системную основу;
- локальную структуру проекта;
- доверенную копию проектного кода;
- служебного пользователя;
- SSH-данные;
- API-учётные данные;
- роли и права Proxmox;
- необходимые хранилища и сеть;
- базовый шаблон;
- локальные административные команды;
- служебное состояние.

Конфигурация гостевых VM/LXC и их внутреннее состояние относятся к разделу гостевых систем.

### 1.2. Основные свойства

Постоянная конфигурация должна быть:

- воспроизводимой;
- проверяемой;
- безопасной для повторного применения;
- однозначной по источнику каждого управляемого элемента;
- устойчивой к повторному запуску.

Ручное изменение фактического состояния не становится автоматически новым требуемым состоянием.

### 1.3. Механизм применения

Постоянная конфигурация применяется механизмом PVE Configuration из доверенной локальной копии проекта.

Первоначальное получение проекта и передача управления описаны в [`210-host-bootstrap.md`](210-host-bootstrap.md).

## 2. Обязательный состав конфигурации

### 2.1. Системная основа

PVE-хост должен иметь:

- поддерживаемую установку Proxmox VE;
- рабочие репозитории пакетов;
- обязательные системные пакеты;
- рабочие DNS и сетевой доступ;
- корректное системное время;
- средства Git и SSH, необходимые проекту.

Обычное применение конфигурации не должно автоматически выполнять полное обновление Debian/Proxmox. Полное обновление выполняется только по явному запросу.

### 2.2. Постоянная локальная структура проекта

На хосте должны существовать постоянные области:

```text
/etc/proxmox-deployer/
/var/lib/proxmox-deployer/
/var/lib/pvedeploy/
/var/log/proxmox-deployer/
```

Также должны существовать отдельные области для локальных резервных копий.

Назначение этих областей должно быть разделено: код, изменяемое состояние и секреты не должны смешиваться в одном месте.

### 2.3. Ограниченный системный пользователь

На PVE должен существовать отдельный системный пользователь:

```text
pvedeploy
```

Его контракт:

```text
primary group = pvedeploy
home = /var/lib/pvedeploy
shell = /bin/bash
```

Он используется для операций, которым не требуется полный доступ `root`, и не должен иметь права изменять доверенную копию проектного кода.

### 2.4. Локальная конфигурация хоста

На PVE должен существовать локальный файл конфигурации:

```text
/etc/proxmox-deployer/config.yaml
```

Он должен задавать как минимум:

- используемый проектный репозиторий;
- рабочую ветку;
- локальную доверенную копию проекта;
- управляемую область Proxmox;
- проектные API-идентичности;
- базовый шаблон.

Если существующая локальная конфигурация противоречит ожидаемой модели, она не должна молча перезаписываться.

### 2.5. Доверенная локальная копия проекта

На PVE должна существовать одна каноническая локальная копия закрытого проекта:

```text
/var/lib/proxmox-deployer/repo/
```

Она должна:

- принадлежать доверенному контуру `root`;
- быть недоступной другим пользователям для изменения;
- иметь `origin` на `git@github.com:zsergeyru/proxmox.git`;
- не содержать неожиданных локальных изменений;
- соответствовать ревизии текущего управляемого запуска.

Неизвестные локальные изменения не удаляются автоматически.

### 2.6. Постоянные SSH-данные

На PVE должны существовать два независимых SSH-контура.

Для чтения закрытого GitHub-репозитория:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519.pub
/etc/proxmox-deployer/ssh/config
/etc/proxmox-deployer/ssh/known_hosts
```

Для управления гостевыми системами:

```text
/etc/proxmox-deployer/ssh/pve_deployer_ed25519
/etc/proxmox-deployer/ssh/pve_deployer_ed25519.pub
```

Это разные SSH-контуры с разным назначением. Постоянные закрытые ключи не должны автоматически заменяться при обычном повторном применении конфигурации.

### 2.7. Реестр управляющих открытых ключей

На PVE должен существовать реестр открытых SSH-ключей:

```text
/var/lib/proxmox-deployer/public-keys/
```

В нём должны использоваться:

```text
pve_deployer_ed25519.pub
<VMID>.pub
management-authorized-keys
```

В реестре хранятся только открытые ключи. Закрытые ключи, API-токены и другие секреты в него помещаться не должны.

### 2.8. Учётные записи и права Proxmox

На PVE должны существовать отдельные проектные API-идентичности:

```text
deployer@pve!host-deploy
ai-agent@pve!infra
```

Должны существовать проектные роли:

```text
AICloneSource
AIManagedGuest
AINetworkUse
AIStorage
AIManagedPool
```

Для обычных управляемых гостевых систем должен существовать пул:

```text
managed
```

Членство конкретного гостя в этом pool определяется effective-параметром `pve_management`: `true` означает членство в `managed`, `false` — отсутствие членства. Этот параметр ограничивает только управление объектом через PVE API/MCP и не отключает management SSH.

Для этих идентичностей должны быть настроены необходимые ACL. Права выдаются по назначению, а не через одну универсальную административную учётную запись.

### 2.9. Хранилища и сеть

PVE Configuration должна проверять доступность используемых проектом объектов:

```text
storage: local
storage: local-lvm
network bridge: vmbr0
```

Также должны быть доступны необходимые исходные образы для гостевых систем.

Эти объекты должны быть пригодны для использования проектными учётными записями.

Общая политика хранения и сети относится к отдельным тематическим разделам.

### 2.10. Базовый Debian-шаблон

На PVE должен существовать базовый Debian-шаблон:

```text
VMID: 9000
name: tpl-debian13
```

Он должен:

- соответствовать своему контракту;
- иметь отдельную версию контракта;
- быть пригодным для полного клонирования;
- проходить проверку созданием и запуском отдельного полного клона.

Проверка полного клона использует отдельную проверочную VM:

```text
VMID: 9099
```

Неуспешный проверочный клон не должен автоматически уничтожаться, если он нужен для диагностики.

### 2.11. Локальные административные команды

На PVE должны быть установлены стабильные локальные команды:

```text
/usr/local/sbin/pve-configuration-status
/usr/local/sbin/deploy-guest
/usr/local/sbin/sync-management-keys
```

Они соответственно используются для проверки состояния PVE Configuration, развертывания отдельной VM/LXC и синхронизации управляющих SSH-ключей.

### 2.12. Служебное состояние

PVE Configuration должна сохранять постоянное машинное состояние в:

```text
/var/lib/proxmox-deployer/state/
```

Основные элементы состояния:

```text
state.json
version
last-run.json
last-revision
template-smoke.json
bootstrap-complete
```

Этого состояния должно быть достаточно для безопасного повторного запуска, просмотра результата предыдущего запуска и проверки согласованности конфигурации.

### 2.13. Версия PVE Configuration

PVE Configuration должна иметь собственную версию в формате:

```text
MAJOR.MINOR.PATCH
```

Используется обычная трёхчастная схема SemVer:

- `MAJOR` — несовместимое изменение контракта;
- `MINOR` — совместимое расширение возможностей;
- `PATCH` — совместимое исправление.

Версия PVE Configuration и версия контракта базового шаблона являются разными сущностями и изменяются независимо.

## 3. Источники и применение конфигурации

### 3.1. Что задаётся из Git

Из проекта приходят:

- сценарии PVE Configuration;
- требования к состоянию хоста;
- модель ролей и прав;
- параметры базового шаблона;
- локальные команды;
- проверки соответствия.

Git не хранит рабочие секреты и закрытые ключи.

### 3.2. Что создаётся локально

На конкретном PVE-хосте создаются и сохраняются:

- закрытые SSH-ключи;
- секреты API-токенов;
- локальная конфигурация;
- служебное состояние;
- журналы;
- данные SSH-доверия;
- локальные резервные копии чувствительных данных.

Эти данные не должны заменяться без необходимости при обычном повторном применении конфигурации.

### 3.3. Один запуск — одна ревизия

Один запуск PVE Configuration должен работать с одной точной Git-ревизией.

Если согласованность исполняемого кода с этой ревизией нельзя подтвердить, выполнение должно остановиться.

### 3.4. Повторное применение

Повторный запуск является штатным режимом.

PVE Configuration должна:

- повторно использовать корректное состояние;
- создавать отсутствующие обязательные элементы;
- исправлять безопасно исправимые расхождения;
- не менять постоянные учётные данные без отдельного решения;
- не уничтожать неоднозначное состояние автоматически;
- после изменений проверять результат.

### 3.5. Ручные изменения и расхождения

Ручное изменение хоста не становится автоматически новым требуемым состоянием.

Если обнаружено расхождение:

- безопасное и однозначное расхождение можно исправить автоматически;
- неизвестное или неоднозначное состояние должно остановить применение;
- намеренное изменение должно быть закреплено в основном источнике требований.

## 4. Проверка состояния

### 4.1. Сохранённое состояние

Для просмотра результата последнего запуска без новой полной проверки используется:

```text
pve-configuration-status
```

Такой результат является только сохранённым снимком и не подтверждает текущее состояние хоста.

### 4.2. Фактическая проверка

Для фактической проверки текущего состояния используется:

```text
pve-configuration-status --check
```

Она должна:

- работать только на чтение;
- не применять конфигурацию;
- заново читать фактическое состояние;
- проверять все обязательные части контракта;
- отдельно показывать успешные проверки, предупреждения и ошибки;
- возвращать различимые коды результата.

Фактическая проверка должна охватывать как минимум:

- системную основу;
- локальную структуру и права доступа;
- служебного пользователя;
- SSH-данные и секреты;
- локальную конфигурацию;
- доверенную копию Git;
- реестр открытых ключей;
- пользователей, токены, роли и эффективные права Proxmox;
- управляемую область;
- хранилища и сеть;
- базовый шаблон;
- локальные административные команды;
- состояние проверочного клона.

Результат проверки должен позволять отличить полное соответствие, соответствие с предупреждениями и ошибку или небезопасное состояние.

Успешное завершение первоначальной подготовки само по себе не является доказательством текущего полного соответствия хоста.

Коды возврата:

```text
0 — все обязательные проверки пройдены
2 — ошибок нет, но есть предупреждения
1 — обнаружена ошибка или несоответствие
```
