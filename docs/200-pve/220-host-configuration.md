# Постоянное состояние PVE-хоста

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** зафиксировать минимальное постоянное состояние самого PVE.

## 1. Основной принцип

PVE должен оставаться максимально близким к штатной установке Proxmox VE.

На физическом PVE не размещаются закрытый Git-репозиторий, инфраструктурный исполнитель или постоянные инструменты развёртывания.

```text
PVE
├─ штатная конфигурация Proxmox
├─ минимальные объекты доступа
└─ LXC 910 infra-manager
```

## 2. Обязательное состояние

### 2.1. Сеть и хранилища

Должны существовать:

```text
vmbr0
local
local-lvm
```

`local` хранит LXC template.

`local-lvm` используется для корневого диска 910 и дисков обычных управляемых гостей.

Имя PVE-узла должно разрешаться в его локальный адрес.

### 2.2. Debian LXC template

На `local` должен быть доступен Debian 13 standard LXC template, достаточный для создания 910.

Если его нет, public bootstrap получает его автоматически.

Это не VM template `9000`.

### 2.3. 910 infra-manager

На PVE существует специальный LXC:

```text
VMID 910
hostname infra-manager
```

Его виртуальным объектом владеет public bootstrap.

910:

- unprivileged;
- имеет `nesting=1,keyctl=1`;
- запускается вместе с PVE;
- защищён `protection=1`;
- не входит в pool `managed`.

### 2.4. Управляемая область

Для обычных VM/LXC существует:

```text
pool managed
```

Это граница изменяющих прав инфраструктурной автоматизации.

### 2.5. Порядок автоматического запуска

После перехода на развёртывание 910 через временный 990 сам 910 получает обычные параметры запуска Proxmox, но имеет самый ранний явно заданный порядок:

~~~text
VMID 910
onboot = true
order = 10
up = 30
~~~

`order=10` означает, что 910 запускается раньше гостей без заданного порядка и раньше будущих групп с порядком 20, 30 и далее.

`up=30` означает паузу 30 секунд после запуска 910 перед переходом Proxmox к следующему гостю. Эта пауза даёт Docker и OpenBao время начать запуск, но не является проверкой готовности OpenBao.

Готовность OpenBao определяется отдельным механизмом автоматического unseal на PVE.

Порядок завершения работы Proxmox выполняется в обратном направлении, поэтому инфраструктурный 910 должен оставаться доступным до остановки зависимых гостей.

При реализации общего гостевого контура параметры Proxmox `startup` не передаются в `guest.yaml` сырой строкой. Группа `boot` расширяется понятными полями проекта:

~~~yaml
boot:
  onboot: true
  order: 10
  startup_delay_seconds: 30
~~~

При необходимости позже добавляется `shutdown_delay_seconds`. Средство построения состояния преобразует эти поля в штатные параметры Proxmox `order`, `up` и `down`.

До реализации этого расширения текущая схема `guest.yaml` поддерживает только `boot.onboot`; настоящий порядок запуска 910 не должен считаться уже применённым.

### 2.6. PVE API token

Для 910 существует:

```text
root@pam!infra-manager
```

с `privsep=1`.

Отдельный пользователь `infra-manager@pve` не создаётся.

Token получает только прямые ACL, описанные в разделе безопасности.

## 3. Чего на PVE не должно требоваться

Новая архитектура не требует:

```text
/etc/proxmox-deployer/
/var/lib/proxmox-deployer/
/var/lib/pvedeploy/
/var/log/proxmox-deployer/

pvedeploy
deploy-guest
sync-management-keys
pve-configuration-status
```

Также на PVE не должны храниться:

- закрытая Git-копия проекта;
- GitHub Deploy Key проекта;
- OpenTofu state;
- Semaphore;
- Docker;
- Ansible;
- Packer.

Оставшиеся от старой реализации объекты удаляются как наследие после подтверждённого перехода.

## 4. Что PVE не управляет

OpenTofu внутри 910 не управляет:

- физическим PVE;
- объектом 910;
- своим PVE API token;
- ACL самого token;
- базовыми хранилищами и мостом PVE.

Эта минимальная основа принадлежит public bootstrap и штатной конфигурации Proxmox.

## 5. Проверка

Проверка PVE должна подтверждать:

- наличие PVE;
- `vmbr0`;
- `local` и `local-lvm`;
- принадлежность VMID 910;
- запуск 910;
- pool `managed`;
- наличие `root@pam!infra-manager`;
- требуемый порядок автоматического запуска 910 после реализации общего поля `boot.order`;
- `privsep=1`;
- успешную внутреннюю проверку 910.

Детальная проверка Semaphore, Runner, OpenTofu и других средств выполняется внутри 910 командой `infra-manager-status`.

## 6. Повторное применение

Повторный public bootstrap:

- повторно использует существующий корректный 910;
- не пересоздаёт его;
- не перевыпускает token без причины;
- обновляет закрытый проект внутри 910;
- передаёт управление внутреннему setup только при новой ревизии;
- останавливается при неоднозначном состоянии.
