# Конфигурация PVE-хоста

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить постоянное требуемое состояние PVE-хоста, его обязательные компоненты, источники конфигурации и правила проверки результата.

Этот документ отвечает на вопрос:

> Что должно быть настроено на PVE-хосте и как определить, что его постоянная конфигурация соответствует требованиям проекта?

Границы PVE-раздела определены в [`200-overview.md`](200-overview.md). Первоначальная подготовка хоста описана в [`210-host-bootstrap.md`](210-host-bootstrap.md).

## 1. Назначение постоянной конфигурации

### 1.1. Что считается конфигурацией PVE-хоста

Постоянная конфигурация PVE-хоста — это набор системных настроек, локальных компонентов, учётных данных и служебного состояния, необходимых для работы самого PVE в рамках проекта.

Она должна быть:

- воспроизводимой;
- проверяемой;
- безопасной для повторного применения;
- отделённой от внутреннего состояния VM и LXC;
- однозначной по источнику каждого управляемого элемента.

### 1.2. Как конфигурация применяется

Основным механизмом применения постоянной конфигурации является `PVE Configuration`.

Её точка входа в проекте:

```text
scripts/pve/setup/configure-pve.sh
```

После первоначальной подготовки она выполняется из доверенной локальной копии проекта на PVE.

Подробный процесс первоначальной передачи управления описан в `210-host-bootstrap.md`.

### 1.3. Требуемое и фактическое состояние

Git хранит версионируемую часть требуемого состояния.

PVE-хост хранит фактическую конфигурацию и локальные данные, которые не должны находиться в Git.

Ручное изменение хоста не становится автоматически новым требуемым состоянием.

Если фактическое состояние расходится с проектом, расхождение должно быть либо устранено, либо осознанно закреплено в основном источнике конфигурации.

## 2. Обязательный состав конфигурации

### 2.1. Системная основа

PVE-хост должен иметь системное окружение, необходимое для работы Proxmox и проектных средств управления.

Конфигурация включает:

- поддерживаемую установку Proxmox VE;
- настроенные APT-репозитории;
- обязательные системные пакеты;
- работоспособные DNS и сетевой доступ;
- корректное системное время;
- необходимые средства Git, SSH и локального управления.

Полное обновление Debian/Proxmox не является обязательным побочным эффектом обычного применения конфигурации и выполняется только по явному запросу.

### 2.2. Постоянная структура проекта

На хосте должна существовать постоянная локальная структура проекта.

Основные области:

```text
/etc/proxmox-deployer/
/var/lib/proxmox-deployer/
/var/lib/pvedeploy/
/var/log/proxmox-deployer/
```

Также используются отдельные каталоги для резервных копий локальной конфигурации и секретов.

Точные пути, файлы, владельцы и права описываются в [`230-host-layout.md`](230-host-layout.md).

### 2.3. Пользователь pvedeploy

На PVE должен существовать отдельный системный пользователь:

```text
pvedeploy
```

Его назначение — выполнение ограниченных операций развёртывания и управления, которым не требуется полный доступ `root`.

Текущий контракт пользователя:

```text
system user
primary group = pvedeploy
home = /var/lib/pvedeploy
shell = /bin/bash
```

Доверенная локальная копия проектного кода, исполняемого от `root`, не должна быть доступна `pvedeploy` на запись.

### 2.4. Локальная конфигурация проекта

На хосте должен существовать основной файл локальной конфигурации:

```text
/etc/proxmox-deployer/config.yaml
```

Он содержит параметры конкретного PVE-контура, в том числе:

- репозиторий проекта;
- рабочую ветку;
- путь к постоянной локальной копии;
- управляемый пул Proxmox;
- используемые учётные записи API;
- VMID базового шаблона.

Существующий файл не должен автоматически перезаписываться при конфликте с ожидаемой моделью.

Неоднозначное или несовместимое состояние должно приводить к остановке применения конфигурации.

### 2.5. Доверенная локальная копия проекта

На PVE должна существовать постоянная доверенная копия:

```text
/var/lib/proxmox-deployer/repo/
```

Она используется как канонический локальный источник проектного кода после первоначальной подготовки.

Для неё обязательны следующие свойства:

- дерево принадлежит `root`;
- запись для группы и остальных пользователей запрещена;
- адрес `origin` соответствует `git@github.com:zsergeyru/proxmox.git`;
- локальные изменения отсутствуют;
- текущая ревизия согласована с ревизией выполняемой конфигурации.

Неизвестные локальные изменения не удаляются автоматически.

### 2.6. Постоянные SSH-данные

На PVE должны существовать постоянные данные доступа к закрытому Git-репозиторию:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519.pub
/etc/proxmox-deployer/ssh/config
/etc/proxmox-deployer/ssh/known_hosts
```

Также должна существовать отдельная SSH-пара для управления гостевыми системами:

```text
/etc/proxmox-deployer/ssh/pve_guest_ed25519
/etc/proxmox-deployer/ssh/pve_guest_ed25519.pub
```

Постоянные закрытые ключи не ротируются автоматически при обычном повторном применении конфигурации.

Полный жизненный цикл ключей относится к разделу безопасности.

### 2.7. Реестр управляющих открытых ключей

На PVE должен существовать канонический реестр:

```text
/var/lib/proxmox-deployer/public-keys/
```

В нём хранятся только открытые управляющие SSH-ключи.

Основные элементы:

```text
deployer.pub
<VMID>.pub
management-authorized-keys
```

Закрытые ключи, API-токены и другие секреты в этот каталог не помещаются.

### 2.8. Учётные записи и права Proxmox

Постоянная конфигурация включает проектные учётные записи и права PVE.

Основные API-учётные данные:

```text
deployer@pve!host-deploy
ai-agent@pve!infra
```

Используются проектные роли:

```text
AICloneSource
AIManagedGuest
AINetworkUse
AIStorage
AIManagedPool
```

Для обычных управляемых гостевых систем используется пул:

```text
managed
```

Здесь фиксируется обязательность этих элементов для конфигурации PVE. Точные привилегии и границы доступа относятся к разделу безопасности.

### 2.9. Хранилища и образы

Конфигурация PVE должна обеспечивать доступность хранилищ, необходимых текущему проектному контуру.

В действующей схеме используются:

```text
local
local-lvm
```

Также подготавливаются необходимые исходные образы для LXC и базового Debian-шаблона.

Общая политика хранения и резервного копирования описывается отдельно.

### 2.10. Базовый Debian-шаблон

В постоянную инфраструктуру PVE входит базовый Debian-шаблон проекта.

Текущий объект:

```text
VMID 9000
tpl-debian13
```

PVE Configuration проверяет его состояние, при необходимости создаёт заново и после новой сборки выполняет проверку полного клона.

Для отдельной проверочной VM используется:

```text
VMID 9099
```

Подробный контракт содержимого шаблона относится к разделу гостевых систем.

### 2.11. Локальные команды управления

На PVE должны быть установлены локальные команды проекта:

```text
/usr/local/sbin/pve-configuration-status
/usr/local/sbin/deploy-guest
/usr/local/sbin/sync-management-keys
```

Их наличие входит в постоянную конфигурацию хоста.

При этом:

- `pve-configuration-status` относится к проверке самого PVE;
- `deploy-guest` относится к управлению отдельными VM/LXC;
- `sync-management-keys` относится к распространению управляющих SSH-ключей.

Подробное поведение последних двух команд описывается в профильных разделах.

### 2.12. Служебное состояние

Постоянное состояние PVE Configuration хранится в:

```text
/var/lib/proxmox-deployer/state/
```

В нём фиксируются, в частности:

- версия конфигурации;
- ревизия проекта;
- состояние последнего запуска;
- итоговый машинный статус;
- состояние проверки шаблона;
- отметка завершённой первоначальной подготовки.

Точные имена файлов относятся к справочнику структуры хоста.

## 3. Источники и применение конфигурации

### 3.1. Что задаётся из Git

Из репозитория `zsergeyru/proxmox` приходят:

- сценарии PVE Configuration;
- требования к постоянной структуре;
- роли и ожидаемая модель ACL;
- параметры базового шаблона;
- локальные команды проекта;
- проверки и правила приведения к требуемому состоянию.

Git не хранит рабочие секреты и закрытые ключи.

### 3.2. Что создаётся локально

На конкретном PVE-хосте создаются и сохраняются:

- закрытые SSH-ключи;
- секреты API-токенов;
- локальный `config.yaml`;
- служебное состояние;
- журналы;
- SSH-данные доверия;
- локальные резервные копии чувствительных файлов.

Эти данные не должны автоматически заменяться только потому, что повторно применена та же конфигурация.

### 3.3. Правило одного запуска

Один запуск конфигурации работает с одной точной Git-ревизией.

Код, который выполняется с правами `root`, должен происходить из доверенного дерева этой ревизии.

Если во время запуска невозможно подтвердить согласованность исходного кода, конфигурация должна остановиться.

### 3.4. Повторное применение

Повторный запуск является штатным режимом.

Механизм должен:

- повторно использовать уже корректное состояние;
- создавать отсутствующие обязательные элементы;
- добавлять недостающие настройки там, где это безопасно;
- не менять постоянные учётные данные без отдельного решения;
- не уничтожать неоднозначное состояние автоматически;
- после изменений повторно проверять результат.

### 3.5. Ручные изменения и расхождения

Ручные изменения на PVE не считаются автоматически принятым новым состоянием проекта.

Если обнаружено расхождение:

- безопасно исправимое расхождение может быть приведено к требованиям проекта;
- неизвестное или неоднозначное состояние должно привести к остановке;
- изменение, которое требуется сохранить, должно быть закреплено в основном источнике требований.

## 4. Проверка состояния

### 4.1. Просмотр сохранённого состояния

Команда:

```text
pve-configuration-status
```

без параметров **не выполняет повторную проверку хоста**.

Она показывает последнее сохранённое машинное состояние PVE Configuration из:

```text
/var/lib/proxmox-deployer/state/state.json
```

и при наличии — сохранённое состояние проверки базового шаблона.

Такой вывод является снимком результата предыдущего запуска и сам по себе не подтверждает, что фактическое состояние хоста с тех пор не изменилось.

### 4.2. Фактическая проверка

Для проверки текущего состояния используется:

```text
pve-configuration-status --check
```

Этот режим заново читает фактическое состояние PVE-хоста и сопоставляет его с обязательным контрактом проекта.

Проверка выполняется только на чтение: команда не исправляет обнаруженные расхождения и не применяет конфигурацию.

Проверяются, в частности:

- доступность Proxmox VE;
- постоянные каталоги, владельцы и права;
- контракт пользователя `pvedeploy`;
- постоянные SSH-ключи и секреты;
- локальный `config.yaml`;
- доверенная локальная копия Git, её `origin`, чистота и ревизия;
- реестр управляющих открытых ключей;
- пользователи, API-токены, их фактическая авторизация, роли и эффективные права Proxmox;
- пул `managed`;
- хранилища `local` и `local-lvm`;
- базовый шаблон;
- наличие локальных административных команд;
- состояние проверки полного клона шаблона.

Результат выводится отдельно по каждой проверке и завершается итогом:

```text
OK
PARTIAL
ERROR
```

Коды возврата:

```text
0 = все обязательные проверки пройдены
2 = обязательные проверки пройдены, но есть предупреждения
1 = обнаружена ошибка или несоответствие
```

### 4.3. Что должно проверяться

Проверка постоянной конфигурации должна подтверждать как минимум:

- доверенная локальная копия проекта существует и согласована;
- обязательная локальная структура создана;
- пользователь `pvedeploy` соответствует контракту;
- постоянные ключи и секреты находятся в ожидаемом состоянии;
- реестр управляющих открытых ключей корректен;
- обязательные роли, учётные записи и ACL PVE существуют;
- необходимые хранилища доступны;
- базовый шаблон соответствует своему контракту;
- локальные административные команды установлены;
- служебное состояние непротиворечиво.

### 4.4. Состояния конфигурации

Машинное состояние должно позволять отличить как минимум:

- полное соответствие;
- частичное соответствие;
- ошибку или небезопасное состояние.

Статус `partial` означает, что инфраструктура существует, но не все обязательные требования подтверждены.

Успешное завершение первоначальной подготовки само по себе не означает полного соответствия текущей постоянной конфигурации.
