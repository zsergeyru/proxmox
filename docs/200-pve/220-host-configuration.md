## 1. Назначение конфигурации хоста

### 1.1. Что считается конфигурацией PVE-хоста

Конфигурацией PVE-хоста считается набор постоянных параметров, системных компонентов и локальных настроек, которые необходимы для работы самого хоста в рамках проекта.

К ней относятся только те элементы, владельцем которых является PVE-хост.

Конфигурация должна быть:

- воспроизводимой;
- проверяемой;
- понятной по источнику;
- безопасной для повторного применения;
- отделённой от состояния гостевых систем.

### 1.2. Что считается требуемым состоянием

Требуемое состояние описывает, каким должен быть подготовленный PVE-хост после применения проектной конфигурации.

Оно включает:

- обязательные системные компоненты;
- настройки самого Proxmox;
- локальные компоненты проекта;
- необходимые служебные параметры;
- подключённые ресурсы, которые принадлежат уровню PVE.

Требуемое состояние не определяется случайным текущим состоянием хоста.

Если фактическая конфигурация расходится с описанием проекта, такое расхождение должно быть явно рассмотрено.

### 1.3. Что в конфигурацию хоста не входит

В постоянную конфигурацию PVE-хоста не входят:

- внутренняя настройка VM и LXC;
- приложения внутри гостевых систем;
- прикладные Docker-контейнеры;
- данные приложений;
- общая политика DNS, VPN и маршрутизации;
- резервные копии как самостоятельная область;
- пользовательские эксплуатационные инструкции;
- временные диагностические изменения.

Эти темы относятся к другим разделам документации.

## 2. Состав управляемой конфигурации

### 2.1. Базовая конфигурация Proxmox

К управляемой конфигурации могут относиться параметры самого Proxmox, которые необходимы для работы проекта.

Например:

- системные параметры хоста;
- параметры, влияющие на работу виртуализации;
- настройки, необходимые для интеграции со средствами управления;
- параметры, которые должны быть одинаково воспроизводимы после переустановки.

Конкретные значения должны находиться в профильных конфигурационных файлах или других основных источниках, а не дублироваться в этом документе без необходимости.

### 2.2. Пакеты и системные зависимости

На PVE-хосте может требоваться дополнительный набор пакетов и системных зависимостей.

Они должны устанавливаться только если необходимы:

- самому PVE;
- средствам управления хостом;
- служебным сценариям проекта;
- проверке и сопровождению конфигурации.

Прикладные приложения не должны устанавливаться на PVE только потому, что технически это возможно.

### 2.3. Служебные компоненты проекта

На хосте могут существовать локальные служебные компоненты проекта.

К ним могут относиться:

- сценарии применения конфигурации;
- средства проверки состояния;
- вспомогательные команды;
- служебные unit-файлы;
- таймеры;
- локальные реестры;
- другие компоненты, необходимые для управления PVE.

Наличие такого компонента должно быть оправдано задачами самого хоста.

### 2.4. Локальные настройки проекта

Часть конфигурации должна существовать локально на PVE.

Это могут быть данные, которые:

- относятся только к конкретному хосту;
- создаются в процессе подготовки;
- не должны храниться в Git;
- формируются на основе локальной среды;
- нужны для работы служебных компонентов.

Каждая локальная настройка должна иметь понятного владельца и причину существования.

### 2.5. Подключаемые ресурсы

PVE-хост может использовать внешние или локальные ресурсы, необходимые для своей работы.

К ним могут относиться:

- хранилища;
- сетевые интерфейсы;
- внешние источники конфигурации;
- API;
- другие инфраструктурные зависимости.

В этом документе фиксируется только сам факт принадлежности ресурса к конфигурации хоста.

Подробная архитектура соответствующей подсистемы описывается в её собственном разделе.

## 3. Источники и применение конфигурации

### 3.1. Что задаётся из Git

Git является основным источником воспроизводимой конфигурации проекта.

Из Git должны приходить данные, которые:

- должны иметь историю изменений;
- одинаково применяются после переустановки;
- не содержат секретов;
- являются частью требуемого состояния;
- подходят для проверки и ревизии.

Например, в Git могут храниться:

- сценарии;
- конфигурационные шаблоны;
- декларативные параметры;
- описание состава управляемых компонентов.

### 3.2. Что создаётся локально

На PVE могут создаваться локальные данные, которые не должны храниться в Git.

Например:

- служебное состояние;
- данные конкретного экземпляра хоста;
- закрытые учётные данные;
- технические блокировки;
- локальные идентификаторы;
- данные, формируемые при первом запуске.

Такие данные не должны дублировать воспроизводимую конфигурацию без необходимости.

### 3.3. Что приходит из внешних систем

Некоторые значения могут зависеть от внешних систем.

Это могут быть:

- сетевые данные;
- параметры внешних сервисов;
- внешние идентификаторы;
- сведения, получаемые через API;
- данные из защищённых хранилищ секретов.

Если внешний источник является обязательным, это должно быть явно известно механизму применения конфигурации.

### 3.4. Как изменения применяются к хосту

Изменения конфигурации должны применяться управляемым способом.

Процесс должен по возможности:

1. получить актуальное требуемое состояние;
2. определить, какие изменения необходимы;
3. применить только нужные изменения;
4. сохранить корректное локальное состояние;
5. выполнить проверку результата.

Повторное применение той же конфигурации не должно без причины изменять уже корректно настроенный хост.

### 3.5. Что делать с ручными изменениями и расхождениями

Ручное изменение PVE не становится автоматически новым требуемым состоянием.

Если обнаружено расхождение, нужно определить:

- было ли изменение намеренным;
- должно ли оно сохраниться;
- нужно ли перенести его в основной источник конфигурации;
- должно ли автоматическое управление вернуть прежнее состояние.

Постоянные изменения должны фиксироваться в основном источнике, а не оставаться только как неизвестное локальное отклонение.

## 4. Проверка конфигурации

### 4.1. Что проверяется

Проверка конфигурации должна подтверждать, что:

- обязательные управляемые компоненты существуют;
- ожидаемые настройки применены;
- обязательные локальные данные находятся в корректном состоянии;
- отсутствуют известные критические расхождения;
- средства управления могут однозначно определить состояние хоста.

Проверка должна оценивать не только наличие файлов или пакетов, но и их значимое состояние, если это необходимо.

### 4.2. Как определяется полнота конфигурации

Состояние хоста может быть:

- полным — все обязательные требования выполнены;
- частичным — основа работает, но часть обязательной конфигурации отсутствует или требует завершения;
- ошибочным — обнаружено состояние, при котором дальнейшее управляемое применение небезопасно или невозможно.

Конкретные машинные статусы могут зависеть от реализации, но их смысл должен соответствовать этой модели.

### 4.3. Когда состояние считается корректным

Конфигурация PVE-хоста считается корректной, когда:

- все обязательные требования выполнены;
- нет критических расхождений между требуемым и фактическим состоянием;
- локальное служебное состояние непротиворечиво;
- повторное применение конфигурации безопасно;
- проверка не требует ручного исправления неизвестных отклонений.

Подробная эксплуатационная диагностика и устранение неисправностей должны находиться в отдельной инструкции, а не в этой спецификации.
