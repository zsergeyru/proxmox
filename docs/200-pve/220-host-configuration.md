# Постоянное состояние PVE-хоста

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить, какое постоянное состояние обязан сохранять PVE для работы и восстановления инфраструктурного контура.

## 1. Граница спецификации

PVE является владельцем объектов Proxmox и физическим местом хранения части постоянных данных управляющего контура.

При этом средства автоматизации работают внутри `910 infra-manager`, а не на самом PVE.

Этот документ фиксирует обязательное состояние и его свойства, но не описывает:

- пошаговое развёртывание;
- точную файловую раскладку;
- внутреннее устройство 910;
- правила SSH и API-доступа;
- порядок резервного копирования.

Для этих тем существуют отдельные профильные документы.

## 2. Базовое состояние Proxmox

На PVE должны существовать и быть пригодны для работы проекта:

- сетевой мост `vmbr0`;
- хранилище `local`;
- хранилище `local-lvm`;
- стандартный LXC-шаблон Debian 13, достаточный для создания 910;
- штатный корневой сертификат PVE.

`local` используется для LXC-шаблона.

`local-lvm` используется для корневого диска 910 и для гостей, которым это задано их конфигурацией.

Имя PVE-узла должно разрешаться в его локальный адрес.

Базовый LXC-шаблон Debian для создания 910 не является VM-шаблоном проекта `9000`.

## 3. Управляющий LXC

На PVE должен существовать специальный LXC `910 infra-manager`.

Его объект Proxmox:

- создаётся первоначальным контуром;
- запускается вместе с PVE;
- защищён от случайного удаления;
- не входит в pool `managed`;
- не входит в постоянное состояние OpenTofu самого 910.

Точные ресурсы, сеть и параметры LXC задаются `guest.yaml` самого 910 и не дублируются в этой спецификации.

## 4. Управляемая область

На PVE должен существовать pool:

```text
managed
```

Он используется как организационная область обычных управляемых VM и LXC.

Pool не является границей полномочий самого 910. Менее доверенные контуры могут использовать его как область ограничения доступа по отдельному контракту безопасности.

## 5. Доступ 910 к PVE

910 должен иметь два раздельных канала административного доступа к PVE:

- HTTPS API для OpenTofu и обычных операций Proxmox;
- отдельный root SSH-доступ только для операций, которые нельзя выполнить через API-токен.

API-доступ использует постоянную идентичность `root@pam!infra-manager` с `privsep=0`.

Отдельный пользователь PVE, собственная роль и отдельная ACL-матрица для 910 не требуются.

Закрытые данные доступа не должны храниться только внутри корневой файловой системы 910. Они должны быть доступны для полного восстановления управляющего LXC.

Подробные правила доступа являются ответственностью раздела безопасности.

## 6. Постоянные данные управляющего контура

Постоянные данные на PVE разделяются на три области с разными границами доступа.

### 6.1. Данные только для PVE

Эта область содержит секреты и служебные данные, которые 910 не должен получать напрямую.

Она не монтируется в 910.

К ней относятся, в частности, данные, необходимые PVE для разблокировки OpenBao и выдачи ограниченных SSH-подписей.

### 6.2. Данные PVE, доступные 910 только для чтения

Эта область содержит данные, владельцем которых остаётся PVE, но которые нужны 910 для работы.

К ней относятся:

- GitHub Deploy Key проекта;
- root SSH-идентичность доступа к PVE;
- сведения для строгой проверки SSH PVE;
- корневой сертификат PVE;
- постоянные данные API-доступа 910.

910 получает эту область только для чтения.

### 6.3. Изменяемое состояние 910

Эта область содержит состояние сервисов, которое должно переживать удаление и повторное создание корневой файловой системы 910.

К ней относятся:

- данные OpenBao;
- состояние OpenTofu;
- данные Semaphore;
- постоянная Ansible-идентичность;
- постоянные секреты 910.

910 получает эту область с правом записи.

Размещение этих данных на PVE не является резервной копией.

## 7. Что не относится к постоянному контуру PVE

На PVE не должны устанавливаться как постоянные средства управления проектом:

- Docker;
- Semaphore;
- OpenTofu;
- Ansible;
- Packer.

На PVE также не требуется постоянная закрытая Git-копия проекта.

Воспроизводимые файлы внутри корневой файловой системы 910 могут создаваться заново и не должны считаться уникальным постоянным состоянием PVE.

## 8. Проверка состояния

Проверка PVE должна подтверждать как минимум:

- доступность требуемой сети и хранилищ;
- наличие подходящего LXC-шаблона Debian;
- существование и запуск 910;
- наличие pool `managed`;
- работоспособность обоих каналов административного доступа 910 к PVE;
- наличие всех трёх областей постоянных данных;
- правильную границу доступа между ними;
- отсутствие 910 в его собственном постоянном состоянии OpenTofu.

Детальная проверка сервисов внутри 910 выполняется самим управляющим контуром.
