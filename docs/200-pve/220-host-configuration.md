# Постоянное состояние PVE-хоста

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** зафиксировать минимальное постоянное состояние самого PVE и данные, которые PVE хранит для работы и восстановления `910 infra-manager`.

## 1. Основной принцип

PVE должен оставаться максимально близким к штатной установке Proxmox VE.

На физическом PVE не работают постоянные средства развёртывания проекта: Docker, Semaphore, OpenTofu, Ansible и Packer выполняются внутри `910 infra-manager`.

При этом PVE является физическим владельцем постоянных данных, которые должны переживать удаление или пересоздание rootfs 910.

Основная схема:

```text
PVE
├─ штатная конфигурация Proxmox
├─ LXC 910 infra-manager
├─ pool managed
├─ API-токен root@pam!infra-manager
├─ отдельный root SSH-доступ 910
└─ /mnt/bindmounts/infra-manager/
   ├─ pve-only/
   ├─ access/
   └─ state/
```

Наличие постоянных файлов на PVE не означает, что PVE выполняет OpenTofu, Ansible или Semaphore. PVE только хранит данные и предоставляет их 910 через bind mount.

## 2. Обязательное состояние

### 2.1. Сеть и хранилища

Должны существовать:

```text
vmbr0
local
local-lvm
```

`local` хранит LXC-шаблон Debian, необходимый для создания 910.

`local-lvm` используется для корневого диска 910 и дисков обычных управляемых гостей.

Имя PVE-узла должно разрешаться в его локальный адрес.

### 2.2. Debian LXC template

На `local` должен быть доступен стандартный LXC-шаблон Debian 13, достаточный для создания 910.

Если его нет, публичный сценарий первоначальной подготовки получает его автоматически.

Это не VM-шаблон `9000`.

### 2.3. 910 infra-manager

На PVE существует специальный LXC:

```text
VMID 910
hostname infra-manager
```

Его объект Proxmox создаётся первоначальным контуром `990 bootstrap-runner` и не входит в постоянное состояние OpenTofu самого 910.

910:

- непривилегированный LXC;
- имеет `nesting=1,keyctl=1`;
- запускается вместе с PVE;
- защищён `protection=1`;
- не входит в pool `managed`.

### 2.4. Управляемая область

Для обычных VM/LXC существует:

```text
pool managed
```

Это организационная область проекта. Она не ограничивает права самого 910, но может использоваться как граница для менее доверенных контуров.

### 2.5. PVE API и root SSH

Для 910 существует постоянная API-идентичность:

```text
root@pam!infra-manager
privsep=0
```

Отдельный пользователь `infra-manager@pve`, отдельная роль и отдельная ACL-матрица для 910 не используются.

Кроме API-токена существует отдельный root SSH-ключ. Он нужен только для операций PVE, которые нельзя выполнить через API-токен, например для применения `keyctl=1` к непривилегированному Docker-LXC.

Открытая часть ключа находится в `/root/.ssh/authorized_keys` PVE с проектной меткой. Закрытый ключ хранится в постоянной области `access/` и передаётся в 910 только для чтения.

### 2.6. Постоянные данные 910 на PVE

Канонический корень:

```text
/mnt/bindmounts/infra-manager/
├── pve-only/
├── access/
└── state/
```

Назначение областей:

- `pve-only/` — секреты и служебные данные, которые доступны только PVE и никогда не монтируются в 910;
- `access/` — данные, которыми владеет PVE и которые 910 получает только для чтения;
- `state/` — постоянное состояние сервисов 910, которое подключается в 910 для чтения и записи.

В `pve-only/` находятся как минимум:

- ключ снятия блокировки OpenBao;
- служебные AppRole-данные для настройки и подписи SSH через OpenBao.

В `access/` находятся как минимум:

- рабочая копия GitHub Deploy Key проекта;
- root SSH-ключ 910 для доступа к PVE;
- `known_hosts` PVE;
- PVE CA;
- постоянный PVE API credential.

В `state/` находятся как минимум:

- Raft-данные OpenBao;
- постоянный OpenTofu state;
- база и служебные данные Semaphore;
- постоянная Ansible-идентичность;
- постоянные секреты 910.

`access/` подключается в 910 как `/mnt/pve-access` только для чтения.

`state/` подключается в 910 как `/mnt/persistent-state` для чтения и записи.

`pve-only/` в 910 не монтируется.

## 3. Чего на PVE не должно требоваться

Новая архитектура не требует старого контура развёртывания:

```text
/etc/proxmox-deployer/
/var/lib/proxmox-deployer/
/var/lib/pvedeploy/
/var/log/proxmox-deployer/

pvedeploy
deploy-guest
sync-management-keys
pve-configuration-status
```

На PVE также не должны постоянно работать или устанавливаться:

- Docker;
- Semaphore;
- OpenTofu;
- Ansible;
- Packer.

Постоянная закрытая Git-копия проекта на PVE не хранится.

При этом сами файлы OpenTofu state, Semaphore, OpenBao и других сервисов 910 физически могут находиться в `/mnt/bindmounts/infra-manager/state/`. Их владельцем по смыслу остаётся управляющий контур 910, а PVE только предоставляет постоянное хранилище.

GitHub Deploy Key также хранится на PVE, потому что он требуется для восстановления 910 до запуска самого 910.

Оставшиеся объекты старой реализации удаляются как наследие после подтверждённого перехода.

## 4. Что не управляется постоянным OpenTofu 910

OpenTofu внутри 910 не управляет:

- физическим PVE как отдельным ресурсом;
- объектом VMID 910 в своём постоянном состоянии;
- собственным PVE API-токеном;
- root SSH-ключом доступа к PVE;
- каталогом `/mnt/bindmounts/infra-manager/`;
- базовыми хранилищами и мостом PVE.

Эта основа принадлежит первоначальному контуру и штатной конфигурации Proxmox.

## 5. Проверка

Проверка PVE должна подтверждать:

- наличие PVE;
- `vmbr0`;
- `local` и `local-lvm`;
- корректную принадлежность VMID 910;
- запуск 910;
- pool `managed`;
- наличие `root@pam!infra-manager`;
- `privsep=0`;
- отсутствие отдельной ACL-матрицы 910;
- рабочий root SSH из 910 к PVE;
- наличие и корректное подключение `access/` и `state/`;
- недоступность `pve-only/` из 910;
- успешную внутреннюю проверку 910.

Детальная проверка Semaphore, OpenTofu, Ansible, Packer и OpenBao выполняется внутри 910 командой `infra-manager-status`.

## 6. Повторное применение

Повторный публичный сценарий первоначальной подготовки:

- повторно использует существующий корректный 910;
- не пересоздаёт его без явной причины;
- не перевыпускает API-токен без необходимости;
- сохраняет `pve-only/`, `access/` и `state/`;
- получает актуальный проект;
- повторно применяет общий путь `deploy-guest → Ansible`;
- не создаёт новый пустой OpenTofu state поверх существующей инфраструктуры;
- останавливается при неоднозначном или опасном состоянии.

Отдельный `setup` для 910 не используется.
