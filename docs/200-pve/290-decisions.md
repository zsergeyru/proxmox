> Почему PVE-хост подготавливается и управляется именно таким образом?

## 1. Решения по первоначальной подготовке и конфигурации

### 1.1. Почему Public Bootstrap отделён от PVE Configuration

**Проблема.**  
Новый PVE-хост сначала должен получить минимально необходимую среду и доступ к закрытому проекту, а затем перейти под постоянное управление. Если объединить оба этапа в один большой сценарий, первоначальная точка входа становится сложной и начинает дублировать постоянную конфигурацию.

**Рассмотренные варианты.**

- один сценарий выполняет всю подготовку и постоянную конфигурацию;
- первоначальная настройка выполняется вручную;
- Public Bootstrap выполняет только подготовку к запуску постоянной конфигурации, после чего управление передаётся PVE Configuration.

**Принятое решение.**  
Public Bootstrap и PVE Configuration являются двумя разными этапами с разной ответственностью.

**Почему.**

- публичная точка входа остаётся небольшой и проверяемой;
- закрытая логика проекта не дублируется в публичном сценарии;
- постоянную конфигурацию можно повторно применять без повторного первоначального запуска;
- ясна граница между получением доверенного проекта и управлением самим PVE-хостом.

**Последствия и ограничения.**

- первоначальное развёртывание состоит минимум из двух логических этапов;
- между ними должен существовать чёткий контракт передачи управления;
- Public Bootstrap не должен постепенно превращаться во вторую систему конфигурации.

**Когда пересматривать.**  
Если появится единый механизм, который сможет безопасно получать доверенный проект и одновременно обеспечивать повторяемую постоянную конфигурацию без смешения этих обязанностей.

### 1.2. Почему Public Bootstrap остаётся минимальным

**Проблема.**  
На этапе первого запуска можно установить и настроить почти всё необходимое для PVE, но тогда первоначальный сценарий становится большим, трудным для проверки и тесно связанным с текущей реализацией проекта.

**Рассмотренные варианты.**

- выполнять полную настройку PVE непосредственно в Public Bootstrap;
- оставлять большую часть действий оператору;
- выполнять только минимальные действия, необходимые для получения доверенной конфигурации и её запуска.

**Принятое решение.**  
Public Bootstrap выполняет только минимальную подготовку среды и передачу управления PVE Configuration.

**Почему.**

- меньше кода выполняется до получения доверенной версии закрытого проекта;
- упрощается повторный запуск;
- уменьшается дублирование;
- постоянная логика остаётся в одном месте.

**Последствия и ограничения.**

- в Public Bootstrap нельзя добавлять удобные, но необязательные настройки только ради сокращения последующего этапа;
- новая функция должна сначала проверяться на принадлежность постоянной конфигурации.

**Когда пересматривать.**  
Если для безопасного запуска PVE Configuration потребуется дополнительный обязательный минимальный этап, который невозможно разумно выполнить уже после передачи управления.

### 1.3. Почему обычный запуск не выполняет полное обновление системы

**Проблема.**  
Полное обновление пакетов во время первоначальной подготовки удобно, но оно расширяет объём изменений, увеличивает вероятность появления посторонних ошибок и смешивает подготовку проекта с обслуживанием операционной системы.

**Рассмотренные варианты.**

- всегда выполнять полное обновление системы;
- никогда не обновлять пакеты в рамках проекта;
- устанавливать только необходимые зависимости, а полное обновление выполнять только отдельным явным действием.

**Принятое решение.**  
Обычный запуск не выполняет полное обновление системы. Такое обновление допускается только как отдельное явно выбранное действие.

**Почему.**

- первоначальная подготовка остаётся предсказуемой;
- проще определить источник ошибки;
- обслуживание ОС не смешивается с конфигурацией проекта;
- оператор сохраняет контроль над более широкими изменениями хоста.

**Последствия и ограничения.**

- обновление системы требует отдельной операции;
- проект не гарантирует, что все пакеты PVE всегда находятся на самой новой доступной версии после обычного запуска.

**Когда пересматривать.**  
Если обновление всей системы станет обязательным предварительным условием для поддерживаемой версии проекта или будет введена отдельная формальная политика обновлений PVE.

### 1.4. Почему один запуск работает с одной зафиксированной ревизией проекта

**Проблема.**  
Во время длинного запуска удалённый репозиторий может измениться. Если разные этапы одного запуска используют разные версии кода, результат перестаёт быть воспроизводимым.

**Рассмотренные варианты.**

- читать текущую ветку перед каждым этапом;
- автоматически обновлять код в середине выполнения;
- определить одну конкретную ревизию в начале управляемого запуска и использовать только её.

**Принятое решение.**  
Один запуск PVE Configuration использует одну зафиксированную Git-ревизию проекта.

**Почему.**

- все этапы выполняются по согласованному набору кода и данных;
- результат можно связать с конкретной версией проекта;
- проще диагностировать ошибку и повторить запуск;
- изменение ветки во время выполнения не меняет уже начатую операцию.

**Последствия и ограничения.**

- новая версия проекта применяется только новым управляемым запуском;
- требуется сохранять принятую ревизию в локальном состоянии.

**Когда пересматривать.**  
Если механизм выполнения будет обеспечивать эквивалентную атомарность и воспроизводимость без явной фиксации одной ревизии.

## 2. Решения по доверенному коду и локальному состоянию

### 2.1. Почему на PVE хранится каноническая доверенная копия репозитория

**Проблема.**  
Локальным административным средствам нужен код проекта. Его можно каждый раз получать заново, запускать прямо из временной копии или поддерживать одну постоянную доверенную копию на PVE.

**Рассмотренные варианты.**

- выполнять сценарии непосредственно из временно загруженного кода;
- каждый инструмент самостоятельно клонирует проект;
- хранить одну каноническую локальную копию, используемую средствами управления.

**Принятое решение.**  
На PVE поддерживается одна каноническая доверенная копия репозитория проекта.

**Почему.**

- все локальные средства используют один источник кода;
- проще проверять происхождение и ревизию;
- не возникает нескольких независимо обновляемых копий;
- можно централизованно проверять целостность и локальные изменения.

**Последствия и ограничения.**

- эта копия становится частью доверенной границы PVE;
- её права и способ обновления должны контролироваться;
- она не должна использоваться как обычный рабочий каталог для ручной разработки.

**Когда пересматривать.**  
Если код проекта будет поставляться как подписанный пакет, образ или другой неизменяемый артефакт с не меньшими гарантиями происхождения и воспроизводимости.

### 2.2. Почему доверенная копия проекта принадлежит root

**Проблема.**  
Ограниченный служебный пользователь должен выполнять отдельные операции, но возможность изменять код, который затем запускается с повышенными полномочиями, фактически дала бы ему возможность обойти ограничение прав.

**Рассмотренные варианты.**

- разрешить служебному пользователю изменять локальную копию проекта;
- хранить код в общем каталоге с групповой записью;
- оставить доверенную копию доступной для изменения только root.

**Принятое решение.**  
Каноническая копия проекта находится под управлением root и недоступна ограниченному служебному пользователю для изменения.

**Почему.**

- ограниченный пользователь не может подменить код перед запуском привилегированной операции;
- сохраняется граница между доверенным кодом и рабочим окружением;
- права служебного пользователя остаются действительно ограниченными.

**Последствия и ограничения.**

- обновление доверенной копии требует привилегированного механизма;
- служебные процессы не могут самостоятельно исправлять или обновлять исходный код.

**Когда пересматривать.**  
Если привилегированные операции перестанут исполнять код из локальной копии либо будет введён другой надёжный механизм проверки неизменности и подписи исполняемого кода.

### 2.3. Почему локальные изменения в доверенной копии не удаляются автоматически

**Проблема.**  
В канонической копии могут неожиданно появиться ручные изменения или посторонние файлы. Автоматический сброс сделал бы запуск удобнее, но мог бы скрыть вмешательство или уничтожить данные, происхождение которых неизвестно.

**Рассмотренные варианты.**

- всегда выполнять принудительный сброс и очистку;
- молча игнорировать локальные изменения;
- останавливать управляемую операцию и требовать явного разбора причины.

**Принятое решение.**  
Неожиданные локальные изменения считаются отклонением и блокируют управляемую операцию. Они не удаляются автоматически.

**Почему.**

- система не уничтожает неизвестные данные без явного решения;
- изменение доверенного кода не остаётся незамеченным;
- причина расхождения должна быть установлена до продолжения работы.

**Последствия и ограничения.**

- случайный файл может остановить автоматизацию;
- безопасные технические файлы, которые неизбежно создаются средой выполнения, требуют отдельного явного исключения;
- восстановление чистого состояния иногда требует ручного действия.

**Когда пересматривать.**  
Если локальная копия станет неизменяемым артефактом, который всегда можно безопасно заменить целиком без риска потери уникальных данных.

### 2.4. Почему код, локальное состояние и секреты разделены

**Проблема.**  
Код проекта, изменяемое служебное состояние и секреты имеют разный жизненный цикл и разные требования к доступу. Их можно было хранить рядом для простоты, но это смешало бы воспроизводимые и уникальные данные.

**Рассмотренные варианты.**

- хранить всё внутри локальной копии Git;
- хранить все данные в одном общем служебном каталоге;
- разделить доверенный код, постоянную конфигурацию, изменяемое состояние и защищённые данные.

**Принятое решение.**  
Код проекта, локальная конфигурация, служебное состояние и секреты хранятся раздельно.

**Почему.**

- обновление кода не затрагивает уникальные данные хоста;
- секреты не попадают в Git;
- можно задавать разные права доступа;
- резервное копирование и восстановление можно строить по типу данных.

**Последствия и ограничения.**

- структура PVE-хоста состоит из нескольких областей;
- для полного восстановления недостаточно одной локальной копии Git;
- каждому виду данных нужен понятный владелец и правило восстановления.

**Когда пересматривать.**  
Если будет внедрено единое защищённое хранилище, которое сможет сохранять те же границы доступа и жизненного цикла без физического разделения данных.

### 2.5. Почему сохранённое состояние и фактическая проверка разделены

**Проблема.**  
Последний успешный запуск показывает, что было настроено в тот момент, но не гарантирует, что состояние хоста не изменилось позже.

**Рассмотренные варианты.**

- считать сохранённый результат достаточным подтверждением текущего состояния;
- всегда выполнять полную проверку при любом просмотре состояния;
- отдельно хранить результат последнего запуска и предоставлять явную проверку фактического состояния.

**Принятое решение.**  
Сохранённое состояние и проверка текущего фактического состояния являются разными операциями.

**Почему.**

- быстрый просмотр не требует повторной проверки всего хоста;
- при необходимости можно явно проверить реальное состояние;
- пользователь видит разницу между историческим результатом и текущим соответствием требованиям.

**Последствия и ограничения.**

- сохранённый статус сам по себе не является доказательством текущего соответствия;
- инструменты и документация должны явно различать эти два вида информации.

**Когда пересматривать.**  
Если будет введён постоянный надёжный механизм наблюдения, который сможет поддерживать актуальное фактическое состояние без отдельного запуска проверки.

## 3. Решения по локальному управлению PVE-хостом

### 3.1. Почему используется отдельный системный пользователь для ограниченных операций

**Проблема.**  
Часть операций требует доступа к гостевым системам и локальным данным, но не требует полного административного доступа ко всему PVE-хосту.

**Рассмотренные варианты.**

- выполнять все действия только от root;
- использовать обычного пользовательского администратора;
- выделить отдельного системного пользователя с ограниченной областью доступа.

**Принятое решение.**  
Для ограниченного локального выполнения используется отдельный системный пользователь, а привилегированные действия остаются за root.

**Почему.**

- уменьшается объём кода, работающего с полными правами;
- можно отдельно контролировать доступ к ключам, журналам и рабочим данным;
- граница между доверенным привилегированным кодом и ограниченным выполнением становится явной.

**Последствия и ограничения.**

- нужно поддерживать права сразу для двух уровней выполнения;
- некоторые операции требуют перехода от root к ограниченному пользователю;
- неверно выставленные права могут либо нарушить работу, либо ослабить границу безопасности.

**Когда пересматривать.**  
Если локальные операции будут вынесены в отдельную изолированную службу или другой механизм, который обеспечит более сильное разделение полномочий.

### 3.2. Почему оператор использует стабильные локальные команды

**Проблема.**  
Административные действия можно запускать непосредственно из файлов репозитория, но тогда оператору нужно знать внутреннюю структуру проекта, а интерфейс меняется вместе с расположением исходного кода.

**Рассмотренные варианты.**

- запускать сценарии непосредственно из репозитория;
- использовать набор длинных команд и путей;
- устанавливать небольшой набор стабильных локальных команд как внешний интерфейс PVE-хоста.

**Принятое решение.**  
Основные административные операции предоставляются через стабильные локальные команды.

**Почему.**

- оператору не нужно знать внутреннее расположение исходного файла;
- можно проверять доверенную ревизию и окружение до запуска основной логики;
- внутреннюю структуру репозитория можно менять без изменения привычного интерфейса;
- одинаковый интерфейс доступен человеку и автоматизации.

**Последствия и ограничения.**

- локальные команды нужно устанавливать и поддерживать вместе с PVE Configuration;
- изменение их контракта должно быть осознанным и совместимым с документацией.

**Когда пересматривать.**  
Если появится другой устойчивый интерфейс управления PVE-хостом, например отдельный локальный API или служба, которая полностью заменит команды оператора.

### 3.3. Почему изменяющие операции используют общую блокировку

**Проблема.**  
Несколько средств управления могут одновременно изменять общие файлы, доверенную копию проекта или объекты Proxmox. Независимые блокировки каждого средства не защищают от конфликтов между ними.

**Рассмотренные варианты.**

- не запрещать параллельный запуск;
- использовать отдельную блокировку для каждого инструмента;
- использовать одну общую блокировку для операций, способных конфликтовать между собой.

**Принятое решение.**  
Изменяющие операции общего контура PVE используют единую блокировку.

**Почему.**

- два инструмента не меняют одновременно одну доверенную копию или общее состояние;
- проще рассуждать о последовательности изменений;
- уменьшается риск частично применённой конфигурации из-за конкурирующих запусков.

**Последствия и ограничения.**

- независимые по сути операции иногда будут ждать друг друга;
- долгий или аварийный процесс может временно блокировать другой запуск;
- при добавлении нового изменяющего инструмента нужно явно решить, входит ли он в общий контур блокировки.

**Когда пересматривать.**  
Если операции будут разделены на независимые области состояния и появится доказуемо безопасная модель более мелких блокировок.

## 4. Решения по базовому шаблону

### 4.1. Почему используется единый базовый шаблон

**Проблема.**  
Гостевые системы можно создавать с нуля, из нескольких специализированных шаблонов или из одного общего минимального шаблона.

**Рассмотренные варианты.**

- каждый раз устанавливать ОС с нуля;
- поддерживать отдельный шаблон для каждого типа сервиса;
- использовать один минимальный базовый шаблон, а различия вносить на следующих этапах.

**Принятое решение.**  
Для стандартных Linux-VM используется единый минимальный базовый шаблон.

**Почему.**

- меньше шаблонов нужно сопровождать;
- базовая ОС создаётся одинаково;
- прикладные различия не зашиваются в образ;
- проще проверять и обновлять базовый контракт.

**Последствия и ограничения.**

- специализированная настройка выполняется после клонирования;
- шаблон должен оставаться достаточно общим;
- сервисы с принципиально другими требованиями могут потребовать отдельного подхода.

**Когда пересматривать.**  
Если появятся классы гостей с настолько различающимися базовыми требованиями, что единый шаблон начнёт усложнять развёртывание или увеличивать риск ошибок.

### 4.2. Почему версия контракта шаблона отделена от версии PVE Configuration

**Проблема.**  
Код конфигуратора и контракт базового шаблона изменяются с разной частотой. Одна общая версия не позволяет понять, изменился ли сам шаблон или только механизм его создания и проверки.

**Рассмотренные варианты.**

- использовать одну общую версию всего PVE-контура;
- определять совместимость только по дате или Git-ревизии;
- вести отдельную версию контракта шаблона.

**Принятое решение.**  
Контракт базового шаблона имеет собственную версию, независимую от версии PVE Configuration.

**Почему.**

- изменение конфигуратора не требует искусственно менять версию шаблона;
- можно явно определить, соответствует ли существующий шаблон ожидаемому контракту;
- проще решать, требуется ли пересоздание шаблона.

**Последствия и ограничения.**

- в системе существует несколько разных версий с разным смыслом;
- документация и проверки должны явно различать версию конфигуратора и версию шаблона.

**Когда пересматривать.**  
Если базовый шаблон перестанет быть отдельным долговечным артефактом и будет всегда создаваться заново вместе с каждым развёртыванием.

### 4.3. Почему шаблон проверяется полным клонированием

**Проблема.**  
Проверка только конфигурационных параметров шаблона не доказывает, что из него действительно можно создать рабочую VM, загрузить её и получить ожидаемую базовую среду.

**Рассмотренные варианты.**

- проверять только параметры шаблона;
- считать успешное создание шаблона достаточным;
- дополнительно создавать полный клон и проверять его запуск и базовое состояние.

**Принятое решение.**  
Контракт шаблона подтверждается отдельной проверкой полного клонирования.

**Почему.**

- проверяется реальный путь, которым затем пользуется развёртывание;
- обнаруживаются ошибки, которые невозможно увидеть только по конфигурации шаблона;
- подтверждается работоспособность диска, загрузки, cloud-init и гостевого агента как единой цепочки.

**Последствия и ограничения.**

- проверка занимает больше времени и ресурсов;
- для неё нужен временный свободный идентификатор VM;
- успешный результат относится к состоянию шаблона на момент проверки.

**Когда пересматривать.**  
Если технология создания гостей изменится так, что полный клон перестанет быть реальным рабочим путём или появится равноценная автоматическая проверка готового артефакта.

### 4.4. Почему неуспешный проверочный клон не удаляется автоматически

**Проблема.**  
После неуспешной проверки временную VM можно автоматически удалить и освободить идентификатор, но вместе с ней исчезают данные, необходимые для понимания причины отказа.

**Рассмотренные варианты.**

- всегда удалять временную VM;
- никогда не удалять её автоматически;
- удалять только успешно проверенный клон, а неуспешный оставлять для диагностики.

**Принятое решение.**  
Успешный проверочный клон удаляется автоматически, а объект с неуспешной или прерванной проверкой сохраняется для диагностики.

**Почему.**

- остаётся возможность изучить реальное состояние после сбоя;
- автоматизация не уничтожает потенциально важные диагностические данные;
- успешная проверка при этом не оставляет постоянный служебный объект.

**Последствия и ограничения.**

- после неудачи временный идентификатор может остаться занятым;
- перед повторной проверкой оператору иногда требуется осознанно удалить оставленный объект;
- автоматизация должна уметь отличать свой проверочный объект от посторонней VM.

**Когда пересматривать.**  
Если диагностические данные будут надёжно сохраняться отдельно до удаления проверочного клона или появится полностью воспроизводимая изолированная среда проверки.
