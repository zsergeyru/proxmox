## 1. Назначение и границы

Этот раздел определяет общие правила безопасности для всего проекта.

Он нужен для того, чтобы было понятно:

- кто и к каким системам может получать доступ;
- почему разные способы доступа разделяются;
- почему автоматизация не должна использовать учётные данные человека;
- где должны находиться реальные технические ограничения;
- как должны храниться секреты;
- как выдаются, изменяются и отзываются полномочия.

Этот документ не описывает точные роли, ACL, имена пользователей, пути к ключам и команды.

Подробности распределяются следующим образом:

- доступ к Proxmox — `710-pve-access.md`;
- административный SSH — `720-ssh-access.md`;
- причины ключевых решений — `790-decisions.md`;
- конкретные учётные данные отдельной гостевой системы — в документации этой гостевой системы;
- прикладные учётные записи конкретного сервиса — в документации самого сервиса.

## 2. Основные принципы безопасности

### 2.1. Минимально необходимые права

Каждая учётная запись, ключ или токен должны получать только те права, которые нужны для своей задачи.

Если для операции достаточно чтения, право записи не выдаётся.

Если доступ нужен только к части инфраструктуры, он не должен автоматически распространяться на остальные объекты.

Расширение прав должно быть отдельным осознанным действием.

### 2.2. Разделение способов доступа

Разные способы доступа считаются независимыми друг от друга.

Например:

- право в Proxmox не означает право входа по SSH;
- SSH-доступ к гостю не означает право менять объект VM/LXC через Proxmox;
- доступ к Git не означает право управлять PVE;
- доступ к одной гостевой системе не означает доступ ко всем остальным.

Наличие одного способа доступа не должно использоваться для скрытого обхода ограничений другого.

### 2.3. Отдельные учётные записи для разных задач

Учётные данные человека, автоматизации и отдельных служебных механизмов должны разделяться там, где это возможно.

Например, человек и AI-агент не должны без необходимости использовать одну и ту же техническую идентичность.

Такое разделение позволяет:

- ограничивать права независимо;
- отзывать один вид доступа, не затрагивая остальные;
- понимать источник выполненного действия;
- менять автоматизацию без передачи личных учётных данных.

### 2.4. Техническое ограничение полномочий

Критичные ограничения должны обеспечиваться средствами самой инфраструктуры.

Текстовое правило вида «этот агент не должен выполнять такую операцию» полезно, но не заменяет:

- ACL;
- отдельную роль;
- отдельный токен;
- ограниченный SSH-ключ;
- ограничение на запись;
- другие технические средства контроля.

Ошибка программы или AI не должна автоматически превращаться в дополнительные полномочия.

### 2.5. Секреты не хранятся в Git

В Git запрещено хранить действующие:

- закрытые ключи;
- пароли;
- секретные токены;
- другие данные, которые непосредственно дают доступ к системе.

В Git можно хранить:

- требования к наличию секрета;
- имя или назначение учётных данных;
- открытые ключи, если их публикация допустима;
- описание места и способа получения секрета;
- правила его использования и смены.

Фактическое значение секрета должно находиться в отдельном защищённом месте.

## 3. Виды доступа

### 3.1. Proxmox

Доступ к Proxmox используется для управления объектами виртуализации и другими функциями PVE.

Он может включать:

- вход пользователя;
- API-токен;
- роль;
- набор привилегий;
- ACL на конкретные объекты или области.

Подробная модель определяется в `710-pve-access.md`.

### 3.2. SSH

SSH используется для административного доступа к операционной системе PVE или гостевой системы там, где это предусмотрено архитектурой.

SSH является отдельным контуром доступа и не наследует права из Proxmox.

В проекте должны различаться:

- вход человека;
- доступ PVE к гостям;
- доступ управляющих систем к другим гостям;
- другие служебные SSH-идентичности.

Подробные правила ключей, регистрации, распространения и отзыва находятся в `720-ssh-access.md`.

### 3.3. Git

Доступ к Git используется для чтения и изменения проектных файлов.

Чтение и запись являются разными полномочиями.

Система, которой требуется только получать конфигурацию или документацию, не должна автоматически получать право изменять репозиторий.

Если записи требует автоматизация, её область должна быть ограничена задачей этой автоматизации.

### 3.4. Доступ между системами

Некоторые гостевые системы должны обращаться к другим системам проекта.

Такой доступ должен быть:

- явно предусмотрен;
- связан с конкретной задачей;
- ограничен необходимой областью;
- независим от личных учётных данных человека.

Наличие технической возможности соединиться по сети само по себе не означает наличие административного права.

### 3.5. Внешние системы

Проект может использовать внешние службы, например Git, облачные службы или другие интерфейсы.

Для каждого такого доступа должно быть определено:

- какая система его использует;
- зачем он нужен;
- какие права требуются;
- где хранится секрет;
- как доступ отзывается или меняется.

Внешний доступ не должен выдавать больше полномочий, чем требуется для функции проекта.

## 4. Учётные данные и их жизненный цикл

### 4.1. Учётные записи и токены

Учётная запись или токен должны иметь:

- понятное назначение;
- владельца в архитектуре;
- определённую область прав;
- понятный способ создания;
- возможность проверки;
- определённый порядок отзыва.

Техническая учётная запись не должна использоваться для задач, для которых она не предназначена.

### 4.2. SSH-ключи

Каждая постоянная SSH-идентичность должна иметь понятное назначение.

Для неё должно быть известно:

- где находится закрытый ключ;
- где зарегистрирован открытый ключ;
- какие системы принимают этот ключ;
- кто имеет право использовать закрытую часть;
- как выполняется смена и отзыв.

Закрытый ключ не должен копироваться в дополнительные места без необходимости.

### 4.3. Хранение секретов

Секрет должен храниться только там, где он действительно нужен для работы.

При выборе места хранения учитываются:

- права доступа к файлу или хранилищу;
- возможность резервного восстановления;
- возможность безопасной смены;
- количество копий;
- риск раскрытия при обычной работе системы.

Критичный секрет не должен существовать в единственном месте без заранее определённого способа восстановления или смены.

### 4.4. Выдача и изменение прав

Выдача нового доступа должна включать:

1. определение задачи;
2. выбор отдельной идентичности, если это возможно;
3. выдачу минимально необходимых прав;
4. проверку фактического доступа;
5. фиксацию постоянного требования в соответствующей документации или конфигурации.

Изменение прав не должно происходить как побочный эффект несвязанной операции.

### 4.5. Смена и отзыв

Смена ключа, токена или другого секрета должна выполняться как управляемая операция.

Для неё важно определить:

- новый секрет;
- где он должен быть установлен;
- как проверить новый доступ;
- когда можно отозвать старый;
- какие зависимые системы нужно обновить.

Если старый доступ нельзя безопасно отозвать автоматически, это должно быть явно указано.

### 4.6. Потеря и восстановление

Для важных учётных данных должно быть заранее понятно, что делать при их потере.

Возможны два основных случая:

- секрет можно безопасно создать заново и зарегистрировать как новую идентичность;
- секрет нужно восстановить из защищённой копии, потому что его смена затрагивает другие системы.

Потерянный закрытый ключ или токен не должен незаметно заменяться новым под видом прежнего, если от его идентичности зависят доверие или права в других системах.

## 5. Границы ответственности

### 5.1. Общие правила

`700-overview.md` описывает только общую модель безопасности:

- минимальные права;
- разделение способов доступа;
- разделение идентичностей;
- обращение с секретами;
- общие правила жизненного цикла доступа.

Он не является справочником конкретных пользователей, токенов или ключей.

### 5.2. Что относится к `710-pve-access.md`

В `710-pve-access.md` должны находиться:

- учётные записи Proxmox;
- API-токены;
- роли;
- наборы привилегий;
- ACL;
- области доступа;
- назначение технических идентичностей Proxmox;
- правила выдачи и отзыва доступа на уровне PVE.

### 5.3. Что относится к `720-ssh-access.md`

В `720-ssh-access.md` должны находиться:

- административные SSH-идентичности проекта;
- правила хранения закрытых ключей;
- регистрация открытых ключей;
- распространение ключей;
- проверка отпечатков;
- смена и отзыв;
- поведение при потере ключа;
- границы между разными SSH-контурами.

### 5.4. Что относится к документации конкретных систем

Если правило касается только одной VM/LXC или одного приложения, оно должно находиться рядом с этой системой.

Например:

- конкретный служебный пользователь внутри одной VM;
- прикладной токен одного сервиса;
- путь к локальному файлу учётных данных;
- права конкретного приложения;
- отдельный доступ к внешнему сервису.

Общий раздел безопасности должен содержать только правила, применимые к нескольким системам или ко всему проекту.
