## 1. Основной принцип

Проект не строится вокруг одного общего ключа.

Требуемые права хранятся в Git как несекретные правила. Внутренние секреты и краткоживущие полномочия выдаёт OpenBao. Конечная система дополнительно проверяет собственные ограничения.

~~~text
Git
→ кто к чему должен иметь доступ

OpenBao
→ можно ли выдать этому субъекту нужный secret или временное полномочие

PVE / SSH / Git
→ что с полученным полномочием реально разрешено сделать
~~~

Секреты не хранятся в Git.

## 2. Границы доверия

### 2.1. PVE

Физический PVE является нижней доверенной границей проекта.

На нём находится постоянное состояние управляющего контура и данные, которые специально не показываются 910.

### 2.2. infra-manager

`910 infra-manager` — доверенный административный контур.

Он управляет жизненным циклом инфраструктуры, но не должен постоянно владеть ключом снятия блокировки OpenBao или recovery private key для всех Linux-гостей.

### 2.3. Обычные гости

Обычный гость получает только собственную машинную идентичность и только те полномочия, которые заданы для него в политике доступа.

Компрометация одного гостя не должна автоматически давать права другого гостя или `infra-manager`.

### 2.4. Человек

Личные ключи и интерактивные учётные данные человека не становятся постоянными credentials автоматизации.

## 3. Роль OpenBao

OpenBao является центральным хранилищем внутренних секретов и центром выдачи технического доступа.

Он хранит:

- KV secrets;
- закрытые SSH CA;
- policies и roles;
- служебное состояние машинной аутентификации.

Он выдаёт:

- короткоживущие SSH-сертификаты для `infra-manager`;
- серверные SSH-сертификаты;
- одноразовый ограниченный SSH-доступ между гостями;
- рабочие credentials PVE, Git и внутренних сервисов согласно policy.

Требуемая матрица прав задаётся не вручную в OpenBao, а в `infrastructure/security/access.yaml`.

## 4. Виды доступа

### 4.1. infra-manager → Linux

Штатный вход выполняется по короткоживущему сертификату, подписанному OpenBao SSH Client CA.

### 4.2. Linux-гость → Linux-гость

Ограниченный доступ проходит через централизованную онлайн-авторизацию OpenBao. Постоянные public keys каждого источника не разносятся по целевым серверам.

### 4.3. Доступ к PVE

`infra-manager` и менее доверенные контуры используют разные PVE identities.

OpenBao контролирует выдачу рабочего API credential, а PVE ACL остаётся окончательной границей полномочий.

### 4.4. Git

Рабочий read-only credential хранится в OpenBao KV и выдаётся только разрешённым субъектам.

### 4.5. Подлинность SSH-серверов

Отдельный SSH Host CA OpenBao подтверждает серверную идентичность управляемых Linux-гостей.

## 5. Аварийное восстановление

OpenBao не должен быть единственным способом восстановить доверие к самому OpenBao.

Поэтому на PVE отдельно хранятся:

- ключ снятия блокировки;
- служебный доступ восстановления OpenBao;
- recovery SSH administrator key для управляемых Linux-гостей;
- recovery-копия GitHub read-only Deploy Key.

Recovery private keys не монтируются в 910 и не используются как автоматический запасной путь.

Если OpenBao полностью потерян, recovery SSH позволяет установить новый публичный SSH CA на серверы, а recovery Git credential — снова получить проект.
