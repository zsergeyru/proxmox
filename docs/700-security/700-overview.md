## 1. Основная модель

Проект не использует один общий ключ или одну общую административную учётную запись для всех задач.

Разные действия имеют разные механизмы доверия:

```text
управление PVE
≠ административный SSH в Linux
≠ проверка подлинности SSH-сервера
≠ межмашинный SSH guest → guest
≠ чтение Git
≠ выполнение задания Semaphore
≠ доступ к OpenBao
```

Компрометация одного механизма не должна автоматически выдавать остальные полномочия.

Секреты не хранятся в Git. Машинные права задаются отдельно от самих секретов.

## 2. Границы доверия

### 2.1. PVE

Физический PVE-хост является корневой доверенной системой инфраструктуры.

Он:

- владеет объектами виртуализации;
- создаёт первоначальный управляющий контур;
- хранит PVE-only данные, которые не выдаются обычным гостям;
- участвует в безопасной разблокировке и административных операциях OpenBao;
- подтверждает идентичность VM/LXC перед выпуском доверенного host certificate.

### 2.2. 910 infra-manager

`guest:910` является доверенным административным исполнителем инфраструктуры.

Он:

- управляет PVE через API;
- выполняет узкие хостовые операции через отдельный root SSH к PVE;
- запускает OpenTofu, Ansible и Packer;
- содержит Semaphore и OpenBao;
- применяет машинный контракт `access.yaml`.

Компрометация 910 рассматривается как компрометация административного управления PVE, но даже внутри 910 отдельные credentials не объединяются без необходимости.

### 2.3. 410 AI-control

`guest:410` не получает прямой административный PVE API и root SSH к PVE.

Для прямого обращения к операторской команде `infra-manager` на PVE принято отдельное **целевое**, пока не реализованное правило: выделенная ограниченная SSH-идентичность с краткоживущим сертификатом OpenBao, принудительной проверкой команд на PVE и обязательным исключением секретов из вывода.

```text
410 Hermes
 ↓ разрешённая операция через ограниченный SSH
PVE: infra-manager (без trusted-pve)
 ↓
910 infra-manager
 ↓
PVE / OpenTofu / Ansible
```

Semaphore остаётся отдельным способом запуска заданий, но в этом маршруте не участвует. SSH-вход 410 на PVE не даёт обычной оболочки, root SSH или административного PVE API. Пока технический доступ не настроен; действующие разрешения 410 в `access.yaml` касаются заданий Semaphore.

### 2.4. Обычные гости

Обычный гость получает только права, явно присутствующие в `access.yaml`.

Наличие гостя в проекте, в `pool managed` или его профиль не выдаёт ему автоматически PVE, Git, SSH или OpenBao credentials.

## 3. Основные взаимодействия

### 3.1. Управление Proxmox

Основной канал:

```text
910 → HTTPS PVE API → Proxmox VE
```

Для операций, которым действительно нужны полномочия самого хоста:

```text
910 → отдельный root SSH → PVE
```

Эти два канала не заменяют друг друга.

### 3.2. Административный SSH в Linux-гости

Штатный путь:

```text
910 / Ansible
 → временный SSH public key
 → OpenBao client CA
 → короткоживущий user certificate
 → Linux-гость
```

Подлинность самого гостя проверяется независимо через host CA.

### 3.3. Подлинность SSH-сервера

```text
реальный SSH host key гостя
 → PVE подтверждает VMID / имя / адрес
 → OpenBao host CA
 → host certificate
 → доверяющий SSH-клиент
```

Client CA и host CA являются разными центрами доверия.

### 3.4. Межмашинный SSH

Целевая схема `guest → guest` использует OpenBao SSH OTP:

```text
access.yaml
   ↓
машинный AppRole источника
   ↓
OpenBao SSH OTP
   ↓ одноразовый пароль только к разрешённой цели
исходный гость ───────────────→ целевой гость
                                  ↓
                         проверка OTP через OpenBao
```

OTP подтверждает право клиента войти. Подлинность сервера всё равно отдельно проверяется через host CA.

### 3.5. Git

Git является отдельным контуром:

```text
субъект с github/repository/read
 → управляемый read-only credential
 → проектный репозиторий
```

Право чтения не включает запись.

### 3.6. OpenBao

OpenBao связывает несколько механизмов:

```text
OpenBao
 ├─ KV v2 → рабочие секреты PVE / Git / Semaphore
 ├─ client CA → временные сертификаты Ansible
 ├─ host CA → сертификаты SSH-серверов
 ├─ AppRole → ограниченные машинные и служебные идентичности
 └─ SSH OTP → одноразовый guest → guest доступ
```

Подробный контракт находится в [`740-openbao.md`](740-openbao.md).

## 4. Секреты и идентичности

Секретами являются:

- закрытые SSH-ключи;
- API secrets;
- пароли;
- unseal key;
- OpenBao SecretID;
- закрытые ключи SSH CA;
- одноразовые OTP до момента использования.

Открытыми данными могут быть:

- SSH public key;
- открытый ключ SSH CA;
- SSH certificate;
- RoleID, если сам по себе он не даёт доступ;
- имя технической идентичности.

Открытость данных не отменяет необходимость проверки их происхождения.

## 5. Источник прав

Машинным источником того, **кто что имеет право делать**, является:

```text
infrastructure/security/access.yaml
```

Он задаёт логические права, например:

```text
guest:910 → pve-api/guests
guest:410 → semaphore/infrastructure-task
guest:410 → ssh/guest
host:pve  → openbao/instance
```

`access.yaml` не содержит самих secrets и не описывает пути их хранения.

Технические механизмы OpenBao, PVE, Semaphore, Git и SSH должны быть производными от этого контракта там, где соответствующее право управляется проектом.

## 6. Жизненный цикл доступа

Для постоянного права должны быть понятны:

```text
создание
→ выдача
→ использование
→ проверка
→ ротация
→ отзыв
→ восстановление
```

Короткоживущие данные, такие как SSH user certificate или OTP, не восстанавливаются и не продлеваются как постоянный secret — при следующей операции выдаётся новое значение.

Удаление права из `access.yaml` должно прекращать выдачу новых полномочий. Для OTP это означает невозможность получить новый одноразовый пароль к удалённой цели.

Фактическое состояние реализации отделено от целевой модели и находится в [`780-implementation-status.md`](780-implementation-status.md).
