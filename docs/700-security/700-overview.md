## 1. Основной принцип

Безопасность проекта строится не вокруг одного общего ключа или одной общей учётной записи.

Разные задачи получают разные технические доступы:

```text
управление Proxmox
≠
административный SSH к Linux
≠
подтверждение подлинности SSH-сервера
≠
чтение Git
≠
доступ к OpenBao
```

Получение одного вида доступа не должно автоматически выдавать другой.

Секреты не хранятся в Git.

Критичные ограничения обеспечиваются техническими средствами, а не только текстовым правилом в документации или инструкцией для программы.

## 2. Границы доверия

### 2.1. PVE

Физический PVE-хост является корневой доверенной системой инфраструктуры.

На нём находятся данные, которые намеренно недоступны обычным гостям и в отдельных случаях даже управляющему контейнеру.

### 2.2. Управляющий контур

`infra-manager` является доверенным административным контуром домашнего PVE.

Его компрометация рассматривается как компрометация административного управления PVE, поэтому постоянный контур получает необходимые административные каналы напрямую, а не имитирует ограниченного прикладного пользователя.

При этом даже внутри доверенного контура разные секреты разделены по назначению.

### 2.3. Обычные гости

Прикладные гости не получают административные учётные данные PVE только потому, что они созданы проектом.

Дополнительные возможности выдаются явно.

Единым машинным источником требований доступа является `infrastructure/security/access.yaml`. `guest.yaml` и resolver не содержат второго списка административных возможностей.

### 2.4. Человек

Личные учётные данные человека не должны становиться постоянными служебными учётными данными автоматизации.

Человеческий доступ и технический доступ автоматизации имеют независимый жизненный цикл.

## 3. Виды доступа

### 3.1. Proxmox

Для управления объектами виртуализации используются PVE API и, только для операций, которым нужны полномочия самого хоста, отдельный root SSH-доступ.

Полный контракт находится в [`710-pve-access.md`](710-pve-access.md).

### 3.2. SSH

Для штатного входа автоматизации в управляемые Linux-гости используются короткоживущие SSH-сертификаты.

Для межмашинного доступа `guest → guest` используется OpenBao SSH OTP: исходный гость получает одноразовый пароль только для разрешённой цели, а целевой гость проверяет его через OpenBao во время установления соединения.

Подлинность самого SSH-сервера проверяется независимо через отдельный host CA.

Полный контракт находится в [`720-ssh-access.md`](720-ssh-access.md).

### 3.3. Git

Git-доступ не является административным SSH-доступом.

Чтение проекта и запись в проект — разные полномочия.

Полный контракт находится в [`730-git-access.md`](730-git-access.md).

### 3.4. OpenBao

OpenBao хранит закрытые ключи SSH-центров доверия, выпускает административные и серверные сертификаты и является центральной точкой выдачи и проверки одноразовых SSH-паролей для `guest → guest`.

Служебные полномочия PVE и машинные AppRole обычных гостей разделены. Гость получает только собственное ограниченное право запросить OTP для целей, разрешённых `access.yaml`.

Полный контракт находится в [`740-openbao.md`](740-openbao.md).

### 3.5. Единый контракт доступа

`access.yaml` фиксирует субъект, подсистему, ресурс, цели и разрешённые действия. Он не содержит секретов и путей их хранения.

Полный контракт находится в [`750-access-contract.md`](750-access-contract.md).

## 4. Секреты и открытые данные

К секретам относятся, например:

- закрытые SSH-ключи;
- API secrets;
- пароли;
- ключ снятия блокировки;
- OpenBao RoleID/SecretID, если их сочетание даёт служебный доступ.

Такие значения не помещаются в Git и не выводятся в обычные журналы.

Открытыми данными могут быть:

- SSH public key;
- открытый ключ центра доверия;
- сертификат;
- отпечаток;
- имя технической идентичности.

Открытость значения не означает, что его можно без проверки использовать как источник доверия. Например, открытый host key должен относиться именно к ожидаемому серверу.

## 5. Жизненный цикл доступа

Для каждого постоянного доступа должны быть определены:

```text
создание
→ хранение
→ использование
→ проверка
→ смена
→ отзыв
→ восстановление
```

Временные учётные данные должны иметь минимально необходимый срок жизни и уничтожаться после операции.

Потерянная или неожиданно изменившаяся идентичность не должна тихо заменяться новой, если это может скрыть подмену системы.

Текущее состояние реализации и известные технические ограничения отделены от нормативных правил и находятся в [`780-implementation-status.md`](780-implementation-status.md).
