## 1. Роль Git в проекте

Git хранит источник требуемого состояния проекта.

Доступ к Git является отдельным контуром доверия и не должен использовать credential от:

- административного SSH в Linux;
- root SSH к PVE;
- PVE API;
- OpenBao SSH CA;
- межмашинного SSH OTP.

Право читать репозиторий и право его изменять являются разными полномочиями.

## 2. Read-only доступ управляющего контура

`guest:910` имеет в `access.yaml` право:

```text
github / repository / zsergeyru/proxmox / read
```

Для этого используется отдельный GitHub Deploy Key без права записи.

Связь компонентов:

```text
access.yaml
   ↓ право читать проект
OpenBao KV
   ↓ рабочий read-only credential
910 / Semaphore / Git
   ↓
репозиторий proxmox
```

OpenBao хранит рабочую закрытую часть credential. PVE имеет независимую аварийную копию, необходимую для восстановления управляющего контура до готовности OpenBao.

Git credential не должен давать shell-доступ к PVE или Linux-гостям.

## 3. Чтение Git обычными гостями

Право задаётся только через `access.yaml`:

```yaml
subject: guest:<VMID>
service: github
resource: repository
targets:
  - zsergeyru/proxmox
access:
  - read
```

Сейчас право чтения проекта требуется, в частности, `guest:410` и `guest:311`.

Такое правило означает только возможность прочитать заранее определённый проект.

Оно не означает:

- право записи;
- PVE API;
- административный SSH;
- автоматическое право межмашинного SSH;
- произвольный выбор другого репозитория.

Техническая реализация должна выдавать credential с областью не шире требуемого read-only доступа и позволять независимо отозвать его.

## 4. Проверка Git-сервера

SSH-соединение с Git-провайдером должно строго проверять его host identity.

Неизвестный или неожиданно изменившийся host key не принимается автоматически.

Доверие к Git-серверу отделено от доверия к:

- PVE;
- управляемым Linux-гостям;
- SSH host CA проекта.

## 5. Право записи

`github/repository/read` никогда не включает запись.

Если автоматизации понадобится изменение репозитория, должно появиться отдельное право с:

- отдельным владельцем;
- отдельной технической идентичностью;
- явно заданной областью записи;
- собственным жизненным циклом ротации и отзыва.

Личный Git credential человека не должен превращаться в постоянный credential автоматизации.

## 6. Жизненный цикл

### 6.1. Создание

Git credential управляющего контура создаётся доверенным первоначальным механизмом и регистрируется без права записи.

### 6.2. Использование

Рабочая копия закрытой части поступает из OpenBao только тем компонентам, которым она нужна для чтения проекта.

### 6.3. Ротация

При потере или компрометации создаётся новая пара, регистрируется новый public key и отзывается прежний Deploy Key.

Тихая замена credential без обновления регистрации и проверки доверия запрещена.

### 6.4. Отзыв

Удаление права `github/repository/read` должно прекращать управляемую выдачу Git credential соответствующему субъекту, не затрагивая его остальные SSH-права.

## 7. Проверка контракта

Проверка должна подтверждать:

- Git credential отделён от PVE и административного SSH;
- `guest:910`, `guest:410`, `guest:311` получают только те Git-права, которые присутствуют в `access.yaml`;
- read-only credential не предоставляет запись;
- Git host identity проверяется строго;
- удаление права прекращает дальнейшую выдачу credential;
- аварийный Git-доступ PVE не становится обычным credential гостей.

Конкретные файлы, права и SSH-конфигурация описываются локально на тех гостях, где Git используется.
