## 1. Основной принцип

Git-доступ является отдельным контуром доверия.

SSH-ключ для Git не должен использоваться для:

- административного входа в Linux;
- root SSH к PVE;
- подписи SSH-сертификатов;
- PVE API.

Чтение и запись в репозиторий являются разными полномочиями.

Запрос на чтение никогда не должен автоматически давать право записи.

## 2. Доступ `infra-manager` к проекту

Для получения проекта используется отдельный GitHub Deploy Key без права записи.

Его назначение ограничено репозиторием проекта.

Закрытая часть:

- создаётся доверенным первоначальным контуром;
- не хранится в Git;
- после инициализации OpenBao хранится как рабочий secret `infra-secrets/data/git/github/proxmox-read`;
- материализуется для 910 только во временный файл `/run/infra-manager/secrets/github_proxmox_repo_ed25519`;
- передаётся `infra-runtime` только для чтения;
- не должна копироваться в обычные гости только потому, что им нужен Git.

Исходная bootstrap-копия на PVE и текущая переходная копия в `access/github/` пока сохраняются для первоначального запуска и последующей общей миграции старой схемы. После успешной настройки KV они не являются штатным рабочим источником.

Точный контракт хранения определён в [`740-openbao.md`](740-openbao.md), физические пути — в [`../200-pve/230-host-layout.md`](../200-pve/230-host-layout.md).

## 3. Проверка Git-сервера

Git SSH должен выполнять строгую проверку подлинности Git-сервера.

Автоматическое принятие неизвестного или изменившегося SSH host key запрещено.

Проверка GitHub host key относится только к Git-доступу и не использует `known_hosts` PVE или Linux-гостей как общий источник доверия.

## 4. Чтение проекта обычным гостем

### 4.1. Назначение

Требование чтения проекта задаётся в `access.yaml` правилом:

```yaml
subject: guest:<VMID>
service: github
resource: repository
targets:
  - zsergeyru/proxmox
access:
  - read
```

Старое `management.project_repo_read` временно сохраняется только для совместимости resolver и должно иметь эквивалентное правило в `access.yaml`.

Правило означает, что конкретному гостю требуется управляемый доступ **только для чтения** репозитория проекта.

Эта возможность не означает:

- право записи;
- административный SSH;
- PVE API;
- наличие отдельного правила SSH identity;
- автоматическую установку Git.

### 4.2. Граница выдаваемого доступа

Гость не выбирает:

- произвольный репозиторий;
- произвольный закрытый ключ;
- произвольный путь к secret;
- режим записи.

Манифест только запрашивает заранее определённую возможность проекта.

Реализация должна выдавать управляемый read-only credential с областью, не превышающей доступ к проектному репозиторию.

Допускается отдельный credential на гостя или управляемый общий read-only credential, если такая модель явно принята и сохраняет возможность безопасной ротации и отзыва.

Нельзя скрыто передавать гостю более привилегированный Git credential только потому, что технически им тоже можно прочитать проект.

### 4.3. Материализация в госте

Если credential требуется внутри гостя:

- закрытая часть должна появляться только в явно управляемом защищённом месте;
- права файла должны быть минимально необходимыми;
- Git/SSH-конфигурация должна использовать только этот credential для проектного репозитория;
- секрет нельзя передавать через аргументы командной строки или обычный журнал;
- проверка должна подтверждать реальное чтение проекта без права записи.

Удаление требования должно отзывать только управляемый Git-доступ и не затрагивать другие SSH-идентичности гостя.

## 5. Право записи

Право записи в Git является отдельным полномочием.

Оно не входит в правило `github/repository/read` и не наследуется из него.

Если автоматизации понадобится запись, для неё должен существовать отдельный:

- владелец;
- credential;
- набор прав;
- порядок ротации и отзыва;
- аудит выполняемых действий.

Личный Git credential человека не должен становиться постоянным credential автоматизации.

## 6. Жизненный цикл Git-доступа

### 6.1. Создание

Deploy Key управляющего контура создаётся первоначальным доверенным механизмом и регистрируется без права записи.

### 6.2. Повторное использование

Повторное создание управляющего контейнера должно переиспользовать существующий защищённый Deploy Key, если он цел и остаётся зарегистрированным.

### 6.3. Потеря

Потерянный Deploy Key заменяется новой парой с явной регистрацией новой открытой части и удалением старой регистрации.

Тихая генерация нового private key под прежней доверенной идентичностью запрещена.

### 6.4. Отзыв

Отзыв Git credential должен быть независим от:

- PVE API;
- root SSH;
- Ansible SSH CA;
- OpenBao.

Компрометация Git-ключа не должна требовать ротации всех остальных инфраструктурных ключей.

## 7. Проверка контракта

Проверка Git-доступа должна подтверждать:

- используется ожидаемая SSH-идентичность;
- Git-сервер проходит строгую проверку;
- проект читается;
- credential не имеет права записи, если запрошено только чтение;
- обычный гость не получает Git credential без явного правила `access.yaml`;
- Git credential не используется как административный SSH-ключ.

Текущее состояние выдачи Git credential обычным гостям находится в [`780-implementation-status.md`](780-implementation-status.md).
