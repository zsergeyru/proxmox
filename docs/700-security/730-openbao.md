# OpenBao и управление секретами

**Тип:** спецификация  
**Статус:** принято к реализации  
**Назначение:** определить роль OpenBao как центрального хранилища машинных секретов проекта, минимальную первую конфигурацию, порядок запуска, границы доверия и восстановление.

Этот документ отвечает на вопрос:

> Где хранятся машинные секреты проекта, как сервисы получают только разрешённые им значения и как OpenBao восстанавливается после перезапуска или потери 910?

## 1. Основное решение

OpenBao является центральным хранилищем машинных секретов проекта.

Первая версия намеренно использует только необходимый минимум возможностей:

~~~text
OpenBao
├── один узел внутри 910 infra-manager
├── Integrated Storage (Raft)
├── KV v2
├── policies
└── AppRole
~~~

Первая версия не требует кластера OpenBao, внешней базы данных, PKI, SSH CA, динамических учётных данных баз данных, OpenBao Agent возле каждого приложения или дополнительных плагинов.

Эти возможности добавляются только при появлении практической необходимости.

## 2. Размещение

OpenBao работает отдельным Docker-контейнером внутри 910 infra-manager.

Постоянные данные должны физически находиться под единым корнем постоянных данных Linux-гостя:

~~~text
/var/lib/persistent/openbao/
~~~

Внутри контейнера OpenBao может использовать штатный путь, связанный с этим каталогом явным bind mount.

OpenBao не является частью infra-runtime. Обновление или пересборка Semaphore не должны затрагивать процесс и данные OpenBao.

## 3. Назначение

OpenBao хранит машинные секреты, необходимые работающим сервисам и средствам управления:

- PVE API tokens;
- API-ключи AI-провайдеров;
- токены внешних и внутренних сервисов;
- VPN credentials;
- секреты автоматизации;
- другие машинные секреты, которые нельзя хранить в Git.

Git хранит не значения секретов, а политики OpenBao, описание ролей, пути секретов, требования к их наличию и повторяемую конфигурацию OpenBao.

## 4. Разделение прав

Каждая самостоятельная система или агент получает отдельную машинную идентичность и минимально необходимую политику.

Пример:

~~~text
infra-manager
→ infrastructure/*

ai-control
→ ai/shared/*
→ pve/ai-control

hermes
→ ai/hermes/*
→ ai/shared/allowed/*

agent-zero
→ ai/agent-zero/*
→ ai/shared/allowed/*
~~~

Один агент не должен автоматически получать доступ к секретам другого агента.

Политики и роли являются требуемым состоянием и хранятся в Git. Ручное создание постоянных прав только через Web UI не является штатным способом настройки.

## 5. Аутентификация приложений

Базовым способом машинной аутентификации первой версии является AppRole.

~~~text
приложение
→ собственная первоначальная AppRole-идентичность
→ OpenBao
→ краткоживущий OpenBao token
→ только разрешённые policy секреты
~~~

OpenBao не устраняет необходимость первоначально передать приложению ограниченную идентичность. Способ доставки RoleID/SecretID определяется при реализации конкретного сервиса.

OpenBao Agent не является обязательным для первой версии. Он добавляется только там, где действительно требуется автоматическое обновление токена, шаблонизация файлов или другая его функция.

## 6. Инициализация

Новый пустой OpenBao инициализируется один раз.

~~~text
новый OpenBao
→ operator init
→ создаются ключевые данные
→ сохраняются аварийные данные восстановления
→ выполняется первоначальная настройка
→ первоначальный root token перестаёт использоваться в обычной работе
~~~

Повторный запуск уже инициализированного OpenBao не должен выполнять новую инициализацию.

Аварийные данные восстановления не должны существовать только внутри 910 или только внутри самого OpenBao.

## 7. Seal и автоматический unseal

После запуска OpenBao его хранилище остаётся запечатанным до выполнения unseal.

Для домашнего сервера обычный запуск автоматизируется:

~~~text
PVE
↓
910 запускается автоматически
↓
Docker запускает OpenBao
↓
OpenBao отвечает, но sealed=true
↓
PVE передаёт ключ unseal
↓
OpenBao sealed=false
↓
клиенты получают доступ к разрешённым секретам
~~~

### 7.1. Ключ обычного запуска

Ключ автоматического unseal хранится на физическом PVE вне 910 в root-only файле с режимом 0600.

Точный путь задаётся при реализации bootstrap и не должен дублироваться несколькими независимыми сценариями.

Ключ не должен постоянно находиться внутри файловой системы 910 и не должен входить в резервную копию 910.

### 7.2. Механизм на PVE

На PVE не требуется отдельный сервер или постоянно работающий демон.

Используется небольшой systemd oneshot и штатный pct:

~~~text
systemd oneshot
→ дождаться running для LXC 910
→ через pct exec проверить OpenBao внутри 910
→ дождаться ответа API
→ определить sealed
→ при необходимости передать ключ через stdin
→ проверить sealed=false
→ завершиться
~~~

Механизм не устанавливает OpenBao CLI, Python, curl, jq или другие дополнительные пакеты на PVE. Клиент HTTP при необходимости выполняется внутри 910.

Ключ не передаётся как аргумент командной строки и не создаётся как временный файл внутри 910.

### 7.3. Границы автоматизации

Если OpenBao ещё не инициализирован, PVE не выполняет автоматическую инициализацию.

Если OpenBao уже sealed=false, дополнительное действие не требуется.

Ошибка автоматического unseal не должна блокировать загрузку PVE, но должна быть явно видна в состоянии systemd и журнале.

Перезапуск только OpenBao во время обслуживания может потребовать явного повторного запуска того же oneshot-механизма. Постоянный наблюдающий демон первой версии не требуется.

## 8. Граница доверия

Разделение хранилища и ключа защищает от получения одной только копии 910:

~~~text
резервная копия 910
→ содержит данные OpenBao
→ не содержит ключ обычного unseal

PVE
→ содержит ключ обычного unseal
~~~

Эта схема не защищает от полного административного захвата работающего PVE. PVE является корнем доверия виртуальной инфраструктуры и технически способен управлять LXC 910.

Аварийные ключи и данные восстановления OpenBao хранятся отдельно от PVE и 910.

## 9. Резервное копирование

Для Integrated Storage используется штатный Raft snapshot.

Перед стандартным резервированием постоянных данных 910 создаётся снимок:

~~~text
OpenBao
→ bao operator raft snapshot save
→ /var/lib/persistent/openbao-backup/openbao.snap
→ стандартная резервная копия /var/lib/persistent/
~~~

Рабочий каталог Raft также находится под /var/lib/persistent/, но основным переносимым объектом восстановления OpenBao считается штатный Raft snapshot.

Снимок содержит секретные данные и должен защищаться не слабее самого хранилища OpenBao.

## 10. Восстановление

Если резервная копия существует:

~~~text
развернуть новый OpenBao
→ восстановить Raft snapshot
→ использовать сохранённую схему ключей восстановления
→ проверить политики и доступы
~~~

Если база OpenBao полностью потеряна:

~~~text
создать новый OpenBao
→ заново применить policies/AppRole из Git
→ перевыпустить машинные секреты, где это возможно
→ заменить их у потребителей
~~~

Потеря OpenBao не должна делать инфраструктуру невосстановимой. Неперевыпускаемые секреты должны иметь отдельную защищённую копию или другой документированный путь восстановления.

## 11. Что остаётся вне OpenBao

OpenBao не может быть единственным источником данных, необходимых для запуска самого OpenBao.

Вне него остаются как минимум:

- ключ обычного автоматического unseal на PVE;
- аварийные данные восстановления OpenBao вне PVE и 910;
- аварийный доступ человека;
- первоначальный доступ к закрытому Git, необходимый до готовности OpenBao.

Этот набор должен оставаться минимальным.

## 12. Будущее расширение

При появлении практической необходимости отдельно рассматриваются SSH CA, PKI, OpenBao Agent, динамические учётные данные, расширенный аудит и несколько узлов OpenBao.

Наличие этих возможностей в OpenBao не является основанием включать их заранее.
