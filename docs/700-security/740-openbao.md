## 1. Роль OpenBao

OpenBao является каноническим защищённым хранилищем рабочих секретов управляющего контура, закрытых ключей двух SSH-центров доверия и центральным сервисом межмашинного SSH OTP.

В OpenBao находятся:

- рабочий PVE API secret;
- рабочий закрытый Git Deploy Key проекта;
- рабочие секреты Semaphore;
- закрытые ключи SSH client CA и SSH host CA;
- SSH-роли подписи;
- OTP-роли, полученные из `access.yaml`;
- машинные AppRole и их политики;
- служебные политики и роли доступа.

OpenBao работает внутри управляющего гостя 910, но этот документ не определяет его Docker-конфигурацию, локальные пути, systemd-службы или порядок запуска контейнера. Эти детали относятся к локальной документации 910.

Для локального управляющего контура допускается только локальный интерфейс. Для межмашинного OTP должен существовать отдельный защищённый сетевой вход, доступный только управляемым Linux-гостям, которым он нужен.

Сетевой вход для OTP обязан:

- использовать TLS;
- требовать проверку сертификата OpenBao;
- не предоставлять открытый HTTP-доступ из гостевой сети;
- быть доступным только необходимым источникам и целям;
- не смешивать административные и машинные AppRole;
- не раскрывать root token, unseal key или PVE-only данные.

## 2. Граница хранения

### 2.1. Постоянное состояние OpenBao

Постоянное состояние OpenBao хранится в Raft.

В него входят:

- KV v2 с рабочими секретами;
- закрытые ключи SSH CA;
- auth methods;
- AppRole;
- политики;
- роли SSH-подписи;
- OTP-роли SSH;
- машинные AppRole и их политики.

Raft является обязательной частью резервного состояния управляющего контура.

### 2.2. Данные только для PVE

Данные, которые нужны до получения штатного доступа к OpenBao или для аварийного восстановления, хранятся в PVE-only области и не должны быть доступны 910 как обычные постоянные файлы.

К ним относятся:

- ключ снятия блокировки;
- ограниченные служебные данные доступа PVE к OpenBao;
- аварийная read-only копия Git credential проекта.

Точные физические пути определяет раздел PVE, а не эта спецификация.

### 2.3. Открытые ключи CA

Открытые ключи SSH CA не являются секретами и могут публиковаться для доверяющих клиентов и серверов.

Закрытые ключи CA не экспортируются из OpenBao как штатный постоянный файл.

## 3. KV v2 для рабочих секретов

Используется отдельное KV v2-хранилище:

~~~text
infra-secrets/
~~~

Логическая структура первой версии:

~~~text
infra-secrets/
├── pve/
│   └── api/
│       └── infra-manager
├── git/
│   └── github/
│       └── proxmox-read
└── services/
    └── semaphore
~~~

### 3.1. PVE API

Логический secret `pve/api/infra-manager` хранит параметры штатного PVE API-доступа управляющего контура.

Поля:

~~~text
endpoint
token_id
token_secret
~~~

### 3.2. Git

Логический secret `git/github/proxmox-read` хранит закрытую часть read-only Git credential проекта.

Поле:

~~~text
private_key
~~~

### 3.3. Semaphore

Логический secret `services/semaphore` хранит постоянные рабочие секреты Semaphore.

Поля:

~~~text
admin_password
access_key_encryption
api_token
timezone
~~~

При перевыпуске `api_token` новое значение должно быть записано обратно в этот secret до следующей материализации.

## 4. Инициализация и разблокировка

### 4.1. Инициализация

OpenBao инициализируется схемой:

~~~text
secret shares: 1
threshold: 1
~~~

Единственный unseal key хранится только в PVE-only области.

Первичная настройка должна быть повторяемой: существующий корректный OpenBao не пересоздаётся и не заменяется пустым.

После переноса рабочих секретов в KV v2 старые постоянные файловые источники не должны оставаться штатным рабочим источником.

### 4.2. Разблокировка

Разблокировку выполняет PVE-only механизм.

Обязательные свойства:

- unseal key не хранится постоянно внутри 910;
- после разблокировки подтверждается `sealed=false`;
- рабочие секреты становятся доступны только через разрешённые служебные роли;
- реализация не должна требовать постоянного root token.

Конкретный механизм вызова и запуска относится к локальной документации 910.

## 5. SSH-механизмы

OpenBao использует три независимых SSH-механизма:

~~~text
ssh-client-signer
ssh-host-signer
ssh-otp
~~~

`ssh-client-signer` выпускает только пользовательские сертификаты для штатного административного входа 910/Ansible.

`ssh-host-signer` выпускает только сертификаты SSH-серверов.

`ssh-otp` не является CA. Он выдаёт одноразовые данные для разрешённых соединений `guest → guest` и проверяет их на целевом госте.

Открытые ключи client CA и host CA должны различаться. Существующий корректный центр доверия при повторной настройке не пересоздаётся.

OTP-роли строятся только из `access.yaml`. Роли, позволяющие запрос OTP для произвольной цели, запрещены.

## 6. Доступ AppRole

Используются два независимых пространства аутентификации:

~~~text
auth/infra-manager
auth/machine
~~~

`auth/infra-manager` предназначен только для PVE-only и управляющего контура.

`auth/machine` предназначен только для отдельных исходных гостей межмашинного SSH.

### 6.1. ssh-ca-config

PVE-only роль может настраивать только проектные роли client CA и host CA.

Она не должна иметь права выпуска сертификатов.

### 6.2. ssh-signer

PVE-only роль может только подписывать через разрешённые роли client CA и host CA.

Она не должна изменять роли подписи.

### 6.3. ssh-otp-config

PVE-only роль управляет только OTP-ролями `guest-*` и соответствующими машинными AppRole, полученными из `access.yaml`.

Для каждого субъекта с правом `ssh/identity/issue` существует отдельная пара:

~~~text
auth/machine/role/guest-<VMID>
ssh-otp/roles/guest-<VMID>
~~~

OTP-роль должна иметь:

- `key_type=otp`;
- пользователя `root`, если именно он разрешён контрактом;
- только адреса целей, разрешённых `ssh/guest/connect-root`.

### 6.4. Машинный AppRole

AppRole `guest-<VMID>` выдаётся только соответствующему исходному гостю.

Полученный token не должен позволять:

- читать KV;
- подписывать SSH-сертификаты;
- менять OTP-роли;
- управлять AppRole;
- использовать OTP-роль другого гостя;
- выполнять PVE-only операции.

RoleID и SecretID доставляются гостю доверенным механизмом настройки. SecretID является машинным секретом и подлежит ротации при компрометации или отзыве доступа.

### 6.5. Проверка OTP целевым гостем

Целевой OTP helper проверяет одноразовое значение через OpenBao.

Проверка не требует выдавать цели машинный AppRole только ради проверки OTP.

Успешно использованное одноразовое значение повторно применить нельзя.

### 6.6. kv-reader

`kv-reader` разрешает чтение только трёх логических секретов управляющего контура:

- PVE API;
- Git read-only credential;
- Semaphore.

Широкий доступ ко всему `infra-secrets/*` запрещён.

### 6.7. kv-semaphore-writer

`kv-semaphore-writer` разрешает только чтение и обновление секрета Semaphore, необходимое для сохранения перевыпущенного API token.

Эта роль не должна иметь доступа к PVE API secret и Git credential.

### 6.8. Ограничения служебных токенов

Служебные токены управляющего контура должны быть короткоживущими и ограниченными минимально необходимой политикой.

Для KV-ролей принимаются:

~~~text
token_ttl: 5m
token_max_ttl: 10m
~~~

Полученный токен отзывается после операции.

Машинные AppRole ограничиваются собственной узкой политикой и сетевыми ограничениями, соответствующими реальному источнику.

## 7. Материализация рабочих секретов

Рабочие программы не читают Raft напрямую.

Нужные значения выдаются только через временное рабочее представление внутри управляющего контура.

Требования:

- временное представление не является постоянным источником;
- запись выполняется атомарно;
- права доступа минимальны для конкретной службы;
- секреты не передаются через аргументы командной строки;
- секреты не печатаются в обычный журнал;
- после перезапуска временное представление восстанавливается из OpenBao;
- изменения постоянного значения, например перевыпуск API token Semaphore, синхронизируются обратно в KV.

Конкретные имена файлов, владельцы, режимы и точки подключения относятся к реализации 910.

## 8. SSH-сертификаты и OTP

### 8.1. Клиентский сертификат Ansible

Роль client CA для `infra-manager` должна:

- выпускать только user certificate;
- разрешать только нужный principal;
- использовать поддерживаемый тип открытого ключа;
- иметь короткий срок действия;
- не использоваться для `guest → guest`.

Текущий целевой срок сертификата — 15 минут.

### 8.2. Межмашинный OTP

Для каждого гостя с `ssh/identity/issue` существует собственная OTP-роль.

Исходный гость после входа через собственный AppRole может запросить OTP только для цели, разрешённой его правилом `access.yaml`.

OTP:

- выдаётся для конкретной цели;
- не является SSH-сертификатом;
- не хранится как постоянный secret;
- не продлевается;
- имеет короткий срок жизни;
- после успешной проверки становится недействительным.

### 8.3. Сертификат SSH-сервера

Роль host CA `managed-host` должна:

- выпускать только host certificate;
- подписывать реальный SSH host key гостя;
- использовать имя и адрес цели, подтверждённые доверенным контуром;
- не смешиваться с client CA.

Целевой срок host certificate — 720 часов.

Host CA используется для независимой проверки сервера как административным SSH, так и межмашинным OTP-клиентом.

## 9. Корневые токены и восстановление

Initial root token используется только для первоначальной настройки OpenBao и после неё отзывается.

Постоянный root token не хранится.

Для явного восстановления недостающей конфигурации допускается краткоживущий временный root token через локальный защищённый механизм. После операции он также отзывается.

Потеря Raft означает потерю рабочих секретов, закрытых SSH CA и конфигурации OpenBao.

Потеря unseal key при запечатанном OpenBao делает штатную разблокировку невозможной.

Raft, unseal key и необходимые PVE-only данные должны рассматриваться как связанные части защищённого резервного комплекта.

Штатное восстановление не должно автоматически создавать новый пустой OpenBao поверх существующей инфраструктуры.

Воспроизводимые служебные AppRole-данные допускается перевыпускать при сохранных Raft и unseal key через отдельную восстановительную операцию.

## 10. Проверка контракта

Проверка должна подтверждать:

- OpenBao инициализирован и не запечатан;
- существует обязательный KV v2;
- разрешённые KV-роли читают только свои секреты;
- `kv-semaphore-writer` не получает лишнего доступа;
- временное рабочее представление получено из OpenBao;
- оба SSH CA существуют и различаются;
- роль настройки CA не имеет права подписи;
- роль подписи не имеет права менять настройки CA;
- существует отдельный SSH OTP;
- набор OTP-ролей соответствует `access.yaml`;
- каждая OTP-роль содержит только разрешённые цели;
- каждому источнику соответствует отдельный машинный AppRole;
- машинный AppRole не может читать KV или использовать чужую роль;
- OTP используется только один раз;
- сетевой вход OTP использует TLS;
- удалённое из проекта право перестаёт выдавать новые данные доступа;
- root token не хранится постоянно;
- аварийное состояние совместимо с текущим OpenBao.

Конкретные команды и локальные проверки 910 относятся к эксплуатационной и локальной документации.
