## 1. Роль OpenBao

OpenBao является центральным хранилищем внутренних секретов проекта и центром выдачи краткоживущих технических полномочий.

Основные задачи:

~~~text
KV v2
→ рабочие внутренние секреты

SSH Client CA
→ штатный административный вход infra-manager в Linux-гости

SSH Host CA
→ подтверждение подлинности Linux-гостей

SSH online access
→ централизованное разрешение ограниченного guest-to-guest доступа

policy
→ какие машинные идентичности могут получать конкретные секреты и полномочия
~~~

OpenBao не является источником требуемых прав. Требуемая матрица доступа хранится в Git в `infrastructure/security/access.yaml`, а OpenBao получает из неё производные policy и role.

## 2. Постоянное состояние и корень восстановления

### 2.1. База OpenBao

Постоянное состояние OpenBao физически хранится на PVE в области `state/openbao/` и подключается в 910, а затем в контейнер OpenBao.

В Raft-состояние входят:

- KV secrets и их метаданные;
- закрытые ключи SSH CA;
- auth methods;
- roles и policies;
- служебное состояние OpenBao.

Корневая файловая система 910 и файловая система Docker-контейнера не являются владельцами этой базы.

### 2.2. Данные, которые нельзя хранить только внутри OpenBao

В PVE-only области остаются:

- `unseal.key`;
- служебные данные, позволяющие PVE получить ограниченный административный доступ к OpenBao для настройки и восстановления.

Они не монтируются в 910 постоянно.

Отдельно в `pve-only/recovery/` находятся независимые восстановительные credentials, необходимые при полной потере OpenBao. Они не являются частью обычной работы OpenBao.

Точные пути определены в `230-host-layout.md`.

## 3. KV-хранилище

Для внутренних секретов используется KV v2.

Логические области:

~~~text
kv/
├── infrastructure/
│   ├── proxmox/
│   ├── github/
│   └── semaphore/
├── guests/
└── services/
~~~

В KV должны храниться рабочие секреты, которым не требуется существовать независимо от OpenBao для его собственного восстановления:

- PVE API credentials;
- рабочий GitHub credential только для чтения;
- пароли и API tokens внутренних сервисов;
- секреты приложений;
- секреты конкретных гостей;
- ключи шифрования приложений, если они относятся к рабочему контуру.

Секреты не помещаются в Git и не передаются через обычные журналы или аргументы командной строки.

Получатель должен видеть только тот KV-путь, который разрешён его policy.

## 4. SSH-центры доверия

OpenBao содержит два независимых SSH CA:

~~~text
ssh-client-signer
ssh-host-signer
~~~

`ssh-client-signer` выпускает только пользовательские сертификаты.

`ssh-host-signer` выпускает только серверные сертификаты.

Закрытые CA-ключи не экспортируются. Открытые ключи CA публикуются тем системам, которым они нужны для проверки.

### 4.1. Сертификаты infra-manager

Для штатного Ansible-задания создаётся временная Ed25519-пара. OpenBao подписывает только её открытый ключ.

Сертификат:

- разрешает административный principal, используемый проектом;
- действует короткое время, целевое значение — 15 минут;
- не даёт возможности подписывать другие ключи.

Временная закрытая часть удаляется после задания.

### 4.2. Сертификаты серверов

Подписывается реальный Ed25519 host public key гостя.

До подписи доверенный механизм обязан подтвердить VMID, имя и административный адрес объекта через PVE или другой принятый доверенный источник.

Сертификат сервера не заменяет собственный private host key сервера.

## 5. Централизованный SSH между гостями

Ограниченный SSH обычного гостя к другому гостю не использует постоянную пару, которую затем приходится распространять по `authorized_keys`.

Целевая модель — онлайн-авторизация OpenBao через SSH OTP или эквивалентный механизм:

~~~text
гость 410
→ аутентификация в OpenBao
→ запрос доступа к конкретному адресу гостя 211
→ policy разрешает или запрещает цель
→ одноразовый SSH credential
→ целевой SSH-сервер проверяет credential через OpenBao
~~~

Разрешённые цели формируются из `access.yaml`.

Изменение списка целей должно требовать обновления policy/role OpenBao, а не распространения нового public key по всем Linux-гостям.

Новые межмашинные SSH-сеансы зависят от доступности OpenBao. Уже открытый сеанс не должен разрываться только из-за временной недоступности OpenBao.

## 6. Машинная аутентификация

`infra-manager` и обычные гости не используют общий OpenBao token.

Каждый субъект, которому требуется прямое обращение к OpenBao, получает собственную машинную идентичность.

Для первого этапа допускается отдельный AppRole на гостя:

- RoleID относится только к конкретному субъекту;
- SecretID хранится только на этом госте и не попадает в Git;
- выдаваемый token имеет короткий TTL;
- token получает только policies этого субъекта;
- SecretID можно явно перевыпустить без восстановления остальных секретов.

Машинный credential гостя является bootstrap-доступом к OpenBao. Его потеря не требует восстановления из резервной копии: доверенный административный контур должен уметь выпустить новый и отозвать старый.

Служебные полномочия настройки самого OpenBao остаются отделены от обычных guest credentials.

## 7. Политики

OpenBao policies создаются из `infrastructure/security/access.yaml`.

Policy должна ограничивать как минимум:

- допустимые KV-пути;
- допустимые SSH roles и цели;
- возможность получить PVE или Git credential;
- срок жизни и тип выдаваемого token.

Ручное расширение OpenBao policy сверх `access.yaml` считается расхождением состояния и должно обнаруживаться проверкой.

Policy не заменяет ограничения конечной системы. Например, OpenBao может разрешить получить PVE credential, но фактический набор операций дополнительно ограничивает PVE ACL.

## 8. Сетевой доступ к OpenBao

Локальные административные операции 910 могут использовать loopback.

Для онлайн-проверки межмашинного SSH и прямой машинной аутентификации OpenBao должен иметь защищённую точку доступа в административной сети.

Требования:

- TLS с проверкой сервера;
- отсутствие открытого доступа из недоверенных сетей;
- обязательная машинная аутентификация;
- отсутствие анонимного чтения;
- минимальные policies;
- журналирование административных изменений без вывода секретных значений.

## 9. Корневые токены

Initial root token используется только для настройки пустого OpenBao и после подготовки штатных auth methods и policies отзывается.

Постоянный root token не хранится.

Для аварийного восстановления допускается отдельная контролируемая процедура получения временных полных полномочий из PVE-only корня доверия. Полученный token должен быть отозван сразу после операции.

## 10. Потеря и восстановление

### 10.1. Сохранены Raft и unseal

OpenBao запускается на прежнем `state/openbao/`, снимается блокировка соответствующим `unseal.key`, после чего сохраняются прежние CA, KV и policies.

### 10.2. Потерян OpenBao state

Новый пустой OpenBao создаёт новые CA и не считается прозрачной заменой старого.

Для возвращения управления используются независимые данные `pve-only/recovery/`:

- аварийный SSH administrator key;
- восстановительный GitHub read-only credential.

После создания новых CA аварийный SSH-доступ используется для установки нового доверенного публичного CA на управляемые Linux-системы. Автоматический fallback штатных заданий на recovery key запрещён.

### 10.3. Потерян unseal key

Если OpenBao запечатан и соответствующий unseal key утрачен, штатная разблокировка невозможна. Поэтому `pve-only/openbao/` и `state/openbao/` должны входить в совместимый восстановительный комплект.

## 11. Проверка контракта

Проверка OpenBao должна подтверждать:

- `initialized=true` и `sealed=false` в штатном состоянии;
- наличие KV v2;
- наличие двух независимых SSH CA;
- отсутствие постоянного root token;
- доступ каждого гостя только к собственной policy;
- запрет чтения неразрешённых KV-путей;
- запрет SSH-целей, которых нет в `access.yaml`;
- соответствие policies машинному источнику требований;
- отсутствие закрытых CA-ключей вне Raft;
- наличие независимого PVE-only корня восстановления.

Фактическая готовность перечисленных механизмов фиксируется только в `780-implementation-status.md`.
