## 1. Роль OpenBao

OpenBao является каноническим защищённым хранилищем рабочих секретов управляющего контура и закрытых ключей двух SSH-центров доверия.

В OpenBao находятся:

- рабочий PVE API secret;
- рабочий закрытый GitHub Deploy Key проекта;
- рабочие секреты Semaphore;
- закрытые ключи SSH client CA и SSH host CA;
- политики, роли и настройки служебного доступа.

OpenBao работает внутри 910 и слушает только локальный адрес:

```text
http://127.0.0.1:8200
```

Рабочие программы не должны использовать постоянные файловые копии PVE, Git или Semaphore secret как штатный источник.

## 2. Граница постоянного хранения

### 2.1. Состояние OpenBao

Постоянное состояние OpenBao хранится в Raft под отдельным постоянным каталогом 910.

В него входят:

- KV v2 с рабочими секретами;
- закрытые ключи SSH CA;
- auth method;
- AppRole;
- политики;
- роли SSH-подписи.

Это состояние является обязательным для резервного копирования.

### 2.2. Данные только для PVE

На PVE вне OpenBao остаются данные, необходимые до получения штатного доступа к самому OpenBao, и аварийная Git-копия проекта:

```text
openbao/unseal.key
openbao/ssh-access.json
openbao/kv-access.json
recovery/github_proxmox_repo_ed25519
```

Они находятся в PVE-only области и не монтируются в 910.

`kv-access.json` содержит только служебные RoleID/SecretID ограниченных ролей OpenBao. Он не содержит PVE API secret, Git Deploy Key или секреты Semaphore.

`recovery/github_proxmox_repo_ed25519` является отдельной PVE-only аварийной копией read-only Deploy Key. Она нужна для получения проекта до запуска 910 и OpenBao и не используется как штатный рабочий secret после восстановления.

Канонические пути определены в [`../200-pve/230-host-layout.md`](../200-pve/230-host-layout.md).

### 2.3. Открытые ключи CA

Открытые ключи SSH CA не являются секретами и публикуются в 910:

```text
/etc/infra-manager/ca/ssh-client-ca.pub
/etc/infra-manager/ca/ssh-host-ca.pub
```

Закрытые CA-ключи из OpenBao не экспортируются.

## 3. KV v2 для рабочих секретов

Используется отдельный KV v2 mount:

```text
infra-secrets/
```

Логическое право на использование этих ресурсов задаётся в `access.yaml`; здесь определено их защищённое физическое хранение и служебная реализация.

Каноническая структура первой версии:

```text
infra-secrets/
├── pve/
│   └── api/
│       └── infra-manager
├── git/
│   └── github/
│       └── proxmox-read
└── services/
    └── semaphore
```

### 3.1. PVE API

Путь:

```text
infra-secrets/data/pve/api/infra-manager
```

Поля:

```text
endpoint
token_id
token_secret
```

Этот secret является штатным источником API-доступа `root@pam!infra-manager`.

### 3.2. Git

Путь:

```text
infra-secrets/data/git/github/proxmox-read
```

Поле:

```text
private_key
```

В нём хранится закрытая часть read-only Deploy Key только для проектного репозитория.

### 3.3. Semaphore

Путь:

```text
infra-secrets/data/services/semaphore
```

Поля:

```text
admin_password
access_key_encryption
api_token
timezone
```

При перевыпуске `api_token` новое значение должно быть записано обратно в этот secret до следующей материализации.

## 4. Инициализация и разблокировка

### 4.1. Инициализация

OpenBao инициализируется схемой:

```text
secret shares: 1
threshold: 1
```

Единственный unseal key сохраняется только на PVE.

При первой миграции существующие PVE, Git и Semaphore secrets временно подготавливаются в `/run/infra-manager/secrets/` и однократно записываются в KV v2.

KV v2 является каноническим рабочим источником секретов 910. После успешной инициализации OpenBao старые файловые источники удаляются проверенной PVE-only операцией; рабочие копии существуют только под `/run/infra-manager/secrets/`.

### 4.2. Разблокировка

PVE-only механизм:

1. проверяет состояние OpenBao;
2. при необходимости временно передаёт unseal key внутрь 910;
3. выполняет unseal;
4. удаляет временную копию unseal key;
5. подтверждает `sealed=false`;
6. при настроенном KV материализует рабочие секреты во временную область 910.

Unseal key не остаётся внутри 910 после операции.

## 5. SSH-центры доверия

Создаются два независимых SSH secrets engine:

```text
ssh-client-signer
ssh-host-signer
```

`ssh-client-signer` выпускает только пользовательские сертификаты.

`ssh-host-signer` выпускает только сертификаты SSH-серверов.

Открытые ключи должны различаться. Существующий корректный центр доверия при повторной настройке не пересоздаётся.

## 6. Служебный доступ AppRole

Используется:

```text
auth/infra-manager
```

Постоянные RoleID/SecretID всех перечисленных ролей остаются только на PVE.

### 6.1. `ssh-ca-config`

Разрешает настройку ролей client CA и host CA, которыми управляет проект.

Для межмашинного SSH эта роль синхронизирует только имена `machine-<VMID>`, выведенные из `access.yaml`, и удаляет лишние `machine-*`.

Не разрешает использовать роли подписи для выпуска сертификата.

### 6.2. `ssh-signer`

Разрешает только подпись через:

```text
ssh-client-signer/sign/infra-manager
ssh-client-signer/sign/machine-*
ssh-host-signer/sign/managed-host
```

Имена `machine-*` не выбираются гостем: PVE-only механизм принимает VMID только после разбора проектного `access.yaml`.

Не разрешает менять роли подписи.

### 6.3. `kv-reader`

Разрешает только чтение трёх точных путей:

```text
infra-secrets/data/pve/api/infra-manager
infra-secrets/data/git/github/proxmox-read
infra-secrets/data/services/semaphore
```

Доступ по шаблону ко всему `infra-secrets/*` запрещён.

### 6.4. `kv-semaphore-writer`

Разрешает только `read` и `update` одного пути:

```text
infra-secrets/data/services/semaphore
```

Роль нужна для сохранения перевыпущенного API token Semaphore.

Она не имеет доступа к PVE API secret и Git Deploy Key.

### 6.5. Ограничения токенов

Все KV AppRole ограничены loopback-адресом управляющей системы.

Для `kv-reader` и `kv-semaphore-writer`:

```text
token_ttl: 5m
token_max_ttl: 10m
```

Полученный токен отзывается после каждой операции.

## 7. Материализация рабочих секретов

Рабочие secrets из KV v2 материализуются только во временную область:

```text
/run/infra-manager/secrets/
```

Текущие файлы совместимости:

```text
pve-api.env
github_proxmox_repo_ed25519
semaphore-server.env
initial-admin-password
semaphore-api-token
.openbao-materialized
```

Требования:

- каталог принадлежит `root:root` и имеет режим `0750`, чтобы служебная группа `0` могла только пройти к файлам;
- секретные файлы принадлежат служебному пользователю `1001:0` и имеют режим `0600`;
- запись выполняется атомарно;
- каталог находится на `tmpfs` через `/run` и не является постоянным хранилищем;
- `infra-runtime` получает каталог только для чтения;
- значения secret не передаются через аргументы командной строки и не печатаются в журнал;
- после перезапуска 910 материализация повторяется после разблокировки OpenBao.

Маркер `.openbao-materialized` не содержит secret. Он показывает, что текущая временная область получена из OpenBao и изменения служебных данных должны синхронизироваться обратно в KV.

## 8. Подпись SSH-сертификатов

### 8.1. Клиентский сертификат

Роль:

```text
ssh-client-signer/roles/infra-manager
```

Основные ограничения:

- только user certificate;
- principal `root`;
- Ed25519 public key;
- срок 15 минут;
- `permit-pty`.

### 8.2. Машинный клиентский сертификат

Для каждого гостя с `ssh/identity/issue` существует отдельная роль:

```text
ssh-client-signer/roles/machine-<VMID>
```

Она разрешает:

- только user certificate;
- только Ed25519 public key;
- единственный principal `guest-<VMID>`;
- срок 2 часа.

Закрытый машинный ключ находится в исходном госте. OpenBao получает только public key. Гостю не передаются AppRole-данные подписи.

### 8.3. Сертификат SSH-сервера

Роль:

```text
ssh-host-signer/roles/managed-host
```

Основные ограничения:

- только host certificate;
- срок 720 часов;
- подписывается реальный Ed25519 host public key гостя.

До подписи PVE-only механизм обязан подтвердить VMID, точное имя и административный адрес цели.

## 9. Корневые токены

Initial root token используется только для первоначальной настройки OpenBao, KV v2, политик и ролей.

После настройки он отзывается и постоянно не хранится.

Для явного восстановления недостающей конфигурации уже инициализированного OpenBao допускается краткоживущий временный root token через локальный защищённый механизм. Он также обязательно отзывается после операции.

## 10. Потеря данных

Потеря unseal key при запечатанном OpenBao делает штатную разблокировку невозможной.

Потеря Raft state означает потерю:

- рабочих секретов KV;
- закрытых SSH CA;
- политик и ролей OpenBao.

PVE-only unseal/AppRole-данные, аварийный Git key и Raft state должны резервироваться как разные части одного защищённого комплекта.

Штатное восстановление 910 не создаёт новый OpenBao поверх потерянного состояния. Перед восстановлением PVE-only helper проверяет наличие обязательных данных и останавливает процесс при потере Raft state, unseal key или других критичных частей.

`ssh-access.json` и `kv-access.json` считаются воспроизводимыми служебными данными. Если они потеряны при сохранных Raft и unseal key, штатная инициализация выпускает временный root token, создаёт новые ограниченные AppRole-данные и сразу отзывает root token.

Отдельный аварийный SSH-ключ для входа в PVE не используется: точкой аварийного восстановления является локальный root PVE. Это не расширяет удалённый административный доступ ради recovery.

## 11. Проверка контракта

Проверка OpenBao должна подтверждать:

- `initialized=true`;
- `sealed=false`;
- существует `infra-secrets` типа KV v2;
- три обязательных secret доступны через `kv-reader`;
- `kv-reader` не имеет доступа к постороннему пути;
- `kv-semaphore-writer` имеет `read/update` только для `services/semaphore`;
- рабочие секреты материализованы в `/run/infra-manager/secrets/`;
- оба SSH CA существуют и различаются;
- `ssh-ca-config` не имеет права подписи;
- `ssh-signer` не имеет права менять роли;
- роли подписи имеют ожидаемые ограничения;
- набор `machine-*` совпадает с субъектами `identity/issue` из `access.yaml`;
- машинная роль ограничена principal своего VMID и сроком 2 часа;
- удалённая из проекта машинная роль исчезает из OpenBao;
- root token не хранится постоянно;
- PVE-only recovery helper подтверждает наличие совместимого OpenBao/recovery-состояния.

`infra-manager-status --full` должен считать инициализированный OpenBao готовым только после успешной PVE-only проверки KV.
