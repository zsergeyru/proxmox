## 1. Роль OpenBao

OpenBao является хранилищем закрытых ключей двух SSH-центров доверия проекта.

Он не является общим хранилищем всех секретов инфраструктуры.

Основные задачи:

```text
SSH client CA
→ подтверждает право управляющей среды войти в Linux-гость

SSH host CA
→ подтверждает подлинность управляемого SSH-сервера
```

Два центра независимы и используют разные закрытые CA-ключи.

OpenBao работает внутри управляющего контейнера и доступен только через локальный адрес этой системы.

## 2. Граница хранения

### 2.1. Состояние OpenBao

Постоянное состояние OpenBao хранится отдельно от корневой файловой системы управляющего контейнера.

В это состояние входят:

- Raft-данные;
- закрытые ключи SSH CA;
- настройки auth method;
- роли и политики.

Потеря этого состояния означает потерю идентичности существующих SSH CA.

### 2.2. Данные только для PVE

Ключ снятия блокировки и постоянные служебные RoleID/SecretID хранятся только в PVE-only области.

Они:

- не монтируются в `infra-manager`;
- не передаются в `infra-runtime` как постоянные файлы;
- не хранятся в Git;
- не должны попадать в журналы.

Канонические пути определены в [`../200-pve/230-host-layout.md`](../200-pve/230-host-layout.md).

### 2.3. Открытые ключи CA

Открытые ключи обоих центров не являются секретами.

После настройки они публикуются управляющему контуру как:

```text
/etc/infra-manager/ca/ssh-client-ca.pub
/etc/infra-manager/ca/ssh-host-ca.pub
```

Закрытые CA-ключи наружу не экспортируются.

## 3. Инициализация и разблокировка

### 3.1. Инициализация

OpenBao инициализируется схемой:

```text
secret shares: 1
threshold: 1
```

Единственный unseal key сохраняется только на PVE.

Если OpenBao ещё не инициализирован, но в PVE-only области уже обнаружены старые unseal/AppRole-данные, автоматическая перезапись запрещена.

Такое состояние требует явного разбирательства.

### 3.2. Разблокировка

PVE-only хостовый механизм:

1. проверяет состояние OpenBao;
2. при необходимости временно передаёт unseal key внутрь управляющего контейнера;
3. выполняет unseal;
4. удаляет временную копию ключа;
5. подтверждает, что `sealed=false`.

Unseal key не остаётся внутри гостя после операции.

## 4. SSH-центры доверия

Создаются два независимых SSH secrets engine:

```text
ssh-client-signer
ssh-host-signer
```

Требования:

- оба имеют тип SSH CA;
- их открытые ключи должны быть корректными;
- открытые ключи должны различаться;
- существующий корректный CA не пересоздаётся при повторной настройке.

### 4.1. Client CA

`ssh-client-signer` выпускает только пользовательские сертификаты.

Он не должен выпускать host certificates.

### 4.2. Host CA

`ssh-host-signer` выпускает только сертификаты SSH-серверов.

Он не должен выпускать пользовательские сертификаты.

## 5. Служебный доступ AppRole

Для OpenBao используется отдельный auth method:

```text
auth/infra-manager
```

Создаются две независимые служебные роли.

### 5.1. `ssh-ca-config`

Назначение — настраивать роли подписи.

Политика разрешает:

- чтение и изменение ролей client CA;
- чтение и изменение ролей host CA;
- проверку собственных capabilities;
- отзыв собственного токена.

Она не выдаёт право подписывать клиентский ключ через роль `infra-manager`.

### 5.2. `ssh-signer`

Назначение — только запрашивать подпись у заранее разрешённых ролей.

Политика разрешает:

- `ssh-client-signer/sign/infra-manager`;
- `ssh-host-signer/sign/managed-host`;
- проверку собственных capabilities;
- отзыв собственного токена.

Она не должна позволять изменять сами роли подписи.

### 5.3. Ограничения токенов

AppRole-доступ ограничен локальным адресом управляющей системы.

Для `ssh-ca-config`:

```text
token_ttl: 10m
token_max_ttl: 15m
```

Для `ssh-signer`:

```text
token_ttl: 5m
token_max_ttl: 10m
```

Полученный токен отзывается после завершения каждой операции.

Постоянные RoleID/SecretID остаются только на PVE.

## 6. Подпись клиентских сертификатов

Роль:

```text
ssh-client-signer/roles/infra-manager
```

Требования роли:

- `key_type=ca`;
- разрешены user certificates;
- host certificates запрещены;
- principal ограничен `root`;
- допустим Ed25519 public key;
- срок сертификата — 15 минут;
- стандартное разрешённое расширение — `permit-pty`;
- key ID строится из назначения `infra-manager` и хэша открытого ключа.

Поток подписи:

```text
временный Ed25519 public key
→ PVE-only helper
→ AppRole ssh-signer
→ короткоживущий OpenBao token
→ sign/infra-manager
→ пользовательский сертификат
→ revoke token
```

Закрытый временный ключ OpenBao не получает.

## 7. Подпись сертификатов SSH-серверов

Роль:

```text
ssh-host-signer/roles/managed-host
```

Требования роли:

- `key_type=ca`;
- разрешены host certificates;
- user certificates запрещены;
- срок сертификата — 720 часов;
- key ID строится из назначения управляемого сервера и хэша открытого ключа.

OpenBao role допускает переданные host principals, но реальная граница безопасности находится **до запроса подписи** на PVE.

PVE-only helper обязан проверить:

- VMID;
- точное имя VM/LXC;
- административный IPv4;
- существование объекта;
- соответствие имени и адреса конфигурации PVE или другому доверенному источнику фактического адреса.

После проверки в сертификат передаются только:

```text
<точное имя>
<подтверждённый административный IPv4>
```

Подписывается только реальный Ed25519 host public key гостя.

Произвольный запрос из `infra-manager` не должен быть достаточен для подписи имени или IP другого сервера.

## 8. Корневые токены

### 8.1. Initial root token

Первоначальный root token используется только для настройки пустого OpenBao.

После:

- создания SSH CA;
- настройки AppRole;
- публикации открытых CA;
- настройки ролей подписи

он немедленно отзывается.

Постоянно хранить initial root token запрещено.

### 8.2. Временный root token

Для восстановления недостающей SSH-настройки уже инициализированного OpenBao допускается выпуск временного root token через защищённое локальное окно совместимости.

Такое окно:

- использует существующий unseal key;
- доступно только локально;
- существует только на время операции;
- восстанавливает штатную конфигурацию после завершения;
- обязательно отзывает временный root token.

Временный root token не становится постоянным credential проекта.

## 9. Потеря и восстановление

### 9.1. Потеря unseal key

Unseal key является критичным восстановительным секретом.

Если OpenBao запечатан, а ключ потерян, штатная разблокировка невозможна.

Поэтому PVE-only данные должны резервироваться отдельно от самого контейнера.

### 9.2. Потеря AppRole-данных

При сохранных OpenBao state и unseal key служебные AppRole-данные могут быть явно перевыпущены доверенным восстановительным механизмом.

Старая пара должна считаться отозванной.

### 9.3. Потеря Raft state

Потеря OpenBao state означает потерю закрытых CA-ключей.

Создание нового пустого OpenBao породит новые центры доверия и потребует явного обновления доверия всех клиентов и серверов.

Автоматически подменять потерянный CA новым под тем же смыслом запрещено.

## 10. Проверка контракта

Проверка OpenBao должна подтверждать:

- `initialized=true`;
- `sealed=false`;
- оба SSH CA существуют;
- их открытые ключи различаются;
- PVE-only AppRole-файл имеет ожидаемые две роли;
- `ssh-ca-config` не имеет права подписи;
- `ssh-signer` не имеет права менять роли;
- роли `infra-manager` и `managed-host` имеют ожидаемые ограничения;
- оба открытых CA опубликованы;
- root token не хранится как постоянный secret.
