## 1. Роль OpenBao

OpenBao является центральной службой машинного доверия управляющего контура.

Он решает пять разных задач:

```text
OpenBao
 ├─ KV v2        → хранение рабочих секретов
 ├─ client CA    → временные SSH-сертификаты Ansible
 ├─ host CA      → сертификаты SSH-серверов
 ├─ AppRole      → ограниченные служебные и машинные идентичности
 └─ SSH OTP      → одноразовый guest → guest доступ
```

OpenBao не является источником решения о том, **кому** положено право. Машинные права задаёт `access.yaml`.

OpenBao реализует эти права технически: хранит нужный secret, выпускает сертификат, выдаёт ограниченный token или OTP.

Конкретная установка OpenBao на 910 — контейнер, Raft-каталог, Compose, systemd, init и unseal — описана в локальном [`openbao.md`](../../infrastructure/guests/910-infra-manager/docs/openbao.md).

## 2. Используемые механизмы

### 2.1. KV v2

KV v2 хранит постоянные рабочие секреты управляющего контура.

Логическое хранилище:

```text
infra-secrets/
```

В нём находятся три основные группы:

```text
PVE API
Git read-only credential
Semaphore runtime
```

Рабочие программы не должны читать Raft напрямую.

Секреты выдаются только через ограниченную роль и временное рабочее представление.

Если рабочий secret меняется во время эксплуатации, например API token Semaphore, новое постоянное значение должно быть синхронизировано обратно в KV.

### 2.2. SSH client CA

Логический mount:

```text
ssh-client-signer
```

Он выпускает только пользовательские SSH-сертификаты для административного управления Linux-гостями.

Основной потребитель:

```text
910 / Ansible
```

Закрытый CA key остаётся внутри OpenBao.

Целевой срок административного сертификата — `15 минут`.

### 2.3. SSH host CA

Логический mount:

```text
ssh-host-signer
```

Он выпускает только сертификаты SSH-серверов.

Перед подписью PVE должен подтвердить, что host key, имя и адрес относятся к ожидаемому VM/LXC.

Роль серверной подписи:

```text
managed-host
```

Целевой срок host certificate — `720 часов`.

Client CA и host CA должны иметь разные закрытые ключи и независимые политики.

### 2.4. AppRole

AppRole используется для выдачи ограниченных машинных полномочий без постоянного root token.

Проект разделяет два пространства:

```text
auth/infra-manager
auth/machine
```

`auth/infra-manager` обслуживает доверенные операции управляющего/PVE-контура.

`auth/machine` предназначен для отдельных исходных Linux-гостей, которым разрешён межмашинный SSH.

Машинная идентичность одного гостя не должна использоваться другим гостем.

### 2.5. SSH OTP

Логический mount:

```text
ssh-otp
```

OTP используется только для целевой схемы `guest → guest`.

Для каждого субъекта с `ssh/identity/issue` существует собственная OTP-роль:

```text
guest:<VMID>
        ↓
ssh-otp/roles/guest-<VMID>
```

Роль содержит только цели, разрешённые его правилами `ssh/guest/connect-root`.

OTP:

- выдаётся только для разрешённой цели;
- одноразовый;
- короткоживущий;
- не является SSH-сертификатом;
- не хранится как постоянный secret;
- проверяется целью через OpenBao.

## 3. Взаимодействие с компонентами проекта

### 3.1. PVE ↔ OpenBao

PVE является отдельной доверенной границей OpenBao.

Он участвует в:

- разблокировке OpenBao;
- хранении PVE-only данных доступа;
- первичной и восстановительной административной операции;
- настройке ограниченных служебных ролей;
- подтверждении VM/LXC перед подписью host certificate;
- материализации рабочих секретов для 910.

Unseal key не должен становиться обычным постоянным secret внутри 910.

### 3.2. infra-manager ↔ OpenBao

910 использует OpenBao, но не владеет полным административным доступом к нему постоянно.

Основные потоки:

```text
OpenBao KV
  → PVE API secret
  → Git credential
  → Semaphore runtime secrets

OpenBao client CA
  → временный сертификат Ansible

OpenBao host CA
  → сертификат подтверждённого Linux-гостя
```

Рабочие данные выдаются 910 только на время, необходимое службе.

### 3.3. Semaphore ↔ OpenBao

Semaphore получает через OpenBao свои постоянные рабочие секреты, включая:

- пароль администратора;
- ключ защиты данных;
- API token.

При перевыпуске API token Semaphore новое значение должно сохраняться обратно в OpenBao.

Semaphore не получает права читать произвольные секреты PVE или Git только потому, что работает внутри того же `infra-runtime`.

### 3.4. Ansible ↔ OpenBao

Для штатного административного SSH:

```text
временный public key Ansible
 → ограниченная операция подписи
 → ssh-client-signer
 → короткоживущий user certificate
```

Ansible не получает закрытый ключ client CA.

### 3.5. Исходный гость ↔ OpenBao

Для `guest → guest`:

```text
исходный гость
 → собственный auth/machine AppRole
 → короткоживущий OpenBao token
 → только собственная ssh-otp role
 → OTP только к разрешённой цели
```

Машинный token не должен позволять чтение KV, подпись сертификатов или изменение OpenBao.

### 3.6. Целевой гость ↔ OpenBao

Цель проверяет введённый OTP через OpenBao.

Для самой проверки OTP цели не требуется AppRole с правом выдачи OTP.

Проверка OTP и проверка host certificate решают разные задачи и обе обязательны.

## 4. Служебные и машинные идентичности

### 4.1. Служебные роли управляющего контура

Архитектура предусматривает отдельные полномочия как минимум для:

| Роль | Назначение |
|---|---|
| `ssh-ca-config` | создавать и изменять только разрешённые роли SSH CA |
| `ssh-signer` | подписывать только через разрешённые client/host роли |
| `ssh-otp-config` | синхронизировать машинные AppRole и OTP-роли из `access.yaml` |
| `kv-reader` | читать только рабочие секреты управляющего контура |
| `kv-semaphore-writer` | обновлять только секрет Semaphore |

Роль настройки CA не должна одновременно быть ролью подписи.

Роль чтения KV не должна автоматически иметь право записи.

Служебные token должны быть короткоживущими и отзываться после операции. Для текущей модели приняты TTL порядка нескольких минут; постоянный долгоживущий административный token не является штатным механизмом.

### 4.2. Вход человека в OpenBao

Встроенный веб-интерфейс OpenBao может использоваться человеком для просмотра и ограниченного администрирования, но такой вход является отдельным контуром и не заменяет машинные роли.

Человеческая учётная запись должна:

- получать отдельную ограниченную ACL policy;
- не получать постоянный root token;
- не получать права восстановления Raft, `sys/init` или выпуска машинных SecretID;
- не использоваться службами, Semaphore или гостями;
- хранить способ восстановления учётных данных только в доверенной PVE-only области.

`access.yaml` остаётся источником машинных прав. Конкретный способ аутентификации человека, срок token и хранение его данных определяются локальной спецификацией 910.

### 4.3. Машинный AppRole гостя

Для каждого исходного гостя OTP существует отдельный AppRole:

```text
auth/machine/role/guest-<VMID>
```

Его policy разрешает только запрос через:

```text
ssh-otp/creds/guest-<VMID>
```

Он не должен позволять:

- KV;
- client CA;
- host CA;
- чужую OTP-роль;
- настройку AppRole;
- PVE-only операции.

SecretID является машинным секретом конкретного гостя и подлежит отдельной ротации.

## 5. Связь с access.yaml

`access.yaml` определяет логическое право, а OpenBao строит из него производный механизм.

Для межмашинного SSH:

```text
access.yaml
 ├─ ssh/identity/issue
 │      ↓
 │   машинный AppRole
 │
 └─ ssh/guest/connect-root
        ↓
     allowed targets OTP-роли
```

Удаление цели из `connect-root` должно исключить её из OTP-роли.

Удаление `identity/issue` должно убрать возможность исходного гостя получать новые OTP.

OpenBao не должен иметь вручную добавленных более широких OTP-прав, которых нет в `access.yaml`.

Для других прав `access.yaml` определяет, какие субъекты вообще должны получать PVE, Git, Semaphore или OpenBao-возможности.

## 6. Сетевые границы

OpenBao имеет два разных класса взаимодействия.

### 6.1. Локальный управляющий доступ

Внутренние административные операции 910 могут использовать локальный интерфейс OpenBao внутри доверенного управляющего контура.

Конкретный listener относится к реализации 910.

### 6.2. Межмашинный OTP

Для OTP источнику и цели нужен сетевой доступ к OpenBao.

Этот сетевой вход обязан:

- использовать TLS;
- проверять сертификат OpenBao;
- быть доступным только необходимым управляемым гостям;
- не раскрывать административные PVE-only интерфейсы;
- не позволять гостям получить служебные роли `auth/infra-manager`;
- не использовать открытый HTTP в гостевой сети.

Отказ OpenBao блокирует новые OTP-подключения, но не должен уничтожать независимый административный путь 910/Ansible через client CA.

## 7. Жизненный цикл и восстановление

### 7.1. Root token

Initial root token допустим только при первоначальной настройке и после неё отзывается.

Постоянный root token не хранится.

Для специального восстановления допускается кратковременный административный token через отдельный PVE-only процесс; после операции он также отзывается.

### 7.2. Постоянное состояние

Критичным постоянным состоянием являются:

- рабочие KV-секреты;
- закрытые client CA и host CA;
- политики и auth methods;
- AppRole;
- SSH-роли;
- OTP-роли.

Их потеря означает потерю не только данных, но и части машинного доверия проекта.

### 7.3. Связанный резервный комплект

Для восстановления должны быть согласованы:

```text
состояние OpenBao
+ unseal key
+ необходимые PVE-only служебные данные
```

Штатное восстановление не должно автоматически создавать новый пустой OpenBao поверх инфраструктуры, которая ожидает старые CA и секреты.

Воспроизводимые служебные AppRole можно перевыпускать только осознанной восстановительной операцией при сохранённом основном состоянии.

## 8. Проверка контракта

Нужно подтверждать:

- OpenBao обслуживает KV, client CA, host CA, AppRole и целевой SSH OTP как разные функции;
- client CA и host CA имеют разные ключи;
- закрытые CA keys не экспортируются как рабочие файлы;
- PVE-only unseal и административные данные не становятся обычными credentials гостей;
- `kv-reader` не имеет широкого доступа ко всему OpenBao;
- роль обновления Semaphore не может менять PVE/Git secrets;
- машинный AppRole одного гостя не может использовать чужую OTP-роль;
- OTP-роль содержит только цели из `access.yaml`;
- OTP одноразовый;
- сетевой OTP использует TLS;
- удаление права прекращает выдачу новых OTP;
- постоянный root token отсутствует;
- восстановление не заменяет существующий центр доверия пустым новым OpenBao.
