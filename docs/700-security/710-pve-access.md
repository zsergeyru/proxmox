# Доступ к Proxmox

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** определить технические идентичности, роли, ACL и границы доступа к Proxmox после перехода на `910 infra-deployer`.

## 1. Технические идентичности

Основные проектные идентичности:

```text
infra-deployer@pve!automation
ai-agent@pve!infra
```

`infra-deployer@pve!automation` используется только постоянным LXC `910 infra-deployer` для штатного управления инфраструктурой.

`ai-agent@pve!infra` остаётся отдельным контуром AI и не заменяет разворачиватель.

Обе идентичности используют отдельные токены с `privsep=1`.

## 2. Граница infra-deployer

`infra-deployer@pve!automation` должен уметь:

- читать состояние нужных объектов Proxmox;
- создавать обычные VM/LXC;
- изменять поддерживаемые параметры обычных управляемых VM/LXC;
- запускать и останавливать обычные гости;
- использовать разрешённые storage;
- использовать `vmbr0`;
- назначать обычные гости в `managed`;
- читать и использовать разрешённые шаблоны.

Он не должен уметь:

- изменять пользователей Proxmox;
- изменять роли;
- изменять ACL;
- создавать или менять собственный токен;
- менять APT/PVE repository;
- менять сеть физического PVE;
- менять определения storage;
- выключать или перезагружать физический PVE;
- изменять `910` как обычный управляемый объект.

Отсутствие этих прав является частью контракта, а не только рекомендацией.

## 3. Области ACL

Основная модель:

```text
/vms
→ только минимальные права, необходимые для обнаружения и создания нового гостя

/pool/managed
→ полное разрешённое управление обычными гостями проекта

/storage/local
/storage/local-lvm
→ использование разрешённых хранилищ

/sdn/zones/localnetwork/vmbr0
→ использование основной сети
```

`910 infra-deployer` не входит в `managed`.

Права изменения существующих обычных гостей должны по возможности приходить через `/pool/managed`, а не через широкое наследование полномочий на весь `/vms`.

Точный минимальный набор привилегий проверяется на реальном OpenTofu-провайдере до реализации и фиксируется после успешного положительного и отрицательного теста. Нельзя копировать широкий пример роли провайдера как готовый контракт.

## 4. Шаблон 9000 и Packer

OpenTofu использует `9000` как источник клонирования после появления шаблона.

Права, необходимые именно для сборки или замены шаблона через Packer, не должны автоматически расширять постоянный токен `automation`.

Если Packer требует дополнительные полномочия, используется отдельная техническая идентичность или отдельный токен с более узким назначением.

## 5. AI

`ai-agent@pve!infra` управляет только обычными гостями, которым это явно разрешено.

Основная область:

```text
/pool/managed
```

AI не получает право:

- менять `910`;
- менять пользователей, роли и ACL;
- менять шаблон `9000`, кроме отдельно разрешённого чтения/клонирования;
- менять сеть и storage хоста;
- управлять физическим PVE.

## 6. Создание и владение правами

Пользователя, токен и ACL для `infra-deployer` создаёт `bootstrap-pve.sh` локально на PVE.

`910` не управляет собственной PVE-идентичностью.

Обычный повторный bootstrap:

- не ротирует корректный токен;
- не меняет его secret;
- проверяет фактические effective permissions;
- останавливается или предупреждает при появлении лишних административных прав.

Полная смена токена допускается только в явном сценарии восстановления.

## 7. Проверка прав

Проверка должна подтверждать не только разрешения, но и запреты.

Минимальные положительные тесты:

```text
прочитать PVE и node
прочитать managed
создать тестовый обычный LXC/VM в разрешённой области
изменить его CPU/RAM
запустить/остановить его
использовать local/local-lvm и vmbr0
```

Минимальные отрицательные тесты:

```text
изменить 910                    → запрещено
изменить пользователя PVE      → запрещено
изменить ACL                   → запрещено
изменить роль                  → запрещено
изменить storage definition    → запрещено
изменить сеть PVE              → запрещено
выключить PVE                  → запрещено
```

Только после этих тестов набор привилегий считается принятым.

## 8. Секрет токена

Secret токена `infra-deployer@pve!automation` не хранится в Git и не хранится постоянно на PVE.

После первого создания bootstrap передаёт secret в `910` через временный root-only файл.

Внутренняя настройка `910`:

```text
временный secret bootstrap
→ /etc/infra-deployer/secrets/pve-api.env
→ Semaphore Key Store проекта Proxmox Infrastructure
```

Файл в `/etc/infra-deployer/secrets/` остаётся защищённой восстановительной копией внутри самого `910`; рабочий проект Semaphore также хранит credential в зашифрованном Key Store. На PVE постоянной копии secret нет.
