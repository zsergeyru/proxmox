# Доступ к Proxmox

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить проектные учётные записи Proxmox, токены, роли, привилегии, области ACL и правила их проверки.

Этот документ отвечает на вопрос:

> Кто и с какими правами может управлять объектами Proxmox в проекте?

Общие принципы безопасности описываются в `700-overview.md`. Административный доступ по SSH относится к `720-ssh-access.md`.

## 1. Назначение и границы

`710-pve-access.md` является основным источником для проектной модели доступа к Proxmox.

Здесь фиксируются:

- проектные пользователи Proxmox;
- их токены;
- проектные роли;
- обязательные привилегии ролей;
- области ACL;
- доступ к пулу `managed`;
- доступ к шаблону `9000`;
- правила повторного применения настроек;
- проверка фактических полномочий.

В этот документ не входят:

- SSH-доступ к PVE и гостевым системам;
- файловые пути хранения секретов;
- права Linux-пользователей на PVE;
- прикладные учётные записи внутри VM/LXC;
- подробная установка и настройка PVE Configuration.

Эти области имеют собственных владельцев документации.

## 2. Участники доступа

### 2.1. Человек

Человек может работать с Proxmox через отдельную пользовательскую учётную запись или административную учётную запись, если это требуется для эксплуатации.

Права человека не используются автоматикой как техническая идентичность.

Точные персональные учётные записи не являются частью проектного контракта этого файла.

### 2.2. Deployer

Для штатного развёртывания гостевых систем используется отдельная идентичность:

```text
deployer@pve!host-deploy
```

Она используется механизмом `deploy-guest`.

Её назначение:

- создавать VM/LXC;
- изменять поддерживаемые параметры VM/LXC;
- работать с дисками, памятью, процессором и сетью гостя;
- запускать и останавливать гостевые системы;
- работать с пулом `managed`;
- использовать разрешённые хранилища и сеть.

Основная область управления:

```text
/vms
```

с наследованием на объекты VM/LXC.

Это право управления гостевыми системами и не является правом администрирования самого PVE-хоста.

### 2.3. AI-агент

Для AI используется отдельная идентичность:

```text
ai-agent@pve!infra
```

Основная область изменения:

```text
/pool/managed
```

AI может управлять только теми обычными гостевыми системами, которые включены в пул `managed`.

Отдельно AI получает ограниченный доступ к шаблону:

```text
/vms/9000
```

только для просмотра и клонирования.

AI не получает обычные права управления гостевыми системами на весь `/vms`.

## 3. Модель доступа Proxmox

### 3.1. Пользователи и токены

Проект использует отдельные пользователи и отдельные токены для разных механизмов.

Основные идентичности:

```text
deployer@pve!host-deploy
ai-agent@pve!infra
```

Токен не должен использоваться для задачи другой идентичности только потому, что технически обладает подходящими правами.

Секрет токена хранится отдельно от Git и не является частью этого документа.

### 3.2. Разделение технических идентичностей

Deployer и AI имеют разные области ответственности.

```text
deployer
→ штатное развёртывание по контракту проекта
→ область /vms

AI
→ интерактивное и автоматизированное управление разрешёнными объектами
→ область /pool/managed
```

Такое разделение позволяет:

- независимо ограничивать права;
- отдельно отзывать доступ;
- отличать действия двух механизмов;
- не давать AI широкие права, необходимые `deploy-guest`.

### 3.3. Роли и привилегии

В проекте используются роли:

```text
AICloneSource
AIManagedGuest
AINetworkUse
AIStorage
AIManagedPool
```

Точные имена привилегий Proxmox не переводятся.

#### `AICloneSource`

```text
VM.Audit
VM.Clone
```

Назначение — использовать разрешённый объект как источник клонирования.

Основной объект:

```text
/vms/9000
```

#### `AIManagedGuest`

Обязательный набор:

```text
VM.Allocate
VM.Audit
VM.Backup
VM.Clone
VM.Config.CDROM
VM.Config.Cloudinit
VM.Config.CPU
VM.Config.Disk
VM.Config.HWType
VM.Config.Memory
VM.Config.Network
VM.Config.Options
VM.Console
VM.GuestAgent.Audit
VM.PowerMgmt
VM.Snapshot
VM.Snapshot.Rollback
```

Роль предназначена для жизненного цикла VM/LXC в разрешённой области.

`VM.Console` фактически даёт доступ к консоли гостевой системы и поэтому применяется только к доверенным проектным идентичностям.

#### `AINetworkUse`

```text
SDN.Use
```

Разрешает использовать разрешённую сеть.

Не даёт права изменять сеть PVE-хоста или настройки SDN.

#### `AIStorage`

```text
Datastore.AllocateSpace
Datastore.Audit
```

Разрешает использовать разрешённое хранилище для дисков и клонирования.

Не даёт права менять определение самого хранилища.

#### `AIManagedPool`

```text
Pool.Allocate
Pool.Audit
```

Разрешает работать с пулом `managed` и его членством в пределах выданной области ACL.

### 3.4. Разделённые токены `privsep`

Новые проектные токены создаются с:

```text
privsep=1
```

Это означает, что полномочия токена определяются собственными ACL и не должны автоматически совпадать со всеми правами пользователя.

Существующий токен с `privsep=1` при обычной повторной конфигурации:

- не пересоздаётся;
- не получает новый секрет;
- сохраняется, если соответствует требованиям.

Если существующий токен имеет:

```text
privsep=0
```

он не переводится автоматически на `privsep=1`.

Вместо этого:

```text
privsep=0
→ предупредить
→ сохранить существующий токен
→ не выполнять скрытую смену его модели прав
```

Изменение такого токена выполняется отдельной осознанной операцией.

### 3.5. Создание, изменение и отзыв

PVE Configuration создаёт только отсутствующие обязательные элементы.

Для роли:

```text
роль отсутствует
→ создать

не хватает обязательной привилегии
→ добавить недостающую

есть дополнительные привилегии
→ автоматически не удалять
```

Для ACL:

```text
обязательная ACL отсутствует
→ добавить

обязательная ACL существует
→ оставить

существует дополнительная ACL
→ автоматически не удалять
```

Обычное повторное применение конфигурации не должно неожиданно сужать существующие права.

Сужение прав или отзыв доступа выполняются отдельной операцией после проверки того, какие механизмы используют эту идентичность.

Если токен существует, но его секрет потерян, токен не пересоздаётся автоматически. Требуется отдельное решение о восстановлении или смене.

## 4. Области доступа и ACL

### 4.1. Deployer

Для `deployer@pve!host-deploy` используется следующая основная схема:

```text
/vms
→ AIManagedGuest

/pool/managed
→ AIManagedPool

разрешённое хранилище
→ AIStorage

разрешённая сеть
→ AINetworkUse
```

Отдельная роль `AICloneSource` на шаблон `9000` для deployer не требуется, потому что `VM.Audit` и `VM.Clone` уже входят в `AIManagedGuest` на `/vms`.

Широкая область `/vms` нужна штатному механизму развёртывания, но не даёт прав управления самим PVE-хостом.

### 4.2. Пул `managed`

Пул:

```text
managed
```

является основной областью обычного управления гостевыми системами для AI.

Схема:

```text
гость входит в managed
→ AI может выполнять разрешённые операции уровня VM/LXC

гость не входит в managed
→ обычные права AI на управление гостем не действуют
```

Членство гостя в `managed` определяется требуемым состоянием гостя через параметр `pve_management`.

Это ограничение относится только к управлению через Proxmox и не определяет SSH-доступ внутрь гостя.

### 4.3. Шаблон `9000`

Базовый шаблон:

```text
VMID 9000
```

не входит в обычную область изменения AI.

Для `ai-agent@pve!infra`:

```text
/vms/9000
→ AICloneSource
```

Разрешено:

- просматривать шаблон;
- использовать его как источник клонирования.

Не разрешено обычными правами AI:

- менять параметры шаблона;
- удалять его;
- использовать его как обычную управляемую VM.

### 4.4. Объекты вне области управления

AI не получает обычных прав изменения на:

- гостевые системы вне `managed`;
- защищённые специальные VM/LXC, если они не включены в `managed`;
- шаблон `9000` кроме просмотра и клонирования;
- сам PVE-хост;
- пользователей, роли и ACL Proxmox;
- настройки сети хоста;
- определения хранилищ;
- сертификаты;
- обновления PVE;
- межсетевой экран самого хоста;
- выключение или перезагрузку физического PVE;
- собственные права доступа.

`protection=1` у VM/LXC является дополнительной защитой, но не заменяет ACL.

## 5. Проверка прав

### 5.1. Проверка конфигурации

Проверка должна подтверждать наличие:

- пользователей Proxmox;
- токенов;
- `privsep=1` для новых и корректно настроенных токенов;
- проектных ролей;
- обязательных привилегий в ролях;
- обязательных ACL;
- пула `managed`;
- доступа к разрешённым хранилищам;
- доступа к разрешённой сети;
- отдельного доступа AI к шаблону `9000`.

Проверка наличия записи в конфигурации сама по себе недостаточна.

### 5.2. Проверка фактических разрешений

Для каждой технической идентичности должны проверяться её фактические эффективные права.

Минимальная проверка для deployer:

```text
управление VM/LXC на /vms
→ разрешено

администрирование самого PVE
→ не разрешено
```

Минимальная проверка для AI:

```text
гость в managed
→ разрешённые операции доступны

гость вне managed
→ обычные операции изменения недоступны

шаблон 9000
→ просмотр и клонирование доступны
→ обычное изменение недоступно
```

Проверка должна учитывать не только назначенные роли, но и итоговые права после применения ACL.

### 5.3. Проверка запретов

Для модели доступа важно проверять не только то, что нужная операция разрешена, но и то, что запрещённая операция действительно недоступна.

В частности, для AI должны проверяться запреты на:

- изменение гостя вне `managed`;
- изменение шаблона `9000`;
- изменение ролей и ACL;
- управление пользователями Proxmox;
- изменение сети PVE;
- изменение определений хранилищ;
- управление самим PVE-хостом.

Проверка границ должна выполняться после существенного изменения ролей или ACL.

## 6. Границы ответственности

Этот документ является основным источником для модели прав внутри Proxmox.

Он определяет:

- проектные идентичности Proxmox;
- роли;
- обязательные привилегии;
- области ACL;
- правила повторного применения;
- проверку фактических прав.

При этом:

- общие принципы безопасности находятся в `700-overview.md`;
- SSH-идентичности и ключи находятся в `720-ssh-access.md`;
- точные файловые пути токенов и других локальных данных PVE находятся в `../200-pve/230-host-layout.md`;
- создание обязательных объектов PVE Configuration описывается в `../200-pve/220-host-configuration.md`;
- членство конкретного гостя в `managed` определяется его требуемым состоянием;
- причины выбора такой модели доступа относятся к `790-decisions.md`.
