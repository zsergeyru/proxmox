## 1. Основной принцип

PVE API и root SSH являются разными каналами.

OpenBao управляет доступностью рабочих API credentials, но не заменяет собственные ACL Proxmox.

Требуемые права менее доверенных субъектов задаются в `access.yaml`.

## 2. Доступ infra-manager к PVE API

`infra-manager` использует отдельную административную PVE API-идентичность `root@pam!infra-manager`.

Для текущего административного контура сохраняется `privsep=0`, потому что 910 является доверенным владельцем инфраструктурного жизненного цикла.

Рабочий API secret в целевой архитектуре хранится в OpenBao KV и выдаётся только управляющему контуру через ограниченную OpenBao policy.

TLS PVE API всегда проверяется по PVE CA.

Секрет API не хранится в Git и не должен быть постоянным файлом в rootfs 910.

## 3. Root SSH к PVE

Отдельный root SSH используется только для операций, которым действительно нужны полномочия физического хоста или доступ к PVE-only данным.

Например:

- отдельные свойства LXC, недоступные API token;
- вызов PVE-only механизма разблокировки и восстановления OpenBao;
- узкие восстановительные операции.

Для него используется отдельная постоянная Ed25519-пара и строгий `known_hosts`.

Эта identity не используется для Linux-гостей, Git или PVE API.

Поскольку доступ к PVE требуется в том числе для восстановления OpenBao, root SSH private key не должен зависеть от работоспособности OpenBao.

## 4. Доступ менее доверенных контуров

Если обычному гостю или AI Control требуется прямой PVE API, он получает отдельную PVE-идентичность.

Право получить её задаётся в `access.yaml` и контролируется OpenBao policy.

Сам credential хранится в OpenBao KV.

Даже если OpenBao разрешил получить credential, Proxmox должен дополнительно ограничить его собственными ACL.

Менее доверенный субъект не получает `root@pam!infra-manager` и root SSH private key PVE.

## 5. Область managed

Pool `managed` является организационной областью и может служить границей полномочий менее доверенных PVE-идентичностей.

Для `infra-manager` он не является границей полномочий.

Например, AI Control может иметь отдельный API credential, ACL которого разрешают изменение только объектов `managed`, при этом сама VM AI Control не обязана входить в этот pool.

Факт нахождения объекта в pool не выдаёт credential автоматически.

## 6. Хранение credentials

Целевая модель:

~~~text
OpenBao KV
→ рабочие PVE API secrets

PVE access-область
→ root SSH identity infra-manager → PVE
→ known_hosts PVE
→ PVE CA

PVE-only
→ данные, необходимые для восстановления OpenBao
~~~

Точные физические пути находятся в `230-host-layout.md`.

## 7. Жизненный цикл

API credential создаётся доверенным контуром, помещается в OpenBao KV и может быть независимо отозван или перевыпущен.

Повторный запуск не должен без причины создавать новую PVE identity.

Root SSH identity меняется только явной процедурой с установкой новой открытой части и подтверждённым удалением старой.

Удаление одного менее доверенного субъекта отзывает только его собственный PVE credential и ACL.

## 8. Проверка

Проверка должна подтверждать:

- TLS PVE API по ожидаемому CA;
- отсутствие API secret в Git;
- доступ `infra-manager` к ожидаемому PVE-контракту;
- отсутствие у менее доверенного субъекта административного credential 910;
- соответствие PVE ACL правилу `access.yaml`;
- невозможность выйти за границу `managed`, если она задана;
- отдельность root SSH identity;
- отсутствие зависимости recovery-доступа к PVE от OpenBao.
