# Доступ 910 к Proxmox

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить PVE API-доступ постоянного управляющего LXC `910 infra-manager`.

## 1. Принцип

`910` не получает постоянный root SSH на PVE.

Для автоматизации используется отдельный API token существующего пользователя:

```text
root@pam!infra-manager
```

Token создаётся с:

```text
privsep=1
```

Права назначаются самому token. Отдельный пользователь `infra-manager@pve`, отдельные группы и собственная роль не используются.

Главная граница 910:

```text
/vms
→ управление всеми VM/LXC

PVE host
→ только необходимое чтение и точечное использование storage/network
```

Для домашнего сервера дополнительное разделение прав 910 по нескольким pool не используется.

## 2. Роль pool managed

Pool:

```text
managed
```

сохраняется, но больше не является границей прав 910.

Он нужен для другой задачи: ограничивать область, которой может управлять AI Control и другие менее привилегированные контуры.

910 должен уметь создавать и назначать обычных гостей в `managed`, а также читать сам pool. Поэтому на этом пути token получает одновременно `PVEVMAdmin` и `PVEPoolUser`. Более специфичный ACL не должен лишать 910 права `Pool.Audit`.

Сам `910 infra-manager` в `managed` не входит.

## 3. ACL token

Используются штатные роли Proxmox:

| Путь | Роль | Назначение |
|---|---|---|
| `/` | `PVEAuditor` | чтение состояния PVE |
| `/vms` | `PVEVMAdmin` | жизненный цикл и конфигурация всех VM/LXC |
| `/pool/managed` | `PVEVMAdmin`, `PVEPoolUser` | управление гостями, назначение в pool и чтение pool |
| `/storage/local-lvm` | `PVEDatastoreUser` | размещение дисков |
| `/storage/local` | `PVEDatastoreAdmin` | загрузка установочных ISO Packer |
| `/sdn/zones/localnetwork/vmbr0` | `PVESDNUser` | использование основной сети |

ACL на `/pool/managed` не ограничивает область 910: основной изменяющий доступ к гостям задаётся `/vms`. `PVEPoolUser` добавляется только для `Pool.Audit`, чтобы 910 мог читать состояние pool без выдачи широких административных прав PVE.

## 4. Почему используется root@pam

`root@pam` используется только как владелец token.

Это не означает передачу полномочий root внутрь 910. При `privsep=1` эффективные права token ограничиваются его собственными ACL.

Такой вариант позволяет не создавать отдельного пользователя только ради одного домашнего управляющего контура и не поддерживать два одинаковых набора ACL.

## 5. Что разрешено

Token должен позволять 910:

- читать состояние PVE;
- создавать VM/LXC;
- клонировать шаблоны;
- изменять параметры VM/LXC;
- запускать и останавливать VM/LXC;
- выполнять снимки и другие штатные операции гостевого уровня, разрешённые `PVEVMAdmin`;
- удалять VM/LXC;
- создавать обычных гостей сразу в `managed`;
- использовать `local-lvm` для дисков;
- загружать установочные ISO Packer в `local`;
- использовать `vmbr0`.

В область `/vms` технически входит и VMID/CTID 910. Это принято осознанно ради простой модели домашнего сервера.

Собственный виртуальный объект 910 при этом остаётся за отдельным bootstrap-state:

- `guest.yaml` 910 использует обычный профиль `debian-lxc-docker`;
- основной OpenTofu state внутри 910 явно исключает VMID 910;
- отдельный bootstrap-state содержит только VMID 910 и применяется временным 990;
- `protection=true` защищает объект от случайного удаления.

## 6. Что не выдаётся

Token не получает права:

- управлять пользователями, token, ролями и ACL;
- изменять конфигурацию физического PVE;
- изменять физическую сеть и bridge-конфигурацию PVE;
- изменять определения хранилищ;
- управлять репозиториями PVE;
- перезагружать или выключать физический PVE;
- произвольно расширять собственные полномочия.

То есть 910 получает широкие права на **гостевые системы**, но не превращается в администратора всего гипервизора.

## 7. Постоянный token 910

Постоянный token создаёт `scripts/infra-manager/pve-bootstrap-access.sh` из закрытого проекта.

После того как временный 990 создал LXC 910, public bootstrap выполняет этот helper от root на PVE. Helper передаёт 910:

~~~text
PVE CA
+
root@pam!infra-manager secret
~~~

Secret сохраняется внутри 910 и затем используется его постоянным инфраструктурным контуром.

При обычном повторном запуске существующий token не перевыпускается без необходимости. Потерянный secret требует явной процедуры восстановления.

## 8. Временный token 990

Временный bootstrap-runner использует отдельную идентичность:

~~~text
root@pam!bootstrap-runner
~~~

Её создаёт:

~~~text
scripts/bootstrap-runner/pve-access.sh
~~~

Token имеет `privsep=1` и получает только права, необходимые для применения bootstrap-state 910:

| Путь | Роль | Назначение |
|---|---|---|
| `/` | `PVEAuditor` | чтение PVE и локального LXC template |
| `/vms` | `PVEVMAdmin` | создать или изменить виртуальный объект 910 |
| `/storage/local-lvm` | `PVEDatastoreUser` | rootfs 910 |
| `/sdn/zones/localnetwork/vmbr0` | `PVESDNUser` | интерфейс 910 |

Права `managed`, загрузка ISO и другие постоянные полномочия 910 временному token не выдаются.

После успешной настройки 910:

~~~text
сохранить bootstrap-state
→ удалить ACL bootstrap-runner
→ удалить token bootstrap-runner
→ удалить 990
~~~

При незавершённой операции token может временно сохраняться вместе с оставленным 990, чтобы не разрушать возможность безопасного продолжения.

## 9. Semaphore и OpenTofu

В Semaphore не создаётся отдельная запись Key Store с копией PVE token.

OpenTofu получает:

```text
TF_VAR_pve_endpoint
TF_VAR_pve_api_token
```

через Variable Group `OpenTofu PVE`.

Тот же PVE-доступ используется инфраструктурными заданиями 910, которым действительно нужен жизненный цикл VM/LXC.

## 10. Проверка

Внутри 910 доступны:

```bash
infra-manager-status
infra-manager-status --full
infra-manager-pve-access-check
infra-manager-pve-lifecycle-test --apply
```

`infra-manager-pve-access-check` проверяет:

- авторизацию API;
- `PVEVMAdmin` на `/vms`;
- возможность назначения гостей в `managed`;
- доступ к требуемому storage и bridge;
- отсутствие административных прав PVE-хоста.

`infra-manager-pve-lifecycle-test --apply` выполняет реальный проверочный цикл на временном LXC:

```text
создать
→ изменить конфигурацию
→ запустить
→ остановить
→ удалить
```

Тестовый гость может создаваться в `managed`, чтобы одновременно проверять и назначение в этот pool.

## 11. Добавление новых прав

Новые host-level права не выдаются заранее.

Для Packer уже добавлен доступ к `/storage/local`, потому что ISO-builder должен загрузить установочный Debian ISO. Файл ответов Debian Installer Packer отдаёт напрямую из `infra-runtime` по временному HTTP-серверу, поэтому отдельный ISO для него не создаётся.

Если Packer, OpenTofu или другой инфраструктурный инструмент потребует дополнительное право, сначала определяется конкретная операция и только затем добавляется минимально необходимый ACL.

Расширение guest-level возможностей внутри уже выданной роли `PVEVMAdmin` отдельного изменения ACL не требует.
