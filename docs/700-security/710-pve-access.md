# Доступ 910 к Proxmox

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** определить минимальный PVE API-доступ постоянного разворачивателя `910 infra-deployer`.

## 1. Принцип

`910` не получает `root`-доступ к PVE по SSH и не получает административный API token.

Для автоматизации используется отдельный API token существующего пользователя `root@pam`:

```text
root@pam!infra-deployer
```

Token создаётся с:

```text
privsep=1
```

Права назначаются самому token. Отдельный пользователь `infra-deployer@pve`, отдельные группы и дублирование ACL пользователя и token не используются.

## 2. Управляемая область

Обычные VM/LXC проекта входят в pool:

```text
managed
```

`910 infra-deployer` в этот pool не входит.

Главная граница:

```text
managed
→ автоматизация может изменять обычные VM/LXC

вне managed
→ автоматизация не получает общих изменяющих VM-прав
```

Это отделяет сам 910 от объектов, которыми он управляет.

## 3. ACL token

Используются только штатные роли Proxmox:

| Путь | Роль | Назначение |
|---|---|---|
| `/` | `PVEAuditor` | чтение состояния PVE |
| `/pool/managed` | `PVEVMAdmin` | жизненный цикл и конфигурация управляемых VM/LXC |
| `/storage/local-lvm` | `PVEDatastoreUser` | размещение дисков |
| `/sdn/zones/localnetwork/vmbr0` | `PVESDNUser` | использование основной сети |

Собственная роль `InfraManagedGuest` больше не используется.

## 4. Почему используется root@pam

`root@pam` используется только как владелец token.

Это не означает передачу прав `root` в 910. При `privsep=1` token использует собственные ACL и остаётся ограниченным ими.

Такой вариант позволяет не создавать отдельного пользователя только ради одного технического token и не поддерживать два одинаковых набора ACL.

## 5. Что разрешено

В текущей модели token должен позволять 910:

- читать состояние PVE;
- создавать обычные VM/LXC сразу в `managed`;
- изменять и удалять членов `managed`;
- запускать и останавливать членов `managed`;
- использовать `local-lvm` для дисков;
- использовать `vmbr0`;


## 6. Что не выдаётся

Token не получает отдельные ACL:

- на изменение `910`;
- на управление пользователями, token, ролями и ACL;
- на изменение конфигурации физического PVE;
- на изменение хранилищ;
- на изменение сети PVE;
- на создание произвольных pool.

Внутренний тест доступа дополнительно проверяет отсутствие изменяющих VM-прав на `/vms/910` и административных прав на `/`.

## 7. Создание и хранение token

Token создаёт публичный `bootstrap-pve.sh` локально на PVE от `root`.

Secret выдаётся Proxmox только при создании token, поэтому первоначальная передача выполняется сразу:

```text
PVE
→ временный root-only файл
→ 910
→ /etc/infra-deployer/secrets/pve-api.env
```

После успешной настройки временная копия удаляется.

При обычном повторном запуске существующий token и постоянный secret в 910 повторно используются.

Если token существует, а secret потерян, обычный запуск останавливается. Явное перевыпускание выполняется через:

```text
bootstrap-pve.sh --recover
```

## 8. Semaphore и OpenTofu

В Semaphore не создаётся отдельная запись Key Store с копией PVE token.

OpenTofu получает:

```text
TF_VAR_pve_endpoint
TF_VAR_pve_api_token
```

через Variable Group `OpenTofu PVE`.

При изменении постоянного PVE credential секрет Variable Group синхронизируется с `pve-api.env`.

## 9. Проверка

Внутри 910 доступны:

```bash
infra-deployer-status
infra-deployer-status --full
infra-deployer-pve-access-check
infra-deployer-pve-lifecycle-test --apply
```

`infra-deployer-pve-access-check` проверяет фактические эффективные права через HTTPS API.

`infra-deployer-pve-lifecycle-test --apply` выполняет реальный проверочный цикл:

```text
создать временный LXC в managed
→ изменить конфигурацию
→ запустить
→ остановить
→ удалить
```

Этот тест уже успешно проходил на реальном PVE для предыдущего минимального набора прав. После перехода на штатную роль `PVEVMAdmin` его необходимо выполнить ещё один раз, чтобы подтвердить новую упрощённую модель.

## 10. Добавление прав

Новые права не выдаются заранее.

Например, право на клонирование будущего шаблона `9000` сейчас не выдаётся. Оно будет добавлено только одновременно с реализацией создания VM из этого шаблона.

Если будущая операция OpenTofu, Ansible или другого средства действительно требует дополнительного PVE-права:

```text
операция не проходит
→ определить конкретное недостающее право
→ оценить область его действия
→ добавить минимально необходимое
→ повторить проверку
```

Отдельные PVE-идентичности для будущих функций не создаются до появления реальной необходимости.
