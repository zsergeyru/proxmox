## 1. Модель доверия

`infra-manager` является доверенным административным контуром PVE.

Для него используются два независимых канала:

```text
HTTPS API
→ обычное управление Proxmox и OpenTofu

root SSH
→ только операции, которым нужны полномочия самого PVE-хоста
```

Root SSH не заменяет API и не создаёт второй способ описывать инфраструктуру.

Если операцию можно штатно выполнить через PVE API, она должна выполняться через API.

## 2. Постоянный API-доступ

Постоянная техническая идентичность:

```text
root@pam!infra-manager
privsep=0
```

При `privsep=0` токен наследует административные полномочия `root@pam`.

Для постоянного `infra-manager` не поддерживается отдельная матрица ограниченных ACL. Это осознанная граница доверия: компрометация управляющего контура уже считается компрометацией административного управления PVE.

API secret:

- не хранится в Git;
- принадлежит постоянной области доступа на PVE;
- показывается `infra-manager` только через предназначенную для этого область;
- не должен без необходимости передаваться внутрь прикладных контейнеров управляющей среды;
- должен использоваться с проверкой TLS.

Канонические пути секрета и PVE CA определены в [`../200-pve/230-host-layout.md`](../200-pve/230-host-layout.md).

Отключение проверки TLS для штатного API-доступа запрещено.

## 3. Временный доступ первоначального контура

До появления постоянного управляющего контура временный bootstrap-runner использует отдельную техническую идентичность:

```text
root@pam!bootstrap-runner
privsep=0
```

Этот доступ:

- существует только для первоначального создания или восстановления;
- не является постоянной учётной записью проекта;
- удаляется после успешной передачи управления;
- не переиспользуется как постоянный токен `infra-manager`.

Временный и постоянный токены имеют разные имена и разные жизненные циклы, даже если оба используют административные полномочия `root@pam`.

## 4. Root SSH к PVE

Для `infra-manager` существует отдельная постоянная SSH-идентичность PVE root.

Она не совпадает с:

- Git Deploy Key;
- Ansible-идентичностью для входа в Linux-гости;
- дополнительными `management.ssh_identity` отдельных гостей.

Закрытая часть принадлежит постоянной области доступа PVE и показывается `infra-manager` только для чтения.

Открытая часть регистрируется только в root SSH-доступе PVE.

Проверка SSH-сервера PVE выполняется строго по отдельному `known_hosts`. Автоматическое принятие изменившегося ключа сервера запрещено.

Root SSH используется для узких операций, например:

- свойств LXC, которые PVE не разрешает менять API-токеном;
- вызова PVE-only служебного механизма OpenBao;
- других явно определённых хостовых операций.

Наличие root SSH не разрешает переносить в shell PVE обычную логику OpenTofu или Ansible.

## 5. Область `managed`

Pool `managed` является организационной классификацией объектов.

Для доверенного `infra-manager` он **не является границей полномочий**.

Поле гостя `pve_management` также не выдаёт PVE API secret и не создаёт административную учётную запись.

Полномочия всегда принадлежат конкретной технической идентичности, а не факту нахождения VM/LXC в pool.

## 6. Кто не получает административный PVE-доступ

Обычные прикладные гости не получают:

- постоянный API secret `infra-manager`;
- root SSH-ключ PVE;
- возможность выполнять `pct`, `qm` или shell PVE как следствие наличия профиля или `pve_management`.

AI-контур также не получает эти секреты автоматически.

Если в будущем менее доверенному контуру понадобится прямой PVE API, для него должна быть создана отдельная идентичность с отдельной моделью прав.

## 7. Жизненный цикл доступа

### 7.1. Создание

Постоянный API token и root SSH-идентичность создаются первоначальным доверенным контуром до передачи управления.

### 7.2. Повторный запуск

Повторный запуск должен переиспользовать существующие постоянные данные доступа, если их целостность подтверждена.

Тихая замена постоянного root SSH-ключа новым ключом под прежним именем запрещена.

### 7.3. Восстановление

API token допускает перевыпуск, если старый secret потерян или отозван.

Root SSH-идентичность должна восстанавливаться из постоянного защищённого состояния либо заменяться явной процедурой ротации с обновлением регистрации на PVE.

### 7.4. Отзыв

Удаление управляющего контура должно отзывать активный API token и убирать его root SSH-авторизацию на PVE.

Удаление объекта не должно неявно уничтожать канонические постоянные данные восстановления. Политика удаления постоянного состояния описана в разделе PVE.

## 8. Проверка контракта

Проверка доступа должна подтверждать:

- API отвечает через проверенный TLS;
- токен имеет ожидаемую административную идентичность;
- доступен необходимый PVE-контракт;
- root SSH действительно выполняется от `root`;
- SSH-сервер PVE проходит строгую проверку;
- временная bootstrap-идентичность отсутствует после успешного завершения первоначального контура.

Конкретные команды проверки относятся к эксплуатационной документации.
