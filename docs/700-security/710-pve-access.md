## 1. Роль PVE в модели доверия

PVE является корневой административной системой инфраструктуры.

Он одновременно:

- создаёт и хранит объекты VM/LXC;
- предоставляет API для штатного управления инфраструктурой;
- предоставляет root SSH для узких операций уровня хоста;
- хранит PVE-only данные восстановления;
- участвует в административных операциях OpenBao;
- подтверждает идентичность гостя перед выпуском SSH host certificate.

Право управлять PVE не выводится из наличия гостя в проекте. Оно должно быть явно закреплено в `access.yaml` и реализовано отдельной технической идентичностью.

## 2. Постоянный доступ infra-manager

`guest:910` является административно доверенным исполнителем PVE.

Для него существуют два независимых канала:

```text
910 → HTTPS PVE API → обычное управление объектами

910 → root SSH → узкие операции физического PVE
```

Если действие можно штатно выполнить через API, оно должно выполняться через API.

Root SSH не является вторым универсальным способом управления инфраструктурой и не заменяет OpenTofu.

## 3. PVE API

Постоянная техническая идентичность:

```text
root@pam!infra-manager
privsep=0
```

При `privsep=0` токен наследует административные полномочия `root@pam`.

Это соответствует принятой границе доверия: компрометация постоянного управляющего контура уже рассматривается как компрометация административного управления PVE.

### 3.1. Как API связан с другими компонентами

```text
access.yaml
   ↓ право guest:910 → pve-api
OpenBao KV
   ↓ рабочий API secret
infra-manager / OpenTofu
   ↓ HTTPS + проверка TLS
PVE API
```

OpenBao хранит рабочий secret, но не решает, кому положено право управлять PVE. Это решение задаёт `access.yaml`.

OpenTofu использует PVE API для декларативного управления объектами. Другой служебный код 910 может использовать тот же API только в пределах функций управляющего контура.

Отключение проверки TLS для штатного API запрещено.

## 4. Root SSH к PVE

Для `infra-manager` существует отдельная постоянная SSH-идентичность пользователя `root` PVE.

Она не совпадает с:

- Git credential;
- временной идентичностью Ansible;
- SSH AppRole обычных гостей;
- SSH host CA;
- PVE API token.

Root SSH нужен только там, где операция относится именно к физическому PVE или не может быть безопасно выполнена через API.

Примеры таких функций:

- операции над свойствами LXC, недоступными используемому API-механизму;
- вызов PVE-only механизма OpenBao;
- проверка объекта PVE перед подписью SSH host key;
- действия аварийного восстановления.

SSH-сервер PVE должен проверяться строго. Неожиданная смена его host identity не принимается автоматически.

## 5. Первоначальный контур

До появления постоянного 910 используется отдельная временная административная идентичность:

```text
root@pam!bootstrap-runner
privsep=0
```

Она нужна только для первоначального создания или восстановления постоянного управляющего контура.

После успешной передачи управления временный доступ должен быть удалён.

Bootstrap credential и постоянный credential 910 не переиспользуют одну идентичность, даже если оба административно доверены.

## 6. Кто не получает прямой PVE-доступ

`guest:410` не имеет прямого административного PVE API и root SSH к PVE.

Для Hermes на 410 реализован в исходниках отдельный **отключённый по умолчанию** ограниченный SSH-вход на физический PVE, **только** для запуска проверенных команд `infra-manager`. Сквозная проверка на работающем сервере ещё не проводилась:

```text
410 Hermes
    ↓ ограниченный SSH + короткоживущий сертификат OpenBao
PVE: отдельная учётная запись и принудительная команда
    ↓ проверка операции, VMID и разрешения
PVE: infra-manager (без trusted-pve)
    ↓ штатная проверка управляющего контейнера и pct exec
910 infra-manager
    ↓ единый исполнитель, OpenTofu / Ansible / PVE API
PVE
```

Semaphore в этом маршруте не участвует. Наличие ограниченного SSH-входа **не означает** права на обычный shell, root SSH, PVE API или прямое выполнение `pct`/`qm`.

Требования к реализации:

- аутентификация выделенной краткоживущей SSH-идентичностью OpenBao; отдельная техническая учётная запись PVE, без интерактивной оболочки, пересылки портов и произвольных команд;
- принудительный серверный обработчик проверяет операцию и числовой VMID, а также разрешения из `access.yaml`, не доверяя аргументам и правилам внутри Hermes;
- `infra-manager guests`, `status [VMID]`, `test VMID` — чтение и проверка только допустимых целей;
- `deploy VMID`, `sync VMID`, `repair VMID` — только для отдельно разрешённых целей и после проверяемого сервером подтверждения оператора вне языковой модели;
- VMID 100, 410 и 910 запрещены для самостоятельных изменений; `recover`, `repair` без VMID и произвольное управление PVE запрещены;
- оболочка PVE должна поддержать **недоверенный режим** вызова без `--trusted-pve`, иначе операторские пароли могут попасть к агенту; нельзя просто открыть ему доступ к текущей root-команде;
- обязательно сохраняются существующая проверка принадлежности 910, общий путь выполнения, блокировки операций и журнал результата без секретов;
- отмена права из `access.yaml` должна блокировать новые вызовы независимо от настроек Hermes.

В ветке `feature/410-restricted-pve-operator` добавлены тип права `pve-operator/guest-operation/execute`, серверный обработчик, отдельная роль подписи OpenBao и клиент-навык Hermes. Автоматическая установка и выдача идентичности связаны с развёртыванием 910 и 410, но требуют явного переключателя `INFRA_ENABLE_PVE_AGENT_ACCESS=1` в доверенном контуре. При выключении PVE удаляет разрешение SSH и отзывает роль OpenBao; 410 удаляет локальный навык и его идентичность. **На работающем PVE доступ ещё не включён и не проверен.** Старое правило Semaphore не выдаёт доступ к PVE.

Обычные прикладные гости также не получают административные PVE credentials автоматически.

Если в будущем менее доверенному контуру понадобится прямой PVE API, для него должна быть отдельная техническая идентичность и отдельная модель полномочий.

## 7. Pool managed и полномочия

`pool managed` классифицирует объекты, но не является самостоятельной границей PVE-прав.

Нахождение VM/LXC в pool не означает, что субъект получает:

- PVE API;
- root SSH;
- возможность выполнять `pct` или `qm`;
- доступ к PVE-only данным.

Полномочия принадлежат технической идентичности и задаются контрактом доступа.

## 8. Жизненный цикл

### 8.1. Создание

Постоянный API token и root SSH-идентичность создаются доверенным первоначальным контуром до передачи управления 910.

### 8.2. Использование

API secret выдаётся рабочим программам через защищённый контур OpenBao.

Root SSH используется как отдельный канал только для явно определённых хостовых функций.

### 8.3. Ротация

API token может быть перевыпущен с обновлением секрета OpenBao.

Замена постоянной root SSH-идентичности требует явной ротации и обновления доверия на PVE; тихая генерация нового ключа под прежней идентичностью запрещена.

### 8.4. Отзыв

Удаление управляющего контура должно отзывать его активный API token и root SSH-авторизацию.

Отзыв рабочего доступа не должен автоматически уничтожать резервные данные, необходимые для осознанного восстановления.

## 9. Проверка контракта

Нужно подтверждать:

- только ожидаемые субъекты имеют прямой административный PVE-доступ;
- API использует TLS с проверкой сертификата;
- постоянная API-идентичность соответствует `infra-manager`;
- root SSH действительно отделён от Git и гостевого SSH;
- root SSH проверяет подлинность PVE;
- `guest:410` не получает прямой PVE API, root SSH или обычную оболочку PVE; будущий отдельный SSH-канал проверяет команду, VMID и согласие оператора;
- агентский режим `infra-manager` не передаёт `--trusted-pve` и не выдаёт секреты;
- до реализации отдельной политики доступ 410 к ограниченному SSH на PVE остаётся закрытым;
- bootstrap-доступ исчезает после передачи управления постоянному контуру.

Конкретные команды и файловые пути относятся к документации PVE и 910.
