# Решения по безопасности

Этот файл хранит устойчивые решения, относящиеся к общей модели безопасности проекта.

## OpenBao является центральным хранилищем машинных секретов

Для машинных секретов проекта используется самостоятельно размещённый OpenBao.

Причины выбора:

- единая точка управления секретами;
- отдельные политики и машинные идентичности для разных сервисов и AI-агентов;
- возможность централизованной смены и отзыва доступа;
- отсутствие необходимости хранить действующие секреты в Git;
- возможность позже добавить SSH CA, PKI и другие функции без замены основной системы секретов.

Первая версия намеренно ограничивается Integrated Storage (Raft), KV v2, policies и AppRole.

## OpenBao размещается в 910

OpenBao работает отдельным Docker-контейнером внутри 910 infra-manager.

Отдельная VM/LXC только ради OpenBao для одного домашнего PVE не создаётся. OpenBao не объединяется с infra-runtime: контейнеры имеют независимый жизненный цикл и отдельные постоянные данные.

## Один узел OpenBao достаточен

Для первой версии используется один узел OpenBao.

HA-кластер на одном физическом PVE не устранил бы основную физическую точку отказа, но увеличил бы сложность эксплуатации. Отказоустойчивость обеспечивается воспроизводимостью 910 и проверяемыми резервными копиями состояния OpenBao.

## Ключ обычного unseal хранится на PVE

Обычный запуск OpenBao после перезагрузки не должен требовать ручного вмешательства.

Ключ автоматического unseal хранится на PVE вне 910 и передаётся уже запущенному OpenBao только при открытии.

~~~text
данные OpenBao → 910
ключ обычного запуска → PVE
аварийные данные восстановления → вне PVE и 910
~~~

Получение одной резервной копии 910 поэтому не даёт одновременно зашифрованное хранилище и ключ обычного запуска.

PVE остаётся корнем доверия виртуальной инфраструктуры; эта схема не предназначена для защиты от полного административного захвата работающего PVE.

## На PVE не запускается дополнительный сервер секретов

Автоматический unseal реализуется небольшим systemd oneshot с использованием штатного pct.

На PVE не устанавливаются OpenBao CLI, Python, curl, jq или отдельный постоянно работающий агент только ради unseal.

## Инициализация не является частью обычной загрузки

PVE может открыть только уже инициализированный OpenBao.

Если хранилище не инициализировано, автоматический механизм не выполняет operator init. Первоначальная инициализация и восстановление являются отдельными управляемыми операциями.

## Резервирование OpenBao выполняется через Raft snapshot

Файловая копия работающего каталога Raft не считается единственным штатным способом резервирования OpenBao.

Перед общей резервной копией 910 создаётся штатный Raft snapshot, который сохраняется под /var/lib/persistent/ и затем попадает в единый механизм резервного копирования гостя.

## Потеря OpenBao не должна блокировать восстановление инфраструктуры

Большинство машинных секретов проектируется как перевыпускаемые.

Если база OpenBao полностью потеряна, допустимо создать новый OpenBao, повторно применить политики из Git и выпустить новые PVE/API/AppRole и другие credentials.

Неперевыпускаемые секреты должны иметь отдельный документированный путь восстановления.

## OpenBao Agent не обязателен

Первая версия не требует OpenBao Agent возле каждого приложения.

Он добавляется только там, где приложение действительно нуждается в автоматическом обновлении токена, шаблонизации секретов или другой функции Agent.
