## 1. Решения по границам доверия

### 1.1. Почему управляющий контур считается административно доверенным PVE

**Проблема.**
Управляющая система должна создавать и изменять инфраструктуру, а часть обязательных операций требует административных полномочий гипервизора.

**Рассмотренные варианты.**

- строить сложную ограниченную матрицу прав для самого управляющего контура;
- разделить управление между несколькими полу-доверенными сервисами;
- считать управляющий контур частью административной границы PVE.

**Принятое решение.**
Основной управляющий контур считается административно доверенным PVE.

**Почему.**

- его назначение уже включает изменение критичной инфраструктуры;
- искусственное дробление прав не устраняет последствия его полной компрометации;
- модель становится проще и проверяемее;
- менее доверенные системы можно ограничивать отдельно.

**Последствия и ограничения.**

- компрометация управляющего контура является серьёзным инцидентом уровня PVE;
- его собственные секреты и обновления требуют высокой защиты;
- прикладные гости не должны автоматически наследовать этот уровень доверия.

**Когда пересматривать.**
Если появится необходимость дать нескольким независимым управляющим контурам разные административные полномочия или существенно снизить доверие к текущему управляющему контуру.

### 1.2. Почему API и root SSH существуют одновременно

**Проблема.**
Основное управление удобно и воспроизводимо через API, но некоторые host-only операции требуют полномочий самого PVE root.

**Рассмотренные варианты.**

- выполнять всё через root SSH;
- отказаться от операций, недоступных API;
- использовать API для обычного управления и отдельный узкий root SSH для исключений.

**Принятое решение.**
API является основным каналом, root SSH используется только для явно определённых host-only операций.

**Почему.**

- инфраструктурное состояние остаётся декларативным;
- shell PVE не превращается в основной механизм развёртывания;
- исключения можно отдельно контролировать и проверять.

**Последствия и ограничения.**

- приходится поддерживать две независимые идентичности;
- root SSH остаётся мощным секретом и требует строгой проверки сервера.

**Когда пересматривать.**
Если PVE API сможет безопасно выполнять все необходимые операции без host-root исключений.

### 1.3. Почему права вынесены в единый `access.yaml`

**Проблема.**
Права были частично описаны в `guest.yaml`, `provision.yaml` и настройках отдельных подсистем. Это затрудняет ответ на простой вопрос: кто именно к чему имеет доступ.

**Рассмотренные варианты.**

- выдавать одинаковые доступы всем гостям;
- наследовать доступы из технического профиля;
- хранить права отдельно в каждом `guest.yaml`;
- хранить один проектный контракт субъектов, целей и действий.

**Принятое решение.**
Единым машинным источником требований доступа является `infrastructure/security/access.yaml`.

**Почему.**

- все права можно проверить одной машинной моделью;
- профиль и описание VM/LXC не расширяют доверие;
- разные виды доступа остаются независимыми;
- секреты и способы их хранения отделены от решения о праве;
- один субъект не получает новое полномочие только из-за настройки другой подсистемы.

**Последствия и ограничения.**

- технические настройки PVE, SSH, Git, Semaphore и OpenBao должны соответствовать этому контракту;
- старые `management` временно остаются только для совместимости resolver;
- полная автоматическая генерация всех производных настроек выполняется поэтапно.

**Когда пересматривать.**
Если появится другой единый механизм полномочий, который обеспечивает не меньшее разделение, проверяемость и возможность независимого отзыва.

## 2. Решения по SSH-доверию

### 2.1. Почему штатный Ansible использует короткоживущие сертификаты

**Проблема.**
Один постоянный административный ключ на всех гостях создаёт большую область последствий при утечке и усложняет ротацию.

**Рассмотренные варианты.**

- один постоянный ключ;
- отдельный постоянный ключ на каждый запускатель;
- короткоживущая идентичность, подписанная доверенным центром.

**Принятое решение.**
Штатный административный вход автоматизации использует короткоживущие SSH-сертификаты.

**Почему.**

- временный private key быстро теряет ценность;
- гостям достаточно доверять открытому CA;
- не нужно массово распространять новые постоянные public keys;
- компрометация одного задания не раскрывает постоянный CA key.

**Последствия и ограничения.**

- доступ зависит от работоспособности центра подписи;
- для первого входа до установки доверия нужен отдельный переходный механизм;
- время жизни сертификата должно оставаться коротким.

**Когда пересматривать.**
Если инфраструктура перейдёт на другой механизм краткоживущей машинной идентичности.

### 2.2. Почему client CA и host CA разделены

**Проблема.**
Сертификат пользователя отвечает на вопрос «кто имеет право войти», а сертификат сервера — «к какому серверу мы подключились».

**Рассмотренные варианты.**

- один CA для обоих типов;
- отказаться от сертификатов серверов;
- использовать два независимых центра.

**Принятое решение.**
Пользовательские и серверные SSH-сертификаты подписывают разные CA.

**Почему.**

- разные задачи доверия не смешиваются;
- ошибка политики одного CA не должна автоматически давать вторую возможность;
- ротацию и ограничения можно проводить независимо.

**Последствия и ограничения.**

- требуется хранить и резервировать два CA;
- конфигурация становится немного сложнее.

**Когда пересматривать.**
Если выбранная SSH-технология будет предоставлять равнозначное разделение ролей другим способом.

### 2.3. Почему PVE проверяет цель перед подписью host key

**Проблема.**
Право вызвать службу подписи само по себе не должно позволять получить доверенный сертификат для произвольного имени или адреса.

**Рассмотренные варианты.**

- доверять параметрам вызывающей стороны;
- проверять только формат ключа;
- подтверждать существование и идентичность объекта на доверенном PVE перед подписью.

**Принятое решение.**
PVE подтверждает цель и только после этого разрешает host-подпись.

**Почему.**

- PVE является источником истины о существовании объекта виртуализации;
- компрометация управляющего процесса не должна автоматически превращать произвольный ключ в доверенный host certificate;
- principal сертификата связывается с конкретным ожидаемым сервером.

**Последствия и ограничения.**

- для динамического адреса нужен доверенный способ получить фактический адрес;
- подпись зависит от доступности host-only проверки PVE.

**Когда пересматривать.**
Если появится более сильный независимый источник идентичности гостя.

### 2.4. Почему неожиданная смена host identity блокирует подключение

**Проблема.**
Автоматическое принятие нового SSH host key удобно после пересоздания, но также скрывает возможную подмену сервера.

**Рассмотренные варианты.**

- всегда автоматически принимать новый ключ;
- всегда требовать ручное изменение;
- блокировать неожиданную смену и разрешать обновление только после подтверждённого жизненного события.

**Принятое решение.**
Неожиданная смена server identity считается блокирующим событием.

**Почему.**

- безопасность важнее удобства автоматического продолжения;
- осознанное пересоздание можно отличить от неожиданной подмены;
- доверие не должно изменяться только потому, что соединение стало неудобно.

**Последствия и ограничения.**

- после законного пересоздания нужна явная процедура обновления доверия.

**Когда пересматривать.**
Если host CA полностью устранит необходимость хранить привязку к отдельному host key без ослабления проверки имени сервера.

### 2.5. Почему машинный private key остаётся в исходном госте

**Проблема.**
Для межмашинного SSH нужен устойчивый владелец идентичности, но распространение общего private key или служебного OpenBao AppRole по гостям расширяет область компрометации.

**Рассмотренные варианты.**

- один общий постоянный SSH-ключ для нескольких гостей;
- хранить private keys всех машин в 910;
- выдавать каждому гостю прямой AppRole OpenBao;
- хранить отдельный private key внутри исходного гостя и централизованно подписывать только его public key.

**Принятое решение.**
Каждый исходный гость хранит собственный private key локально. 910 получает только public key, а PVE-only механизм выпускает короткоживущий сертификат OpenBao.

**Почему.**

- компрометация одного гостя не раскрывает идентичности других;
- 910 и PVE не становятся постоянным хранилищем машинных private keys;
- гостю не требуется доступ к OpenBao;
- право входа можно отзывать отдельно от самого ключа через principals цели;
- сертификат ограничивает срок действия постоянной локальной пары.

**Последствия и ограничения.**

- исходный гость должен сохранять свой локальный ключ между перезапусками;
- обновление сертификатов зависит от доступности 910, PVE и OpenBao;
- целевые гости должны получать актуальный список разрешённых principals.

**Когда пересматривать.**
Если появится другой механизм машинной идентичности с не меньшим разделением секретов и централизованным отзывом.

## 3. Решения по OpenBao и секретам

### 3.1. Почему закрытые SSH CA остаются внутри OpenBao

**Проблема.**
Экспортируемый CA private key легко скопировать, после чего становится трудно определить, кто ещё может выпускать доверенные сертификаты.

**Рассмотренные варианты.**

- хранить CA key обычным файлом;
- передавать его управляющему контейнеру;
- хранить закрытый CA только внутри специализированного хранилища.

**Принятое решение.**
Закрытые SSH CA не экспортируются из OpenBao.

**Почему.**

- операции подписи отделены от владения CA key;
- выдаваемые полномочия можно ограничивать политиками;
- проще контролировать ротацию и резервирование.

**Последствия и ограничения.**

- потеря постоянного состояния OpenBao означает потерю CA;
- доступность подписывающего сервиса становится частью штатного управления.

**Когда пересматривать.**
Если будет выбран другой сервис машинной идентичности с сопоставимой защитой закрытого CA.

### 3.2. Почему unseal и служебный AppRole-доступ остаются на PVE

**Проблема.**
Если управляющий контейнер постоянно хранит и unseal key, и полномочия подписи, его компрометация снимает дополнительную границу защиты OpenBao.

**Рассмотренные варианты.**

- хранить всё внутри управляющего контейнера;
- вводить внешнюю KMS/HSM;
- использовать PVE как отдельную локальную доверенную границу.

**Принятое решение.**
Unseal key и постоянные служебные данные подписи остаются в области, доступной только PVE.

**Почему.**

- управляющий контейнер не может сам прочитать эти данные;
- PVE может проверить контекст операции до использования секрета;
- не требуется отдельная внешняя инфраструктура.

**Последствия и ограничения.**

- PVE становится частью критичного пути разблокировки и подписи;
- эти PVE-only данные требуют отдельного резервного копирования.

**Когда пересматривать.**
Если появится независимое безопасное хранилище ключей или аппаратный механизм автоматической разблокировки.

### 3.3. Почему постоянный root token не хранится

**Проблема.**
Root token делает бессмысленным большинство более узких политик OpenBao.

**Рассмотренные варианты.**

- хранить root token для удобства;
- использовать только root token;
- сохранять лишь ограниченные служебные доступы и выпускать root token только в исключительном восстановительном окне.

**Принятое решение.**
Постоянный root token отсутствует.

**Почему.**

- штатная работа идёт через минимально необходимые политики;
- утечка служебного credential не даёт полные права OpenBao;
- административное восстановление остаётся отдельной процедурой.

**Последствия и ограничения.**

- восстановление сложнее, чем использование сохранённого root token;
- потеря unseal key становится особенно критичной.

**Когда пересматривать.**
Только если появится другой безопасный механизм break-glass с не меньшим уровнем контроля.

## 4. Решения по Git-доступу

### 4.1. Почему Git credential отделён от административного SSH

**Проблема.**
Один SSH private key технически можно использовать для нескольких сервисов, но тогда компрометация одного назначения раскрывает все остальные.

**Рассмотренные варианты.**

- один общий SSH-key;
- личный ключ человека;
- отдельные credentials по назначению.

**Принятое решение.**
Git использует отдельную идентичность.

**Почему.**

- чтение репозитория не даёт административный shell;
- Git credential можно независимо отозвать;
- личные и машинные полномочия не смешиваются.

**Последствия и ограничения.**

- появляется больше отдельных credentials;
- для каждого нужен собственный жизненный цикл.

**Когда пересматривать.**
Если Git-провайдер перейдёт на другой механизм краткоживущего машинного доступа.

### 4.2. Почему право записи не входит в read-only capability

**Проблема.**
Системе часто нужно читать конфигурацию, но возможность менять источник требований существенно опаснее.

**Рассмотренные варианты.**

- всегда выдавать read/write;
- использовать личный write credential;
- разделить чтение и запись.

**Принятое решение.**
`project_repo_read` означает только чтение. Запись требует отдельного полномочия.

**Почему.**

- компрометация читающего гостя не должна позволять менять источник инфраструктурных требований;
- принцип минимальных полномочий проще проверять технически.

**Последствия и ограничения.**

- автоматизация, которой действительно нужна запись, потребует отдельного контракта.

**Когда пересматривать.**
Если изменится модель хранения проекта или запись станет неотъемлемой частью доверенной автоматизации.
