## 1. Решения по SSH-доверию

### 1.1. Почему infra-manager использует короткоживущие сертификаты

**Проблема.** Постоянный административный private key на всех гостях создаёт широкое долговременное полномочие.

**Рассмотренные варианты.** Один постоянный key; отдельные постоянные keys; короткоживущие сертификаты от общего CA.

**Принятое решение.** Штатный вход `infra-manager` выполняется по короткоживущему сертификату OpenBao SSH Client CA.

**Почему.** На гостях достаточно доверия к одному public CA; временный private key задания быстро теряет ценность; CA private key не покидает OpenBao.

**Последствия и ограничения.** Для выпуска нового сертификата нужен работающий OpenBao. Первоначальный ввод и полная потеря CA требуют независимого пути.

**Когда пересматривать.** Если появится более простой механизм краткоживущей машинной идентичности с теми же гарантиями.

### 1.2. Почему Client CA и Host CA разделены

**Проблема.** Право войти на сервер и подтверждение подлинности самого сервера — разные задачи.

**Рассмотренные варианты.** Один CA; только client CA; два независимых CA.

**Принятое решение.** Пользовательские и серверные SSH-сертификаты подписываются разными CA.

**Почему.** Ошибка или компрометация одного назначения не должна автоматически давать второе.

**Последствия и ограничения.** Нужно сохранять и проверять два CA.

**Когда пересматривать.** Если выбранный механизм доверия даст равнозначное разделение другим способом.

### 1.3. Почему guest-to-guest SSH проверяется OpenBao онлайн

**Проблема.** Если доступ `410 → 210/310` выражать public keys или разрешёнными principals на каждом сервере, любое изменение матрицы требует обновлять затронутые Linux-системы.

**Рассмотренные варианты.** Разносить public keys; разносить списки principals; выдавать общий сертификат; проверять конкретную цель централизованно в OpenBao.

**Принятое решение.** Ограниченный межмашинный SSH использует OpenBao SSH OTP или эквивалентную online authorization с проверкой конкретной цели.

**Почему.** Изменение права меняет централизованную policy, а не конфигурацию всех целей; постоянные guest private keys для этого доступа не нужны.

**Последствия и ограничения.** Новый SSH-сеанс зависит от доступности OpenBao; на Linux-целях один раз требуется общий helper/PAM-механизм.

**Когда пересматривать.** Если появится стандартный механизм SSH-сертификата, который безопасно ограничивает конкретные destination hosts без распределённой конфигурации.

## 2. Решения по OpenBao и секретам

### 2.1. Почему OpenBao хранит внутренние секреты централизованно

**Проблема.** Размещение PVE, Git и сервисных secrets в отдельных каталогах создаёт несколько независимых способов хранения, ротации и выдачи.

**Рассмотренные варианты.** Отдельные файлы на PVE; отдельные файлы в гостях; централизованный KV; внешнее отдельное хранилище.

**Принятое решение.** OpenBao KV v2 является основным рабочим хранилищем внутренних секретов проекта.

**Почему.** Policies, аудит выдачи, ротация и разграничение по субъектам сосредоточены в одном месте; секреты не нужно постоянно копировать в гости.

**Последствия и ограничения.** OpenBao становится критичной службой и его Raft-state требует особо надёжного резервирования.

**Когда пересматривать.** При переходе на отдельный внешний secret manager, KMS/HSM или другой сервис с более подходящими гарантиями.

### 2.2. Почему закрытые SSH CA остаются внутри OpenBao

**Проблема.** Экспортируемый CA private key трудно контролировать после копирования.

**Рассмотренные варианты.** Обычный файл; private key внутри 910; private key только в OpenBao.

**Принятое решение.** Закрытые SSH CA не экспортируются из OpenBao.

**Почему.** Операция подписи отделена от владения CA и ограничивается policy.

**Последствия и ограничения.** Потеря OpenBao state означает потерю прежней CA identity.

**Когда пересматривать.** Если будет выбран другой защищённый подписывающий сервис.

### 2.3. Почему постоянный root token не хранится

**Проблема.** Постоянный root token обходит все узкие policies.

**Рассмотренные варианты.** Хранить root token; работать только им; использовать ограниченные credentials и отдельное recovery-окно.

**Принятое решение.** Постоянный root token отсутствует.

**Почему.** Штатные операции должны выполняться с минимальными capabilities.

**Последствия и ограничения.** Аварийная настройка сложнее и зависит от PVE-only корня доверия.

**Когда пересматривать.** Только при появлении другого контролируемого break-glass механизма.

## 3. Решения по централизованной политике доступа

### 3.1. Почему access.yaml хранится в Git

**Проблема.** Если policy вручную живёт только в OpenBao, невозможно надёжно понять требуемое состояние и воспроизвести его после потери сервиса.

**Рассмотренные варианты.** Ручные policies OpenBao; права в каждом `guest.yaml`; единая матрица доступа в Git.

**Принятое решение.** Канонический источник межсистемных прав — `infrastructure/security/access.yaml`.

**Почему.** Изменения версионируются и проверяются вместе с проектом; одна связь не размазывается по манифестам двух систем.

**Последствия и ограничения.** Нужны схема, resolver, plan/apply и проверка расхождений с OpenBao.

**Когда пересматривать.** Если появится иной декларативный источник прав с такой же воспроизводимостью и проверяемостью.

### 3.2. Почему права не остаются флагами guest.yaml

**Проблема.** Поля вроде `management.ssh_identity` описывают только одну сторону связи и не отвечают, к каким именно целям разрешён доступ.

**Рассмотренные варианты.** Расширять `guest.yaml`; хранить ACL на целевых гостях; отдельная матрица.

**Принятое решение.** Межсистемный доступ вынесен из `guest.yaml` в `access.yaml`.

**Почему.** `guest.yaml` продолжает описывать сам объект VM/LXC, а политика доступа описывает связи между объектами.

**Последствия и ограничения.** Старые `management.*` поля требуют миграции схемы и манифестов.

**Когда пересматривать.** Если модель проекта станет настолько простой, что отдельные связи исчезнут как самостоятельная сущность.

## 4. Решения по восстановлению

### 4.1. Почему recovery SSH private key находится вне OpenBao

**Проблема.** После полной потери OpenBao новые SSH CA не доверяются существующими серверами.

**Рассмотренные варианты.** Только консоль PVE; хранить recovery key в OpenBao; независимый PVE-only key.

**Принятое решение.** Один recovery administrator private key хранится только в PVE-only области, а его public key устанавливается на управляемые Linux-гости.

**Почему.** Он позволяет установить новый trusted CA без зависимости от потерянного OpenBao.

**Последствия и ограничения.** Это мощный долгоживущий секрет, который нужно отдельно резервировать и никогда не использовать как автоматический fallback.

**Когда пересматривать.** При появлении независимого out-of-band механизма массового восстановления SSH-доверия.

### 4.2. Почему unseal и control credentials остаются PVE-only

**Проблема.** Секрет, нужный для открытия OpenBao, нельзя хранить только внутри самого OpenBao.

**Рассмотренные варианты.** Внутри 910; внутри OpenBao; внешний HSM/KMS; PVE-only.

**Принятое решение.** Минимальный корень управления OpenBao остаётся только на PVE.

**Почему.** Это устраняет циклическую зависимость восстановления без отдельного внешнего оборудования.

**Последствия и ограничения.** PVE становится частью критического recovery path.

**Когда пересматривать.** При появлении независимого HSM/KMS или другого безопасного auto-unseal.

## 5. Решения по Git-доступу

### 5.1. Почему рабочий Git credential хранится в OpenBao, а recovery-копия — на PVE

**Проблема.** Штатный Git credential должен выдаваться по policy, но после полной потери OpenBao проект всё равно нужно получить для восстановления.

**Рассмотренные варианты.** Только файл на PVE; только OpenBao; отдельный recovery credential; рабочий credential в OpenBao с PVE-only recovery-копией.

**Принятое решение.** Рабочее представление read-only Deploy Key хранится в OpenBao KV, а защищённая восстановительная копия той же пары — в `pve-only/recovery/`.

**Почему.** В штатной работе Git-доступ подчиняется OpenBao policy, а аварийное получение проекта не зависит от OpenBao.

**Последствия и ограничения.** При ротации должны согласованно обновляться GitHub registration, KV и recovery-копия.

**Когда пересматривать.** Если Git-провайдер даст краткоживущий credential, который можно безопасно выпускать из независимого recovery-контура.

### 5.2. Почему read и write разделены

**Проблема.** Чтение требований нужно многим системам, а изменение Git меняет сам источник требований.

**Рассмотренные варианты.** Общий read/write credential; личный write credential; отдельные права.

**Принятое решение.** `read` не включает запись. Write требует отдельного явно заданного полномочия и credential.

**Почему.** Компрометация читающего гостя не должна позволять менять инфраструктурный проект.

**Последствия и ограничения.** Автоматизации с записью потребуется отдельный жизненный цикл.

**Когда пересматривать.** При смене модели хранения исходного проекта.
