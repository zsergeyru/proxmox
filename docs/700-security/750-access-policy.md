## 1. Основной принцип

Права между системами не являются свойством одной VM или LXC. Они описывают связь между субъектом, ресурсом и разрешённым действием.

Поэтому межсистемные доступы не должны задаваться отдельными флагами в `guest.yaml`.

Проект разделяет три уровня:

~~~text
Git
→ требуемые правила доступа

OpenBao
→ секреты, машинная аутентификация и централизованная выдача доступа

целевая система
→ окончательная проверка того, что выданное полномочие действительно допустимо
~~~

OpenBao policy является производным состоянием. Ручная настройка policy не становится источником требований проекта.

## 2. Источник требуемого состояния

Канонический файл:

~~~text
infrastructure/security/access.yaml
~~~

Он хранится в Git и не содержит секретов.

Минимальная модель правила:

~~~yaml
schema_version: 1

grants:
  - subject: guest:410
    service: ssh
    targets:
      - guest:211
      - guest:311
    access: root

  - subject: guest:410
    service: proxmox
    resource: pool:managed
    access:
      - read
      - clone
      - create
      - configure
      - power

  - subject: guest:410
    service: git
    resource: project
    access: read
~~~

`subject` определяет техническую систему, которой выдаётся право. Ссылки вида `guest:<VMID>` должны разрешаться через гостевой контур проекта.

Файл задаёт только несекретные требования: кто, к чему и с каким уровнем доступа может обращаться.

## 3. SSH между гостями

Штатный административный вход `infra-manager → Linux-гость` остаётся сертификатным и описан отдельно в SSH-спецификации.

Для ограниченного межмашинного доступа обычных гостей используется централизованное решение OpenBao.

Требуемая модель:

~~~text
гость
→ аутентифицируется в OpenBao как собственная машинная идентичность
→ запрашивает доступ к конкретной цели
→ OpenBao сверяет правило из access.yaml
→ выдаёт одноразовый SSH-доступ только к разрешённой цели
~~~

Целевой механизм — SSH OTP OpenBao или эквивалентная онлайн-проверка, при которой разрешённая цель проверяется до выдачи одноразового доступа.

На Linux-цели один раз настраивается общий механизм проверки OpenBao. Список отдельных исходных гостей не должен переноситься в `authorized_keys` и не должен требовать обновления сервера при каждом изменении матрицы доступа.

Изменение `410 → 310` на `410 → 510` должно менять централизованную политику OpenBao, а не запускать Ansible на всех трёх серверах.

## 4. Доступ к Proxmox

OpenBao определяет, имеет ли субъект право получить соответствующий PVE credential.

Сам Proxmox остаётся последней границей полномочий:

~~~text
access.yaml
→ OpenBao разрешает получить credential
→ PVE ACL ограничивает фактические действия и ресурсы
~~~

Например, AI Control может получить отдельный credential, который Proxmox ограничивает областью `pool:managed`. Наличие такого права не означает, что сама VM AI Control должна находиться в этом pool.

Полномочия `infra-manager` и менее доверенных контуров должны использовать разные PVE-идентичности.

## 5. Git и секреты OpenBao KV

Рабочие внутренние секреты хранятся в OpenBao KV v2.

К ним относятся, в частности:

- рабочие PVE API credentials;
- рабочий GitHub credential только для чтения;
- пароли и API tokens внутренних сервисов;
- секреты конкретных гостей;
- ключи приложений, если им требуется постоянное секретное значение.

`access.yaml` определяет, какой субъект может получить конкретный класс секрета или credential.

Для Git право `read` не даёт права записи. Восстановительная копия GitHub read-only Deploy Key хранится независимо от OpenBao в PVE-only recovery-области.

## 6. Применение изменений

`infra-manager` должен строить производное состояние OpenBao из `access.yaml` и применять только изменившиеся правила.

Ожидаемая последовательность:

~~~text
access.yaml
→ проверка ссылок и допустимых полномочий
→ построение требуемых OpenBao policy/role
→ план изменений
→ применение только отличий
→ проверка фактических capabilities
~~~

Изменение одной связи не должно приводить к безусловному повторному развёртыванию всех гостей.

Настройка Linux-цели повторно требуется только при изменении самого общего механизма SSH-доверия, а не при обычном изменении разрешений между гостями.

## 7. Проверка

Проверка должна подтверждать:

- отсутствие секретов в `access.yaml`;
- существование всех указанных субъектов и целей;
- невозможность получить неразрешённый OpenBao credential;
- невозможность SSH-входа к цели, отсутствующей в разрешённом наборе;
- соответствие PVE ACL заявленной области;
- отсутствие скрытого права записи в Git при `access: read`;
- отсутствие ручных OpenBao policies, которые расширяют требуемые права проекта.

Фактическое состояние реализации находится в `780-implementation-status.md`.
