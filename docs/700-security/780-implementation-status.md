## 1. Полностью реализовано

### 1.1. Рабочие секреты OpenBao KV v2

Реализованы:

- отдельный KV v2 mount `infra-secrets`;
- PVE API secret по точному пути `pve/api/infra-manager`;
- read-only GitHub Deploy Key по точному пути `git/github/proxmox-read`;
- пароль, ключ защиты и API token Semaphore по пути `services/semaphore`;
- PVE-only AppRole `kv-reader` с чтением только этих трёх путей;
- PVE-only AppRole `kv-semaphore-writer` с `read/update` только `services/semaphore`;
- отзыв короткоживущих OpenBao token после каждой операции;
- атомарная материализация рабочих файлов в `/run/infra-manager/secrets/`;
- read-only подключение этой временной области в `infra-runtime`;
- обратная запись перевыпущенного API token Semaphore в OpenBao;
- проверка KV через `infra-manager-status --full`.

### 1.2. Постоянный PVE API-доступ

Реализованы:

- техническая идентичность `root@pam!infra-manager`;
- `privsep=0`;
- проверка TLS по PVE CA;
- штатное чтение API secret из временной материализации OpenBao;
- использование того же источника OpenTofu, проверками и lifecycle test.

### 1.3. Root SSH `infra-manager → PVE`

Реализованы:

- отдельная Ed25519-пара;
- регистрация только проектного ключа в root `authorized_keys` PVE;
- отдельный строгий `known_hosts`;
- использование только для host-only операций и PVE-only OpenBao helper.

Root SSH-ключ намеренно не перенесён в KV: он нужен до получения доступа к OpenBao. Аварийное восстановление самого управляющего контура выполняется локально на PVE и не требует отдельного удалённого recovery SSH key.

### 1.4. Git Deploy Key управляющего контура

Реализованы:

- отдельный GitHub Deploy Key без права записи;
- штатное рабочее значение в OpenBao KV;
- временная материализация для 910;
- использование Semaphore из временного файла;
- строгая проверка Git SSH.

### 1.5. OpenBao и SSH CA

Реализованы:

- постоянное Raft state;
- инициализация 1/1;
- PVE-only unseal key;
- удаление временной копии unseal key после разблокировки;
- отзыв initial root token;
- защищённый временный root token для сверки конфигурации;
- независимые `ssh-client-signer` и `ssh-host-signer`;
- AppRole `ssh-ca-config` и `ssh-signer`;
- публикация обоих открытых CA;
- роли подписи `infra-manager` и `managed-host`.

### 1.6. Пользовательские и серверные SSH-сертификаты

Реализованы:

- одноразовая Ed25519-пара для штатного входа Ansible;
- пользовательский сертификат с principal `root` на 15 минут;
- установка `TrustedUserCAKeys`;
- подпись реального host public key гостя;
- проверка VMID, имени и статического административного IPv4 на PVE;
- установка `HostCertificate` и проверка конфигурации sshd.

### 1.7. Единый `access.yaml`

Реализованы:

- единый файл `infrastructure/security/access.yaml`;
- машинная схема `infrastructure/schemas/access.schema.yaml`;
- правила для 910, 410, 311 и PVE-only операций OpenBao;
- запрет прямого PVE API и root SSH к PVE для 410;
- проверка существования гостевых субъектов;
- проверка допустимых сочетаний подсистемы, ресурса и прав;
- запрет путей хранения секретов в контракте;
- переходная сверка старых `management` с новым контрактом;
- отдельный тест `test-access-contract.py` и включение его в CI.

Из `access.yaml` уже автоматически выводится межмашинный SSH. Полное получение всех остальных производных PVE/OpenBao/Semaphore/Git настроек остаётся отдельной работой.

### 1.8. Централизованный межмашинный SSH

Реализованы:

- отдельная машинная Ed25519-пара у каждого исходного гостя;
- закрытый ключ не покидает исходный гость;
- отдельные OpenBao-роли `machine-<VMID>`;
- principal `guest-<VMID>` и срок сертификата 2 часа;
- выдача сертификата через PVE-only signer без AppRole в гостях;
- `AuthorizedPrincipalsFile` на целевых Linux-гостях;
- построение разрешённых principals из `access.yaml`;
- проверка серверов через `ssh-host-signer` и `@cert-authority`;
- автоматическое удаление лишних `machine-*` ролей;
- периодическое обновление сертификатов;
- отдельное задание Semaphore `Sync Machine SSH`;
- проверка разрешённых и запрещённых связей.

### 1.9. Аварийный контур 910

Реализованы:

- независимый PVE-only helper `/usr/local/sbin/infra-manager-recovery`;
- аварийная PVE-only копия read-only GitHub Deploy Key;
- восстановление bootstrap/access Git-копий без работающего 910;
- строгий recovery-preflight до изменения существующего или пересоздания 910;
- preflight-проверка аварийного Git key, `unseal.key`, Raft state и Semaphore DB;
- полный check восстановленных OpenBao AppRole-данных после инициализации;
- восстановление потерянных `ssh-access.json` и `kv-access.json` из сохранного OpenBao через временный root token;
- обязательность OpenTofu state при наличии объектов в `pool managed`;
- допустимость отсутствия OpenTofu state на действительно пустой новой установке;
- запрет автоматической подмены recovery пустой установкой;
- автоматическая подготовка recovery Git-copy при настройке 910;
- полный recovery-check после `Initialize OpenBao 910`;
- инструкция восстановления существующего и уничтоженного 910.

Отдельный удалённый recovery SSH key не создаётся. Аварийная точка входа — локальный root физического PVE.

## 2. Реализовано частично

### 2.1. Переходные файловые копии секретов

До выполнения общего пункта миграции старой схемы сохраняются:

- `access/pve-api/pve-api.env`;
- `access/github/github_proxmox_repo_ed25519`;
- постоянные старые файлы Semaphore в `state/secrets`.

Они используются только как вход первой миграции и запас совместимости при текущем переходе.

После успешной материализации OpenBao рабочий код использует `/run/infra-manager/secrets/`.

Удаление этих старых каталогов и окончательное изменение bootstrap-контракта относится к отдельному этапу миграции.

### 2.2. Переходный постоянный Ansible-ключ

Постоянная пара `guest_ed25519` пока используется для первого входа в новый гость и для части первоначального контура.

Штатное управление уже использует краткоживущий пользовательский сертификат.

### 2.3. Доверие клиента к SSH host CA

Host CA создаётся, выпускает и устанавливает серверные сертификаты, но клиентская сторона `deploy-guest` пока продолжает использовать строгий `known_hosts`.

### 2.4. DHCP и host certificates

Контракт гостей поддерживает DHCP, но текущая проверка цели host certificate подтверждает адрес по статической конфигурации PVE.

### 2.5. Границы первой версии межмашинного SSH

Текущая автоматическая синхронизация рассчитана на:

- один PVE-узел;
- одну административную IPv4-подсеть /16;
- поддерживаемые Linux-гости с `provision.yaml`;
- работающие гости во время обновления сертификата и principals.

Расширение на несколько узлов, другие маски сети и недоступные во время синхронизации цели требует отдельной реализации.

## 3. Ещё не реализовано

### 3.1. Полная миграция старой схемы

`management.*`, переходные файловые secret и старые каталоги credentials ещё не удалены.

### 3.2. Git credential обычных гостей

Требование чтения уже находится в `access.yaml`, но выдача управляемого Git credential обычному гостю ещё не реализована. Старое `management.project_repo_read` пока остаётся только совместимым входом resolver.

## 4. Известные технические долги

### 4.1. Переходные источники первоначальной миграции

Ansible пока умеет подготовить `/run/infra-manager/secrets/` из старых файлов, если OpenBao ещё не инициализирован или PVE-only KV-доступ ещё отсутствует.

После завершения общей миграции этот fallback должен быть удалён.
