## 1. Полностью реализовано

### 1.1. Постоянный PVE API-доступ

Реализованы:

- `root@pam!infra-manager`;
- `privsep=0`;
- PVE-owned постоянный API secret;
- проверка TLS по PVE CA;
- доступ `infra-manager` к credential через постоянную read-only область.

### 1.2. Root SSH `infra-manager → PVE`

Реализованы:

- отдельная Ed25519-пара;
- регистрация только project-managed ключа в root `authorized_keys` PVE;
- отдельный строгий `known_hosts`;
- использование root SSH для host-only операций;
- удаление активной авторизации при удалении управляющего контура.

### 1.3. Git Deploy Key управляющего контура

Реализованы:

- отдельный GitHub Deploy Key;
- режим без права записи;
- исходная восстановительная копия на PVE;
- постоянная рабочая копия в PVE-owned области доступа;
- read-only представление ключа внутри `infra-manager`.

### 1.4. OpenBao

Реализованы:

- постоянное Raft state;
- инициализация 1/1;
- PVE-only unseal key;
- удаление временной копии unseal key после разблокировки;
- отзыв initial root token;
- защищённый выпуск и отзыв временного root token для восстановления SSH-настройки;
- отдельные `ssh-client-signer` и `ssh-host-signer`;
- отдельные AppRole `ssh-ca-config` и `ssh-signer`;
- публикация обоих открытых CA;
- роли `infra-manager` и `managed-host`.

### 1.5. Пользовательские SSH-сертификаты Ansible

Реализованы:

- одноразовая Ed25519-пара на время задания;
- подпись только public key через PVE/OpenBao;
- principal `root`;
- сертификат на 15 минут;
- установка `TrustedUserCAKeys` в управляемые Linux-гости;
- блокировка автоматического fallback, если гость уже доверяет CA, но вход по сертификату не прошёл.

### 1.6. Сертификаты SSH-серверов

Реализованы:

- чтение реального Ed25519 host public key гостя;
- проверка VMID, имени и статического административного IPv4 на PVE;
- подпись ролью `managed-host`;
- principals из имени и IP;
- установка `HostCertificate`;
- проверка `sshd -t` и эффективной конфигурации.

## 2. Реализовано частично

### 2.1. Переходный постоянный Ansible-ключ

Постоянная пара `guest_ed25519` пока сохраняется.

Она используется:

- для первого входа в новый гость до установки пользовательского CA;
- для базовой стадии первоначального создания управляющего контейнера;
- для восстановления собственного управляемого `authorized_keys` управляющего контейнера.

Целевая штатная модель полного управления гостями уже использует краткоживущий пользовательский сертификат.

### 2.2. Доверие клиента к SSH host CA

Host CA уже:

- создаётся;
- публикуется;
- выпускает сертификаты;
- устанавливает сертификаты серверу.

Но клиентская сторона `deploy-guest` пока продолжает использовать строгий `known_hosts`.

Открытый `ssh-host-ca.pub` ещё не заменил обычную клиентскую проверку host key через `@cert-authority` или эквивалентную конфигурацию.

То есть серверные сертификаты уже существуют, но полный переход клиента на host CA ещё не завершён.

### 2.3. DHCP и host certificates

Нормативный контракт гостей поддерживает DHCP.

Низкоуровневое получение фактических интерфейсов через PVE также предусмотрено в коде.

Однако текущая проверка цели перед host-подписью подтверждает IP по статической конфигурации PVE.

Поэтому полный безопасный выпуск host certificate для DHCP-гостя требует связать подпись с доверенно полученным фактическим адресом после запуска.

## 3. Ещё не реализовано

### 3.1. `management.ssh_identity`

Сейчас:

- поле поддерживается схемами;
- resolver переносит его в итоговое состояние;
- оно присутствует в манифестах отдельных гостей.

Но рабочий механизм выдачи собственной исходящей SSH-пары гостю, регистрации её открытой части на разрешённых целях и управляемого отзыва в новом `infra-manager` ещё не реализован.

### 3.2. `management.project_repo_read`

Сейчас:

- поле поддерживается схемами;
- resolver переносит его в итоговое состояние;
- оно присутствует в манифестах отдельных гостей.

Но новый рабочий механизм материализации управляемого read-only Git credential в обычном госте ещё не реализован.

Нормативные требования к нему уже определены в `730-git-access.md`.

## 4. Известные технические долги

### 4.1. Старая команда проверки PVE lifecycle

Сценарий:

```text
scripts/infra-manager/commands/pve-lifecycle-test.sh
```

всё ещё содержит старый путь к PVE API credential.

Он не является источником текущего security-контракта и должен быть приведён к PVE-owned access layout перед использованием как достоверная проверка.

### 4.2. Соседняя документация

Часть старых подробных описаний OpenBao и SSH всё ещё может встречаться в эксплуатационной документации и паспорте управляющего гостя.

Основными нормативными источниками теперь являются:

- `710-pve-access.md`;
- `720-ssh-access.md`;
- `730-git-access.md`;
- `740-openbao.md`.

При последующей переработке соседних документов подробности должны заменяться ссылками на эти спецификации.
