## 1. Полностью реализовано

### 1.1. Текущий PVE API-доступ infra-manager

Реализованы `root@pam!infra-manager`, `privsep=0`, проверка TLS по PVE CA и PVE-owned постоянный API secret.

Сейчас этот secret доступен 910 из отдельной read-only области PVE. Перенос рабочего API secret в OpenBao KV относится к целевой модели и ещё не выполнен.

### 1.2. Root SSH infra-manager → PVE

Реализованы отдельная Ed25519-пара, project-managed запись в `authorized_keys` PVE, строгий `known_hosts` и применение root SSH только для host-only операций.

### 1.3. Текущий Git Deploy Key

Реализованы отдельный GitHub Deploy Key без права записи, восстановительная копия на PVE и рабочая PVE-owned копия, доступная 910 только для чтения.

Перенос рабочего представления в OpenBao KV и новая recovery-структура ещё не выполнены.

### 1.4. Базовый OpenBao

Реализованы:

- постоянное Raft state;
- инициализация 1/1;
- PVE-only unseal key;
- отзыв initial root token;
- временный root token для восстановления SSH-настройки;
- отдельные `ssh-client-signer` и `ssh-host-signer`;
- AppRole `ssh-ca-config` и `ssh-signer`;
- публикация открытых ключей обоих CA;
- роли `infra-manager` и `managed-host`.

### 1.5. Пользовательские SSH-сертификаты Ansible

Реализованы одноразовая Ed25519-пара задания, подпись public key через PVE/OpenBao, короткоживущий root-сертификат, установка `TrustedUserCAKeys` и запрет автоматического fallback после перехода гостя на CA.

### 1.6. Сертификаты SSH-серверов

Реализованы чтение реального host public key, проверка VMID/имени/статического IPv4 на PVE, подпись OpenBao, установка `HostCertificate` и проверка `sshd`.

## 2. Реализовано частично

### 2.1. Постоянный Ansible-ключ

Постоянная пара `guest_ed25519` пока остаётся для первого входа и отдельных bootstrap/recovery сценариев.

Целевая модель должна отделить первоначальный ввод от постоянного recovery administrator key, который хранится только в PVE-only области и не используется штатными заданиями.

### 2.2. Доверие клиента к SSH Host CA

Host CA уже выпускает и устанавливает сертификаты серверов, но `deploy-guest` пока продолжает использовать обычный строгий `known_hosts` вместо полного доверия через host CA.

### 2.3. DHCP и host certificates

Гостевой контракт допускает DHCP, но текущая проверка цели перед host-подписью опирается на статический адрес. Для DHCP ещё нужен доверенный способ подтвердить фактический адрес после запуска.

## 3. Целевая централизованная модель ещё не реализована

### 3.1. OpenBao KV v2 как основное внутреннее хранилище секретов

Рабочие PVE API credentials, Git credential, пароли и другие внутренние secrets пока не перенесены в единый KV-контур.

### 3.2. Защищённый сетевой доступ к OpenBao

Сейчас OpenBao рассчитан на локальный доступ управляющего контура. Для guest-to-guest online authorization ещё не настроена защищённая TLS-точка доступа в административной сети.

### 3.3. Отдельная машинная аутентификация гостей

Нет общего механизма индивидуальной OpenBao identity для каждого гостя, которому нужен прямой запрос секрета или SSH-доступа.

### 3.4. Централизованный guest-to-guest SSH

SSH OTP или эквивалентная online authorization OpenBao, ограничивающая конкретные целевые адреса, ещё не реализована.

### 3.5. `infrastructure/security/access.yaml`

Каноническая матрица доступа, её схема, resolver, plan/apply и проверка расхождений OpenBao policy ещё не реализованы в коде.

### 3.6. Recovery administrator key

Отдельный PVE-only recovery private key с управляемым public key на всех Linux-гостях ещё не создан как самостоятельный постоянный контур.

### 3.7. Новая раскладка credentials

Ещё не выполнены:

- перенос рабочего Git credential в OpenBao KV;
- сохранение recovery-копии Git credential в `pve-only/recovery/`;
- перенос рабочего PVE API secret в OpenBao KV;
- сокращение старых `access/github`, `access/pve-api`, `state/ansible` и `state/secrets` после завершения миграции.

## 4. Переход от старых management-флагов

Текущая схема `guest.yaml` и resolver всё ещё поддерживает:

~~~text
management.ssh_identity
management.project_repo_read
~~~

Они присутствуют в отдельных гостевых манифестах, но их старые runtime handlers в новом `infra-manager` не реализованы.

В целевой архитектуре эти флаги удаляются из гостевого контракта.

Вместо них:

- SSH-связи задаются в `access.yaml`;
- Git read задаётся в `access.yaml`;
- OpenBao создаёт производные policies и выдаёт соответствующий доступ.

До изменения схемы и манифестов код и нормативная документация временно расходятся. Это намеренный переход, а не скрытая поддержка двух архитектур.

## 5. Известные технические долги

### 5.1. Старая команда проверки PVE lifecycle

`scripts/infra-manager/commands/pve-lifecycle-test.sh` всё ещё использует старый путь к PVE API credential и не должен считаться источником нового security-контракта.

### 5.2. Соседние машинные контракты

`infrastructure/guests/910-infra-manager/provision.yaml`, гостевая JSON Schema и манифесты 311/410 пока описывают старые пути и `management`-флаги. Их нужно менять вместе с реализацией, а не подменять документацией.
