# Состояние реализации безопасности

**Тип:** состояние реализации  
**Статус:** действующий  
**Назначение:** показать, какие части нормативной модели безопасности уже реализованы, а какие ещё находятся в переходном состоянии.

Этот файл не задаёт новые требования. Нормативные правила находятся в `710`, `720`, `730`, `740` и `750`.

## 1. Полностью реализовано

### 1.1. Рабочие секреты OpenBao KV v2

Реализовано постоянное хранение рабочих секретов PVE, Git и Semaphore в OpenBao KV v2.

Рабочие значения материализуются во временную область 910, а перевыпущенный API token Semaphore сохраняется обратно в OpenBao.

Конкретное размещение на 910 описано в [`data-and-access.md`](../../infrastructure/guests/910-infra-manager/docs/data-and-access.md), нормативные ограничения — в [`740-openbao.md`](740-openbao.md).

### 1.2. Постоянный PVE API-доступ

Постоянная идентичность `root@pam!infra-manager` создаётся и используется управляющим контуром.

Рабочий secret хранится через OpenBao, API используется с проверкой TLS, а проверка подтверждает ожидаемый административный контракт.

### 1.3. Root SSH infra-manager → PVE

Отдельная SSH-идентичность для предусмотренных операций физического PVE существует независимо от Git и гостевого SSH.

Проверка сервера выполняется строго; этот канал используется только там, где требуется хостовая операция PVE.

### 1.4. Git Deploy Key управляющего контура

Для проектного репозитория используется отдельный read-only Deploy Key.

Рабочее значение хранится через OpenBao, а PVE имеет отдельную аварийную копию для восстановления управляющего контура.

### 1.5. OpenBao и SSH CA

OpenBao развёрнут на 910, использует постоянное Raft-состояние и хранит закрытые ключи двух независимых SSH CA.

Роли client CA и host CA создаются повторяемо, а закрытые ключи не экспортируются как штатные постоянные файлы.

### 1.6. Пользовательские и серверные SSH-сертификаты

Реализованы:

- выпуск короткоживущего пользовательского сертификата для административного Ansible;
- выпуск host certificate на основе реального SSH host key гостя;
- установка host certificate на управляемый Linux-гость;
- проверка соответствия цели перед подписью.

### 1.7. Единый access.yaml

`infrastructure/security/access.yaml` используется как единственный машинный источник требований доступа.

Схемы гостей больше не должны дублировать эти права отдельными полями.

### 1.8. Проверка подлинности цели межмашинного SSH

Общая часть проверки SSH-сервера через host CA реализована и сохраняется в целевой OTP-схеме.

### 1.9. Аварийный контур 910

Реализован независимый от работающего 910 путь восстановления с PVE.

Он проверяет обязательное состояние до опасных изменений, позволяет вернуть проектный Git-доступ и используется совместно с инструкцией восстановления 910.

Конкретные команды и пути находятся в [`830-recovery.md`](../800-operations/830-recovery.md) и локальной документации 910.

### 1.10. Межмашинный SSH через OpenBao OTP

1 октября 2026 года на действующих гостях выполнено задание Semaphore `Sync SSH Access` (успешный запуск № 44). Действующий маршрут `910 → 410` проверен реальным входом `infra-openbao-ssh`; полный `infra-manager-status --full --quiet` прошёл.

Из `access.yaml` строятся отдельные OTP-роли и машинные AppRole. OTP выдаётся через TLS OpenBao, а цель проверяет его через отдельный PAM-контур; клиент доверяет host CA только для разрешённого IP. Машинный token ограничен пятью минутами. TLS CA имеет `keyCertSign`; прежний сертификат CA был перевыпущен с тем же закрытым ключом.

После проверки удалены старые гостевые машинные ключи, сертификаты и principals, таймер на 910, роли `machine-*` в OpenBao и задание `Sync Machine SSH` в Semaphore. Успешный OTP-вход повторно проверен после удаления. Контракт сейчас разрешает только `910 → 410`; гость 311 исключён из правил доступа по текущему решению.

Реализация OpenBao OTP/TLS перенесена в `main`; отдельная ветка `feature/openbao-otp-tls` больше не требуется для штатных заданий и проверки статуса.

## 2. Реализовано частично

### 2.1. Переходный постоянный Ansible-ключ

Постоянная пара `guest_ed25519` пока используется для первого входа в новый гость и части первоначального контура.

Штатное управление уже использует краткоживущий пользовательский сертификат.

После появления надёжного первого входа без постоянного ключа эта переходная идентичность должна быть удалена.

### 2.2. Доверие клиента к SSH host CA

Host CA создаётся, выпускает и устанавливает серверные сертификаты, но часть клиентского пути `deploy-guest` пока продолжает использовать строгий `known_hosts`.

Целевое состояние — единая проверка управляемых Linux-гостей через host CA без ослабления проверки подлинности.

### 2.3. DHCP и host certificates

Контракт гостей поддерживает DHCP, но текущий путь проверки цели host certificate ещё опирается на адрес, известный из конфигурации PVE.

Для полностью динамического адреса нужно надёжно получать и подтверждать фактический административный адрес цели.
