## 1. Разделение SSH-идентичностей

Проект использует несколько независимых SSH-контуров.

Они не должны использовать одну и ту же закрытую пару:

| Контур | Назначение |
|---|---|
| временный сертификат Ansible | штатный вход управляющей среды в Linux-гость |
| SSH host certificate | подтверждение подлинности самого Linux-гостя |
| постоянный root SSH к PVE | узкие операции на физическом PVE |
| Git SSH | доступ к репозиторию проекта |
| правило `access.yaml` для SSH identity | исходящая SSH-идентичность конкретного гостя |
| личный SSH человека | интерактивный человеческий доступ |

Получение одной идентичности не означает получение остальных.

## 2. Штатный вход Ansible в Linux-гости

### 2.1. Центр доступа

Штатный административный вход Ansible основан на пользовательских SSH-сертификатах OpenSSH.

OpenBao содержит отдельный центр:

```text
ssh-client-signer
```

Управляемый Linux-гость доверяет только его открытому ключу:

```text
/etc/ssh/trusted-user-ca-keys.pem
```

и подключает его через:

```text
TrustedUserCAKeys /etc/ssh/trusted-user-ca-keys.pem
```

Закрытый ключ центра гостю и управляющей среде не выдаётся.

### 2.2. Временная идентичность задания

Для полного запуска Ansible создаётся новая временная пара Ed25519.

Правило:

```text
временный private key
→ остаётся только в каталоге текущего задания

public key
→ PVE-only механизм подписи

OpenBao
→ сертификат пользователя

сертификат + временный private key
→ SSH root
```

Сертификат:

- разрешает principal `root`;
- действует 15 минут;
- относится только к пользовательскому входу;
- не даёт права подписывать другие ключи.

После задания временный закрытый ключ и сертификат удаляются.

### 2.3. Ошибка входа

Если гость уже доверяет `ssh-client-signer`, неуспешный вход по корректно выпущенному временному сертификату считается ошибкой безопасности или состояния.

Автоматически переходить в этом случае на постоянный запасной ключ запрещено.

## 3. Подлинность SSH-сервера гостя

### 3.1. Отдельный центр серверов

Подлинность управляемого SSH-сервера подтверждает отдельный центр:

```text
ssh-host-signer
```

Он не используется для пользовательских сертификатов.

### 3.2. Что подписывается

Подписывается реальный Ed25519 host public key работающего Linux-гостя.

Новый произвольный host key только ради сертификата не создаётся.

До подписи PVE-only механизм должен подтвердить, что запрос относится к ожидаемому объекту.

Для подписи проверяются:

- VMID;
- точное имя VM/LXC;
- административный IPv4;
- существование объекта в PVE;
- соответствие фактических параметров заявленным.

Для статического адреса PVE должен подтверждать его своей конфигурацией.

Для DHCP фактический адрес должен быть получен доверенным способом после запуска; нельзя подписывать адрес только потому, что его сообщил сам запрашивающий гость.

### 3.3. Сертификат сервера

Сертификат выдаётся через роль:

```text
managed-host
```

В principals входят:

- точное имя гостя;
- его подтверждённый административный IPv4.

Срок серверного сертификата — 720 часов.

Ansible устанавливает сертификат рядом с исходным host key и включает его через:

```text
HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
```

Конфигурация SSH должна пройти `sshd -t` и проверку эффективных параметров.

### 3.4. Проверка клиентом

До полного перехода на доверие к host CA клиент обязан использовать строгий `known_hosts`.

Неожиданная смена обычного host key:

```text
не принимать автоматически
→ заблокировать подключение
→ выяснить причину
```

Открытый ключ `ssh-host-signer` публикуется управляющему контуру отдельно. Переход клиента на проверку через host CA должен сохранять ту же строгую связь имени/адреса с ожидаемым объектом.

Текущее состояние этого перехода указано в [`780-implementation-status.md`](780-implementation-status.md).

## 4. `authorized_keys` и переходный постоянный ключ

### 4.1. Чужие пользовательские ключи

Проект не должен удалять личные или сторонние ключи из `authorized_keys` только потому, что они неизвестны автоматизации.

Полный контроль над всем файлом допускается только если это явно принято для конкретной системы.

Обычно автоматизация управляет только собственным отмеченным блоком.

### 4.2. Переходный постоянный Ansible-ключ

Пока новый гость ещё не доверяет пользовательскому SSH CA, разрешён переходный постоянный ключ `infra-manager`.

Он нужен только для:

- первого входа в новый Linux-гость до установки `TrustedUserCAKeys`;
- базовой стадии первоначального создания управляющего контейнера;
- восстановления собственного управляемого блока доступа управляющего контейнера.

После появления доверия к SSH CA штатный вход должен выполняться по временным сертификатам.

Этот ключ не является целевой общей системой распространения ключей между гостями.

Старый глобальный реестр management public keys и массовый `sync-management-keys` не являются частью текущей архитектуры.

## 5. SSH к PVE

Root SSH `infra-manager → PVE` является отдельным контуром.

Он использует:

- отдельный постоянный закрытый ключ;
- отдельный `known_hosts`;
- `StrictHostKeyChecking=yes`;
- `BatchMode=yes`;
- `IdentitiesOnly=yes`.

Этот ключ нельзя переиспользовать для входа в Linux-гости или для Git.

Полный контракт полномочий PVE находится в [`710-pve-access.md`](710-pve-access.md).

## 6. Исходящая SSH-идентичность гостя

### 6.1. Назначение

Требование собственной исходящей SSH-идентичности задаётся в `access.yaml` правилом вида:

```yaml
subject: guest:<VMID>
service: ssh
resource: identity
targets:
  - self
access:
  - issue
```

Старое `management.ssh_identity` временно сохраняется только как совместимый вход действующего resolver и должно иметь эквивалентное правило в `access.yaml`.

Такое правило означает, что конкретному гостю нужна **собственная исходящая SSH-идентичность** для разрешённых связей с другими системами.

Она не является:

- ключом Ansible для входа в этот гость;
- root SSH-ключом PVE;
- Git-ключом;
- общей идентичностью всех гостей.

### 6.2. Требования к идентичности

Для каждого гостя с таким правилом должна существовать отдельная управляемая пара.

Закрытая часть:

- принадлежит только этому гостю;
- не публикуется;
- не хранится в Git;
- не должна копироваться в PVE или другие гости как обычный способ распространения.

Открытая часть может быть зарегистрирована только на тех целях, где этому гостю явно разрешён вход.

Наличие правила выдачи identity само по себе не определяет список целей и не даёт доступ ко всем управляемым гостям. Цели подключения задаются отдельными правилами `access.yaml`.

### 6.3. Выдача и отзыв

Выдача исходящей идентичности должна быть повторяемой и проверяемой.

Удаление соответствующего правила из `access.yaml` должно приводить к отзыву только управляемых регистраций этой идентичности и, если политика конкретного гостя не требует сохранения, к удалению его управляемой закрытой пары.

Пользовательские ключи и другие независимые SSH-контуры при этом не затрагиваются.

## 7. Смена, потеря и отзыв

### 7.1. Временные сертификаты

Временные пользовательские сертификаты не восстанавливаются и не продлеваются. Для следующей операции выпускается новая временная идентичность.

### 7.2. Сертификат сервера

Новый host certificate может быть выпущен для того же подтверждённого host key после истечения срока.

Если изменился сам host key, это должно рассматриваться как смена идентичности сервера и проходить отдельную проверку.

### 7.3. Постоянные закрытые ключи

Потерянный постоянный ключ нельзя тихо заменить новым под прежней идентичностью.

Новая пара требует явной повторной регистрации открытой части и удаления старых разрешений.

### 7.4. Отзыв центра доверия

Смена SSH CA затрагивает все системы, которые доверяют его открытому ключу.

Поэтому закрытые ключи CA являются критичным постоянным состоянием OpenBao и не должны ротироваться как обычный временный ключ.

## 8. Проверка контракта

Проверка SSH должна подтверждать:

- пользовательский CA установлен в госте;
- SSH действительно принимает сертификат с ожидаемым principal;
- сертификат сервера соответствует реальному host key;
- SSH-сервер использует `HostCertificate`;
- клиент не принимает неожиданно изменившийся host key;
- root SSH PVE использует только свою идентичность;
- Git SSH не использует административный ключ;
- дополнительные исходящие SSH-идентичности не появляются у гостя без явного правила `access.yaml`.
