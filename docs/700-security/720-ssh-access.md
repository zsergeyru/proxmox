## 1. Разделение SSH-идентичностей

Проект использует несколько независимых SSH-контуров.

Они не должны использовать одну и ту же машинную идентичность или общий секрет:

| Контур | Назначение |
|---|---|
| временный сертификат Ansible | штатный вход управляющей среды в Linux-гость |
| SSH host certificate | подтверждение подлинности самого Linux-гостя |
| постоянный root SSH к PVE | узкие операции на физическом PVE |
| Git SSH | доступ к репозиторию проекта |
| OpenBao SSH OTP гостя | одноразовый исходящий SSH конкретного гостя к разрешённым Linux-целям |
| личный SSH человека | интерактивный человеческий доступ |

Получение одной идентичности не означает получение остальных.

## 2. Штатный вход Ansible в Linux-гости

### 2.1. Центр доступа

Штатный административный вход Ansible основан на пользовательских SSH-сертификатах OpenSSH.

OpenBao содержит отдельный центр:

```text
ssh-client-signer
```

Управляемый Linux-гость доверяет только его открытому ключу:

```text
/etc/ssh/trusted-user-ca-keys.pem
```

и подключает его через:

```text
TrustedUserCAKeys /etc/ssh/trusted-user-ca-keys.pem
```

Закрытый ключ центра гостю и управляющей среде не выдаётся.

### 2.2. Временная идентичность задания

Для полного запуска Ansible создаётся новая временная пара Ed25519.

Правило:

```text
временный private key
→ остаётся только в каталоге текущего задания

public key
→ PVE-only механизм подписи

OpenBao
→ сертификат пользователя

сертификат + временный private key
→ SSH root
```

Сертификат:

- разрешает principal `root`;
- действует 15 минут;
- относится только к пользовательскому входу;
- не даёт права подписывать другие ключи.

После задания временный закрытый ключ и сертификат удаляются.

### 2.3. Ошибка входа

Если гость уже доверяет `ssh-client-signer`, неуспешный вход по корректно выпущенному временному сертификату считается ошибкой безопасности или состояния.

Автоматически переходить в этом случае на постоянный запасной ключ запрещено.

## 3. Подлинность SSH-сервера гостя

### 3.1. Отдельный центр серверов

Подлинность управляемого SSH-сервера подтверждает отдельный центр:

```text
ssh-host-signer
```

Он не используется для пользовательских сертификатов.

### 3.2. Что подписывается

Подписывается реальный Ed25519 host public key работающего Linux-гостя.

Новый произвольный host key только ради сертификата не создаётся.

До подписи PVE-only механизм должен подтвердить, что запрос относится к ожидаемому объекту.

Для подписи проверяются:

- VMID;
- точное имя VM/LXC;
- административный IPv4;
- существование объекта в PVE;
- соответствие фактических параметров заявленным.

Для статического адреса PVE должен подтверждать его своей конфигурацией.

Для DHCP фактический адрес должен быть получен доверенным способом после запуска; нельзя подписывать адрес только потому, что его сообщил сам запрашивающий гость.

### 3.3. Сертификат сервера

Сертификат выдаётся через роль:

```text
managed-host
```

В principals входят:

- точное имя гостя;
- его подтверждённый административный IPv4.

Срок серверного сертификата — 720 часов.

Ansible устанавливает сертификат рядом с исходным host key и включает его через:

```text
HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
```

Конфигурация SSH должна пройти `sshd -t` и проверку эффективных параметров.

### 3.4. Проверка клиентом

До полного перехода на доверие к host CA клиент обязан использовать строгий `known_hosts`.

Неожиданная смена обычного host key:

```text
не принимать автоматически
→ заблокировать подключение
→ выяснить причину
```

Открытый ключ `ssh-host-signer` публикуется управляющему контуру отдельно.

Штатный Ansible пока может использовать свой строгий `known_hosts`. Межмашинный SSH использует host CA: исходный гость доверяет только серверным сертификатам `ssh-host-signer` в административной сети и сохраняет `StrictHostKeyChecking=yes`.

Текущее состояние этого перехода указано в [`780-implementation-status.md`](780-implementation-status.md).

## 4. `authorized_keys` и переходный постоянный ключ

### 4.1. Чужие пользовательские ключи

Проект не должен удалять личные или сторонние ключи из `authorized_keys` только потому, что они неизвестны автоматизации.

Полный контроль над всем файлом допускается только если это явно принято для конкретной системы.

Обычно автоматизация управляет только собственным отмеченным блоком.

### 4.2. Переходный постоянный Ansible-ключ

Пока новый гость ещё не доверяет пользовательскому SSH CA, разрешён переходный постоянный ключ `infra-manager`.

Он нужен только для:

- первого входа в новый Linux-гость до установки `TrustedUserCAKeys`;
- базовой стадии первоначального создания управляющего контейнера;
- восстановления собственного управляемого блока доступа управляющего контейнера.

После появления доверия к SSH CA штатный вход должен выполняться по временным сертификатам.

Этот ключ не является целевой общей системой распространения ключей между гостями.

Старый глобальный реестр management public keys и массовый `sync-management-keys` не являются частью текущей архитектуры.

## 5. SSH к PVE

Root SSH `infra-manager → PVE` является отдельным контуром.

Он использует:

- отдельный постоянный закрытый ключ;
- отдельный `known_hosts`;
- `StrictHostKeyChecking=yes`;
- `BatchMode=yes`;
- `IdentitiesOnly=yes`.

Этот ключ нельзя переиспользовать для входа в Linux-гости или для Git.

Полный контракт полномочий PVE находится в [`710-pve-access.md`](710-pve-access.md).

## 6. Межмашинный SSH

### 6.1. Источник права

Межмашинный SSH разрешается только двумя связанными правилами `access.yaml`.

Первое правило разрешает гостю собственную машинную идентичность:

```yaml
subject: guest:<VMID>
service: ssh
resource: identity
targets:
  - self
access:
  - issue
```

Второе правило задаёт допустимые цели:

```yaml
subject: guest:<VMID>
service: ssh
resource: guest
targets:
  - <selector>
access:
  - connect-root
```

Правило целей без `identity/issue` является ошибкой проекта.

Другого источника межмашинных SSH-прав нет. `guest.yaml`, `provision.yaml`, локальные SSH-файлы гостя и настройки OpenBao не могут самостоятельно расширять список допустимых целей.

### 6.2. Идентичность исходного гостя

Для `guest → guest` используется OpenBao SSH OTP.

Каждый исходный гость с `ssh/identity/issue` получает собственный AppRole. Его назначение — аутентифицировать только этот гость в OpenBao и разрешить ему запрос одноразового SSH-пароля только через собственную OTP-роль.

Постоянные данные AppRole:

- уникальны для конкретного гостя;
- не используются другими гостями;
- не хранятся в Git;
- не являются root token или служебным PVE-only AppRole;
- передаются гостю только через доверенный контур настройки;
- хранятся на госте с правами только для root.

После входа по AppRole гость получает короткоживущий OpenBao token. Политика token разрешает только запрос:

```text
ssh-otp/creds/guest-<VMID>
```

OTP-роль `guest-<VMID>` строится из `access.yaml` и содержит только адреса целей, разрешённых правилами `ssh/guest/connect-root`.

Для роли обязательны:

```text
key_type = otp
default_user = root
port = 22
```

Роли с нулевым адресом, разрешающие запрос OTP для произвольного IP, в проекте запрещены.

### 6.3. Проверка OTP на целевом госте

Каждый Linux-гость, который может быть целью межмашинного SSH, использует совместимый с OpenBao SSH OTP helper через PAM.

Для OTP-входа SSH должен:

- использовать PAM;
- разрешать keyboard-interactive authentication;
- не включать обычную парольную аутентификацию;
- передавать введённый одноразовый пароль только OTP helper.

Helper отправляет OTP в:

```text
ssh-otp/verify
```

и принимает вход только после успешной проверки OpenBao.

Для проверки OTP целевому гостю не выдаётся AppRole. Проверочный endpoint используется только через защищённое TLS-соединение к доверенному OpenBao.

Пользовательский SSH CA для Ansible остаётся отдельным способом входа и не зависит от OTP. Межмашинные public keys и principals по целевым гостям не распространяются.

### 6.4. Проверка сервера исходным гостем

OTP подтверждает право клиента войти, но не подлинность сервера.

Исходный гость обязан отдельно проверять цель через открытый `ssh-host-signer` как `@cert-authority` и использовать:

```text
StrictHostKeyChecking yes
```

Поэтому межмашинный вход требует одновременно:

- успешной AppRole-аутентификации исходного гостя в OpenBao;
- OTP, выданного для конкретного адреса разрешённой цели;
- успешной проверки OTP целевым гостем через OpenBao;
- действующего host certificate цели.

Отключение проверки host key ради автоматического ввода OTP запрещено.

### 6.5. Применение и отзыв

Настройки OTP выводятся из `access.yaml`.

При синхронизации:

1. определяются субъекты с `ssh/identity/issue`;
2. для каждого субъекта создаётся или обновляется собственный AppRole;
3. создаётся или обновляется OTP-роль `guest-<VMID>`;
4. список адресов роли приводится к точному набору разрешённых целей;
5. на целевых Linux-гостях проверяется общий OTP helper, PAM и доверие к TLS OpenBao;
6. удаляются лишние OTP-роли и машинные AppRole, которых больше нет в контракте.

Удаление `source → target` должно немедленно исключать адрес цели из OTP-роли источника. После этого новый OTP для этой цели получить нельзя.

Удаление `identity/issue` должно удалить или отключить машинный AppRole, отозвать доступные ему token и удалить соответствующую OTP-роль.

Уже выданный OTP является одноразовым и ограниченным коротким сроком жизни. Уже установленный SSH-сеанс автоматически не разрывается изменением `access.yaml`; отзыв влияет на новые подключения.

Для `guest → guest` не используются машинные SSH-сертификаты, периодическое их перевыпускание или таймер обновления сертификатов.

### 6.6. Доступность OpenBao

Новое межмашинное SSH-подключение зависит от доступности OpenBao дважды:

- исходный гость получает OTP;
- целевой гость проверяет OTP.

Поэтому OpenBao должен быть разблокирован и доступен обоим участникам по защищённому TLS-каналу.

Это осознанная граница архитектуры. Отказ OpenBao блокирует новые `guest → guest` подключения, но не должен блокировать независимый административный путь `910/Ansible → guest` по SSH CA.

## 7. Смена, потеря и отзыв

### 7.1. Временные учётные данные

Временные сертификаты Ansible не восстанавливаются и не продлеваются. Для следующей операции выпускается новая временная идентичность.

Межмашинный OTP также не сохраняется и не продлевается. Он выдаётся для одного подключения, после успешной проверки становится недействительным и в любом случае ограничен коротким сроком жизни OpenBao.

### 7.2. Сертификат сервера

Новый host certificate может быть выпущен для того же подтверждённого host key после истечения срока.

Если изменился сам host key, это должно рассматриваться как смена идентичности сервера и проходить отдельную проверку.

### 7.3. Постоянные машинные данные

Постоянные AppRole-данные исходного гостя являются машинным секретом. Их нельзя копировать между гостями или использовать как общий credential.

При подозрении на утечку SecretID должен быть отозван и выпущен заново через доверенный контур настройки.

Постоянный SSH-ключ, который сам является зарегистрированным источником доверия, нельзя тихо заменить новым под прежней идентичностью. Это относится к root SSH PVE, Git Deploy Key и закрытым ключам CA.

### 7.4. Отзыв центра доверия

Смена SSH CA затрагивает все системы, которые доверяют его открытому ключу.

Поэтому закрытые ключи CA являются критичным постоянным состоянием OpenBao и не должны ротироваться как обычный временный ключ.

## 8. Проверка контракта

Проверка SSH должна подтверждать:

- пользовательский CA установлен в госте;
- штатный Ansible действительно принимает сертификат с ожидаемым principal;
- сертификат сервера соответствует реальному host key;
- SSH-сервер использует `HostCertificate`;
- клиент не принимает неожиданно изменившийся host key;
- root SSH PVE использует только свою идентичность;
- Git SSH не использует административный ключ;
- машинный AppRole не создаётся без `identity/issue`;
- политика AppRole разрешает запрос только собственной OTP-роли;
- OTP-роль содержит только цели, разрешённые `access.yaml`;
- zero-address OTP-роли отсутствуют;
- целевой helper успешно проверяет OTP через TLS OpenBao;
- разрешённая машинная связь действительно работает;
- запрещённая машинная связь не может получить рабочий OTP;
- повторное использование уже принятого OTP невозможно;
- удаление правила запрещает выдачу нового OTP для удалённой цели;
- отказ OpenBao не уничтожает независимый административный SSH CA-доступ.
