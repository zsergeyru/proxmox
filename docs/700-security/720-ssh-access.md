## 1. Три разные задачи SSH

SSH в проекте решает три независимые задачи:

```text
кто имеет право войти
≠
как клиент убеждается, что подключается к правильному серверу
≠
как один гость получает разовое право войти в другой гость
```

Поэтому используются разные механизмы:

| Задача | Механизм |
|---|---|
| `910/Ansible → Linux-гость` | короткоживущий user certificate от client CA |
| подтверждение Linux-гостя | host certificate от отдельного host CA |
| `guest → guest` | OpenBao SSH OTP + машинный AppRole |
| `910 → PVE` | отдельный постоянный root SSH |
| Git | отдельный Git credential |

Одна идентичность не должна автоматически давать другую.

## 2. Административный SSH Ansible

Штатное управление Linux-гостями выполняет 910 через Ansible.

Поток выглядит так:

```text
Ansible создаёт временную пару ключей
        ↓ public key
PVE-only доверенный механизм
        ↓
OpenBao ssh-client-signer
        ↓ короткоживущий user certificate
Ansible + временный private key
        ↓
управляемый Linux-гость
```

### 2.1. Client CA

OpenBao содержит отдельный центр пользовательских сертификатов:

```text
ssh-client-signer
```

Управляемые Linux-гости доверяют его открытому ключу для административного входа.

Закрытый CA key не выдаётся 910, Ansible или гостям.

### 2.2. Временная идентичность

Для каждого штатного запуска создаётся новая временная Ed25519-пара.

Сертификат:

- является user certificate;
- разрешает только ожидаемый административный principal;
- имеет короткий срок жизни;
- не может использоваться для подписи других ключей;
- удаляется вместе с временным private key после операции.

Целевой срок административного сертификата — `15 минут`.

### 2.3. Отказ не должен ослаблять проверку

Если гость уже настроен на доверие client CA, ошибка входа по корректно выпущенному сертификату не должна автоматически приводить к использованию постоянного запасного ключа.

Такая ошибка означает проблему состояния или безопасности и требует диагностики.

## 3. Подлинность SSH-сервера

Право клиента войти и подлинность сервера — разные вещи.

Для проверки управляемых Linux-гостей используется отдельный центр:

```text
ssh-host-signer
```

Он выпускает только host certificate.

### 3.1. Что подписывается

Подписывается реальный SSH host public key работающего гостя.

Перед подписью доверенный PVE-контур должен подтвердить:

- VMID;
- имя VM/LXC;
- административный адрес;
- существование объекта в PVE;
- соответствие заявленной цели фактическому объекту.

Нельзя подписывать произвольный ключ только потому, что вызывающая сторона передала нужное имя или IP.

Для DHCP нужен отдельный доверенный способ определить фактический адрес после запуска.

### 3.2. Host certificate

Роль OpenBao:

```text
managed-host
```

выпускает серверный сертификат с principals, соответствующими подтверждённому имени и адресу.

Целевой срок host certificate — `720 часов`.

Client CA и host CA должны быть независимы и иметь разные ключи.

### 3.3. Проверка клиентом

Штатный клиент должен проверять сервер строго.

Целевое состояние — доверие к `ssh-host-signer` как к host CA.

Неожиданная смена host identity:

```text
не принимать автоматически
→ остановить подключение
→ подтвердить причину смены
→ только после этого обновить доверие
```

Пока миграция на host CA не завершена во всех клиентах, часть административного пути использует строгий `known_hosts`. Это переходное состояние, а не альтернативная архитектура.

## 4. Межмашинный SSH через OpenBao OTP

Целевая схема `guest → guest` не использует общие постоянные SSH-ключи и не использует периодически перевыпускаемые машинные SSH-сертификаты.

Для неё используется **OpenBao SSH OTP**.

### 4.1. Источник права

Межмашинный доступ существует только при наличии двух связанных правил `access.yaml`.

Источник должен иметь собственную машинную идентичность:

```yaml
service: ssh
resource: identity
targets: [self]
access: [issue]
```

И отдельно допустимые цели:

```yaml
service: ssh
resource: guest
targets:
  - <разрешённые цели>
access: [connect-root]
```

`connect-root` без `identity/issue` считается ошибкой контракта.

### 4.2. Идентичность исходного гостя

Для каждого субъекта `ssh/identity/issue` OpenBao создаёт отдельный машинный AppRole:

```text
guest:<VMID>
 ↓
auth/machine/role/guest-<VMID>
```

RoleID/SecretID этой роли принадлежат только данному исходному гостю.

После AppRole-аутентификации выдаётся короткоживущий OpenBao token с единственным нужным полномочием: запросить OTP через собственную роль.

Машинный token не должен позволять:

- читать KV;
- подписывать SSH-сертификаты;
- менять AppRole;
- менять OTP-роли;
- использовать роль другого гостя;
- выполнять PVE-only функции.

### 4.3. OTP-роль источника

Для того же субъекта существует:

```text
ssh-otp/roles/guest-<VMID>
```

Её допустимые адреса выводятся только из правил `ssh/guest/connect-root` этого субъекта.

Роль должна быть ограничена:

```text
key_type = otp
default_user = root
port = 22
allowed_cidr_list = только разрешённые цели
```

Роль, позволяющая получать OTP для произвольного адреса, запрещена.

### 4.4. Получение OTP

Поток:

```text
исходный гость
 → собственный AppRole
 → короткоживущий OpenBao token
 → собственная OTP-роль
 → одноразовый пароль для конкретной разрешённой цели
```

OTP:

- не является сертификатом;
- не хранится как постоянный secret;
- выдаётся для конкретной цели;
- имеет короткий срок жизни;
- не продлевается;
- после успешной проверки больше не действует.

### 4.5. Проверка на целевом госте

Целевой Linux-гость использует совместимый OTP helper через SSH/PAM.

При подключении:

```text
SSH keyboard-interactive
        ↓
OTP helper
        ↓
OpenBao ssh-otp/verify
        ↓
разрешить или запретить вход
```

Цели не требуется собственный машинный AppRole только для проверки введённого OTP.

Обычная постоянная парольная аутентификация не должна включаться ради OTP.

### 4.6. Проверка самого сервера

OTP подтверждает право клиента, но не доказывает, что клиент подключился к правильному серверу.

Поэтому исходный гость одновременно обязан проверить host certificate цели через `ssh-host-signer` и сохранить строгую проверку SSH-сервера.

Успешный межмашинный вход требует одновременно:

1. собственной AppRole-аутентификации источника;
2. OTP только для разрешённой цели;
3. успешной проверки OTP целью через OpenBao;
4. действующего host certificate цели.

### 4.7. Сетевой доступ к OpenBao

Новое `guest → guest` соединение зависит от OpenBao дважды:

- источник получает OTP;
- цель проверяет OTP.

Поэтому для межмашинного доступа OpenBao должен иметь отдельный защищённый сетевой вход для нужных Linux-гостей.

Этот вход обязан использовать TLS с проверкой сертификата.

Открытый HTTP-доступ OpenBao из гостевой сети запрещён.

### 4.8. Синхронизация и отзыв

`access.yaml` является единственным источником целей.

При изменении контракта должны синхронизироваться:

- машинные AppRole;
- OTP-роли;
- разрешённые адреса целей;
- наличие OTP helper на допустимых целях;
- доверие источников к host CA.

Удаление `source → target` должно исключить цель из OTP-роли источника. Новый OTP к этой цели после этого получить нельзя.

Удаление `identity/issue` должно отключить машинную идентичность источника и его OTP-роль.

Уже установленный SSH-сеанс не разрывается автоматически изменением `access.yaml`; отзыв действует на новые подключения.

## 5. Root SSH к PVE

`910 → PVE root` является отдельным постоянным SSH-контуром.

Он не использует:

- client CA Ansible;
- машинный AppRole;
- OTP;
- Git credential.

Его назначение и жизненный цикл описаны в [`710-pve-access.md`](710-pve-access.md).

## 6. Переходный постоянный ключ

До того как новый Linux-гость научился доверять client CA, проекту нужен способ первого входа.

Сейчас для этого существует переходный постоянный Ansible-ключ.

Он допустим только для:

- первого входа;
- первоначальной базовой настройки;
- восстановления собственного управляемого доступа.

Он не является целевой системой административного доступа и не должен использоваться как общий межмашинный ключ.

Фактическое состояние его использования находится в [`780-implementation-status.md`](780-implementation-status.md).

## 7. Отзыв и ротация

### 7.1. User certificate Ansible

Не восстанавливается и не продлевается. Следующая операция получает новый сертификат.

### 7.2. OTP

Не восстанавливается и не продлевается. Для следующего соединения запрашивается новый OTP.

### 7.3. Машинный AppRole

SecretID является постоянным машинным секретом конкретного источника.

При компрометации он должен быть отозван и перевыпущен через доверенный контур настройки.

Копировать один SecretID нескольким гостям запрещено.

### 7.4. Host certificate

После истечения можно выпустить новый сертификат для того же подтверждённого host key.

Смена самого host key требует отдельного подтверждения идентичности.

### 7.5. SSH CA

Смена client CA или host CA затрагивает все системы, доверяющие соответствующему открытому ключу.

Поэтому закрытые CA keys являются критичным состоянием OpenBao и не должны тихо заменяться новым центром доверия.

## 8. Проверка контракта

Проверка должна подтверждать:

- административный SSH использует отдельный client CA;
- host certificate подписывает отдельный host CA;
- client CA и host CA различаются;
- PVE проверяет цель до выпуска host certificate;
- SSH-клиенты не отключают проверку сервера;
- каждый OTP-источник имеет отдельный AppRole;
- AppRole не может использовать чужую OTP-роль;
- OTP-роль содержит только цели из `access.yaml`;
- OTP нельзя повторно использовать;
- целевой helper проверяет OTP через OpenBao;
- межмашинный доступ к OpenBao использует TLS;
- удаление права прекращает выдачу новых OTP;
- отказ OpenBao не уничтожает независимый административный путь 910/Ansible.

Пока OTP ещё не полностью реализован, фактическая проверка должна отдельно показывать переходное состояние, а не считать старые машинные сертификаты целевой моделью.
