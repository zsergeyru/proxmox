# SSH-доступ

**Тип:** спецификация  
**Статус:** проектируется  
**Назначение:** определить SSH-доступ после переноса управления Linux-гостями в `910 infra-deployer` и Ansible.

## 1. Основной принцип

В новой архитектуре нет общего реестра `<VMID>.pub` на PVE и нет `management-authorized-keys`.

Основной административный SSH-контур:

```text
910 infra-deployer
└─ Semaphore / Ansible
   └─ управляемые Linux-гости
```

PVE не является центром распространения SSH-ключей.

## 2. Ansible identity

Для первой версии используется одна техническая SSH-идентичность Ansible.

Закрытый ключ хранится в Semaphore Key Store внутри `910`.

Открытый ключ передаётся новому Linux-гостю при его первоначальном создании и затем управляется Ansible.

Закрытый ключ не передаётся другим гостям и не хранится на PVE.

## 3. authorized_keys

Ansible управляет только явно определённым набором проектных ключей.

Сторонние пользовательские ключи не должны удаляться только потому, что они не принадлежат инфраструктурному контуру.

Если для конкретного системного пользователя проект принимает полный контроль над `authorized_keys`, это должно быть явно задано соответствующей Ansible-ролью.

Собственный механизм `sync-management-keys` больше не является частью целевой архитектуры.

## 4. Git SSH

GitHub Deploy Key закрытого репозитория является отдельной идентичностью.

Он создаётся и хранится внутри `910` и используется только для чтения:

```text
git@github.com:zsergeyru/proxmox.git
```

Git-ключ не используется для административного входа в VM/LXC.

## 5. SSH к PVE

Штатное управление Proxmox из `910` выполняется через HTTPS API.

Постоянный root SSH с `910` на физический PVE не входит в контракт.

Если будущая функция конкретного инструмента действительно потребует SSH к PVE, для неё проектируется отдельная ограниченная идентичность и отдельный набор разрешённых команд. Полный root-доступ не выдаётся автоматически.

## 6. Доверие к SSH host keys

Первое подключение к новому Linux-гостю допускается только после однозначного подтверждения его VMID, адреса и факта создания проектом.

После принятия SSH host key последующие подключения используют строгую проверку.

Неожиданная смена host key:

```text
ключ изменился
→ BLOCKED
→ старую запись автоматически не удалять
→ выяснить причину
```

Осознанное пересоздание гостя должно иметь отдельную процедуру обновления доверия.

## 7. SSH CA

Переход на OpenSSH CA допускается в будущем, если число управляемых систем сделает обычное управление ключами неудобным.

SSH CA не требуется для первой версии новой архитектуры.

## 8. Потеря Ansible key

Ansible private key является критичным секретом и должен входить в резервную копию Semaphore.

Если ключ потерян без резервной копии, новый ключ не выдаётся скрытно под видом старого. Требуется явная процедура восстановления доступа и ротации публичного ключа в управляемых гостях.
