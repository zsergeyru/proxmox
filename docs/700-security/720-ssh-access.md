# Административный доступ по SSH

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить управляющие SSH-идентичности проекта, реестр открытых ключей, правила их распространения, проверки, смены и отзыва.

Этот документ отвечает на вопрос:

> Как в проекте организован административный SSH-доступ к гостевым системам и как управляются ключи этого доступа?

Общие принципы безопасности описываются в `700-overview.md`. Права внутри Proxmox относятся к `710-pve-access.md`.

## 1. Назначение и границы

`720-ssh-access.md` является основным источником для управляющего SSH-контура проекта.

Здесь фиксируются:

- SSH-идентичность deployer на PVE;
- собственные SSH-идентичности управляющих гостевых систем;
- канонический реестр открытых ключей на PVE;
- итоговый набор разрешённых управляющих ключей;
- участие гостя в управляющем SSH-контуре;
- работа `sync-management-keys`;
- правила проверки SSH-ключа сервера;
- создание, повторное использование, смена и отзыв ключей;
- проверка фактического административного доступа.

В этот документ не входят:

- права пользователей и токенов Proxmox;
- Git-ключи для чтения или записи репозитория;
- личные SSH-ключи человека, если они не являются частью управляемого проектного контура;
- прикладные ключи отдельных сервисов;
- точные владельцы и права всех файлов на PVE.

Эти вопросы относятся к другим профильным документам.

## 2. Участники SSH-доступа

### 2.1. Deployer

На PVE существует постоянная SSH-идентичность deployer:

```text
/etc/proxmox-deployer/ssh/pve_deployer_ed25519
/etc/proxmox-deployer/ssh/pve_deployer_ed25519.pub
```

Закрытая часть остаётся на PVE.

Эта идентичность используется для административного входа в управляемые Debian-гости.

Deployer не использует эту пару для доступа к Git.

### 2.2. Управляющие гостевые системы

Некоторым гостевым системам может требоваться собственная управляющая SSH-идентичность.

Это задаётся в требуемом состоянии гостя:

```yaml
management:
  - ssh_identity
```

Закрытая часть такой пары создаётся и хранится внутри самого гостя.

На PVE передаётся только открытая часть, которая регистрируется в общем реестре.

Механизм не зависит от назначения гостя: это может быть AI Control, Ansible-контроллер или другая управляющая система.

### 2.3. Управляемые гости

В управляющий SSH-контур входит любой проектный гость с `profile`: для него действует фиксированный административный SSH-контракт `root:22`.

Отдельный признак участия в фактическом состоянии Proxmox для этого не используется.

Средства синхронизации должны определять состав управляемых гостей из нормативного состояния проекта и дополнительно проверять фактическое состояние перед изменением гостя.

### 2.4. Человек

Личный SSH-доступ человека не смешивается с проектным реестром автоматически.

Если в `authorized_keys` уже существуют личные или другие неуправляемые ключи, проект не должен удалять или заменять их.

Проект управляет только своим выделенным блоком ключей.

## 3. SSH-идентичности

### 3.1. Идентичность Deployer

Пара deployer:

```text
/etc/proxmox-deployer/ssh/pve_deployer_ed25519
/etc/proxmox-deployer/ssh/pve_deployer_ed25519.pub
```

создаётся один раз и после этого считается постоянной.

При обычной повторной конфигурации:

```text
пара существует и корректна
→ сохранить

пары нет
→ создать по установленному контракту

пара существует, но состояние неоднозначно
→ не заменять автоматически
```

Закрытый ключ не переносится в гостевые системы.

В общий реестр попадает только открытая часть.

### 3.2. Идентичность управляющего гостя

Если у гостя указано:

```yaml
management:
  - ssh_identity
```

для него создаётся собственная пара SSH-ключей внутри гостевой системы.

Закрытая часть остаётся в этом госте.

Открытая часть регистрируется на PVE как:

```text
/var/lib/proxmox-deployer/public-keys/<VMID>.pub
```

Таким образом, управляющий гость может административно подключаться к другим участникам управляющего SSH-контура, не передавая свой закрытый ключ на PVE.

### 3.3. Закрытые и открытые ключи

В проекте разделяются:

```text
закрытый ключ
→ хранится только у владельца идентичности

открытый ключ
→ может регистрироваться и распространяться
```

Канонический реестр на PVE содержит только открытые ключи.

В нём запрещено хранить:

- закрытые SSH-ключи;
- Git-ключи;
- API-токены;
- пароли;
- другие секреты.

### 3.4. Привязка к VMID

Открытый ключ собственной идентичности гостя хранится под именем:

```text
<VMID>.pub
```

Следовательно, идентичность привязана к VMID, а не к имени гостя.

Переименование гостя:

```text
имя изменилось
→ ключ не меняется
→ имя файла <VMID>.pub не меняется
```

Повторное использование того же VMID для нового гостя требует новой идентичности.

Старый ключ не должен автоматически переходить новому объекту.

## 4. Реестр и распространение открытых ключей

### 4.1. Реестр на PVE

Канонический реестр находится в:

```text
/var/lib/proxmox-deployer/public-keys/
```

Основные элементы:

```text
pve_deployer_ed25519.pub
<VMID>.pub
management-authorized-keys
```

`pve_deployer_ed25519.pub` — открытый ключ deployer.

`<VMID>.pub` — открытый ключ собственной управляющей идентичности конкретного гостя.

`management-authorized-keys` — итоговый набор всех разрешённых управляющих открытых ключей.

### 4.2. Итоговый набор разрешённых ключей

Файл:

```text
management-authorized-keys
```

собирается из всех зарегистрированных и проверенных открытых ключей.

Он является единым набором, который должен быть установлен во всех управляемых Debian-гостях, участвующих в этом контуре.

Добавление или удаление отдельного ключа должно приводить к пересборке итогового набора.

Непроверенный или неоднозначный ключ не должен автоматически попадать в итоговый файл.

### 4.3. Участие гостя в управляющем SSH-контуре

Состав гостей, которым должен распространяться актуальный набор управляющих ключей, определяется по итоговому требуемому состоянию проекта.

Гость участвует в этом контуре, если его `guest.yaml` содержит `profile`. Список `management` не включает и не отключает административный вход в сам гость.

Перед изменением гостя дополнительно проверяются:

- тип гостевой системы;
- ожидаемый административный адрес;
- фактическое существование и состояние объекта;
- сохранённый SSH-ключ сервера;
- соответствие фактического объекта ожидаемому гостю.

Фактическое состояние Proxmox не используется как параллельный источник решения о том, должен ли гость участвовать в управляющем SSH-контуре.

### 4.4. `sync-management-keys`

Команда:

```text
sync-management-keys
```

выполняет массовое распространение только открытых управляющих ключей.

Общая схема:

```text
канонический реестр на PVE
→ собрать management-authorized-keys
→ определить по итоговому состоянию существующих гостей с profile
→ проверить фактическое состояние и возможность безопасного подключения
→ обновить управляемый набор ключей у гостя
```

Команда не создаёт и не меняет закрытые ключи.

Она также не используется для скрытой ротации идентичностей.

### 4.5. Управляемый блок `authorized_keys`

В гостевой системе проект управляет только выделенным блоком:

```text
# BEGIN PROXMOX-MANAGEMENT-KEYS
<management-authorized-keys>
# END PROXMOX-MANAGEMENT-KEYS
```

в файле:

```text
/root/.ssh/authorized_keys
```

Ключи и строки за пределами этого блока сохраняются без изменений.

После удаления открытого ключа из канонического реестра следующая успешная синхронизация удаляет его только:

- из управляемого блока `authorized_keys`;
- из локальной копии управляющего набора открытых ключей.

Другие ключи пользователя не затрагиваются.

## 5. Доверие к SSH-серверу гостя

### 5.1. Первое подключение

При первом подключении к новому ожидаемому гостю его SSH-ключ сервера ещё неизвестен.

Первичное принятие допускается только если одновременно известны и проверены:

- ожидаемый VMID;
- ожидаемый административный адрес;
- факт создания или включения гостя в проект;
- отсутствие неоднозначности с уже существующим объектом.

После первого успешного подключения SSH-ключ сервера сохраняется.

### 5.2. Сохранённый ключ сервера

Для уже известного гостя последующие подключения должны использовать сохранённый SSH-ключ сервера.

Автоматическая работа должна подтверждать, что подключение происходит именно к тому же узлу, которому ранее было установлено доверие.

### 5.3. Неожиданная смена ключа

Если у уже известного гостя неожиданно меняется SSH-ключ сервера:

```text
новый ключ не совпадает с сохранённым
→ остановить автоматическую работу
→ старую запись не удалять автоматически
→ выяснить причину изменения
```

Допустимая причина может быть связана с осознанным пересозданием гостя, но такое изменение должно подтверждаться отдельно.

Автоматическое удаление старого ключа сервера ради продолжения работы запрещено.

## 6. Жизненный цикл ключей

### 6.1. Создание

Для deployer:

```text
первичная конфигурация PVE
→ создать постоянную пару, если её ещё нет
→ зарегистрировать открытый ключ
```

Для гостя с собственной управляющей идентичностью:

```text
первое развёртывание
→ создать пару внутри гостя
→ проверить соответствие закрытой и открытой частей
→ передать только открытый ключ на PVE
→ зарегистрировать <VMID>.pub
→ синхронизировать общий набор
```

### 6.2. Повторное использование

Обычное повторное развёртывание не должно создавать новую пару, если существующая идентичность корректна.

```text
существующая пара корректна
→ использовать её повторно

пара отсутствует или повреждена
→ не маскировать ситуацию автоматической заменой
```

### 6.3. Смена

Смена постоянной SSH-идентичности является отдельной операцией.

Безопасный порядок:

```text
создать или подтвердить новую пару у владельца
→ зарегистрировать новый открытый ключ
→ синхронизировать общий набор
→ проверить вход новой идентичностью
→ только после этого удалить старый открытый ключ
→ снова синхронизировать
```

Нельзя сначала удалить старый рабочий ключ, а затем пытаться проверить новый доступ.

### 6.4. Отзыв

Для отзыва управляющей идентичности:

```text
удалить соответствующий открытый ключ из канонического реестра
→ пересобрать management-authorized-keys
→ выполнить sync-management-keys
→ проверить отсутствие ключа в управляемых гостях
```

Закрытая часть у бывшего владельца после этого больше не должна давать доступ к управляемым гостям.

### 6.5. Удаление гостя

Если удаляется гость с собственной управляющей идентичностью, операция не считается полностью завершённой, пока не выполнено:

```text
удалить <VMID>.pub
→ пересобрать общий набор
→ выполнить sync-management-keys
```

Иначе удалённая система или сохранившаяся копия её закрытого ключа может продолжать иметь административный доступ.

### 6.6. Повторное использование VMID

Если позже создаётся новый гость с тем же VMID:

```text
старый <VMID>.pub не использовать
→ создать новую пару
→ зарегистрировать новый открытый ключ
```

Совпадение VMID не означает продолжение прежней доверенной идентичности.

### 6.7. Потеря закрытого ключа

Если закрытый ключ потерян, новый ключ не создаётся незаметно под видом старого.

Для deployer требуется отдельная восстановительная или ротационная операция.

Для управляющего гостя порядок такой же:

```text
подтвердить потерю старой идентичности
→ создать новую пару
→ зарегистрировать новый открытый ключ
→ синхронизировать
→ проверить новый доступ
→ считать старую идентичность отозванной
```

Если существует защищённая резервная копия исходного ключа и принято решение восстановить именно прежнюю идентичность, это выполняется как отдельная операция восстановления.

## 7. Проверка состояния

### 7.1. Проверка идентичностей

Для deployer проверяется:

- наличие закрытой и открытой частей;
- соответствие пары;
- ожидаемый владелец и права файла;
- наличие открытого ключа в каноническом реестре.

Для гостя с собственной управляющей идентичностью проверяется:

- наличие пары внутри гостя;
- соответствие закрытой и открытой частей;
- соответствие зарегистрированному `<VMID>.pub`.

### 7.2. Проверка реестра

Канонический реестр должен проверяться на:

- допустимые имена файлов;
- отсутствие закрытых ключей и других секретов;
- отсутствие повреждённых ключей;
- однозначную связь `<VMID>.pub` с существующей управляющей идентичностью;
- корректную сборку `management-authorized-keys`.

Неизвестный или неподтверждённый ключ считается ошибкой, а не автоматически допустимым элементом реестра.

### 7.3. Проверка распространения

Для каждого гостя, участвующего в управляющем SSH-контуре, проверяется:

- наличие проектного `guest.yaml` с `profile`;
- доступность по ожидаемому административному адресу;
- корректный SSH-ключ сервера;
- актуальная локальная копия общего набора открытых ключей;
- соответствие управляемого блока `authorized_keys` каноническому набору.

### 7.4. Проверка фактического доступа

После изменения ключей должна выполняться реальная проверка входа.

Минимально:

```text
deployer
→ может войти в управляемый гостевой Linux

управляющий гость с собственной identity
→ может войти в разрешённый управляемый гость

отозванная identity
→ больше не имеет доступа
```

Если в проекте существуют несколько независимых управляющих идентичностей, после существенных изменений желательно проверить минимум две из них.

## 8. Границы ответственности

Этот документ является основным источником для управляющего SSH-доступа проекта.

Он определяет:

- проектные SSH-идентичности;
- канонический реестр открытых ключей;
- общий набор разрешённых ключей;
- участие гостя в управляющем SSH-контуре по наличию `profile` в требуемом состоянии;
- работу `sync-management-keys`;
- проверку SSH-ключа сервера;
- жизненный цикл ключей.

При этом:

- общая политика безопасности находится в `700-overview.md`;
- права Proxmox находятся в `710-pve-access.md`;
- точные пути, владельцы и права файлов PVE находятся в `../200-pve/230-host-layout.md`;
- создание базовой SSH-инфраструктуры PVE относится к `../200-pve/220-host-configuration.md`;
- административный SSH определяется наличием `profile`, а список `management` задаёт только дополнительные возможности `ssh_identity` и `project_repo_read`;
- порядок применения этих параметров при развёртывании относится к `../300-guests/330-deploy-guest.md`;
- Git-доступ не является частью управляющего SSH-контура.
