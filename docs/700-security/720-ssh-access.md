## 1. Разделение SSH-контуров

Проект не использует один общий private key для всех задач.

| Контур | Назначение |
|---|---|
| временный сертификат `infra-manager` | штатный административный вход в Linux-гости |
| SSH host certificate | подтверждение подлинности Linux-гостя |
| OpenBao online SSH | ограниченный guest-to-guest доступ |
| recovery administrator key | аварийное восстановление доверия при потере OpenBao |
| root SSH `infra-manager → PVE` | узкие операции физического PVE |
| Git SSH | доступ к GitHub |
| личный SSH человека | интерактивный доступ человека |

Получение одного контура не выдаёт остальные.

## 2. Штатный вход infra-manager в Linux-гости

Управляемый Linux-гость доверяет открытому ключу `ssh-client-signer` OpenBao через `TrustedUserCAKeys`.

Для каждого Ansible-задания `infra-manager` создаёт новую временную Ed25519-пару, передаёт OpenBao только public key и получает короткоживущий пользовательский сертификат.

Целевой срок сертификата — 15 минут.

Private key существует только на время задания и затем удаляется.

Постоянный public key `infra-manager` не распространяется по всем гостям для штатного входа.

Если гость уже доверяет Client CA, ошибка входа по корректно выпущенному сертификату является ошибкой. Тихий переход на recovery key запрещён.

Первоначальный ввод нового гостя до установки Client CA может использовать отдельно определённый bootstrap-механизм. Он не должен становиться постоянным штатным обходом сертификатного доступа.

## 3. Подлинность SSH-сервера

Каждый Linux-сервер сохраняет собственный Ed25519 host private key.

OpenBao `ssh-host-signer` подписывает только его public key.

До подписи доверенный механизм проверяет VMID, имя и административный адрес объекта.

Сервер устанавливает выданный host certificate через `HostCertificate`.

Клиенты должны проверять ожидаемое имя или адрес сервера. Неожиданная смена host identity не принимается автоматически.

## 4. Централизованный SSH между гостями

Обычный гость не получает постоянную `management` SSH-пару, которую нужно разносить по другим серверам.

Право `guest A → guest B` задаётся в `access.yaml` и применяется через OpenBao.

Целевая модель использует SSH OTP или эквивалентную онлайн-проверку OpenBao:

~~~text
источник
→ запрашивает одноразовый доступ к конкретной цели
→ OpenBao проверяет policy и цель
→ выдаёт одноразовый credential
→ целевой SSH-сервер проверяет его через OpenBao
~~~

После первоначальной настройки общего helper/PAM-механизма целевой сервер не должен хранить отдельный public key каждого возможного источника.

Изменение матрицы доступа должно применяться централизованно в OpenBao.

## 5. Аварийный административный ключ

На каждом управляемом Linux-госте должен быть зарегистрирован один проектный recovery public key.

Его private key хранится только в PVE-only recovery-области и не доступен штатным заданиям `infra-manager`.

Назначение ключа:

- восстановить доверие к новому SSH Client CA после полной потери OpenBao;
- исправить SSH-конфигурацию, если штатный центр доверия недоступен;
- обеспечить независимую последнюю точку входа до использования консоли PVE.

Recovery key никогда не используется как автоматический fallback.

Операция восстановления должна запускаться явно и после неё обязана проверяться работа штатного доступа через OpenBao.

Проект управляет только собственной строкой или блоком в `authorized_keys` и не удаляет неизвестные пользовательские ключи без отдельного правила.

## 6. SSH к PVE

Root SSH `infra-manager → PVE` остаётся отдельной постоянной идентичностью.

Она использует собственные private/public key, строгий `known_hosts`, `BatchMode=yes`, `IdentitiesOnly=yes` и не применяется для Linux-гостей или Git.

Этот доступ описан подробнее в `710-pve-access.md`.

## 7. Смена и отзыв

Временные сертификаты и OTP не восстанавливаются: выпускается новое краткоживущее полномочие.

Смена SSH Client CA требует обновить публичный доверенный CA на управляемых Linux-гостях. При полной потере прежнего CA для этого используется recovery administrator key.

Смена recovery key является отдельной аварийной операцией: новый public key сначала должен быть подтверждённо установлен на всех требуемых системах, и только затем старый ключ может быть отозван.

Смена host key сервера считается сменой его идентичности и требует повторной доверенной проверки перед выдачей нового host certificate.

## 8. Проверка

Проверка должна подтверждать:

- доверие гостя к ожидаемому Client CA;
- успешный штатный вход по короткоживущему сертификату;
- отсутствие автоматического fallback на recovery key;
- соответствие host certificate реальному host key;
- невозможность получить guest-to-guest SSH к запрещённой цели;
- наличие recovery public key на управляемых Linux-системах;
- отсутствие recovery private key внутри 910 и обычных гостей;
- независимость root SSH PVE и Git SSH.
