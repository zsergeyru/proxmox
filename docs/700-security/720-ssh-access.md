# SSH-доступ

**Тип:** спецификация
**Статус:** внедрено в переходном режиме
**Назначение:** определить SSH-доступ после переноса управления Linux-гостями в `910 infra-manager` и Ansible.

## 1. Основной принцип

В новой архитектуре нет общего реестра `<VMID>.pub` на PVE и нет `management-authorized-keys`.

Основной административный SSH-контур:

```text
910 infra-manager
└─ Semaphore / Ansible
   └─ управляемые Linux-гости
```

PVE не является центром распространения SSH-ключей.

## 2. Ansible identity

Основной штатный доступ Ansible после настройки SSH CA выполняется по короткоживущему пользовательскому сертификату OpenSSH.

Перед полной настройкой `deploy-guest`:

```text
создать временную пару Ed25519
→ передать на PVE только открытый ключ
→ подписать его через ssh-client-signer / роль infra-manager
→ получить сертификат на 15 минут с principal root
→ проверить реальный SSH-вход
→ запустить Ansible с временным private key + CertificateFile
→ удалить временный каталог
```

Закрытый временный ключ существует только в каталоге текущего задания `infra-runtime` и не передаётся на PVE или в OpenBao.

Постоянные AppRole RoleID/SecretID для подписи хранятся только на PVE в `pve-only/openbao/ssh-access.json`. Они не монтируются в 910 и не сохраняются в рабочем каталоге задания. Для запроса подписи служебные данные используются только хостовым сценарием; выданный OpenBao токен короткоживущий и отзывается после операции.

На переходном этапе остаётся прежняя постоянная пара:

~~~text
/etc/infra-manager/ansible/guest_ed25519
/etc/infra-manager/ansible/guest_ed25519.pub
~~~

Она нужна для первого подключения к новому гостю, который ещё не получил `TrustedUserCAKeys`, и для базовой стадии первоначального создания 910 до готовности OpenBao. Если гость уже доверяет проектному CA, ошибка входа по временному сертификату является блокирующей: автоматический откат на постоянный ключ запрещён.

Временный `990 bootstrap-runner` по-прежнему использует отдельную краткоживущую пару для первоначального создания 910.

## 3. authorized_keys

Ansible управляет только явно определённым набором проектных ключей.

Сторонние пользовательские ключи не должны удаляться только потому, что они не принадлежат инфраструктурному контуру.

Если для конкретного системного пользователя проект принимает полный контроль над `authorized_keys`, это должно быть явно задано соответствующей Ansible-ролью.

Собственный механизм `sync-management-keys` больше не является частью целевой архитектуры.

## 4. Git SSH

GitHub Deploy Key закрытого репозитория является отдельной идентичностью.

Он создаётся и хранится внутри `910` и используется только для чтения:

```text
git@github.com:zsergeyru/proxmox.git
```

Git-ключ не используется для административного входа в VM/LXC.

## 5. SSH к PVE

`910 infra-manager` считается доверенным административным контуром PVE и имеет отдельный постоянный root SSH-доступ.

Этот ключ не переиспользует:

- GitHub Deploy Key;
- ключ Ansible для управляемых гостей.

Пути внутри 910:

```text
/etc/infra-manager/pve-host/root_ed25519
/etc/infra-manager/pve-host/known_hosts
```

Root SSH используется общим кодом только для операций PVE, которые нельзя выполнить API token. Основным путём OpenTofu остаётся HTTPS API.

Для `container-host`:

```text
nesting=1 → PVE API
keyctl=1  → root SSH
```

AI Control и прикладные гости этот ключ не получают.

## 6. Доверие к SSH host keys

Первое подключение к новому Linux-гостю допускается только после однозначного подтверждения его VMID, адреса и факта создания проектом.

После принятия SSH host key последующие подключения используют строгую проверку.

Неожиданная смена host key:

```text
ключ изменился
→ BLOCKED
→ старую запись автоматически не удалять
→ выяснить причину
```

Осознанное пересоздание гостя должно иметь отдельную процедуру обновления доверия.

## 7. SSH CA

OpenBao хранит два независимых SSH-центра доверия:

- `ssh-client-signer` — подписывает пользовательские сертификаты для входа Ansible;
- `ssh-host-signer` — предназначен для сертификатов SSH-серверов и подключается отдельным следующим этапом.

Для клиентской подписи используется роль `infra-manager`:

- разрешены только пользовательские сертификаты;
- principal ограничен пользователем `root`;
- срок сертификата — 15 минут;
- закрытый ключ CA не экспортируется;
- подписывающий служебный доступ не может менять саму роль.

Открытый ключ `ssh-client-signer` устанавливается гостям как:

```text
/etc/ssh/trusted-user-ca-keys.pem
```

и подключается через `TrustedUserCAKeys`.

Проверка подлинности самого SSH-сервера пока остаётся на обычном `known_hosts`. Переход на `ssh-host-signer` выполняется отдельно, чтобы не смешивать доверие клиента и подлинность сервера.

## 8. Потеря переходного постоянного ключа

Пока миграция не завершена, постоянный `guest_ed25519` остаётся резервируемым секретом, потому что нужен для первого подключения к гостю без установленного CA.

После удаления старой схемы этот ключ перестанет быть частью штатного доступа. Рабочий SSH-доступ будет зависеть от доступности OpenBao, PVE-only служебного доступа к роли подписи и доверенного открытого CA на гостях.

До окончательного удаления постоянного ключа его потеря требует явного восстановления, а не скрытой генерации нового ключа под старым именем.
