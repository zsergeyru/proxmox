## 1. Назначение `access.yaml`

Требования к доступу не должны быть разбросаны между `guest.yaml`, `provision.yaml`, OpenBao, PVE ACL и настройками отдельных программ.

Единым источником требований является:

```text
infrastructure/security/access.yaml
```

Он отвечает только на вопрос:

> какой субъект имеет право обратиться к какому ресурсу и что именно ему разрешено.

Файл не описывает способ хранения секрета и не содержит сам секрет.

Из этого контракта могут выводиться технические настройки PVE, Semaphore, OpenBao, SSH и Git. Фактический механизм применения зависит от соответствующей подсистемы.

## 2. Расположение и структура

Машинная схема:

```text
infrastructure/schemas/access.schema.yaml
```

Верхний уровень:

```yaml
schema_version: 1
rules:
  - ...
```

Каждое правило имеет уникальный `id`.

## 3. Поля правила

Пример:

```yaml
- id: infra-manager-project-repository
  subject: guest:910
  service: github
  resource: repository
  targets:
    - zsergeyru/proxmox
  access:
    - read
```

Поля:

| Поле | Назначение |
|---|---|
| `id` | устойчивое уникальное имя правила |
| `subject` | кто получает право |
| `service` | через какую подсистему действует право |
| `resource` | класс ресурса |
| `targets` | конкретная область действия |
| `access` | разрешённые действия |

Поддерживаемые субъекты первой версии:

```text
guest:<VMID>
host:pve
service:<name>
```

Поддерживаемые подсистемы:

```text
pve-api
ssh
github
semaphore
openbao
```

Права задаются только из фиксированного набора схемы. Произвольные строки не допускаются.

## 4. Текущие субъекты доступа

### 4.1. `guest:910`

`910 infra-manager` является доверенным исполнителем инфраструктуры.

Контракт фиксирует:

- управление жизненным циклом VM/LXC через PVE API в области `/vms`;
- чтение требуемых PVE-хранилищ;
- отдельный root SSH к `host:pve` только для host-only операций;
- чтение `zsergeyru/proxmox`;
- административный SSH к Linux-гостям проекта.

Точное разделение PVE API и host-only SSH определено в `710-pve-access.md`.

### 4.2. `guest:410`

`410 ai-control` не получает прямой PVE API и root SSH к PVE.

Контракт разрешает:

- чтение `zsergeyru/proxmox`;
- собственную исходящую SSH-идентичность;
- SSH только к Linux-гостям в `pool:managed`;
- запуск ограниченного набора инфраструктурных операций через Semaphore:
  - `opentofu-plan`;
  - `deploy-managed-guest`;
  - `verify-managed-guest`.

Это не даёт права:

- управлять 410 или 910 как объектами Proxmox;
- выполнять bootstrap;
- выполнять произвольный shell;
- менять PVE ACL, пользователей, токены, сеть или хранилища хоста;
- получать root SSH к PVE.

### 4.3. `guest:311`

Для 311 пока сохраняются старые поля `management`.

Их действующий смысл уже отражён в `access.yaml`:

- собственная исходящая SSH-идентичность;
- чтение проектного репозитория.

Цели межмашинного SSH для 311 не добавляются без отдельного решения.

### 4.4. `host:pve`

PVE-only контур получает только служебные операции OpenBao, которые нужны до появления штатных рабочих доступов:

- снятие блокировки OpenBao;
- материализация логических рабочих credentials;
- узкое обновление данных Semaphore;
- настройка и использование SSH CA.

В `access.yaml` используются логические имена ресурсов, а не пути KV или файловой системы.

## 5. Связь с другими машинными описаниями

Области ответственности разделены так:

| Файл | Что описывает |
|---|---|
| `guest.yaml` | объект VM/LXC в Proxmox |
| `provision.yaml` | содержимое и службы Linux-гостя |
| `status.yaml` | проверку и итоговое представление состояния |
| `access.yaml` | права между субъектами и ресурсами |

`guest.yaml` не должен становиться каталогом прав.

`provision.yaml` может содержать технические параметры реализации доступа конкретной роли, но не является источником решения о том, кому это право положено.

`access.yaml` не описывает процессор, память, пакеты, каталоги приложений или порядок установки.

## 6. Что запрещено хранить

В `access.yaml` запрещены:

- пароли;
- API secrets;
- закрытые ключи;
- токены;
- RoleID/SecretID;
- пути к файлам с секретами;
- пути OpenBao KV;
- произвольные credentials;
- данные, которые позволяют восстановить секрет.

Например, вместо:

```text
/run/infra-manager/secrets/pve-api.env
infra-secrets/data/pve/api/infra-manager
```

используется логическое имя:

```text
pve-api-infra-manager
```

Физическое хранение рабочих секретов определено отдельно в `740-openbao.md`.

## 7. Применение правил

`access.yaml` является нормативным машинным входом.

Техническое применение может включать:

```text
access.yaml
→ PVE API ACL / роли
→ Semaphore permissions
→ OpenBao policy / AppRole
→ SSH CA role / principals
→ Git credential
```

Не все эти производные механизмы уже полностью автоматизированы.

Пункт 2 архитектурного плана реализует сам единый контракт, схему и проверку согласованности.

Централизованное применение межмашинного SSH относится к следующему пункту архитектурного плана.

## 8. Переход от старых `management`

Старые поля:

```yaml
management:
  - ssh_identity
  - project_repo_read
```

пока остаются в `guest.yaml` как совместимый вход действующего resolver.

Они больше не должны быть единственным источником требования.

Проверка проекта требует, чтобы каждому старому значению уже соответствовало правило в `access.yaml`.

Окончательное удаление `management` из схем, resolver и гостевых файлов выполняется отдельно после перехода всех потребителей на новый контракт.

## 9. Проверка контракта

Команда:

```bash
python scripts/validate_repo.py
```

проверяет:

- соответствие `access.schema.yaml`;
- уникальность `id`;
- существование гостей, указанных как `guest:<VMID>`;
- допустимость сочетания `service/resource/access`;
- отсутствие путей хранения секретов;
- отсутствие прямого PVE API и root SSH к PVE у `guest:410`;
- соответствие старых `management` новому контракту на переходном этапе.

Отдельная автоматическая проверка:

```bash
python scripts/tests/test-access-contract.py
```

закрепляет принятые правила для 410, 910, 311 и PVE-only OpenBao.
