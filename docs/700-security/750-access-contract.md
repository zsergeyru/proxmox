# Единый контракт доступа

**Тип:** спецификация  
**Статус:** действующий  
**Назначение:** определить правила `access.yaml`: как описываются субъекты, ресурсы, цели и действия, как проверяется контракт и как из него должны строиться технические механизмы доступа.

Этот документ **не перечисляет права конкретных машин**. Фактический набор субъектов и правил находится только в `infrastructure/security/access.yaml`.

## 1. Назначение access.yaml

Файл:

```text
infrastructure/security/access.yaml
```

является единым машинным источником требований доступа.

Он отвечает только на вопросы:

```text
кто является субъектом?
к какому сервису относится право?
какой ресурс используется?
какие цели разрешены?
какие действия разрешены?
```

`access.yaml` задаёт **право**, но не содержит сам secret, ключ, token, пароль, путь установки или способ развёртывания службы.

Документация этого файла определяет правила формата и смысл полей. Она не должна дублировать текущее содержимое `access.yaml`.

## 2. Структура правила

Каждое правило содержит:

| Поле | Назначение |
|---|---|
| `id` | уникальное стабильное имя правила |
| `subject` | субъект, которому требуется право |
| `service` | логическая подсистема |
| `resource` | тип ресурса внутри подсистемы |
| `targets` | допустимые цели |
| `access` | разрешённые действия |

Общий вид:

```yaml
- id: <unique-rule-id>
  subject: <subject>
  service: <service>
  resource: <resource>
  targets:
    - <target>
  access:
    - <action>
```

Правило должно быть декларативным: оно описывает требуемое право, а не последовательность команд по его созданию.

## 3. Типы субъектов и целей

### 3.1. Субъект

Субъект — тот, кому требуется право.

Поддерживаемые типы задаются схемой проекта. Типичные формы:

```text
guest:<VMID>
host:<name>
```

Идентификатор должен однозначно ссылаться на сущность проекта.

Нельзя использовать свободный текст, если он не проверяется схемой и не разрешается однозначно.

### 3.2. Конкретная цель

Конкретная цель указывает один объект:

```text
guest:<VMID>
host:<name>
<repository-name>
<storage-name>
<task-name>
```

Допустимый формат цели зависит от сочетания `service/resource`.

### 3.3. Групповой селектор

Если право относится к группе объектов, используется логический селектор, например:

```text
pool:<name>
project:<group>
self
```

Групповой селектор должен раскрываться в фактический набор целей воспроизводимо и проверяемо.

Изменение состава группы должно приводить к пересчёту производных прав.

### 3.4. `self`

`self` означает самого субъекта правила.

Такой селектор применяется только там, где ресурс действительно связан с собственной идентичностью субъекта.

Он не означает автоматическое право на другие объекты того же типа.

## 4. Правила service, resource и access

`service`, `resource` и `access` образуют единый типизированный контракт.

Не каждое действие допустимо для каждого ресурса.

Примеры логических сочетаний:

```text
pve-api / guests / read|create|configure|power|delete
pve-api / storage / read
ssh / host / connect-root
ssh / identity / issue
ssh / guest / connect-root
github / repository / read|write
semaphore / infrastructure-task / execute
openbao / instance / unseal
openbao / credential / materialize|update
openbao / ssh-ca / configure|sign
```

Фактически разрешённый перечень должен закрепляться схемой `access.schema.yaml` и проверкой репозитория.

Нельзя расширять смысл действия только потому, что используемый технический credential способен на большее.

Например:

```text
read ≠ write
execute одной операции ≠ административный доступ к сервису
connect-root к одной группе целей ≠ root SSH ко всем системам
issue собственной identity ≠ право выпускать identity другим субъектам
```

## 5. Производные механизмы

`access.yaml` задаёт логическое право. Конкретная служба должна построить из него минимально необходимый технический механизм.

### 5.1. API-доступ

Общее правило:

```text
<subject>
 → service/resource/action
 → отдельная техническая identity
 → только требуемые API-возможности
```

Наличие технически более сильной identity не расширяет нормативное право субъекта.

### 5.2. Git

```text
github / repository / read
        ↓
управляемый read-only credential
```

`read` не включает `write`.

Право записи должно задаваться отдельно.

### 5.3. Выполнение операций через сервис-посредник

```text
semaphore / infrastructure-task / execute
        ↓
конкретный разрешённый набор операций
        ↓
исполнение доверенным контуром
```

Такое правило разрешает вызвать операцию через посредника, но не выдаёт субъекту credentials внутренних систем, которыми пользуется посредник.

### 5.4. Межмашинный SSH

Для целевой OpenBao SSH OTP-схемы используются два связанных права одного субъекта.

Первое:

```text
ssh / identity / self / issue
```

создаёт право на собственную машинную идентичность.

Второе:

```text
ssh / guest / <targets> / connect-root
```

задаёт допустимые цели подключения.

Из них строится:

```text
identity/issue
   ↓
отдельный машинный AppRole

connect-root
   ↓
точный набор целей собственной OTP-роли
```

Обязательные правила:

- `connect-root` требует собственного `identity/issue`;
- один субъект не использует AppRole другого субъекта;
- OTP-роль содержит только цели этого субъекта;
- произвольная цель, отсутствующая в контракте, запрещена;
- удалённая цель должна исчезнуть из производной OTP-роли;
- удаление `identity/issue` должно прекращать выдачу новых машинных полномочий.

Машинные SSH-сертификаты, периодическое перевыпускание таких сертификатов и списки машинных principals не являются целевой производной этого контракта.

### 5.5. Административные функции OpenBao

Права управления OpenBao должны разделяться по функции:

```text
разблокировка
материализация credential
обновление отдельного credential
настройка SSH CA
подпись SSH certificate
настройка OTP/AppRole
```

Наличие одного такого права не должно автоматически выдавать остальные.

Например, право подписи сертификата не должно давать право менять политику CA, а право чтения credential — право читать все secrets.

## 6. Связь с другими машинными файлами

Области ответственности разделены:

| Файл | Что описывает |
|---|---|
| `guest.yaml` | объект VM/LXC и его параметры |
| `provision.yaml` | содержимое и службы конкретного гостя |
| `status.yaml` | проверки состояния |
| `access.yaml` | логические права между субъектами и ресурсами |

`guest.yaml` не должен содержать второй список административных прав.

`provision.yaml` может описывать техническую реализацию уже разрешённого механизма, но не является источником решения о выдаче права.

`status.yaml` подтверждает состояние, но не создаёт право.

## 7. Что запрещено хранить

В `access.yaml` запрещены:

- пароли;
- API secrets;
- private keys;
- OpenBao tokens;
- RoleID/SecretID;
- OTP;
- пути к файлам с секретами;
- KV paths;
- конфигурация контейнеров;
- команды установки;
- локальные пути конкретного гостя;
- данные, позволяющие восстановить secret.

Ресурсы и цели задаются логическими именами.

Физическое хранение и доставка secrets описываются профильным сервисом и локальной документацией гостя.

## 8. Изменение и отзыв прав

`access.yaml` является источником не только выдачи, но и отзыва.

Общее правило:

```text
добавили право
→ появился минимальный производный механизм

изменили targets
→ производный набор целей синхронизирован точно

удалили право
→ новые операции по этому праву больше не выдаются
```

Синхронизация не должна только добавлять новые права. Она обязана удалять лишние управляемые производные объекты, которых больше нет в контракте.

Уже завершённое действие или уже установленная сессия не обязаны отменяться задним числом, если это отдельно не предусмотрено механизмом.

Для краткоживущих credentials отзыв означает прежде всего прекращение выдачи новых значений.

## 9. Проверка контракта

Статическая проверка должна подтверждать:

- соответствие `access.schema.yaml`;
- уникальность `id`;
- корректность формата `subject`;
- существование конкретных ссылочных субъектов и целей, если это требуется типом;
- допустимость сочетания `service/resource/access`;
- допустимость типа каждого `target` для данного ресурса;
- отсутствие secrets и физических путей;
- отсутствие второго источника прав в других машинных описаниях;
- наличие `identity/issue` у субъекта, имеющего межмашинный `connect-root`;
- отсутствие противоречивых или неоднозначных правил.

Проверка производных механизмов должна подтверждать:

- производные права не шире `access.yaml`;
- удалённые правила удаляют лишние управляемые механизмы;
- групповые селекторы раскрываются в ожидаемый набор целей;
- каждый машинный субъект получает только собственную identity;
- OTP-роль точно совпадает с разрешёнными целями;
- нельзя использовать чужую машинную роль;
- отсутствуют универсальные обходные роли, расширяющие контракт.

Текущие средства проверки:

```bash
python scripts/validate_repo.py
python scripts/tests/test-access-contract.py
```

Конкретные проверки отдельных машин относятся к тестам и состоянию реализации, а не к этой спецификации правил.
