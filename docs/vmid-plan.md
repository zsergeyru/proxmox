# План VMID / CTID

Функциональная нумерация используется для новых VM/LXC. Номер не определяет порядок запуска.

| Диапазон | Назначение |
|---|---|
| `100–199` | сеть и базовая инфраструктура |
| `200–299` | Home Assistant и автоматика |
| `300–399` | прикладные, DevOps- и AI-сервисы |
| `400–499` | мониторинг и обслуживание |
| `500–599` | видео и камеры |
| `600–699` | временные и экспериментальные VM/LXC |
| `900–999` | legacy-системы |

## Правило VMID и management IP

Для новых VM/LXC целевой VMID/CTID не должен заканчиваться на `0`.

### Новая квартира

Серверы не выделяются в отдельный VLAN и находятся в доверенной MAIN-сети:

```text
MAIN / native
10.0.0.0/16
```

Для обычных инфраструктурных VM/LXC основной статический management IP кодирует VMID напрямую:

```text
VMID XYZ
→ 10.0.X.YZ/16
```

Где:

- `10.0` — MAIN / trusted network;
- `X` — первая цифра трёхзначного VMID;
- `YZ` — последние две цифры VMID как число без ведущего нуля.

Примеры:

```text
201 → 10.0.2.1/16
202 → 10.0.2.2/16
203 → 10.0.2.3/16
211 → 10.0.2.11/16
301 → 10.0.3.1/16
311 → 10.0.3.11/16
321 → 10.0.3.21/16
331 → 10.0.3.31/16
401 → 10.0.4.1/16
501 → 10.0.5.1/16
```

Proxmox host использует отдельный хорошо читаемый management IP, например:

```text
PVE → 10.0.0.10/16
```

Так VMID визуально читается в IP, а Proxmox, VM/LXC и доверенные пользовательские устройства находятся в одной MAIN-сети без отдельного серверного VLAN.

### Исключение: network-gateway

`101-network-gateway` — маршрутизатор между сетями, поэтому его адреса определяются не VMID-формулой, а ролью шлюза.

Целевая схема новой квартиры:

```text
MAIN / native     → 10.0.0.1/16
IOT / VLAN 20     → 10.20.0.1/16
CAMERAS / VLAN 30 → 10.30.0.1/16
REMOTE-VPN        → 10.60.0.1/16
```

При появлении дополнительных изолированных VLAN сохраняется правило `VLAN N → 10.N.0.0/16`, а шлюз обычно получает `10.N.0.1/16`.

Правило VMID → IP относится только к основному management IP обычных VM/LXC в MAIN. Если гостю требуется несколько адресов или сетевых интерфейсов, дополнительные IP выбираются по назначению и отдельно описываются в `guest.yaml`; они не обязаны кодировать VMID.

## Текущая квартира и переходный период

Действующая сеть пока остаётся `192.168.0.0/16`, но будущая `10.0.0.0/16` вводится заранее параллельно на том же MAIN/L2.

Историческое правило текущей сети:

```text
VMID XYZ
→ 192.168.X.YZ/16
```

Будущее постоянное правило:

```text
VMID XYZ
→ 10.0.X.YZ/16
```

Пример переходного состояния:

```text
321-app-services

10.0.3.21/16      → постоянный целевой адрес
192.168.3.21/16   → временный legacy-адрес

default gateway   → 10.0.0.1
```

На Keenetic Hopper в текущей квартире дополнительно к `192.168.1.1/16` планируется адрес `10.0.0.1/16` на домашнем LAN-интерфейсе. Для `10.0.0.0/16` должны быть проверены NAT, доступ в интернет и маршрутизация к текущей `192.168.0.0/16`.

Новые серверы создаются сразу с постоянным `10.0.X.YZ/16` и gateway `10.0.0.1`. Временный `192.168.X.YZ/16` добавляется только при необходимости совместимости.

Уже работающие серверы мигрируют постепенно: сначала получают второй `10.0.x.x`, затем после проверки переводят default gateway на `10.0.0.1`, а старый `192.168.x.x` удаляется только после полного перехода.

Default gateway на сервере должен быть один. Не создавать одновременно обычные default route через `192.168.1.1` и `10.0.0.1`.

При физическом переезде в новую квартиру адрес `10.0.0.1` переходит от Keenetic/старого шлюза к целевому сетевому шлюзу новой квартиры. Поскольку IP серверов и gateway уже постоянные, массово менять сетевые настройки VM/LXC в день переезда не требуется.

Текущая логика физических адресов `192.168.1.x` остаётся действующей на время перехода:

```text
192.168.1.1–192.168.1.9    → роутеры, точки доступа и другая базовая сеть
192.168.1.20–192.168.1.29  → принтеры и подобные стационарные устройства
192.168.1.50–192.168.1.99  → IoT / умный дом и другие устройства со статическим адресом
192.168.1.100–192.168.1.254 → DHCP для обычных клиентских устройств
```

Если VLAN IOT/CAMERAS понадобятся в текущей квартире ещё до полной миграции, они сразу используют будущие непересекающиеся сети:

```text
VLAN 20 → 10.20.0.0/16
VLAN 30 → 10.30.0.0/16
```

Remote-access VPN может сразу использовать `10.60.0.0/16`.

## Текущий целевой план

- `101` — `network-gateway` (VM)
- `201` — `ha-main` (LXC)
- `202` — `ha-test` (LXC)
- `203` — `ha-flat2` (LXC, при необходимости)
- `211` — `automation-services` (LXC)
- `301` — `ai-control` (VM)
- `311` — `dev-services` (LXC)
- `321` — `app-services` (LXC)
- `331` — `ai-services` (LXC)
- `401` — `monitoring` (LXC)
- `411` — резерв под `backup-services`
- `501` — `frigate` (VM/LXC после теста)

Текущая `320-ai-control` рассматривается как временный bootstrap-узел до развёртывания новой `301-ai-control`. После проверки новой управляющей VM старую `320` можно вывести из эксплуатации.

Существующие legacy VM не перенумеровывать только ради унификации.

Общее правило VLAN, подсетей и миграции описано в [`network.md`](network.md).
