# План VMID / CTID

Функциональная нумерация используется для новых VM/LXC. Номер не определяет порядок запуска.

| Диапазон | Назначение |
|---|---|
| `100–199` | сеть и базовая инфраструктура |
| `200–299` | Home Assistant и автоматика |
| `300–399` | прикладные, DevOps- и AI-сервисы |
| `400–499` | мониторинг и обслуживание |
| `500–599` | видео и камеры |
| `600–699` | временные и экспериментальные VM/LXC |
| `900–999` | legacy-системы |

## Правило VMID и management IP

Для новых VM/LXC целевой VMID/CTID не должен заканчиваться на `0`.

### Новая квартира

Целевой серверный сегмент новой квартиры:

```text
VLAN 10
10.10.0.0/16
```

Для обычных инфраструктурных VM/LXC основной статический management IP кодирует VMID напрямую:

```text
VMID XYZ
→ 10.10.X.YZ/16
```

Где:

- `10.10` — серверный VLAN 10;
- `X` — первая цифра трёхзначного VMID;
- `YZ` — последние две цифры VMID как число без ведущего нуля.

Примеры:

```text
201 → 10.10.2.1/16
202 → 10.10.2.2/16
203 → 10.10.2.3/16
211 → 10.10.2.11/16
301 → 10.10.3.1/16
311 → 10.10.3.11/16
321 → 10.10.3.21/16
331 → 10.10.3.31/16
401 → 10.10.4.1/16
501 → 10.10.5.1/16
```

Так VMID визуально читается в IP, а все VM/LXC остаются в одном серверном VLAN 10.

### Исключение: network-gateway

`101-network-gateway` — маршрутизатор между сетями, поэтому его интерфейсные адреса определяются не VMID-формулой, а ролью шлюза.

Целевая схема новой квартиры:

```text
MAIN / native     → 10.0.0.1/16
SERVERS / VLAN 10 → 10.10.0.1/16
IOT / VLAN 20     → 10.20.0.1/16
CAMERAS / VLAN 30 → 10.30.0.1/16
```

При появлении дополнительных VLAN сохраняется правило `VLAN N → 10.N.0.0/16`, а шлюз обычно получает `10.N.0.1/16`.

Правило VMID → IP относится только к **основному management IP** обычных VM/LXC в серверном VLAN. Если гостю требуется несколько адресов или сетевых интерфейсов, дополнительные IP выбираются по назначению и отдельно описываются в `guest.yaml`; они не обязаны кодировать VMID.

## Текущая квартира и переходный период

Действующая сеть пока остаётся `192.168.0.0/16`. Существующие устройства и VM/LXC не требуется перенумеровывать немедленно.

Исторически для инфраструктурных VM/LXC использовалось правило:

```text
VMID XYZ
→ 192.168.X.YZ/16
```

Например:

```text
201 → 192.168.2.1/16
301 → 192.168.3.1/16
321 → 192.168.3.21/16
```

Это правило остаётся допустимым для текущей квартиры до плановой миграции, но **целевой схемой новой квартиры является серверный VLAN 10 и адреса `10.10.X.YZ/16`**.

Текущая логика физических адресов `192.168.1.x`:

```text
192.168.1.1–192.168.1.9    → роутеры, точки доступа и другая базовая сеть
192.168.1.20–192.168.1.29  → принтеры и подобные стационарные устройства
192.168.1.50–192.168.1.99  → IoT / умный дом и другие устройства со статическим адресом
192.168.1.100–192.168.1.254 → DHCP для обычных клиентских устройств
```

Сейчас `192.168.1.1`, `192.168.1.2` и `192.168.1.3` заняты роутерами, `192.168.1.20` — принтером, а часть диапазона `192.168.1.50–60` — умными устройствами.

Основной текущий DHCP-пул:

```text
192.168.1.100–192.168.1.254
```

Если VLAN IOT/CAMERAS понадобятся в текущей квартире ещё до полной миграции, они могут сразу использовать непересекающиеся сети:

```text
VLAN 20 → 10.20.0.0/16
VLAN 30 → 10.30.0.0/16
```

Существующие гости и сетевые устройства не перенумеровываются автоматически только ради нового правила. Новая схема применяется при плановом переразвертывании, переносе в новую квартиру или создании нового гостя в целевой сети.

## Текущий целевой план

- `101` — `network-gateway` (VM)
- `201` — `ha-main` (LXC)
- `202` — `ha-test` (LXC)
- `203` — `ha-flat2` (LXC, при необходимости)
- `211` — `automation-services` (LXC)
- `301` — `ai-control` (VM)
- `311` — `dev-services` (LXC)
- `321` — `app-services` (LXC)
- `331` — `ai-services` (LXC)
- `401` — `monitoring` (LXC)
- `411` — резерв под `backup-services`
- `501` — `frigate` (VM/LXC после теста)

Текущая `320-ai-control` рассматривается как временный bootstrap-узел до развёртывания новой `301-ai-control`. После проверки новой управляющей VM старую `320` можно вывести из эксплуатации.

Существующие legacy VM не перенумеровывать только ради унификации.

Общее правило VLAN и подсетей описано в [`network.md`](network.md).
