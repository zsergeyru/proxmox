# План VMID / CTID

Функциональная нумерация используется для новых VM/LXC. Номер не определяет порядок запуска.

| Диапазон | Назначение |
|---|---|
| `100–199` | сеть и базовая инфраструктура |
| `200–299` | Home Assistant и автоматика |
| `300–399` | прикладные, DevOps- и AI-сервисы |
| `400–499` | мониторинг и обслуживание |
| `500–599` | видео и камеры |
| `600–699` | временные и экспериментальные VM/LXC |
| `900–999` | legacy-системы |

## Правило VMID и основного IP

Для новых VM/LXC целевой VMID/CTID не должен заканчиваться на `0`.

Для инфраструктурных VM/LXC основной статический management IP кодирует VMID напрямую в общей сети `192.168.0.0/16`:

```text
VMID XYZ
→ 192.168.X.YZ/16
```

Где:

- `X` — первая цифра трёхзначного VMID;
- `YZ` — последние две цифры VMID как число без ведущего нуля.

Примеры:

```text
201 → 192.168.2.1/16
202 → 192.168.2.2/16
211 → 192.168.2.11/16
301 → 192.168.3.1/16
311 → 192.168.3.11/16
321 → 192.168.3.21/16
331 → 192.168.3.31/16
401 → 192.168.4.1/16
501 → 192.168.5.1/16
```

Так VMID визуально читается в IP, а отказ от VMID, заканчивающихся на `0`, исключает основные адреса вида `192.168.X.0`.

Правило соответствия VMID относится только к **основному management IP** VM/LXC. Если гостю требуется несколько адресов или сетевых интерфейсов, дополнительные IP выбираются по назначению и отдельно описываются в `guest.yaml`; они не обязаны кодировать VMID.

## Диапазон `192.168.1.x`

Диапазон `192.168.1.x` используется преимущественно для физических сетевых, бытовых и клиентских устройств, а не для общей нумерации серверных VM/LXC.

Текущая логика адресов:

```text
192.168.1.1–192.168.1.9    → роутеры, точки доступа и другая базовая сеть
192.168.1.20–192.168.1.29  → принтеры и подобные стационарные устройства
192.168.1.50–192.168.1.99  → IoT / умный дом и другие устройства со статическим адресом
192.168.1.100–192.168.1.254 → DHCP для обычных клиентских устройств
```

Сейчас `192.168.1.1`, `192.168.1.2` и `192.168.1.3` заняты роутерами, `192.168.1.20` — принтером, а часть диапазона `192.168.1.50–60` — умными устройствами. Эти адреса можно постепенно привести к выбранной схеме без немедленного перенумерования всей сети.

Если в будущем `network-gateway` с VMID `101` станет основным шлюзом, для него естественный целевой адрес по общей логике — `192.168.1.1/16`. До такой миграции существующий основной роутер продолжает использовать этот адрес.

## DHCP

Основной DHCP-пул:

```text
192.168.1.100–192.168.1.254
```

При маске `/16` DHCP-клиенты и инфраструктурные статические адреса находятся в одной локальной сети `192.168.0.0/16`, но визуально разделены по диапазонам.

Существующие гости и сетевые устройства не перенумеровываются автоматически только ради нового правила. Новая схема применяется при плановом переразвертывании или создании нового гостя.

## Текущий целевой план

- `101` — `network-gateway` (VM)
- `201` — `ha-main` (LXC)
- `202` — `ha-test` (LXC)
- `203` — `ha-flat2` (LXC, при необходимости)
- `211` — `automation-services` (LXC)
- `301` — `ai-control` (VM)
- `311` — `dev-services` (LXC)
- `321` — `app-services` (LXC)
- `331` — `ai-services` (LXC)
- `401` — `monitoring` (LXC)
- `411` — резерв под `backup-services`
- `501` — `frigate` (VM/LXC после теста)

Текущая `320-ai-control` рассматривается как временный bootstrap-узел до развёртывания новой `301-ai-control`. После проверки новой управляющей VM старую `320` можно вывести из эксплуатации.

Существующие legacy VM не перенумеровывать только ради унификации.
