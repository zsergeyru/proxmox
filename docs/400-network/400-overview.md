## 1. Назначение сетевого раздела

### 1.1. За что отвечает сетевой контур

Сетевой контур отвечает за передачу трафика между системами, сетями и внешними ресурсами.

К нему относятся:

- адресация;
- DNS;
- маршрутизация;
- VPN;
- сетевые правила;
- связь между сетевыми сегментами;
- выбор сетевого пути для разных видов трафика.

Сетевой раздел описывает общие правила и устройство этой части проекта.

Он не должен повторять параметры конкретных VM/LXC или постоянную конфигурацию самого PVE-хоста.

### 1.2. Что не относится к сетевому разделу

К сетевому разделу не относятся:

- установка и постоянная конфигурация Proxmox VE;
- описание требуемого состояния конкретной VM или LXC;
- настройка приложений внутри гостевых систем;
- полное описание физической кабельной инфраструктуры;
- общая политика безопасности проекта;
- управление учётными записями, ключами и другими средствами доступа.

Если для работы сети используются VM/LXC, они остаются гостевыми системами с точки зрения Proxmox, даже если выполняют специализированные сетевые функции.

## 2. Общая схема сети

### 2.1. Основные участники

В сетевой схеме проекта участвуют:

- физический маршрутизатор Keenetic;
- PVE-хост;
- сетевые мосты Proxmox;
- гостевые VM/LXC;
- отдельная сетевая VM для специализированных сетевых функций;
- внешние DNS-сервисы;
- VPN-подключения;
- локальные клиенты и другие устройства сети.

Упрощённая схема:

```text
локальные устройства
        │
        ▼
     Keenetic
        │
        ▼
   локальная сеть
        │
        ├──────────────► PVE
        │                  │
        │                  ▼
        │               vmbr
        │                  │
        │                  ▼
        │              VM / LXC
        │
        └──────────────► сетевая VM
                           │
                           ├── DNS
                           ├── маршрутизация
                           └── VPN
```

Конкретная схема прохождения трафика зависит от назначения трафика и действующих правил маршрутизации.

### 2.2. Поток трафика

Обычный сетевой запрос может включать несколько этапов:

```text
клиент
→ DNS
→ определение нужного адреса
→ выбор сетевого пути
→ обычный маршрут или VPN
→ внешний или внутренний ресурс
```

DNS и маршрутизация связаны между собой, но выполняют разные задачи.

DNS определяет адрес ресурса и при необходимости помогает отнести его к определённой группе.

Маршрутизация определяет, каким путём должен идти уже сформированный сетевой трафик.

### 2.3. Роль PVE

PVE предоставляет инфраструктуру виртуализации и сетевые подключения для VM/LXC.

В частности, он предоставляет сетевые мосты, через которые гостевые системы подключаются к сети.

PVE не используется как основной центр:

- DNS;
- VPN;
- сложной маршрутизации;
- прикладных сетевых правил.

Это позволяет не смешивать обязанности гипервизора и сетевой инфраструктуры.

## 3. Адресация и подключение систем

### 3.1. Сетевые сегменты

Сеть может содержать несколько логических сегментов с разным назначением.

Сегментация должна использоваться осознанно и только там, где она действительно нужна.

Для каждого сегмента должны быть понятны:

- назначение;
- диапазон адресов;
- шлюз;
- связь с другими сегментами;
- правила прохождения трафика.

Точная структура сегментов описывается в профильной сетевой документации.

### 3.2. Адреса гостевых систем

Гостевые системы получают сетевые параметры в соответствии с общей моделью адресации проекта.

Конкретные параметры VM/LXC, включая индивидуальный IP-адрес, сетевой мост и другие значения, относятся к требуемому состоянию конкретного гостя.

Сетевой раздел определяет общие правила адресации, но не должен дублировать описание полей `guest.yaml`.

### 3.3. Шлюзы и сетевые мосты

Сетевой мост Proxmox связывает виртуальный сетевой интерфейс гостя с соответствующей сетью.

При этом нужно различать:

- сетевой мост PVE;
- IP-адрес гостя;
- шлюз;
- маршрутизатор;
- сетевой сервис внутри отдельной VM.

Эти сущности связаны, но выполняют разные функции.

## 4. DNS

### 4.1. Роль DNS

DNS используется для преобразования доменных имён в IP-адреса.

В проекте DNS также участвует в общей сетевой логике, потому что доменные имена могут использоваться для последующего выбора сетевого пути.

DNS не должен самостоятельно заменять маршрутизацию.

### 4.2. Основной DNS-компонент

Основным DNS-компонентом проекта является SmartDNS.

Он используется как единая точка обработки DNS-запросов и позволяет работать с несколькими вышестоящими DNS-сервисами.

Подробная конфигурация SmartDNS относится к отдельной документации DNS.

### 4.3. Вышестоящие DNS

Проект может использовать несколько внешних DNS-сервисов.

В зависимости от требований могут применяться:

- обычный DNS;
- DNS over HTTPS;
- DNS over TLS;
- разные вышестоящие серверы для разных групп запросов.

Выбор конкретного вышестоящего сервера не должен менять общую модель сети.

### 4.4. Связь DNS с маршрутизацией

Некоторые домены могут относиться к специальным группам, для которых требуется отдельный сетевой путь.

В таком случае DNS помогает определить принадлежность ресурса к нужной группе, а дальнейшее решение принимает механизм маршрутизации.

Таким образом:

```text
DNS
→ определение адреса и группы
→ маршрутизация
→ выбор сетевого пути
```

## 5. Маршрутизация

### 5.1. Основной принцип

Для обычного трафика используется основной сетевой путь.

Для отдельных направлений могут использоваться дополнительные маршруты, включая VPN.

Маршрутизация должна быть предсказуемой и явно описанной.

### 5.2. Выбор маршрута

Выбор пути может зависеть от:

- адреса назначения;
- сетевого сегмента;
- клиента;
- принадлежности ресурса к определённой группе;
- используемого VPN-интерфейса;
- других явно определённых правил.

Не следует создавать несколько независимых механизмов маршрутизации, которые принимают противоречащие друг другу решения.

### 5.3. nftables и policy routing

Для сетевой логики используются:

- `nftables` — для обработки и классификации сетевого трафика;
- policy routing — для выбора маршрута по дополнительным правилам.

Эти механизмы дополняют обычную таблицу маршрутизации.

Подробные таблицы, цепочки, метки и конкретные правила должны находиться в профильной документации маршрутизации, а не в обзорном файле.

### 5.4. Сетевые правила

К сетевым правилам относятся технические правила обработки трафика, например:

- NAT;
- разрешение или ограничение передачи между сетями;
- маркировка трафика;
- направление трафика в нужную таблицу маршрутизации.

Общие требования безопасности не должны смешиваться с техническим описанием маршрутизации.

## 6. VPN

### 6.1. Роль VPN

VPN предоставляет дополнительный сетевой путь.

Сам по себе VPN не определяет, какой трафик должен через него проходить.

Такое решение принимает механизм маршрутизации.

### 6.2. VPN-интерфейсы

Основным рассматриваемым VPN-механизмом является AmneziaWG.

Архитектура должна допускать подключение других VPN-интерфейсов без изменения общей модели маршрутизации.

Каждый VPN-интерфейс рассматривается как один из доступных сетевых выходов.

### 6.3. Связь VPN с маршрутизацией

Общая модель:

```text
трафик
→ проверка правил
→ выбор маршрута
├── обычный выход
└── VPN-интерфейс
```

VPN не должен самостоятельно становиться отдельной системой принятия решений о маршрутизации.

### 6.4. Роль sing-box

`sing-box` используется только там, где требуется прокси или более сложный сценарий исходящего соединения.

Он не является:

- основным DNS-сервером;
- центральным маршрутизатором;
- заменой `nftables`;
- заменой policy routing.

Это позволяет использовать его только для тех задач, где он действительно нужен.

## 7. Роли сетевых компонентов

### 7.1. Keenetic

Keenetic остаётся физическим маршрутизатором локальной сети и точкой связи с внешним подключением.

Часть базовых сетевых функций может оставаться на нём.

При этом специализированная логика DNS, маршрутизации и VPN не должна зависеть исключительно от возможностей Keenetic, если они недостаточны для требований проекта.

### 7.2. Сетевая VM

Отдельная сетевая VM выполняет специализированные сетевые функции.

В ней могут размещаться:

- SmartDNS;
- правила маршрутизации;
- `nftables`;
- policy routing;
- VPN-интерфейсы;
- дополнительные сетевые инструменты.

С точки зрения Proxmox эта система остаётся обычной VM.

Её ресурсы, VMID, диски и сетевые интерфейсы описываются как параметры гостевой системы.

Сетевой раздел описывает только её роль в общей сетевой архитектуре.

### 7.3. Гостевые системы

Обычные VM/LXC используют общую сетевую инфраструктуру.

Они могут иметь собственные прикладные сетевые службы, но не должны самостоятельно менять общие правила сети проекта без отдельного архитектурного решения.

### 7.4. PVE

PVE предоставляет виртуальные сетевые интерфейсы и мосты.

Он не должен становиться местом, где без необходимости размещаются:

- DNS;
- VPN-клиенты;
- прикладные маршруты;
- сложные правила обработки пользовательского трафика.

## 8. Границы ответственности

### 8.1. Граница с PVE

Постоянная конфигурация самого PVE-хоста относится к разделу `200-pve`.

Например, сам факт существования и настройки `vmbr` как объекта PVE относится к документации хоста.

Сетевой раздел описывает, как этот мост используется в общей сетевой модели.

### 8.2. Граница с гостевыми системами

Параметры конкретной VM/LXC относятся к разделу `300-guests`.

К ним относятся, например:

- конкретный IP-адрес гостя;
- выбранный сетевой мост;
- параметры виртуального сетевого интерфейса;
- индивидуальные переопределения сетевых параметров.

Раздел `400-network` определяет общие сетевые правила, которым эти параметры должны соответствовать.

### 8.3. Граница с безопасностью

Сетевой раздел описывает техническое прохождение и обработку трафика.

Будущий раздел безопасности должен описывать:

- требования доступа;
- доверительные границы;
- правила минимальных полномочий;
- требования к защите;
- управление секретами и учётными данными.

Один и тот же механизм, например `nftables`, может технически участвовать в обеих областях, но нормативное требование и его техническая реализация должны быть разделены.

### 8.4. Физическая сеть

Полное описание физической инфраструктуры не является задачей этого раздела.

Сюда не нужно переносить подробные сведения о:

- прокладке кабелей;
- расположении розеток;
- физическом размещении коммутаторов;
- шкафах;
- точках установки оборудования.

При необходимости сетевой раздел может ссылаться на физическую инфраструктуру, но не должен дублировать её описание.
