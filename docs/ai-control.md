# AI Control — архитектурные принципы

`ai-control` — отдельная VM управляющего контура. Целевой VMID — `301`; текущая `320-ai-control` сохраняется как bootstrap до развёртывания и проверки новой VM.

## Назначение

AI-агент должен уметь администрировать домашнюю инфраструктуру, а не только собственный контейнер.

Базовое разделение ответственности:

```text
Proxmox MCP
→ создание и жизненный цикл VM/LXC, ресурсы, start/stop/reboot, snapshots и backups

SSH
→ всё внутри гостевых ОС: пакеты, файлы, systemd, Docker/Compose, приложения и диагностика

специализированные MCP/API
→ используются там, где дают реальное преимущество над SSH или прямым API
```

Отдельный универсальный `deploy-mcp` не является частью целевой архитектуры. Docker на `ai-control` и других управляемых гостях обслуживается через SSH и обычные Docker/Docker Compose команды.

Принятое решение подробно зафиксировано в [`../guests/320-ai-control/decisions/001-simple-management-model.md`](../guests/320-ai-control/decisions/001-simple-management-model.md).

## Размещение компонентов

В `ai-control` находятся только компоненты управляющего контура:

- Hermes и другие AI-агенты;
- Proxmox MCP и другие специализированные MCP;
- SSH/Git/Ansible/API-клиенты;
- web/voice интерфейсы к агентам;
- служебный код, относящийся непосредственно к управлению инфраструктурой.

Общие сервисы не должны жить внутри `ai-control` только потому, что ими пользуется Hermes:

- STT/TTS → `331-ai-services`;
- DNS/VPN/PBR → `101-network-gateway`;
- MQTT/Zigbee2MQTT/ESPHome → `211-automation-services`;
- Git/CI → `311-dev-services`;
- Homarr и обычные приложения → `321-app-services`;
- monitoring → `401-monitoring`;
- Frigate → `501-frigate`.

## Файлы и Git

Конфигурация самого гостя описывается его `guest.yaml`. Всё, что должно находиться внутри гостевой ОС, хранится под `rootfs/` по реальному абсолютному пути.

`ai-control` не хранит копии `rootfs/` других VM/LXC. При управлении другим гостем агент читает соответствующий каталог из monorepo и синхронизирует только его содержимое.

## Права и модель защиты

Агенту предоставляются достаточные административные права для поставленных задач. Не строится отдельная песочница для каждого типа операции только ради дополнительного слоя абстракции.

Основная защита:

1. Git — источник истины для повторяемой конфигурации и кода.
2. Proxmox snapshots перед рискованными изменениями.
3. Регулярные Proxmox backups.
4. Отдельный backup persistent data и Docker volumes.
5. Резервная копия критичных файлов перед изменением, если это требуется.
6. Логирование действий агента.
7. Проверка health/status/logs после изменений.
8. Поэтапная замена: сначала создать/проверить новое, затем удалять старое.

Секреты, приватные SSH-ключи, пароли и API tokens в Git не хранятся.

## Текущий bootstrap и переход на 301

`320-ai-control` используется для отработки Hermes, MCP, SSH-доступа и модели управления. Это не причина сохранять VMID 320 как целевой.

Переход выполняется поэтапно:

```text
320 bootstrap работает
→ создаётся 301-ai-control
→ переносится воспроизводимая конфигурация из Git
→ проверяются Proxmox MCP, SSH и управление гостями
→ 301 становится основным control plane
→ 320 выводится из эксплуатации отдельным решением
```

До завершения миграции документация `guests/320-ai-control/` остаётся актуальной для фактически работающего bootstrap-узла.
