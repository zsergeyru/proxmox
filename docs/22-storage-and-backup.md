# Storage и резервное копирование

## Принципы

- snapshot не заменяет backup;
- Git хранит конфигурацию и код без секретов, но не persistent data;
- backup должен храниться минимум на двух независимых носителях/узлах;
- критичные backup проверяются восстановлением, а не только фактом успешного создания;
- storage Frigate и backup не смешиваются без явного контроля retention и свободного места;
- backup с private keys и другими секретами считается чувствительным объектом.

## Текущая схема

На ближайшем этапе:

```text
Proxmox
├── SMB/CIFS → отдельный обычный компьютер — основная внешняя копия
└── USB storage `backup`               — дополнительная локальная копия
```

NAS и Proxmox Backup Server пока не вводятся. К PBS можно вернуться, когда появится практическая потребность в дедупликации, централизованном retention и расширенной проверке backup.

## Базовая backup-политика

### Критичные гости

К критичным относятся как минимум production Home Assistant, network/control-plane после их ввода в production и другие сервисы, потеря которых заметно нарушает работу дома.

Цель:

```text
backup frequency: daily
retention:        7 daily + 4 weekly
RPO target:       до 24 часов
restore test:     не реже 1 раза в 3 месяца
```

### Некритичные/легко воспроизводимые гости

Для dev/test/простых сервисов:

```text
backup frequency: 2–3 раза в неделю
retention:        4–7 последних копий
```

Если гость полностью воспроизводим из template + Git + Ansible и не содержит persistent data, частоту можно уменьшить.

## RPO и RTO

Для каждого реально критичного сервиса при его вводе в production нужно определить:

- **RPO** — сколько данных допустимо потерять;
- **RTO** — за какое время сервис должен быть восстановлен;
- какие persistent data нужны дополнительно к backup VM/LXC.

Для текущего этапа базовый ориентир критичных домашних сервисов:

```text
RPO ≤ 24 часа
RTO ≤ несколько часов при доступном backup и исправном PVE
```

Если конкретный сервис требует меньшего RPO, его данные резервируются отдельным механизмом чаще, чем полный backup VM.

## Restore verification

Успешный job backup не считается достаточным доказательством восстановления.

Не реже одного раза в три месяца для критичных систем выполняется практический restore-test:

1. выбрать актуальную backup-копию;
2. восстановить её во временный VMID/изолированную среду;
3. проверить загрузку и целостность ключевого сервиса;
4. зафиксировать результат и время восстановления;
5. удалить тестовый объект после проверки.

После крупных изменений storage/backup-схемы restore-test выполняется вне очереди.

## Persistent data

Отдельно от Git и при необходимости отдельно от полного VM backup сохраняются:

- Home Assistant backup/конфигурация;
- Docker volumes и базы данных;
- Git-сервисы и пользовательские репозитории;
- данные приложений;
- конфигурации, которые не входят в `rootfs/`;
- при необходимости записи/метаданные Frigate согласно собственной retention-политике.

## SMB/CIFS storage

Для внешнего компьютера:

- стабильный IP;
- отдельная папка Proxmox backup;
- отдельная учётная запись с минимальными достаточными правами;
- компьютер доступен во время расписания backup;
- периодически контролируется свободное место.

## USB storage

Текущий USB storage остаётся второй копией и аварийным вариантом. До признания его надёжной частью схемы обязательно проверить automount после reboot PVE и реальное восстановление хотя бы одной тестовой VM.

## Аварийное восстановление Proxmox

Сценарий рассчитан на полную потерю системного диска PVE.

Сам Proxmox не требуется сохранять как полный образ диска. Базовый способ восстановления:

```text
чистая установка Proxmox
→ восстановление основных настроек хоста
→ восстановление постоянных infrastructure credentials
→ повторный private Stage 1/bootstrap
→ подключение хранилищ резервных копий
→ восстановление критичных VM/LXC
→ восстановление остальных гостей
→ проверка сервисов и резервного копирования
```

### Что нужно сохранять с PVE

Отдельно от резервных копий гостей должны сохраняться данные, которые нельзя просто получить заново из Git или безопасно восстановить скриптами:

- `/etc/network/interfaces`;
- `/etc/hosts` и `/etc/hostname`;
- настройки хранилищ Proxmox;
- настройки пользователей, ролей и прав;
- сведения о подключённых дисках и хранилищах;
- проектные SSH-ключи, API-токены и другие секреты, если они используются на хосте;
- перечень дополнительных пакетов и значимых ручных настроек PVE.

Особенно важны постоянные host-side credentials:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
/etc/proxmox-deployer/ssh/pve_guest_ed25519
/etc/proxmox-deployer/secrets/host-deploy.token
/etc/proxmox-deployer/secrets/ai-agent-infra.token
```

`pve_guest_ed25519` нельзя считать просто пересоздаваемым ключом. Его public half может уже находиться в `authorized_keys` существующих VM/LXC. Поэтому потеря private half при сохранённых гостях требует осознанной recovery/rotation процедуры, а не автоматической генерации новой пары.

GitHub Deploy Key также является постоянным credential после handoff. При его потере потребуется зарегистрировать новый Deploy Key на GitHub и выполнить явное восстановление canonical credential.

Секреты и резервные копии, содержащие их, должны храниться как чувствительные данные и не должны попадать в Git.

### Что не нужно дублировать в резервной копии

Конфигурация и программы, которые полностью воспроизводятся из `zsergeyru/proxmox` и скриптов проекта, должны восстанавливаться из Git, а не храниться как отдельная уникальная копия.

Цель — уменьшить количество ручных и невоспроизводимых настроек самого PVE, не смешивая при этом воспроизводимый код с невоспроизводимыми credentials.

### Конфигурация `/etc/pve`

`/etc/pve` — специальная файловая система конфигурации Proxmox. Не следует рассчитывать на простое копирование всего каталога обратно поверх новой установки.

Нужные настройки должны либо:

- восстанавливаться штатными средствами Proxmox;
- либо создаваться повторно нашим bootstrap-скриптом;
- либо восстанавливаться из заранее сохранённых конкретных конфигурационных данных.

### Порядок восстановления

При полной потере системного диска:

1. установить чистый Proxmox VE;
2. вернуть имя хоста, сеть и доступ к панели управления;
3. восстановить permanent infrastructure credentials, которые нельзя безопасно пересоздать без ротации;
4. запустить canonical Stage 0/Stage 1 и вернуть воспроизводимую host-конфигурацию;
5. подключить локальные и внешние хранилища;
6. проверить доступ к внешним резервным копиям;
7. восстановить критичные VM/LXC;
8. после проверки критичных сервисов восстановить остальные гости;
9. проверить сеть, основные сервисы и работу нового резервного копирования.

Если старый `pve_guest_ed25519` восстановить невозможно, его ротация выполняется как отдельная операция с обновлением public key на нужных гостях.

### Проверка восстановления PVE

После реализации нового `init-pve.sh` нужно хотя бы один раз выполнить учебное восстановление:

```text
чистый PVE
→ восстановить infrastructure credentials
→ init-pve.sh
→ хранилища доступны
→ резервные копии видны
→ тестовая VM/LXC успешно восстановлена и запущена
→ host-side SSH к тестовому managed guest работает ожидаемым credential
```

Такой тест подтверждает не только наличие резервных копий, но и возможность реально восстановить инфраструктуру после потери хоста.
