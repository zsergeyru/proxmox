# Хранилища и резервное копирование

**Тип:** Политика  
**Статус:** Действующий  
**Основной источник:** Да — для правил хранения, резервного копирования, сроков хранения копий, RPO/RTO и требований к восстановлению.

Этот документ отвечает на вопрос **«что и с какими гарантиями мы резервируем»**. Пошаговые процедуры восстановления находятся в [`27-backup-and-disaster-recovery-runbook.md`](27-backup-and-disaster-recovery-runbook.md).

## 1. Основные принципы

- снимок состояния не заменяет резервную копию;
- Git хранит воспроизводимую конфигурацию и код, но не заменяет резервное копирование постоянных данных;
- критичные данные должны иметь минимум две независимые резервные копии или два независимых места хранения;
- успешное выполнение задания резервного копирования не считается достаточной гарантией без периодической проверки восстановления;
- резервная копия, содержащая закрытые ключи, токены или другие секреты, считается чувствительным объектом;
- хранилище видеонаблюдения и резервные копии не должны конкурировать за место без явно заданных сроков хранения и ограничений по объёму;
- то, что полностью воспроизводится из Git, первичной настройки и Ansible, не должно становиться уникальным невоспроизводимым содержимым резервной копии.

## 2. Текущая схема хранения

На текущем этапе:

```text
Proxmox
├── SMB/CIFS → отдельный компьютер — основная внешняя резервная копия
└── USB-хранилище `backup`      — дополнительная локальная копия
```

NAS и Proxmox Backup Server пока не являются обязательной частью архитектуры. PBS имеет смысл вводить, когда появится практическая потребность в дедупликации, централизованном управлении сроками хранения, инкрементальном копировании или расширенной проверке резервных копий.

Фактическое состояние подключённых хранилищ находится в [`../host/pve/storage/README.md`](../host/pve/storage/README.md) и [`../host/pve/backup/README.md`](../host/pve/backup/README.md).

## 3. Классы резервного копирования

### Критичные гостевые системы

К критичным относятся рабочий Home Assistant, сетевой и управляющий контуры после ввода в постоянную эксплуатацию и другие сервисы, потеря которых заметно нарушает работу дома.

Базовая цель:

```text
частота:                 ежедневно
срок хранения:           7 ежедневных + 4 еженедельных копии
целевой RPO:              <= 24 часов
проверка восстановления: не реже 1 раза в 3 месяца
```

### Некритичные и легко воспроизводимые гостевые системы

Для разработки, тестов и простых сервисов:

```text
частота:        2–3 раза в неделю
срок хранения:  4–7 последних копий
```

Если гостевая система полностью воспроизводится из шаблона, Git и Ansible и не содержит уникального постоянного состояния, частоту можно уменьшить.

## 4. RPO и RTO

Для каждого сервиса, введённого в постоянную эксплуатацию, должны быть определены:

- **RPO** — какой объём последних изменений допустимо потерять;
- **RTO** — за какое время сервис должен быть восстановлен;
- какие данные требуют отдельного резервного копирования на уровне приложения помимо полной копии VM/LXC.

Базовый ориентир для критичных домашних сервисов:

```text
RPO <= 24 часа
RTO <= несколько часов при доступной резервной копии и исправном PVE
```

Если сервис требует меньшего RPO, его постоянные данные резервируются чаще отдельным механизмом.

## 5. Какие данные считаются постоянными

Отдельного внимания требуют:

- резервные копии и конфигурация Home Assistant;
- тома Docker и базы данных;
- Git-репозитории и их служебные данные;
- состояние приложений;
- конфигурация и данные, которые нельзя воспроизвести из Git;
- при необходимости записи и метаданные Frigate согласно отдельным правилам хранения.

Размещение постоянных данных внутри Linux-гостей определяется [`34-linux-filesystem-layout.md`](34-linux-filesystem-layout.md).

## 6. Инфраструктурные учётные данные

Постоянные учётные данные PVE нельзя считать обычными пересоздаваемыми файлами.

К чувствительным объектам относятся как минимум:

```text
/etc/proxmox-deployer/ssh/github_proxmox_repo_ed25519
/etc/proxmox-deployer/ssh/pve_guest_ed25519
/etc/proxmox-deployer/secrets/host-deploy.token
/etc/proxmox-deployer/secrets/ai-agent-infra.token
```

`github_proxmox_repo_ed25519` — мастер-копия одного общего GitHub Deploy Key только для чтения `zsergeyru/proxmox`. Она хранится root-only на PVE. Гости с принятым `access.project_repo_read: true` после реализации этого интерфейса могут содержать локальную копию того же read-only credential; поэтому резервная копия такого гостя также считается чувствительной.

Локальная копия общего Git read-key в госте считается воспроизводимой из защищённой PVE мастер-копии. Она не заменяет резервирование мастер-копии на PVE.

Все перечисленные инфраструктурные секреты должны иметь защищённую внешнюю резервную копию с шифрованием и контролем доступа.

Особенно важен `pve_guest_ed25519`: его открытая часть уже может быть установлена на существующих VM/LXC. Потеря закрытой части требует отдельной процедуры восстановления или смены ключа, а не тихой генерации новой пары.

Общие правила работы с учётными данными определены в [`23-security.md`](23-security.md).

## 7. Внешнее хранилище SMB/CIFS

Для внешнего SMB/CIFS-хранилища требуется:

- стабильная доступность во время запланированного резервного копирования;
- отдельная учётная запись с минимально необходимыми правами;
- контроль свободного места;
- независимость от системного диска PVE;
- практическая проверка восстановления.

## 8. USB-хранилище резервных копий

USB-хранилище используется как дополнительная локальная копия и аварийный вариант.

До признания его надёжной частью системы должны быть подтверждены:

- автоматическое подключение после перезагрузки PVE;
- стабильное сопоставление устройства и хранилища;
- успешное создание резервной копии;
- успешное восстановление хотя бы одной тестовой гостевой системы.

## 9. Правила проверки восстановления

Для критичных систем проверка восстановления обязательна не реже одного раза в три месяца.

Также внеочередная проверка выполняется после существенных изменений:

- структуры хранилищ;
- средств резервного копирования;
- шифрования или работы с учётными данными;
- процедуры восстановления;
- перехода на новое хранилище или средство резервного копирования.

Пошаговая процедура описана в [`27-backup-and-disaster-recovery-runbook.md`](27-backup-and-disaster-recovery-runbook.md).

## 10. Полная потеря PVE-хоста

Проект не требует хранить полный уникальный образ системного диска PVE как единственный способ восстановления.

Целевая модель:

```text
чистый Proxmox
→ восстановить невоспроизводимые инфраструктурные учётные данные
→ повторно применить проектную первичную настройку и конфигурацию
→ подключить хранилища резервных копий
→ восстановить критичные гостевые системы
→ восстановить остальные гостевые системы
→ проверить результат
```

Конфигурация хоста, которую можно безопасно воспроизвести средствами проекта, должна восстанавливаться из Git и скриптов настройки. Невоспроизводимые учётные данные и данные сервисов резервируются отдельно.

`/etc/pve` не рассматривается как каталог, который нужно просто побайтно копировать обратно поверх новой установки. Конфигурация восстанавливается штатными средствами Proxmox и автоматикой проекта.

## 11. Что должно быть проверяемым

Политика резервного копирования считается реализованной только если можно подтвердить:

```text
задания резервного копирования выполняются
сроки хранения соблюдаются
свободное место контролируется
внешняя копия доступна
критичные учётные данные имеют защищённую внешнюю копию
проверка восстановления фактически выполнялась
результат проверки восстановления зафиксирован
```

Текущее фактическое состояние инфраструктуры резервного копирования хранится в `host/pve/`, а не в этом документе.
