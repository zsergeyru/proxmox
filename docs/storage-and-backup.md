# Storage и резервное копирование

## Принципы

- snapshot не заменяет backup;
- Git хранит конфигурацию и код без секретов, но не persistent data;
- backup должен храниться минимум на двух независимых носителях/узлах;
- критичные backup проверяются восстановлением, а не только фактом успешного создания;
- storage Frigate и backup не смешиваются без явного контроля retention и свободного места;
- backup с private keys и другими секретами считается чувствительным объектом.

## Текущая схема

На ближайшем этапе:

```text
Proxmox
├── SMB/CIFS → отдельный обычный компьютер — основная внешняя копия
└── USB storage `backup`               — дополнительная локальная копия
```

NAS и Proxmox Backup Server пока не вводятся. К PBS можно вернуться, когда появится практическая потребность в дедупликации, централизованном retention и расширенной проверке backup.

## Базовая backup-политика

### Критичные гости

К критичным относятся как минимум production Home Assistant, network/control-plane после их ввода в production и другие сервисы, потеря которых заметно нарушает работу дома.

Цель:

```text
backup frequency: daily
retention:        7 daily + 4 weekly
RPO target:       до 24 часов
restore test:     не реже 1 раза в 3 месяца
```

### Некритичные/легко воспроизводимые гости

Для dev/test/простых сервисов:

```text
backup frequency: 2–3 раза в неделю
retention:        4–7 последних копий
```

Если гость полностью воспроизводим из template + Git + Ansible и не содержит persistent data, частоту можно уменьшить.

## RPO и RTO

Для каждого реально критичного сервиса при его вводе в production нужно определить:

- **RPO** — сколько данных допустимо потерять;
- **RTO** — за какое время сервис должен быть восстановлен;
- какие persistent data нужны дополнительно к backup VM/LXC.

Для текущего этапа базовый ориентир критичных домашних сервисов:

```text
RPO ≤ 24 часа
RTO ≤ несколько часов при доступном backup и исправном PVE
```

Если конкретный сервис требует меньшего RPO, его данные резервируются отдельным механизмом чаще, чем полный backup VM.

## Restore verification

Успешный job backup не считается достаточным доказательством восстановления.

Не реже одного раза в три месяца для критичных систем выполняется практический restore-test:

1. выбрать актуальную backup-копию;
2. восстановить её во временный VMID/изолированную среду;
3. проверить загрузку и целостность ключевого сервиса;
4. зафиксировать результат и время восстановления;
5. удалить тестовый объект после проверки.

После крупных изменений storage/backup-схемы restore-test выполняется вне очереди.

## Persistent data

Отдельно от Git и при необходимости отдельно от полного VM backup сохраняются:

- Home Assistant backup/конфигурация;
- Docker volumes и базы данных;
- Git-сервисы и пользовательские репозитории;
- данные приложений;
- конфигурации, которые не входят в `rootfs/`;
- при необходимости записи/метаданные Frigate согласно собственной retention-политике.

## SMB/CIFS storage

Для внешнего компьютера:

- стабильный IP;
- отдельная папка Proxmox backup;
- отдельная учётная запись с минимальными достаточными правами;
- компьютер доступен во время расписания backup;
- периодически контролируется свободное место.

## USB storage

Текущий USB storage остаётся второй копией и аварийным вариантом. До признания его надёжной частью схемы обязательно проверить automount после reboot PVE и реальное восстановление хотя бы одной тестовой VM.
