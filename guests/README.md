# Guests

Каждый каталог соответствует одной целевой VM/LXC и собирает в одном месте её документацию и все файлы, которые должны быть развернуты на этом госте.

Правило именования:

```text
<VMID>-<name>/
```

Базовая структура:

```text
<VMID>-<name>/
├── README.md
├── guest.yaml
├── decisions/        # при необходимости
├── STATUS.md         # при необходимости
└── rootfs/
```

Назначение элементов:

- `README.md` — назначение, ресурсы, зависимости, структура и особенности гостя;
- `guest.yaml` — декларативное описание гостя и параметры его создания/развёртывания после утверждения формата;
- `decisions/` — журнал важных архитектурных решений по этому гостю, если он нужен;
- `STATUS.md` — состояние длинной работы или миграции, если требуется;
- `rootfs/` — дерево файлов, которое соответствует корневой файловой системе VM/LXC.

## Правило `rootfs/`

`rootfs/` является зеркалом корневой файловой системы гостя. Всё, что находится после `rootfs/`, разворачивается относительно `/` на VM/LXC.

Например:

```text
guests/100-network-gateway/rootfs/etc/nftables.conf
```

на целевой системе становится:

```text
/etc/nftables.conf
```

Тот же принцип применяется к приложениям и собственному коду. Например:

```text
guests/320-ai-control/rootfs/opt/ai-control/agents/hermes/
```

соответствует:

```text
/opt/ai-control/agents/hermes/
```

Отдельного каталога `services/` нет. Код приложения, Dockerfile, Compose-файлы, MCP, агенты, скрипты и системные конфиги — всё хранится внутри `rootfs/` по тому пути, где должно находиться на гостевой системе.

Сам Git-репозиторий целиком на гостя копировать не требуется. Агент должен брать только каталог конкретного гостя и по SSH синхронизировать нужное содержимое `rootfs/` с `/` на целевой системе.

Не требуется автоматически создавать отдельный Git-репозиторий для каждого MCP, скрипта или внутреннего приложения. Отдельный репозиторий создаётся только при реальной причине: компонент используется несколькими независимыми проектами, выпускается и версионируется отдельно, публикуется как самостоятельный продукт или должен развиваться независимо от Proxmox-инфраструктуры.

## Управление VM/LXC

Для управления инфраструктурой принято простое разделение уровней:

```text
Proxmox MCP
→ создание и жизненный цикл VM/LXC

SSH
→ всё внутри гостевой операционной системы
```

Через Proxmox MCP выполняются операции уровня виртуализации: создание VM/LXC, CPU, RAM, диски, сеть, start/stop/reboot, snapshots и backups.

SSH является основным универсальным каналом для настройки гостевых систем, включая `320-ai-control`: установка пакетов, изменение файлов, управление `systemd`, установка Docker, Docker Compose и развёртывание приложений.

Не требуется отдельный deploy-агент или deploy-MCP на каждом госте. Специализированный инструмент добавляется только тогда, когда решает отдельную задачу и даёт реальное преимущество перед SSH.

Агент может полностью выполнить цепочку:

```text
создать VM через Proxmox MCP
→ подключиться по SSH
→ подготовить ОС
→ синхронизировать нужное содержимое rootfs/
→ установить/запустить приложения
→ проверить состояние
```

Защита строится прежде всего на восстанавливаемости: Git, Proxmox snapshots, backups, резервировании persistent data, логировании и проверке результата изменений.

Подробное решение для AI-control зафиксировано в:

```text
guests/320-ai-control/decisions/001-simple-management-model.md
```

## Общие правила

- `proxmox` является основным monorepo инфраструктуры;
- общие Ansible playbook/roles не дублировать по гостям — они хранятся в `/ansible`;
- Ansible не является обязательным механизмом управления: при необходимости он используется поверх SSH для повторяемых процедур;
- общие шаблоны хранятся в `/templates`;
- не создавать фиктивные `compose.yaml`: файл появляется только вместе с реальной конфигурацией;
- секреты, токены, пароли и приватные ключи в Git не добавлять.
