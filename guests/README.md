# Guests

Каждый каталог соответствует одной целевой VM/LXC и собирает в одном месте её документацию, конфигурацию и код сервисов, относящихся к этому гостю.

Правило именования:

```text
<VMID>-<name>/
```

Рекомендуемая структура:

```text
<VMID>-<name>/
├── README.md
├── guest.yaml
├── files/
└── services/
```

Назначение элементов:

- `README.md` — назначение, ресурсы, зависимости и статус гостя;
- `guest.yaml` — описание гостя и правила deploy после утверждения формата;
- `files/` — файлы, которые разворачиваются в системные пути VM/LXC;
- `services/` — собственный программный код, Dockerfile, зависимости, тесты и прочие файлы сервисов, относящихся к этому гостю;
- `STATUS.md` — при необходимости состояние длинной работы или миграции.

## Правило `files/`

Структура внутри `files/` повторяет целевой абсолютный путь на гостевой системе.

Например:

```text
guests/100-network-gateway/files/etc/nftables.conf
```

при deploy должен стать:

```text
/etc/nftables.conf
```

Сам Git-репозиторий целиком на гостя для этого копировать не требуется. Deploy-инструмент должен брать только относящееся к выбранному гостю содержимое.

## Правило `services/`

Если собственная программа или вспомогательный сервис относится только к конкретному гостю или к данной домашней инфраструктуре, его код по умолчанию хранится прямо в этом monorepo.

Пример:

```text
guests/320-ai-control/services/deploy-mcp/
├── Dockerfile
├── requirements.txt
├── src/
└── tests/
```

Не требуется автоматически создавать отдельный Git-репозиторий для каждого MCP, скрипта или внутреннего сервиса.

Отдельный репозиторий создаётся только при наличии реальной причины: компонент используется несколькими независимыми проектами, выпускается и версионируется отдельно, публикуется как самостоятельный продукт или должен развиваться независимо от Proxmox-инфраструктуры.

## Управление VM/LXC

Для управления инфраструктурой принято простое разделение уровней:

```text
Proxmox MCP
→ создание и жизненный цикл VM/LXC

SSH
→ всё внутри гостевой операционной системы
```

Через Proxmox MCP выполняются операции уровня виртуализации: создание VM/LXC, CPU, RAM, диски, сеть, start/stop/reboot, snapshots и backups.

SSH является основным универсальным каналом для настройки гостевых систем, включая `320-ai-control`: установка пакетов, изменение конфигурации, управление `systemd`, установка Docker, Docker Compose и развертывание контейнеров.

Не требуется отдельный deploy-агент или MCP на каждом госте только ради выполнения этих операций. Специализированный инструмент добавляется только тогда, когда он решает реальную отдельную задачу и даёт преимущество перед SSH.

Агент может полностью выполнить цепочку:

```text
создать VM через Proxmox MCP
→ подключиться по SSH
→ подготовить ОС
→ установить Docker
→ развернуть сервис
→ проверить состояние
```

Защита строится прежде всего на восстанавливаемости: Git, Proxmox snapshots, backups, резервировании persistent data, логировании и проверке результата изменений.

Подробное решение для AI-control зафиксировано в:

```text
guests/320-ai-control/decisions/001-simple-management-model.md
```

## Общие правила

- `proxmox` является основным monorepo инфраструктуры;
- общие Ansible playbook/roles не дублировать по гостям — они хранятся в `/ansible`;
- Ansible не является обязательным механизмом управления: при необходимости он используется поверх SSH для повторяемых процедур;
- общие шаблоны хранятся в `/templates`;
- не создавать фиктивные `compose.yaml`: файл появляется только вместе с реальной конфигурацией;
- секреты, токены и пароли в Git не добавлять.
