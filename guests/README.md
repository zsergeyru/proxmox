# Guests

Каждый каталог соответствует одной VM/LXC и собирает в одном месте её документацию, машинно-читаемый паспорт и файлы, которые должны быть развернуты на этом госте.

Правило именования:

```text
<VMID>-<name>/
```

Актуальная целевая нумерация определяется только [`../docs/vmid-plan.md`](../docs/vmid-plan.md).

## Базовая структура

```text
<VMID>-<name>/
├── README.md
├── guest.yaml
├── decisions/        # при необходимости
├── STATUS.md         # при необходимости
└── rootfs/
```

- `README.md` — назначение, зависимости и особенности гостя;
- `guest.yaml` — машинно-читаемый паспорт VM/LXC и желаемые параметры в Proxmox;
- `decisions/` — ADR конкретного гостя;
- `STATUS.md` — временное состояние длинной работы или миграции;
- `rootfs/` — дерево файлов, соответствующее корневой файловой системе гостя.

Формат `guest.yaml` утверждён как schema version 1.

## `guest.yaml`

`guest.yaml` описывает сам объект VM/LXC в Proxmox, но не содержимое его ОС.

```text
guest.yaml
→ VMID, имя, тип, состояние, ресурсы, сеть, автозапуск, способ управления

rootfs/
→ /etc, /opt, приложения, Compose, конфиги и собственный код внутри гостя
```

### Минимальный формат

```yaml
schema_version: 1
vmid: 101
name: network-gateway
type: vm
state: planned
```

Обязательные поля:

- `schema_version` — версия схемы, сейчас `1`;
- `vmid` — VMID/CTID; должен совпадать с номером каталога;
- `name` — имя гостя; должно совпадать с именем в каталоге;
- `type` — `vm` или `lxc`;
- `state` — жизненный цикл гостя: `planned`, `active`, `bootstrap` или `legacy`.

### Состояние гостя

```text
planned   → целевой объект запланирован, но ещё не считается рабочим
active    → рабочий целевой объект
bootstrap → временный рабочий объект, используемый для развёртывания/миграции
legacy    → существующий старый объект, сохраняемый до планового вывода или миграции
```

Изменение `state` должно отражать реальное состояние инфраструктуры. Нельзя переводить объект в `active` только потому, что его каталог и `guest.yaml` уже созданы в Git.

Допустимые дополнительные поля добавляются только тогда, когда ими реально нужно управлять.

Пример расширенного описания:

```yaml
schema_version: 1
vmid: 101
name: network-gateway
type: vm
state: planned
node: pve

description: Network gateway, DNS, VPN and policy routing

resources:
  cpu:
    cores: 2
  memory_mb: 2048
  disk:
    size_gb: 16
    storage: local-lvm

network:
  bridge: vmbr0
  ipv4:
    method: dhcp

boot:
  onboot: true

management:
  ssh:
    user: infra-agent
    port: 22
```

Значения в примере демонстрируют формат. Фактические параметры каждого гостя задаются только в его собственном `guest.yaml`.

### Ресурсы

При необходимости используются поля:

```yaml
resources:
  cpu:
    cores: 4
    type: host
  memory_mb: 8192
  ballooning_mb: 4096
  disk:
    size_gb: 64
    storage: local-lvm
    discard: true
```

Не следует копировать все значения Proxmox по умолчанию. В `guest.yaml` фиксируются параметры, важные для воспроизводимого создания или сознательно контролируемые проектом.

### Сеть

Простой вариант с DHCP:

```yaml
network:
  bridge: vmbr0
  ipv4:
    method: dhcp
```

Целевой статический адрес обычного сервера в MAIN новой квартиры:

```yaml
network:
  bridge: vmbr0
  ipv4:
    method: static
    address: 10.0.3.21/16
    gateway: 10.0.0.1
```

VLAN при необходимости, например IOT / VLAN 20:

```yaml
network:
  bridge: vmbr0
  vlan: 20
  ipv4:
    method: static
    address: 10.20.2.11/16
    gateway: 10.20.0.1
```

Адреса `192.168.x.x` **не считаются ошибкой и пока не запрещены**. Текущая квартира продолжает использовать `192.168.0.0/16`, а во время миграции сервер может одновременно иметь постоянный будущий адрес `10.0.x.x/16` и временный legacy-адрес `192.168.x.x/16`. Целевая адресация новой квартиры — `10.x.x.x`; подробная переходная схема описана в [`../docs/network.md`](../docs/network.md).

Если гостю потребуется несколько интерфейсов или несколько адресов, схема может быть расширена только при появлении реального сценария.

### Автозапуск

```yaml
boot:
  onboot: true
```

Startup order не выводится из VMID и задаётся отдельно при необходимости.

### Управление

```yaml
management:
  ssh:
    user: infra-agent
    port: 22
```

SSH является базовым каналом доступа внутрь управляемых Linux-гостей и транспортом для Ansible.

Приватные SSH-ключи, пароли и токены в `guest.yaml` не хранятся.

### ОС и источник создания

При автоматическом создании можно добавить:

```yaml
os:
  family: debian
  version: "13"
  source:
    type: template
    template: debian-13-cloud
```

или:

```yaml
os:
  family: debian
  source:
    type: clone
    vmid: 9000
```

### VM/LXC-специфичные параметры

```yaml
vm:
  machine: q35
  bios: ovmf
  guest_agent: true
```

или:

```yaml
lxc:
  unprivileged: true
  nesting: true
```

Пустые секции не добавляются.

### Что не хранить в `guest.yaml`

Не помещать туда:

- пароли и API tokens;
- приватные SSH-ключи;
- содержимое файлов `/etc`, `/opt` и других путей гостевой ОС;
- Docker Compose и конфиги приложений;
- runtime-состояние;
- автоматически обнаруживаемые данные, которыми проект не управляет.

`guest.yaml` описывает желаемое состояние, а не является полным экспортом конфигурации Proxmox.

## Правило `rootfs/`

`rootfs/` повторяет абсолютные пути внутри гостевой ОС. Это **набор файлов и каталогов, которыми управляет проект, а не полный образ корневой файловой системы**.

```text
guests/101-network-gateway/rootfs/etc/nftables.conf
→ /etc/nftables.conf
```

Тот же принцип используется для приложений:

```text
guests/301-ai-control/rootfs/opt/ai-control/agents/hermes/
→ /opt/ai-control/agents/hermes/
```

Отдельного каталога `services/` нет. Код приложений, Dockerfile, Compose-файлы, MCP, агенты, скрипты и системные конфиги хранятся внутри `rootfs/` по реальному пути назначения.

Не создавать отдельные верхнеуровневые каталоги вроде `dns/`, `vpn/`, `nftables/` или `docker/`, если это файлы гостевой ОС.

Сам Git-репозиторий целиком на гостя копировать не требуется.

## Простая и безопасная модель deploy `rootfs/`

Штатный повторяемый deploy выполняет Ansible из `311-dev-services` по SSH. Собственный deploy-MCP, `managed-files.txt` и отдельная база состояния файлов не вводятся.

### 1. Каталоги, полностью принадлежащие проекту

Если каталог создан специально под наш сервис и всё его содержимое должно соответствовать Git, его можно синхронизировать целиком с удалением отсутствующих файлов.

Например:

```text
rootfs/opt/app-services/
→ /opt/app-services/
```

Для такого явно принадлежащего проекту каталога допустима синхронизация с семантикой `--delete`.

### 2. Общие системные каталоги

Файлы в `/etc`, `/usr/local/bin`, `/etc/systemd/system` и других общих системных каталогах устанавливаются только по конкретным путям.

Например:

```text
rootfs/etc/nftables.conf
→ /etc/nftables.conf

rootfs/etc/systemd/system/network-watchdog.service
→ /etc/systemd/system/network-watchdog.service
```

Нельзя считать весь `/etc` или `/etc/systemd/system` принадлежащим проекту.

Удаление отдельного системного файла выполняется явной Ansible-задачей только после осознанного решения его удалить.

### 3. Глобальное зеркалирование запрещено

Никогда не применять удаляющую синхронизацию всего дерева `rootfs/` в `/`.

Запрещён эквивалент:

```bash
rsync --delete rootfs/ /
```

Также запрещено синхронизировать с `--delete` целиком общие системные каталоги вроде `/etc`.

### 4. Persistent data отдельно

Базы данных, Docker volumes, репозитории пользователей, записи камер, runtime state и другие persistent data не являются содержимым `rootfs/` и резервируются отдельно.

Секреты также не хранятся в Git.

Полное решение по инструментам deploy: [`311-dev-services/decisions/001-deployment-tooling.md`](311-dev-services/decisions/001-deployment-tooling.md).

## Управление VM/LXC

Принято следующее разделение:

```text
Proxmox MCP
→ создание и жизненный цикл VM/LXC

Ansible на 311-dev-services
→ повторяемая настройка ОС, rootfs, systemd, Docker/Compose и приложений через SSH

прямой SSH из AI Control
→ bootstrap, диагностика, разовые и аварийные действия

Semaphore на 311-dev-services
→ ручной web-интерфейс к Ansible для пользователя
```

Semaphore не является обязательным промежуточным слоем для Hermes.

## Текущий bootstrap AI Control

`320-ai-control` является временным bootstrap-узлом. Целевой управляющий гость — `301-ai-control`.

Пока `311-dev-services` ещё не развёрнут, bootstrap-операции допустимо выполнять напрямую по SSH. После появления `311` Ansible и Semaphore остаются там и не переносятся в `301-ai-control`.

## Общие правила

- `proxmox` является основным monorepo инфраструктуры;
- общие Ansible roles/playbooks хранятся в `/ansible` и исполняются из `311-dev-services`;
- общие шаблоны хранятся в `/templates`;
- не создавать фиктивные `compose.yaml`: файл появляется вместе с реальной конфигурацией;
- отдельный репозиторий создаётся только при реальной независимости компонента;
- секреты, токены, пароли и приватные ключи в Git не добавляются.
