# Guests

Каждый каталог соответствует одной целевой VM/LXC и собирает в одном месте её документацию и все файлы, которые должны быть развернуты на этом госте.

Правило именования:

```text
<VMID>-<name>/
```

Базовая структура:

```text
<VMID>-<name>/
├── README.md
├── guest.yaml
├── decisions/        # при необходимости
├── STATUS.md         # при необходимости
└── rootfs/
```

Назначение элементов:

- `README.md` — назначение, зависимости, структура и особенности гостя;
- `guest.yaml` — машинно-читаемый паспорт VM/LXC и желаемые параметры её создания в Proxmox;
- `decisions/` — журнал важных архитектурных решений по этому гостю, если он нужен;
- `STATUS.md` — состояние длинной работы или миграции, если требуется;
- `rootfs/` — дерево файлов, которое соответствует корневой файловой системе VM/LXC.

## `guest.yaml`

`guest.yaml` описывает **сам объект VM/LXC в Proxmox**, но не содержимое его операционной системы.

Разделение ответственности:

```text
guest.yaml
→ что создать в Proxmox: VMID, тип, CPU, RAM, диск, сеть, автозапуск

rootfs/
→ что должно находиться внутри гостевой ОС: /etc, /opt, приложения, Compose, конфиги
```

Файл нужен как единый машинно-читаемый источник желаемых параметров гостя. Его сможет читать человек, скрипт или AI-агент перед созданием, проверкой или изменением VM/LXC.

### Базовый формат

Используется следующая структура:

```yaml
schema_version: 1

vmid: 320
name: ai-control
type: vm
node: pve

description: Central AI control plane

resources:
  cpu:
    cores: 2
  memory_mb: 4096
  disk:
    size_gb: 32
    storage: local-lvm

network:
  bridge: vmbr0
  ipv4:
    method: static
    address: 192.168.1.20/24
    gateway: 192.168.1.1

boot:
  onboot: true

management:
  ssh:
    user: infra-agent
    port: 22
```

Значения выше являются примером формата, а не параметрами конкретной VM.

### Обязательные поля

```yaml
schema_version: 1
vmid: 320
name: ai-control
type: vm
```

- `schema_version` — версия структуры `guest.yaml`; текущая версия — `1`;
- `vmid` — VMID в Proxmox; должен совпадать с номером в имени каталога гостя;
- `name` — имя гостя; рекомендуется, чтобы оно совпадало с частью имени каталога после VMID;
- `type` — тип гостя: `vm` или `lxc`.

Например каталог:

```text
guests/320-ai-control/
```

должен иметь:

```yaml
vmid: 320
name: ai-control
type: vm
```

### Размещение

```yaml
node: pve
```

- `node` — имя Proxmox-ноды, на которой должен находиться гость;
- для одноузлового Proxmox обычно будет `pve`;
- поле можно не указывать, если инструмент развертывания умеет выбрать ноду сам.

### Описание

```yaml
description: Central AI control plane
```

Короткое назначение гостя. Это поле предназначено для человека и может также использоваться как описание VM/LXC в Proxmox.

### Ресурсы

```yaml
resources:
  cpu:
    cores: 2
  memory_mb: 4096
  disk:
    size_gb: 32
    storage: local-lvm
```

- `resources.cpu.cores` — количество vCPU;
- `resources.memory_mb` — объём RAM в мегабайтах;
- `resources.disk.size_gb` — размер основного диска в гигабайтах;
- `resources.disk.storage` — Proxmox storage для основного диска.

Дополнительные параметры добавляются только когда они реально нужны. Например:

```yaml
resources:
  cpu:
    cores: 4
    type: host
  memory_mb: 8192
  ballooning_mb: 4096
  disk:
    size_gb: 64
    storage: local-lvm
    discard: true
```

Не следует копировать в `guest.yaml` десятки значений Proxmox по умолчанию только потому, что они существуют. Храним прежде всего параметры, которыми хотим управлять.

### Сеть

Простой вариант:

```yaml
network:
  bridge: vmbr0
  ipv4:
    method: dhcp
```

Статический адрес:

```yaml
network:
  bridge: vmbr0
  ipv4:
    method: static
    address: 192.168.1.20/24
    gateway: 192.168.1.1
```

При необходимости можно добавить VLAN:

```yaml
network:
  bridge: vmbr0
  vlan: 20
  ipv4:
    method: static
    address: 192.168.20.10/24
    gateway: 192.168.20.1
```

- `bridge` — Proxmox bridge, обычно `vmbr0`;
- `vlan` — VLAN tag, если используется;
- `ipv4.method` — `dhcp` или `static`;
- `ipv4.address` — адрес с CIDR для статической конфигурации;
- `ipv4.gateway` — шлюз.

Если у гостя несколько сетевых интерфейсов, формат можно расширить до списка `network.interfaces`. Не усложнять схему заранее, пока такой гость реально не появится.

### Автозапуск

```yaml
boot:
  onboot: true
```

- `boot.onboot` — запускать ли гостя автоматически вместе с Proxmox;
- дополнительные параметры порядка запуска добавляются только при необходимости.

### Доступ для управления

```yaml
management:
  ssh:
    user: infra-agent
    port: 22
```

Этот раздел описывает, **как агент должен подключаться к уже работающему гостю**.

- `management.ssh.user` — management-пользователь;
- `management.ssh.port` — SSH-порт.

Приватный SSH-ключ, пароль и другие секреты в `guest.yaml` не хранятся.

### ОС и источник создания

Если гость должен создаваться автоматически из конкретного образа или шаблона, можно добавить:

```yaml
os:
  family: debian
  version: "13"
  source:
    type: template
    template: debian-13-cloud
```

или для клонирования существующего Proxmox template:

```yaml
os:
  family: debian
  source:
    type: clone
    vmid: 9000
```

Точный набор `os.source` зависит от принятого способа автоматического создания VM/LXC и будет расширяться по мере появления реальных сценариев.

### VM- и LXC-специфичные параметры

Общие параметры хранятся на верхнем уровне. Если появятся настройки, применимые только к одному типу гостя, они помещаются в отдельный раздел:

```yaml
vm:
  machine: q35
  bios: ovmf
  guest_agent: true
```

или:

```yaml
lxc:
  unprivileged: true
  nesting: true
```

Не добавлять пустые `vm:` или `lxc:` секции, если специальных настроек нет.

### Что не хранить в `guest.yaml`

Не помещать туда:

- пароли;
- API tokens;
- приватные SSH-ключи;
- содержимое файлов из `/etc`, `/opt` и других путей гостевой ОС;
- Docker Compose и конфиги приложений;
- временное runtime-состояние;
- автоматически обнаруживаемые данные, которыми мы не собираемся управлять.

Файлы гостевой ОС хранятся в `rootfs/`, секреты — вне Git, а текущий временный статус большой работы при необходимости хранится в `STATUS.md`.

### Принцип заполнения

`guest.yaml` описывает **желаемое состояние**, а не является полным экспортом конфигурации Proxmox.

Поэтому правило такое:

> Добавлять параметр в `guest.yaml`, если он важен для воспроизводимого создания гостя или мы хотим сознательно контролировать его значение.

Если параметр можно безопасно оставить стандартным и он не важен для нашей архитектуры, его можно не указывать.

## Правило `rootfs/`

`rootfs/` является зеркалом корневой файловой системы гостя. Всё, что находится после `rootfs/`, разворачивается относительно `/` на VM/LXC.

Например:

```text
guests/100-network-gateway/rootfs/etc/nftables.conf
```

на целевой системе становится:

```text
/etc/nftables.conf
```

Тот же принцип применяется к приложениям и собственному коду. Например:

```text
guests/320-ai-control/rootfs/opt/ai-control/agents/hermes/
```

соответствует:

```text
/opt/ai-control/agents/hermes/
```

Отдельного каталога `services/` нет. Код приложения, Dockerfile, Compose-файлы, MCP, агенты, скрипты и системные конфиги — всё хранится внутри `rootfs/` по тому пути, где должно находиться на гостевой системе.

Сам Git-репозиторий целиком на гостя копировать не требуется. Агент должен брать только каталог конкретного гостя и по SSH синхронизировать нужное содержимое `rootfs/` с `/` на целевой системе.

Не требуется автоматически создавать отдельный Git-репозиторий для каждого MCP, скрипта или внутреннего приложения. Отдельный репозиторий создаётся только при реальной причине: компонент используется несколькими независимыми проектами, выпускается и версионируется отдельно, публикуется как самостоятельный продукт или должен развиваться независимо от Proxmox-инфраструктуры.

## Управление VM/LXC

Для управления инфраструктурой принято простое разделение уровней:

```text
Proxmox MCP
→ создание и жизненный цикл VM/LXC

SSH
→ всё внутри гостевой операционной системы
```

Через Proxmox MCP выполняются операции уровня виртуализации: создание VM/LXC, CPU, RAM, диски, сеть, start/stop/reboot, snapshots и backups.

SSH является основным универсальным каналом для настройки гостевых систем, включая `320-ai-control`: установка пакетов, изменение файлов, управление `systemd`, установка Docker, Docker Compose и развёртывание приложений.

Не требуется отдельный deploy-агент или deploy-MCP на каждом госте. Специализированный инструмент добавляется только тогда, когда решает отдельную задачу и даёт реальное преимущество перед SSH.

Агент может полностью выполнить цепочку:

```text
создать VM через Proxmox MCP
→ подключиться по SSH
→ подготовить ОС
→ синхронизировать нужное содержимое rootfs/
→ установить/запустить приложения
→ проверить состояние
```

Защита строится прежде всего на восстанавливаемости: Git, Proxmox snapshots, backups, резервировании persistent data, логировании и проверке результата изменений.

Подробное решение для AI-control зафиксировано в:

```text
guests/320-ai-control/decisions/001-simple-management-model.md
```

## Общие правила

- `proxmox` является основным monorepo инфраструктуры;
- общие Ansible playbook/roles не дублировать по гостям — они хранятся в `/ansible`;
- Ansible не является обязательным механизмом управления: при необходимости он используется поверх SSH для повторяемых процедур;
- общие шаблоны хранятся в `/templates`;
- не создавать фиктивные `compose.yaml`: файл появляется только вместе с реальной конфигурацией;
- секреты, токены, пароли и приватные ключи в Git не добавлять.
