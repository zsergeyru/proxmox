# Гостевые системы

`guests/` хранит требуемое состояние и локальную документацию VM/LXC. Этот README объясняет структуру каталога; точная спецификация манифеста находится в [`../docs/300-guests/320-guest-manifest.md`](../docs/300-guests/320-guest-manifest.md).

## Структура

```text
guests/
├── defaults.yaml
├── README.md
└── <VMID>-<name>/
    ├── guest.yaml
    ├── README.md
    ├── decisions.md
    ├── STATUS.md
    └── rootfs/
```

Не каждая гостевая система обязана иметь все дополнительные каталоги и файлы. Создаются только те, которые реально нужны.

## Роли файлов

| Файл/каталог | Назначение |
|---|---|
| `defaults.yaml` | Общие параметры развёртывания и профили для управляемых гостевых систем |
| `<guest>/guest.yaml` | Индивидуальное требуемое состояние конкретной VM/LXC |
| `<guest>/README.md` | Назначение и эксплуатационные особенности гостевой системы |
| `<guest>/decisions.md` | Устойчивые решения, относящиеся только к этой гостевой системе |
| `<guest>/STATUS.md` | Временное фактическое состояние или расхождение, если оно действительно нужно |
| `<guest>/rootfs/` | Управляемые файлы, которые должны попадать внутрь гостевой ОС |

`README.md`, `decisions.md` и `STATUS.md` не заменяют машинное описание гостя как источник требуемого состояния.

## Основной источник

Для управляемой VM/LXC итоговое требуемое состояние строится из:

```text
guests/defaults.yaml
+ выбранный профиль
+ guests/<guest>/guest.yaml
+ детерминированные правила проекта
→ итоговое требуемое состояние
```

Модель построения требуемого состояния описана в [`../docs/300-guests/310-guest-state.md`](../docs/300-guests/310-guest-state.md), формат и поля `guest.yaml` — в [`../docs/300-guests/320-guest-manifest.md`](../docs/300-guests/320-guest-manifest.md), а машинные ограничения — в `../schemas/`.

Поэтому в этом README не фиксируются номера схем, конкретные подсети и шлюзы, `Template-Version` или списки обязательных полей — они быстро устаревают и принадлежат основной спецификации.

## Что хранить в `guest.yaml`

Только индивидуальные параметры гостевой системы и осознанные переопределения.

Общие значения должны жить в `defaults.yaml` и профилях. Не следует копировать в каждый манифест общую сеть, хранилище или другие общие параметры только ради наглядности. Административный SSH `root:22` является фиксированным контрактом проекта и в YAML не настраивается.

Если объект известен проекту, но ещё не готов к универсальному `deploy-guest`, поле `profile` не задаётся. Наличие `profile` означает, что для гостя можно построить полное effective state по общим правилам проекта.

## Документация конкретной гостевой системы

`README.md` гостевой системы полезен для информации, которую не стоит кодировать в манифест, например:

- назначение VM/LXC;
- какие сервисы внутри ожидаются;
- эксплуатационные особенности;
- ссылки на внешний проект или репозиторий;
- необычные замечания по восстановлению или миграции.

Устойчивые решения по конкретному гостю хранятся в одном файле `decisions.md`. Отдельный каталог решений для обычного гостя не требуется.

`STATUS.md` используется только для временного состояния или расхождения. После устранения расхождения постоянное правило должно перейти в манифест, политику или ADR.


### Специальные гости

Специальный гость, жизненным циклом которого владеет внешний контур, может не иметь `guest.yaml`.

Текущий пример:

```text
guests/910-infra-deployer/
├── README.md
└── decisions.md
```

`910 infra-deployer` создаётся публичным `zsergeyru/proxmox-bootstrap` и поэтому намеренно не включается в обычное OpenTofu-состояние гостей. Его машинный контракт принадлежит bootstrap, а в каталоге гостя хранится документация конкретного LXC.

## Управляемые файлы

`rootfs/` содержит только файлы, которыми проект действительно управляет как частью конфигурации гостевой системы.

Постоянные данные приложений, состояние текущего запуска, резервные копии и секреты не следует складывать в `rootfs/`.

Общая политика файловой структуры Linux: [`../docs/34-linux-filesystem-layout.md`](../docs/34-linux-filesystem-layout.md).

## Проверка

После изменения манифестов выполнить:

```bash
python scripts/validate_repo.py
```

`validate_repo.py` и `sync-management-keys` используют общий модуль `scripts/guest_config.py`. `deploy-guest` будет переведён на новый контракт при отдельной полной переработке.
