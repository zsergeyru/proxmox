# 101 — network-gateway

**Тип:** VM  
**ОС:** Debian (целевая)  
**Назначение:** пользовательский сетевой шлюз, DNS, исходящие VPN, remote-access VPN и policy-based routing.

## В ОС VM

- IP forwarding;
- nftables;
- `ip rule` и routing tables;
- fwmark/PBR;
- Amnezia/AmneziaWG и другие VPN-клиенты для исходящего трафика;
- WireGuard/AmneziaWG server для удалённого доступа;
- маршрутизация remote-access клиентов в домашние сегменты;
- IPv6 forwarding и DHCPv6 Prefix Delegation при включении IPv6;
- Router Advertisement и IPv6 firewall для клиентских сегментов;
- при необходимости mDNS reflector/repeater между явно разрешёнными сегментами;
- health-check/watchdog.

## В Docker

- SmartDNS — основной DNS-сервис;
- AdGuard Home — опциональный фронтенд для статистики/фильтрации, если он действительно понадобится;
- sing-box — только для отдельных proxy/outbound-сценариев, а не как центральный DNS или маршрутизатор.

Маршрутизация, PBR и VPN принадлежат ОС VM, а не Docker networking.

## DNS и mDNS

### Принятый DNS/PBR-стек

Для `101-network-gateway` зафиксирована следующая архитектура:

```text
Клиенты
   │
   │ DNS
   ▼
SmartDNS
   ├── обычные upstream DNS
   ├── DoH / DoT
   ├── группы через обычный ISP
   └── группы через VPN при необходимости

Разрешённые адреса / наборы назначения
   │
   ▼
nftables sets + fwmark
   │
   ▼
ip rule / routing tables
   ├── обычный ISP
   ├── AmneziaWG
   └── другие VPN/маршруты при необходимости
```

Основные принципы:

- SmartDNS является основным DNS-движком и точкой применения DNS-групп/правил;
- SmartDNS может использовать несколько upstream, включая DoH/DoT, и разные группы upstream для разных наборов доменов;
- фактический маршрут пользовательского трафика выбирается не DNS-сервисом, а `nftables` + `ip rule`/routing tables;
- AmneziaWG и другие VPN поднимаются на уровне ОС VM;
- sing-box добавляется только там, где требуется прокси или сложный outbound, который неудобно реализовывать обычной маршрутизацией;
- AdGuard Home не является обязательным элементом базовой схемы; при добавлении он используется как дополнительный фронтенд/фильтр и не должен подменять основной SmartDNS/PBR-контур;
- `keen-pbr` внутри этой VM не используется: серверный PBR реализуется штатными средствами Linux.

На первом этапе для Network VM принят постоянный адрес:

```text
192.168.1.32
```

Клиенты, переводимые на новый DNS-контур, используют `192.168.1.32` как DNS-сервер. Docker-контейнерам отдельные адреса домашней LAN по умолчанию не требуются: наружу публикуются только необходимые порты VM.

Основной управляемый внутренний DNS-домен:

```text
home.arpa
```

Постоянные инфраструктурные имена должны использовать обычный DNS, например:

```text
pve.home.arpa
ha.home.arpa
mqtt.home.arpa
apps.home.arpa
```

mDNS работает параллельно через специальный домен `.local` и используется прежде всего для автоматического обнаружения устройств. Критичные зависимости инфраструктуры не должны строиться только на mDNS.

Поскольку mDNS обычно не маршрутизируется между VLAN, после появления изолированных сегментов при необходимости обнаружения IOT-устройств из MAIN на `101-network-gateway` может быть включён reflector/repeater, например Avahi или эквивалент. Reflection включается только между нужными сегментами и с учётом firewall; без необходимости CAMERAS в такой reflection не включать.

Remote-access VPN должен получать домашний DNS и разрешать `*.home.arpa`. Перенос mDNS через VPN не является обязательной частью базовой архитектуры.

Полное решение описано в [`../../docs/dns.md`](../../docs/dns.md).

## Два этапа сети

### Этап 1 — до переезда

`101-network-gateway` разворачивается в текущей общей LAN Keenetic. VLAN для запуска сетевых сервисов не требуются.

Текущая физическая схема:

```text
Internet / WAN
      │
   Keenetic
   ├── LAN-порт → компьютеры / домашние устройства
   └── LAN-порт → Proxmox nic0 → vmbr0 → 101

Оба LAN-порта принадлежат одной локальной сети/L2-сегменту.
```

На этом этапе Keenetic остаётся физическим edge-router и WAN-шлюзом, а `101` уже предоставляет:

- DNS и `home.arpa`;
- DoH/DoT и upstream DNS;
- исходящие VPN;
- PBR;
- remote-access VPN;
- firewall и сопутствующие сетевые сервисы.

Компьютеры и `101` находятся в одной LAN, поэтому отдельная маршрутизация между «общей» и «серверной» сетями на первом этапе не требуется. Какие клиенты и какой трафик должны использовать `101` для DNS/VPN/PBR, настраивается отдельно по мере внедрения этих сервисов.

### Этап 2 — после переезда

У Proxmox по-прежнему остаётся одна физическая Ethernet-карта. Тот же порт может использоваться как VLAN trunk через VLAN-aware `vmbr0`.

Целевые сегменты:

```text
MAIN / native     10.0.0.0/16    gateway 10.0.0.1
IOT / VLAN 20     10.20.0.0/16   gateway 10.20.0.1
CAMERAS / VLAN 30 10.30.0.0/16   gateway 10.30.0.1
REMOTE-VPN        10.60.0.0/16   gateway 10.60.0.1
```

Вероятным физическим edge-router после переезда является OpenWrt, но это пока не окончательное решение. Точное разделение L3/firewall-функций между OpenWrt и `101-network-gateway` будет определено перед вторым этапом. DNS/VPN/PBR и другие уже работающие сервисы `101` при этом должны по возможности сохраняться без перепроектирования.

`101-network-gateway` является специальным сетевым гостем, поэтому его интерфейсные адреса определяются ролью шлюза, а не обычным правилом VMID → management IP.

## Переходный период

До переезда текущая общая LAN Keenetic продолжает работать без VLAN. Наблюдаемая адресация PVE:

```text
LAN:      192.168.0.0/16
PVE:      192.168.1.11/16
gateway:  192.168.1.1
```

На LAN-интерфейсе Keenetic можно заранее добавить будущий адрес `10.0.0.1/16`, чтобы проверить целевую адресацию ещё до переезда. Новые серверы при этом могут сразу получать постоянные `10.0.x.x/16`; при необходимости совместимости им временно добавляются вторые адреса `192.168.x.x/16`.

После переезда адрес `10.0.0.1` принимает целевой шлюз MAIN. Каким именно устройством будет этот шлюз, определяется перед вторым этапом. Благодаря этому серверные IP и default gateway не должны без необходимости меняться повторно. Полная процедура описана в [`../../docs/network.md`](../../docs/network.md).

## IPv6

IPv6 поддерживается параллельно с IPv4 в режиме dual stack и не заменяет принятую адресацию `10.x.x.x`.

При включении IPv6 эта VM должна:

- получать delegated prefix от провайдера через DHCPv6-PD, если эта функция останется на `101` после окончательного разделения ролей;
- выделять отдельный `/64` для каждого L2-сегмента/VLAN, если `101` выполняет L3 для этих сегментов;
- отправлять Router Advertisement при соответствующей роли;
- выполнять IPv6 routing и stateful firewall через `nftables` в пределах своей сетевой ответственности;
- поддерживать DNS AAAA и IPv6 в remote-access VPN.

NAT66 по умолчанию не используется. Конкретный глобальный IPv6-префикс заранее не фиксируется и будет определён после проверки возможностей провайдера новой квартиры.

Полная IPv6-архитектура описана в [`../../docs/ipv6.md`](../../docs/ipv6.md).

## Remote-access VPN

Удалённые доверенные ноутбуки, компьютеры и телефоны подключаются к этой VM и получают адреса из отдельной tunnel-сети:

```text
REMOTE-VPN  10.60.0.0/16
gateway     10.60.0.1
```

Целевой профиль удалённого клиента:

- домашний DNS через `10.60.0.1` → SmartDNS;
- доступ к MAIN `10.0.0.0/16`, включая Proxmox и серверы;
- доступ к IOT `10.20.0.0/16`;
- доступ к CAMERAS `10.30.0.0/16`;
- возможность использовать full-tunnel через домашний интернет-шлюз;
- возможность использовать split-tunnel только для домашних сетей;
- применение тех же PBR и исходящих VPN-политик, что и для локальных клиентов.

Основной remote-access VPN должен завершаться именно здесь, чтобы DNS, PBR и исходящие VPN оставались единым контуром. На первом этапе Keenetic при необходимости пробрасывает входящий порт на эту VM. После переезда входящая схема зависит от окончательного разделения ролей с физическим edge-router.

Дополнительный ограниченный VPN на физическом роутере можно сохранить как аварийный административный канал на случай недоступности Proxmox или этой VM.

## Предварительные ресурсы

- vCPU: 2
- RAM: 2 GB
- Disk: 16–32 GB
- NIC: VirtIO
- Ballooning: на первом этапе не использовать

## Размещение конфигурации

Все файлы, которые должны оказаться внутри VM, хранятся только под `rootfs/` по реальному пути назначения. Старые верхнеуровневые каталоги `dns/`, `vpn/`, `routing/`, `nftables/` больше не используются.

Примеры целевых путей:

```text
rootfs/etc/nftables.conf
rootfs/etc/systemd/system/...
rootfs/etc/wireguard/...
rootfs/opt/network-gateway/adguard-home/...
rootfs/opt/network-gateway/smartdns/...
```

VPN-секреты, peer private keys и preshared keys в Git не добавляются. Реальные файлы `rootfs/` создаются только при появлении фактической конфигурации, без фиктивных заглушек.
