# ADR 001 — Простая модель управления инфраструктурой

## Статус

Принято. Решение проверяется на текущем bootstrap `320-ai-control` и должно быть перенесено без изменения принципов на целевой `301-ai-control`.

## Контекст

AI Control должен уметь:

- создавать и настраивать VM/LXC в Proxmox;
- устанавливать ПО внутри гостевых систем;
- устанавливать Docker и Docker Compose;
- разворачивать и сопровождать приложения на разных VM/LXC;
- устанавливать MCP и другие инфраструктурные компоненты;
- изменять конфигурацию;
- проверять состояние, логи и результат изменений.

Ранее рассматривался `deploy-mcp` как промежуточный слой между агентом и Docker. После пересмотра архитектуры решено отказаться от отдельного универсального deploy-механизма.

## Решение

Использовать два основных механизма управления:

```text
AI-агент
   │
   ├── Proxmox MCP
   │      └── уровень виртуализации
   │
   └── SSH
          └── ОС и приложения внутри VM/LXC
```

### Proxmox MCP

Используется для операций уровня Proxmox:

- создать или клонировать VM/LXC;
- настроить CPU/RAM/disk/network;
- start/stop/reboot;
- snapshots и backups;
- удалить VM/LXC;
- другие операции жизненного цикла гостя.

### SSH

SSH является универсальным каналом управления внутри VM/LXC, включая сам AI Control.

Через SSH агент может:

- устанавливать и обновлять пакеты;
- создавать пользователей и каталоги;
- читать и изменять конфигурационные файлы;
- управлять `systemd`;
- устанавливать Docker и Docker Compose;
- создавать и редактировать Compose-файлы;
- запускать и обновлять контейнеры;
- читать логи и проверять health/status;
- разворачивать MCP и приложения;
- выполнять другие необходимые административные операции.

Один подход применяется к текущему `320-ai-control`, будущему `301-ai-control`, `101-network-gateway`, `211-automation-services`, `311-dev-services`, `321-app-services`, `331-ai-services`, `401-monitoring` и новым управляемым гостям.

Отдельный `guest-mcp` не требуется, если задачу нормально решает SSH.

## Развёртывание новой VM/LXC

Типовая последовательность:

```text
1. Proxmox MCP
   → создать VM/LXC
   → настроить CPU/RAM/disk/network

2. дождаться загрузки

3. SSH
   → подключиться
   → подготовить ОС
   → установить Docker/Compose при необходимости

4. SSH
   → синхронизировать нужное содержимое rootfs/ конкретного guest
   → запустить сервисы

5. SSH
   → проверить health/status/logs

6. сохранить повторяемую конфигурацию и документацию в Git
```

## Размещение файлов

Для каждого гостя используется единый каталог `rootfs/`, повторяющий корневую файловую систему VM/LXC.

`rootfs/` не создаётся внутри гостевой системы. Всё после `rootfs/` разворачивается относительно `/`.

Отдельного `services/` нет. Исходный код, Dockerfile, Compose, агенты, MCP и системные конфиги хранятся по реальному пути внутри `rootfs/`.

Например:

```text
guests/202-ha-test/rootfs/opt/home-assistant/compose.yaml
→ /opt/home-assistant/compose.yaml
```

Для текущего bootstrap:

```text
guests/320-ai-control/rootfs/opt/ai-control/agents/hermes/
→ /opt/ai-control/agents/hermes/
```

`ai-control` хранит только собственные файлы управляющего контура, а не копии конфигурации других VM/LXC.

## Решение по `deploy-mcp`

`deploy-mcp` удалён из целевой архитектуры.

Основной путь:

```text
SSH → rootfs → Docker / Compose / systemd
```

Новые компоненты и документация не должны зависеть от `deploy-mcp`. Специализированный deploy-инструмент может появиться только для конкретной задачи, если даст заметное преимущество перед SSH.

## Ansible

Ansible не является обязательной частью архитектуры. Его можно применять позже для повторяемых процедур поверх SSH.

## Модель прав

Агент рассматривается как администратор домашней инфраструктуры и получает достаточные права для выполнения поставленных задач.

Предпочтительно:

- отдельный management-пользователь, например `infra-agent`;
- отдельный SSH-ключ для AI Control;
- public key добавлять новым VM через cloud-init;
- секреты и приватные ключи не хранить в Git;
- права Proxmox выдавать осознанно.

## Основная модель защиты

Защита строится прежде всего на обнаружении ошибки и восстановлении:

1. Git — источник истины для конфигурации и кода.
2. Proxmox snapshots — перед рискованными изменениями.
3. Proxmox backups — регулярное восстановимое копирование.
4. Backup persistent data / Docker volumes отдельно от конфигурации.
5. Резервные копии критичных файлов перед изменением при необходимости.
6. Логирование действий агента.
7. Проверка после изменения — health, status, logs и доступность.
8. Поэтапные изменения — сначала создать/проверить новое, потом удалять старое.

Принцип:

> Максимально простое управление, достаточные административные права и хорошая восстанавливаемость предпочтительнее множества специальных песочниц и промежуточных deploy-слоёв.

## Миграция bootstrap

Архитектурное решение не привязано к VMID 320. После развёртывания `301-ai-control` тот же набор принципов переносится на новую VM. `320` выводится из эксплуатации только после проверки 301.
