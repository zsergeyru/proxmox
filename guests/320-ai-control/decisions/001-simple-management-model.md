# ADR 001 — Простая модель управления инфраструктурой

## Статус

Принято для bootstrap. Часть про повторяемое развёртывание внутри гостей уточнена решением [`../../311-dev-services/decisions/001-deployment-tooling.md`](../../311-dev-services/decisions/001-deployment-tooling.md): целевой штатный deploy выполняется Ansible из `311-dev-services`, а прямой SSH остаётся базовым транспортом, bootstrap- и аварийным каналом.

## Контекст

AI Control должен уметь:

- создавать и настраивать VM/LXC в Proxmox;
- устанавливать ПО внутри гостевых систем;
- устанавливать Docker и Docker Compose;
- разворачивать и сопровождать приложения на разных VM/LXC;
- устанавливать MCP и другие инфраструктурные компоненты;
- изменять конфигурацию;
- проверять состояние, логи и результат изменений.

Ранее рассматривался `deploy-mcp` как промежуточный слой между агентом и Docker. От отдельного универсального deploy-MCP решено отказаться.

## Базовое решение

Уровень виртуализации и уровень гостевой ОС разделяются:

```text
AI-агент
   │
   ├── Proxmox MCP
   │      └── уровень виртуализации
   │
   └── SSH
          └── базовый канал доступа внутрь VM/LXC
```

### Proxmox MCP

Используется для операций уровня Proxmox:

- создать или клонировать VM/LXC;
- настроить CPU/RAM/disk/network;
- start/stop/reboot;
- snapshots и backups;
- удалить VM/LXC;
- другие операции жизненного цикла гостя.

### SSH

SSH остаётся универсальным каналом доступа внутрь VM/LXC.

Через него можно выполнять bootstrap, диагностику и разовые административные операции. Он также является транспортом, по которому Ansible из `311-dev-services` управляет гостевыми ОС.

Отдельный `guest-mcp` не требуется, если задачу нормально решают штатные механизмы Proxmox, Ansible или SSH.

## Целевая модель повторяемого развёртывания

После появления `311-dev-services` повторяемые изменения внутри гостя выполняются так:

```text
AI-агент / пользователь
→ конфигурация в Git
→ Ansible на 311-dev-services
→ SSH
→ нужная VM/LXC
→ проверка результата
```

Прямой SSH из AI Control используется для:

- первоначального bootstrap;
- диагностики;
- разовых действий;
- аварийного восстановления;
- работы до развёртывания `311-dev-services`.

Semaphore в `311-dev-services` даёт пользователю web-интерфейс к тем же Ansible playbook и не является обязательным звеном для Hermes.

## Развёртывание новой VM/LXC

Типовая целевая последовательность:

```text
1. Proxmox MCP
   → создать VM/LXC
   → настроить CPU/RAM/disk/network

2. дождаться загрузки

3. bootstrap по SSH при необходимости
   → создать management-доступ
   → подготовить минимальную ОС

4. Ansible на 311-dev-services
   → установить пакеты
   → применить нужное содержимое rootfs/ конкретного guest
   → настроить systemd/Docker/Compose
   → запустить сервисы

5. проверить health/status/logs

6. сохранить повторяемую конфигурацию и документацию в Git
```

Пока `311-dev-services` отсутствует, пункты 3–5 допустимо выполнять напрямую по SSH с текущего `320-ai-control`.

## Размещение файлов

Для каждого гостя используется единый каталог `rootfs/`, повторяющий абсолютные пути внутри VM/LXC.

`rootfs/` не создаётся внутри гостевой системы. Всё после `rootfs/` разворачивается относительно `/`.

Отдельного `services/` нет. Исходный код, Dockerfile, Compose, агенты, MCP и системные конфиги хранятся по реальному пути внутри `rootfs/`.

Например:

```text
guests/202-ha-test/rootfs/opt/home-assistant/compose.yaml
→ /opt/home-assistant/compose.yaml
```

Для текущего bootstrap:

```text
guests/320-ai-control/rootfs/opt/ai-control/agents/hermes/
→ /opt/ai-control/agents/hermes/
```

`ai-control` хранит только собственные файлы управляющего контура, а не копии конфигурации других VM/LXC.

Правила безопасного применения `rootfs/`, включая допустимый `--delete` только для полностью принадлежащих проекту каталогов и запрет глобального `rsync --delete rootfs/ /`, определены в ADR `311-dev-services`.

## Решение по `deploy-mcp`

`deploy-mcp` удалён из целевой архитектуры.

Для повторяемого deploy используется Ansible поверх SSH. Новые компоненты не должны зависеть от универсального deploy-MCP.

## Размещение Ansible

Ansible не является AI-агентом и не размещается в `agents/` или как постоянный компонент `301-ai-control`.

Целевое место Ansible и Semaphore — `311-dev-services`.

## Модель прав

Агент и DevOps-контур получают достаточные права для выполнения поставленных задач.

Предпочтительно:

- отдельный management-пользователь, например `infra-agent`;
- отдельные SSH-ключи для управляющего контура;
- public key добавлять новым VM через cloud-init;
- секреты и приватные ключи не хранить в Git;
- права Proxmox выдавать осознанно.

## Основная модель защиты

Защита строится прежде всего на обнаружении ошибки и восстановлении:

1. Git — источник истины для конфигурации и кода.
2. Proxmox snapshots — перед рискованными изменениями.
3. Proxmox backups — регулярное восстановимое копирование.
4. Backup persistent data / Docker volumes отдельно от конфигурации.
5. Резервные копии критичных файлов перед изменением при необходимости.
6. Логирование действий агента и deploy-задач.
7. Проверка после изменения — health, status, logs и доступность.
8. Поэтапные изменения — сначала создать/проверить новое, потом удалять старое.

Принцип:

> Максимально простое управление, готовые стандартные инструменты и хорошая восстанавливаемость предпочтительнее собственного deploy-слоя и множества специальных песочниц.

## Миграция bootstrap

Архитектурное решение не привязано к VMID 320. После развёртывания `311-dev-services` и `301-ai-control` повторяемый deploy выполняется через Ansible на 311, а 320 выводится из эксплуатации только после проверки целевой схемы.
