# ADR 001 — Простая модель управления инфраструктурой

## Статус

**Частично заменено более новыми общепроектными решениями.**

ADR сохраняется как история решения временного узла `320`. Действующая модель повторяемой настройки уточнена в [`../../311-dev-services/decisions/001-deployment-tooling.md`](../../311-dev-services/decisions/001-deployment-tooling.md), а текущие общепроектные правила SSH, PVE ACL и AI Control находятся в:

- [`../../../docs/23-security.md`](../../../docs/23-security.md);
- [`../../../docs/25-pve-access-control.md`](../../../docs/25-pve-access-control.md);
- [`../../../docs/33-guest-bootstrap-and-provisioning.md`](../../../docs/33-guest-bootstrap-and-provisioning.md);
- [`../../../docs/50-ai-control.md`](../../../docs/50-ai-control.md).

В частности, старое решение использовать универсального пользователя `ops` **больше не действует**: текущий административный пользователь управляемых Debian-гостей — `root` с доступом только по независимым SSH-ключам.

## Контекст

AI Control должен уметь:

- создавать и настраивать VM/LXC в Proxmox;
- устанавливать ПО внутри гостевых систем;
- устанавливать Docker и Docker Compose;
- разворачивать и сопровождать приложения на разных VM/LXC;
- устанавливать MCP и другие инфраструктурные компоненты;
- изменять конфигурацию;
- проверять состояние, журналы и результат изменений.

Ранее рассматривался `deploy-mcp` как промежуточный слой между агентом и Docker. От отдельного универсального MCP для развёртывания решено отказаться.

## Базовое решение

Уровень виртуализации и уровень гостевой ОС разделяются:

```text
AI-агент
   │
   ├── Proximo MCP
   │      └── уровень виртуализации
   │
   └── SSH
          └── базовый канал доступа внутрь VM/LXC
```

### Proximo MCP

Используется для операций уровня Proxmox:

- создание или клонирование VM/LXC;
- настройка CPU, RAM, диска и сети;
- запуск, остановка и перезагрузка;
- снимки и резервные копии;
- удаление VM/LXC;
- другие операции жизненного цикла гостевой системы.

### SSH

SSH остаётся универсальным каналом доступа внутрь VM/LXC.

Через него выполняются первичная настройка, диагностика и разовые административные операции. Он также является транспортом, по которому Ansible из `311-dev-services` управляет гостевыми ОС.

Отдельный `guest-mcp` не требуется, если задачу нормально решают штатные механизмы Proxmox, Ansible или SSH.

## Целевая модель повторяемой настройки

После появления `311-dev-services` повторяемые изменения внутри гостевой системы выполняются так:

```text
AI-агент / пользователь
→ конфигурация в Git
→ Ansible на 311-dev-services
→ SSH
→ нужная VM/LXC
→ проверка результата
```

Прямой SSH из AI Control используется для:

- первоначальной настройки;
- диагностики;
- разовых действий;
- аварийного восстановления;
- работы до развёртывания `311-dev-services`.

Semaphore в `311-dev-services` даёт пользователю веб-интерфейс к тем же Ansible playbook и не является обязательным звеном для Hermes.

## Развёртывание новой VM/LXC

Типовая целевая последовательность:

```text
1. Proximo MCP
   → создать VM/LXC
   → настроить CPU, RAM, диск и сеть

2. дождаться загрузки

3. при необходимости выполнить первоначальную настройку по SSH
   → административный доступ уже должен быть подготовлен штатным механизмом создания гостя
   → подготовить минимальную ОС

4. Ansible на 311-dev-services
   → установить пакеты
   → применить нужное содержимое rootfs/ конкретной гостевой системы
   → настроить systemd/Docker/Compose
   → запустить сервисы

5. проверить состояние, журналы и работу сервисов

6. сохранить повторяемую конфигурацию и документацию в Git
```

Пока `311-dev-services` отсутствует, необходимые действия внутри гостевой ОС допустимо выполнять напрямую по SSH с текущего `320-ai-control`.

## Размещение файлов

Для каждого гостя используется единый каталог `rootfs/`, повторяющий абсолютные пути внутри VM/LXC.

`rootfs/` не создаётся внутри гостевой системы. Всё после `rootfs/` разворачивается относительно `/`.

Отдельного `services/` нет. Исходный код, Dockerfile, Compose, агенты, MCP и системная конфигурация хранятся по реальному пути внутри `rootfs/`.

Например:

```text
guests/202-ha-test/rootfs/opt/home-assistant/compose.yaml
→ /opt/home-assistant/compose.yaml
```

Для текущего временного узла:

```text
guests/320-ai-control/rootfs/opt/ai-control/agents/hermes/
→ /opt/ai-control/agents/hermes/
```

`ai-control` хранит только собственные файлы управляющего контура, а не копии конфигурации других VM/LXC.

Правила безопасного применения `rootfs/`, включая допустимый `--delete` только для полностью принадлежащих проекту каталогов и запрет глобального `rsync --delete rootfs/ /`, определены в ADR `311-dev-services`.

## Решение по `deploy-mcp`

`deploy-mcp` удалён из целевой архитектуры.

Для повторяемой настройки используется Ansible поверх SSH. Новые компоненты не должны зависеть от универсального `deploy-mcp`.

## Размещение Ansible

Ansible не является AI-агентом и не размещается в `agents/` или как постоянный компонент `301-ai-control`.

Целевое место Ansible и Semaphore — `311-dev-services`.

## Актуальная модель административного доступа

Историческое решение ADR про пользователя `ops` заменено общепроектной политикой.

Сейчас действует:

```text
административный пользователь Debian-гостей → root
пароль root → заблокирован
SSH → только по открытым ключам
PVE / AI / Ansible → независимые пары ключей
```

Открытые ключи устанавливаются штатными механизмами создания VM/LXC; закрытые ключи и другие секреты в Git не хранятся.

## Основная модель защиты

Защита строится на разделении прав, предварительных проверках и возможности восстановления:

1. Git хранит воспроизводимую конфигурацию и код.
2. Перед рискованными изменениями используются снимки состояния или резервные копии по ситуации.
3. Постоянные данные резервируются отдельно от воспроизводимой конфигурации.
4. Действия автоматики журналируются.
5. После изменения проверяются состояние, журналы и работа сервисов.
6. Изменения выполняются поэтапно: сначала создать и проверить новое, затем удалять старое.

Принцип:

> Простое управление, готовые стандартные инструменты и хорошая восстанавливаемость предпочтительнее собственного универсального слоя развёртывания и множества специальных промежуточных сервисов.

## Переход с временного узла

Архитектурное решение не привязано к VMID `320`. После развёртывания `311-dev-services` и `301-ai-control` повторяемая настройка выполняется через Ansible на `311`, а `320` выводится из эксплуатации только после проверки целевой схемы.
