# ADR 001 — Простая модель управления инфраструктурой

## Статус

Принято.

## Контекст

`320-ai-control` — центральная точка управления домашней инфраструктурой. Агентов может быть несколько. Они должны уметь:

- создавать и настраивать VM/LXC в Proxmox;
- устанавливать ПО внутри существующих и новых гостевых систем;
- устанавливать Docker и Docker Compose;
- разворачивать и сопровождать Docker-приложения на разных VM/LXC;
- устанавливать новые MCP, инфраструктурные и прикладные компоненты;
- изменять их конфигурацию;
- проверять состояние, логи и результат развертывания.

Ранее для Docker на `320-ai-control` использовался `deploy-mcp` как промежуточный слой между агентом и Docker socket. После пересмотра архитектуры решено отказаться от этого отдельного deploy-механизма.

## Решение

Не строить отдельную песочницу и отдельную систему деплоя для каждого типа ресурса.

Использовать два основных механизма управления:

```text
AI-агент
   │
   ├── Proxmox MCP
   │      └── управление уровнем виртуализации
   │
   └── SSH
          └── управление ОС и приложениями внутри VM/LXC
```

### Proxmox MCP

Используется для операций уровня Proxmox:

- создать VM/LXC;
- клонировать шаблон;
- настроить CPU/RAM/disk;
- настроить сеть;
- start/stop/reboot;
- snapshots;
- backups;
- удалить VM/LXC;
- другие операции жизненного цикла гостевой системы.

### SSH

SSH является основным универсальным каналом управления внутри VM/LXC, включая саму `320-ai-control`.

Через SSH агент может:

- устанавливать и обновлять пакеты;
- создавать пользователей и каталоги;
- читать и изменять конфигурационные файлы;
- управлять `systemd`;
- устанавливать Docker и Docker Compose;
- создавать и редактировать Compose-файлы;
- запускать, обновлять и удалять контейнеры;
- читать логи;
- проверять health/status;
- разворачивать MCP и другие приложения;
- выполнять административные операции, необходимые для поставленной задачи.

Один и тот же подход применяется к `320-ai-control`, `300-app-services`, `330-ai-services`, `400-monitoring`, новым VM/LXC и другим управляемым гостям.

Отдельный `guest-mcp` не требуется, если задачу нормально решает SSH.

## Развертывание новой VM

Пример команды:

```text
Создай новую VM Debian, выдели ей 2 CPU и 4 ГБ RAM,
установи Docker и разверни в Docker новую копию Home Assistant.
```

Ожидаемая последовательность:

```text
1. Proxmox MCP
   → создать VM
   → настроить CPU/RAM/disk/network

2. дождаться загрузки VM

3. SSH
   → подключиться к новой VM
   → настроить ОС
   → установить Docker и Compose

4. SSH
   → передать файлы из каталога соответствующего guest
   → docker compose up -d

5. SSH
   → проверить docker compose ps
   → проверить health/logs

6. обновить документацию и конфигурацию в Git
```

## Размещение файлов в репозитории

Для каждого гостя используется единый каталог `files/`, который повторяет целевую файловую систему VM/LXC.

Отдельного `services/` нет: исходный код, Dockerfile, Compose-файлы, агенты, MCP и системные конфиги — всё хранится под `files/` в том месте, куда должно быть развернуто на госте.

Например:

```text
guests/321-ha-test/
├── README.md
├── guest.yaml
└── files/
    └── opt/
        └── home-assistant/
            └── compose.yaml
```

соответствует:

```text
/opt/home-assistant/compose.yaml
```

Для самого `320-ai-control`:

```text
guests/320-ai-control/files/opt/ai-control/agents/hermes/
```

соответствует:

```text
/opt/ai-control/agents/hermes/
```

`320-ai-control` хранит только собственные файлы управляющего контура, а не копии конфигурации приложений других VM.

## Решение по `deploy-mcp`

`deploy-mcp` удаляется из целевой архитектуры.

Основной путь развертывания на VM/LXC:

```text
SSH → files → Docker / Compose / systemd
```

Новые компоненты и документация не должны зависеть от `deploy-mcp`.

Если когда-нибудь появится специализированный deploy-инструмент, он должен решать конкретную проблему и давать заметное преимущество по сравнению с SSH, а не существовать только как дополнительный слой абстракции.

## Ansible

Ansible не является обязательной частью архитектуры. Его можно использовать позже для повторяемых процедур, например подготовки Debian VM или установки одинакового набора ПО на несколько хостов. В обычной схеме Ansible использует SSH как транспорт.

## Модель прав

Агент рассматривается как администратор домашней инфраструктуры и должен иметь достаточные права для выполнения поставленных задач.

Предпочтительно:

- отдельный management-пользователь, например `infra-agent`;
- отдельный SSH-ключ для AI-control;
- public key добавлять новым VM через cloud-init;
- секреты и приватные ключи не хранить в Git;
- права Proxmox выдавать осознанно.

## Основная модель защиты

Защита строится прежде всего не на запрете административных операций, а на возможности быстро обнаружить ошибку и восстановиться.

Основные механизмы:

1. Git — источник истины для конфигурации, кода и истории изменений.
2. Proxmox snapshots — перед рискованными изменениями VM/LXC.
3. Proxmox backups — регулярное восстановимое резервное копирование.
4. Backup persistent data / Docker volumes — отдельно от конфигурации.
5. Резервные копии важных файлов перед автоматическим изменением, если они не покрываются Git.
6. Логирование действий агента.
7. Проверка после изменения — health, status, logs, доступность приложения.
8. Поэтапные изменения — сначала создать/изменить и проверить, потом удалять старое.

Принцип:

> Максимально простое управление, достаточные административные права и хорошая восстанавливаемость предпочтительнее множества специальных песочниц и промежуточных deploy-слоёв.

## Итоговая схема

```text
                         Пользователь
                              │
                    ┌─────────┴─────────┐
                    │                   │
                 Hermes             Agent Zero
                    │                   │
                    └─────────┬─────────┘
                              │
                   ┌──────────┴──────────┐
                   │                     │
                   ▼                     ▼
              Proxmox MCP               SSH
                   │                     │
                   ▼          ┌──────────┼──────────┐
              Proxmox API     │          │          │
                   │          ▼          ▼          ▼
                   │        VM 320     VM 330     новая VM
                   │          │          │          │
                   │       Docker     Docker      Docker
                   │          │          │          │
                   └──── VM/LXC lifecycle      приложения
```

Главный принцип:

> Proxmox MCP управляет жизненным циклом VM/LXC, SSH управляет всем внутри гостевых систем, файлы каждого гостя хранятся единым деревом `files/`, а надёжность обеспечивается Git, snapshots, backups и проверяемым откатом.
