# ADR 001 — Простая модель управления инфраструктурой

## Статус

Принято.

## Контекст

`320-ai-control` должен быть не только VM с одним агентом, а центральной точкой управления домашней инфраструктурой. Агентов может быть несколько. Они должны уметь:

- создавать и настраивать VM/LXC в Proxmox;
- устанавливать ПО внутри существующих и новых гостевых систем;
- устанавливать Docker и Docker Compose;
- разворачивать и сопровождать Docker-сервисы на разных VM/LXC;
- устанавливать новые MCP, инфраструктурные и прикладные сервисы;
- изменять конфигурации этих компонентов;
- проверять состояние, логи и результат развертывания.

Ранее для Docker на `320-ai-control` использовался специальный `deploy-mcp`, который был промежуточным слоем между агентом и Docker socket. Эта схема давала дополнительные ограничения, но одновременно создавала отдельный механизм деплоя только для одной VM и усложняла общую архитектуру.

## Решение

Не строить отдельную песочницу и отдельную систему деплоя для каждого типа ресурса.

Использовать два основных механизма управления:

```text
AI-агент
   │
   ├── Proxmox MCP
   │      └── управление уровнем виртуализации
   │
   └── SSH
          └── управление операционной системой и приложениями внутри VM/LXC
```

### Proxmox MCP

Используется для операций уровня Proxmox:

- создать VM/LXC;
- клонировать шаблон;
- настроить CPU/RAM/disk;
- настроить сетевые параметры;
- start/stop/reboot;
- snapshots;
- backups;
- удалить VM/LXC;
- другие операции жизненного цикла гостевой системы.

Proxmox MCP не должен становиться универсальным способом выполнения обычных команд внутри гостевой ОС.

### SSH

SSH является основным универсальным каналом управления внутри VM/LXC, включая саму `320-ai-control`.

Через SSH агент может:

- устанавливать и обновлять пакеты;
- создавать пользователей и каталоги;
- читать и изменять конфигурационные файлы;
- управлять `systemd`;
- устанавливать Docker;
- устанавливать Docker Compose;
- создавать и редактировать Compose-файлы;
- запускать, обновлять и удалять контейнеры;
- читать логи;
- проверять health/status;
- разворачивать MCP и другие сервисы;
- выполнять прочие административные операции, необходимые для поставленной задачи.

Один и тот же подход применяется к:

```text
320-ai-control
300-app-services
330-ai-services
400-monitoring
новым VM/LXC
и другим управляемым гостям
```

Не требуется отдельный `guest-mcp` только ради выполнения команд внутри гостевой системы, если эту задачу нормально решает SSH.

## Развертывание новой VM

Целевой сценарий должен выполняться агентом целиком.

Пример пользовательской команды:

```text
Создай новую VM Debian, выдели ей 2 CPU и 4 ГБ RAM,
установи Docker и разверни в Docker новую копию Home Assistant.
```

Ожидаемая последовательность:

```text
1. Proxmox MCP
   → создать VM
   → настроить CPU/RAM/disk/network

2. дождаться загрузки VM

3. SSH
   → подключиться к новой VM
   → выполнить начальную настройку ОС
   → установить Docker и Compose

4. SSH
   → передать/создать файлы сервиса
   → docker compose up -d

5. SSH
   → проверить docker compose ps
   → проверить health/logs

6. обновить документацию и конфигурацию в Git
```

## Размещение файлов в репозитории

Файлы сервиса должны относиться к тому гостю, на котором сервис реально работает.

Например, если Home Assistant разворачивается на VM `321-ha-test`, его конфигурация должна храниться здесь:

```text
guests/321-ha-test/
├── README.md
├── guest.yaml
├── files/
└── services/
    └── home-assistant/
        └── compose.yaml
```

а не в:

```text
guests/320-ai-control/services/home-assistant/
```

`320-ai-control` хранит агентов и инструменты управления, а не копии конфигурации всех сервисов других VM.

## `deploy-mcp`

`deploy-mcp` больше не считается обязательной частью целевой архитектуры и не должен быть универсальным центром развертывания инфраструктуры.

Основной путь развертывания сервисов на VM/LXC:

```text
SSH → Docker / Compose / systemd / files
```

Существующий `deploy-mcp` может временно оставаться как legacy-компонент до завершения миграции или использоваться в экспериментах, но новые архитектурные решения не должны зависеть от него.

Если позже появится реальная необходимость в специализированном deploy-инструменте, он должен решать конкретную проблему и давать заметное преимущество по сравнению с обычным SSH, а не существовать только как дополнительный слой абстракции.

## Ansible

Ansible не является обязательной частью архитектуры.

Он может использоваться позже для повторяемых типовых процедур, например:

- подготовить чистую Debian VM;
- установить стандартный набор пакетов;
- установить Docker;
- применить одинаковую конфигурацию к нескольким хостам.

При этом Ansible в обычной схеме сам использует SSH как транспорт. Поэтому на первом этапе достаточно SSH и обычных скриптов/команд.

## Модель прав

Цель — не ограничивать агента настолько, чтобы он постоянно упирался в песочницу.

Агент рассматривается как администратор домашней инфраструктуры и должен иметь достаточные права для выполнения поставленных задач.

При этом доступы следует разделять технически там, где это удобно:

- отдельный management-пользователь, например `infra-agent`;
- отдельный SSH-ключ для AI-control;
- public key можно добавлять при создании VM через cloud-init;
- секреты и приватные ключи не хранить в Git;
- права Proxmox выдавать осознанно и расширять по мере необходимости.

## Основная модель защиты

Защита строится прежде всего не на запрете агенту выполнять административные операции, а на возможности быстро обнаружить ошибку и восстановиться.

Основные механизмы:

1. **Git** — источник истины для конфигурации, кода и истории изменений.
2. **Proxmox snapshots** — перед рискованными изменениями VM/LXC.
3. **Proxmox backups** — регулярное восстановимое резервное копирование гостевых систем.
4. **Backup persistent data / Docker volumes** — отдельно от конфигурации.
5. **Резервные копии важных файлов перед автоматическим изменением**, если изменение не покрывается Git.
6. **Логирование действий агента** — чтобы можно было понять, что было изменено.
7. **Проверка после изменения** — health, status, logs, доступность сервиса.
8. **Поэтапные изменения** — сначала создать/изменить, затем проверить, только после этого удалять старое.

Принцип:

> Максимально простое управление, достаточные административные права и хорошая восстанавливаемость предпочтительнее множества специальных песочниц и промежуточных deploy-слоев.

## Последствия решения

Преимущества:

- один понятный способ управления Linux-гостями;
- одинаковая логика для `320` и остальных VM/LXC;
- агент способен самостоятельно создавать инфраструктуру от VM до приложения;
- меньше собственных промежуточных сервисов;
- меньше кода, который нужно поддерживать;
- проще диагностика;
- проще перенос сервисов между VM;
- не требуется устанавливать deploy-agent на каждый Docker host.

Цена решения:

- SSH-пользователь агента получает широкие административные возможности;
- ошибка агента потенциально может повредить гостевую систему или сервис;
- поэтому snapshots, backups, Git и проверка изменений становятся обязательной частью эксплуатационной модели.

## Итоговая схема

```text
                         Пользователь
                              │
                    ┌─────────┴─────────┐
                    │                   │
                 Hermes             Agent Zero
                    │                   │
                    └─────────┬─────────┘
                              │
                   ┌──────────┴──────────┐
                   │                     │
                   ▼                     ▼
              Proxmox MCP               SSH
                   │                     │
                   ▼          ┌──────────┼──────────┐
              Proxmox API     │          │          │
                   │          ▼          ▼          ▼
                   │        VM 320     VM 330     новая VM
                   │          │          │          │
                   │       Docker     Docker      Docker
                   │          │          │          │
                   └──── VM/LXC lifecycle      приложения
```

Главный принцип:

> Proxmox MCP управляет жизненным циклом VM/LXC, SSH управляет всем внутри гостевых систем, а надежность обеспечивается Git, snapshots, backups и проверяемым откатом, а не лишними песочницами.
