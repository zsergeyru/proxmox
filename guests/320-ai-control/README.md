# 320 — ai-control (bootstrap)

`320-ai-control` — текущий bootstrap-узел центрального AI-контура управления домашней инфраструктурой.

**Целевой узел:** `301-ai-control`.  
`320` сохраняется до тех пор, пока `301` не будет развёрнут, проверен и принят как основной control plane.

Здесь работают один или несколько AI-агентов, которые должны уметь управлять не только собственными контейнерами, но и создавать VM/LXC в Proxmox, настраивать гостевые ОС, устанавливать Docker и разворачивать приложения на других VM/LXC.

## Основной принцип управления

Используются два базовых механизма:

```text
AI-агент
   │
   ├── Proxmox MCP
   │      └── VM/LXC, ресурсы, lifecycle, snapshots, backups
   │
   └── SSH
          └── ОС, пакеты, файлы, systemd, Docker/Compose и приложения
```

От отдельного универсального `deploy-mcp` отказались. Docker на `320-ai-control` и остальных управляемых VM/LXC обслуживается через SSH и обычные Docker/Docker Compose команды.

Подробное решение: [`decisions/001-simple-management-model.md`](decisions/001-simple-management-model.md).

## Структура каталога

`320-ai-control` следует общему правилу `guests/`: всё, что должно существовать внутри VM, хранится в `rootfs/`, а путь после `rootfs/` повторяет абсолютный путь на гостевой системе.

```text
guests/320-ai-control/
├── README.md
├── guest.yaml
├── decisions/
│   └── 001-simple-management-model.md
└── rootfs/
    └── opt/
        └── ai-control/
            ├── agents/
            │   ├── README.md
            │   ├── hermes/
            │   └── agent-zero/
            ├── mcp/
            │   └── README.md
            └── interfaces/
                └── README.md
```

Например:

```text
guests/320-ai-control/rootfs/opt/ai-control/agents/hermes/
→ /opt/ai-control/agents/hermes/
```

`rootfs/` не создаётся как каталог внутри VM. Его содержимое разворачивается относительно `/` гостевой системы.

Отдельного каталога `services/` нет: агенты, MCP, web-интерфейсы, Compose-файлы, исходный код и системные конфиги размещаются под `rootfs/` по своим реальным путям.

## `decisions/`

Здесь хранится журнал важных архитектурных решений. Текущий ADR фиксирует:

- Proxmox MCP для уровня виртуализации;
- SSH для управления внутри VM/LXC;
- отказ от универсального `deploy-mcp`;
- единое дерево `rootfs/`;
- модель защиты через Git, snapshots, backups, проверку и откат.

## `/opt/ai-control/agents/`

Текущая модель:

- `hermes/` — основной агент;
- `agent-zero/` — второй агент для тестов и отдельных сценариев;
- новые агенты добавляются отдельными подкаталогами.

Файлы конкретного агента хранятся рядом с ним: `AGENTS.md`, Dockerfile, конфиги, скрипты, документация и `STATUS.md` при необходимости.

## `/opt/ai-control/mcp/`

Исходники и конфигурации MCP, используемых агентами. Ключевой MCP — Proxmox MCP. Другие специализированные MCP добавляются только там, где они удобнее SSH или прямого API.

## `/opt/ai-control/interfaces/`

Пользовательские интерфейсы к AI-агентам: web UI, голосовой интерфейс, agent gateway/API и другие компоненты взаимодействия.

Общие STT/TTS-функции относятся к `331-ai-services`, потому что ими могут пользоваться также Home Assistant, голосовые панели и другие приложения.

## Размещение файлов других VM/LXC

`320-ai-control` хранит только собственные файлы управляющего контура. Файлы приложения, работающего на другой VM/LXC, находятся в каталоге соответствующего гостя.

Например:

```text
guests/202-ha-test/
├── README.md
├── guest.yaml
└── rootfs/
    └── opt/
        └── home-assistant/
            └── compose.yaml
```

Сам monorepo целиком на каждую VM копировать не требуется.

## SSH

SSH — основной универсальный канал управления внутри VM/LXC, включая саму `320-ai-control`.

Через SSH агент должен уметь устанавливать пакеты, управлять файлами и `systemd`, устанавливать Docker/Compose, управлять контейнерами и volumes, читать логи, проверять состояние и устанавливать новые приложения и MCP.

Предпочтительная модель доступа:

- отдельный management-пользователь, например `infra-agent`;
- отдельный SSH-ключ для AI-control;
- public key добавляется в новые VM через cloud-init;
- секреты и приватные ключи не хранятся в Git.

## Ansible

Ansible не является обязательной частью архитектуры. При необходимости он используется поверх SSH для повторяемых процедур.

## Модель защиты

Агенты получают достаточные административные права для самостоятельной работы. Основная защита строится на восстанавливаемости:

1. Git — источник истины для конфигурации и кода.
2. Proxmox snapshots — перед рискованными изменениями.
3. Регулярные Proxmox backups.
4. Отдельные backup persistent data и Docker volumes.
5. Резервные копии критичных файлов перед изменением при необходимости.
6. Логирование действий агента.
7. Проверка health/status/logs после изменения.
8. Поэтапные изменения: сначала создать/изменить и проверить, затем удалять старое.

## Переход на `301-ai-control`

`320` не нужно переименовывать или удалять заранее. Миграция выполняется так:

```text
зафиксировать рабочую конфигурацию 320 в Git
→ создать 301 по guests/301-ai-control/guest.yaml
→ развернуть воспроизводимые файлы через rootfs
→ проверить Hermes, MCP, SSH и управление остальными гостями
→ назначить 301 основным control plane
→ отдельным решением вывести 320 из эксплуатации
```

## Секреты

В Git запрещено хранить пароли, API tokens, Proxmox tokens, приватные SSH-ключи и другие секреты. В репозитории хранятся только конфигурация, пути, шаблоны и описание требуемых секретов.
