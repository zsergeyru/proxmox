# 320 — ai-control

`320-ai-control` — центральный AI-контур управления домашней инфраструктурой.

Здесь работают один или несколько AI-агентов, которые должны уметь управлять не только собственными контейнерами, но и создавать VM/LXC в Proxmox, настраивать гостевые ОС, устанавливать Docker и разворачивать приложения на других VM/LXC.

## Основной принцип управления

Используются два базовых механизма:

```text
AI-агент
   │
   ├── Proxmox MCP
   │      └── уровень виртуализации: VM/LXC, ресурсы, lifecycle, snapshots, backups
   │
   └── SSH
          └── всё внутри гостевой ОС: пакеты, файлы, systemd, Docker/Compose, приложения
```

От отдельного универсального `deploy-mcp` отказались. Docker на `320-ai-control` и на остальных управляемых VM/LXC обслуживается через SSH и обычные Docker / Docker Compose команды.

Подробное решение: [`decisions/001-simple-management-model.md`](decisions/001-simple-management-model.md).

## Структура каталога

`320-ai-control` следует общему правилу `guests/`: всё, что должно существовать внутри VM, хранится в `rootfs/`, а путь после `rootfs/` повторяет абсолютный путь на гостевой системе.

```text
guests/320-ai-control/
├── README.md
├── guest.yaml                 # когда будет утверждён формат
├── decisions/
│   └── 001-simple-management-model.md
└── rootfs/
    └── opt/
        └── ai-control/
            ├── agents/
            │   ├── README.md
            │   ├── hermes/
            │   └── agent-zero/
            ├── mcp/
            │   └── README.md
            └── interfaces/
                └── README.md
```

Например:

```text
guests/320-ai-control/rootfs/opt/ai-control/agents/hermes/
```

соответствует реальному пути:

```text
/opt/ai-control/agents/hermes/
```

`rootfs/` — это не каталог, который создаётся внутри VM. Его содержимое разворачивается относительно корня `/` гостевой системы.

Отдельного каталога `services/` нет: агенты, MCP, web-интерфейсы, Compose-файлы, исходный код и другие приложения — это такие же файлы целевой VM и поэтому размещаются под `rootfs/` по своим реальным путям.

Если позже понадобятся системные конфиги самой VM, они также помещаются в `rootfs/`. Например:

```text
rootfs/etc/ssh/sshd_config.d/90-ai-control.conf
→ /etc/ssh/sshd_config.d/90-ai-control.conf

rootfs/etc/docker/daemon.json
→ /etc/docker/daemon.json
```

## `decisions/`

Журнал важных архитектурных решений по `320-ai-control`.

Файлы здесь фиксируют, какую проблему решали, какой вариант выбрали, от каких альтернатив отказались и почему. Это позволяет позже понять не только текущую схему, но и причины её появления.

Текущий `001-simple-management-model.md` фиксирует выбор Proxmox MCP для уровня виртуализации, SSH для управления внутри VM/LXC, отказ от `deploy-mcp` и модель защиты через Git, snapshots, backups и откат.

## `/opt/ai-control/agents/`

AI-агенты управляющего контура.

Текущая модель:

- `hermes/` — основной агент;
- `agent-zero/` — второй агент для тестов и возможного использования в отдельных сценариях;
- новые агенты добавляются отдельными подкаталогами.

Файлы конкретного агента хранятся рядом с ним: `AGENTS.md`, Dockerfile, конфиги, скрипты, документация, `STATUS.md` и другие относящиеся только к нему файлы.

## `/opt/ai-control/mcp/`

Исходники и конфигурации MCP, используемых агентами.

Агент должен иметь возможность устанавливать, настраивать и обновлять нужные ему MCP. Ключевой MCP — Proxmox MCP, через который выполняются операции уровня виртуализации.

Специализированный MCP имеет смысл там, где он реально удобнее обычного SSH или прямого API.

## `/opt/ai-control/interfaces/`

Пользовательские интерфейсы к AI-агентам: web UI, голосовой интерфейс, agent gateway/API и другие интерфейсные компоненты.

Общие STT/TTS-функции сюда не относятся. Они размещаются в `330-ai-services`, потому что могут использоваться также Home Assistant, голосовыми панелями и другими приложениями.

## Роль агентов

Hermes и будущие агенты рассматриваются как администраторы домашней инфраструктуры.

Целевая зона ответственности включает Proxmox, VM/LXC, Docker, Home Assistant, сеть, VPN/DNS, мониторинг, инфраструктурные и прикладные приложения.

Пример целевой команды пользователя:

```text
Создай новую Debian VM, выдели 2 CPU и 4 ГБ RAM,
установи Docker и разверни новую копию Home Assistant.
```

Ожидаемый сценарий:

```text
1. Proxmox MCP
   → создать VM
   → настроить CPU/RAM/disk/network

2. SSH
   → подключиться к новой VM
   → настроить ОС
   → установить Docker и Compose

3. SSH
   → перенести нужное содержимое rootfs/ соответствующего guest
   → docker compose up -d

4. SSH
   → проверить status / health / logs

5. сохранить актуальную конфигурацию и документацию в Git
```

## Размещение файлов других VM/LXC

`320-ai-control` хранит только собственные файлы управляющего контура. Файлы приложения, работающего на другой VM/LXC, должны находиться в каталоге соответствующего гостя.

Например для `321-ha-test`:

```text
guests/321-ha-test/
├── README.md
├── guest.yaml
└── rootfs/
    └── opt/
        └── home-assistant/
            └── compose.yaml
```

Сам репозиторий целиком на каждую VM копировать не требуется.

## SSH

SSH — основной универсальный канал управления внутри VM/LXC, включая саму `320-ai-control`.

Через SSH агент должен уметь устанавливать пакеты, управлять файлами и `systemd`, устанавливать Docker/Compose, управлять контейнерами и volumes, читать логи, проверять состояние и устанавливать новые приложения и MCP.

Предпочтительная модель доступа:

- отдельный management-пользователь, например `infra-agent`;
- отдельный SSH-ключ для AI-control;
- public key добавляется в новые VM через cloud-init;
- секреты и приватные ключи не хранятся в Git.

## Ansible

Ansible не является обязательной частью архитектуры. При необходимости его можно использовать позже для повторяемых сценариев поверх SSH.

## Модель защиты

Агенты не ограничиваются множеством специальных песочниц. Им должны быть доступны достаточные административные права для самостоятельной работы.

Основная защита строится на восстанавливаемости:

1. Git — источник истины для конфигурации и кода.
2. Proxmox snapshots — перед рискованными изменениями.
3. Регулярные Proxmox backups.
4. Отдельные backup persistent data и Docker volumes.
5. Резервные копии важных файлов перед изменением, если они не покрываются Git.
6. Логирование действий агента.
7. Проверка health/status/logs после изменения.
8. Поэтапные изменения: сначала создать/изменить и проверить, затем удалять старое.

Принцип:

> Максимально простое управление, достаточные административные права и хорошая восстанавливаемость предпочтительнее множества специальных песочниц и промежуточных deploy-слоёв.

## Секреты

В Git запрещено хранить пароли, API tokens, Proxmox tokens, приватные SSH-ключи и другие секреты. В репозитории хранятся только конфигурация, пути, шаблоны и описание того, какие секреты требуются компоненту.
