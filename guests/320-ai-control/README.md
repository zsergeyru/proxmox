# Архитектура AI-агента и управление инфраструктурой

Документ фиксирует решения и принципы, принятые при настройке Hermes, `deploy-mcp`, Proxmox MCP, локальных моделей и будущих агентов.

## 1. Роль Hermes

Hermes рассматривается не как «Docker-агент», а как общий администратор домашней инфраструктуры.

Целевая зона ответственности:

- Proxmox;
- VM;
- LXC;
- Docker;
- Home Assistant;
- сеть;
- VPN/DNS;
- мониторинг;
- другие сервисы.

Главный принцип:

> Сначала определить, какой системе принадлежит ресурс, затем использовать инструмент управления именно этой системой.

Примеры маршрутизации:

- Docker на `ai-agent` → `deploy-mcp`;
- Proxmox → `proxmox-mcp` / `proxmox-full`;
- команды внутри VM/LXC → SSH / QEMU Guest Agent / `pct exec` / отдельный management MCP;
- Home Assistant → HA-инструменты;
- сеть → будущий `network-mcp`.

Локальный Terminal Hermes не должен считаться терминалом Proxmox-хоста, VM или LXC.

---

## 2. Hermes работает внутри собственного Docker-контейнера

Hermes видит собственную файловую систему контейнера.

Если путь не виден через Terminal Hermes, это не означает, что такого пути нет на хосте.

Неправильная логика:

```text
не вижу файл
→ find /
→ sudo
→ создать заглушку
```

Правильная логика:

```text
не вижу host resource
→ определить, какой MCP имеет к нему доступ
→ использовать этот MCP
```

Не использовать широкие поиски `find /` для поиска host-файлов и секретов, которые намеренно не примонтированы в контейнер Hermes.

Не использовать `sudo` как способ обхода границ доступа.

---

## 3. Один основной Compose

Основной Docker Compose-файл один:

```text
/opt/ai-control/compose.yaml
```

В нём описываются все контейнеры этой VM:

- `hermes`;
- `deploy-mcp`;
- `proxmox-mcp`;
- `proxmox-full`;
- `agent-zero`;
- мониторинг;
- будущие сервисы.

`compose.yaml` является источником истины по Docker-сервисам:

- image / build;
- ports;
- volumes;
- environment;
- restart policy;
- labels;
- лимиты;
- сети и другие параметры.

От отдельного `managed/compose.yaml` отказались.

---

## 4. Структура `/opt/ai-control`

Целевая структура:

```text
/opt/ai-control/
├── compose.yaml
├── hermes/
│   ├── data/
│   └── AGENTS.md
├── mcp/
│   ├── deploy/
│   └── proxmox/
│       └── secrets/
├── services/
│   ├── proxmox-full/
│   ├── agent-zero/
│   └── ...
└── archive/
```

Старая папка `managed/` — переходное наследие, после окончательной проверки может быть удалена.

---

## 5. `services/` — рабочая территория Hermes

Hermes имеет read/write доступ к:

```text
/opt/ai-control/services/
```

Здесь Hermes может напрямую создавать и изменять:

- `Dockerfile`;
- `entrypoint.sh`;
- исходный код;
- конфиги;
- `README.md`;
- `STATUS.md`;
- другие файлы конкретного сервиса.

Разделение ответственности:

```text
файлы сервиса
→ Hermes редактирует напрямую

Docker/Compose lifecycle
→ deploy-mcp
```

---

## 6. `deploy-mcp` — единственная точка управления Docker

Hermes не получает Docker socket напрямую.

Схема:

```text
Hermes
  ↓
deploy-mcp
  ↓
Docker socket
  ↓
Docker / Compose
```

`deploy-mcp` уже умеет:

- показывать Compose-сервисы;
- создавать сервис;
- обновлять сервис;
- выбирать свободный внешний порт;
- создавать persistent volume;
- собирать image;
- запускать сервис;
- перезапускать сервис;
- показывать логи;
- удалять обычный сервис;
- подключать разрешённый secret-файл.

Проверено реальными тестовыми контейнерами.

---

## 7. Hermes сам занимается портами и volumes

Пользователь не должен вручную писать типовой Compose для каждого нового сервиса.

Пример желаемого пользовательского запроса:

```text
Поставь Uptime Kuma.
```

Hermes через `deploy-mcp` должен сам:

1. определить image;
2. выбрать свободный порт;
3. создать volume при необходимости;
4. добавить сервис в Compose;
5. запустить его;
6. проверить состояние;
7. сообщить URL.

---

## 8. Автовыбор портов

Для автоматически создаваемых сервисов используется диапазон:

```text
18000–18999
```

`deploy-mcp` проверяет занятые порты и выбирает свободный.

Тесты:

- `18000` → `test-hello`;
- `18001` → следующий тестовый сервис / `proxmox-full` в ходе настройки.

---

## 9. Защищённые сервисы

От whitelist разрешённых сервисов отказались.

Используется модель default allow + явная защита критичных сервисов.

Label:

```yaml
labels:
  hermes.protected: "true"
```

Сейчас защищены:

- `hermes`;
- `deploy-mcp`;
- `proxmox-mcp`.

Для `hermes.protected=true` запрещены:

- build;
- update;
- restart;
- remove.

Hermes не должен обходить этот запрет через Terminal, прямой Docker или другой механизм.

Защита проверена: попытка перезапустить `proxmox-mcp` через `deploy-mcp` была отклонена.

---

## 10. Удаление сервисов

Добавлен инструмент:

```text
deploy_remove_service
```

Он:

- останавливает контейнер;
- удаляет контейнер;
- удаляет запись сервиса из `compose.yaml`;
- делает backup Compose.

По умолчанию сохраняются:

- named volumes;
- `services/<name>/`.

То есть удаление сервиса не должно автоматически уничтожать данные и исходники.

---

## 11. Backup Compose

Перед автоматическим изменением Compose `deploy-mcp` делает резервную копию в:

```text
/opt/ai-control/archive/compose-backups/
```

Автоматические изменения инфраструктуры должны оставаться обратимыми.

---

## 12. Секреты не должны быть доступны Hermes напрямую

Hermes не должен видеть напрямую:

```text
/opt/ai-control/mcp/*/secrets/
```

Например:

```text
/opt/ai-control/mcp/proxmox/secrets/proxmox_token
```

То, что такой файл не виден из Terminal Hermes, — нормальное поведение.

Запрещённая логика:

```text
не вижу secret
→ искать через find /
→ sudo
→ docker inspect
→ создать новый secret
→ создать пустую заглушку
→ попросить пользователя вставить токен
```

Правильная схема:

```text
Hermes знает host path
        ↓
deploy_create_service(secret_files=...)
        ↓
deploy-mcp проверяет source-файл на host
        ↓
монтирует его read-only
```

---

## 13. `secret_files`

`deploy_create_service` расширен параметром:

```text
secret_files
```

Пример:

```text
source:
/opt/ai-control/mcp/proxmox/secrets/proxmox_token

target:
/run/secrets/proxmox_token
```

Ограничения:

- source только из `/opt/ai-control/mcp/*/secrets/`;
- target только внутри `/run/secrets/`;
- mount только read-only.

Секрет не должен появляться:

- как значение в `compose.yaml`;
- в Dockerfile;
- в исходном коде;
- в `services/`;
- в чате;
- в логах.

---

## 14. Если приложение требует секрет как environment variable

Если приложение ожидает, например:

```text
PROXMOX_TOKEN_SECRET
```

используется `entrypoint.sh` внутри контейнера:

```sh
export PROXMOX_TOKEN_SECRET="$(cat /run/secrets/proxmox_token)"
exec ...
```

Значение существует только внутри процесса контейнера и не хранится открытым в Compose.

---

## 15. `proxmox-mcp` и `proxmox-full`

Существующий `proxmox-mcp` сохраняется как защищённый базовый read-only MCP.

Дополнительно устанавливается:

```text
proxmox-full
```

на базе:

```text
gordcurrie/proxmox-mcp
```

Старый MCP не удаляется, пока новый полностью не проверен.

Для первого этапа `proxmox-full` запускается с destructive-функциями отключёнными:

```text
PROXMOX_ALLOW_DESTRUCTIVE=false
```

---

## 16. Права Proxmox

Используется токен:

```text
ai-agent@pve!infra-agent
```

На текущем этапе он имеет read-only роль.

Это нормально для первичной проверки MCP.

Позже отдельно определить права для:

- создания VM;
- создания LXC;
- изменения CPU/RAM/disk;
- snapshots;
- backups;
- start/stop/reboot;
- других управляющих операций.

Не выдавать агенту максимальные права заранее.

---

## 17. Управление программами внутри VM/LXC — отдельный уровень

Важно:

```text
создать LXC
≠
установить пакеты внутри LXC
```

Proxmox MCP управляет объектом VM/LXC:

- создать;
- запустить;
- CPU;
- RAM;
- disk;
- network;
- snapshot и т.д.

Для команд внутри гостевой системы нужен отдельный канал:

- SSH;
- QEMU Guest Agent;
- `pct exec`;
- отдельный guest-management MCP.

Целевая задача:

```text
Создай LXC Debian, выдели 2 ГБ RAM, установи Docker и сервис X.
```

Hermes должен сам разбить её минимум на две фазы:

1. создать и настроить LXC через Proxmox;
2. установить ПО внутри гостя через подходящий guest execution механизм.

---

## 18. Глобальный `AGENTS.md`

Для глобальных правил Hermes создан файл:

```text
/opt/ai-control/hermes/AGENTS.md
```

Он монтируется read-only в:

```text
/opt/hermes/AGENTS.md
```

Правила пишутся на русском языке.

В `AGENTS.md` фиксируются:

- маршрутизация по инструментам;
- смысл локального Terminal;
- правила работы с secret-файлами;
- protected services;
- работа с VM/LXC;
- запрет на обход границ доступа;
- поведение при нехватке нужного инструмента.

---

## 19. `STATUS.md` для длинных задач

Для сложных сервисов и длительных задач использовать:

```text
services/<service>/STATUS.md
```

Например:

```text
services/proxmox-full/STATUS.md
```

В нём хранить:

- что уже сделано;
- какие решения приняты;
- какие файлы созданы;
- что осталось сделать;
- текущие проблемы.

Это позволяет продолжить работу даже после потери/прерывания сессии агента.

---

## 20. Разделение памяти

Принята модель:

```text
AGENTS.md
→ постоянные правила поведения

MEMORY.md
→ ключевые долгоживущие факты

STATUS.md
→ состояние конкретной задачи или сервиса

история сессии
→ подробный ход разговора и tool calls
```

Не хранить всю историю инфраструктуры только в контексте текущего чата.

---

## 21. Hermes sessions

Случайное прерывание текущего агентного цикла обычно не удаляет чат.

Сессия остаётся, но выполнение может остановиться.

Можно использовать команду смыслом:

```text
Продолжай с того места, где остановился. Не начинай всё заново.
```

Для надёжности длинные задачи всё равно должны иметь `STATUS.md`.

---

## 22. Кэш схемы MCP tools в Hermes

Если в MCP:

- добавлен новый tool;
- удалён tool;
- изменены параметры tool;

Hermes может продолжать использовать старую схему инструментов.

Новый чат не всегда обновляет schema.

Надёжный способ после изменения tool schema:

```text
перезапустить Hermes gateway
```

Если меняется только внутренняя логика существующего tool без изменения schema, перезапуск обычно не нужен.

---

## 23. Reasoning у Qwen

Для модели:

```text
qwen/qwen3.6-35b-a3b
```

LM Studio показал:

```text
Reasoning setting 'medium' is not supported
Supported settings: 'on', 'off'
Falling back to 'on'
```

Следовательно, для этой модели корректнее сравнивать:

```text
reasoning ON
reasoning OFF
```

а не `low / medium / high`.

---

## 24. Reasoning у gpt-oss

Для `gpt-oss-20b` уровни reasoning реально влияют на поведение.

Наблюдение:

- `medium` мог надолго уходить в агентный цикл;
- `low` выполнял простые инфраструктурные задачи значительно быстрее.

Reasoning mode нужно подбирать отдельно для каждой модели.

---

## 25. Скорость агента — не только tok/s

Нужно оценивать:

- time to first token;
- prompt prefill;
- reasoning tokens;
- количество tool calls;
- количество агентных циклов;
- полное время до полезного результата.

Хороший специализированный MCP tool может ускорить задачу сильнее, чем несколько дополнительных tokens/sec.

Пример из тестов:

```text
старый путь
→ около 20 tool calls

правильный специализированный tool
→ около 2 tool calls
```

---

## 26. Потоковый вывод

Для текущей Qwen потоковый вывод возвращён:

```text
streaming: true
```

`streaming: false` ранее использовался как workaround для `gpt-oss`, когда tool calls могли выводиться сырым текстом.

Этот workaround не следует автоматически переносить на все модели.

---

## 27. Контекст модели

Hermes работает с большим окном контекста, около:

```text
65.5K
```

Это максимальная ёмкость, а не желаемый постоянный размер prompt.

Длинные сессии увеличивают prefill и задержку.

После завершения больших задач лучше:

1. зафиксировать состояние в `STATUS.md`;
2. начать новую сессию.

---

## 28. Локальные модели

Основные текущие кандидаты:

- `gpt-oss-20b`;
- `Qwen3.6-35B-A3B`.

Qwen показала более устойчивое агентное поведение, несмотря на более низкий tok/s.

Критерий выбора локальной модели:

```text
не максимальное количество параметров,
а качество tool use + reasoning + итоговое время задачи
```

Также планируется тестировать другие модели, подходящие под 16 ГБ VRAM и native/tool calling.

---

## 29. LM Studio

Основной локальный inference server:

```text
http://192.168.1.178:1234/v1
```

GPU:

```text
RTX 5060 Ti 16 GB
```

Принципы оптимизации:

- максимальный GPU offload;
- Flash Attention ON;
- KV cache на GPU, если это выгодно по памяти;
- concurrent predictions = 1 для Hermes;
- разумный context;
- не раздувать историю;
- тестировать quantization;
- сравнивать reasoning ON/OFF;
- оценивать итоговое время агентной задачи.

Live logs LM Studio могут немного нагружать UI/CPU, но это не главный источник больших просадок inference.

---

## 30. Быстрый путь для Home Assistant

Простые команды умного дома не должны идти через тяжёлого агента.

Примеры:

```text
включи свет
закрыто ли окно?
```

Для них нужен быстрый путь через Home Assistant intents / Assist.

Hermes нужен для:

- диагностики;
- многошаговых действий;
- проектирования;
- управления инфраструктурой;
- сложных межсистемных задач.

---

## 31. Не переусложнять безопасность

От чрезмерной enterprise-архитектуры отказались.

Оставлены простые и полезные границы:

- protected services;
- отсутствие Docker socket у Hermes;
- `secret_files`;
- Compose через `deploy-mcp`;
- `services/` как рабочая зона Hermes;
- backup Compose.

Принцип:

> Минимальные понятные guardrails лучше сложной системы, которая мешает автоматизации.

---

## 32. Тест Agent Zero

Решено попробовать Agent Zero рядом с Hermes, не заменяя Hermes сразу.

Схема:

```text
LM Studio
  ├── Hermes
  └── Agent Zero
```

Так можно честно сравнивать агентов на:

- одной локальной модели;
- одном GPU;
- одном OpenAI-compatible API;
- одинаковых задачах.

Первый этап установки Agent Zero:

- отдельный Docker-сервис;
- без Docker socket;
- без privileged;
- без host network;
- без прямого доступа к Proxmox;
- без наших MCP;
- persistent storage;
- подключение к существующему LM Studio.

Сначала сравнить:

- Web UI;
- удобство;
- память;
- reasoning;
- скорость;
- устойчивость длинных задач.

Если Agent Zero окажется удобнее, затем подключить:

- `deploy-mcp`;
- `proxmox-full`;
- Home Assistant;
- `network-mcp`.

## Итоговая архитектура

```text
                        Пользователь
                             │
                   ┌─────────┴─────────┐
                   │                   │
                Hermes             Agent Zero
                   │               (тестируем)
                   │
       ┌───────────┼─────────────┐
       │           │             │
  deploy-mcp   proxmox-mcp   proxmox-full
       │                         │
       │                         │
Docker ai-agent              Proxmox API
       │                         │
 services/                  VM / LXC lifecycle
                                 │
                          guest execution
                        SSH / agent / pct
```

Главный принцип всей конструкции:

> LLM принимает решение и выбирает инструмент, а реальные границы полномочий обеспечивают MCP и инфраструктура, а не обещание модели вести себя аккуратно.

Второй главный принцип:

> Агент должен быть максимально самостоятельным в рутинной работе, чтобы пользователю не приходилось вручную выбирать порты, писать Compose, создавать volumes и выполнять типовые команды.
