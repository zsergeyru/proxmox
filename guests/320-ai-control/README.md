# 320 — ai-control

`320-ai-control` — центральный AI-контур управления домашней инфраструктурой.

Здесь работают один или несколько AI-агентов, которые должны уметь не только управлять собственными контейнерами, но и создавать VM/LXC в Proxmox, настраивать гостевые ОС, устанавливать Docker и разворачивать сервисы на других VM/LXC.

## Основной принцип управления

Используются два базовых механизма:

```text
AI-агент
   │
   ├── Proxmox MCP
   │      └── уровень виртуализации: VM/LXC, ресурсы, lifecycle, snapshots, backups
   │
   └── SSH
          └── всё внутри гостевой ОС: пакеты, файлы, systemd, Docker/Compose, приложения
```

От отдельного универсального `deploy-mcp` отказались. Docker на `320-ai-control` и на остальных управляемых VM/LXC должен обслуживаться тем же способом — через SSH и обычные Docker / Docker Compose команды.

Подробное решение: [`decisions/001-simple-management-model.md`](decisions/001-simple-management-model.md).

## Структура каталога

```text
guests/320-ai-control/

│   ├── README.md

├── mcp/
│   └── README.md
├── services/

└── interfaces/

```

### `decisions/`

Журнал принятых архитектурных решений по `320-ai-control`.

Файлы в этой папке фиксируют не только итоговую схему, но и контекст решения: какую проблему решали, какой вариант выбрали, от каких альтернатив отказались и какие последствия у этого выбора. Это нужно, чтобы позже можно было понять не только **как** устроена система, но и **почему** она устроена именно так.

Решения нумеруются последовательно:

```text
decisions/
├── 001-simple-management-model.md
├── 002-...
└── ...
```

Текущий `001-simple-management-model.md` фиксирует выбор простой модели управления инфраструктурой: Proxmox MCP для уровня виртуализации, SSH для управления внутри VM/LXC, отказ от `deploy-mcp` как отдельного универсального слоя и защиту через Git, snapshots, backups и возможность отката.

### `agents/`

AI-агенты управляющего контура.

Текущая модель:

- `hermes/` — основной агент;
- `agent-zero/` — второй агент для тестов и возможного использования в отдельных сценариях;
- новые агенты добавляются отдельными подкаталогами.

Конфигурация и файлы конкретного агента хранятся рядом с ним: `AGENTS.md`, Dockerfile, конфиги, скрипты, `STATUS.md` и другие относящиеся только к этому агенту файлы.

### `mcp/`

Исходники и конфигурации MCP-сервисов, используемых агентами.

MCP не делятся на отдельные «разрешённые» и «запрещённые» агенту категории. Агент должен иметь возможность устанавливать, настраивать и обновлять нужные ему MCP.

Ключевой MCP — Proxmox MCP, через который выполняются операции уровня виртуализации.

Специализированный MCP имеет смысл использовать там, где он реально удобнее и надёжнее обычного SSH или прямого API.

### `services/`

Вспомогательные сервисы, работающие именно внутри `320-ai-control` и не являющиеся агентами, MCP или пользовательскими интерфейсами.

Если сервис фактически работает на другой VM/LXC, его конфигурация и собственный код должны находиться в каталоге соответствующего гостя, а не здесь.

### `interfaces/`

Пользовательские интерфейсы к AI-агентам:

- web UI;
- голосовой интерфейс;
- agent gateway/API;
- другие интерфейсные компоненты.

Общие STT/TTS-сервисы сюда не относятся. Они размещаются в `330-ai-services`, потому что могут использоваться также Home Assistant, голосовыми панелями и другими приложениями.

## Роль агентов

Hermes и будущие агенты рассматриваются как администраторы домашней инфраструктуры.

Целевая зона ответственности включает:

- Proxmox;
- VM и LXC;
- Docker;
- Home Assistant;
- сеть;
- VPN/DNS;
- мониторинг;
- инфраструктурные сервисы;
- прикладные сервисы.

Пример целевой команды пользователя:

```text
Создай новую Debian VM, выдели 2 CPU и 4 ГБ RAM,
установи Docker и разверни новую копию Home Assistant.
```

Ожидаемый сценарий:

```text
1. Proxmox MCP
   → создать VM
   → настроить CPU/RAM/disk/network

2. SSH
   → подключиться к новой VM
   → настроить ОС
   → установить Docker и Compose

3. SSH
   → передать/создать конфигурацию сервиса
   → docker compose up -d

4. SSH
   → проверить status / health / logs

5. сохранить актуальную конфигурацию и документацию в Git
```

## Размещение файлов других VM/LXC

`320-ai-control` хранит агентов и инструменты управления, но не должен становиться складом конфигураций всех остальных VM.

Например, если новая копия Home Assistant работает на `321-ha-test`, её файлы должны находиться здесь:

```text
guests/321-ha-test/
├── README.md
├── guest.yaml
├── files/
└── services/
    └── home-assistant/
```

Структура `files/` повторяет абсолютные пути целевой гостевой ОС. Сам репозиторий целиком на каждую VM копировать не требуется.

## SSH

SSH — основной универсальный канал управления внутри VM/LXC, включая саму `320-ai-control`.

Через SSH агент должен уметь:

- устанавливать и обновлять пакеты;
- управлять файлами и каталогами;
- управлять `systemd`;
- устанавливать Docker и Compose;
- управлять контейнерами и volumes;
- создавать и редактировать Compose-файлы;
- читать логи;
- проверять состояние сервисов;
- устанавливать MCP и другие приложения.

Предпочтительная модель доступа:

- отдельный management-пользователь, например `infra-agent`;
- отдельный SSH-ключ для AI-control;
- public key добавляется в новые VM через cloud-init;
- секреты и приватные ключи не хранятся в Git.

## Ansible

Ansible не является обязательной частью архитектуры.

При необходимости он может позже использоваться для повторяемых сценариев — например, подготовки чистой Debian VM или установки Docker на много машин. В обычной схеме Ansible сам использует SSH как транспорт, поэтому на первом этапе достаточно SSH и обычных команд/скриптов.

## Модель защиты

Агенты не ограничиваются множеством специальных песочниц. Им должны быть доступны достаточные административные права для самостоятельной работы.

Основная защита строится на восстанавливаемости:

1. Git — источник истины для конфигурации и кода.
2. Proxmox snapshots — перед рискованными изменениями.
3. Регулярные Proxmox backups.
4. Отдельные backup persistent data и Docker volumes.
5. Резервные копии важных файлов перед изменением, если они не покрываются Git.
6. Логирование действий агента.
7. Проверка health/status/logs после изменения.
8. Поэтапные изменения: сначала создать/изменить и проверить, затем удалять старое.

Принцип:

> Максимально простое управление, достаточные административные права и хорошая восстанавливаемость предпочтительнее множества специальных песочниц и промежуточных deploy-слоёв.

## Общие AI-сервисы

Общие AI-функции, не зависящие от конкретного агента, вынесены в `330-ai-services`.

Туда относятся, например:

- Whisper / faster-whisper — общий STT API;
- TTS;
- в будущем другие общие inference/API-сервисы.

Это позволяет перезапускать или перестраивать `320-ai-control`, не останавливая общие голосовые функции Home Assistant и других систем.

## Секреты

В Git запрещено хранить:

- пароли;
- API tokens;
- Proxmox tokens;
- приватные SSH-ключи;
- другие секреты.

В репозитории хранятся только конфигурация, пути, шаблоны и описание того, какие секреты требуются компоненту.
