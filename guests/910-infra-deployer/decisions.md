# Решения по 910 infra-deployer

Этот файл хранит устойчивые решения, относящиеся только к `910 infra-deployer`.

## Bootstrap владеет объектом 910

`910` создаётся и восстанавливается публичным `bootstrap-pve.sh`.

OpenTofu внутри `910` не управляет собственным виртуальным объектом. Это исключает зависимость, при которой разворачиватель мог бы случайно изменить или уничтожить сам себя.

## 910 не входит в managed

`910` не включается в обычный пул управляемых гостей.

Его жизненный цикл отделён от обычных VM/LXC проекта.

## Нет root SSH на PVE

Штатное управление Proxmox выполняется через HTTPS API.

Постоянный root SSH с `910` на физический PVE не используется.

Если отдельному инструменту в будущем действительно понадобится SSH к PVE, для него проектируется отдельный ограниченный доступ.

## Отдельная PVE-идентичность

`910` использует:

```text
infra-deployer@pve!automation
```

Идентичность не должна иметь права менять пользователей, роли, ACL, собственный токен, сеть физического PVE или определения хранилищ.

## Semaphore Server и Runner разделены

Semaphore Server отвечает за интерфейс, задания, историю, расписания и секреты.

Semaphore Runner выполняет инфраструктурные задачи и содержит OpenTofu, Ansible, Packer и необходимые зависимости.

Это не даёт веб-сервису Semaphore лишних возможностей выполнения инфраструктурных команд.

## SQLite используется в первой версии

Для одного домашнего сервера отдельная PostgreSQL-база не требуется.

Semaphore начинает работу с SQLite. Переход на отдельную СУБД допускается только при появлении практической причины.

## OpenTofu state хранится локально

Первая версия использует локальное постоянное состояние внутри `910`.

State не хранится в Git, резервируется и изменяется только одним заданием одновременно.

Внешний backend может быть добавлен позже без изменения общей роли `910`.

## Одна Ansible SSH-идентичность

Для первой версии используется одна техническая SSH-идентичность Ansible для управляемых Linux-гостей.

Собственный реестр `<VMID>.pub` и `management-authorized-keys` на PVE не используется.

## GitHub Deploy Key находится в 910

Ключ чтения закрытого проекта создаётся и хранится внутри `910`.

PVE-хост не хранит этот закрытый ключ и не содержит постоянную закрытую Git-копию проекта.

## Критичные данные обязательно резервируются

К критичным относятся база Semaphore, ключ шифрования Semaphore, OpenTofu state и постоянные секреты.

Потеря OpenTofu state не должна приводить к автоматическому запуску `apply` с новым пустым состоянием поверх существующей инфраструктуры.
