# Стандарт файловой структуры сервисов

Этот документ фиксирует принятую для Linux VM проекта схему размещения программ, конфигурации, данных, логов, кэша и временных файлов.

Цель — не раскладывать файлы по каталогам ради формального соответствия Linux-стандартам, а отделять сущности с разным жизненным циклом: то, что можно заново развернуть из Git, то, что нужно обязательно сохранять, то, что можно удалить, и то, что существует только во время работы системы.

## Основное правило

Для типового сервиса используем следующую смысловую модель:

```text
/opt/<service>       → приложение, наш код, deploy и административные скрипты
/etc/<service>       → конфигурация
/var/lib/<service>   → внутреннее постоянное состояние приложения
/srv/<service>       → данные, которые сервис непосредственно предоставляет наружу
/var/log/<service>   → логи
/var/cache/<service> → пересоздаваемый кэш
/run/<service>       → runtime-файлы текущего запуска
/tmp                 → временные файлы
```

Это правило не означает, что каждый сервис обязан иметь все перечисленные каталоги. Создаются только реально необходимые каталоги.

## `/opt/<service>` — программа, код и deploy

`/opt` используем для нашего собственного кода, вручную устанавливаемых приложений, deploy-файлов и вспомогательных скриптов, которые не являются штатными пакетами Debian.

Пример:

```text
/opt/my-service/
├── app/
├── scripts/
├── deploy/
└── README.md
```

Главный признак: содержимое `/opt/<service>` должно быть возможно восстановить из Git, release-архива, пакета или другого источника поставки программы.

Поэтому удаление и повторное развёртывание `/opt/<service>` само по себе не должно приводить к потере важных рабочих данных.

### Что хранить в `/opt`

- наш код;
- собственные shell/Python-скрипты;
- deploy-обвязку;
- бинарники, устанавливаемые вручную вне пакетного менеджера;
- Docker Compose-файлы, если они относятся именно к deploy сервиса;
- административные инструменты проекта.

### Что не хранить в `/opt`, если данные критичны

- рабочие базы данных;
- большие persistent volumes;
- пользовательские файлы;
- секреты в открытом виде;
- логи, которые постоянно растут;
- кэш.

## `/etc/<service>` — конфигурация

`/etc` предназначен для конфигурации системы и сервисов.

Пример:

```text
/etc/my-service/
├── config.yaml
└── policy.conf
```

Конфигурация отделяется от программы потому, что программа может обновляться или переустанавливаться независимо от настроек.

Это особенно важно при восстановлении:

```text
программа → разворачивается заново
конфигурация → восстанавливается отдельно
```

Конфигурация обычно занимает мало места, но часто является критичной для быстрого восстановления сервиса.

Секреты, пароли, токены и приватные ключи не должны попадать в публичный Git даже если сами конфигурационные файлы версионируются.

## `/var/lib/<service>` — постоянное внутреннее состояние приложения

Несмотря на слово `lib`, `/var/lib` не является каталогом обычных программных библиотек. В Linux/FHS он используется для **изменяемого постоянного состояния приложений**.

Примеры штатных каталогов:

```text
/var/lib/postgresql/
/var/lib/docker/
/var/lib/prometheus/
```

Сюда относятся данные, которые приложение меняет во время работы и которые нужны ему после перезапуска:

- базы данных;
- индексы;
- очереди;
- metadata;
- внутренние state-файлы;
- реестры и служебные данные;
- persistent state сервиса.

Главный признак: пользователь обычно не работает с этими файлами напрямую, но без них сервис может потерять своё состояние.

`/var/lib/<service>` обычно относится к наиболее важным каталогам для файлового backup.

## `/srv/<service>` — данные, ради которых работает сервис

`/srv` используем для данных, которые сервер непосредственно предоставляет пользователям, клиентам или другим системам.

Примеры:

```text
/srv/files/
/srv/www/
/srv/media/
/srv/backups/
```

Разница между `/var/lib` и `/srv`:

```text
/var/lib → внутренние данные, нужные самому приложению
/srv     → содержимое, которое сервис обслуживает или предоставляет наружу
```

Пример файлового сервера:

```text
/opt/file-service/       → программа
/etc/file-service/       → конфигурация
/var/lib/file-service/   → база пользователей, индексы, metadata
/srv/files/              → реальные пользовательские файлы
```

`/srv` особенно удобно использовать, если большие данные позже потребуется вынести на отдельный диск или storage.

## `/var/log/<service>` — журналы

Здесь хранятся файловые логи сервиса, если сервис действительно пишет их в файлы.

Пример:

```text
/var/log/my-service/service.log
```

Логи отделены от данных потому, что у них другой жизненный цикл:

- они постоянно растут;
- для них применяется retention;
- старые записи можно сжимать и удалять;
- ими управляет `logrotate` либо journald;
- обычно их не требуется восстанавливать после аварии.

Если сервис пишет только в systemd journal, отдельный `/var/log/<service>` создавать не требуется.

## `/var/cache/<service>` — пересоздаваемый кэш

Кэш хранит данные, которые ускоряют работу, но могут быть пересозданы из исходных данных.

Пример:

```text
/var/cache/my-service/
```

Для кэша действует важное правило:

```text
потеря cache не должна означать потерю пользовательских данных
```

Поэтому `/var/cache` обычно не включается в backup.

## `/run/<service>` — runtime-состояние текущего запуска

`/run` предназначен для короткоживущих данных, существующих только пока работает система или сервис:

- PID-файлы;
- Unix sockets;
- lock-файлы;
- runtime metadata.

Пример:

```text
/run/my-service/my-service.sock
```

Содержимое `/run` не является persistent data и не восстанавливается из backup.

## `/tmp` и `/var/tmp` — временные файлы

`/tmp` используется для обычных временных файлов, которые не должны считаться постоянными.

`/var/tmp` также предназначен для временных данных, но традиционно может переживать перезагрузку дольше, чем `/tmp`. На конкретной системе политика очистки зависит от systemd/tmpfiles и настроек ОС.

Ни `/tmp`, ни `/var/tmp` не следует использовать как место хранения важных данных.

## Сводная таблица

| Каталог | Назначение | Можно пересоздать | Обычно backup |
|---|---|---|---|
| `/opt/<service>` | код, приложение, deploy, скрипты | да, из Git/release | обычно нет, если всё есть в Git |
| `/etc/<service>` | конфигурация | не всегда | да |
| `/var/lib/<service>` | внутреннее persistent state | обычно нет | да, при наличии важных данных |
| `/srv/<service>` | обслуживаемые файлы/контент | обычно нет | по ценности данных |
| `/var/log/<service>` | журналы | не требуется | обычно нет |
| `/var/cache/<service>` | кэш | да | нет |
| `/run/<service>` | runtime PID/socket/lock | да при запуске | нет |
| `/tmp`, `/var/tmp` | временные файлы | да | нет |

## Почему не хранить всё в одном каталоге

Хранить весь небольшой собственный сервис в одном каталоге технически можно. Разделение требуется не ради красоты, а когда разные части сервиса требуют разных действий.

Например:

```text
/opt/my-service      → можно удалить и заново получить из Git
/etc/my-service      → нужно сохранить настройки
/var/lib/my-service  → нельзя потерять рабочую базу
/var/log/my-service  → можно очищать по retention
/var/cache/my-service→ можно удалить без backup
```

Это даёт несколько преимуществ:

1. обновление приложения не затрагивает рабочие данные;
2. backup может сохранять только действительно важное;
3. логи и кэш можно очищать независимо;
4. для каталогов можно задавать разные права;
5. большие данные можно позже вынести на отдельный storage;
6. при аварийном восстановлении понятно, что взять из Git, а что вернуть из backup.

## Упрощённая схема для небольших собственных сервисов

Для маленького собственного сервиса допустимо начать с единого каталога:

```text
/opt/my-service/
├── app/
├── config/
├── data/
└── scripts/
```

Это удобно, пока сервис небольшой и его данные легко управляемы.

При росте сервиса данные выносятся по смыслу:

```text
/opt/my-service/data
        ↓
/var/lib/my-service
```

если это внутреннее состояние приложения, либо:

```text
/opt/my-service/files
        ↓
/srv/my-service
```

если это файлы, которые сервис предоставляет пользователям или сети.

Разделение следует делать, когда появляются разные требования к backup, объёму, storage, правам доступа, обновлению или retention.

## Политика для пакетных сервисов Debian

Для программ, установленных из Debian-пакетов или официальных сторонних пакетов, не нужно искусственно переносить их данные в нашу собственную структуру.

Используем штатные каталоги самого приложения, например:

```text
/var/lib/postgresql
/var/lib/docker
/etc/ssh
```

Это уменьшает количество нестандартных настроек и упрощает обновления, диагностику и использование документации производителя.

## Политика для VM-шаблона

Базовый `tpl-debian13` **не должен заранее создавать каталоги каждого будущего сервиса**.

В шаблоне фиксируется только стандарт размещения. Каталоги `/opt/<service>`, `/etc/<service>`, `/var/lib/<service>`, `/srv/<service>` и другие создаются при развёртывании конкретной роли VM.

Это сохраняет шаблон универсальным и не оставляет в нём пустые структуры для сервисов, которые конкретной машине никогда не понадобятся.

## Практическая схема восстановления

Для собственного сервиса аварийное восстановление должно по возможности сводиться к следующему:

```text
1. Развернуть чистую VM из шаблона.
2. Получить приложение/deploy из Git → /opt.
3. Восстановить конфигурацию → /etc.
4. Восстановить persistent state → /var/lib.
5. Восстановить обслуживаемые данные → /srv.
6. Запустить сервис.
7. Кэш, runtime-файлы и обычные логи создать заново.
```

Именно такое разделение позволяет не превращать полный образ VM в единственный способ восстановления каждого сервиса.
