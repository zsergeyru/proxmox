# Пользователи, SSH-ключи и простой backup секретов

Этот документ фиксирует базовую модель пользователей и SSH-ключей для VM, создаваемых из `tpl-debian13`.

## 1. Базовые пользователи шаблона

В базовом шаблоне не создаём большое количество заранее подготовленных пользователей.

### `root`

Системный superuser Debian.

Назначение:

- аварийное администрирование;
- локальная консоль через Proxmox;
- системные операции, для которых нужен полный root-доступ.

Правило:

- не использовать `root` как обычного SSH-пользователя;
- вход по SSH с паролем для `root` должен быть запрещён;
- основное администрирование выполнять через пользователя `ops` и `sudo`.

### `ops`

Основной административный пользователь для Linux VM.

Назначение:

- обычный вход по SSH;
- ручное администрирование;
- запуск административных команд через `sudo`;
- работа с Git, конфигами, логами и сервисами.

Планируемые группы:

```text
ops
sudo
adm
```

Не добавлять `ops` заранее в специальные группы вроде `docker`, `www-data`, `lxd`, `backup` и т. п. Такие права выдаются только на конкретной VM по необходимости.

## 2. Пользователи сервисов

Пользователи конкретных сервисов не создаются в базовом шаблоне.

Примеры:

```text
gitea
jenkins
prometheus
postgres
backup
deploy
```

Они создаются только на тех VM, где реально нужны соответствующие сервисы или роли.

Это позволяет не накапливать лишние аккаунты и не выдавать права заранее.

## 3. Cloud-Init и пользователь `ops`

Для рабочих VM пользователь `ops` должен настраиваться через Cloud-Init.

Cloud-Init передаёт новой VM первоначальные параметры, например:

```text
hostname
user
SSH public keys
IP / network configuration
```

В шаблон не вшиваются реальные пользовательские SSH-ключи.

Рекомендуемое значение:

```text
CIUSER=ops
```

Публичный SSH-ключ передаётся уже при создании конкретной VM.

## 4. Личные SSH-ключи

Личные SSH-ключи принадлежат устройствам, а не конкретным VM.

Пример:

```text
proxmox_ops_laptop
proxmox_ops_desktop
proxmox_ops_phone
```

Приватная часть хранится только на соответствующем устройстве:

```text
~/.ssh/proxmox_ops_laptop
```

Публичная часть:

```text
~/.ssh/proxmox_ops_laptop.pub
```

может передаваться через Cloud-Init и попадать на VM в:

```text
/home/ops/.ssh/authorized_keys
```

### Главное правило

Приватные личные SSH-ключи:

- не хранить в Git;
- не хранить в шаблоне VM;
- не хранить на Proxmox-хосте без отдельной необходимости;
- резервировать отдельно вместе с данными пользовательского устройства.

Публичные ключи не являются секретом и могут храниться в Git.

## 5. Технические SSH-ключи

Технические ключи принадлежат роли или сервису, а не человеку.

Примеры:

```text
deploy_ed25519
backup_ed25519
ci_ed25519
```

Не использовать один технический ключ для всех задач.

### Где хранить приватные технические ключи

Приватный технический ключ хранится на той VM или в том сервисе, который инициирует действие.

Примеры:

```text
/home/deploy/.ssh/id_ed25519
/home/backup/.ssh/id_ed25519
```

Для CI/CD по возможности использовать встроенное хранилище credentials/secrets соответствующей системы вместо обычного файла в репозитории.

### Права

Для файловых SSH-ключей:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
```

## 6. Публичные технические ключи

Публичные части технических ключей можно хранить в Git и раскладывать на нужные VM.

Пример структуры:

```text
ssh/
└── authorized_keys/
    ├── sergey-laptop.pub
    ├── deploy.pub
    └── backup.pub
```

На целевой VM публичный ключ обычно попадает в:

```text
/home/<user>/.ssh/authorized_keys
```

## 7. SSH host keys самой VM

SSH host keys VM — это отдельные ключи, которые идентифицируют сам сервер.

Они находятся в:

```text
/etc/ssh/ssh_host_ed25519_key
/etc/ssh/ssh_host_rsa_key
...
```

Эти ключи не должны копироваться одинаковыми во все VM.

Перед превращением машины в template host keys нужно удалить, чтобы каждый клон при первом запуске создал собственные уникальные ключи.

## 8. Простой backup технических ключей

На первом этапе не создаём отдельную инфраструктуру `secret backup`.

Если приватный технический ключ находится внутри VM, то при полном backup этой VM средствами Proxmox он попадает в backup автоматически.

Схема:

```text
VM
└── /home/deploy/.ssh/id_ed25519
        ↓
Proxmox backup
        ↓
полное восстановление VM вместе с ключом
```

Это считается достаточным базовым решением для проекта на текущем этапе.

### Следствие

Backup VM, содержащей приватные ключи, сам становится чувствительным объектом.

Поэтому:

- доступ к backup storage должен быть ограничен;
- backup не хранить в открытом публичном доступе;
- не копировать backup в Git;
- при возможности хранить backup на доверенном внешнем storage;
- при компрометации backup считать скомпрометированными и находившиеся внутри приватные ключи.

## 9. Что пока не вводим

На первом этапе не создаём:

- отдельный центральный secret-backup сервер;
- автоматический сбор приватных ключей со всех VM;
- Vault-подобную систему только ради SSH-ключей;
- общий технический private key для всей инфраструктуры.

Если количество VM, сервисов и секретов вырастет, к централизованному secret management можно вернуться отдельно.

## 10. Итоговая модель

```text
Личный ноутбук
└── private key пользователя
        ↓ public key

VM
└── /home/ops/.ssh/authorized_keys

Управляющая / deploy VM
└── private deploy key
        ↓ public key

Целевые VM
└── authorized_keys для технической роли

Proxmox backup
└── полная копия VM, включая находящиеся внутри технические private keys
```

Основные правила:

1. `root` — аварийный/system account, не основной SSH-пользователь.
2. `ops` — основной административный пользователь.
3. Пользователи сервисов создаются только по необходимости.
4. Личные ключи создаются отдельно для каждого устройства.
5. Технические ключи создаются отдельно по ролям.
6. Private keys никогда не хранятся в Git.
7. Public keys можно хранить в Git.
8. Технические private keys на первом этапе резервируются вместе с полной VM через Proxmox backup.
