# Политика сборки и базовой настройки `tpl-debian13`

Этот документ фиксирует согласованные решения перед финальной реализацией скрипта создания базового Debian 13 template для Proxmox.

## 1. Главный принцип: Proxmox-хост остаётся чистым

На Proxmox-хост **не устанавливаем `virt-customize`, `libguestfs-tools` и другие build-инструменты**, которые нужны только для подготовки гостевой ОС.

Proxmox должен оставаться гипервизором и содержать только компоненты, необходимые для PVE и обслуживания самого хоста.

Сборка шаблона выполняется через временную VM:

```text
Debian 13 genericcloud image
        ↓
временная builder-VM в Proxmox
        ↓
Cloud-Init первого запуска
        ↓
apt update / upgrade
установка базовых пакетов
настройка ОС
очистка machine-specific данных
        ↓
shutdown
        ↓
преобразование этой VM в tpl-debian13
```

После успешной подготовки отдельная builder-VM не сохраняется как самостоятельная рабочая машина: подготовленная VM становится template.

## 2. Что разрешено использовать на Proxmox-хосте

Скрипт создания template должен опираться прежде всего на штатные средства Proxmox и базовой Debian-системы хоста:

- `qm`;
- `pvesm`;
- Cloud-Init support Proxmox;
- стандартные средства скачивания и проверки образа, уже доступные на хосте;
- штатные операции импорта диска и управления VM.

Если для новой реализации потребуется дополнительный пакет на PVE-хосте, это считается отдельным архитектурным решением и не должно происходить автоматически и незаметно.

## 3. Базовый пользователь

Основной административный пользователь рабочих Linux VM:

```text
ops
```

`ops` используется для:

- SSH-входа;
- ручного администрирования;
- `sudo`;
- работы с Git, конфигурацией и логами.

Планируемые группы:

```text
ops
sudo
adm
```

Специальные группы (`docker`, `www-data`, `backup` и т. п.) добавляются только на конкретных VM по необходимости.

## 4. Root

Учётная запись `root` как системная часть Debian **не удаляется**.

Но удалённый SSH-login для `root` полностью запрещается:

```text
PermitRootLogin no
```

Аварийный root-доступ остаётся через консоль VM в Proxmox.

Обычное администрирование выполняется:

```text
SSH → ops → sudo
```

## 5. SSH-политика

Целевая политика:

```text
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
```

Парольный SSH-вход не используется.

Публичные ключи пользователя `ops` передаются конкретной VM через Cloud-Init. Реальные private keys в template не вшиваются.

Подробная модель ключей описана в [`users-and-keys.md`](./users-and-keys.md).

## 6. Cloud-Init

Cloud-Init используется только для первоначальной персонализации VM и bootstrap-подготовки template.

Для рабочих клонов через Cloud-Init задаются:

- hostname;
- пользователь `ops`;
- SSH public keys;
- IP/network configuration;
- при необходимости DNS и другие параметры первого запуска.

Cloud-Init не должен превращаться в огромную систему конфигурационного управления конкретными сервисами. SmartDNS, Docker, Gitea, monitoring и другие роли устанавливаются отдельными deploy/Ansible/script механизмами после клонирования.

## 7. Временная зона

Для всех VM из базового template используется:

```text
Europe/Moscow
```

Это осознанное решение проекта. Системное время синхронизируется штатными средствами Linux.

## 8. Локаль

Основная системная локаль:

```text
en_US.UTF-8
```

Она выбрана для предсказуемых логов, команд, скриптов и совместимости серверного ПО.

Русская локаль может быть дополнительно установлена при необходимости, но не должна менять базовую server locale без отдельного решения.

## 9. Обновление системы при сборке

При создании нового template выполняется актуализация пакетов Debian:

```text
apt update
apt full-upgrade
```

После этого устанавливается согласованный базовый набор утилит.

Цель: каждый заново собранный template должен быть актуальным на дату сборки.

## 10. Автоматические обновления

`unattended-upgrades` в базовом template автоматически не включаем.

Обновление VM должно выполняться контролируемо. Централизованную политику обновления можно ввести позднее через Ansible или другой механизм управления.

## 11. Синхронизация времени

Используется штатный механизм Debian/systemd.

При сборке template необходимо убедиться, что синхронизация времени включена и работает. Отдельный сторонний NTP-клиент без необходимости не устанавливаем.

## 12. Swap

В базовом template отдельный swap-раздел или swap-файл **не создаём**.

Причины:

- потребности VM различаются;
- Proxmox управляет RAM VM централизованно;
- swap при необходимости можно добавить конкретной VM;
- template остаётся проще и универсальнее.

## 13. Виртуальный диск

Базовые решения:

```text
Controller: VirtIO SCSI Single
iothread:   enabled
discard:    enabled
```

`discard` нужен для TRIM/возврата освобождённых блоков underlying storage, если storage это поддерживает.

`iothread` используется для более эффективной обработки I/O виртуального диска.

Для SSD-backed storage допускается/предпочтительно выставлять SSD emulation (`ssd=1`), если это соответствует фактическому storage.

Размер системного диска по умолчанию:

```text
16 GiB
```

После клонирования диск можно увеличить под конкретную роль.

## 14. QEMU Guest Agent

`qemu-guest-agent` обязательно входит в template.

Внутри Debian сервис должен быть установлен и включён, а в конфигурации VM Proxmox должна быть включена поддержка guest agent.

Он используется для:

- корректного shutdown;
- получения информации о гостевой системе;
- IP-информации;
- freeze/thaw файловой системы при поддерживаемых операциях backup.

## 15. Serial console

Template должен иметь рабочую serial console, доступную из Proxmox даже при неработающей сети.

Планируемая конфигурация Proxmox:

```text
serial0
vga: serial0
```

Это важный аварийный канал управления VM.

## 16. Очистка перед превращением в template

Перед финальным shutdown и `qm template` необходимо очистить machine-specific и временные данные, которые не должны клонироваться во все VM.

Минимальный перечень:

- Cloud-Init state;
- `/etc/machine-id` по корректной для Debian/cloud-init процедуре;
- SSH host keys;
- DHCP lease/state, если они созданы;
- APT cache;
- временные файлы;
- лишние installer/build artifacts;
- историю первоначальной builder-сессии, если она содержит ненужные данные;
- journal/logs, которые относятся только к процессу сборки template.

При первом запуске клона должны сформироваться собственные machine-id и SSH host keys.

## 17. Shell history

Для административных пользователей полезно включить timestamp команд и увеличить разумный размер истории.

Это общая удобная настройка template и может быть реализована через `/etc/profile.d/`, без персональных пользовательских файлов.

История не должна использоваться как место хранения секретов. Команды с паролями/токенами в открытом виде вводить нежелательно.

## 18. MOTD

Template получает короткий нейтральный MOTD, например:

```text
Managed VM
Base template: tpl-debian13
Infrastructure: zsergeyru/proxmox
Do not store secrets in Git.
```

MOTD нужен как напоминание о происхождении VM и правилах управления, но не должен содержать секреты или динамические данные конкретной VM.

## 19. Информация о происхождении template

В template создаётся файл:

```text
/etc/vm-template-info
```

Минимальное содержимое:

```text
Template: tpl-debian13
Template-Version: 1
OS: Debian 13
Source: zsergeyru/proxmox
Build-Date: <дата фактической сборки>
```

Файл нужен для диагностики: внутри любой клонированной VM можно быстро понять, из какого поколения template она создана.

## 20. Версионирование

Вводится простое внутреннее версионирование template:

```text
Template-Version: 1
```

Версию повышаем, когда меняется значимая базовая политика или состав образа так, что полезно различать поколения VM.

Номер версии не обязан совпадать с версией Debian.

## 21. Структура файлов сервисов

Template не создаёт заранее каталоги будущих сервисов.

Правила `/opt`, `/etc`, `/var/lib`, `/srv`, `/var/log`, `/var/cache`, `/run` и `/tmp` описаны отдельно в [`filesystem-layout.md`](./filesystem-layout.md).

Каталоги конкретного сервиса создаются только при его развёртывании.

## 22. Backup

На первом этапе backup остаётся простым:

- полные VM backup средствами Proxmox;
- `restic`/`rsync` доступны для отдельных файловых сценариев, но не заменяют backup VM;
- отдельный secret-backup пока не создаётся;
- технические private SSH keys, находящиеся внутри VM, попадают в полный backup этой VM.

Backup, содержащий private keys и другие секреты, считается чувствительным объектом и хранится только на доверенном storage.

## 23. Что не входит в base template

Не устанавливаем заранее:

- Docker Engine / Docker Compose;
- SmartDNS;
- AdGuard Home;
- `sing-box`;
- AmneziaWG и другие VPN;
- специальные `nftables`/policy-routing правила;
- Gitea;
- Jenkins;
- базы данных;
- reverse proxy;
- пользователей и каталоги прикладных сервисов.

Это добавляется по роли конкретной VM.

## 24. Требование к финальному скрипту

Финальная версия `create-template.sh` должна соответствовать этому документу.

Особенно важно:

1. не использовать `virt-customize`;
2. не устанавливать `libguestfs-tools` на Proxmox;
3. выполнять подготовку Debian внутри временной VM;
4. не хранить в template реальные private keys, пароли и токены;
5. после успешной подготовки преобразовывать VM в `tpl-debian13`;
6. при любой неоднозначной/опасной ситуации останавливаться, а не удалять существующие VM или storage автоматически.
